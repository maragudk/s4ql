The storage code, under faults

Built from a commit that is not known for this build. The code is internal/core, run by internal/simulator.

The storage code of s4ql runs in this page: the Go code itself, unchanged, compiled to WebAssembly, with its cache on the official SQLite WebAssembly build. S3 and time are simulated.

s4ql is built for one long-running instance per database. Here that instance holds the lease and serves a stream of reads and writes, and a second instance stands by to take over when it fails. Add a fault, and watch what the code does.

Things to try

  • Crash the instance with the lease, or cut it off from S3. Once its lease has run out, the other instance takes it over and catches up from the log in S3.
  • Stop the monotonic clock of the instance with the lease, and start it again a minute later. Its timers stop with the clock, so the other instance takes the lease over. When the clock runs again, it refuses calls and learns that it lost the lease.
  • Make S3 unreachable. The instance with the lease refuses calls once its lease runs out, and asks S3 how its last renewal went when S3 is back.
  • Lose the answer to the next commit. S3 has the commit, and the instance cannot tell. Watch it find out before it acknowledges the write.
