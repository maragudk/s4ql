The storage code, under faults

This page runs the storage code of s4ql in your browser. Instances of one database share a bucket in S3. They write, read, and take turns with the lease while you crash them, cut them off from S3, stop and shift their clocks, and lose answers from S3.

It is the Go code itself, unchanged, compiled to WebAssembly. Its cache runs on the official SQLite WebAssembly build. S3 and time are simulated, and one seed decides every random choice, so a run is the same each time.

The engine runs a whole run at once, in a Worker, and the page plays it back. When you add a fault at the current time, the page asks the engine for the run again with the fault in its schedule. Everything before that time stays the same, so the run goes on from where it was. A checker in the engine watches six invariants.

The seed, the settings, and every fault you add are kept in the link, so you can share a run and anyone who opens it gets the same run.

Things to try

  1. Watch the default run. b takes the lease and commits until it crashes at 0:40. Once b's lease has run out, another instance takes it over and starts to catch up from the log in S3.
  2. Pause, arm "Lose its answer" for the next commit under "Faults and actions", and write on the instance that holds the lease. S3 handles the swap, but its answer never arrives, so the core does not know whether its commit went through. It asks S3 again until it knows.
  3. Cut the writer off from S3 for 40 s. It stops serving once its lease runs out by its own clocks, and another instance takes over.
  4. Stop the monotonic clock of the writer and shift its wall clock back. By its own clocks, its lease then lasts too long. The design accepts that a read on it may miss a commit, and the checker excuses such a read. The checker still requires that no acknowledged write is lost.
  5. Switch on buggify under Settings and try new seeds. Marked points of the core then do legal but unusual things.

Instances

Each instance is a process with its cache, a wall clock, and a monotonic clock. The one that holds the lease and is caught up serves. A restart starts a new process of the instance, such as b2, on a copy of the cache.

The instances appear once the engine has run.

Faults and actions

Each one happens just after the current time. Faults of one instance are on its card under "Instances". These act on S3, the network, and the workload.

S3 and the network

"For" is how long an outage or a cut-off lasts. Calm switches off the random faults of S3 for the rest of the run. What a fault has started goes on to its end.

The next request

An armed fault waits for the first request that matches. When the answer is lost, S3 has handled the request, and the caller cannot tell.

Workload

Each instance runs callers, as an application would: 2 callers, each pausing up to 5 s between calls, 40% writes. A write inserts one row with a key of its own, so the keys tell the transactions apart.

The bucket

S3 is strongly consistent. The manifest is replaced only by a compare-and-swap on its version. A commit object is created only if nothing is at its key, under its SHA-256. The log runs from the head of the manifest back through each parent.

            What the page simulates, and what it leaves out

            The code
            The storage core, internal/core, unchanged, through its exported API. The engine around it, internal/simulator, starts the instances, runs the workload and your schedule, and records what happens. Its tests check that a request gives the same run natively and in Chromium.
            SQLite
            The cache of each instance is a SQLite database on the official SQLite WebAssembly build, in memory in the Worker. The tests of the core run on SQLite compiled with cgo.
            S3
            A simulated store, the one the tests of the core run against, with every fault set here. Each way of a request takes from 0 to the latency. A conformance suite checks the simulated store against a real S3-compatible bucket.
            Time
            Fake time of the scheduler of the simulation. A clock can be shifted, stopped, and started again, but it never runs faster or slower than true time.
            The workload
            One table t with one integer key. A write inserts one row in one transaction, and a read reads every row. s4ql's own SQL is not part of the storage core, and not part of a run.
            Random faults
            Only S3 and the network fault at random. Faults of processes, clocks, and single requests come only from your schedule.
            Not here
            Faults of the local disk, which the tests of the core reach and this page cannot. Snapshots and garbage collection, which are not in the design yet. Planted bugs: the page shows the code as it is.
