# SQLite binding

`internal/sqlite` is the project's own small cgo binding to the official SQLite C code. The cache and the oracle use it.

The binding covers only what slice 1 of [docs/roadmap.md](../../docs/roadmap.md) and the cache of the storage core in `internal/core` need:

- open and close a database, in a file or `:memory:`
- prepare one statement
- bind and read 64-bit integers and text, and bind NULL
- read the column count, the column names, and the type of each value
- step, reset, and finalize
- run a statement with `Exec`
- return errors with SQLite's extended result code and message

It also reports the SQLite version, the source ID, the compile options, and the keywords. `Tokenize` splits SQL text with SQLite's private tokenizer `sqlite3GetToken`, which no public API exposes, so that the Go tokenizer in `internal/sql/token` can be checked against it. It is a wrapper in the binding's translation unit and not a second compile of SQLite: production builds then carry no second copy, and the build cache tracks the vendored source through `source.h` as it does for the rest of the binding. More is added when a slice needs it.

The vendored version is SQLite 3.54.1, from https://sqlite.org/2026/sqlite-amalgamation-3540100.zip.

## Why our own binding

The oracle is then the real C code and not a translation of it, the project chooses the SQLite version and the compile options and updates on its own terms, and no third-party code sits between the engine and SQLite. `modernc.org/sqlite` was considered first and dropped for these reasons.

The API fits the engine, not `database/sql`, and stays small. It can change shape when the engine needs it to, for example to return several rows per call into C.

## Compile options

`options.h` holds the compile options, each with its reason, and the options that were considered and left out. Every option is a way in which this build differs from a stock build of SQLite, so an option is added only for a reason that `options.h` states, never for performance alone. The research behind the choice, which covers every option on https://sqlite.org/compile.html, is in [docs/research/sqlite-compile-options.md](../../docs/research/sqlite-compile-options.md).

`SQLITE_MAX_MMAP_SIZE=0` covers the database file only. In WAL mode SQLite memory-maps the wal-index (`-shm`) file in any case, so an I/O error there can still arrive as a signal. This is an open point in [docs/todo.md](../../docs/todo.md#the-memory-mapped-wal-index).

## Requirements

- cgo and a C compiler (clang or gcc)
- Docker, for `make test-asan` on macOS

## Layout

- `c/` holds the vendored amalgamation, unmodified: `sqlite3.c`, `sqlite3.h`, `sqlite3ext.h`, and `shell.c`. It also holds `c/source.json`, which records the download URL, size, SHA3-256 (as published on sqlite.org), and SHA-256 of the zip, and the SHA-256 of each vendored file.
- `options.h` holds the compile options, described below. Both the binding and the C programs that the tests build use it.
- `source.h` is generated by the update tool and holds the version and the SHA-256 of each vendored file. The go command rebuilds a package only when a file in its own directory changes, not one in `c/`, so this header is what makes an update of `c/` rebuild the binding.
- `sqlite.go` is the binding. All C calls are in this one file. `asan.go` and `noasan.go` tell it whether it is built with `-asan`.
- `update/` is the tool that vendors and verifies the amalgamation.
- `crosscheck/` is a separate Go module with the tests against `github.com/mattn/go-sqlite3`.

## Symbols

`sqlite.go` includes the amalgamation into its cgo preamble with `SQLITE_API` defined as `static`, so all of SQLite's symbols are local to that translation unit. Another copy of SQLite, such as mattn's, can therefore be linked into the same test binary. Without the `static`, the link fails with 271 duplicate symbols.

`TestSymbols` checks that no SQLite symbol is global, and the cross-check module links only if this holds.

Two rules follow:

- Every C call must stay in `sqlite.go`.
- `sqlite.go` must not use `//export`, which would copy the preamble into a second translation unit.

## Tests

`make test` runs the tests of the main module and of the cross-check module. They compare the binding with two references that run the same C code, so that any difference is a bug in the glue and not in SQLite.

The first reference is the official `sqlite3` shell. The tests build it from `c/shell.c` and `c/sqlite3.c` with `options.h` and the C compiler from `go env CC`. They check that the shell reports the same version, the same source ID, and exactly the same compile options as the binding, and that it gives the same results and error messages for slice-1 statements.

The tests also build `testdata/subtype.c` against the same compiled SQLite, to show the effect of `SQLITE_STRICT_SUBTYPE`, which only C code can see.

The second reference is `github.com/mattn/go-sqlite3`, for what the shell cannot exercise: parameter binding, typed column access, and statement reuse. The cross-check module checks that:

- mattn's bundled C code is identical to `c/sqlite3.c`, apart from mattn's `#ifndef USE_LIBSQLITE3` wrapper
- the versions and the source IDs match
- both bindings give the same rows and errors for slice-1 scripts, also in a differential fuzz test

mattn builds the same C code with other compile options. The differences that SQL can see are listed in `TestCompileOptions` in `crosscheck/`, and the comparisons avoid them: mattn does not enforce foreign keys on a new connection, accepts double-quoted strings, lacks the math functions unless it is built with the `sqlite_math_functions` tag, and lets `PRAGMA mmap_size` switch on memory-mapped I/O.

## Memory safety

The binding is memory-unsafe code, which Go's race detector and memory safety do not cover. `make test-asan` runs all tests, and then each fuzz test, under the C address sanitizer with `go test -asan`. Each fuzz test runs for `FUZZTIME`, which defaults to 30s. Go supports `-asan` only on Linux, so on macOS the target runs itself in a `golang` Docker container.

SQLite's lookaside allocator reuses memory inside its own slabs, where the sanitizer cannot see it, so a statement used after it is finalized would go unnoticed. A binary built with `-asan` therefore turns lookaside off on every connection it opens. Other builds keep it on.

`make fuzz` runs the fuzz tests without the sanitizer. On Linux, `FUZZFLAGS=-asan` adds it. Go's fuzzer measures coverage of Go code only, so for the C code the fuzzing is close to random mutation of the seeds.

CI runs `make test-asan FUZZTIME=30s`.

## Updating SQLite

Run these steps from the repository root:

1. Run `make sqlite-update VERSION=x.y.z`. It reads the URL and the SHA3-256 from the PRODUCT lines on https://sqlite.org/download.html, downloads the zip, checks its size and SHA3-256, writes the files into `c/`, and rewrites `c/source.json` and `source.h`.
2. Bump `github.com/mattn/go-sqlite3` in `crosscheck/go.mod` to a release that bundles the same SQLite version. The cross-check tests fail until the versions and the C source match.
3. Run `make test`, `make test-asan`, and `make lint`.

SQLite upgrades wait for mattn: the cross-check fails unless mattn bundles exactly the vendored version, so the project moves to a new SQLite only once a mattn release bundles it. This is deliberate, because the check guards against drift between the two references. The project pins SQLite on its own terms and does not chase releases. The one exception is an urgent SQLite fix that arrives before mattn has it: for that upgrade only, the version and source checks against mattn are skipped on purpose, and restored when mattn catches up.

For a version that is no longer on the download page, replace step 1 with:

```sh
go run ./internal/sqlite/update -version x.y.z -url URL -sha3 HASH
```

`make sqlite-verify` checks that the URL in `c/source.json` is the amalgamation of the recorded version on sqlite.org, and, while the version is on the download page, that the recorded size and SHA3-256 match it. It then downloads the zip again, checks it against `c/source.json`, compares every vendored file with it byte for byte, and checks `source.h`. CI runs it only on changes to `c/`, `source.h`, or `update/`, so that CI does not fail whenever sqlite.org is down.
