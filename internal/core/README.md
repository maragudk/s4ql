# Storage core

`internal/core` is the storage core of s4ql. A `DB` is one instance of one database: a cache in SQLite, a lease in the manifest, and commits through a manifest swap. `Open` does not wait for the lease, and `DB.Wait` does. `DB.Begin` gives a write transaction, a `Tx`. `DB.Reader` opens a `Reader`, a read connection to the cache that its owner closes, and `Reader.Read` gives a read transaction, a `ReadTx`. The package starts one goroutine, `DB.leaseLoop`.

What the package does in each case is in the code:

- the package comment and the doc comments of `Options` and `DB` in `core.go`
- the doc comments of `Tx.Commit` and of `Tx.spoolCommit`, with the net effect of a transaction, in `tx.go`
- the doc comments of `Reader`, `DB.Reader`, `Reader.Read`, and `Reader.Close` in `read.go`, with the check of the lease before a read
- the doc comments of `IndexScan`, `Tx.CreateIndex`, `table.scanSQL`, and `conn.loadIndexes` in `index.go`, for the indexes and a scan by one
- the doc comments of `DB.acquire`, `DB.resumeLocked`, `DB.renewLocked`, `DB.observe`, and `flight` in `lease.go`, and of `margin` in `core.go`, for the lease and for a swap whose outcome is unknown
- the doc comments of `DB.catchUp` and `DB.fetch` in `catchup.go`, and of `replay` in `replay.go`
- the errors and the doc comment of `classify` in `errors.go`
- the names of the events and of their attributes in `telemetry.go`
- the planted bugs in `bugs.go`

This file holds the reasons behind the design, what was chosen and what was rejected, what was measured, and what the package cannot do. The rules that the package follows are in [docs/spec.md](../../docs/spec.md) under "Concurrency" and "Constraints", and this file does not repeat them. Until the core was built, the reasoning behind those rules was in four items of [docs/todo.md](../../docs/todo.md). That reasoning is now here, with Markus's words and their dates. What is still open or not built is in the todo, under [The storage core](../../docs/todo/storage-core.md) and [Tests of the storage core](../../docs/todo/storage-core-tests.md).

The core was built on 2026-11-12 and 2026-11-13, and merged in pull request #12. It is the first code that uses the simulation harness ([internal/sim/README.md](../sim/README.md)), the storage formats ([internal/format/README.md](../format/README.md)), and the object store in `internal/store` together. The diary is [2026-11-12-storage-core.md](../../docs/diary/2026-11-12-storage-core.md).

## The interface

The future SQL engine is the only user of the package, and the interface is made for it.

- **Every call that can fail takes a context.** A call that waits ends when its context ends, and a call logs its events with its context.
- **A table is an `s4qlpb.CreateTable`, and a value is an `s4qlpb.Value`.** They are the messages of the commit object, so nothing is converted between the engine and the log.
- **An index is an `s4qlpb.CreateIndex`, as a table is an `s4qlpb.CreateTable`.** `Tx.CreateIndex` and `Tx.DropIndex` create and drop one inside a transaction, and a rollback and the statement savepoint undo them as they undo the create and the drop of a table. `Indexes` on `Tx` and `ReadTx` lists the indexes of a table in the order in which they were created, which is the same on every instance and after replay, and the engine breaks ties by it. `Index` gives one index by its name. Indexes came with slice 9 of the [roadmap](../../docs/roadmap.md#slice-9-indexes), on 2026-11-20. Markus agreed that day that the log holds only the definition of an index, that the cache holds a real index of SQLite, and that the engine picks the index and the core scans exactly that one. What the agreement left open, the builder of the core step decided the same day, by SQLite's behaviour and the agreed rules.
- **A scan is an `iter.Seq2`.** It runs on the goroutine of the caller, so a scan starts no goroutine.
- **A scan can be bounded by the key.** `ReadTx.ScanRange` and `Tx.ScanRange` give the rows of a table whose primary key is one column, from a lower to an upper `Bound`, each closed, open, or none, in the order of the key; `Scan` is the scan without bounds. The cache seeks the bounds in its index of the primary key, with SQLite's comparison, so a scan that is bounded reads no more of the table than its bounds hold. A bound is checked as the key of `Get` is (`table.checkBounds`). It came with slice 7 of the roadmap, on 2026-11-20, and `TestScanRange` compares every pair of bounds of the edges of each type with a filter of the full scan.
- **A scan can go by an index.** `ReadTx.ScanIndex` and `Tx.ScanIndex` take an `IndexScan`: `Index` names the index, and no name means the primary key; `Equal` pins the leading columns of the key to values; `Lower` and `Upper` bound the column after those; `Backward` reverses the order; and `Order` has the cache sort the rows, as the bullets below say. The key of an index is its columns and then the primary-key columns that it does not hold, as SQLite stores an index of a table without a rowid, so `Equal` and the bounds can reach into those. The bounds are stated as values: `Lower` is the smallest value and `Upper` the largest, also on a column that the index holds in descending order, and SQLite turns them into the ends of the range, because the statement compares values (`scanConditions`). A NULL in `Equal` pins a column to NULL. A bound that is NULL is refused with `ErrInvalid`, as is a NULL in `Equal` for a column that does not take it, and a row whose bounded column is NULL is within no bound, as in SQL. NULL sorts first in an ascending column and last in a descending one, as SQLite orders it. It came with slice 9 of the roadmap, on 2026-11-20.
- **SQLite never picks the index of a scan.** The statement of every scan names its index with `indexed by` (`table.scanSQL`). `not indexed` does nothing on a table without a rowid, so to read the table itself the statement names SQLite's index of the primary key, `sqlite_autoindex_<table>_1`, whose name the core reads from `pragma_index_list`. SQLite gives no error for an `indexed by` that its conditions cannot use, and scans the whole index, so the statement's only conditions are those of the scan, on a prefix of the key, and SQLite seeks all of them. Both facts of SQLite are in [research/index-selection.md](../../docs/research/index-selection.md). `Scan`, `ScanRange`, and the scan of a commit use the same statement. The statement orders by the columns of the key that the scan does not pin, in the order in which SQLite reads the index, so SQLite sorts nothing. SQLite compares at most 63 terms of an `order by` with an index, so a scan with more than 63 such columns reads the same rows by the same index and then sorts them, which `TestScanIndex` pins. Such a scan reads every row within its bounds before it gives the first, so a loop that stops early has still read them all, and `RowsRead` counts only the rows that the loop stepped to.
- **A scan can sort its rows.** `IndexScan.Order` is a list of `KeyColumn`, each the position of a column of the table and whether it is descending. If it is not empty, the scan reads the same rows, and the cache sorts them: by the first column of `Order`, and among rows that are equal in it by the next, as SQLite orders the values of a column, with NULL before every value in an ascending column and after every value in a descending one. Rows that are equal in every column of `Order` come in the order of the primary key, or in its reverse if `Backward`, so the order of the rows is total. For a scan with `Order`, that is all that `Backward` does. `table.checkScan` refuses a column of `Order` that the table does not have, and an `Order` of more columns than the table has, with `ErrInvalid`. It came with slice 13 of the roadmap, on 2026-11-21, and `TestScanIndex_order` pins it.
- **SQLite sorts every row of such a scan in one sort.** The statement of a scan with `Order` orders by the terms of `table.sortTerms` and not by its key: each column of `Order` after a unary plus, in its direction, and then the columns of the primary key that `Order` does not name, ascending, or descending for a scan backward. A column after a unary plus is no column of an index to SQLite. So SQLite sorts every row within `Equal` and the bounds in one sort, also where the index holds the rows in the order of some or all of the terms, and reads them all before it gives the first. Without the plus, SQLite uses the order of the index where it can: for an `order by` whose first terms the index delivers, it sorts only within groups and reads lazily, and what a loop that stops early has read then depends on where it stops. With the plus, SQLite's plan for the statement has exactly one `USE TEMP B-TREE FOR ORDER BY`, whatever the index, and what the scan reads does not depend on how much of it is consumed. The plus changes neither a value nor, in a table whose columns have no collation, the order of the values. The tie-break leaves out the primary-key columns that `Order` names, so the statement has no more terms than the table has columns.
- **The statement selects each column of `Order` as its ordering term** (`table.sortColumns`): `+"c"` in place of `"c"`, which has the value of the column. SQLite keeps a selected column that is also a term of the ORDER BY once in the record that it sorts. With `select *` it kept the value twice, and refused the record as `string or blob too big` where the two were longer than the length limit of the connection, for a row that the table holds: a review found it. A real that holds an integer is still longer in what SQLite sorts than in the table, which keeps it as an integer, so the step in which SQLite sorts runs under SQLite's largest length limit (`conn.step`), and the limit of the connection is put back after it. `TestScanIndex_order` sorts the longest row that a table takes under a limit of 1,000 bytes by each of its columns.
- **A scan by the primary key that pins the whole key is not sorted,** with `Order` or without. It reads one row at most, SQLite knows that, and its plan has no sort. A scan by an index that pins its whole key is sorted as every other.
- **The sorted rows live in SQLite, outside the memory of Go.** SQLite's sorter holds the rows in memory up to the size of its page cache, 2 MB, and then writes them to temporary files and merges them. The cache sets no `temp_store`, and the pinned build has `SQLITE_TEMP_STORE` at its default, so the temporary files are files, which SQLite opens through the VFS of the connection. So a scan of any number of rows holds one row at a time in Go, as every other scan does. SQLite sorts whole rows. [The todo on performance](../../docs/todo/performance.md) has the ways to make a sort hold less, which are not built.
- **`RowsRead` counts the rows that the cache gave a transaction,** on `Tx` and `ReadTx`: one for each row that a scan stepped to, and one for each row that a get found, so that a test can pin how many rows a query reads. The statement of a scan has no condition but its bounds, and SQLite seeks all of them, so the rows that a scan stepped to are the rows within its bounds. The core counts the steps and does not ask SQLite: the build has no `SQLITE_ENABLE_STMT_SCANSTATUS`, and the binding has no call for `sqlite3_stmt_status`.
- **Of a scan with `Order`, `RowsRead` counts every row that the sort read,** which is every row within the bounds of the scan, however early the loop over it stops. Such a scan has read them all when it gives its first row. When the loop stops early, the core counts the rows of the scan with a second statement, a count of the first column of the primary key by the same conditions on the same index, in the same transaction (`table.countSQL`), and adds those that the scan did not give (`conn.unread`). It is not `count(*)`: SQLite runs a `count(*)` without conditions in one instruction that reads the whole table, which the progress handler below cannot stop, and a count of a column, which no row has NULL in, as a loop that it stops. SQLite does not say how many rows its sorter holds, and to step through the rest would cost a call into SQLite for each row that nothing reads. To count only the rows given would make a sort of every row of a table look like one row read. The scans of `ReadTx` and `Tx` make the count once their loop has ended and the statement of the scan is at rest. A count that fails adds no rows, and no caller is left to take its error, so the error goes where a failure of the scan goes: to `DB.cacheError` in a read, which stops the instance for a local failure, and to `Tx.fail` in a write. `TestScanIndex_context` fails the count with rows larger than the page cache, so that the count reads pages again, and a fault of the VFS on reads reaches it. A scan that SQLite sorts because its key has more than 63 columns that it does not pin keeps counting only the rows stepped to, as before. The count is not made after the context has ended, or when the loop ends by a panic, and a count that the end of the context stops adds no rows: `RowsRead` then has the rows that the loop stepped to.
- **SQLite stops the sort of a scan, and the count, when the context ends.** The first step of a scan, in which SQLite sorts the rows of a scan that sorts, and the steps of the count run with `sqlite.Stmt.StepContext`, whose progress handler looks at the context every 10,000 instructions of SQLite's virtual machine (`conn.step`, `conn.queryContext`). So a scan whose context ends during its sort ends with the error of the context after work that does not grow with the table; before, it ended only after the sort. Each later step reads one row and runs to its end, as does every statement that writes, which SQLite would roll back with its whole transaction if it were stopped. SQLite rolls nothing back for a read that it stops, so the error of the context from a scan or a count does not fail a write transaction (`ended`), and its writes stay. A step that SQLite stops while the context has not ended would be a fault, and goes where any other error of SQLite goes. The handler calls Go, and does not read a flag that another goroutine sets, because no goroutine may watch the context: the simulation runs one goroutine at a time, and `internal/simlint` forbids `context.AfterFunc` in library code. The scan of a commit runs to its end whatever the context.
- **The names of tables are compared as SQLite compares them:** ASCII letters without regard to case, and every other character exactly (`fold`). The cache is SQLite, and the oracle is SQLite. A table keeps the spelling of its create.
- **The errors of `Tx.CreateIndex` come in SQLite's order:** `ErrNoTable`, `ErrReservedName`, `ErrTableExists` if a table has the name, `ErrIndexExists`, and then `ErrInvalid`. A table and an index share their names, so `Tx.CreateTable` under the name of an index fails with `ErrIndexExists`. `Tx.DropIndex` fails with `ErrNoIndex` for anything that is no index of the database, a table and SQLite's index of a primary key among them. After each of these errors the transaction goes on. The core takes the columns of an index as positions, so SQLite's `no such column` is the engine's to give.
- **A primary key has at most 250 columns.** A row is found by a condition with a term for each column of its key, and SQLite refuses a condition that is nested deeper than a thousand levels, which about 500 terms are. SQLite itself allows a key of 2000 columns, so this is a restriction of the build. maragubot accepted it on 2026-11-13.
- **An index has at most 250 columns,** where SQLite takes 2,000 (`MaxIndexColumns`), and a create index with more is `ErrInvalid`. It is a restriction of the build, as the 250 columns of a primary key are. A scan pins each column of a key with one term, the key of an index is its columns and then the primary key's, so 500 columns at most, and SQLite refuses a condition that is nested deeper than a thousand levels. Measured on 2026-11-20: SQLite takes a condition of 501 terms, which is the most that a scan has, and refuses one of 1,201.
- **The core checks the storage class of every value itself,** in a write and in replay (`table.checkValue`). A `STRICT` table does not refuse every wrong value: for an `INT` column, SQLite converts the text `'1'` and the real `1.0` to an integer without an error, and for a `REAL` column the integer `1` to a real. This is a choice of the build, and maragubot accepted it on 2026-11-13. Since slice 4 the types are exact, as the roadmap says: an `int` or `integer` column takes an integer, `real` a real, `text` text, and `blob` a blob, and anything else is `ErrInvalid`. Since slice 6 a column takes NULL only if its `Column` in the commit format says `nullable`, which no primary-key column does; a NULL has no type, so it goes into a column of any type that takes it, and the core refuses it in any other column, in a write before SQLite sees the row and at replay. The core also refuses what s4ql never stores: a real that is NaN or infinite, and text that is not valid UTF-8 or holds the character NUL.
- **A real that is -0.0 is stored as 0.0, not refused.** SQLite stores a real in a `REAL` column of a strict table that has no fraction as an integer, so a column of the cache gives back 0.0 for -0.0, and -0.0 and 0.0 are one key. The roadmap's slice 4 says that `-0.0` is stored as `0.0`, as in SQLite, so the core takes it and binds it as 0.0 (`bind`), which SQLite would do anyway; the bind keeps the sign out of every row, key, and temporary table without relying on how SQLite encodes a record. The commit object is written from what the cache holds, so it holds 0.0 too, and the format refuses -0.0 in a row or a key. `TestTx_types` checks the cache, the commit object, and a replay.
- **A column carries its default, and the core stores nothing by it.** The default is `Column.default` in the table that `Tx.CreateTable` takes and that `Table` and `Tables` give: NULL or a value of the column's type, in a field with presence, so a column without a default and one with `default null` differ. NULL is a default for every column, also for one that does not take NULL and for a primary-key column, as in SQLite. Every row that the core takes has a value for each column: `Tx.Upsert` and `Tx.Insert` refuse a shorter row with `ErrInvalid`, as before, and an explicit NULL stays NULL. The engine fills in a column that a statement leaves out, with its default or with NULL where it has none, and hands the core whole rows. `Tx.CreateTable` takes a default of -0.0 and keeps 0.0, in the cache, in `Table` and `Tables`, and in the commit object, as `Tx.Upsert` takes -0.0 in a row, and it leaves the caller's table as it is (`withoutNegativeZero`). A default is copied into the table at `Tx.CreateTable` and out of it at `Table` and `Tables`, so neither the caller's message nor one that the core gave can change the table. A default that the commit format refuses, such as a value of another storage class than its column's type, is `ErrInvalid` before anything changes, and the transaction goes on. Defaults came with slice 11 of the [roadmap](../../docs/roadmap.md#slice-11-default-with-a-literal), on 2026-11-21. Markus agreed to the slice on 2026-11-20, and the builder of the core step decided what the agreement left open, by SQLite's behaviour and the agreed rules. The reasons for the field are in [internal/format/README.md](../format/README.md).
- **A text or blob longer than SQLite's limit, and a row larger than it, is `ErrTooBig`, and the transaction goes on.** The limit is SQLite's `SQLITE_LIMIT_LENGTH`, 1,000,000,000 bytes, which SQLite counts for one value and for the record of a row, its header included. The core refuses a value above the limit before SQLite sees it, and turns SQLite's `SQLITE_TOOBIG` from a write into `ErrTooBig`, so that the engine can give SQLite's "string or blob too big". Before, SQLite's error failed the transaction, which could then only be rolled back. SQLite refuses such a statement before it changes anything. To refuse exactly where SQLite's own table refuses, no record that the core writes for a row may be larger than SQLite's record of the row: the temporary tables hold the key alone, and the query that writes the commit object sorts nothing, because a sorter's record holds the key and the row together. `TestTx_tooBig` lowers the limit to 1000 with `Options.LengthLimit` and compares every length around it with SQLite's own table of the same shape.

## Concurrency

- **There is no state machine.** The package is plain blocking Go. Each caller's goroutine does its own work from top to bottom, and the one goroutine of the package renews the lease. The rest of the concurrency comes from the callers. The spec once asked for a state machine that does no I/O, and that sentence was deleted with Markus's agreement on 2026-11-10 and 2026-11-11. The reasons: a state machine does not solve the hard part, which is the order goroutines run in; it fits interactive transactions poorly; and FoundationDB, whose testing this project follows, runs plain coroutine code on a deterministic scheduler and has no such state machine. The design was to be judged by building on it. Markus on 2026-11-11: "I think we should just try it out."
- **No read starts on a cache that lacks an acknowledged commit.** If the cache fails after the manifest swap, `Tx.Commit` stops the instance before it returns, and no read starts after the stop. A read can still start while SQLite fails and before the core sees the error. That read sees the state before the commit, which is allowed, because the commit is not acknowledged until `Tx.Commit` returns. Before the build, the todo asked that no read start between the failure and the return of `Commit`, which cannot be met as worded. The rule that the build keeps is the spec's: a read that starts after a commit is acknowledged sees it. The workload with everything has reads that race these stops.
- **The owners of the readers set how many reads run at once.** `DB.Reader` opens a `Reader`: one connection to the cache, with `pragma query_only = on`, which its owner closes with `Reader.Close`. The instance keeps the open ones in the list `DB.readers`, and sets no limit on their number. The spec says: "The number of connections in the database pool sets how many reads run at once." Before 2026-11-19 the core had a fixed pool of read connections, `Options.Readers`, 4 by default, behind `DB.Read`, and a fifth concurrent read waited. Markus agreed on 2026-11-19 that the code follows the spec's sentence: each connection of the pool of `database/sql` has a reader of its own. The details are maragubot's, chosen the same day. `DB.Read`, the list of idle connections, the semaphore of the readers, and `Options.Readers` are gone, and `Open` opens only the write connection.
- **A reader runs one read transaction at a time, and a read never waits.** `Reader.Read` starts a read transaction on the reader, and is what `DB.Read` was. A second `Read` while the first is open fails at once with `ErrReaderBusy`, and a `Read` on a closed reader fails with `ErrReaderClosed`. The second read fails and does not wait, because of the driver above the core. `database/sql` holds the mutex of a connection during every call of the driver on it, also during `Rows.Close` and `Rows.Next`. A second query on one `sql.Conn` that waited inside the driver for the rows of the first would hold that mutex, so nothing could close or read those rows, and the wait could end only with its context.
- **A reader that is closed leaves the descriptor of the cache open until the instance closes.** A reader has two files open, the cache and its write-ahead log. `Reader.Close` closes its SQLite connection, and the descriptor of the write-ahead log goes with it. SQLite's unix VFS does not close the descriptor of the database file while another connection of the process holds a lock on that file, which the write connection always does in the journal mode wal. It keeps the descriptor and gives it to the next connection that opens the file. So the descriptors of the cache stay at the most readers that were open at once, plus the write connection, until `DB.Close` closes the last connection. Measured with `lsof` through the driver on 2026-11-19: 50 queries open gave 51 descriptors of the cache and 51 of the log; after the pool had closed every connection, 51 and 1; 20 queries open after that, 51 and 21; after the close, 0 and 0. `faultvfs.VFS.OpenFiles` counts the files that SQLite opens through the VFS, not these descriptors, so no test shows it. The review of the reader of each connection found it.

## The cache

- **SQLite's own schema is the catalogue.** The core keeps no table of tables. It reads the names and the statements from `sqlite_schema` and the columns from `pragma_table_info`. There is then one source of truth, and a person with the `sqlite3` shell sees the tables of the database.
- **The cache has one table of its own, `s4ql_cache`.** It holds the version of the cache's layout and the position, which is the name of the last commit object that the cache has applied. The position is text, 64 hexadecimal digits, so that a person can compare it with the manifest.
- **The cache records the identity of its database, and `Open` refuses a cache of another one.** The identity is `Options.Identity`, which the core only compares. A new cache gets the table `s4ql_cache` with its row in one transaction that takes SQLite's write lock at its start and looks again whether the table is there, so of two instances that open one new cache at once, exactly one makes it and the other reads its record. An instance of the same database then opens the cache, and one of another database gets `ErrCacheDatabase`. Before, two instances of two databases that started on one empty cache both served, and each read the tables that the other wrote. Markus agreed to the approach on 2026-11-19; the version of the layout went from 0 to 1, and no cache of version 0 is kept.
- **The version of the layout stayed 1 when the other types came, on 2026-11-19.** A table with `int` columns is declared as before, so a cache made before holds what this version makes, and opens and is read as one of its own; a test builds such a cache statement by statement and opens it (`TestOpen_cache`). The layout itself did not change: `s4ql_cache` is the same, and the temporary tables of a transaction are never in the file. A version before slice 4 that opens a cache with a table of another type refuses the table with `ErrCacheVersion` when it first looks it up, and stops, and it refuses a commit object with such a type as one of a newer version when it catches up; it never misreads one. A new version of the layout would only have made this version refuse or convert the caches of the version before, which hold nothing that it cannot read.
- **The version of the layout went from 1 to 2 when columns that take NULL came, on 2026-11-20.** A column that takes NULL is declared `default null` in the cache, and `conn.load` reads it from the default that `pragma_table_info` reports, which is the text `null` for such a column and SQL NULL for a column with no default. Every other column outside the primary key is declared `not null`, so that SQLite also refuses a NULL there if the core's own check ever lets one through. `Tx.Insert` therefore runs `insert ... on conflict do nothing`, which skips a row only for its key, and not `insert or ignore`, which would skip a row that breaks `not null` as well. The default is the only part of a column's declaration that `pragma_table_info` reports and that a strict table leaves free: the type must be one of SQLite's. The version changes, and does not stay as it did for the types of slice 4, because a version that reads version 1 would read a column declared `default null` as one that does not take NULL, and so misread the table without an error; with version 2 it refuses the cache with `ErrCacheVersion`, and asks for a new cache. This version refuses a cache of version 1 in the same way, as any version other than 2, and leaves it as it is: the operator opens the database with a new cache, which catches up from the log. There is no upgrade in place, because nothing outside the tests uses s4ql yet; a builder wrote one, and Markus had it removed on 2026-11-20: "Yes, remove it." A table with another default, a default on a primary-key column, or `not null` beside `default null` is not one that s4ql makes, and `conn.load` refuses it with `ErrCacheVersion`. `TestOpen_cache` refuses a cache of version 1 and finds its file unchanged. maragubot chose the layout; the lead decided the field `nullable` of the commit format, and Markus confirmed it on 2026-11-20. Since version 4, a column that takes NULL is told by its lack of `not null`, and `default null` is a default like any other, so this bullet describes versions 2 and 3.
- **The version of the layout went from 2 to 3 when indexes came, on 2026-11-20.** The cache holds an index of SQLite for each index of the database: not unique, on plain columns, each ascending or descending (`table.createIndexSQL`). A version from before would not know the indexes of a cache that this version made, so the version changes, and the older one refuses such a cache with `ErrCacheVersion`. This version refuses a cache of version 2 in the same way and leaves it as it is: the operator opens the database with a new cache, which catches up from the log and builds each index from the rows. There is no upgrade in place, because nothing outside the tests uses s4ql yet. Markus agreed to version 3 with no upgrade on 2026-11-20, for slice 9 of the roadmap. `TestOpen_cache_indexes` refuses a cache of version 2 and finds it as it was.
- **The version of the layout went from 3 to 4 when defaults came, on 2026-11-21.** A column outside the primary key that does not take NULL is declared `not null`, as before, and `conn.load` now tells a column that takes NULL by the lack of it, from the flag `notnull` of `pragma_table_info`. A column with a default declares it in SQLite, as `default` and a literal, and a column without one declares none. Nullability and the default are then independent, so `not null default null`, a column that takes NULL with `default null`, and one that takes NULL without a default each read back as they were made. The core writes whole rows and names every column, so SQLite never applies a default itself. The default is declared in SQLite all the same, and is not kept in a table of the core's own, because SQLite's schema is the one catalogue of the cache: a drop of the table removes the default with it, no second table can disagree with the schema, a person with the `sqlite3` shell sees it, and SQLite would store the same value if a row ever came without the column. The cost is a canonical form for the literal and a strict parse of it, which the next bullet describes. The version rises because a version that reads version 3 would read a column of version 4 that takes NULL and has no default as one that does not take NULL, without an error; with version 4 it refuses the cache with `ErrCacheVersion`. This version refuses a cache of version 3 in the same way and leaves it as it is: the operator opens the database with a new cache, which catches up from the log. There is no upgrade in place, because nothing outside the tests uses s4ql yet. Markus agreed on 2026-11-20, for slice 11 of the roadmap, that the layout rises by one with no upgrade. `TestOpen_cache_defaults` refuses a cache of version 3 and finds its file unchanged.
- **The cache declares a default in one canonical form and reads no other.** `defaultSQL` writes the form: an integer in decimal, with a minus only when it is negative; a real as the shortest decimal that reads back to its bits, in exponent form (`1e+00`, `-1.5e-300`, `5e-324`), so that SQLite reads a real and never an integer; text in single quotes with each single quote doubled; a blob as `x'...'` in lowercase hexadecimal; and `null`. SQLite reads each back as the same value. Measured with the binding on 2026-11-21, `select` with the literal gave the same bits for 240,010 reals, among them random bits, subnormals, and the edges, and `-9223372036854775808` after `default` is the smallest integer, because SQLite takes the minus there as part of the literal. `conn.load` reads a default with `parseDefault`, and refuses with `ErrCacheVersion` a text that is not the canonical form of a valid default of the column's type: another spelling of a value, such as `+1`, `00012`, `1.5` for a real, `X'AB'`, or `NULL`; a value of another type; an expression; a real that is NaN, infinite, or -0.0; and text that holds NUL or is not valid UTF-8. The parse sees only what `pragma_table_info` reports, which for `default (1)` is `1`, so the parse alone read that default as the literal; the comparison of the whole statement in the next bullet refuses it. `conn.load` also refuses a primary-key column that SQLite reports as taking NULL, which is the key of a table with a rowid. `not null default null` and a default on a primary-key column, which version 3 refused, are now read.
- **The cache accepts a table or an index only if its statement is exactly the one that the core writes.** `pragma_table_info` hides much of what a statement can declare: a generated column, a collation, a check, a foreign key, a constraint of uniqueness, the conflict clause of a key, and whether the table has a rowid or is strict. It reports `default (1)` as `1`, and the key of a table with a rowid declared `not null` as not null. A table made by hand with any of these was read as a table of the core's until 2026-11-21, when an independent review found it by running. Since then `conn.load` builds the table from the pragma as before, and then compares the text that SQLite keeps for it in `sqlite_schema` with `table.createSQL` of what it read, and `conn.loadIndexes` does the same for each index with `table.createIndexSQL`; a difference is `ErrCacheVersion`, with the advice to open the database with a new cache. SQLite keeps `CREATE TABLE ` or `CREATE INDEX ` and then the statement from the name on, as it was written (`kept`), and the core never alters a table, so a table or an index that the core made always has that text, and anything else that a statement declares, even a second space, changes it. The other choice was to read `strict` and the rowid from `pragma_table_list` and the columns from `pragma_table_xinfo`, which would leave each hole that no pragma reports to be found one at a time, such as a check or a conflict clause. `conn.load` also refuses a table with a trigger, from the same statement that finds the table, since a trigger would run on the core's writes, and a virtual table before `pragma_table_info`, which fails for one whose module is not there. `Open` refuses, after the record of the cache, every object of the schema that is neither the core's nor SQLite's own (`conn.checkObjects`): a view, a trigger, a table of a reserved name other than `s4ql_cache` and SQLite's `sqlite_` tables such as `sqlite_stat1`, an index on a table of a reserved name, and a table `s4ql_cache` that is not declared as the core declares it. What another process changes while an instance runs is checked only where the core looks: a table and its indexes at their first look-up in each transaction, and the rest at the next open. A trigger on `s4ql_cache` made then runs on the commits until the next open, as a process that writes the rows of the cache itself would go unseen; a trigger that skips the update of the position fails the commit, since `conn.setPosition` counts the row it changed. The layout's version stays 4, because no cache that the core wrote is refused: a test creates random tables and indexes, with hostile and random names, every type, keys of every length and order, and random defaults, and reads them back after a close and an open and after a replay into an empty cache (`TestOpen_cache_foreign`), and the tests at the length limit read back tables and indexes whose statements are as long as the limit. The check reads the statement of the table with the statement that finds it, and that of an index with the statement that reads its columns, so it adds no statement, and `TestSchemaReads` counts the same statements as before. Measured on 2026-11-21 on an Apple M4: building and comparing the text costs about 1 µs for a table of six columns and under 1 µs for an index, against about 110 µs for the first look-up of a table and a get of one row in a new transaction (the connection forgets its prepared statements at the end of each), so under 1%. A benchmark of that look-up and get, run in turns on the code before and after, showed no difference (p > 0.15 in each of four cases, of 15 runs each), but the machine was busy and the runs varied by 10% to 70%, so it could not have shown one of a few percent. The statement that reads the columns of an index has no `order by`, and checks the order of `seqno` itself, because the record of a sorter would hold the text of the index beside the other columns, and could then be longer than the length limit when the text alone is not.
- **The statement of a table in the cache holds its defaults, and the length limit counts them.** A table whose statement is longer than the length limit is refused with `ErrInvalid` before anything changes, as before (`conn.create`), so a default is never longer than the limit as a value. The canonical form of a real can be a few bytes longer than the user's spelling (`.5` is `5e-01`, `1.5` is `1.5e+00`), and that of an integer shorter (`00012` is `12`). A create table within a few bytes of the limit that SQLite takes can therefore get `ErrInvalid` from the core, as it could before for its quoted names.
- **SQLite's schema is the catalogue for indexes too.** `conn.loadIndexes` reads the indexes of a table from `pragma_index_list` and `pragma_index_xinfo`, and none at `Open`. An index that this package does not make stops the instance with `ErrCacheVersion`: one that is unique, partial, on an expression, with a collation, with a column twice, or with a reserved name, and one whose statement differs from the core's in any other way (see the bullet on statements above). An index of a constraint, such as that of a column declared `unique`, is in the statement of its table, which `conn.load` refuses before the indexes are read, so `Get` and `Table` already refuse such a table.
- **The indexes of a table are read when a call first needs them.** A table is read from the schema with two statements, and its indexes with one more and one for each index. `Get`, `Table`, and `Tables`, on `Tx` and on `ReadTx`, read no index (`conn.lookUpWithoutIndexes`). A point read therefore costs the two statements, whatever indexes the table has. Every other call that names a table or an index reads the indexes of the table first (`conn.lookUp`): every scan, `Indexes`, `Index`, `Tx.Upsert`, `Tx.Insert`, `Tx.Delete`, `Tx.Keys`, `Tx.KeysBy`, `Tx.CreateIndex`, `Tx.DropIndex`, `Tx.DropTable`, the check of the name in `Tx.CreateTable`, the commit, and replay. The indexes then stay with the table until the connection forgets its tables, at the end of the transaction or at a change of the schema. The check of foreign indexes is part of that read, so it runs before any write of a row of the table and before any scan of it. A unique index that s4ql did not make would let an upsert replace another row, so no row is written before the check. `Get`, `Table`, and `Tables` answer on a table with a foreign index, and the first call that needs the indexes stops the instance. A table says whether its indexes are read (`table.indexed`), and the code that reads its indexes, scans it, or writes a row of it refuses a table without them with `ErrCacheVersion` (`table.checkIndexed`), which would be a fault of the core. It came on 2026-11-20, after a review of the core step of indexes. Before, the first look-up of a table read its indexes, and a `Get` on a table with five indexes read the schema with eight statements.
- **The order in which the indexes were created is not stored.** It is the order of the rowids of the indexes in `sqlite_schema`. SQLite gives a new row the rowid after the largest one in the table ([sqlite.org/autoinc.html](https://sqlite.org/autoinc.html)), so an index that is created later than another that still exists has the larger rowid, also after drops. Measured with the pinned shell on 2026-11-20: after indexes at the rowids 2 to 5 and a drop of the one at 3, the next index got the rowid 6. The index of the primary key of a table without a rowid is the table itself, and has a name and no row in `sqlite_schema`. `pragma_index_list` lists the newest index first, which the tests use as a second way to the order (`cacheDump`).
- **The create and the drop of an index run under SQLite's largest length limit, as those of a table do.** `conn.createIndex` and `conn.dropIndex` go through `conn.changeSchema`, which sets the length limit of the connection to 1,000,000,000 bytes for the one statement and then back to `Options.LengthLimit`. SQLite formats the statement that writes an index into its schema under the length limit. That statement holds the name of the index, the name of its table, and the statement that creates the index. So, under a lowered limit of the connection, SQLite refuses as too big an index whose own statement fits in the limit.
- **An index whose statement in the cache is longer than the length limit is refused with `ErrInvalid` before anything changes,** as such a table is (`conn.createIndex`, `conn.create`). SQLite keeps the statement in its schema, without `main.`, and a connection under the limit cannot read a schema that holds a longer text. After the refusal the transaction goes on (`Tx.CreateIndex`). A subtest of `TestTx_tooBig` in `tx_test.go` has both cases under a limit of 1000. In one transaction it refuses an index whose statement is a byte longer than the limit, creates and drops one whose statement is as long as the limit, and creates one with a name of 470 bytes, which SQLite cannot write into its schema under the limit. It then reads that index and scans by it after a restart and after a replay of the log.
- **The names that start with `s4ql_` are the core's.** The core refuses a table whose name starts with `s4ql_` or `sqlite_`, in any case of the letters (`ErrReservedName`). SQLite reserves `sqlite_` itself. maragubot chose the prefix before the build and told Markus on 2026-11-12. The roadmap lists the restriction under [Restrictions](../../docs/roadmap.md#restrictions).
- **`synchronous` is `full`.** SQLite then syncs the write-ahead log at every commit, before the commit is in the index of the log, so a failed sync of the log fails the commit that needed it, and the instance stops at that commit, as the rule for local I/O failures says. The file of the cache is synced only by a checkpoint that copies the whole log, so a failed sync of the file fails no commit: it surfaces at the checkpoint after a later commit, which stops the instance then. Under `normal`, which the cache had until 2026-11-26, SQLite synced only at a checkpoint, and a commit whose pages never reached the disk went on being served until the next checkpoint, if that one reported its failure at all. Markus decided on 2026-11-26: "I'm leaning full. Correctness wins over speed in our design." A commit to the cache comes after the manifest swap, so a commit whose sync fails is in the log, and the next start catches the cache up to it (`TestDB_sync` in `cache_test.go`). Tests that test neither syncing nor the production setting turn syncs off (`synchronous = off`), since a test that neither fails a sync nor crashes the operating system cannot tell syncs from none: the scenario tests through their helper `world.openWith`, unless their options say `SyncOn`, as those of `TestDB_sync`, `TestDB_checkpoint`, `TestDB_checkpoint_busy`, and `TestDB_Close_afterLocalFailure` do; the workloads of the simulation, except its cell with syncs (`workload.syncs`); and the tests of other packages through `coretest.SyncOff`. That function calls `core.SyncOff`, which takes a key of the package `internal/core/internal/testonly`, which Go lets only the packages under `internal/core` import and whose type no literal of another package can stand for, and the linter's rule `coretest` lets only tests import `coretest`, so no code outside `internal/core` can turn syncs off without a lint failure. A subtest of `TestOpen` shows that `Open` with default options runs `full`. The cost is in [docs/todo/cache-checkpoints.md](../../docs/todo/cache-checkpoints.md).
- **The core runs the checkpoints of the cache itself.** SQLite's automatic checkpoint drops its error (`sqlite3WalDefaultHook` returns `SQLITE_OK`), so every connection has `wal_autocheckpoint = 0` (`openConn`), and the writer runs a passive checkpoint (`DB.checkpoint`) after each commit to the cache that leaves 1000 frames or more in the log: after `Tx.commitCache`, and after each commit object of a catch-up. That is when and how SQLite checkpointed before, so the log behaves as it did. A checkpoint that read transactions hold back copies what it can and is no failure, and neither is one that cannot start because another connection checkpoints or because a statement is still open on the write connection; the log then grows by what is committed while the oldest read is open, as it did under SQLite's own checkpoint. Any other error stops the instance with `ErrLocal`, and a commit whose checkpoint fails still returns nil, because it is committed. The close of the instance runs no checkpoint of the core. Once a local failure has stopped the instance, or met it after it stopped for another cause, or failed its `Open`, its connections close without SQLite's own checkpoint at the close of the last one (`SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE`, through `sqlite.Conn.NoCheckpointOnClose`), which would try the failed sync again in place: the log stays, and the next open recovers from it. The reasons, and the open point about another instance that shares the cache, are in [docs/todo/cache-checkpoints.md](../../docs/todo/cache-checkpoints.md).
- **The SQLite binding got four methods for this package:** `Stmt.BindText`, `Stmt.BindNull`, `Stmt.ColumnText`, and `Stmt.Reset`, in `internal/sqlite`. The position and the names of tables and columns are text, a value can be NULL, and replay runs one statement for many rows.

How the cache handles SQLite's "busy" was chosen by maragubot on 2026-11-11, after an investigation, and told to Markus. The investigation is [research/sqlite-busy.md](../../docs/research/sqlite-busy.md).

- **A lock in Go does not keep SQLite from reporting "busy".** A reader that starts while the writer commits can take the WAL write lock for a moment, and the writer's next `begin immediate` then fails at once. It happens with a single reader, and only with real parallelism.
- **Every connection has a busy timeout,** one second by default (`Options.BusyTimeout`). SQLite then waits out the window itself. In the investigation a timeout of one millisecond already removed every failure, and the wait was about 1.5 ms on fewer than 1% of begins.
- **The write connection opens first, runs one statement, and stays open while the instance runs.** Recovery of the WAL after a crash, and the cleanup when the last connection closes, also report "busy", and this keeps both away from the read connections. A read connection opens only through `DB.Reader`, on an instance that `Open` has returned.
- **"Busy" after the timeout is returned to the caller and logged as a warning** (`ErrBusy`). It is not a local I/O failure, and the instance goes on. In this design it means that another process has the cache open, or that s4ql has a bug.

## A write transaction

- **Which rows a transaction changed is kept in the cache, not in memory.** For each table that existed when the transaction began, a temporary table holds the primary key of every row that the transaction upserted or deleted, and a second one the keys of those rows that existed then. A key goes in with `insert or ignore` after the write, and into the second table only when the first took it, so the first record of a key stays. A delete of a row that is not there records nothing, since it changes nothing. `Tx.Commit` writes the commit object from joins of those tables with the real ones. A transaction can therefore change any number of rows. Until slice 4 one table held the key and a column `existed`, whose record was a byte longer than the row's in a table of one column, so that a row at the length limit would have been refused there and not in SQLite's own table.
- **A table that the transaction created needs no temporary table,** because all its rows are new.
- **In the commit object, the drops of indexes come before the tables, and the new indexes after them.** The net effect of a transaction is, first, the drops of the indexes that were there when it began and that it dropped by name, in the order of the drops; then the tables, as before; and last the indexes that it created and that are there, in the order in which it created them. An index that went with its table is in no drop of an index, because the drop of the table drops it. An index that is created and dropped leaves nothing. An index that is dropped and created again, also exactly as it was, is a drop and a create, because it is then the last of its table's indexes. Applied in this order at replay, every change finds what it needs: a dropped index is there, because no table was dropped before it; a name is free for a table, because the index or the table that had it was dropped before; and a created index finds its table with all its rows, so it is built once. The doc comment of `Tx.spoolCommit` gives the whole order. It came with slice 9 of the roadmap, on 2026-11-20.
- **A statement that changes the rows it finds collects their keys first, in a set in the cache.** `Tx.Keys` makes a temporary table of keys of one table for the length of a call, `KeySet.Add` puts a key in, and `KeySet.All` gives the keys back in the order of the key, each read by a statement of its own that has ended before the caller sees the key: the least key of the set above the one before. SQLite leaves undefined what a cursor gives when its table changes under it, so an UPDATE or a DELETE of the engine scans the table and adds the keys of the rows it finds while only the set changes, and then changes the row of each key while no cursor is open on a table. A row that the statement writes, also under a new key, never comes back to it, and none is held in memory. The set's table and its statements at rest are dropped when the call ends, and a roll back to a savepoint takes them with it. It came with slice 8 of the roadmap, on 2026-11-20, and `TestTx_Keys` checks the order of the edges of each type, a key of two columns, changes between two keys, and the refusals. `Tx.KeysBy` makes a set whose `All` gives the keys in another order, by the values of columns of their rows that hold the primary key, each in its direction, as the key of an index holds them: `Add` takes those values, and the first `All` numbers the keys in that order with `row_number()` into a second temporary table, after which the set takes no key. It is for an UPDATE that SQLite changes in the order of an index, and came on 2026-11-26; `TestTx_KeysBy` checks the order against a scan of the index of the same columns.
- **The commit object and the annotations go through spool files.** The files are next to the cache. Each is unlinked as soon as it is open, so a crash leaves none behind. A failure of a spool file is a local I/O failure, and it stops the instance.
- **A transaction that changed nothing writes no commit object,** also when it has annotations, which are then stored nowhere. It commits if the lease is valid by the clocks, as a read does. A commit object without changes would only lengthen the log, and without a manifest swap nothing but the clocks can judge the commit. This is a choice of the build, not an agreed rule, and maragubot accepted it on 2026-11-13.
- **An error of the cache in a call of a transaction leaves the transaction fit only for a rollback.** One way to get there is to drop a table while a scan of the transaction is running, which SQLite refuses.
- **`DB.Begin` looks at the clocks, and `Tx.Commit` does not.** `DB.Begin` refuses at once when the lease has run out by a clock, as the spec says. In `Tx.Commit` the manifest swap decides, and a swap that is applied also renews the lease. This is a choice of the build too.
- **A write transaction has no maximum duration, for now.** A writer that waits for the writer lock gives up when its own context ends.
- **An instance that has lost its lease ends the write transaction that is open,** unless it is in its commit or its roll back, so that the lease task can take the writer lock, which it needs to take the lease back and to catch up (`DB.endForLease`). Before, an idle transaction kept the instance from serving until the application ended it, and such a transaction could never commit anyway. Markus decided on 2026-11-19 that the instance fails it at once. The transaction is rolled back in the cache, every later call fails with an error that wraps `ErrTxLeaseLost`, which wraps `ErrNoLease`, and `Tx.Rollback` returns nil. A lease that has only run out by the clocks ends nothing, because a renewal does not need the writer lock: meanwhile `Tx.Serving` refuses with `ErrNoLease`, and when the store comes back and no other instance has taken the lease, the instance renews it and the transaction goes on and can commit. `TestLease_openTx` pins this.
- **The end for the lease never cuts a call.** The lease task never uses the write connection while a call of the transaction does. It marks the transaction under `DB.mu`, in the critical section where every call counts itself on the connection, and the last call that leaves the connection does the roll back and frees the writer lock (`Tx.leave`); with no call running, the lease task does it at once. A scan looks at the mark before each row, so a loop over a scan ends at its next row. Rows of a scan that the caller does not read hold a statement of SQLite on the connection, which no other goroutine can end safely, so the instance waits for the caller to read the next row or stop the scan; that is the one case in which it does not serve again by itself. A scan that holds no statement between rows, and seeks again by the last key for each row or batch, would close this gap; it is not built (see `docs/todo/slice-03.md`). `DB.Begin` records its transaction in the critical section that finds the instance serving, so no transaction begins unseen by the lease task. The event of the end is `transaction_ended`, at Info.
- **A savepoint lets one statement of a transaction fail without an effect.** `Tx.Savepoint` runs SQLite's `savepoint s4ql_statement` and copies what the transaction has recorded of each table for its commit object; `Tx.RollbackTo` restores both, and `Tx.Release` keeps what came since. One savepoint is open at a time. The spool of annotations only grows, so a rollback to a savepoint before an annotation leaves the transaction fit only for a rollback, and a commit with a savepoint open is refused as not committed. The engine runs each write of a transaction that spans statements between a savepoint and its release, as SQLite runs a statement.
- **`Tx.Serving` and `ReadTx.Serving` look at the clocks, as `DB.Begin` and `Reader.Read` do.** The engine calls them before each statement of a transaction that spans statements, so that such a statement is refused as a statement of its own would be. The other calls of an open transaction do not look at the clocks. maragubot chose this on 2026-11-19, for slice 3.

## The commit

- **The keys of a database are `<prefix>/manifest.json` and `<prefix>/commits/<shard>/<name>`,** where the name is the commit object's SHA-256 as 64 hexadecimal digits, and the shard is the first two digits of the name, as in `commits/9f/9f2c…e41a`. With an empty prefix, the keys have none. maragubot chose the keys before the build and told Markus on 2026-11-12, and the shard was agreed with Markus on 2026-11-13.
- **The commit objects are sharded for a copy on a disk, not for S3.** S3 does not care how many keys share a prefix. A generic tool that mirrors a bucket to a disk keeps the layout, though, and a database writes one commit object for every transaction, so one flat folder would reach millions of files. Markus on 2026-11-13: "Sharding by the first few characters might be a good thing? In case we ever need to replicate commits to a disk or something." One level of 256 folders holds about 39,000 files each at ten million commits. Two levels would give a small database nearly one folder per commit. Unlike git, the file keeps the full name, so that a file that is copied alone still names itself. The format is a draft at version 0, so nothing reads the old layout, and nothing migrates.
- **The commit object is uploaded before the manifest lock is taken.** The lease task can then renew the lease while a large commit object is on its way.
- **A commit object that the store can never take fails the commit at once.** When the store refuses the upload with `store.ErrTooLarge`, `Tx.Commit` returns an error that wraps `ErrTooLarge` and does not try again. Nothing is committed, and the instance keeps the lease and goes on serving. On S3 the limit is 5 GiB, the most that one PutObject takes. Markus said of this case before it was built: "Don't worry too much about commit objects above 5GB for now."
- **A write of the manifest that the store refuses as too large is taken as of unknown outcome,** as any error of the store that does not mean "not applied". A manifest is a few hundred bytes, so only a store that is set up wrong refuses one, and an unknown outcome is never wrong, only slower. The doc comment of `refusal` in `lease.go` says so too.
- **The position is written into the cache's transaction before the swap.** After the swap, all that the cache has to do is to commit.
- **The two locks are taken in one order:** the writer lock, then the manifest lock.
- **`serving` becomes true only under the writer lock.** A write transaction that saw the instance serve therefore cannot miss a catch-up.
- **One ordinary mutex, `DB.mu`, guards the flags of the instance.** It is never held across a wait. That is the rule for library code that neither the lint nor the scheduler checks; see [Conditions for keeping the design](../sim/README.md#conditions-for-keeping-the-design).

## The lease

The design was agreed with Markus on 2026-11-11 and changed on 2026-11-12. Markus on the frame for all of it, on 2026-11-11: s4ql is "designed mostly for always-on server-side usage", and "I don't want to design around theoretical failures."

- **The cost of the design is a wait after a crash.** An instance that starts after a crash waits the holder's duration and the margin before it serves, even if the crash was long ago: 33 seconds with the defaults. A clean shutdown releases the lease, so a normal restart does not wait. Markus asked on 2026-11-12: "we agree that regular shutdowns still don't have to wait, right?" A spare that is already running takes over sooner, because it has watched the manifest since about the holder's last renewal.
- **An instance without the lease reads the manifest every `Options.Watch`,** which is 5 seconds by default. It then sees a release within that time. When a holder dies, the instance has already watched the manifest since about the holder's last renewal.
- **The wait counts from after the read,** because a read shows the manifest as it was at some moment before the answer came.
- **The margin is the larger of two seconds and a tenth of the holder's duration.** It is for a monotonic clock that runs fast on the instance that waits. The doc comment of `margin` gives the numbers.
- **The holder counts its lease from when the first attempt of a renewal was sent,** not from a retry and not from the answer. Section 6 of [research/s3-clock.md](../../docs/research/s3-clock.md) says why.
- **A new holder writes a new lease entry.** The fields of the old holder's entry that this version does not know are not kept. One holder keeps them from renewal to renewal. The todo lists this as an open question under [Storage formats](../../docs/todo/storage-formats.md), and this is what the build chose.
- **The retries of the lease task back off,** from one second to `Options.Watch`, while the store gives no answer.
- **Both clocks of the holder stay in the check.** If both fail, reads can be stale, and Markus accepts that, on 2026-11-11: "if the server is in such bad a state that both clocks fail, stale reads are probably okay too."
- **The lease is checked before the state of a read is fixed, and that check is the one that counts.** At its moment no other instance holds the lease, so the cache holds the newest state, and the state that the read fixes later is that state or a newer one. Before the build, the todo said that one check was enough and that its order did not matter, because "The cache never holds another instance's commits". The research note on S3's clock advises the check after the read. Neither is so: catch-up puts the commits of other instances into the cache, so an instance that fixed the state of a read while it was a spare could take the lease and catch up before a check that came only afterwards. That check would then pass on stale data. The review of the build found this. `Reader.Read` checks a second time after the state is fixed, which only keeps a read from being served late. Both checks are `DB.servingLocked`.
- **A write that waits for the writer lock waits no longer than the lease has left** (`DB.acquireServing`, whose one caller is `DB.Begin`). Nothing wakes a caller when the lease runs out by a clock, so the wait ends then and looks again. A read has no lock to wait for; see [Concurrency](#concurrency). `DB.Wait` returns only when the lease is valid by the clocks too, and is woken when a renewal makes it valid again.
- **A lease lasts a year at the most,** so that no sum of a time and a lease leaves the range of a duration. The duration of another holder comes from the manifest and can be any, so the wait for it is computed without such a sum. This is a choice of the build, and maragubot accepted it on 2026-11-13.
- **An instance without a valid lease is a normal state.** It covers an instance that cannot reach S3 and whose lease runs out, an instance whose lease another one has taken, and an instance that has just started. Markus on 2026-11-11, on an instance that cannot reach S3: "this is where we'd return a HTTP 502 and let the clients retry." On a spare: "we can have a spare instance running, and it'll never serve anything until it gets the lease."
- **Opening does not wait for the lease.** `DB.Wait` waits, as `Ping` does next to `Open` in `database/sql`. Wrong S3 settings therefore do not fail `Open`. They show in `DB.Wait` and in the error of every call.

### How the design of the lease came about

On 2026-11-12, unless a date is given:

- **On 2026-11-11 the manifest was to record an absolute expiry time.** Another instance was to take the lease when its own wall clock had passed that time, which is only safe if the wall clocks of the machines agree. The alternative was a duration and a value that another instance watches stand still, and it was passed over. Markus: "A is fine for now."
- **The simulation harness showed that one wrong wall clock is enough for stale reads.** The holder's wall clock is behind. The holder renews, and writes an expiry that is already past for every other instance. A spare takes the lease, correctly by its own clock, and commits. The holder's two checks both pass, so it serves reads from its cache until its next renewal fails. A spare whose clock is ahead does the same. The design of 2026-11-11 said "A wall clock that is set backward is caught by the monotonic clock", which held only while the holder wrote no expiry from the wrong clock.
- **maragubot proposed to take the time from S3:** compare the manifest's `Last-Modified` with the `Date` of S3's response. Markus: "Ooh, of course. S3 should be our clock, I can't believe I didn't think of that."
- **The research found S3's clock better than the wall clocks, but not safe enough to rest the lease on.** On Tigris a client can set `Last-Modified` with a request header, and MinIO has the same hole through a header of its own. The two timestamps usually come from different machines. The only store that documents a bound on the skew between its own clocks is MinIO, and its bound is 15 minutes. No system was found that compares the two timestamps. The idea swaps "our machines' clocks agree" for "the store's clocks agree", which cannot be checked either. The note is [research/s3-clock.md](../../docs/research/s3-clock.md).
- **The research pointed to the rule that Kubernetes and the DynamoDB Lock Client use, which compares no clocks.** It is the alternative of 2026-11-11. Markus: "didn't we discard this design already? But I think it sounds good."

Why the manifest has a salt, and not a counter, is in [internal/format/README.md](../format/README.md#the-manifest).

## A swap whose outcome is unknown

The rule is in the spec, under "An unknown commit outcome is resolved from S3". It was agreed with Markus on 2026-11-11. Markus on the state after "outcome unknown": "it's kind of the same as when the lease expired? We return a temporary error to readers and writers." It is the same state: the instance does not know whether its cache is current, so it refuses and keeps trying.

One mechanism serves the rule, for commits and for renewals:

- **Every swap that the holder sends is a swap from the one version that it knows.** A swap that ends without an answer is kept as a `flight`.
- **At most one flight is ever applied,** because all flights are swaps from the same version. Any swap from that version that is applied rules all the others out for good. A version that a holder wrote never comes back, because of the salt.
- **`DB.observe` reads the manifest and tells three cases.** The manifest is unchanged. Or it is the manifest of one of the flights, which the instance then adopts. Or it is another manifest, and the lease is lost.

What follows from the mechanism:

- **A commit can be sent while the outcome of a renewal is unknown.** If the renewal turns out to be applied, the commit is sent again as a new swap from the new version.
- **After a refusal with an unchanged manifest, the same swap is sent again.** This is the 409 of S3: S3 can refuse a swap from the right version while another write to the same key is on its way, and that other write can be the first attempt. A refusal therefore does not prove that the first attempt arrived. The builder of the simulated store found this in AWS's documentation on 2026-11-12, and the simulated store does it on purpose (`internal/store`).
- **After the lease is lost, a commit with an unknown attempt is looked for in the log** (`Tx.inLog`). The walk goes back from the new head to the parent of the transaction. Another instance may have committed on top in the meantime, so the walk does not look at the head alone.
- **While `Tx.Commit` still waits, it pushes the commit:** it sends the same swap again.
- **While `Tx.Commit` still waits, reads go on** for as long as the lease is valid by the clocks. They see the state before the transaction, which is allowed, because the commit is not acknowledged.
- **After the caller gave up, the lease task does not push the commit.** It reads the manifest. If the manifest is unchanged, the lease task renews the lease without the commit, and that renewal is the swap that rules the stuck request out. A read alone never settles it, because the stuck request can arrive after the read.
- **After "outcome unknown", the instance serves nothing until it knows.** It refuses reads and writes with `ErrNoLease`, as an instance without a valid lease does. Otherwise the application could check its data on a cache that lacks the transaction, conclude that the transaction was not committed, and repeat it, while the stuck request commits the first one.
- **An application that gets "outcome unknown" must check its own data,** or make its transactions safe to repeat. FoundationDB does the same with `commit_unknown_result` ([research/foundationdb.md](../../docs/research/foundationdb.md)).
- **`Tx.Commit` goes on finding out when the instance stops meanwhile.** The caller is owed an answer for as long as it waits, and the answer comes from the store. The error for an unknown outcome wraps nothing but `ErrOutcomeUnknown`, so that a caller that tests for `ErrStopped` first is not told "not committed" for a commit that may be in the log.
- **One more case gives "outcome unknown" without the caller giving up:** the lease is lost, the commit must be looked for in the log, and the log holds a commit object that can never be read. Nothing can tell then. The spec first said "only if the caller gives up first". Markus agreed on 2026-11-13 to name this case in the spec too: "Also sounds quite theoretical, but yes, sounds like the right response."
- **The transaction of the cache is rolled back when `Tx.Commit` returns "outcome unknown".** If the commit object turns out to be in the log, catch-up applies it from the store. There is then one path, and it is the path of every start.

### A take that arrives late

The version of a manifest without a lease entry can come back, because such a manifest has the same bytes whenever the head is the same, and a version comes from the bytes, as S3's ETag does. A request to take a free lease that is stuck in the network can therefore be applied after a later release. The manifest then names a holder that does not know it, and the next instance waits for that lease to time out. maragubot proposed a salt at the top level of the manifest, new at every write, so that no version ever comes back. Markus decided against it on 2026-11-13: "Isn't that a bit theoretical? And the cost is only a delay in lease? I'd say no. As long as we don't gamble with correctness."

It is no gamble with correctness, for this reason:

- **A request that is stuck in the network can be applied late only if the version that it is from comes back,** and a version comes back only if the same bytes are written again.
- **The only manifest that is written again with the same bytes is the one without a lease entry.** Every write of a lease entry carries a new salt.
- **The only swaps sent from a manifest without a lease entry are takes of the lease** (`DB.acquire`), and every attempt of a take draws a new salt, so no two takes carry the same bytes. A take that arrives late can therefore install a lease and nothing else.
- **Every commit and every renewal is sent from a version that a holder wrote,** which holds a salt and never comes back: the holder's first swap is from the version that its take wrote, and each later one from the version of the swap before it. A release is sent from such a version too.

The reasoning rests on one more thing: nothing sends a take twice with the same bytes. The core never does, and the client of the store must not either. The client for real S3 must already never let the SDK retry a conditional write by itself ([docs/todo/s3-client.md](../../docs/todo/s3-client.md)), which also covers this.

`TestLease_unsure` shows both: that every attempt of a take carries a salt of its own, and the case itself, in which a take that is stuck is applied after the holder released the lease, a commit of the holder that is stuck is refused, the head is unchanged, and the next instance takes the lease after the holder's duration and the margin. The workloads of the simulation meet the case too, which `run.verifyLease` allows for. The workload of writes that land late meets it in most seeds, and the planted bug `resendTake` shows that the last condition matters: an instance that sends a take that got no answer again with the same bytes gives the manifest a version that it had before, when the first attempt lands after the next release at the same head.

## Catching up and replay

- **Catch-up downloads every missing commit object twice.** It walks the log back from the head to the cache's position, and it reads each commit object on the way to its end, so that it trusts a parent only when the bytes match the name. It then applies the commit objects, oldest first, and downloads each again. A spool of the walk could remove the second download later.
- **The holder renews its lease during a long catch-up** (`DB.keepLease`): between commit objects, and between the changes of one.
- **A download that fails is tried again where it failed** (`DB.fetchAgain`). The first build started the walk from the head again after any failure, so a cache that was N commit objects behind needed N downloads in a row to succeed, and with a store that fails one download in twenty, a log of 30 commit objects was never caught up. The review of the build found this.
- **Replay is strict.** A commit object that the reader accepts and that does not fit the cache stops the instance with `ErrLogBroken`. Examples are a table that is there already, a row to delete that is not there, and a value of the wrong storage class. The cache is right up to the parent, so the commit object is wrong.
- **Replay applies the creates and the drops of indexes in the order of the commit object,** and checks each against the cache as it is then, so an index can follow the create of its table in one commit object. Replay refuses as a broken log, with `ErrLogBroken`: a create index on a table that is not there, on a column outside the table, under the name of a table or of an index, under a reserved name, or of more than 250 columns; a drop of an index that is not there; and a create table under the name of an index. A drop table takes the indexes of its table with it. It came with slice 9 of the roadmap, on 2026-11-20.
- **Before replay refuses a commit object, it reads the commit object to its end** (`authentic`). Bytes that were damaged on their way must give "does not match its name" and a second download, not a stop.
- **A commit object that the store does not have is `ErrLogBroken` too.**

## Stopping

The rules for a local I/O failure were agreed with Markus on 2026-11-10, and they are in the spec. The failure that started them: the manifest swap succeeded, so the transaction is committed in S3, and the commit to the cache then fails. The commit is real, but the cache cannot show it, so the instance must not go on serving reads from the cache at the old state. Markus asked for a story that covers every local I/O failure, not only a full disk, because local disk I/O can fail in many ways. What comparable systems tell the client, and what the node does, in that failure is in [research/commit-acknowledgement.md](../../docs/research/commit-acknowledgement.md).

- **One rule covers every local I/O failure.** Any I/O failure on the cache stops the instance, also where nothing was committed: a full disk during a write before the swap, a failed read, or a failure during catch-up. There is then one rule and one recovery path to test, at the cost of availability on transient failures. Markus: "We can relax later if needed."
- **Which SQLite codes are a local I/O failure** was chosen by maragubot on 2026-11-11 and told to Markus. The list is in the doc comment of `classify`, and the full classification is in [research/sqlite-busy.md](../../docs/research/sqlite-busy.md). SQLite's `INTERNAL` is not in the list, and the core does not treat it as one.
- **A reader that cannot be opened falls under the same rule.** A failure to open a reader goes through `DB.cacheError`, as every error of the cache does while the instance runs, so what `classify` calls a local I/O failure stops the instance. That includes SQLite's `CANTOPEN`, which a process without a free file descriptor gets. The first read of a new connection opens the write-ahead log too, and a failure there stopped the instance before 2026-11-19 too. An open that failed without a stop would make the outcome depend on which of the two files met the limit. maragubot chose this on 2026-11-19.
- **Only the write connection makes the cache.** `Open` opens it with `sqlite.OpenVFS`, which creates a missing file, and `DB.Reader` opens a reader with `sqlite.OpenExistingVFS`, which does not. So a cache whose files are deleted under a running instance is `CANTOPEN` for the next reader, and the instance stops. Until a reader opens, nothing sees the deletion: the write connection and the readers that are open go on with the deleted files, so an instance whose readers are all open already may never stop for it. Until 2026-11-19 a reader created the file, an empty cache without the table `s4ql_cache`, and every query on it failed with `no such table: main.s4ql_cache` while writes went on into the deleted file, without a stop. The review of the reader of each connection found it. The start after the stop is a normal one: the write connection makes a new cache, and catch-up replays the log into it. `TestDB_Reader` in `read_test.go` and `TestStop` in the root package have the case.
- **Nothing is tried again in place.** After a failed fsync, the local state cannot be trusted until it is opened again. PostgreSQL makes the same choice for the same reason.
- **Stopped means a dead handle.** s4ql is a library and cannot crash the process, so the `DB` dies instead. It also signals the stop directly, in the style of a context: `DB.Done` closes, and `DB.Err` gives the cause. The application can then react at once, and not only at its next call.
- **`Tx.Commit` returns nil when the swap succeeded,** also when the cache then fails. Its result keeps one meaning: nil if and only if the transaction is known to be committed. An error that means "committed, but stopped" was considered and rejected. Almost all Go code treats any error from `Commit` as "not committed", so a job queue would deliver the job again and a user would submit again after the restart, and the transaction would be written twice.
- **Running reads fail.** This is a lean, not a hard rule. Markus: "Sounds theoretical. Don't overfocus on it. Leaning towards abort." Letting them finish would break no rule, because they hold a state from before the commit.
- **The library does not open itself again, for now.** The application closes the database and opens it again, so recovery from a stop is the same path as recovery from a crash of the application.
- **Recovery follows the cache's recorded position.** If the failed local commit did not land, the start applies the missing commit object. If it landed despite the error, there is nothing to apply. An I/O error from SQLite's `COMMIT` does not say whether the commit happened, so recovery never assumes either state.
- **`DB.stop` is for three things:** a local I/O failure, something in the store that the instance cannot read, and `DB.Close`. Before the build, the item on the lease in the todo said that a permanent stop is for local I/O failures only. maragubot chose before the build, and told Markus on 2026-11-12, that what cannot be read stops the instance too: a manifest or a commit object that needs a newer version of s4ql, one that is malformed, a commit object whose bytes do not match its name after a second download, and a log that is broken. Nothing that cannot be read is skipped.
- **The lease task makes the one attempt to release the lease** (`DB.releaseOnce`), after a stop for a failure.
- **`DB.Close` releases the lease itself** (`DB.release`), and ends the lease task, with its attempt. It reads the manifest and releases the lease while the manifest names the instance, for at most as long as the lease lasts. A clean shutdown therefore releases the lease also after a failed first try, and also a lease that the instance holds without knowing it.

### Closing the cache

- **`DB.Close` closes the cache whatever the store does.** Before 2026-11-13, `Close` spent its whole context on the release of the lease and only then closed the cache. With a short deadline and a store that could not be reached, the caller got an error and a cache that stayed open, again at every retry. A test fell into exactly this, in the step of `leak-builder` in the diary. maragubot had it changed, and the todo held it until then.
- **When `Close` returns, every connection that no call uses is closed,** whether the store answered or not, and the connection of every reader is among them. The first thing that `Close` does after the stop is to close them. The release of the lease comes after, with half of the time that the context has left, if it has a deadline, so that the rest is left for the calls that still run.
- **A connection that a call uses is never closed under it.** Each call that touches a connection counts itself on it while it runs (`DB.use` and `DB.unuse`), and so does the lease task while it takes the lease or catches up. The last call to leave a connection of an instance that is closing closes it. `Close` waits for those calls until its context is done, and then returns an error that says that a call still uses the cache. After the stop, every call fails at its next check, so the wait is short. Two things take longer: a `Tx.Commit` whose swap may be applied, which goes on finding out and then commits or rolls back the transaction of the cache, and a request to the store that is on its way, which ends at its answer or its timeout.
- **A transaction that is open and idle does not keep the cache open.** Its connection is closed, which rolls the write transaction back, and every later call of the transaction fails with `ErrStopped`. `Tx.Rollback` and `ReadTx.Close` then return nil. Waiting for such a transaction would gain nothing, because no call of it can succeed after the stop. This is a choice of the build, and maragubot made it on 2026-11-13.
- **A reader is closed by its owner, and the instance still ends every reader itself.** `Reader.Close` ends the read transaction that is open, closes the connection, and takes it off the list `DB.readers`. While a call of the read transaction runs, such as a loop over `ReadTx.Scan`, it returns `ErrReaderInUse` and closes nothing. A stop of the instance ends the read transaction of every reader, as it ended every read before: each call fails at its next check. `DB.Close` closes the connection of every reader, also one whose read transaction is open, and waits for one that a call uses. `Reader.Close` then has nothing left to close and returns nil. Closing a reader twice does nothing, and no reader opens on a stopped instance. `DB.Reader` opens its connection without `DB.mu`, so that a slow open holds nothing up, and counts itself in `DB.opening` meanwhile. `DB.Close` waits for that count too, and a reader that finds the instance stopped after its open closes its connection before it lowers the count, so no connection is open when `Close` returns. `Reader.Close` closes its connection under `DB.mu`, as `DB.closeIdleLocked` does, so that no two connections to the cache close at once; the todo says why, under the storage core.

## Waiting

- **A wait for a condition needs nothing new from the host.** The wait is `host.Host.Sleep`, or the `Acquire` of a semaphore, with a context that is derived from the caller's. Whoever changes `stopped`, `holder`, or `serving` cancels the contexts that are registered (`DB.waitLocked`, `DB.wakeLocked`).
- **Three things wait this way.** `DB.Wait` waits until the instance serves. A writer that waits for the writer lock fails at once when the instance stops serving. The lease task is woken from its pause. A read is not among them: `Reader.Read` refuses at once, with `ErrNoLease` on an instance that does not serve and with `ErrStopped` on one that has stopped. Until 2026-11-19 a read waited for a free read connection, as a writer waits for its lock.
- **Polling was rejected,** because a call that waits must fail "at once". The toy library that the harness once had polled with `Sleep`. The host has no method to wait for a condition; see [The host interface](../sim/README.md#the-host-interface). The build was free to add one, and none was needed.

## Planted bugs

The reason for planted bugs is in [Conditions for keeping the design](../sim/README.md#conditions-for-keeping-the-design): a check can pass for the wrong reason.

- **The tests plant wrong decisions in the real code.** `Options` has an unexported field, `bugs`. Each field of it switches on one wrong decision, at the one place where the right decision is made. Twenty-six fields are for the simulation, and one is a data race for the race detector.
- **A program that uses the package cannot switch a bug on.** Only the package's own test files can set the field, through `export_test.go`.
- **The cost is that the wrong branches are compiled into the package,** each behind a test of one boolean.

## Events

- **The instance logs one wide event for each unit of work,** through `Options.Logger`, which is a `*slog.Logger`. The names of the events and of the attributes are in one place, `telemetry.go`. maragubot chose this before the build and told Markus on 2026-11-12.
- **The level of an event says how much an operator needs it.** Routine work is Debug: a commit that succeeded, also one that changed nothing, a renewal of the lease that succeeded, and a call that was refused for lack of a valid lease. A change of state is Info: the lease taken, lost, or released, a catch-up, and a close. What went wrong and did not stop the instance is Warn, and a stop for good is Error. The list is in the doc comment of the events in `telemetry.go`. With a logger at the default level, Info, a healthy instance logs nothing after it has started. The levels were agreed with Markus on 2026-11-13, who asked: "So we log on each commit? Isn't that a bit much? But maybe on a debug or trace level it's fine".
- **A checkpoint of the cache is an event of its own, `checkpoint`,** with its outcome (`checkpointed`, `held_back`, `busy`, `locked`, or `failed`: `busy` when another connection holds the lock of the checkpoint or SQLite reports "busy", and `locked` when a statement is still open on the write connection), the frames in the log after it (`checkpoint.log_frames`), the frames that it copied into the file (`checkpoint.frames_moved`), and its duration (`duration.total`). It is Debug as routine work, also when reads held it back, and Warn when it failed, beside the Error of the stop that follows. The core has no metrics, so it adds none; the attributes are what a metric would count.
- **A commit whose cache fails after the manifest swap is Warn,** though `Tx.Commit` returns nil for it, because something went wrong. The stop that follows is Error.
- **An event at Debug costs almost nothing while Debug is off.** The core asks the logger whether it takes the level, with the context, before it builds attributes that cost anything to build: the event of a commit keeps plain values until then (`commitReport`), and the events of a renewal and of a refusal are not built at all.
- **Every event is logged with a context, through `slog.Logger.LogAttrs`,** so that tracing can later add a span to it through the context. Markus on 2026-11-13: "make sure to use their context-aware log function counterparts, so we can add tracing context (span ID etc.) later through the context". An event of a call carries the context of its caller. The lease task has no caller: its events carry the context that `Open` was given, without its cancellation, because the task outlives the call of `Open`. The events of `DB.Close` carry the context of `Close`. `TestEvents` checks the contexts of a commit, of a read and a `Begin` that are refused, of the lease task, and of a close.
- **The readers added no event** when they replaced the pool of read connections on 2026-11-19. A read that is refused is logged as it was.
- **There is no OpenTelemetry, no trace, and no metric yet.** The todo holds them.

## What the package does not do, and what to know

- **A catch-up downloads every missing commit object twice.** See [Catching up and replay](#catching-up-and-replay).
- **Replay holds one batch of rows decoded.** That is about twenty mebibytes for a batch of one mebibyte, whatever the size of the commit object.
- **No test shows that the margin is enough.** The tests check that an instance waits for the holder's duration and the margin (`run.verifyHistory`). The harness cannot make a clock run fast, so the fault that the margin is for stays out of the workloads; see the comment of `clockFaults` in `simulation_test.go`.
- **A take of the lease that arrives late can make the next instance wait for a lease to time out.** It adds no commit. See [A take that arrives late](#a-take-that-arrives-late).
- **The simulation does not reach SQLite's "busy".** The write connection opens first, and every connection has a busy timeout; see [The cache](#the-cache). Both guard against "busy" under real parallelism, which the scheduler never produces; see [What the scheduled mode cannot do](../sim/README.md#what-the-scheduled-mode-cannot-do).
- **The manifest has no guard against bytes that are damaged on their way.** A commit object is checked against its name and downloaded a second time. A manifest that is damaged and no longer parses stops the instance at the first download. One that is damaged and still parses would be believed, and the swap that takes the lease would write it back, because the swap is from the version that the store gave, not from the bytes. The store's contract promises content that is not changed, and the design has no checksum for the manifest.
- **A layer under SQLite that injects faults is used by tests only.** `internal/sqlite/faultvfs` fails opens, reads, writes, syncs, and locks on demand for the scenario tests, and fails syncs in the cell of the simulation with syncs. SQLite tests its own handling of I/O errors, and using the official C code is how s4ql inherits that.
- **There are no snapshots and no garbage collection.** Nothing deletes a commit object of the log, or one that was uploaded and never committed.
- **There is no branch other than `main`.**

## Tests

`model_test.go` holds a second, simpler implementation, in maps. `mstate.apply` replays a commit object strictly: a key that appears twice is an error, and so is a delete of a row that is not there. `mtx` computes the net effect of a transaction. `model` reads the log through the direct view of the simulated store.

`simulation_test.go` holds the harness. Callers create and drop tables, upsert, delete, get, and scan, and every result is compared with the model. Each caller owns one reader (`caller`), as a connection of a pool does. It opens the reader at its first read of a database, and closes it when the node has opened its database again or when the caller ends. A close of a reader that fails is a violation. The callers of an instance that crashes never close theirs. A read parks at no semaphore, so a yield, "core: a read before it starts", stands where the acquire of a read connection was, and another, "core: a reader before its open", lets a stop or a close come between the count of a reader that is opening and its open. The workloads set no number of readers. After the change to readers on 2026-11-19 every planted bug was still found, and the minimums of `TestSimulation` held but for those of the workload whose callers never pause, which were derived again with more seeds, as the paragraph on its seeds below says. The tables have three names in two spellings each, with characters that must be quoted, and eight shapes, four of which have columns of the other types than `int` and keys of one and of two columns. The keys of each type come from a few values with the edges that matter most to a key (`simKeys`), such as 0.0 and -0.0, the empty text and blob, and text and blobs that differ in a later byte, and the other columns take the edges of their type (`edges` in `model_test.go`). The minimums of `TestSimulation` count the upserts and deletes of text and blob keys and of -0.0 by markers of the trace. The doc comment of `workload.run` lists the invariants, and the doc comment of `run.verifyHistory` lists the checks of the store's history.

`workloads_test.go` holds the three workloads, `singleWorkload`, `fullWorkload`, and `hammerWorkload`. It also holds the four aimed workloads: `competing` for the rules of the lease, `unknownOutcomes` for a swap whose outcome is unknown, `lateWrites` for writes that land long after they were sent, and `idling` for write transactions that sit idle while their instance loses the lease. The list `plantedBugs` gives each bug its workload, and a control where the bug needs one ability of the harness or one fault.

`lateWrites` is for a write that lands long after it was sent. A real store can apply a write many minutes after its caller gave up or crashed, and no store documents a bound. The simulated store holds such a write for up to `Faults.LateBy`, a minute in the other workloads, and with `Faults.Long` for up to `Faults.LongBy`, 15 minutes here. The lease lasts 30 seconds and a takeover takes about 33, so only the long hold makes it common for a write of one holder to land after others took the lease and committed. The callers run for about 15 simulated minutes, with crashes, restarts, closes, and cut-offs, and `run.verifyLandings` reads the history of the manifest after each run to count what became of every write that was held back, and to check that a swap of the manifest that lands after the lease changed hands is applied only as a take of a free lease. The design says that such a write is harmless, and the runs show it: a late swap of the manifest is from a version that a holder wrote, which never comes back, so it is refused, and a late create of a commit object finds the object there already, or creates an object that no manifest names. `TestSimulation` requires that both kinds land after another node took the lease in a quarter of its seeds at least. The planted bug `resendTake` needs a write that lands late, and its workload, a variant of this one, finds it 12 times as often with the long hold as with holds of up to a minute; see [A take that arrives late](#a-take-that-arrives-late) and the table below.

Over 1000 seeds of `lateWrites` on 2026-11-13, each run twice, no seed violated an invariant and no pair of traces differed. 28596 commits were acknowledged, and 1396 had an unknown outcome. Of 17691 swaps of the manifest that landed late, 17570 were refused, and the 121 that were applied all landed before another holder had written. In 887 seeds such a swap landed after another node had taken the lease, and in 643 after other nodes had taken it twice. Of 4283 creates of commit objects that landed late, 2050 were refused because the object was there, and 2233 created an object that no manifest names. `idling` is `competing` with one idler on each instance (`run.idler`): a caller that begins a write transaction, makes one change, and lets it sit idle while its instance is cut off from the store, half of the time, for 30 to 60 seconds, long enough for the other instance to take the lease. A buggify point sits between the manifest swap and the commit to the cache (`Tx.commitCache`), with two variants: the commit to the cache is rolled back and reports an error, or it goes through and still reports an error. The second variant is not distrust of SQLite, which can legitimately return an I/O error from `COMMIT` after the transaction became durable. It catches a bug of ours: recovery that assumes that an error means that the cache did not get the transaction, and so applies the commit object twice.

A crash in the workload with everything copies the cache and its write-ahead log at the moment of the crash, without the shared-memory index, and a new instance starts on the copy. Nothing opens the copy before the instance does, so `Open` recovers the cache from the log, as after a real crash. The harness then checks that the cache holds what it held at the crash, and what the log says up to its position. It also reads a copy of the file of the cache alone, without the log, and counts the restarts where the file lacked commits that the cache had, which only the recovery from the log can bring back. Copying the cache without its log makes the check fail in most seeds. Over 1000 seeds on 2026-11-13, 761 of the 1000 restarts recovered commits that only the log held, from logs of 5064 frames in all and 36 in the largest. Before that day, the harness read the copy before the instance opened it, and its connection, as the last one to close, checkpointed the copy and deleted the log, so `Open` never recovered anything.

Every test that opens a cache checks at its end that no connection to it is left open (`leftOpen`): the scenario tests through `cacheDir`, and each run of a workload as a violation of the run. SQLite deletes the write-ahead log when the last connection to a database closes, so a log that is left shows a connection that is left, or an instance that stopped for a local failure and closed without that checkpoint. So for each cache with a log, the check opens a connection of its own, reads the cache, and closes the connection: the log is gone after that close if no other connection holds the cache, and stays if one does. A connection that has not read the cache keeps no log and holds no lock, so the check misses that one. The C address sanitizer finds a connection that is left too, but only once nothing on the Go heap points to its memory any more, which depends on when the collector ran, and only when the whole test binary passes.

The environment variables:

- `S4QL_SIM_SEEDS` sets the number of seeds for every workload and every bug, and the number of free runs, 1 or more. The workload of each bug then runs all of them, to count how many find the bug. With fewer seeds than the default run, what a workload reached is not checked, and with fewer than 200, whether a bug is found is not checked; the test logs a line that starts with "NOT CHECKED" for each.
- `S4QL_CORE_ROWS` sets the number of rows of `TestTx_Commit_large`.

The flags of the test binary replay one seed:

- `-replay` makes `TestSimulation` replay that one seed, and nothing else, and log its whole trace. `-workload` chooses the workload: `single`, the default, `full`, `hammer`, or `late`.
- `-bug` makes the replay run the workload of the planted bug that it names. `-control` then runs the control of that bug, and `-clean` runs the workload without the bug.

A seed that fails in `TestSimulation` or `TestSimulation_plantedBugs` prints the command that replays it, with `-race` or `-asan` if the run that failed had one, such as:

```sh
go test -run '^TestSimulation$' -v ./internal/core/ -replay 7 -workload full
```

They are flags and not environment variables so that a variable left in the shell cannot turn the full simulation into one seed unseen.

  The diary has the reason for each.
- **After local files that fail on demand** (2026-11-13, [diary](../../docs/diary/2026-11-13-failing-file-system.md)), three of those four are caught. Each test arms its fault before the operations that it fails, and chooses them by their kind and count, not by time:
  - a read of the spool file during the upload (`upload-spool-error-retried`), by "should stop for a failure to read the spool file during the upload, and not try the upload again" in `TestDB_stop`;
  - a read of the length of an annotation from its spool file (`spool-length-error-ends`), by "should stop for a failure to read the length of an annotation from its spool file, and not commit without it" in `TestDB_stop`;
  - a write of the cache that fails while replay applies a change (`replay-cache-error-as-broken`), by "should stop for good with a local failure, and not a broken log, when the file system fails while replay applies a change, and keep the cache as it was" in `TestDB_stop_cache`.

  The fourth, the rollback at the end of a read (`read-end-swallows-local`), is still not caught, because no file system can make it fail. SQLite 3.54.1 ends a read transaction through `sqlite3RollbackAll`, `pager_unlock`, and `sqlite3WalEndReadTransaction`, which return nothing, so a `ROLLBACK` after only reads returns `SQLITE_OK` whatever the files do, or `SQLITE_ERROR` ("no transaction is active") after a failed read that SQLite rolled back itself, which is not a local failure. A test in `internal/sqlite/faultvfs` shows that such a rollback meets no operation that can fail. Out of memory is the one local failure that could still reach the check, in the prepare of the `ROLLBACK`. The check stays, because it costs nothing and holds if SQLite changes.

  The test of replay depends on SQLite's page cache: its commit object takes about twice the pages that the default cache of 2 MB holds, so that replay writes pages before its commit. It also checks, through the event of the catch-up, that replay failed before it read the commit object to its end, so it fails, and does not pass without reaching the check, if a change of the cache's settings ends the spill.
