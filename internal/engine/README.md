# The engine

`internal/engine` runs one statement of [slice 1](../../docs/roadmap.md#slice-1-one-integer-column), with the parameters of [slice 2](../../docs/roadmap.md#slice-2-parameters), the five column types of [slice 4](../../docs/roadmap.md#slice-4-the-other-types), the several columns of [slice 5](../../docs/roadmap.md#slice-5-several-columns), the NULL of [slice 6](../../docs/roadmap.md#slice-6-null), the WHERE of [slice 7](../../docs/roadmap.md#slice-7-where-on-select), the UPDATE and DELETE of [slice 8](../../docs/roadmap.md#slice-8-update-and-delete), and the indexes of [slice 9](../../docs/roadmap.md#slice-9-indexes), on a database of the [storage core](../core/README.md), a `*core.DB`, and gives SQLite's results and SQLite's errors. A statement is its own transaction, unless a transaction that spans statements is open on its connection; see [Transactions](#transactions). What a statement of slice 1 is, token for token, is in [the README of `stmt`](../sql/stmt/README.md#slice-1).

The interface:

| Name | What it does |
| --- | --- |
| `New(d, host, Options)` | Gives an `*Engine` for the database `d`. The engine reads the monotonic clock of the host, for the duration in its events, and draws the direction of each query from the host. `Options.Logger` takes the events, and the default discards them. |
| `Engine.Conn()` | Gives a `*Conn`, a connection of the engine, which holds nothing until it runs a statement. See [Connections](#connections). |
| `Conn.Exec(ctx, src, args...) (Result, error)` | Runs the statement of the text `src`, with the arguments `args`, each an `*s4qlpb.Value`, for its parameters by position. A query is run to its end, and its rows are dropped. The result comes with an error too. See [Parameters](#parameters). |
| `Conn.Query(ctx, src, args...) (*Rows, error)` | Runs the statement with its arguments and gives its rows. A statement that is not a query is run as `Exec` runs it. Its rows have no columns and no rows, and `Rows.Result` gives its result; Query gives these rows also with its error. |
| `Conn.Begin(ctx) error` | Begins a write transaction on the connection. It waits for the place of the single writer as long as `ctx` allows. See [Transactions](#transactions). |
| `Conn.BeginReadOnly(ctx) error` | Begins a read-only transaction on the connection, which sees the state of its beginning. It waits for nothing. |
| `Conn.Commit(ctx) error` | Commits the transaction of the connection. The transaction is over when `Commit` returns, also with an error. |
| `Conn.Rollback(ctx) error` | Rolls the transaction of the connection back: nothing that it did is kept. |
| `Conn.Close(ctx) error` | Closes the connection, and its reader, if it has one. It rolls back a transaction that is open on the connection. |
| `Rows.Columns()` | The columns of each row, each a `Column` with the name as the table stores it and the declared type, such as `INT` or `TEXT`. |
| `Rows.All()` | The rows, as an `iter.Seq2[[]*s4qlpb.Value, error]`, in the order in which the scan of the query reads them; see [The order of the rows](#the-order-of-the-rows). The sequence ends at the first error, and can be used once. |
| `Rows.Close()` | Ends the rows. |
| `Rows.Result()` | The result of a statement that is not a query. |
| `Result{Changes, SetsChanges}` | See [Changes and the last insert rowid](#changes-and-the-last-insert-rowid). |
| `ErrNoStatement` | The error of a text that is empty or holds only spaces, comments, and semicolons. SQLite prepares such a text into no statement and gives no error. |
| `ErrArguments` | Matched by the error of a statement that is given another number of arguments than it has parameters. |
| `Check(src, n) error` | The errors of the text `src` and of the number `n` of its arguments, as `Exec` gives them, without the database and without an event. |
| `ErrTooLarge` | Matched by the error of a commit whose commit object the store refuses as too large. The error also matches `core.ErrTooLarge`. |
| `ErrRowsOpen` | The error of a begin, and of a statement in a transaction, while the rows of an earlier query of the connection have not ended. Matched by the error of a commit of a write transaction while a loop reads its rows. |
| `ErrTxOpen` | The error of a begin on a connection whose transaction is open. |
| `ErrNoTx` | The error of a commit or a roll back on a connection without a transaction. |
| `ErrTxDone` | The last error of rows whose transaction ended while a loop over them ran. |
| `ErrInternal` | Matched by the error of a fault of s4ql. See [Errors](#errors). |

An `Engine` is safe for concurrent use. A `Conn` is not, and `Rows` are not.

## Connections

A statement runs on a `Conn`, which is to the engine what a connection of a pool is to its database: it runs one statement at a time. The driver gives each connection of `database/sql` a `Conn` of its own.

- **A `Conn` owns one reader of the core,** a `*core.Reader`, on which every read transaction of the connection runs. It opens the reader for its first statement that reads, so a connection that only writes has none, and closes it in `Conn.Close`. So the connections that are open are the queries that can run at once, and nothing in the engine or in the core limits their number.
- **A connection runs one read at a time.** A statement that reads while the rows of an earlier query of the same connection have not ended fails at once, with an error that matches `core.ErrReaderBusy`. It does not wait for the rows, and [the README of the core](../core/README.md#concurrency) says why. A statement that changes the database needs no reader, and runs. This is the rule for a statement of its own. In a transaction, open rows refuse every statement; see [Rows in a transaction](#rows-in-a-transaction).
- **A reader that cannot be opened fails the statement that needed it,** and the next statement that reads tries again. If the cache cannot be opened, that is a local failure, which stops the instance as any other.
- **`Conn.Close` returns `core.ErrReaderInUse`, and closes nothing, while a loop over the rows of a query of the connection runs.** Rows of the connection that have not ended must not be used after its close: their read transaction has ended with the reader, and what they give then is an internal error. A statement on a closed `Conn` is an internal error, and so is a begin. Closing a closed `Conn` does nothing.
- **`Conn.Close` rolls back a transaction that is open on the connection,** which frees the place of the writer.
- **Why a `Conn`, and not a reader that is passed to each call.** A statement decides whether it reads only after it is parsed, so the engine must be the one to open the reader. A connection is also where the state of a connection belongs, such as a transaction that spans statements. maragubot chose the `Conn` on 2026-11-19, after Markus had agreed that each connection of the pool has a reader of its own. `Engine.Exec` and `Engine.Query` are gone.

## One statement, one transaction

A statement is its own transaction of the core, unless a transaction is open on its connection. This section is about a statement of its own. [Transactions](#transactions) is about a statement in a transaction that spans statements.

- **A statement that changes the database runs between `DB.Begin` and `Tx.Commit`.** The engine annotates the transaction with the text of the statement before the commit; see [Annotations](#annotations). Any failure rolls the transaction back, and so does a panic of an operator. A commit ends the transaction whatever it gives.
- **A query runs in a read transaction of the reader of its connection,** which `Reader.Read` starts. Its `Rows` hold the read transaction, and with it the reader, until they end. They end when `Rows.All` has given the last row or an error, when the loop over it stops early, when the loop panics, or at `Rows.Close`. One of these must happen.
- **`Rows.Close` during a loop over `Rows.All` ends the loop at its next row,** and the read transaction ends then. The loop holds the transaction also while it is suspended in its body, so an iterator that is suspended must be resumed or stopped for the transaction to end.
- **A failure of the end of the read transaction after a loop that stopped early is the error of the next `Rows.Close`.**
- **A panic while a query is built ends its read transaction too.**
- **`Rows.All` yields to the host between two rows,** so that under the simulation other tasks run while a query is open.
- **A failure of the end of the read transaction after the last row is the last error of `Rows.All`.**

## Transactions

A transaction that spans statements is open on a `Conn` from `Conn.Begin` or `Conn.BeginReadOnly` to `Conn.Commit` or `Conn.Rollback`. Every statement of the connection runs in it meanwhile. The code is in `tx.go`.

The product owner decided the design:

- **A write transaction takes the place of the single writer when it begins,** as SQLite's `begin immediate` does, and holds it until its commit or its roll back. It sees the newest state that is committed, and its own writes. Nothing outside sees its writes before its commit.
- **A read-only transaction is a read transaction.** It sees the state of its beginning, never writes, takes no place of a writer, and blocks no one.

The builder decided the details below.

### The begin

- **`Begin` waits for the place of the writer as long as its context allows.** It has no deadline of its own. If the context ends first, `Begin` gives the error of the context. On an instance that does not serve, it fails as a write of its own does, with an error that matches `core.ErrNoLease` or `core.ErrStopped`.
- **`BeginReadOnly` waits for nothing.** It starts a read transaction on the reader of the connection, and fails as a query does.
- **Both fail with `ErrTxOpen` while a transaction is open on the connection.**
- **Both fail with `ErrRowsOpen` while the rows of an earlier query of the connection have not ended,** also the rows of a statement of its own.
- **When a begin fails, nothing has begun,** and the engine logs no event for it.

### A statement in a transaction

- **The text and the arguments are checked first,** as everywhere. Three checks follow, in this order (`Conn.ready`):
  1. The context has not ended. If it has, the statement fails with the error of the context.
  2. The instance serves now, by the clocks, as a statement of its own needs it. The engine asks `Tx.Serving` or `ReadTx.Serving` of the core. If the instance does not serve, the error matches `core.ErrNoLease` or `core.ErrStopped`.
  3. No rows of an earlier query of the connection are open. If some are, the statement fails with `ErrRowsOpen`.
- **Only `Serving` looks at the clocks.** The other calls of an open transaction of the core do not, because the commit of a write transaction is judged by its manifest swap.
- **In a write transaction, a statement that changes the database runs between a savepoint and its release:** `Tx.Savepoint` and `Tx.Release` of the core, on SQLite's `savepoint s4ql_statement`. The engine annotates the statement before the release. A query takes no savepoint.
- **A statement that fails has no effect, and the transaction stays open.** When the statement fails, or an operator panics, the engine calls `Tx.RollbackTo`. That call restores the cache, and what the transaction had recorded of each table for its commit object, which is its net effect. The work of the statements before it is kept, as in SQLite.
- **The engine annotates last, because an annotation cannot be taken back** from its spool file. A roll back to a savepoint before an annotation makes the core fail the transaction. The engine never makes such a roll back.
- **After an error of the cache, the core lets the transaction only roll back.** Every later statement fails, the commit fails, and the roll back works.
- **`create table`, `drop table`, `create index`, and `drop index` are transactional.** The later statements of the transaction see them, and a roll back undoes them.
- **The texts `begin`, `commit`, `end`, `rollback`, `savepoint`, and `release` stay "not supported",** also inside a transaction, and the transaction stays open.

### A read-only transaction

- **Every statement sees the state of the beginning,** whatever commits meanwhile.
- **A statement that would write fails with SQLite's `attempt to write a readonly database`,** with the code 8 and the extended code 8, as in SQLite under `pragma query_only = 1`. SQLite's errors of the names come first: `no such table`, `has no column named`, and `already exists`. With indexes they are also `there is already a table named`, `there is already an index named`, `no such column` for a column of a create index, and `no such index`. So do the number of values of an insert and the errors of the columns of a create table. SQLite gives them when it prepares the statement, and refuses the write when it steps it. For an update and a delete, `no such column` of SET and of WHERE comes first too, and so does "not supported" for a value of WHERE of another type than its column. The engine looks the names up in the state of the transaction.
- **The transaction stays usable after such an error.**
- **`Commit` and `Rollback` end it, and write nothing.** On an instance that has stopped they return nil, because there is nothing to commit.

### The commit and the roll back

- **A write transaction commits as a statement of its own does.** All its changes are one commit object, and every read that starts after `Commit` has returned nil sees them.
- **The transaction is over when `Commit` returns,** with or without an error. `Rollback` ends it too, whatever it returns.
- **`Commit` and `Rollback` on a connection without a transaction give `ErrNoTx`.**
- **A transaction that changes nothing in the end writes no commit object, and its commit succeeds.** This is the core's rule. Examples are a create and a drop of the same table, a transaction whose statements all failed, and one that only read.
- **The commit object holds, in order, the statements of the transaction that succeeded and that write,** each with its arguments. It holds no statement that failed and no query. See [Annotations](#annotations).
- **A commit object that the store refuses as too large gives an error that matches `ErrTooLarge`.** The error also matches `core.ErrTooLarge`, and its message starts with `s4ql: the transaction is too large to commit: `. Nothing is committed. A statement of its own gets the same error. The tests set the limit of the store to 4 KiB with `simstore.Options.MaxSize`, which the commit object of 100 inserts exceeds.
- **An instance that has lost its lease ends the write transaction that is open,** unless it is committing, so that it can take the lease back; the core decides this (`DB.endForLease`). Every later statement and the commit of the transaction fail with an error that matches `core.ErrTxLeaseLost` and `core.ErrNoLease`, `Rollback` returns nil, and the connection is usable after either. Rows of a query of the transaction that a loop reads end at their next row with that error. The event `transaction` of such a transaction has the outcome `lease_lost`, at Debug, with the error, and `transaction.end` is what the application called; a statement refused so has the outcome `lease_lost` too. The transaction's writes are never in the log.
- **On an instance that has lost its lease or has stopped, the commit fails and the roll back works.** The statements fail as said above. `Commit` gives the error of the core. One that matches `core.ErrNoLease` or `core.ErrStopped` means that nothing is committed. One that matches `core.ErrOutcomeUnknown` means what it means for a statement of its own. `Rollback` frees the place of the writer, and returns nil, except after a stop by a local failure, where the roll back in the cache can give its error. The spec: "A write transaction that is already open commits only if its manifest swap still succeeds."

### Rows in a transaction

The rows of a query in a transaction read the state of the transaction. Their end does not end the transaction.

- **While the rows of a query of the transaction are open, every statement of the connection fails with `ErrRowsOpen`,** also a write. The scan holds a statement of SQLite on the connection of the transaction.
- **`Commit` and `Rollback` first end the rows that no loop reads.** A later `Rows.All` on them gives nothing.
- **Rows that a loop over `Rows.All` reads cannot be ended from outside.** A loop reads them while its body runs, and while its iterator is suspended. `Commit` and `Rollback` mark such rows. The loop then ends at its next row with `ErrTxDone`, and reads nothing more.
- **The end of the transaction runs when that loop ends,** after the scan of the core has ended. It is the roll back of a write transaction, or the end of a read transaction. `Rows.Close` after the loop gives the error of that end, which is nil when the end worked.
- **Until the loop ends, a write transaction keeps the place of the writer.** Every statement and every begin of the connection fail with `ErrRowsOpen`, and `Conn.Close` gives `core.ErrReaderInUse`.
- **A `Commit` of a write transaction does not commit in that case.** It rolls the transaction back, and fails with an error that matches `ErrRowsOpen` and ends with `so the transaction is rolled back and not committed`. A `Commit` of a read-only transaction ends it, and returns nil.
- **Why the end is left to the loop.** SQLite cannot commit while a statement of the connection reads: the commit of the core drops temporary tables, and SQLite refuses that then. A roll back can run then, but it aborts the statement, and the loop would finish the aborted statement later, on the write connection, while the transaction of the next writer runs there. So the roll back waits for the loop. A commit cannot be left to the loop in the same way, because the transaction is over when `Commit` returns: the transaction is rolled back, and the error of `Commit` says so.
- **A driver whose `Rows.Close` ends the loop does not meet this case.** `database/sql` closes the rows of a `sql.Tx` before it calls `Commit` or `Rollback` of the driver.

## The stages

A statement goes through three stages. A test can call each on its own.

1. **`stmt.Check`** reads the text into a typed statement, or gives SQLite's syntax error, "not supported", or no statement.
2. **`NewPlan`** turns the statement into a `Plan`. A plan is plain data, and `Format` prints it. It holds each name as a `stmt.Name`, as the statement writes it, and nothing of the catalogue: whether a table or a column exists is not known when the plan is made.
3. **Execution** runs the plan in a transaction of the core. `buildQuery` and `buildSink` turn the plan into a tree of operators inside the transaction. They look the names up there, and give SQLite's errors about them in SQLite's order. The engine then runs the tree.

CREATE TABLE "T""1" (V1 INT PRIMARY KEY) WITHOUT ROWID, STRICT

create table "T""1" (V1 INT, primary key (V1))

```

```

```

  values (-9223372036854775808)
```

```
select * from été

query

    scan été
```

A plan is a `*CreateTable`, a `*DropTable`, a `*CreateIndex`, a `*DropIndex`, an `*Insert`, an `*Update`, a `*Delete`, or a `*Query`. An insert, an update, a delete, and a query read their rows from a tree of nodes: `*Scan`, `*Filter`, `*Values`, and `*Project`. A `*Filter` holds its conditions, each a `Condition`. The expressions are `*Integer`, `*Real`, `*Text`, `*Blob`, `*Null`, and `*Parameter`. `*Null` is the literal NULL, which `Format` prints as `null`. `Format` prints a `*Parameter` as `?1`, by its number.

- **A `*CreateTable` holds every column, in the order of the statement, and the position of its key** in `PrimaryKey`.
- **A column of a plan is NOT NULL unless it is `Nullable`.** `ColumnDef.Nullable` is true for a column that is not the primary key and has no `not null`. `Format` prints ` NULL` after the type of such a column, and nothing more for any other, so the plans of slices 1 to 5 print as before.
- **The key is never `Nullable`,** as SQLite marks the key of a WITHOUT ROWID table NOT NULL. So a table with `not null` on its key and one without have the same plan and the same commit object, and the cache declares both in the same way. SQLite records another text of the schema for each, which s4ql does not expose.
- **The commit object has `nullable` on each column that takes NULL.** `buildSink` sets it only when it is true, as the core gives the table back. A replay of the log into an empty cache gives the same table.
- **A `*CreateIndex` holds the name of the index, the name of the table, and the columns of the index, in the order of the statement.** Each column is a `stmt.IndexColumn`, with its name and whether it is descending. `Format` prints ` desc` after a descending column, and nothing after any other, so `asc` and no direction print the same. `SQL` holds the text that SQLite keeps for the index, which `Format` does not print. A `*DropIndex` holds the name of the index.
- **A plan holds no access.** A `*Scan` names its table, and a `*Filter` its conditions. How the rows are read is chosen when the operators are built, in the transaction, where the indexes of the table are known; see [Indexes and the choice of an access](#indexes-and-the-choice-of-an-access).
- **An `*Insert` has `Columns` nil when the statement has no list of columns.** Its `*Values` node has one row, which holds all its values in the order of the statement.
- **A `*Project` has `Star` for `*`, and otherwise `Columns`:** the names in the order of the select list, each as often as the list names it.
- **A select with WHERE has a `*Filter` below its `*Project`,** with the `*Scan` as its `Source` and its `Conditions` in the order of the text. A `Condition` has `Column`, a `stmt.Name`, `Operator`, a `stmt.Operator`, and `Value`, an expression, which is nil for IS NULL and IS NOT NULL. `Format` prints the filter on a line of its own, each column as the statement writes it and each operator as its `String` gives it, so `==` prints as `=` and `<>` as `!=`. A select without WHERE has no filter, and its plan prints as before.
- **An `*Update` and a `*Delete` have the rows that they change as their `Source`:** a `*Scan` of the table, or a `*Filter` over it if the statement has a WHERE. `rowsOf` builds it, as it builds the rows of a select. An `*Update` holds its assignments in `Set`, in the order of the text. An `Assignment` has `Column`, a `stmt.Name`, and `Value`, an expression. `Format` prints each assignment with `=`, also one that the statement writes with `==`. The parameters of SET have the numbers before those of WHERE.

**Why a tree of iterators, and not a bytecode machine like SQLite's.** The lead recommended it on 2026-11-18, and Markus left the choice to the lead: "I'll trust your recommendation." Each operator is tested alone, a plan is data that tests can read, and the oracle stays rows and errors compared with SQLite, which does not change between SQLite's releases. A bytecode machine that mirrors SQLite's would give `EXPLAIN` as a second oracle and SQLite's order of checks more cheaply, but it ties the engine to an instruction set that SQLite says is not an interface. Where SQLite's order of checks or of errors is visible, the engine reproduces it on purpose, and the differential tests find the places. The plan is the seam: an executor of another kind can replace the operators behind it without touching the parser or the pass after it. The trade-offs are in [research/sql-front-end.md](../../docs/research/sql-front-end.md) §6.3.

## The storage interface

The operators and the engine do not call the core. They call seven interfaces in `storage.go`:

| Interface | Holds |
| --- | --- |
| `reader` | `table`, `indexes`, `index`, `scan`, `get`, and `rowsRead` of one transaction. `table` gives nil when there is no table of the name, and `index` gives nil when there is no index of the name. `indexes` gives the indexes of a table in the order in which they were created, which is the same on every instance. `scan` reads the rows of a table by one of its indexes, or by its primary key, as a `core.IndexScan` says, in the order of that key or in its reverse. `rowsRead` is the number of rows that the transaction has read from the storage, by its scans and its gets. |
| `writer` | A `reader`, with `createTable`, `dropTable`, which drops the indexes of the table too, `createIndex`, `dropIndex`, `insertNew`, which inserts a row only if its key is new, `upsert`, which inserts a row or replaces the row with its key, `delete`, which deletes the row of a key and reports whether there was one, and `keys`, which runs a function with an empty `keySet` of a table. It reads its own writes. |
| `keySet` | A set of primary keys of a table, for a statement that changes the rows that it finds. `add` adds a key, unless the set has it. `all` gives the keys in the order of the key, as SQLite compares keys. The table and the set can change between two keys: `all` gives the least key of the set above the one before. The set lasts for the call of `keys`. |
| `database` | `begin`, which gives a write transaction, and `reader`, which gives a reader that its owner closes. |
| `readConn` | A reader of the database: `read`, which gives a read transaction and fails while the one before it on the reader is open, and `close`. |
| `readTx` | A `reader`, with `position`, `serving`, and `end`. |
| `writeTx` | A `writer`, with `position`, `annotate`, `serving`, `savepoint`, `release`, `rollbackTo`, `commit`, and `rollback`. One savepoint is open at a time. |

Only a transaction that spans statements calls `serving`, `savepoint`, `release`, and `rollbackTo`; see [A statement in a transaction](#a-statement-in-a-transaction).

A name of a table or of an index is compared as SQLite compares names: without regard to the case of the ASCII letters, and every other character exactly.

The adapters `coreDB`, `coreTx`, `coreReader`, `coreReadTx`, and `coreKeys` put the interfaces on a `*core.DB`, a `*core.Tx`, a `*core.Reader`, a `*core.ReadTx`, and a `*core.KeySet`. They change two things:

- **A lookup of a table or of an index that does not exist gives nil,** where the core gives an error that wraps `core.ErrNoTable` or `core.ErrNoIndex` (`lookUp`, `lookUpIndex`). The operators turn the nil into SQLite's error.
- **A refusal of the core becomes an internal error** (`fromCore`). The refusals are `core.ErrTableExists`, `core.ErrNoTable`, `core.ErrIndexExists`, `core.ErrNoIndex`, `core.ErrReservedName`, and `core.ErrInvalid`. The engine checks for each before it calls the core, so one that the core still returns is a fault of the engine or of the pass after the parser. So are `core.ErrTxDone`, a call on a transaction that has ended, and `core.ErrReaderClosed`, a read on a reader that is closed. The error of `Tx.Commit` passes through as it is: its `core.ErrInvalid` is a commit time that the commit object cannot hold, which comes from the clock.

Every other error of the core passes through as it is.

The adapters pass `serving`, `savepoint`, `release`, and `rollbackTo` of a write transaction to `Tx.Serving`, `Tx.Savepoint`, `Tx.Release`, and `Tx.RollbackTo` of the core, and `serving` of a read transaction to `ReadTx.Serving`. Each goes through `fromCore`. So a refusal of a savepoint, such as a second one while the first is open, is an internal error.

The adapters pass `scan` to `ReadTx.ScanIndex` and `Tx.ScanIndex` of the core, with the `core.IndexScan` as it is. It names the index, and no name means the primary key. `Equal` pins the leading columns of the key to values, `Lower` and `Upper` bound the column after those, and `Backward` reverses the order. The cache names the index in its statement, so SQLite reads that index and no other, and SQLite compares the values. The core refuses a scan that it cannot run with `core.ErrInvalid` or `core.ErrTooBig`: a bound that is NULL and a NULL in `Equal` for a column that does not take it are among these. So the engine never asks for such a scan. [The README of the core](../core/README.md#the-interface) has the scan in full.

The adapters pass `indexes` and `index` to `Indexes` and `Index` of the core, `rowsRead` to `RowsRead`, and `createIndex` and `dropIndex` to `Tx.CreateIndex` and `Tx.DropIndex`. Each call that can fail goes through `fromCore`.

The adapters pass `delete` and `keys` to `Tx.Delete` and `Tx.Keys` of the core, and `add` and `all` of a `keySet` to `KeySet.Add` and `KeySet.All`. Each goes through `fromCore`. The cache keeps the set in a temporary table; see [the README of the core](../core/README.md#a-write-transaction).

The interfaces exist for the tests:

- **The operators are tested alone, against a fake.** `fake` in `operator_internal_test.go` keeps tables in memory, records every call, and fails or panics on demand. Its transaction, `fakeTx`, records a look-up of the indexes of a table as `indexes` and the name of the table. It records a scan that pins or bounds something, or that names an index: `range` for a scan by the primary key, or `index` and the name of the index, then the name of the table, `=` and the value of each pinned column, and each bound as an operator and an integer. A scan backward records `backward` last, and a scan of every row forward records nothing. It records a `create index` with the names of the index and the table, and a `drop index` with the name of the index. It records a `delete` as `delete`, the name of the table, and the key, and `keys` as `keys` and the name of the table. Its set of keys records each `add` as `add` and the key, and each key that `all` gives as `key` and the key. Its four calls of a transaction that spans statements do nothing and record nothing. `spanning` in `tx_internal_test.go` wraps it, records them, and fails them on demand.
- **The fuzz tests run on a database in memory too.** `memory` in `memory_internal_test.go` is fast enough for many more texts and sequences than the core is. Its savepoint is a copy of its tables. It holds the definition of an index and nothing else. For a scan, it sorts every row of the table by the key of the index, each column in its direction and with its own comparison, and keeps the rows that the pinned values and the bounds let through. That is a second way to the rows of a scan by an index, and the fuzz tests compare it with SQLite. Its set of keys is a map, and its `all` looks for the least key above the one before each time.

## The operators

Operators are of two kinds. A source gives rows to the operator above it. A sink runs a statement that changes the database, and gives the number of rows that it changed.

| Operator | Kind | What it does |
| --- | --- | --- |
| `scan` | source | Gives the rows of a table as its `access` reads them: no row, the row of one primary key by a `get`, or a scan by the primary key or by an index, in the order of that key or in its reverse. The zero `access` reads every row in the order of the primary key. It checks the context before each row, and ends with the error of the context when the context has ended. |
| `filter` | source | Gives the rows of its source for which every one of its conditions is true, in the order of the source. |
| `values` | source | Gives rows of constants. It checks the context before each row too. |
| `project` | source | Gives the columns of each row of its source at its positions: those that the query names, in the order of its list, each as often as the list names it. For `*`, they are all the columns, in the order of the table. |
| `insert` | sink | Writes each row of its source into a table as a new row. The key of the table can be at any position. |
| `update` | sink | Sets columns of each row of its source, the rows that an UPDATE finds in a table. The key can be among the columns. |
| `remove` | sink | Deletes each row of its source, the rows that a DELETE finds in a table. |
| `createTable` | sink | Creates a table. |
| `dropTable` | sink | Drops a table, by the name that the table stores. |
| `createIndex` | sink | Creates an index. |
| `dropIndex` | sink | Drops an index, by the name that the index stores. |

- **The operators build only the plans that a statement gives.** A plan of another shape fails with an internal error: an insert of several rows or of no rows, an insert into a table whose key is not exactly one of its columns, an insert that names a column twice, a table with a key of several columns or outside its columns, a table whose key takes NULL, an index that names a column twice, a projection of no columns, a filter of another node than a scan, a test for NULL with a value, a comparison without one, an update or a delete of another node than a scan or a filter of one, an update or a delete of a table whose key is not exactly one of its columns, an update that sets a column twice, and an update that sets no column. What SQLite gives for these has not been compared with SQLite, so the engine gives no answer of SQLite's for them. A slice that adds such a shape replaces its internal error with what the differential test has compared with SQLite.
- **`project` resolves the names of the select list in their order,** once `scan` has found the table, and gives the columns their names as the table stores them. `select B from t` with a column `b` gives a column named `b`, and a column that is named twice is given twice, with the same name.
- **The names of the select list are resolved before those of the conditions,** as SQLite resolves them, though the filter is below the projection in the plan. `build.node` builds the scan, then the positions of the projection, and then the filter, in `build.filter`. `build.filter` is two steps: `build.conditions` looks the columns of the conditions up, and `build.bind` evaluates their values, checks them, and gives the scan its access. The order of the errors of the filter is under [Errors](#errors).
- **`filter` has SQLite's logic of three values.** A comparison with NULL on either side is unknown: a NULL in the row, the literal NULL, or a nil argument. The WHERE leaves out a row for which a condition is unknown, as it leaves out one for which a condition is false. IS NULL and IS NOT NULL are always true or false.
- **`compare` compares two values of one type as SQLite does.** Integers and reals compare by their number, with 0.0 equal to -0.0. Text and blobs compare by their bytes, as memcmp does, and the shorter is first where it begins the other, which is SQLite's BINARY collation for text. Two values of different kinds are an internal error, which the exact types rule out.
- **`scan` reads by the primary key or by an index where the conditions of the filter above it allow it.** `build.access` gives the scan its `access`, by the rules of `chooseAccess`; see [Indexes and the choice of an access](#indexes-and-the-choice-of-an-access). A scan without a filter reads every row.
- **`buildValues` places each value of an insert at the position of its column in the table,** and puts NULL at a column that the insert leaves out, as SQLite gives such a column its default, which is NULL. The expression of that column is nil. So each row that `insert` gets has a value for each column of the table, in the order of the table.
- **`insert` checks each row before it writes,** in `insert.check`. First, no column that does not take NULL holds NULL: the first such column gets `NOT NULL constraint failed`, and the key is among these columns. Then each value that is not NULL has the type of its column. Both checks go through the columns in the order of the table. A NULL that the statement gives, as a literal or as an argument, and the NULL of a column that it leaves out are the same to both. See [Types](#types).
- **`insert` writes every row through `insertNew`,** which is `core.Tx.Insert`: SQLite's `insert ... on conflict do nothing`. It returns false for a key that the table has, also from an earlier row of the same statement, and `insert` then fails with `UNIQUE constraint failed`. For a row whose record is too long it fails with `core.ErrTooBig`, which is `string or blob too big`. SQLite builds the record of a row of a WITHOUT ROWID table before it looks for its key, so the two errors come in SQLite's order, and `insert` calls no `get` before the write. The lead decided this on 2026-11-20, after an independent review. An insert calls `upsert` only for the planted bug `skipUnique`, which writes the row so that it replaces the row with its key. See [Types](#types) for the order of the two errors.
- **`update` and `remove` find their rows as a select finds them.** `build.change` builds their source from the same `scan` and `filter`, with `build.conditions`, `build.bind`, and the same choice of an access, and makes the lookups in SQLite's order of errors; see [Errors](#errors). Their scan reads forward. A path that the tests force holds for an update and a delete too.
- **`changeRows` collects the keys of the rows first, and changes the rows after.** While the scan runs, it adds the key of each row that the source gives to a `keySet`, and only the set changes. Then `all` gives the keys back, one at a time, and `changeRows` changes the row of each: `update` sets its values, and `remove` deletes it with `delete`. The core reads each key by a statement of its own, which has ended when the row changes. So SQLite never has a cursor open on a table that changes, which its documentation leaves undefined. A row that the statement writes, also under a new key, is never in the set. So each row that the statement finds is changed once, and none is missed, also when SET writes the key or the columns that WHERE reads. The core keeps the set in the cache, so a statement changes any number of rows and holds none in memory.
- **The rows change in the order of the key.** SQLite changes the rows of an update of several rows that changes the key in that order too. The order decides only which error a failing update gives, such as `string or blob too big` of one row before `UNIQUE constraint failed` of another.
- **`update` reads the row of each key with `get`, sets its values, and writes it.** A row whose key stays is written in place, with `upsert`. A row under a new key is the old row deleted, with `delete`, and the new one inserted, with `insertNew`. As for an insert, `insertNew` fails with `string or blob too big` for a record that is too long before it looks for the key, and returns false for a key that the table has, also from an earlier row of the same statement; `update` then fails with `UNIQUE constraint failed`. A new key that is the old one by SQLite's comparison, such as -0.0 for 0.0, is no change of the key, and the row is written in place, as SQLite does.
- **An update that fails leaves no change, also when it fails after it has changed rows.** The transaction of a statement of its own rolls back, and a statement in a transaction that spans statements rolls back to its savepoint.
- **`update.check` checks the values of SET before any row changes,** as `insert.check` checks a row. First, no column that the update sets and that does not take NULL gets NULL, in the order of the table, the key among these columns. SQLite checks NOT NULL on each row that it changes, so the NULL fails only an update that finds a row. The check reads that from its source with `finds`, which stops at the first row, so the `check` of a sink takes a context. Then each value that is not NULL has the type of its column, in the order of the table, whether the update finds a row or not. `remove` has nothing to check.
- **The commit object holds the net effect of an update and a delete, and its format did not change.** An update is the row as it is afterwards. A change of the key is that row and the delete of the old key. A delete is the delete of the key. The core records the keys that a transaction touches, and gives the net effect for each. `TestConn_netEffect` reads it from the log.
- **A source is a push-style iterator,** an `iter.Seq2`. The operator above ranges over the rows, and ends the source by leaving the loop. Everything runs on the goroutine of the caller.
- **No operator uses `iter.Pull`.** It starts a goroutine, and [`simlint`](../simlint/simlint.go) forbids it in code that runs under the simulation.

## Indexes and the choice of an access

Slice 9 adds `create index` and `drop index`. With an index, a statement with a WHERE can read its rows in more than one way, and the engine chooses the way by fixed rules. The rules are in `access.go`.

### The statements

- **`create index i on t (a, b desc)` and `drop index i` run as a create table and a drop table do.** Their plans are `*CreateIndex` and `*DropIndex`. `buildCreateIndex` and `buildDropIndex` in `operator.go` build their sinks, `createIndex` and `dropIndex`. Both statements are transactional, both are annotated as every write is, and both leave the count of changes.
- **The engine gives the storage the definition of the index.** It is an `s4qlpb.CreateIndex`: the name of the index as the statement writes it, the name of the table as the table stores it, and each column as its position in the table, with `descending` only when it is true. The commit object holds this definition, and each instance builds the index in its cache; see [the README of the core](../core/README.md#the-interface). An index is not unique.
- **A table and an index share their names.** A create index under the name of a table fails, and so does a create table under the name of an index. A drop index of the name of a table gives `no such index`.
- **`drop table` drops the indexes of the table.** Their names are free for new tables and indexes afterwards.
- **An index has at most 250 columns** (`core.MaxIndexColumns`). The storage core holds no more in an index, where SQLite takes 2,000. A create index of more columns is "not supported", as `index of more than 250 columns`, at the 251st column.
- **The errors of both statements are SQLite's, in SQLite's order.** They are under [Errors](#errors).

### The rules

`chooseAccess(t, indexes, conditions)` is one pure function of the table, its indexes in the order in which they were created, and the conditions of the WHERE. It has no statistics and reads no row. So the choice is the same on every instance and for every state of the rows.

A candidate is the primary key or an index. The key of the primary key is its columns. The key of an index is its columns and then the columns of the primary key that it does not hold, as SQLite stores an index of a WITHOUT ROWID table (`indexKey`). The rules take a primary key of any number of columns. A table that a statement creates has a primary key of one column.

The rules, in the order in which `chooseAccess` tries them:

1. **No row,** if a condition is never true (`never`): a comparison with NULL, or IS NULL of a column of the primary key.
2. **The row of one primary key, by a `get`,** if `=` pins every column of the primary key (`pointOf`). This holds also when an index pins more columns.
3. **Otherwise, a scan by the candidate that fits the conditions best** (`fit`). The candidate that pins the most leading columns of its key wins. Of those that pin as many, one with a bound on the next column wins over one without. Of those that are still the same, the primary key wins, and then the index that was created first.
4. **Every row,** if the winner of rule 3 pins nothing and bounds nothing.

How a candidate is fitted:

- **A column is pinned by `=`, or by IS NULL of a column that takes NULL** (`pinOf`). The first condition, in the order of the text, that pins the column gives its value. `a = 1 and a = 2` pins `a` to 1, and `b is null and b = 'x'` pins `b` to NULL.
- **IS NULL of a column that does not take NULL pins nothing.** No row has NULL there, and the storage refuses a scan that pins such a column to NULL. For a column of the primary key, rule 1 reads no row. For any other such column, the statement reads the rows that its other conditions leave, and the filter rejects every one of them.
- **`fit` pins the leading columns of the key, one after the other, while a condition pins each.** At the first column that no condition pins, it takes the tightest bounds of the conditions that compare that column with `<`, `<=`, `>`, or `>=`, and stops. Of two bounds at the same value, the open one is tighter (`tighter`). `!=`, IS NOT NULL, and a condition on a later column of the key pin nothing and bound nothing.
- **The pinned values and the bounds reach into the columns of the primary key at the end of the key of an index.** With an index on `(a)` and the primary key `k`, `a = 1 and k > 3` pins `a` and bounds `k`.
- **The bounds are stated by value, also for a column that the index holds in descending order.** The lower bound is the smallest value that the scan lets through, and the upper bound the largest. The storage turns them into the ends of the range of the index.
- **Bounds that hold no value are passed on as they are.** `k > 5 and k < 3` is a scan by the primary key between the two bounds, which gives no row.

What follows from the rules:

- **The access only leaves rows out.** The filter above the scan tests every condition on every row that the access gives. So the rows of a statement do not depend on the choice.
- **The errors of a statement and their order do not depend on the choice.** `build.bind` checks the names, the lengths, and the types of the conditions first, and gives the scan its access last.
- **An update and a delete find their rows by the same choice.**
- **A point lookup reads no index of its table.** Rules 1 and 2 do not depend on the indexes. So `build.access` calls the rules first without the indexes, and reads the indexes of the table (`reader.indexes`) only when the answer is neither "no row" nor the row of a primary key.
- **The rules know the WHERE of slice 7 and nothing else.** The rules for `order by` and `limit` come with [slice 13](../../docs/roadmap.md#slice-13-order-by-and-limit-on-select).
- **`chooseAccess` fails only with an internal error,** for two bounds of values of two types, which the check of the types refuses before.

Examples, on `create table t (k int primary key, a int not null, b text, c real) strict, without rowid` with `create index ia on t (a)` and then `create index iab on t (a, b)`. `TestEngine_indexes` pins each, also after a replay of the log into an empty cache:

| WHERE | Access |
| --- | --- |
| `a = 10` | A scan of `ia` with `a` pinned. Both indexes pin one column, and `ia` was created first. |
| `a = 10 and b = 'x'` | A scan of `iab` with `a` and `b` pinned. |
| `a = 10 and b > 'x'` | A scan of `iab` with `a` pinned, from a lower bound of `b`. |
| `a = 10 and k < 2` | A scan of `ia` with `a` pinned, to an upper bound of `k`. `ia` bounds the next column of its key, `k`, and `iab` does not bound its next column, `b`. |
| `b = 'x'` | A scan of every row. No key starts with `b`. |
| `k = 2 and a = 10` | A `get` of the row with the key 2. |

### The order of the rows

The spec says: "Unspecified row order varies." With indexes, the order of the rows of a select without `order by` depends on the access. The engine varies it further, so that no application comes to depend on it.

- **For each query, the engine draws whether its scan runs forward or backward** (`Engine.reading`). Forward is the order of the key of the access, and backward is its reverse. The draw holds for every access: every row, the primary key, and each index. A select without WHERE is drawn too.
- **The draw is the low bit of `host.Host.Uint64`, one draw for each query.** An odd number is backward. The engine draws when it builds the query, also for a query that then reads no row or one row.
- **An engine with a seed of its own draws from a splitmix64 sequence of that seed, and nothing from the host.** The seed is `Options.Directions`, an option of the engine and nothing of the public package: a run that must be had again from a seed sets it, which are the tests of the engine (also through `Options.Seed` and `Engine.SetSeed` in `export_test.go`), its simulation, and the simulator of the site. The driver sets none, so in production each direction is a draw of the host. The n-th query of two engines with one seed reads in the same direction.
- **An update and a delete read forward, and draw nothing.** The order in which they find their rows shows nowhere: `changeRows` changes the rows in the order of the key.
- **The rules set no direction.** `build.bind` puts the direction of the statement on the access that the rules give.
- **The engines of the tests have seeds, so that a failure can be run again in the same directions.** An instance of the tests draws a seed, logs it when its test fails, and takes it from the flag `-directions`. The simulation derives the seed of each engine from the seed of the run. Both are under [How it is tested](#how-it-is-tested).

### A forced path, for the tests

The comparison of rows cannot tell one access from another. So the tests can force the access of every statement of an engine, and read the access that a statement got.

A `path` in `access.go` forces an access. The tests set it as a `Path` of `export_test.go`, through `Options.Path` and `Engine.SetPath`. The zero value forces nothing.

| Field of `Path` | What it forces |
| --- | --- |
| `Full` | Every row of the table, in the order of the primary key. No condition is tested for being never true. |
| `Primary` | A scan by the primary key, as `fit` fits the conditions to it, also where the rules read one row by a `get`. |
| `Index` | A scan by the index of that name, as `fit` fits the conditions to its key. |
| `Limited`, `Pins` | At most `Pins` pinned columns, for a path of the primary key or of an index. An access that would pin more pins that many and bounds nothing. |
| `Forward`, `Backward` | The direction of the scan, for a query, an update, and a delete. The engine then draws nothing. |

- **`forcedAccess` says what a path of the primary key or of an index reads.** It reads no row for conditions of which one is never true, as the rules do, because the storage takes no scan for such conditions.
- **A path of an index that the table of a statement does not have reads as the rules say.**
- **A statement without WHERE has no access to force.** It reads every row, in the direction of the path, if the path has one.
- **`Options.ScanAll`, `Engine.SetScanAll`, and `Engine.ScansAll` are the path `Full`.**
- **Four functions show the tests the choice,** each as an `Access`: which index, the pinned values, the bounds, and the direction. `ChooseAccess` is `chooseAccess`. `AccessOf` gives the access of the text of a select, an update, or a delete with WHERE, on a table and its indexes, and reads no rows. `PathAccessOf` does the same under a path. `Rows.Access` gives the access of the rows of a query, with the direction that the engine drew.

### The rows read from the cache

`TestEngine_rowsRead` pins how many rows named queries read from the cache. The number is `statement.rows_read` of the event of the query: the rows that the cache gave the scan or the `get` of the statement, as `core.ReadTx.RowsRead` counts them, whether or not the conditions hold for them. It depends only on the rows of the table and on the access. It does not depend on the direction, on the machine, or on timing: the test runs each query as the rules choose, then forward, and then backward, and requires the same number each time. These counts are the first of the [performance measurements](../../docs/todo.md#performance-measurement) of the project.

A table `t (k int primary key, a int not null, b int not null, c text)` holds 4,000 rows: 40 for each value of `a`, with `b` from 0 to 6. The rows that each query reads:

| Query | No index | Index on `(a)` | Indexes on `(a)` and `(a, b)` |
| --- | --- | --- | --- |
| `where k = ?`, a point lookup, which gives 1 row | 1 | 1 | 1 |
| `where a = ?`, which gives 40 rows | 4,000 | 40 | 40 |
| `where a = ? and b >= ?`, which gives 22 rows | 4,000 | 40 | 22 |
| `where k >= ? and k < ?`, which gives 100 rows | 100 | 100 | 100 |

A table shaped like goqite's holds 3,000 messages in 3 queues of 1,000. The query is goqite's receive without its `order by` and its `limit`, `select id from goqite where queue = ? and timeout <= ? and received < ?`, and it gives 400 rows:

| Indexes | Access | Rows read |
| --- | --- | --- |
| None | Every row. | 3,000 |
| goqite's index, on `(queue, priority desc, created)` | That index with `queue` pinned: the rows of the queue. | 1,000 |
| goqite's index, and one on `(queue, timeout)` | The index on `(queue, timeout)`. It pins as many columns, and it bounds the next one. | 500 |

The rules of slice 13 for `order by` with `limit` will change the choice for goqite's real query, which has both.

## How to add a statement of the next slice

1. Add a type or a field to `stmt`. Its README has [the steps](../sql/stmt/README.md#how-to-add-the-next-slice), which start with the agreement on the slice in the roadmap.
2. Add a plan node to `plan.go`, with a case in `NewPlan` and in `Format`.
3. Add an operator to `operator.go`, and build it in `build.node`, `buildValues`, or `buildSink`. Make the lookups there in the order in which SQLite gives their errors. Replace the internal error of each shape of a plan that the slice adds.
4. Add a constructor to `errors.go` for each new error of SQLite, and pin its codes, its message, and the form of each name against SQLite in `TestEngine_errors`.
5. Add the kind of the statement to `report.of` in `telemetry.go`. If the statement sets SQLite's count of changes, add its plan to `setsChanges` in `engine.go`. `write` of `engine.go`, which runs a statement of its own, and `writeIn` of `tx.go`, which runs a statement in a transaction, both ask it. `checked` in `engine.go` decides the count for an error of the sink's `check`: SQLite's error sets it, and "not supported" leaves it.
6. Extend the generator in [`stmttest`](../sql/stmt/stmttest/stmttest.go), and `Sequence` in [`stmttest`](../sql/stmt/stmttest/sequence.go), which the differential tests of the engine and of the driver share: the mix of statements in `Next`, and the near misses in `Others`.
7. Extend `fake` and `memory` to what the new operator calls.
8. Update this README.

## Errors

SQLite's errors have one type, `*sqlerr.Error` of [`internal/sql/sqlerr`](../sql/sqlerr/sqlerr.go), which the syntax errors of the pass have too. It holds `Code`, `ExtendedCode`, and `Message`, each exactly as SQLite gives it. `Offset` is extra information, and s4ql does not promise it.

| Message | Code | Extended code | The names in the message |
| --- | --- | --- | --- |
| `table %s already exists` | 1 | 1 | `Name.Raw` of the statement: the name as written, with its quotes. |
| `no such table: %s` | 1 | 1 | `Name.Value` of the statement: the name without its quotes. For the table of a create index, the message is `no such table: main.%s`, with the name of the schema before the name. |
| `there is already an index named %s` | 1 | 1 | `Name.Value` of the table of a create table. |
| `there is already a table named %s` | 1 | 1 | `Name.Value` of the index of a create index. |
| `index %s already exists` | 1 | 1 | `Name.Value` of the index of a create index. |
| `no such index: %s` | 1 | 1 | `Name.Value` of the index of a drop index. |
| `table %s has no column named %s` | 1 | 1 | `Name.Value` of the statement, for both. |
| `duplicate column name: %s` | 1 | 1 | `Name.Value` of the later column of the statement. From `CreateTable.ColumnsError()` of the pass. |
| `too many columns on %s` | 1 | 1 | `Name.Value` of the table of the statement. From `CreateTable.ColumnsError()` of the pass. |
| `table %s has %d columns but %d values were supplied` | 1 | 1 | `Name.Value` of the statement. |
| `%d values for %d columns` | 1 | 1 | None. |
| `no such column: %s` | 1 | 1 | `Name.Value` of the statement. For a name in double quotes, the message is `no such column: "%s" - should this be a string literal in single-quotes?`, because the pinned build of SQLite takes double quotes for names only (`DQS=0`). A column of a create index has both forms too. A column of the SET of an update is the exception: its message is `no such column: %s` with `Name.Value` also for a name in double quotes (`noSuchSetColumn`). SQLite's update gives that error itself, where its resolver of names gives the others and adds the question. |
| `NOT NULL constraint failed: %s.%s` | 19 | 1299, `SQLITE_CONSTRAINT_NOTNULL` | The names as the table stores them. The column is the first, in the order of the table, that does not take NULL and gets it. |
| `UNIQUE constraint failed: %s.%s` | 19 | 1555, `SQLITE_CONSTRAINT_PRIMARYKEY` | The names as the table stores them, which are those of its CREATE TABLE. |
| `attempt to write a readonly database` | 8, `SQLITE_READONLY` | 8 | None. |
| `string or blob too big` | 18, `SQLITE_TOOBIG` | 18 | None. |
| A syntax error, such as `near "frm": syntax error` | 1 | 1 | From the pass. |

The code 8 is the constant `sqlerr.CodeReadOnly`. The engine gives this error for a statement that would write in a read-only transaction, and `TestConn_Begin` pins it against SQLite under `pragma query_only = 1`. The extended code 1299 is the constant `sqlerr.CodeConstraintNotNull`.

Examples, each pinned against SQLite in `TestEngine_errors`:

- With a table `t1`, `create table "T1" (x int primary key) strict, without rowid` gives `table "T1" already exists`.
- `select * from "T""2"` gives `no such table: T"2`.
- With a table `t1`, `insert into "T1" ("V""2") values (1)` gives `table T1 has no column named V"2`.
- After `create table "Foo bar" ("Bar""x" int primary key) strict, without rowid`, a second insert of the same key through `"FOO BAR" ("BAR""X")` gives `UNIQUE constraint failed: Foo bar.Bar"x`.

The examples of several columns are on a table `t3`, of `create table t3 (v1 int primary key, v2 text not null, v3 real not null) strict, without rowid`:

- `insert into T3 values (1, 'a')` gives `table T3 has 3 columns but 2 values were supplied`.
- `insert into t3 (v3, v1) values (1.5, 1, 'a')` gives `3 values for 2 columns`.
- `insert into T3 (V3, V1) values (1.5, 1)` gives `NOT NULL constraint failed: t3.v2`.
- `select "V""1" from t3` gives `no such column: "V"1" - should this be a string literal in single-quotes?`.
- `create table t (v int primary key, w text not null, "V" real not null) strict, without rowid` gives `duplicate column name: V`.

The examples of NULL are on a table `t`, of `create table t (a text, k int primary key, b real not null, c blob) strict, without rowid`. `TestEngine_nulls` pins each against SQLite:

- `insert into t values ('a', null, 1.5, x'01')` gives `NOT NULL constraint failed: t.k`, and so does `insert into t (a, b) values ('a', 1.5)`, which leaves the key out.
- `insert into t (k, a) values (2, 'a')` gives `NOT NULL constraint failed: t.b`.
- `insert into t (b, a) values (null, 'a')` gives `NOT NULL constraint failed: t.k`. The key, which the list leaves out, is before `b`, which gets the literal, in the order of the table.
- `insert into t values (1, 2, null, null)` gives `NOT NULL constraint failed: t.b`, before the refusal of the integer 1 for the TEXT column `a`.

The order of the errors is SQLite's:

- **A table that does not exist comes before a column that does not exist.** `insert into t2 (v2) values (1)` without `t2` gives `no such table: t2`.
- **A create table gives that the table exists before the errors of its columns:** `table %s already exists`, then `there is already an index named %s` if an index has the name, then `too many columns on %s` or `duplicate column name: %s`, as `CreateTable.ColumnsError()` of the pass gives them, then `string or blob too big` for a table that SQLite cannot write into its schema under the length limit: SQLite writes it with an UPDATE of `sqlite_schema` that holds the name twice and `CreateTable.SQL` of the pass, each in single quotes with a quote doubled, and 96 bytes more, and refuses the statement when it prepares it if that UPDATE is the limit or longer (`schemaTooBig`). With `t3`, `create table T3 (v int primary key, v text not null) strict, without rowid` gives `table T3 already exists`.
- **A create index gives the table, then the name of the index, then its columns.** The errors, in order:
  1. `no such table: main.%s`, if the table does not exist.
  2. `there is already a table named %s`, if a table has the name of the index, the table of the statement among them.
  3. `index %s already exists`, if an index has the name, on any table.
  4. `no such column: %s`, for the first column, in the order of the text, that the table does not have, with the question about quotes for a name in double quotes.
  5. `string or blob too big`, if SQLite cannot write the index into its schema under the length limit. SQLite writes it with an INSERT into its schema. The text of that INSERT holds the name of the index, the name of the table as the table stores it, and `CreateIndex.SQL` of the pass, the text that SQLite keeps for the index, each in single quotes with a quote doubled. SQLite refuses the statement when it prepares it if that text is the limit or longer (`indexTooBig`).
  6. "Not supported", as `index of more than 250 columns`, at the 251st column. It is s4ql's own error, and it comes after every error of SQLite.

  With a table `t` that has a column `a` and an index `i`, and a table `u` without a column `nosuch`, `create index t on nosuch (a)` gives `no such table: main.nosuch`, `create index T on u (nosuch)` gives `there is already a table named T`, `create index I on u (nosuch)` gives `index I already exists`, and `create index j on t (a, z desc, y)` gives `no such column: z`. `no such column` has the offset of the name, and the other errors of SQLite have the offset -1. `TestEngine_indexes` pins the order and the offsets against SQLite.
- **A drop index gives `no such index: %s` for a name that no index has,** also when a table has the name.
- **An insert gives the columns of its list that the table does not have, in the order of the list, before the number of its values.** `insert into t3 (v1, x) values (1)` gives `table t3 has no column named x`. The errors that follow are in their order under [Types](#types).
- **A select gives the table before its columns, and the first name of its list that the table does not have.** `select x from t3` without `t3` gives `no such table: t3`, and with it `select v1, x, y from t3` gives `no such column: x`.
- **A select with WHERE gives the names of its list before those of its conditions, and those in the order of the text.** The first comparison of a column that the table does not have gives `no such column`. A missing column under IS NULL or IS NOT NULL does not stop SQLite: a later such test replaces the message, and the next comparison ends the walk with it, before SQLite looks its own column up. On a table `t` with the key `a`, `select * from t where x is null and y is null` gives `no such column: y`, `select * from t where x is null and y = 1` gives `no such column: x`, and `select * from t where x is not null and a is null and y is not null and a = 2` gives `no such column: y`. A name in double quotes gets `no such column: "y" - should this be a string literal in single-quotes?`, and `rowid`, `oid`, and `_rowid_` give `no such column`. After the names comes `string or blob too big` for a value of a condition that is longer than the length limit, an argument, for which SQLite gives it when it binds, or a literal. Last comes "not supported" for the first value of a condition, in the order of the text, that is not NULL and is of another type than its column; see [Types](#types). So `select * from t where a = 'x' and y = 1` gives `no such column: y`. `TestEngine_where` pins the order against SQLite.
- **An update gives the table, then the columns of its SET, then those of its WHERE.** The first column of SET, in the order of the text, that the table does not have gives `no such column`, without the question about quotes: with `t3`, `update t3 set v2 = 'x', z = 1, y = 2` gives `no such column: z`, and `update t3 set "Z""z" = 1` gives `no such column: Z"z`. The columns of WHERE follow, by the rule of a select, with the question for a name in double quotes. So `update t3 set z = 1 where y is null` gives `no such column: z`. A delete gives the table, and then the columns of its WHERE by the same rule. The errors that follow are in their order under [Types](#types). `TestEngine_update` and `TestEngine_delete` pin the order against SQLite.
- **In a read-only transaction, every error that SQLite gives when it prepares the statement comes before `attempt to write a readonly database`:** the errors of the names, the number of values of an insert, and the errors of the columns of a create table. There, `insert into t2 (v1) values (1)` without `t2` gives `no such table: t2`, and `create table t1 …` with `t1` gives `table t1 already exists`. A create index and a drop index give the errors of their names there, and a create index or a drop index without such an error gives `attempt to write a readonly database`. An insert of a key that exists gives `attempt to write a readonly database` there, and not `UNIQUE constraint failed`, as in SQLite. So does an insert of NULL, given or for a column left out, into a column that does not take it, and one of a value of another type than its column. An update and a delete give three kinds of error there before `attempt to write a readonly database`: the errors of their names, `string or blob too big` for a value that is too long, and "not supported" for a value of WHERE of another type than its column. Every other update and delete gives `attempt to write a readonly database` there, whether it finds a row or not: also an update that sets NULL in a column that does not take it, a value of another type, or a key that exists.
- **A syntax error never depends on the database.** The spec: "Text with a syntax error gets the error that SQLite gives for it on an empty database." So `stmt.Check` alone decides it, before the engine begins a transaction, and a text with a syntax error gives its syntax error also on a closed instance, without the lease, and with a context that has ended. SQLite differs on a database that is not empty: it starts to create a table as soon as it has read `CREATE TABLE`, the name, and the `(` or `AS` after it, and if a table of the name exists, it gives `table %s already exists` and never meets the syntax error. With a table `t1`, SQLite gives `table t1 already exists` for `create table t1 (v1 int primary key) strict without rowid`, and the engine gives `near "without": syntax error`, as SQLite does on an empty database. This is the one difference from SQLite that the tests accept: `stmttest.ExistsAfterStart`, which the differential tests of the engine and of the driver share, accepts it where `stmttest.StartedTable` gives the name of the table that the text starts, SQLite gives that the table exists with the name as written, and the engine gives what SQLite gives on an empty database. The other texts where SQLite gives an error that is not the syntax error are in [the known gaps of `stmt`](../sql/stmt/README.md#known-gaps).

The errors that are not SQLite's:

- **"Not supported"** is the `*stmt.NotSupportedError` of the pass, unchanged. It matches `stmt.ErrNotSupported`. The engine runs every form of slices 6 to 8 that the pass supports, and `Check` refuses none of them. A form that the pass does not support, such as `-null`, which is `NULL after a sign`, or a WHERE with `or`, stays "not supported" by the text alone.
- **A value of another type than its column is "not supported",** in an insert, in the SET of an update, and in a condition of a select, an update, or a delete; see [Types](#types).
- **An index of more than 250 columns is "not supported",** as `index of more than 250 columns`, with the offset of the 251st column. SQLite takes an index of up to 2,000 columns.
- **A text without a statement** gives `ErrNoStatement`.
- **The state of the transaction of a connection has four errors:** `ErrTxOpen`, `ErrNoTx`, `ErrRowsOpen`, and `ErrTxDone`. Each is returned as it is, but for the commit of a write transaction while a loop reads its rows, whose error wraps `ErrRowsOpen`. See [Transactions](#transactions).
- **A commit that is too large gives an error that matches `ErrTooLarge`,** and that wraps the error of the core, which matches `core.ErrTooLarge`.
- **Every other error of the core passes through unchanged,** so that `errors.Is` finds its sentinel, such as `core.ErrStopped`, `core.ErrOutcomeUnknown`, or `core.ErrReaderBusy`. So does an error of the context. Neither is ever given as a `*sqlerr.Error`.
- **A refusal of the core becomes an error that matches `ErrInternal`** and wraps nothing else; see [The storage interface](#the-storage-interface). It is a fault of s4ql, and never SQLite's error.
- **Under a lowered length limit, the engine gives an internal error for a create index that SQLite takes,** if the statement of the index in the cache is longer than the limit. The cache writes that statement with every name in double quotes, so it can be longer than the text that SQLite measures, and the core refuses it with `core.ErrInvalid`. [The todo](../../docs/todo.md#the-public-package-and-the-driver) has the open item for a table, which has the same fault.

## Changes and the last insert rowid

The engine gives what is needed to report `sqlite3_changes` and `sqlite3_last_insert_rowid` as SQLite 3.54.1 does. The differential test compares both with SQLite after every statement.

- **An insert that succeeds sets the count of changes to 1.** Its result has `Changes` 1 and `SetsChanges` true.
- **An update and a delete that succeed set the count to the number of rows that they find.** An update counts a row also when its values do not change, as SQLite does. Without WHERE the count is every row of the table, and for a statement that finds no row it is 0. Their result has `SetsChanges` true.
- **CREATE TABLE, DROP TABLE, CREATE INDEX, DROP INDEX, and SELECT leave the count as the statement before left it.** Their result has `SetsChanges` false. A select with WHERE leaves the count also when it fails, with SQLite's error or with "not supported".
- **An insert that fails with `UNIQUE constraint failed` sets the count to 0.** SQLite gives this error when it steps the statement. The engine gives `Result{SetsChanges: true}` with the error of an insert that fails after its checks: in its operator, in its annotation, or in its commit. For an insert in a write transaction, the release of its savepoint takes the place of the commit.
- **An insert that fails with `NOT NULL constraint failed` sets the count to 0 too.** SQLite gives this error when it steps the statement, as it gives `UNIQUE constraint failed`. The sink's `check` finds it, and gives "not supported" for a value of another type than its column there too, which leaves the count. `checked` in `engine.go` tells the two apart: SQLite's error gets `Result{SetsChanges: true}`, and every other error of the check the empty result.
- **An insert that a read-only transaction refuses sets the count to 0,** as SQLite does under `pragma query_only = 1`. Its result is `Result{SetsChanges: true}`. `TestConn_Begin` measured it against SQLite. A create or a drop that is refused there leaves the count.
- **An update or a delete that fails when SQLite steps it sets the count to 0:** an update with `NOT NULL constraint failed`, with `UNIQUE constraint failed`, or with `string or blob too big` for a row whose record is too long, and an update or a delete that a read-only transaction refuses. Every other failure leaves the count: an error of its names, `string or blob too big` for a value that is too long, and "not supported".
- **An error that SQLite gives when it prepares the statement leaves the count:** `no such table`, `has no column named`, `already exists`, `no such column`, the two errors of the number of values of an insert, the two errors of the columns of a create table, the errors of the names of a create index and of a drop index, and a syntax error. A text without a statement leaves it too.
- **The last insert rowid never changes.** Every table is WITHOUT ROWID, and SQLite does not record an insert into such a table. The value is 0 on a new connection, and stays 0.

The engine keeps no count between statements. A connection that reports the counts as SQLite does keeps one number, its count of changes, which starts at 0. After a statement whose result has `SetsChanges`, also one that failed, the count is `Result.Changes`; after any other statement, the count stays.

Its last insert rowid is always 0.

## Annotations

- **Each write that is committed carries one annotation: the text of its statement,** from its first token to its end. The end is that of its semicolon, if it has one.
- **The commit object of a transaction that spans statements holds one annotation for each of its statements that succeeded and that write,** in their order. `TestConn_Commit` reads them from the log.
- **Comments and semicolons before the statement, and the text after it, are left out.** A comment inside the statement stays. `  /* before */ create table t1 (v1 int primary key) strict, without rowid; -- after` is annotated as `create table t1 (v1 int primary key) strict, without rowid;`.
- **An annotation holds all the arguments of the statement,** by position, in `Statement.parameters` of the commit object: one for each parameter of an insert, an update, or a delete, and none otherwise. Those of an update are the arguments of its SET and then those of its WHERE. `insert into t3 (v3, v1, v2) values (?, 1, ?)` with the arguments 1.5 and `a` is annotated with both, in that order. An argument that is NULL is kept as the format's NULL.
- **A statement that fails commits nothing,** and leaves no annotation. A query leaves none either.
- **Every write of slice 1 that succeeds changes something.** The core writes no commit object for a transaction that changed nothing, and would then store its annotation nowhere. No statement of slice 1 on its own meets that case: a create, an insert of a new key, and a drop each change the database.
- **A transaction that spans statements can meet that case.** A create and a drop of the same table succeed and change nothing in the end. The transaction then writes no commit object, and its annotations are stored nowhere.
- **An update or a delete that finds no row meets it too.** As a statement of its own it succeeds and writes no commit object, so its annotation is stored nowhere. One that finds a row writes a commit object, also an update that sets the values that the row has.

## Parameters

Slice 2 adds the plain `?` as a value of an insert; [the README of `stmt`](../sql/stmt/README.md#insert) defines it, and `Statement.Parameters()` gives how many a statement has.

- **The text is checked first, then the arguments,** in `prepare`, before the statement needs a transaction: a syntax error, "not supported", or `ErrNoStatement` comes whatever the arguments are, and the errors of the arguments come on a stopped instance and with a context that has ended too.
- **Another number of arguments than parameters** fails with an error that matches `ErrArguments`, such as `s4ql: wrong number of arguments: 2 for a statement with 1 parameter`. SQLite binds NULL to a parameter without an argument; the engine refuses it.
- **An argument that no column holds** is "not supported", in an error that matches `stmt.ErrNotSupported`, before the statement needs a transaction: a value of no kind (`s4ql: not supported: argument 1, which has no value`), a real that is not a number or is infinite (`which is a real that is not a number`, `which is an infinite real`), and text that is not valid UTF-8 or holds the character NUL (`which is text that is not valid UTF-8`, `which is text that holds the character NUL`). The core refuses each of these with `core.ErrInvalid`, which the engine would report as an internal error, so none may reach it. An integer, every other real and text, a blob, also an empty one, and NULL are values. Whether a value is of the type of its column, and whether its column takes NULL, is checked later, when the table is known: see [Types](#types).
- **An argument that is NULL is a value since slice 6.** `checkArgument` takes it, and the refusal `argument 1, which is NULL` is gone. The driver gives NULL for a nil argument; the decisions of slice 6 in [`docs/todo.md`](../../docs/todo.md#the-sql-front-end) list what `database/sql` hands the driver as nil.
- **The insert binds the argument through `*Parameter`** of the plan, which `eval` reads from the arguments. A parameter without its argument is an internal error, which the check of the number rules out.
- **The parameters of a select are numbered across its conditions, in the order of the text.** `select v1, v2 from t3 where v1 >= ? and v2 != ? and v3 < ?` has the parameters 1, 2, and 3, and `build.bind` reads each argument through `*Parameter` too. A select writes nothing, so no annotation holds its arguments.
- **The parameters of an update are numbered across its SET and then its WHERE, in the order of the text,** and those of a delete across its conditions. `update t3 set v2 = ?, v3 = ? where v1 >= ? and v2 < ?` has the parameters 1 to 4. `build.change` reads the arguments of SET, and `build.bind` those of WHERE.
- **No value of an argument is in an error or an event.**

## Types

Slice 4 adds the column types `integer`, `real`, `text`, and `blob` beside `int`, and real, string, and blob literals and arguments; [the roadmap](../../docs/roadmap.md#slice-4-the-other-types) has what it includes.

- **A column keeps its type as declared.** `NewPlan` maps `stmt.Type` to the format's `Type`, so INT and INTEGER stay apart, in the commit object and after a replay, and `Rows.Columns` gives the declared type as SQLite reports it: `INT`, `INTEGER`, `REAL`, `TEXT`, or `BLOB`.
- **A value must have the type of its column:** an integer for INT and INTEGER, a real for REAL, text for TEXT, and a blob for BLOB. Any other value is "not supported", also where SQLite would convert it (the integer 1 for a REAL column, `'1'` for an INT column) and where SQLite gives an error of its own (`'a'` for an INT column, text for a BLOB column). The message names the value and the column, with the names as the table stores them, and no value: `s4ql: not supported: argument 1, which is text, for the column t1.v1 of type INT`, and `s4ql: not supported: a string literal for the column t1.v1 of type INT`, or `an integer literal`, `a real literal`, `a blob literal`. Such a refusal leaves the count of changes, as every "not supported" does.
- **A value that a condition compares with a column must have the type of the column too,** also where SQLite would convert it, such as `'1'` for an INT column and `1` for a REAL column. `checkType`, which also checks the values of an insert, refuses the first such value, in the order of the text, after SQLite's errors of the names and of the length. The messages are `s4ql: not supported: a string literal compared with the column t.a of type INT`, or `an integer literal`, `a real literal`, `a blob literal`, and `s4ql: not supported: argument 1, which is text, compared with the column t.a of type INT`, with the names as the table stores them. A NULL has no type and is never refused. The refusal comes in a read-only transaction too, because a select reads there as anywhere.
- **A value of the SET of an update must have the type of its column, as a value of an insert,** with the messages of an insert: `s4ql: not supported: an integer literal for the column t3.v2 of type TEXT`. The rule is of the text, so it holds also when the update finds no row, where SQLite would change nothing: with `t3`, `update t3 set v2 = 1 where v1 = 9` is refused. A value of a condition of an update or a delete is checked as that of a select, with the messages of a select, and in a read-only transaction too.
- **NULL has no type.** A column of any type that takes NULL holds it, and a NULL is never refused for its type: the check of the type passes it and goes on to the other columns. Whether a column takes NULL is the check of NOT NULL, which comes before the check of the type. A query gives a NULL back as NULL.
- **The order of the errors of an insert is SQLite's,** where SQLite gives an error: the errors of the text and of the arguments, then the names (`no such table`, then `has no column named` for the columns of the list in their order) and the number of values (`table t has N columns but M values were supplied` without a list of columns, `M values for N columns` with one), which SQLite gives when it prepares the statement; then `string or blob too big` for a text or a blob longer than the limit, which SQLite gives when it binds such an argument; then, in a read-only transaction, `attempt to write a readonly database`, which SQLite gives at its `OP_Transaction`, before it looks at a value; then `NOT NULL constraint failed` for the first column, in the order of the table, that does not take NULL and gets it, the key column too, which SQLite tests before it looks at a type; then "not supported" for the first column, in the order of the table, whose value is not NULL and is of another type, where SQLite has its `OP_TypeCheck`; then `string or blob too big` for a row whose record is longer than the limit while its values are not, also when its key exists, because SQLite builds the record of a row of a WITHOUT ROWID table before it looks for its key; and last `UNIQUE constraint failed`. A NULL that the statement gives, as a literal or as an argument, and a column that it leaves out are one case of NOT NULL, in the order of the table, also mixed in one statement. `buildSink` makes the checks up to the length, the sink's `check` makes those of NOT NULL and of the type, and `run` the rest. `run` asks the core to insert each row only if its key is new, `core.Tx.Insert`, which runs SQLite's `insert ... on conflict do nothing`: SQLite measures the record there as it does for its own insert, so the length at which the row is too long is SQLite's for every shape of table, and for a row that fits and whose key the table has nothing is inserted. `TestEngine_errors`, `TestEngine_tooBig`, `TestEngine_nulls`, and `TestConn_Begin` pin the order against SQLite.
- **The order of the errors of an update is SQLite's too,** where SQLite gives an error: the errors of the text and of the arguments; then the names (`no such table`, then `no such column` for the columns of SET in the order of the text, then `no such column` for those of WHERE by the rule of a select); then `string or blob too big` for a value of SET, and then of WHERE, that is longer than the limit, each in the order of the text, which is the order of the parameters; then "not supported" for the first value of WHERE, in the order of the text, of another type than its column, as for a select; then, in a read-only transaction, `attempt to write a readonly database`; then `NOT NULL constraint failed` for the first column of SET, in the order of the table, the key among them, that gets NULL and does not take it, if the update finds a row; then "not supported" for the first value of SET, in the order of the table, of another type than its column, whether the update finds a row or not; and last, for each row in the order of the key, `string or blob too big` for a row whose record is too long, and then `UNIQUE constraint failed` for a new key that another row has. `build.change` makes the checks up to the values of WHERE, `update.check` those of NOT NULL and of the type of SET, and `run` the rest. A delete has the errors of its table and of its WHERE, in the same places. `TestEngine_update`, `TestEngine_delete`, and `TestConn_Begin` pin the order against SQLite.
- **The limit is the core's,** `core.Options.LengthLimit`, 1,000,000,000 bytes by default, which `DB.LengthLimit` gives. Tests lower it to 1000, and compare with SQLite under `sqlite3_limit` at the same value. The engine checks the length of every value, a literal too, after the names; the core gives `core.ErrTooBig` for the record of a row, which `fromCore` turns into SQLite's error, and the transaction goes on after it. A literal longer than the limit is not compared with SQLite: SQLite meets one only with a limit below the length of the text that holds it, which `SQLITE_LIMIT_SQL_LENGTH`, also 1,000,000,000, rules out, and under the lowered limit alone it gives `string or blob too big` for a string literal only when it steps the statement, and turns a blob literal into NULL. In a condition of a select it does the same: such a string literal gets `string or blob too big`, also on an empty table, except as the upper bound of a search of the key, which SQLite evaluates only when the search reaches a row, and such a blob literal is NULL, so the select gives no rows. The engine gives `string or blob too big` for both, as for an insert. `TestEngine_where` compares the string literal with SQLite, and pins the difference of the blob literal. A literal of SET that is longer than the limit gets `string or blob too big` also when the update finds no row, where SQLite steps no value and gives no error; `TestEngine_update` pins that difference. [`docs/todo.md`](../../docs/todo.md#the-sql-front-end) has both, the first beside the open item on `statement too long`.
- **A NULL takes no bytes of its own in SQLite's record,** so a row with NULL is too long at another length than the same row with a value in the place of the NULL. The core measures the record as SQLite does. `TestEngine_tooBig` finds a length at which a row with NULL fits and the same row with a real in its place does not, and compares both with SQLite, also in a transaction and after a replay of the log.
- **A real that is -0.0 is stored as 0.0,** by the core, as SQLite stores it, and read back as 0.0. It is the key of 0.0, so either after the other is `UNIQUE constraint failed`. The annotation keeps the argument as given, -0.0.
- **Keys compare as SQLite compares them,** which the cache does: integers and reals by their number, text and blobs byte by byte. A scan gives the rows in that order of its key, or in the reverse of it; see [The order of the rows](#the-order-of-the-rows). The test double in `memory_internal_test.go` compares them so too.

## Events

The engine logs one event for each statement, named `statement`, when the statement ends. For a query, that is when its rows end. It logs one event for each transaction that spans statements, named `transaction`, when the transaction ends; see [The event of a transaction](#the-event-of-a-transaction). The names are in `telemetry.go`.

| Attribute | Value | Present |
| --- | --- | --- |
| `statement.kind` | `create_table`, `drop_table`, `create_index`, `drop_index`, `insert`, `update`, `delete`, or `select`. | When the text is a supported statement. |
| `statement.table` | The name of the table, as its value. A drop index names no table, and has the empty name. | When the text is a supported statement. |
| `statement.sql` | The text that the call was given. | When the level of the event is Debug. |
| `transaction.kind` | The kind of the transaction that spans statements: `write` or `read_only`. | For a statement that the connection is given while such a transaction is open. |
| `statement.position` | The last commit object of the state that the statement saw: the position of its read transaction, or the parent of its write transaction. In a transaction that spans statements, it is the state that the transaction began from. | Once the statement has a transaction. |
| `commit.parent` | The same value, under the core's name. | For a statement in a write transaction, also a query in a write transaction that spans statements. |
| `statement.access` | How a select, an update, or a delete reads the rows of its table: `none` for no row, `primary_key` for a get or a scan by the primary key, `index` for a scan by an index, or `full_scan`. | Once the access is chosen. A statement that fails before that has neither this attribute nor `statement.rows_read`. |
| `statement.index` | The name of the index of an access by an index, as the index was created. For a create index and a drop index, the name of the index that the statement names, as its value. | For an access by an index, and for a create index and a drop index. |
| `statement.rows_read` | The number of rows that the statement read from the cache after the choice of its access, by its scans and its gets, whether or not its conditions held for them. For a query, these are the rows of its scan or its get. An update reads each row that it changes a second time, to write it, and one row more when it checks a NULL for a column that does not take it. | With `statement.access`. |
| `statement.rows` | The number of rows that the statement returned or changed. | Always. |
| `outcome` | How the statement ended, in a word; see below. | Always. |
| `sqlite.code`, `sqlite.extended_code` | The result codes. | For SQLite's error. |
| `error` | The text of the error. | When the statement failed. |
| `duration.total` | The duration from the call to the end, on the monotonic clock of the host. | Always. |

The level follows the conventions of the core, so a healthy instance logs nothing at the default level, Info:

| Level | `outcome` | When |
| --- | --- | --- |
| Debug | `ok` | The statement succeeded. |
| Debug | `sqlite_error` | It failed with SQLite's error, which is an answer to the application. |
| Debug | `not_supported` | It is not supported. So is a statement that reads on a connection whose rows of an earlier query are open, which the core refuses with `ErrReaderBusy`: it is what the caller asked for, and nothing that went wrong. An error that matches `ErrRowsOpen` has this outcome too. |
| Debug | `tx_state` | It failed with `ErrTxOpen`, `ErrNoTx`, or `ErrTxDone`: the state of the transaction of the connection does not allow it. |
| Debug | `too_large` | Its commit failed with an error that matches `ErrTooLarge`. It is the application's transaction that is too large, and nothing that went wrong. |
| Debug | `no_statement` | The text holds no statement. |
| Debug | `wrong_arguments` | It was given another number of arguments than it has parameters. |
| Debug | `refused` | The core refused it with `ErrNoLease` or `ErrStopped`. The core logs that itself. |
| Debug | `canceled` | Its context ended. |
| Warn | `core_error` | It failed with another error of the core, such as a commit of unknown outcome. |
| Error | `internal_error` | It failed with an internal error, or panicked in the engine. |

- **A statement that panics in the engine logs one event,** with the outcome `internal_error` and the error `s4ql: internal error: the statement panicked`, and the panic goes on to the caller. This holds for a panic while the statement is checked, planned, or built, while a write runs, and while a source gives the rows of a query. A panic in the body of a loop over `Rows.All` is the application's, and ends the rows as a break does: the event has the outcome `ok` and the rows given until then.
- **The event of a write statement joins the core's event of its commit** by `commit.parent`, which is the same in both, and by the context, which both are logged with.
- **The SQL text is only in an event at Debug,** because it can hold the application's data. An event at Warn or Error has no text.
- **No value of a row is in any event.**
- **Of the three errors of `tx_state`, only `ErrTxDone` reaches an event now:** the event of a query whose loop the end of its transaction cut. A begin logs no event, and a commit or a roll back without a transaction logs none.

### The event of a transaction

The event `transaction` has the style of the event of a statement. Its level and its `outcome` follow the table of levels above, for the error of the commit or the roll back. A commit that succeeds and a roll back that succeeds are at Debug.

| Attribute | Value | Present |
| --- | --- | --- |
| `transaction.kind` | `write` or `read_only`. | Always. |
| `transaction.end` | `commit` or `rollback`. A close of the connection is a roll back. | Always. |
| `transaction.statements` | The number of statements that the connection was given while the transaction was open, also those that failed. | Always. |
| `transaction.writes` | The number of statements that changed the database and succeeded, each of which the transaction annotated. A commit object holds them only if the transaction commits and changes something in the end. | Always. |
| `transaction.position` | The last commit object of the state that the transaction began from. | Always. |
| `commit.parent` | The same value, under the core's name. | For a write transaction. |
| `outcome` | How the commit or the roll back ended, in a word. | Always. |
| `error` | The text of the error. | When the commit or the roll back failed. |
| `duration.total` | The duration from the call of the begin to the end, on the monotonic clock of the host. The wait of `Begin` for the place of the writer is in it. | Always. |

- **The event of a write transaction joins the core's event of its commit** by `commit.parent`, as the event of a write statement does.
- **The event of a statement of the transaction has the position of the transaction:** its `statement.position` is the `transaction.position`.
- **The event has no SQL text and no value.**
- **The event is logged when the transaction has ended.** That is when `Commit` or `Rollback` returns, or, if a loop reads rows of the transaction then, when the loop ends and the transaction ends with it. The event then has the error that `Commit` gave, or else the error of that later end, and its duration goes to that end.

## How it is tested

SQLite is the judge. `oracle` in `differential_test.go` runs each text on a database in memory through the binding in [`internal/sqlite`](../sqlite/README.md), as `sqlite3_prepare_v2` and `sqlite3_step` run it.

The layers:

1. **The differential test.** `TestDifferential` runs random sequences of statements on SQLite and on the engine, which runs on the real core with a simulated store. After each statement it compares the answer: the error as code, extended code, and message, or the columns and the rows. It also compares the count of changes, and requires a last insert rowid of 0. A statement that fails must leave SQLite's count as it was, with three exceptions that `pair.step` accepts, each of which sets the count to 0: a broken constraint, an insert, an update, or a delete that a read-only transaction refuses, and an insert or an update whose record is too long while none of its values is. The second occurs only in `TestConn_differential`, which runs the same step in transactions, and the third only under the lowered length limit. The generator marks each statement that is of slice 1, and the engine must support every one of them. A text that the engine does not support is not run in SQLite, which would change its database; SQLite prepares it on an empty database, and must give no syntax error, since a text that is not supported is one that SQLite accepts. The one difference from SQLite that the test accepts is that of [a syntax error after the start of a table that exists](#errors). Each call has the arguments that the generator gives: one value in three of an insert is a `?` with the value as its argument, an `int64`, a `float64`, a `string`, a `[]byte`, or nil for NULL, and one call in four of a statement with a parameter, and one in twenty of one without, has the cases around it, as [`docs/todo.md`](../../docs/todo.md#parameters) lists them. Among these cases are an `int`, an `int32`, a `uint64`, and a `float32` in place of the argument, and the arguments that no column holds: a `bool`, a `time.Time`, a `uint64` above the largest `int64`, NaN, an infinity, text that holds a NUL or is not valid UTF-8, and a nil `[]byte`. A nil argument is NULL since slice 6, so the engine takes it, and its call runs in SQLite. One of the cases around it puts a nil `[]byte` in its place, which the engine refuses. A call that the engine refuses for its arguments is not run in SQLite, which binds NULL to a missing argument and binds every type; the test checks it against s4ql's rule instead, with the exact message: the error of the number of arguments, or "not supported" for the first argument that no column holds. Half of the sequences, the third and the fourth of every four, run with the length limit of the cache and of SQLite (`sqlite3_limit`) lowered to 1,000 bytes, `stmttest.LengthLimit`. An argument that is too long, and a row whose record is too long, are compared with SQLite. An insert with a literal that is too long is not run in SQLite, and must give `string or blob too big` after the names (`pair.checkLength`, which takes the longest literal of the insert). An update or a delete with a literal that is too long, in SET or in WHERE, is not run in SQLite either. It must give the same error after the names, whether it finds a row or not, and the test counts it as `excusedLongChange`. SQLite gives that error only when it changes a row, and turns a blob literal into NULL, which is the known difference of a long literal, for SET, in [the todo](../../docs/todo.md#the-sql-front-end). An insert that SQLite prepares, with a value, a literal or an argument, of another type than its column, is not run in SQLite either, and is checked against the rule of [Types](#types). `typeRule` gives that rule, and the simulation shares it. It reads the columns of the table from SQLite, in the order of the table (`oracle.columns`), and asks `stmttest.TypeRule`, which the test of the driver shares. The rule is "not supported" for the first column, in the order of the table, whose value is of another type, with the names and the type of that column from SQLite. NULL is of no other type than any column. The rule decides nothing for an insert that gives NULL to a column that does not take it, the key among them, or leaves such a column out: SQLite gives `NOT NULL constraint failed` first, so such an insert runs in SQLite. `oracle.columns` reads from `pragma_table_info` whether a column takes NULL: its `notnull` is 0, and it is not the key. `TestTypeRule` in `stmttest` pins the rule, the faults of `stmttest.Faults` for NULL, which are "NULL in the key" and "NULL in a column that does not take it", and the cases of `stmttest.NullCases`. The rule also decides nothing in a read-only transaction, where SQLite and the engine refuse the write first, nor for an argument that is too long, which SQLite refuses when it binds it. For a select with WHERE, `typeRule` asks `stmttest.ConditionRule`: "not supported" for the first condition, in the order of the text, whose value is not NULL and is of another type than its column. That rule decides nothing where SQLite's error of a name comes first, as `stmttest.MissingColumn` gives it by SQLite's walk, or where the number of arguments differs. It holds in a read-only transaction too, where a select reads (`pair.checkType`), and `TestConditionRule` in `stmttest` pins it. For an update, `typeRule` asks `stmttest.UpdateRule`: "not supported" for the first condition of its WHERE whose value is of another type than its column, and then for the first column of its SET, in the order of the table, whose value is. That rule decides nothing where SQLite's error of a name comes first, nor where SET gives NULL to a column that does not take it and the update finds a row, because SQLite gives `NOT NULL constraint failed` first then. The rule asks SQLite whether the update finds a row, with the select of `stmttest.FoundQuery`. For a delete, `typeRule` asks `stmttest.DeleteRule`, which is the rule of a select with the same WHERE. In a read-only transaction `readOnlyRule` takes the place of `typeRule`: it decides nothing for an insert, and for an update it is the rule of the WHERE alone (`stmttest.WhereRule`), because the write is refused before a value of SET is looked at. `TestUpdateRule` in `stmttest` pins the rules of an update and of a delete. A select with a literal in a condition that is longer than the length limit is not checked against that rule, because s4ql gives `string or blob too big` before it looks at the type of a value (`pair.longCondition`). It runs in SQLite, which mostly gives the same. Where SQLite gives no error, which is [the known difference](../../docs/todo.md#the-sql-front-end), the engine must give `string or blob too big`, and the test excuses the select, and counts it as `excusedLongCondition`. An update that the engine refuses for a record that is too long, and that SQLite runs without that error, is excused as `excusedRecordSlip` only in one shape: it finds two rows or more, and when the rows change one at a time in SQLite, in the order of the key, the first error is `string or blob too big` (`pair.recordSlips`, which `TestPair_recordSlips` pins). SQLite does not always measure the record of a row after the first of a statement, which is [a known difference](../../docs/todo.md#the-sql-front-end) that depends on the platform, so the count of this excuse is not pinned. Every other call runs in SQLite with the same arguments bound, each by its type, so that an argument of another type than its column meets SQLite's errors of the names as the engine does.    Every comparison of rows with SQLite is a comparison of multisets. SQLite leaves the order of the rows of a select without `order by` unspecified, and the engine varies it from one query to the next; see [The order of the rows](#the-order-of-the-rows). So `answer.String`, which every comparison of two answers goes through, gives the rows sorted by their texts, each row in quotes. Two answers have one text only if they hold the same rows the same number of times. A row that is wrong changes an element of the sorted list. A row that is missing, one too many, or there twice changes the length of the list or another element. So the sorting hides no fault. `answer.rows` keeps the order in which the rows came, for the tests that check the order.

   A sequence comes from `stmttest.Sequence`. Its statements meet at one or two tables and at four or more names of columns, each in several spellings: some that SQLite takes for the same name, and some that it takes for another. The tenth has one to three columns at random, whose names can repeat, which SQLite refuses, and each of them outside the key takes NULL one time in two.    Every select with WHERE is read both ways, and every update and delete with WHERE finds its rows both ways. A `pair` has a second engine, `pair.other`: a second instance of the kind of its instance, in memory or on the core, with the same length limit. After `pair.step` has run a call, `pair.bothWays` runs the same call on the second engine by a path that it forces, with `Engine.SetPath` of `export_test.go`, where the first engine reads as the rules choose. The calls take the paths of `otherPaths()` in turn: every row forward, every row backward, the primary key forward, and the primary key backward, and then each index that `otherPaths` is given, forward and backward. The generated sequences create no index, so the pairs give it none. The two engines must give the same answer, with the rows as a multiset, the same message, and the same count of changes. After an update or a delete with WHERE, a select of `*` of its table must give the same rows on both. An update or a delete cannot run twice on one engine, because it changes what a second run would find. Before the generated checks of slice 8, `pair.bothWays` ran a select a second time on the same engine. The second engine runs every call, so it holds what the first holds, also in transactions, which `txDifferential` and `FuzzChanges` begin and end on both. At the end of each sequence and of each transaction, the tables of both engines are compared with SQLite. Every test that goes through `pair.step` therefore compares both ways of reading rows with SQLite, without a flag: `TestDifferential`, `TestConn_differential`, in transactions too, and the fuzz targets below. With the flag `-scanall`, the first engine reads every row, and the second reads as the rules choose.

   The comparison of the rows cannot tell a plan that reads every row from one that reads by the key. So `reachWhere` also checks the access of each select with WHERE against [the rules](#the-rules). `stmttest.KeyAccess` gives the rules for a table without an index a second time, apart from the engine's `chooseAccess`, from the columns of the table in SQLite, the conditions, and the arguments. `engine.AccessOf` in `export_test.go` gives the access that `buildQuery` gives the scan, on a reader of the one table, without an index, that reads no rows. The text of that access, as `Access.String` gives it, must be the text of the rule, so a plan that reads more rows than the rule says fails. `engine.AccessOf` knows an update and a delete too. It builds their sink with `buildSink` on the same table, which reads and writes no rows, and gives the access of the scan that finds the rows. `reachChange` compares that access with `stmttest.KeyAccess` of the select of the same conditions, which `stmttest.SelectOf` gives with its parameters numbered from 1. The check runs where a test counts what it reaches, which is in `TestDifferential` and `TestConn_differential`.

   `pair.reach` counts what the statements reach, under "reached: " in the tally. For an insert, it counts every argument by its kind, as `stmttest.ArgumentKind` names it; every literal by its kind, as `stmttest.LiteralKind` names it, which is integer, real, real -0.0, text, empty text, blob, empty blob, or null; each insert with a text or a blob of more than 900 bytes; each insert that SQLite prepares, by the type of the key column and its outcome; -0.0 in the key that meets a key that exists; and the outcome by what the insert reaches of NULL, as `stmttest.NullCases` names it. These cases are each NULL, as a literal or as an argument, into the key, into a column that takes NULL, or into one that does not; an insert that leaves out a column that takes NULL; and NULL beside a value of another type. For an insert into a table of several columns, it also counts the outcome by the form of the insert, which is without a list, with a list in the order of the table, or with a list in another order, and by its faults, as `stmttest.Faults` names them: a column that the table does not have, the wrong number of values, a column without a value, NULL in the key, NULL in a column that does not take it, a value of another type in the key, and a value of another type in another column. An insert with more than one fault is counted as "two faults". For a create table that SQLite prepares, it counts the outcome by the number of columns and by the position of the key, for a table of mixed types and one with two columns of a type, and for a table of several columns by whether none, all, or some of the columns outside the key take NULL. For a select of a table that SQLite has, it counts the outcome by the form: `*` by the number of columns, names, names in another order than the table's, a name twice, and a name that the table does not have, as written and in double quotes. It also counts a select of `*` and one of names with NULL among the values of its rows. A select of such a name in double quotes is compared with the pinned build of SQLite here, which the test of the driver cannot do with mattn's build; the default run reaches it 71 times.

   For a select with WHERE, `reachWhere` counts the outcome by each case of `stmttest.WhereCases`. These cases are each operator on the key or on another column; the value of each comparison by its kind, as a literal or as an argument; a column that the table does not have, in a comparison or under IS NULL or IS NOT NULL, alone, before other conditions, or after them, and such a column in double quotes; a value of another type; a column that is tested more than once; contradicting conditions; and how the plan reads the rows, as `stmttest.KeyAccess` gives it. The plan reads no row, a get of one key, a scan from a lower bound, a scan to an upper bound, a scan between two bounds, also two bounds that hold no key, or a scan of every row. `reachWhere` counts a select whose arguments the engine refuses apart, for their number or for an argument that no column holds. For a query that succeeds on a table with rows, it counts whether the WHERE gives none, some, or all of them. `pair.reach` counts a select with a literal in a condition longer than the length limit, and `pair.bothWays` each select that it reads both ways, and those of them in a read-only transaction.

   For an update and a delete of a table that SQLite has, `reachChange` counts the statement by its kind, with or without WHERE, and by its outcome. An outcome "ok" is "ok, rows changed" or "ok, no row found", by the count of changes. It counts apart a statement whose arguments the engine refuses. For an update, it counts each case of `stmttest.SetCases`: a column that the table does not have, also in double quotes; the key; every column; NULL for a column that does not take it; each kind of value; and a value of another type. For a WHERE, it counts the cases of `stmttest.WhereCases` of the WHERE as a whole. For a statement that succeeds on a table with rows, it counts whether the statement changes none, some, or all of them. `pair.reach` counts an update of a row whose record is too long, and an update or a delete with a literal longer than the length limit, in SET or in WHERE. `pair.bothWays` counts each update and delete with WHERE that it changes both ways, and those of them in a read-only transaction.

   The full run with the default flags requires a least number of each kind, in `reachedDifferential`: for each of the five types an insert that succeeds, one that meets a key that exists, and one of a value of another type; -0.0 that meets a key that exists, as a literal and as an argument; `string or blob too big` for TEXT and for BLOB; and every kind of literal and of argument. For slice 5 it requires create tables of one, two, and three columns, with the key at each position, of mixed types, and with two columns of a type; inserts of each form that succeed; inserts with a list in another order that meet a key that exists, a value of another type, and a column without a value; inserts with each fault, and with two; and selects of each form. For slice 6 it requires create tables of which no column, every column, and some columns outside the key take NULL; NULL as a literal and as an argument in a column that takes it, also with a key that exists and beside a value of another type; NULL as a literal and as an argument in the key and in a column that does not take it; inserts that leave out a column that takes NULL; NULL beside a value of another type in another column; and selects of `*` and of names with NULL in their rows. For slice 7 it requires each of the eight operators on the key and on another column; each comparison on the key with a value of another type; each way that the plan reads rows, also two bounds that hold no key; a WHERE that gives no row, some rows, and every row of a table with rows; each kind of value as a literal and as an argument, with NULL as both; each fault of a WHERE, which is a column that the table does not have, in each place and in double quotes, a value of another type, an argument that no column holds, the wrong number of arguments, a column tested more than once, and contradicting conditions; a literal of a condition longer than the length limit; and the selects that are read both ways. For slice 8 it requires updates and deletes, with and without WHERE, that change rows and that find none; updates and deletes that change every row, some rows, and no row of a table with rows; a change of the key that succeeds, that meets a key that exists, and that gets NULL; NULL for a column that does not take it, with a row found and without; a column of SET that the table does not have, also in double quotes; a value of another type in SET and in WHERE; each kind of literal in SET, and an integer, a real, text, a blob, and NULL as an argument there; a column of WHERE that the table does not have; `NOT NULL constraint failed` and `UNIQUE constraint failed` with and without WHERE; a record that is too long; a literal of SET longer than the length limit; arguments that s4ql refuses; each way that the scan reads the rows; and the updates and deletes that are changed both ways. Each least number is about a third of what the run gave on 2026-11-20, so that the test fails when the generator stops reaching a case. The sequence writes fewer inserts and selects since it writes updates and deletes, so two least numbers of earlier slices fell to a third of what the run gives now: -0.0 as a literal that meets a key that exists from 6 to 2, and a select of names with NULL in its rows from 25 to 7. No select of the run has a column that the table does not have under IS NULL or IS NOT NULL alone any more, so the run requires that case of a delete. The run also requires one literal longer than the length limit.
2. **Fuzzing.** `FuzzSQL` gives the engine any SQL text, on a database with a fixed set-up of tables, some with rows, with names in different cases and in quotes (`fuzzSetUp`), and gives SQLite the same text on the same tables. It compares them as the differential test does: the error as code, extended code, and message, or the columns and the rows; the count of changes; and the tables after the text. It runs on the database in memory, and `FuzzSQL_core` runs the same on the core, which is about 45 times slower. Their seeds are statements of the sequence of the differential test, the texts of `stmttest.Others`, and every 500th text of the corpus. Beside the difference of a table that exists, they excuse the known gaps of `stmt` as its tests do, and count them apart: a syntax error where an error of a grammar action of SQLite came first, and a syntax error where SQLite gives an error about the database first, such as `no such table: main.X` for a trigger.

   `FuzzDifferential` explores seeds of the generator of the differential test, on the database in memory: its input is a seed and a length, not SQL text, so the guidance of the fuzzer by coverage has little to work with, and its count of executions is not a measure of the SQL text that it covers. `FuzzDifferential_core` runs such a sequence on the core, with or without restarts, and with or without the lowered length limit.

   `FuzzTypes` gives the engine the bytes of its input as the value of an insert into a table of each of the five types, in the form that its input chooses: a text, blob, real, or integer argument, a string literal, a blob literal in lower or upper case, or SQL text in the place of the value. For each type, the value is the key of a table of one column, and the first column of two tables of two, whose second column is an INT key that the insert sets to 1 and names first in its list. In one of the two, `t_<type>_n`, the first column takes NULL. The form `formNull` gives NULL in place of the bytes, by their length: as a nil argument for a length of 1 modulo 3, by leaving the first column out of the list of a table of two for 2, and otherwise as the literal. Each insert runs twice, so that the second meets the key of the first, and a query reads each table; `pair.step` compares each call with SQLite, by the rules for arguments, types, and lengths of the differential test, and the tables are compared at the end. It runs on the database in memory, and `FuzzTypes_core` runs the same on the core, at a length limit from 1001 to 1255 bytes or SQLite's default, and replays the log into an empty cache and compares the tables again. Their seeds are 27 values at the edges of the types in every form, and values of 995 to 1002 bytes at the limit of 1001.

   `FuzzWhere` builds the WHERE of a select from the bytes of its input. The first byte chooses a table `w_<type>` of one of the five types, with a key `k` and a column `v` that takes NULL. The rows have keys at the edges of the type. One row in three has `v` NULL, and the others have `v` as the key. `whereOf` gives the select up to eight conditions, each on `k`, on `v`, or on `x`, which the table does not have, also in double quotes, and each with one of the eight operators in any of its spellings. The value of a comparison is the key of a row, a value of the type from the bytes that follow, NULL, or a value of another type, as a literal or as an argument. `pair.step` compares the select with SQLite. It runs on the database in memory, and `FuzzWhere_core` runs the same on the core. Their seeds have every operator on `k` and on `v` with each kind of value, a column that the table does not have, and several conditions.

   `FuzzChanges` builds updates and deletes from the bytes of its input. The first byte chooses a table `c_<type>` of one of the five types, with a key `k`, a column `v` that takes NULL, and a column `w` that does not. The rows are those of `FuzzWhere`, and `w` holds the value of the key. The second byte chooses whether the statements run on their own or in a write transaction, and whether that transaction commits or rolls back. `changesOf` builds up to four updates and deletes from the other bytes. An update sets the columns of a mask, which are `k`, `v`, `w`, and `x`, which the table does not have, in either order and also in double quotes. A WHERE has up to three conditions on the same four names. The values and the conditions are as `FuzzWhere` builds them, through the reader `fuzzBytes`, which `whereOf` uses too. `pair.step` compares each call with SQLite and runs it both ways, and the tables of both engines are compared with SQLite at the end. It runs on the database in memory, and `FuzzChanges_core` runs the same on the core, and replays the log into an empty cache and compares the tables again. Their seeds have updates of each column and of several, also of `x`, with each kind of value as a literal and as an argument, with and without WHERE; deletes with and without WHERE, of one row and of many; a change of the key that meets a key that exists; and several statements in a transaction.

   `FuzzCreateIndex_core` creates an index under the lowered length limit `stmttest.LengthLimit`, on the storage core and in SQLite. Its input chooses the length of the name of the index, the length of the names of its columns, from one to four columns, their direction, double quotes around the name, and what follows the statement. The engine must refuse with `string or blob too big` exactly the statements that SQLite refuses, and hold the indexes that SQLite takes, also after a restart on the same cache and after a replay of the log into an empty cache. Its seeds are a length at which the cache needs SQLite's largest limit to hold the index, a length at which SQLite refuses a text far below the limit, a text longer than the limit, and the longest name that SQLite takes on a column of one byte with the name one byte longer.

   `FuzzColumns` builds a table of several columns, and the inserts and selects on it, from the bytes of its input. The table `t` has two to four columns, `c0` to `c3`, each of one of the five types, with the key at any position. Each column outside the key takes NULL or says NOT NULL, the key says NOT NULL before PRIMARY KEY, after it, or not at all, and the two options of the table come in either order. Up to 16 inserts and selects follow, each of `t` or of `T`, and then a select of every column. An insert has no list, a list in the order of the table, a shuffled list, or a shuffled part of the columns, with names also in upper case and in double quotes. It has no fault or one of four: a value more, a value fewer, the name `x`, which the table does not have, in the list, or a name twice in it. `columnsValue` gives each value, as a literal or as an argument: one of four values of the type, so that keys meet, a value from the bytes that follow, NULL, a value of another type, a text or a blob of up to 1275 bytes, a value at an edge of the type, or an argument that no column holds. A select is of `*` or of one to four names, in the same spellings and with `x` among them, and has a WHERE of up to three conditions, each on a column or on `x`, with one of the eight operators in any of its spellings. `pair.step` compares each call with SQLite, by the rules of the differential test, so it reads a select with WHERE both ways, and the tables are compared at the end. It runs on the database in memory, and `FuzzColumns_core` runs the same on the core, at a length limit from 1001 to 1255 bytes or SQLite's default, and replays the log into an empty cache and compares the tables again. Their seeds are built by hand for five shapes of table. For each shape, after four rows, they have each kind of list, NULL in a column that takes it and in one that does not, each fault, a value of another type in each column, each kind of select, and a WHERE on each column. For the four shapes with a TEXT or a BLOB column, they also have values of 800, 1000, and 1005 bytes at the limit of 1001, where a value or a record of several is too long. Beside these are 40 inputs of random bytes from a fixed seed, half of them at that limit.

   Every fuzz target here runs its calls through `pair.step`, so each reads a select with WHERE both ways, and finds the rows of an update or a delete with WHERE both ways, as the differential test does. None of them checks the access against `stmttest.KeyAccess`, because that check runs only where a test counts what it reaches.
3. **The simulation.** `TestSimulation` runs statements under the scheduler of [`internal/sim`](../sim/README.md) while the store fails, hangs, and loses requests. The default workload has two instances that compete for the lease, two callers on each, one crash, and one close. Each caller is a `client` with a connection of the engine of its own, which it replaces when its node has opened its database again. A caller whose statement is refused for want of the lease waits up to two minutes for its instance to serve, and stops if it does not, as a client behind a check of health would turn to another instance; without that, the callers of the instance that does not hold the lease made more than half of all statements, and each was refused. The crash takes an instance that runs a statement, if one does within ten seconds, so that it often cuts one. After a crash, a new instance starts on a copy of the cache or on an empty one. Every second engine of a node reads every row of a table in each query (`run.open`): the first engine of a node reads as the rules choose, the second, which opens after a crash or a close, reads every row, and so on in turn. So the checks of the queries against SQLite see both ways of reading rows, also across crashes and closes. Each engine draws the directions of its queries from a seed of its own, which `run.open` derives from the seed of the run, the name of the node, and the number of the node's engine. It draws nothing from the host for them. So the draws of the scheduler are those of a run without the directions, and a replay of a seed reads in the same directions. The hammer workload has one instance with four callers that hardly wait, so that two statements often run at once. Its instance opens once, and reads as the rules choose. Each statement has a timeout, so a commit can end with its outcome unknown. Each statement carries an ID in a comment, which its annotation keeps, and its event gives the state that it saw. The first three seeds run twice, and the traces must be the same.

   In both workloads, one turn of a caller in four is a transaction that spans statements (`run.transaction`), on the caller's connection: a write transaction, or one time in four a read-only one, of two to six statements of the same sequence, with a wait of up to half a second before each. Its begin, each statement, and its end each have a timeout of up to the workload's, so a begin can give up its wait for the place of the writer, and a commit can end with its outcome unknown. It ends with a commit, or one time in four with a roll back. A statement that is refused for want of the lease or by a stop ends it early with a roll back, so these callers do not leave a transaction open. The idle workload adds the callers that do: it is the default workload with one idler on each instance (`run.idler`), whose two write transactions each make their statements and then sit idle while the instance is cut off from the store, half of the time for 30 to 60 seconds, long enough for the other instance to take the lease. The first runs one more statement after up to a minute and ends. The second is cut off for two minutes always, sits idle for three, and stays open after the end of the workload; the write of the end runs in it (`run.endKept`), and `run.readsFree`, which closes each instance in turn once its connections have run their query, requires that an instance where it is still open serves within ten minutes, with a violation of its own, "is open and idle, does not serve". An instance that lost its lease meanwhile must have ended the transaction. The core logs the end of a transaction for the lease, and `run.verifyOverlaps` takes it for the end of the place of the writer of that transaction, because the core frees the place before the caller ends the transaction. The engine cannot plant the core's bug `keepIdleTx`, so the check was shown by hand on 2026-11-19: with `DB.endForLease` made to do nothing, 89 of the first 100 seeds of the idle workload failed, each by that violation. Over 1,000 seeds the idle workload ended 1,348 transactions for the lease, 1,317 of them kept open, with no violation, and `TestSimulation` pins a quarter of both counts.

   `run.verify` checks each run against SQLite and the log:
   - Every commit object of the log holds the statements of one call. A statement of its own is of a call that succeeded, that had an unknown outcome, or whose instance crashed while it ran. A transaction that spans statements is a write transaction whose caller called its commit, and whose commit succeeded, had an unknown outcome, or did not return because its instance crashed; nothing of a transaction that was rolled back, or whose commit failed, is in the log. Its commit object holds exactly its statements that succeeded and that write, in order, and its parent is the state that its statements saw, so no commit landed while it was open. No statement and no transaction is in the log twice. The parameters of each statement are exactly the arguments that the caller gave, by position, kind, and value.
   - Every write that was acknowledged is in the log: a statement of its own when it succeeded, and the writes of a transaction when its commit succeeded. A transaction whose net effect is nothing writes no commit object, and its writes must not be in the log: one whose writes are all of tables that SQLite does not have at its beginning nor at its end. A write transaction whose rows SQLite has at its end as at its beginning may leave no commit object either, as one that inserted a row and deleted it: the core commits nothing for a key whose row was not there before and is not there after. An update or a delete of its own that changed no row is in no commit object, and need not be in the log.
   - The statements of the log, run in SQLite in their order with their parameters, each succeed. A parameter that is NULL is bound as NULL (`oracleValues`).
   - Every value of every insert of the log has the type of its column in SQLite, where the insert runs, as `typeRule` says. An insert with a value that does not is the violation "stores a value of another type than its column". SQLite converts some such values without an error, so the replay of the log alone does not find them.
   - Every row that a commit of the log upserts fits its table (`run.verifyRows`). The log has the table at that commit. The rows are for every column of the table, in the order of the table. Each row has one value for each column, and each value has the type of its column, or is NULL in a column that takes NULL. A NULL in any other column is the violation "holds a row of the table … with NULL in the column …, which does not take NULL". The replay of the log in SQLite runs the statements of the log, and not its rows, so it does not see a row that holds the values of its statement in other columns.
   - A statement of its own that failed with SQLite's error gives that error in SQLite on the state that it saw. An insert that the engine refused for the type of its value is refused so by `typeRule` there. A query that succeeded gives its rows there, each value compared by its type. That state is the state after a commit of the log, and it holds every write that was acknowledged before the statement started.
   - An update or a delete of its own that succeeded with a count of changes of 0 changes no row in SQLite on the state that it saw. Such a statement is in no commit object, so without this check only the engine's word says that it changed nothing. `run.verify` runs it in SQLite, in a savepoint that is rolled back, and requires no error and a count of changes of 0. A count above 0 is the violation "changes no row, is in no commit, and changes … rows in SQLite".
   - The count of changes of each update and delete that succeeded is SQLite's: for a statement of its own by the run of the statement of its commit, and for a statement of a transaction by the run of the statements of the transaction (`run.verifyTxs`). Another count is the violation "changes … rows in SQLite, and its caller was told …".
   - The statements of a transaction that spans statements all saw one state, which holds every write that was acknowledged before the begin (`run.verifyTxs`). SQLite runs the log up to that state, under `pragma query_only = 1` for a read-only transaction, and then each statement of the transaction that succeeded or failed with SQLite's error, in order, and each must give what the engine gave, a write that succeeded included: for a write transaction, the state of its beginning and its own writes so far; for a read-only one, the state of its beginning, whatever committed meanwhile. An insert of a write transaction that the engine refused for the type of its value is refused so by `typeRule` on SQLite's state at that statement. A read-only transaction must refuse no insert for its type, since it refuses the write, with `attempt to write a readonly database`, before it looks at the value, and an update only for a value of its WHERE (`readOnlyRule`). So no caller sees a write of a transaction that has not committed, of its own transaction excepted.
   - Two write transactions of one engine never overlap (`run.verifyOverlaps`): no write transaction's begin returns between the return of another's begin and the call of its end, and no statement of its own that writes both starts and commits in that time. The calls are ordered by a clock of events of the run, and an engine is one node's between two opens of its database.
   - A text that the engine does not support is one that SQLite prepares on an empty database without a syntax error, as in the differential test.
   - A new instance with an empty cache replays the log to the state that SQLite has after it, with every value of every row.

   A commit of a transaction whose outcome is unknown may be in the log or not, as for a statement of its own. One query in four is not read to its end: its loop stops at the first row, it is closed unread, or its consumer panics. Its rows are not compared, and the rest of the run must still hold. The callers run the calls of the differential test's generator with their arguments, and a call that the engine refuses for its arguments must be refused by the rule, as in the differential test. A refusal of an insert for the type of its value is checked by `typeRule` against SQLite on the state that the statement saw: in `run.verify` for a statement of its own, and in `run.verifyTxs` for a statement of a transaction. An insert of such a value that succeeds is found in the log, by the check of the type of each value there. A statement of slice 1 must not be refused as not supported. A statement that saw no state, because it failed before it had a transaction, is a syntax error, and must give what SQLite gives for it on an empty database.

   `TestSimulation` counts what each workload reaches: the statements by how they ended (succeeded, SQLite's error, unknown outcome, cut by a crash, not supported or without a statement, and refused for want of the lease, by a stop, or by the timeout), the queries not read to their end, the inserts and the selects refused for the type of a value, the acknowledged writes, the commits, the commits of more than one statement, the rows of tables of several columns in the log, the NULL values in the rows of the log, the selects with WHERE that the checks compare with SQLite, the updates and deletes, the statements in a transaction, the write and the read-only transactions, the transactions by how they ended (committed, of unknown outcome, not committed, rolled back, and not begun), the crashes followed by an empty cache and by a copy of the cache, the closes, and the faults that the store injects, by kind, from the lines of the trace that the store writes for each. In a run of at least 50 seeds, each kind must occur at least as often as `reached` says for each seed, from a fifth to a third of what the first 1,000 seeds give, so that the test fails when a kind stops happening. The least numbers of "refused for the type" are 0.5, 0.1, and 1 for each seed in the default, the idle, and the hammer workload, where the first 200 seeds gave 505, 112, and 980. The least numbers of "rows of several columns" are 1.1, 0.17, and 2 for each seed, about a quarter of the 4,591, 715, and 8,380 that the first 1,000 seeds gave on 2026-11-20. The least numbers of "NULL values in the log", which `run.verifyRows` counts, are 0.4, 0.08, and 0.67 for each seed, a quarter of the 1,581, 316, and 2,694 that the first 1,000 seeds gave the same day, when the sequence wrote NULL. `run.countWhere` counts the selects with WHERE that `run.verify` and `run.verifyTxs` compare with SQLite, of their own and in a transaction, those of them on an engine that reads every row, and those of them that give rows. The least number of each is a quarter of what the first 1,000 seeds gave the same day, when the sequence wrote WHERE. The selects of their own were 3,078 in the default workload, 1,107 of them on an engine that reads every row and 324 that give rows; 2,449, 786, and 58 in the idle workload; and 6,968, 857 of which give rows, in the hammer workload. The selects in a transaction were 4,254, 1,507, and 468; 2,875, 892, and 78; and 8,052 and 1,041. For the 58 and the 78, the least number is one in fifty seeds. `TestSimulation` also requires a least number of the updates and deletes: of all of them, of those that succeeded and changed rows, of those with SQLite's error, of those of their own that changed no row and that `run.verify` runs in SQLite, and of those of their own and of those in a transaction whose count of changes the checks compare with SQLite's. Each least number is a quarter of what the first 1,000 seeds gave the same day, when the sequence wrote updates and deletes. They gave 18,084, 1,575, 8,481, 1,845, 717, and 2,587 in the default workload; 12,853, 326, 4,609, 356, 91, and 975 in the idle workload; and 36,081, 3,412, 14,982, 3,433, 1,545, and 5,002 in the hammer workload. In such a run, at most the share `noLease` of the statements may be refused for want of the lease: 0.15 of them in the default workload and 0.12 in the hammer workload, where the first 1,000 seeds refused 0.08 and 0.07 before the workloads had transactions, and refuse 0.04 and 0.03 with them. A caller that does not wait for its instance to serve took the share to 0.60 and 0.31, measured before the workloads had transactions. The seeds are the same in every run, so the counts are too.

   A run also fails in these cases: a statement gives an error that the workload does not expect, as an internal error is; an instance stops; a close of an instance does not end within five minutes; a close of a connection fails; no instance runs a write within ten minutes after the store has calmed; a connection of a caller of a live instance has a read transaction left open after the workload; or a live instance does not run a query on each connection of its callers within ten minutes after that.

   `run.readsFree` makes the last two checks. Every connection of the callers of a live instance must run a query of a table that does not exist, which gives SQLite's `no such table` once the query has its read transaction. A connection whose read transaction was left open fails the query with `core.ErrReaderBusy`, and that is a violation at once: "… has a connection of a caller with a read transaction left open after the end of the workload". An instance that has not run the queries within ten minutes is a violation too: "… does not run a query on each connection of its callers ten minutes after the end of the workload". Only the instance that holds the lease can read, so each instance whose connections have all run their query is closed, which hands the lease to the next.
4. **Planted bugs.** `TestSimulation_plantedBugs` plants each of fifteen bugs in the engine, and runs seeds until two have found it by its own violation. A seed finds a bug only with a violation that the bug causes: a commit that fails in SQLite for `skipUnique` and `checkOutside`, and for `skipUnique` also an insert of a write transaction that succeeds where SQLite fails, an acknowledged statement that is not in the log for `ackUnknown`, no write after the workload, or an instance that does not run a query on each connection of its callers then, for `keepOpen`, whose open write transaction also keeps its instance from releasing the lease, for `keepRead` a connection with a read transaction left open after the workload, or a later query of the same connection that fails with "the reader has a read transaction open", and for `annotateNext`, which annotates each argument plus one, a commit whose parameters are not the arguments that its caller gave. Of the bugs of transactions, `keepFailed` is found by a commit object that holds other statements than its transaction's that succeeded and write, or a commit that fails in SQLite; `readNewest` by a statement of a read-only transaction that gives in SQLite another answer on the state of the beginning of its transaction, a read-only transaction whose statements saw more than one state, or an end of the transaction that fails with "the transaction has ended", because the transaction keeps the read that the bug ended when its read of the newest state fails; and `rollbackKeeps` by a transaction in the log that its caller rolled back. `convertReal` is found by an insert of the log that stores a value of another type than its column, or by a refusal for the type that is not the rule's: in a table of several columns, the real that the bug converts can be the first value of another type than its column, and the engine then refuses a later one, where the rule refuses the real. `listOrder` puts the values of a row in other columns than its statement names. It is found by a replay of the log into an empty cache that differs from SQLite, because the replay writes the rows and SQLite runs the statements; by a later insert of the log that fails in SQLite, or a statement that gives another answer than in SQLite, because the key of the row is another value; or by a refusal for the type where the rule refuses nothing, because a value is in a column of another type. No row of the log holds a value of another type than its column, because the engine's check of the type sees the values in the columns where the bug puts them. `zeroLeftOut` gives a column that takes NULL, and that the list of an insert leaves out, the zero value of its type. It is found by a query that gives the zero value where SQLite has NULL, or by a replay of the log into an empty cache that differs from SQLite, because the replay writes the rows and SQLite runs the statements. No check of a value that is not NULL finds it, because the zero value has the type of its column, and no column that takes NULL is the key. `openBound` makes a scan between bounds of the key read a closed bound, of `<=` or `>=`, as open, so that the scan leaves out the row whose key is the bound, which the filter above it would give. It is found only by a select with WHERE, of its own or in a transaction, that gives fewer rows than in SQLite, because a select writes nothing and fails nothing. An engine that reads every row, as every second engine of a node does, gives its scan no bound, and does not have the bug. `changeNothing` makes an update and a delete find no row, change nothing, and report a count of changes of 0. It is found by an update or a delete of its own that is in no commit and changes rows in SQLite on the state that it saw; by an update or a delete in a transaction whose count of changes differs from SQLite's; or by a later statement that gives another answer than in SQLite, because the rows that it should have changed are as they were. `keepOldKey` makes an update that gives a row a new key leave the row of the old key. It is found by a replay of the log into an empty cache that differs from SQLite, because the commit object holds the new row and no delete of the old key; or by a later statement that gives another answer than in SQLite, because the table holds the row twice. Since the simulation compares the counts of changes, `listOrder` and `zeroLeftOut` are also found by an update or a delete whose count of changes differs from SQLite's, as when a WHERE meets the zero value of `zeroLeftOut`. `keepRead` also leaves open the rows of a query in a transaction, so a later statement of the connection fails with "the rows of an earlier query of the connection are open". The first of these for each bug is its own, and two seeds must find the bug by it: `keepOpen` by no write after the workload, `keepRead` by the read transaction left open after the workload, `listOrder` and `keepOldKey` by the replay of the log, `zeroLeftOut` and `openBound` by the query that gives another answer than in SQLite, and `changeNothing` by the update or the delete of its own that is in no commit and changes rows in SQLite. Each seed that finds a bug runs again without it, and must find nothing. The bugs are fields of `bugs` in `bugs.go`, which only the test files can set, through `Options.Plant` in `export_test.go`.

   Of the bugs of statements of their own, a write in a transaction that spans statements (`writeIn`) plants only `skipUnique`, `convertReal`, `changeNothing`, and `keepOldKey`. `convertReal` is in `insert.check` in `operator.go`, which a statement of its own and a write in a transaction both run. In a table of one column, only the check of the log finds it, with "stores a value of another type than its column": SQLite converts the real of the log as the bug did, so the replay of the log and every comparison with SQLite agree with the engine. In a table of several columns, the check of a refusal against the rule can find it too, with "and the rule for the type of a value". `listOrder` and `zeroLeftOut` are in `buildSink` in `operator.go`, and only a statement of its own plants them: `writeIn` does not give them to `buildSink`. `changeNothing` is at the top of `changeRows`, and `keepOldKey` is in `update.run`, both in `operator.go`. They get there through a field `bugs` of `build`, `update`, and `remove`. `writeIn` gives both to `buildSink` too, so a statement of its own and one in a transaction both plant them. `ackUnknown`, `checkOutside`, `keepOpen`, and `annotateNext` are in `write`, which runs a statement of its own. `checkOutside` checks the key itself, with a `get` in its own read transaction, after the checks of the sink: the sink's `run` calls no `get` since every row goes through `insertNew`. The write that follows goes through `upsert`, as with `skipUnique`. The pinned order of its calls did not change. `keepRead` is in `Rows.Close`, so it also leaves open the rows of a query in a transaction. The three bugs of transactions are in `tx.go`: `keepFailed` in `writeIn`, `readNewest` in `Conn.ready`, which every statement of a transaction passes, and `rollbackKeeps` in `Conn.Rollback`. `openBound` is in `bugs.reader` in `bugs.go`, which wraps the reader that `Conn.query` and `Conn.queryIn` give `buildQuery`, so a query of its own and a query in a transaction both plant it.

   The bug that the brief of the checks of transactions asked for first, a rollback to the savepoint that is skipped after a failed statement so that its change commits, cannot be found with the statements of slice 1, because no statement of slice 1 fails after it has changed anything. An insert writes one row, checks its table and its columns before it writes, and writes nothing for a key that exists; a create checks the name, and a drop the table, before they change anything; the context is checked before the write and not after it; and nothing yields to the scheduler between the write and the annotation, where a stop of the instance would come. A failed statement therefore has nothing to roll back, and a release in place of the rollback to the savepoint leaves the same transaction. A probe on 2026-11-19 planted it as `skipRollbackTo`, which released the savepoint of a failed statement instead of rolling back to it, and 100 seeds of the default workload found nothing. `keepFailed` is the nearest bug that the statements of slice 1 make visible: it skips the rollback to the savepoint and keeps the failed statement, annotated, in the transaction. Since slice 8 a statement can fail after a write: an update that gives a row the key of another has deleted the old row when `insertNew` finds the key. `TestConn_Begin` shows that the rollback to the savepoint puts the old row back, and `TestConn_writeIn` in `tx_internal_test.go` shows the order of its calls against a fake.

11. **Mutation testing.** [`internal/sql/mutation`](../sql/mutation/README.md) mutates this package too, and runs the simulation as a layer of its own.

Under `-short`, the race detector, or the address sanitizer, `TestDifferential`, `TestSimulation`, `TestEngine_noneOpen`, `TestEngine_namesOfTheCore`, and `TestConn_differential` run a tenth of their sequences, seeds, statements, and names, and the simulation at least two seeds.

**The simulation runs no crashes under the address sanitizer.** A crashed database stays open until the test binary ends, because only the core's own tests can close the cache of a crashed instance. The sanitizer reports what is left open.

The flags of the test binary:

- `-seed` is the first seed of the sequences of statements. The default is 0.
- `-sequences` is the number of sequences of `TestDifferential`. The default is 300.
- `-length` is the number of statements in each sequence. The default is 40.
- `-scanall` makes each query of `TestDifferential` and `FuzzDifferential_core` read every row of its table, and not the rows that the rules choose. Every test that goes through `pair.step` reads rows both ways, with the flag and without it: `pair.bothWays` runs each call on a second engine, which reads another way.
- `-directions` is the seed of the directions of the queries of every instance of the tests. The default is 0, and each instance then draws a seed. Every engine of an instance has a seed: the engine of the n-th open of an instance has the seed of the instance plus n, unless its options have a seed. A test that fails logs the seed of each of its instances, with the flag that runs the test again in the same directions.
- `-replay` makes `TestSimulation` replay that one seed, and nothing else, and log its whole trace. `-workload` chooses the workload: `default`, the default, or `hammer`.
- `-bug` plants the bug of that name in the replay.

A seed that fails in `TestSimulation` or `TestSimulation_plantedBugs` prints the command that replays it, with `-race` or `-asan` if the run that failed had one: the simulation runs no crashes under the address sanitizer, so a replay without it would be another run.

The environment variables:

- `S4QL_ENGINE_SIM_SEEDS` sets the number of seeds of each workload of `TestSimulation`, 50 by default. For `TestSimulation_plantedBugs` it sets the limit, 100 by default, and makes the test run every seed up to it, to count how many find each bug.

Examples of larger runs:

```sh
go test ./internal/engine/ -run '^TestDifferential$' -sequences 10000 -length 40
go test ./internal/engine/ -run '^$' -fuzz '^FuzzDifferential$' -fuzztime 10m
go test ./internal/engine/ -run '^$' -fuzz '^FuzzDifferential_core$' -fuzztime 10m
S4QL_ENGINE_SIM_SEEDS=1000 go test ./internal/engine/ -run '^TestSimulation$'
S4QL_ENGINE_SIM_SEEDS=1000 go test ./internal/engine/ -run '^TestSimulation_plantedBugs$'
go test -run '^TestSimulation$' -v ./internal/engine/ -replay 7 -bug skipUnique
```
