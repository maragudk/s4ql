  The storage format and the storage core now handle all five types, with exact
  types, -0.0 stored as 0.0, and a new `core.ErrTooBig`. The work is on branch
  `types-core`, based on `origin/binding-types`: 9 commits, not pushed. `make

  ## Format
  - `enum Type` gets `TYPE_INTEGER=2`, `TYPE_REAL=3`, `TYPE_TEXT=4`,
  `TYPE_BLOB=5`. `int` and `integer` stay apart. The code was regenerated with
  `make generate`.
  - In a row or a primary key, the reader and the writer now refuse text with
  NUL, an infinite real, and -0.0 (new `checkStored` in
  `internal/format/check.go`).
  - In an annotation parameter, the writer refuses NaN, infinities and text with
  NUL, but keeps -0.0 with its sign. The reader still checks no annotations.

  ## Core
  - **Declared types:** `typeNames`/`typeOf` in `cache.go` declare and load the
  five types, compared without case, because SQLite reports strict types in
  capitals.
  - **Reading and binding:** `bind` handles reals, text and blobs, and binds
  -0.0 as 0.0. `readRow` reads all kinds.
  - **Exact types:** `table.checkValue(position, v, limit)` checks them before
  SQLite sees the value. It refuses NaN and infinities in a real, and invalid
  UTF-8 or NUL in text, with `ErrInvalid`.
  - **Too-long values:** `ErrTooBig` is not wrapped in `ErrInvalid`. A text or
  blob longer than the limit is refused before SQLite. SQLite's `SQLITE_TOOBIG`
  (code 18) from the row write in `Upsert` also becomes `ErrTooBig`, and the
  transaction stays usable.
  - **The limit:** an unexported option `lengthLimit` (default 1,000,000,000,
  set with `SetLengthLimit` on every connection). Tests lower it through
  `Options.SetLengthLimit` in `export_test.go`.
  - **Touched keys:** this changed more than expected. The single temporary
  table with an `existed` column is replaced by two key-only tables,
  `s4ql_touched_N` and `s4ql_existed_N`.
    - The key is recorded after the write succeeds.
    - `Delete` records a key only if it found the row, but still marks the table
  as changed so the order of tables in the commit object stays the same.
    - `spoolTouched` reads with a `cross join`, so SQLite sorts nothing.
  - **Planted bug `blobCut`**, at `Tx.committed`: the commit object cuts a blob
  at its first zero byte.

  ## Decisions of detail
  - **-0.0:** the core stores it as 0.0 and does not refuse it, which is what
  the roadmap's slice 4 says. SQLite would store 0.0 anyway; `bind` normalising
  it is a second guard. The commit object is written from the cache, so it holds
  0.0. Annotations keep -0.0. Tested for the cache, the commit object,
  Get/Delete with -0.0, and replay.
  - **Too-long value:** `ErrTooBig` is returned exactly where SQLite's own table
  refuses the row. SQLite counts the whole record of the row, header included,
  so the boundary is a few bytes below the limit and depends on the table's
  shape.
    - That is why the temporary tables hold keys only: the old `existed` column
  made the key's record one byte longer than the row's, so the core would refuse
  a row that SQLite's own table accepts.
    - It is also why the commit query must not sort: a sorter's record holds the
  key and the row together. `TestTx_tooBig` caught this with a `union all`
  design, which failed the commit with SQLite's "string or blob too big".
    - `TestTx_tooBig` uses a limit of 1000 and compares every length from 980 to
  1002 with SQLite's own table, in four table shapes, both for a table created
  in the transaction and one that existed before.
  - **Cache version stays 1.** A table of `int` columns is declared exactly as
  before, and the layout itself is unchanged; temp tables never reach the file.

  **Verdict: merge as is.** I found nothing that can corrupt or lose data. `go
  test -short ./internal/core/ ./internal/format/` passes (core 52s, format
  0.2s). I mutated four spots to probe the tests and restored the worktree after
  each; it is clean, and nothing was pushed.

  **1. Net effect per key (`Upsert`, `Delete`, `touch`, `spoolTouched`): correct
  in every sequence I traced.**
  - Upsert, then delete, of a key that did not exist: the key is in `touched`
  only, so nothing is written.
  - Delete, then upsert, of a key that existed: the key is in both tables and
  the row is there, so one upsert.
  - Delete of a key that never existed: `found` is false and nothing is
  recorded.
  - A failed upsert is caught by `checkRow` before SQLite, or by a TOOBIG
  statement rollback, before `touch`.
  - Savepoints: `Savepoint` copies each `txTable`, names included, and SQLite's
  savepoint rolls back the temp DDL and rows with it. A first touch undone by
  `RollbackTo` is recorded again later with the right `existed`. `tx.temps` is
  not rolled back, so names stay unique.
  - An `int` key and a `real` key cannot meet, because each strict column has
  one type and `checkValue` enforces the kind.
  - `0.0` and `-0.0` compare equal in SQLite, and NaN is refused, so no other
  pair of reals can collide.
  - Commit order is deterministic: an explicit `order by` on the temp table's
  primary key.
  - Mutations: passing `existed=false` from `Upsert` is caught by
  `TestTx_Savepoint_random`. `TestTx_types` misses it, because it only deletes
  before upserting again. Recording `existed` on a later touch (dropping the
  `first == 0` guard) is caught by `TestTx_Savepoint_random` and
  `TestTx_tooBig`.

  **2. Values reaching SQLite (`checkValue`, `bind`, `readRow`, `typeOf`): no
  conversion is possible.** Kinds must match the column type exactly, and
  SQLite's integer storage of integral reals in a REAL column reads back bit for
  bit. An empty blob and an empty text never meet, since their columns differ.
  `BindBlob` binds nil as an empty blob, and a nil `Blob` is no value, which
  `checkValue` refuses. The commit object is built from rows read back from the
  cache, so it holds what the cache holds.

  **3. Reader and writer (`format/check.go`): symmetric.** Both use
