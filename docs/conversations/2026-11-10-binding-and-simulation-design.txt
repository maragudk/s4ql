  The rule: any local I/O failure on the cache puts the database handle into a
  terminal stopped state. That covers a failure at commit, in a read, in a write
  before the swap, or during catch-up. There is no retry in place, because
  after a failed fsync the local state cannot be trusted until it is reopened.

  What "stopped" means: s4ql is a library, so it cannot crash the process. The
  handle is dead instead: no new statement starts, in-flight reads and queued
  writers get a sticky error that wraps the cause, and renewal stops.

  The committing caller: Commit returns success if the swap succeeded, because
  the transaction is durable. The handle stops first, so no read can ever show
  the old state after the acknowledgement. The spec's rule becomes "acknowledged
  after the cache has it, or after the instance has stopped serving".

  The lease: stop first, then try once to release it. If the release fails, the
  lease times out as it would after a crash.

  Recovery: the application closes and reopens, which is the normal startup
  path. The cache's recorded position says whether the local commit landed, so
  recovery does not need to know what went wrong. It also covers the case where
  the local commit succeeded but reported an error.

  A persistent failure: Open fails loudly. Nothing deletes or rebuilds the cache
  automatically, in line with the spec's "refused loudly, not rebuilt
  silently".

  Simulation: two buggify variants after the swap. One rolls back the local
  commit and reports an error; the other commits and reports an error. The
  invariant to check is that no read starting after an acknowledged commit
  returns a state without it.

  Three decisions are yours:

  1. Uniform stop. Should every local I/O failure stop the handle, including a
     full disk in a write before the swap, where nothing was committed? I
     recommend yes: one rule and one tested path, at the cost of availability on

  ## Short answer

  "Return success, then stop serving" is how established systems end up
  behaving, but they get there by ordering, not by a decision made after the
  failure. In the closest analogies (FoundationDB, CockroachDB, Neon, etcd),
  applying the entry to the local store is not on the acknowledgement path at
  all. The client gets success as soon as the authoritative log is durable. If
  the local apply fails afterwards, that node or role dies, and it recovers by
  replaying the log or rebuilding from other copies.

  I found no system that sees the local failure before replying and then
  deliberately replies with plain success. The nearest is PostgreSQL's
  synchronous-replication cancel path. It replies with success plus a WARNING,
  because an ERROR "would lead the client to believe that the transaction
  aborted, which is not true".

  Servers that hit a fatal error before replying die without replying:
  PostgreSQL PANIC, MySQL `ABORT_SERVER`, etcd, rqlite. The client sees a lost
  connection, which client libraries report as "outcome unknown". No system I
  checked returns an error meaning "not committed" once the authoritative record
  is durable.

  The precedents support the proposal, with one caveat: make the stopped state
  loud and visible, as PostgreSQL does with its WARNING.

  ## Per system (V = primary source read in this run, I = inferred or from
  memory)

  - **PostgreSQL, sync replication wait cancelled** (V, `syncrep.c`, https://git
  hub.com/postgres/postgres/blob/master/src/backend/replication/syncrep.c)
    - Client told: on cancel, success plus WARNING "The transaction has already
  committed locally, but might not have been replicated to the standby". On
  terminate, the same WARNING, then no reply, and the backend exits.
    - Reasoning: an error would falsely mean "aborted", and a plain ack would
  falsely mean "replicated".
  - **PostgreSQL, fsync failure** (V, `data_sync_retry` in
  https://www.postgresql.org/docs/current/runtime-config-error-handling.html)
    - Node: PANIC, then recovery from WAL.
    - Reasoning: page-cache state is unknown after a write-back failure, so
  retrying in place can report success after data was lost.
    - `xact.c` (V) runs the commit record write in a critical section, and it
  PANICs on "cannot abort transaction ..., it was already committed".
  - **MySQL** (V,
  https://dev.mysql.com/doc/refman/8.4/en/replication-options-binary-log.html)
    - `binlog_error_action=ABORT_SERVER` (the default) shuts the server down on
  binlog write, flush or sync errors. Restart recovers as after a crash.
    - V, `sql/binlog.cc`: the engine-commit step after the binlog sync returns
  `void`, so MySQL treats it as infallible and has no error path to the client.
    - I: InnoDB aborts the server on redo-log I/O errors.
  - **CockroachDB** (V, `kvserver/apply/task.go`, `replica_raft.go`,
  https://github.com/cockroachdb/cockroach)
    - Client told: success before the write is applied ("the raft log is the
  provider of atomicity and durability ..., not ... the replicated state machine
  itself").
    - Node: any apply error is `log.Fatalf`, so the process exits.
    - V,
  https://docs.cockroachlabs.com/docs/stable/cluster-setup-troubleshooting: a
  disk stall of 20 s or more terminates the process.
    - `AmbiguousResultError` (V, `errors.proto`) is what a client gets when the
  response is lost.
    - This is the strongest precedent for success followed by the node stopping.
  - **etcd** (V, `etcdserver/server.go`, `backend/backend.go`, `batch_tx.go`)
    - Client told: success after the entry is applied to an in-memory batch
  transaction. The bbolt commit happens later on a timer.
    - Node: `Fatal("failed to commit tx")`, then restart and replay of the raft
  WAL.
  - **rqlite** (V, `store/store.go`)
    - Node: a whole-request apply error is `Fatalf("... aborting to prevent
  divergence between nodes")`.
    - Client told: nothing, because the reply comes after apply.
    - I: I could not verify whether an SQLite I/O error counts as a
  per-statement error or a request error.
  - **TiKV** (V, `raftstore/.../apply.rs`)
    - Node: `panic!("failed to write to engine")`.
    - Reply timing: not verified.
  - **FoundationDB** (V, https://apple.github.io/foundationdb/architecture.html,
  `fdbserver/worker/worker.cpp`)
    - Client told: success once the mutations are durable on the transaction
  logs. Storage servers pull them later.
    - Node: a storage role with `io_error` ends, data distribution repairs the
  team, and the old disk files are deleted. So the store is rebuilt, not
  repaired in place.
    - V, developer guide: `commit_unknown_result` is used only when the client
  genuinely does not know. Retrying after it can double-apply non-idempotent
  transactions.
  - **Neon** (V, https://neon.com/docs/introduction/architecture-overview)
    - Client told: committed at a safekeeper quorum.
    - Node: a failed pageserver is replaced and rebuilds its pages from WAL and
  object storage.
  - **Durable Objects** (V,
  https://blog.cloudflare.com/durable-objects-easy-fast-correct-choose-three/)
    - If the authoritative write fails, the held responses are replaced with
  errors, which is truthful there.
    - The object is "shut down and restarted from scratch".
  - **SlateDB** (V via the project's note `slatedb.md`, not re-read here)
    - A fatal WAL error makes the writer unusable. Recovery is reopen.
  - **SQLite** (V, `pager.c`)
    - In rollback-journal mode, COMMIT can return an I/O error after the commit
  point. The code says "At this point the transaction is committed", then runs
  truncates that can fail.
    - In WAL mode (V for the ordering in `wal.c`, I for the consequence): the
  commit frame is written before the fsync, so a failed sync may still leave a
  transaction that recovery will treat as committed.
    - Docs (V): the docs do not say whether a failed COMMIT may have committed.
  - **Not checked:** mvSQLite, turbopuffer, WarpStream, dqlite, Kafka. Aurora
  only from memory (I).

  ## Precedents against, and what they imply

  1. **Most servers never reply in this state.** They die, and the client sees
  "unknown". An embedded library cannot drop the connection, though, and s4ql
  knows the outcome. Returning "unknown" would push the application into a retry
  or an idempotency check for a question that is already answered.
  2. **PostgreSQL refuses a plain ack when the ack promises more than
  happened.** If s4ql's "committed" also promises that this handle will show the
  write, success is honest only because the handle stops. Make the stop loud:
  every later call returns a distinct stopped error that wraps the I/O cause, it
  is logged at error level, and it is visible in health checks.
  3. **An error invites a retry that applies the transaction twice.**
  FoundationDB documents this as its biggest gotcha. That supports returning
  success, not an error.
  4. **For the recovery story, SQLite's IOERR on COMMIT does not tell you
  whether the cache committed.** Recovery must read the cache's recorded
  last-applied change file and catch up from there, never assume either way. The
  spec already records that position in the same local transaction as the rows.
  Retrying in place is unsafe, for the same reason PostgreSQL gives for
  `data_sync_retry`.

  Almost all Go code treats any error from Commit as "it did not commit". A job

  Both write the transaction twice, which is the outcome we were avoiding. Only
  callers that check for the specific error get it right.

  ### The minimum API, decided from slice 1
  - `Open(path)` (read-write, create, extended result codes) and `Conn.Close`.
  - `Conn.Prepare`: exactly one statement. It refuses trailing SQL, comments,
  NUL bytes and empty SQL, because SQLite would otherwise ignore part of the
  input.
  - `Conn.Exec`: written in Go over Prepare, Step and Finalize.
  - `Stmt.BindInt64`, `Stmt.Step`, `Stmt.ColumnCount`, `Stmt.ColumnName`,
  `Stmt.ColumnType`, `Stmt.ColumnInt64`, `Stmt.Finalize`.
  - `Error{Code ResultCode (extended), Message}` with `Code.Primary()`.
  - `Version`, `SourceID`, `CompileOptions`.

  There is no reset, no `sqlite3_exec` and no transaction API: each statement
  runs in its own transaction, as SQLite does by default. I kept two calls
  beyond the strict list:
  - **`ColumnType`**: without it, an integer read cannot tell an integer from
  NULL or a converted value.
  - **`ColumnName`**: `select *` results have names that the oracle should
  compare.

  Strike them if you disagree.

  Misuse of the column methods panics. That covers a read without a current row,
  an index out of range, and any column call on a finalized statement. Bind and
  Step on a finalized statement return `SQLITE_MISUSE`.

  ### Compile options (`options.h`), for review
  The rule: an option must implement a roadmap restriction, make misuse
  detectable or impossible, or be needed by the build. Options that only tune
  performance are left out.
  - **`SQLITE_DQS=0`**: double quotes mean identifiers only (roadmap). One
  exception remains: SQLite reads any identifier after `DEFAULT`, quoted or not,
  as a string. That is pinned by a test, and the engine must reject it itself.
  - **`SQLITE_DEFAULT_FOREIGN_KEYS=1`**: foreign keys are on for every new
  connection (roadmap).
  - **`SQLITE_THREADSAFE=1`**: SQLite's default, stated explicitly. It protects
  SQLite's own structures if a connection is misused from two goroutines.
  - **`SQLITE_ENABLE_API_ARMOR`**: misuse of the C API returns `SQLITE_MISUSE`
  instead of undefined behaviour. No SQL result changes.
  - **`SQLITE_OMIT_AUTORESET`**: stepping a finished or failed statement returns
  `SQLITE_MISUSE` instead of silently running it again. The exception is after
  `SQLITE_BUSY` or `SQLITE_LOCKED`, where SQLite still restarts the statement.
  - **`SQLITE_OMIT_SHARED_CACHE`**: shared-cache mode is obsolete and changes
  isolation.
  - **`SQLITE_OMIT_LOAD_EXTENSION`**: the binding cannot load extensions, and
  without this Linux also needs `-ldl`.

  Left out on purpose:
  - `SQLITE_OMIT_DEPRECATED`: I tested it, and it does not remove the deprecated
  PRAGMAs as I had assumed. It does change how the default cache size is
  chosen.
  - `SQLITE_LIKE_DOESNT_MATCH_BLOBS`: it changes `LIKE` on blobs compared with
  stock SQLite.
  - `SQLITE_ENABLE_MATH_FUNCTIONS`: the official CLI has it.
  - `SQLITE_TRUSTED_SCHEMA=0`, and the performance options (`WAL_SYNCHRONOUS`,

⏺ Yes, and I think it's worth revisiting. Here is what it is, in plain terms.

  What it means. There are two ways to write a commit. The plain way reads top
  to bottom and calls S3 and SQLite directly:

  func (db *DB) commit(tx *Tx) error {
      file := db.s3.Upload(tx.changes)
      db.s3.SwapManifest(file)
      return db.cache.Commit()
  }

  The state machine way splits deciding from doing. The logic never calls S3 or
  SQLite. It is told what just happened and answers what to do next, and
  separate "driver" code does the real calls and reports back:

  commit requested  →  "upload this file"
  upload finished   →  "swap the manifest"
  swap succeeded    →  "commit to the cache"
  cache committed   →  "tell the caller it is committed"

  Why it is in the spec. The spec says it "is what lets the simulation replay a
  run exactly". A test can feed that logic any sequence of events, including
  failures in odd orders, with no real S3, clock or goroutines.

  What today's research showed. That claim is weaker than it looked:

  - The state machine does not solve the hard part, which is the order
    goroutines run in. That lives in the driver, and so do the rules most likely
    to break.
  - It fits interactive transactions poorly, where the application runs its own
    code between statements.
  - If design B's seeded scheduler works, it makes plain code like the first
    example replay exactly too. The replay then comes from S3, time and
    randomness being behind interfaces, which the spec already requires, plus
    the scheduler. The shape of the code no longer matters.

  What dropping it costs. We lose the ability to test the commit logic against
  any order of events with no concurrency at all. We also lose the fallback: if
  the seeded scheduler turns out not to work, a state machine is the one design
  that still gives exact replay of the core.

  I recommend dropping it and writing plain blocking Go: one writer at a time,
  one owner of the manifest, everything external behind interfaces. Plain code
  is also code you can read and review, which matters when the goal is trust.
  The condition is the spike: it must show that the scheduler replays plain
  concurrent code. If it fails, we choose again between a state machine and
  giving up exact replay of ordering.

❯ State design B again                                                          

⏺ Design B: the real library, run one goroutine at a time under a seed.

  Production. Plain blocking Go, no state machine:

  - Each caller's goroutine does its own work top to bottom.
  - A lock lets one write transaction through at a time.
  - One background goroutine renews the lease.
  - S3, time and randomness are behind interfaces. SQLite is called through our
    binding.

  Simulation. The same library code, unchanged, inside a testing/synctest test:

  - Fakes. S3 is a simulated object store, time is fake, and randomness comes
    from the seed.
  - Callers. The test starts goroutines that play application callers.
  - Parking. Wherever a goroutine meets the outside world, it stops and waits:
    at an S3 call, at a timer, and at marked points in a read.
  - Scheduling. A scheduler waits until every goroutine is parked, picks one by
    the seed, lets it run to its next parking point, and repeats. So exactly one
    goroutine runs at a time, and the seed decides the order.
  - SQLite. Its calls run to completion inside whichever goroutine is running.
  - Faults. The fake S3 and the buggify points inject failures, also from the
    seed.
  - Self-check. Every seed is run twice and the two runs are compared, so any
    nondeterminism that leaks in fails the test.

  A second mode. The same tests run with the scheduler off, under the race
  detector. Goroutines then run truly in parallel, which finds data races, but a
  failure there cannot be replayed from the seed.

  What it costs. Three rules the compiler does not enforce:

  - All waiting on time goes through our clock interface.
  - No goroutine parks while holding an ordinary mutex. A lock held across I/O
    must be built on a channel.
  - Parking points have stable names.

  What it cannot do. Replay two SQLite calls running at the same instant. It
  also only works under go test.

  What is unproven. That this works at all in Go with real SQLite. The spike
  builds the scheduler with a toy workload and checks that running a seed twice
  gives the same result.

  Here is design B as it stands after the spike.

  Production

  - Plain blocking Go. Each caller's goroutine does its own work top to bottom.
    There is no state machine.
  - Two locks. A writer lock is held for a whole write transaction, so one runs
    at a time. A separate manifest lock is held only around each swap, so lease
    renewal can run while a write transaction sits open.
  - One background goroutine, which renews the lease.
  - Readers run in parallel on pooled SQLite connections.
  - One small runtime interface for everything that waits: starting a goroutine,
    locks, sleeping and timers, the clock, timeouts, and yielding. In
    production it maps straight onto ordinary Go.
  - S3 and randomness sit behind interfaces, as the spec says.
  - SQLite's "busy" must be handled on the write connection. How is open until
    the investigation reports.

  Simulation, scheduled mode

  - Same library code, inside a testing/synctest test. Test goroutines play the
    application's callers.
  - The scheduler implements the runtime interface. It owns the clock, the locks
    and the randomness. The spike found two reasons it cannot leave these to
    Go: timers due at the same instant fire in random order, and a channel-based
    lock wakes the next holder directly, so two goroutines would run at once.
  - One goroutine runs at a time. It runs until it waits: at an S3 call, a
    sleep, taking or releasing a lock, or an explicit yield. The seed then picks
    who goes next.
  - Random delays. Half of all yields get a random simulated delay, or
    timer-driven work such as renewal never gets in between.
  - Faults. The fake S3 injects latency, errors, operations that succeed but
    report failure, and delays longer than the lease. Buggify points add more.
  - Run twice. Every seed runs twice and the traces are compared.
  - Replay. One command reruns a single seed and prints its trace.

  Simulation, free-running mode

  ## Root cause (proven)

  When a reader starts a read transaction while the writer is committing, it can
  read the two copies of the WAL-index header while they differ. It then takes
  WAL_WRITE_LOCK for a moment to read the header again. If the writer's next
  `begin immediate` arrives in that window, the writer finds WAL_WRITE_LOCK held
  by a sibling connection and gets SQLITE_BUSY at once.

  The path in `internal/sqlite/c/sqlite3.c`:
  - The writer writes the header at commit: `walIndexWriteHdr`, line 67846; it
  copies `aHdr[1]`, then a barrier, then `aHdr[0]` (67855-67857).
  - The reader sees the mismatch in `walIndexTryHdr`: `return 1; /* Dirty read
  */` (69574).
  - `walIndexReadHdr`, 69656-69668: "So get a WRITE lock and try again." It
  calls `walLockExclusive(pWal, WAL_WRITE_LOCK, 1)`.
  - The writer fails at 70679-70683 ("Only one writer allowed at a time...
  Return SQLITE_BUSY if unable"). `unixShmLock` returns BUSY right away when a
  sibling holds the lock (46092-46098).

  **Evidence (verified):** I instrumented a scratch copy of the amalgamation.
  Under the shm mutex it records who holds lock 0, the call site, and why that
  thread's header read failed. In three macOS runs the writer failed 38, 52 and
  70 times. Each time, the log shows a failure at 70682 with a reader holding
  the lock at 69668 after a dirty read, in exactly the same numbers. Linux
  matched too (192 = 192). For the counterfactual I patched readers to retry
  instead of taking the lock: 0 writer failures in 3 runs on macOS and 1 on
  Linux.

  ## Answers

  1. **Reproduce (verified).** The failing call is `begin immediate`, extended
  code exactly 5, with the message "database is locked". Through the Go binding
  I measured 32, 34 and 32 per 3000 transactions (temporary test, now deleted).
  In the C harness it was 36–125 on macOS and 182–389 in a Linux container.
  Readers never got any error in steady state, over about 100 runs of 100k–3M
  reads each, including FULL, RESTART and TRUNCATE checkpoints.
  2. **Docs.** https://sqlite.org/wal.html's section "Sometimes Queries Return
  SQLITE_BUSY In WAL Mode" lists exclusive locking mode, the last connection's
  cleanup, and recovery. It does not mention this race.
  3. **Conditions (verified, 5 runs each).** None of these removes it:
     - turning off autocheckpoint, or manual checkpoints of any mode
     - readers reopening a connection per read, or reading without an explicit
  transaction
     - `synchronous` set to normal or off
     - `begin exclusive`; a deferred `begin` only moves the failure to the first
  write statement
     - the platform: it happens on macOS and Linux, more often on Linux
     - the number of readers: even 1 reader got 85 and 532 failures per 30000 in
  two of five runs

     The smallest fix: `busy_timeout = 1` on the writer, with 0 failures on both
  platforms.
  4. **Other ways BUSY reaches us (verified unless noted):**
     - **Recovery:** the first statement on other connections gets **261
  BUSY_RECOVERY**, readers and writer alike, in the same process. The docs say
  "different process". Measured: a 100 MB WAL took about 20 ms to recover with a
  warm page cache.
     - **Last connection closing:** it holds an EXCLUSIVE lock on the database
  file (`sqlite3WalClose`, 69481-69483), so a new connection's first statement
  gets **5**.
     - **517 BUSY_SNAPSHOT:** returned at once even with a busy timeout.
  Repeating the statement in the same transaction fails again; it is cleared
  only by rollback and restart. It cannot happen with one writer using `begin
  immediate` (inferred).
     - **FULL, RESTART and TRUNCATE checkpoints** return 5 while readers are
  active, even with a 1000 ms timeout.
     - **SQLITE_PROTOCOL (15):** returned after 100 internal retries, under 10 s
  in total (70006-70010). Never seen in testing.
     - **BUSY_TIMEOUT:** cannot occur in our build.
  5. **The busy handler** covers 5 and 261 only at transaction start
  (`btreeBeginTrans`, 76497).

  The cause. When a reader starts while the writer is committing, it can catch
  SQLite's WAL index header half-updated. It then takes the WAL write lock for a
  moment to read the header again. If the writer's next begin immediate lands
  in that window, it gets "busy" at once. The agent proved this with an

  lock after such a read, on macOS and Linux. SQLite's documentation does not
  mention this case.

  connections, or fewer readers: even one reader triggers it.

  What I'm choosing, as implementation detail:

    the window by itself. With a timeout of one millisecond the failures already

❯ I don't fully understand the consequences of unix-excl mode.                  

⏺ In short: it changes who may open the cache file and where SQLite keeps one
  internal structure. It does not change the file format, so it can be switched
  on or off at any time.

  What changes

  - Only one process can open the cache. While our process has it open, every
    other process gets "database is locked". That covers the sqlite3 shell, any
    backup or inspection tool, and a second copy of the application pointed at
    the same cache path.
  - The WAL index lives in our process's memory. Normally SQLite keeps it in a
    -shm file that all connections memory-map, so that several processes can
    share it. With one process there is nothing to share, and no such file is
    created.

  What that means in practice

  - Debugging. You cannot look into a live cache from outside. You would stop
    the instance, or copy the files and open the copy. S3 holds the truth, so I
    expect this to be rare.
  - Restarts on one machine. A new process cannot open the cache until the old
    one has closed it. It could not serve before then anyway, because the old
    one holds the lease.
  - The memory-mapping gap closes. There is no mapped file left for a disk error
    to hit, so such an error can no longer kill the process. The agent inferred
    this from the source and did not test it.
  - Connections inside our process are unaffected. The agent tested the writer
    with parallel readers, and it works as before.

  What I'm less sure of

  - After a crash, the operating system should release the lock when the process
    dies, so nothing stale is left behind. That is my understanding and was not
    tested.
  - It is a less-travelled path. It ships with SQLite, but far fewer deployments
    use it than the default, so it has had less exposure.
  - It exists on macOS and Linux only. Windows would need another answer, if
    Windows ever matters.

  Because it is reversible and nothing we build next depends on it, there is no
  need to decide today. I can leave it in docs/todo.md as an option for when the
  local-failure handling is built, with a test of the two unverified points
