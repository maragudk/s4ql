  ## The API the driver builds on (`internal/engine`)

  - **Engine:** `engine.New(d *core.DB, h host.Host, engine.Options{Logger})`
  gives an `*Engine`, which is safe for concurrent use.
  - **`Exec(ctx, src) (Result, error)`:** runs a statement. A query passed to it
  is run to its end and its rows dropped. The `Result` comes back with an error
  too.
  - **`Query(ctx, src) (*Rows, error)`:** runs a statement and gives its rows. A
  statement that is not a query is run as `Exec` runs it, and its rows carry
  the result, also when it fails.
  - **`Rows`:**
    - `Columns()` gives each column's name and declared type.
    - `All()` is a push-style `iter.Seq2` that can be used once. It holds the
  read transaction until the last row, an error, an early stop, a panic, or
  `Close()`.
    - `Close()` during a loop cannot end the transaction; it stops the loop at
  its next row. An iterator suspended in the loop body must be resumed or
  stopped.
    - `Close()` returns the error of ending the transaction, also after an early
  stop.
    - `Result()` gives the result of a statement that is not a query.
  - **`Result{Changes, SetsChanges}`:** see the change counts below.
  - **Errors:** `ErrNoStatement` for a text with no statement, and `ErrInternal`
  for a fault of s4ql.

  ## Plans and operators

  - **Stages:** `stmt.Check`, then `NewPlan`, which gives plain data printed by
  `Format`. A plan holds names as written and nothing of the catalogue. Then
  `buildQuery`/`buildSink` build operators inside the statement's own
  transaction and do SQLite's lookups in SQLite's order.
  - **Plan types:** `*CreateTable`, `*DropTable`, `*Insert` (whose rows come
  from a `Node`) and `*Query`. The nodes are `*Scan`, `*Values` and `*Project`;
  the one expression is `*Integer`.
  - **Operators:** the sources are `scan` (key order, checks the context before
  each row), `values` and `project`. The sinks are `insert`, `createTable` and
  `dropTable`. Because the core only upserts, `insert` checks the key with `get`
  inside the write transaction first.
  - **Storage:** operators talk to a small interface of the engine's own
  (`reader`, `writer`, `database`, `readTx`, `writeTx`). The core sits behind
  adapters; tests use a fake and a database in memory.
  - **Transactions:**
    - **Writes:** `Begin`, the operators, `Annotate`, `Commit`. Any failure or
  panic rolls back.
    - **Reads:** `DB.Read`.
    - `Rows.All` yields to the host between rows so other work can interleave
  under the simulation.

  ## Errors

  All are one type, `*sqlerr.Error{Code, ExtendedCode, Message, Offset}` in the
  new package `internal/sql/sqlerr`. It replaces `stmt.SyntaxError`, so `stmt`
  gives the same type. Every row below is pinned against the SQLite binding in
  `TestEngine_errors` and the differential tests.

  | Error | Codes | Names printed |
  |---|---|---|
  | `table %s already exists` | 1/1 | `Name.Raw`, quotes included |
  | `no such table: %s` | 1/1 | `Name.Value` |
  | `table %s has no column named %s` | 1/1 | both `Name.Value` |
  | `UNIQUE constraint failed: %s.%s` | 19/1555 | the names as the table stores
  them |
  | syntax errors | 1/1 | from the pass |

  - **Precedence:** a missing table wins over a missing column. A duplicate key
  reached through a name in another case prints the stored names.
  - **Not SQLite's errors:**
    - "Not supported" passes through as `*stmt.NotSupportedError`.
    - Core and context errors pass through unchanged, so `errors.Is` works on
  them.
    - The core's `ErrTableExists`, `ErrNoTable`, `ErrReservedName`, `ErrInvalid`
  and `ErrTxDone` become `ErrInternal`. `TestEngine_namesOfTheCore` and the
  differential tests show that no input reaches them.

  ## Change counts, last insert rowid, annotations

  - **Change counts**, from SQLite's `changes()` after every statement in the
  differential test:
    - An insert sets the count to 1.
    - CREATE TABLE, DROP TABLE and SELECT leave the count of the statement
  before (`SetsChanges` false).
    - An insert that fails at step (`UNIQUE constraint failed`) sets it to 0.
  `Exec` returns `Result{SetsChanges: true}` with that error.
    - Errors at prepare (no such table, no column, already exists, syntax error)
  and a text with no statement leave it unchanged.
  - **Last insert rowid:** always 0. SQLite does not record inserts into WITHOUT
  ROWID tables.
  - **Annotations:** each committed write carries one annotation: the
  statement's text from its first token to its end (including its semicolon),
  with no parameters. Comments before it and text after it are dropped. A failed
  statement leaves none. The core stores annotations only with a commit object.

  ## Decisions for you

  - **Pull-style rows for the driver.** The engine gives push-style rows only,
  and simlint forbids `iter.Pull`. But `database/sql` starts its own goroutines,
  so the driver cannot run under the scheduler anyway. Should the driver be
  exempt from simlint, like `s3store`, and bridge with `iter.Pull`? The bridge
  must stop the iterator to end the transaction.
  - **`ErrNoStatement`.** I made it a sentinel error, which is the safer default
  if the driver forgets to handle it. Changing it to a successful empty result
  is cheap if you prefer.
  - **Annotation text.** I store the statement's span, not the whole text given
  to the call.
