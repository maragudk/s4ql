  **The identity and where it is stored.** `Options.identity()` in `/s4ql.go`
  builds `s3://<bucket>/<prefix>`. The bucket and each segment of the prefix go
  through `url.PathEscape`. If `Options.Endpoint` is set, ` at <endpoint>`
  follows, exactly as given. Example: `s3://bucket/app at
  https://t3.storage.dev`. Two different databases can never produce the same
  string. `newConnector` puts it in the new field `core.Options.Identity`, which
  the core only compares. It is stored in a new column, `database text not
  null`, of `s4ql_cache`, so `cacheVersion` goes from 0 to 1. A version-0 cache
  is refused with `ErrCacheVersion`, and that error now says what to do.

  **Refused at `Open`, not as a stop.** `core.Open` returns `ErrCacheDatabase`,
  which is not wrapped in `ErrLocal`. The public error is:
  `s4ql: open the cache: the cache belongs to another database: it records the
  database "s3://bucket/db at https://t3.storage.dev", and this instance opens
  the database "s3://bucket/other at https://t3.storage.dev"; open each database
  with a cache of its own, or delete the cache, with its files -wal and -shm,
  if the database has moved`
  The driver's `open` event gains `db.identity`. A refused open logs nothing,
  like any failed open.

  **The race.** `conn.setUp` first checks, without locking, whether `s4ql_cache`
  exists. If it does, it only reads it, so a spare of the same database still
  opens while the serving instance holds a write transaction. If not, it runs
  `begin immediate`, checks again, and creates the table and row in that
  transaction. Exactly one instance creates it; the other then reads a record
  that is not its own.

  the same change. The new `conn.wal` waits for the write lock with `begin
  immediate`/`rollback` and asks again, up to 5 tries. In testing one retry was
  always enough (37 retries in 250 opens).

❯ I still don't understand what the sanitizer job does.                         

⏺ It runs the same tests a second time, in a mode that watches the C code for
  memory errors.

  Why we need that. s4ql calls SQLite, which is C, through our own binding. Go
  protects its own memory: a read past the end of a slice panics. C doesn't. If
  our binding hands SQLite a wrong length, or uses a statement after it was
  freed, C reads or writes memory it doesn't own. Often nothing visible happens:
  the test passes, and the damage shows up later as wrong data or a crash
  somewhere else.

  What the sanitizer does. With go test -asan, the C code is compiled with extra
  checks around every memory access. The moment C touches memory outside an
  allocation, or memory that was freed, the test stops with a report that names
  the line. So a silent corruption becomes a failing test.

  What the job runs, then:

  1. The normal tests, built that way. They don't test anything new; they just
     fail loudly if any of them makes C misuse memory.
  2. The fuzz tests, built that way. Fuzzing feeds random inputs to the binding
     and the parser, to reach paths the hand-written tests don't. Each runs for
     30 seconds.

  Why it's slow. The checked code runs several times slower, SQLite is one very
  large C file that gets compiled again with the checks, and the fuzz tests ran
  one after another.

  What it is not. The race detector, which the normal test job uses, finds Go
  goroutines touching the same data. It sees nothing of C's memory. The two
  catch different faults.

  Has it earned its place? It hasn't found a memory fault in the binding so far,
  as far as the diaries record. What it did catch were tests that depended on
  timing, because it's slow. I'd keep it: a memory fault in the binding is the
  kind of bug that corrupts data without an error, and this is the only check we
  have for it.
