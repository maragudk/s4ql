  ### Decisions
  - **`store.ErrTooLarge`** is the fifth "not applied" error. It is documented

  write of the same content will never be applied"), and in the docs of `Create`

  - **`s3store` also maps a store's own `400 EntityTooLarge` answer to

  - **New request outcome in `s3store`:** `too_large`, logged at Warn, for both

  (commit 560cc9a), not pushed. It is `docs/research/sql-front-end.md`, about

  **How I got the facts.** I didn't trust the Homebrew shell, whose compile
  options differ. Instead I built throwaway C probes against the vendored
  amalgamation with `options.h`, opened the way `sqlite.Open` opens (EXRESCODE).
  I read `parse.y` and `lemon.c` at tag version-3.54.1, and the Go 1.27.3
  `database/sql` source. Three research agents surveyed the parsers, the testing
  practice and the APIs; I checked their key claims. The probes are in
  `/private/tmp/claude-502/-Users-maragubot-Developer-s4ql--claude-worktrees-obj
  ect-store/f1343515-adca-4ca0-9eb0-f507768f8fc7/scratchpad/fe/probe/`.

  **1. Tokenizer.** SQLite's tokenizer is one byte-level function,
  `sqlite3GetToken`, with quirks a Go copy must keep:
  - A vertical tab is legal only after other whitespace.
  - A byte order mark counts as whitespace only at the start of a token.
  - Every byte from 0x80 up is an identifier character, so a no-break space
  (U+00A0) is part of a name.
  - Digit separators like `1_` are checked later, and that error carries offset
  -1.
  - An unterminated `/*` comment is accepted.

  s4ql's restrictions don't shrink the tokenizer, because brackets and backticks
  must still be found as tokens to be rejected.
  - **Oracle:** a C test program that includes `sqlite3.c` can call the private
  `sqlite3GetToken` directly. I did this, and it gives an exact token-by-token
  oracle for Go's fuzzer.
  - **Weak oracle:** `sqlite3_complete` uses a different scanner. `select 1;--x`
  counts as incomplete, which contradicts its own header doc.
  `sqlite3_incomplete` is new in 3.54.0.
  - **Evidence favours:** a tokenizer for all of SQLite's tokens, checked
  against `sqlite3GetToken`.

  **2. Parser.**
  - **Facts:**
    - `near "X"` is fixed by the grammar's language (inferred from LR theory,
  not proven). So a parser for slice 1 alone stops earlier than SQLite and
  cannot match SQLite's syntax errors on inputs outside the subset.
    - The order of errors is subtle. `sqlite3ErrorMsg` overwrites any earlier
  message, and the parse loop checks only between tokens. Measured: `... strict,
  bar, without rowid` reports the bad table option, but `(v1 foo ...) strict,
  without rowid, bar` reports `unknown datatype`.
    - `table X already exists` is raised mid-parse, so it wins over later
  faults.
  - **Biggest find:** `github.com/sqlc-dev/meyer`. It is an MIT, hand-written
  recursive-descent port of all of `parse.y` that claims SQLite's exact syntax
  messages and offsets on 21,326 cases. sqlc main switched to it on 2026-08-01.
  It has one author and seven commits, and pins 3.53.4. I checked that between
  3.53.4 and 3.54.1 `tokenize.c` is identical and `parse.y` differs only inside
  C action code. I did not run its tests.
  - **Others:**
    - rqlite/sql: Go-style errors, no digit separators.
    - modernc: transpiled C with no parser API.
    - ANTLR grammars: ANTLR's messages, and the Go runtime has had no release
  since 2024.
    - golemon: the author promises no support, and a 2022 attempt on `parse.y`
  was abandoned.
    - goyacc: has no `%fallback`.
  - **Evidence favours:** a full-grammar parser that s4ql owns, with a pass
  after parsing that rejects anything slice 1 does not list. meyer would serve
  as a reference or a starting point. A slice-1-only parser is the smaller start
  if Markus doesn't require SQLite's syntax messages for unsupported inputs.

  **3. Exact errors (run on 3.54.1).**

  | Case | Message | Primary / extended | At |
  |---|---|---|---|
  | Key inserted twice | `UNIQUE constraint failed: t1.v1` | 19 / 1555 | step |
  | Table exists | `table t1 already exists` | 1 / 1, offset 13 | prepare |
  | Missing table (select, insert, drop) | `no such table: t2` | 1 / 1 | prepare
  |

  How names appear:
  - `already exists` prints the name exactly as typed, quotes included: `table
  "t1" already exists`.
  - `no such table` prints the name as typed but without quotes, and keeps any
  schema prefix.
  - `UNIQUE` prints the stored names (`Foo.Bar`), whatever case the statement
  used.

  So the syntax tree must keep the raw token text of names.

  Slice 1's own shapes can also produce errors the roadmap doesn't list:
  - `table t1 has no column named v2`
  - `object name reserved for internal use: sqlite_x`
  - `table sqlite_master may not be dropped`
  - `cannot store REAL value in INT column t1.v1` (3091), for
  9223372036854775808
  - `hex literal too big`

  For most inputs s4ql will reject, SQLite gives no error at all: a second
  column, `integer`, `where`, `if exists`, missing `strict`. A few are SQLite
  errors too, such as `PRIMARY KEY missing` and `sqlite_` names.

  The note lays out three options for what s4ql promises to match, and how to
  mark "not supported" (a distinct error, a message that can't be SQLite's, the
  offset). The facts for that choice: matching codes alone can't tell `no such
  table` from `already exists`, because both are 1 / 1. And the docs promise no
  stable message text, but the version is pinned.

  **4. Testing.**
  - **musql** (`samyfodil/musql`) is a Go engine with mattn/go-sqlite3 as its
  oracle, which is s4ql's setup. It compares outcome kind, column names and
  typed values, and keeps "declined" separate from "wrong".
  - **Turso** runs `EXPLAIN` on both sides first and skips any statement either
  side can't prepare, so the two states never drift.
  - None of the surveyed projects compares error messages in live differential
  tests. Exact messages would make s4ql stricter than all of them, which a
  pinned in-process oracle allows.
  - The note sketches a slice-1 harness:
    - hand-written scripts for each measured case
    - a Hegel generator of slice-1 shapes
    - a mutator that changes one token, to check the "reject what is not listed"
  rule
    - tokenizer fuzzing against `sqlite3GetToken`
    - mined TCL corpora
    - table snapshots after each change and after replay from S3

  **5. API.**
  - **Retry hazard:** `database/sql` runs an operation up to three times when
  the driver returns `ErrBadConn` (`sql.go` 1574-1589). This covers
  `DB.ExecContext`, `QueryContext`, `BeginTx`, `Ping` and `Stmt.Exec`. An insert
  whose commit outcome is unknown, and `ErrNoLease`, must never wrap
  `ErrBadConn`.
  - **Commit context:** `driver.Tx.Commit()` takes no context. `sql.Tx.Commit`
  cancels its own derived context before calling the driver, but the driver's
  `BeginTx` gets the caller's original context, so the driver can keep it for
  `core.Tx.Commit`.
  - **What the driver can't carry:** `DB.Close` takes no context, and nothing in
  `database/sql` expresses the instance stopping.
  - **Other drivers:** none of the surveyed ones returns `ErrBadConn` from query
  paths.
  - **Agreement:** what Markus agreed on 2026-11-10 (`database/sql` as the main
  interface, `OpenDB` with a connector, an explicit `Register`) is only in the
  conversation export, not in `spec.md` or `todo.md`.
  - **Evidence favours:** the driver as the main interface, built as a thin
  adapter over an own API, the way ncruces is built.

  **6. Layers.**
  - The core's catalogue (`Tx.Table`/`Tables`) and its errors cover slice 1's
  cases, but the engine has to format SQLite's messages itself from the syntax
  tree.
  - `Tx.Upsert` replaces silently, so the engine must check the key first and
  raise `UNIQUE` itself.
  - SQLite's bytecode is not a stable interface by its own docs (opcode.html).
  Turso copies it and compares `EXPLAIN` by hand; go-mysql-server, chai, TiDB
  and ramsql all use iterator trees.
  - For slice 1 the two hardly differ.
  - The note lists four places where the oracle plugs in: tokens, statements,
  table state (the cache is SQLite too) and acceptance.

  **Surprising:**
  - meyer exists and claims SQLite-exact syntax errors in Go.
  - Error messages depend on whether several errors happen while the same token
  is handled.
  - `sqlite3_complete` contradicts its own doc.
  - SQLite accepts `insert into t (v1, v1) values (1, 2)`.
  - SQLite accepts single-quoted names, and the roadmap's restrictions don't
  mention them.

  **Open for Markus:** whether single-quoted names are rejected; what "any
  integer value" includes (sign, hex, separators); what an error promises to
  match; whether SQLite may classify rejected statements in production; whether
  the own API is public.

  **Not verified:** meyer's coverage claims; whether musql's harness runs in CI;
  whether Turso compares `EXPLAIN` automatically; the LR argument that default
  reductions never move the error token; whether SQLite has its own "not
  supported" messages; the authorizer as a way to see dequoted names; whether
  modernc's newest tag has `NewConnector`.

  `LikeKw`, `JoinKw`, `CTimeKw`, `Temp`. It has `String()`, which gives the TK_
  name, and `IsKeyword()`.

  copies SQLite's `aiClass` and `sqlite3CtypeMap` tables as they are, and reads
  any byte past the end as NUL.

  `Token.Text(src)`.

  exactly as SQLite does, and `Tokens` stops there. I chose this over a separate
  end kind so that kinds map one to one onto TK_ codes. The parser can spot a
  NUL by comparing where the tokens stop with `len(src)`.
  - The package comment says what it promises and what it leaves to the parser,
  with line numbers in the vendored `sqlite3.c`.

  **How the oracle is reached, and why**
  - The oracle is a thin wrapper in the binding's own translation unit, not a
  test-only package with its own copy of SQLite. In `internal/sqlite/sqlite.go`,
  a static C function `s4ql_tokenize` sits in the preamble, and two new Go
  functions use it: `sqlite.Tokenize(src) []sqlite.Token{Type, Len}` and
  `sqlite.Keywords()`.

  binding's review found and fixed with `source.h`; the wrapper inherits that
  fix.

  - The cost is two exported functions in the production binding that production

  - The tests never hard-code TK_ numbers. They read the `#define TK_` lines

  On the oracle: we have to go through more than SQLite's parser, but not
  through the whole engine. SQLite has no parser-only entry point. Its grammar
  actions call the code generator directly, and it builds no syntax tree that it
  hands out. The way in is sqlite3_prepare_v2, which runs the tokenizer, the
  parser, and the code generator, and stops before anything executes.

  That gives the oracle three properties:

  - Accept or reject, and the syntax message, come from SQLite itself. A
    statement that fails with near "X": syntax error, unrecognized token, or
    incomplete input failed in the parser. One that prepares, or fails with
    something like no such table, got through the parser.
  - A semantic error can hide a later syntax error. The research measured this:
    table t1 already exists is raised in the middle of parsing and wins over a
    fault further on. So for pure syntax checks we prepare against a schema
    where names resolve, or an empty one, and treat the remaining cases as
    "SQLite does not say".
  - The tree has no oracle. SQLite can tell us whether a statement parses, not
    what our tree should look like. The tree is checked indirectly: the engine
    runs the statement and the rows and errors are compared with SQLite's.

  I have not checked whether the private sqlite3RunParser could be called

  **Short answer.** `select`, `insert`, `update`, `delete` and `create
  table/index/view/trigger` build a tree. Every other statement's grammar action
  generates bytecode straight from tokens, so no tree of it ever exists. The
  meyer README claim ("SQLite cannot dump its parse tree") holds for the public
  API only. It is false for a project that compiles SQLite itself.

  **Routes that work, all run on 3.54.1:**
  1. **SQLite's tree printer (`treeview.c`).** It needs `-DSQLITE_DEBUG
  -DSQLITE_ENABLE_TREETRACE`; TREETRACE alone prints nothing. You switch it on
  with `.treetrace 0x10000` or `SQLITE_TESTCTRL_TRACEFLAGS`, and it prints to
  stdout through a process-wide global. It dumps at the entry of
  `sqlite3Select`, `sqlite3Insert`, `sqlite3Update` and `sqlite3Delete`. That is
  after the grammar's actions, before name resolution.
     - It loses quote style, every position, the `RETURNING` expressions (prints
  only the word) and `NATURAL`.
     - In normal mode, `x and 5 is null` (or `a in () and b`) replaces the whole
  `WHERE` with `0`.
     - Multi-row `VALUES` is compiled into a co-routine while parsing (since
  3.46.0). The first dump is the first row alone, and later rows appear in no
  dump.
     - Each statement also prints dumps of nested and rewritten statements, so
  "the first dump is the statement's tree" does not hold.
  2. **A C walker of our own over a rename-mode parse, in the production
  build.** The static `renameParseSql` (used by `ALTER TABLE ... RENAME`) is
  callable from the binding's translation unit. I wrap a `select` as `CREATE
  VIEW s4ql_v AS ...`, and an `insert`, `update` or `delete` as a trigger body.
  The trees stay in `pNewTable`, `pNewIndex` and `pNewTrigger`.
     - It also gives `create table/index/view/trigger`.
     - It keeps quote flags and source positions (rename tokens plus
  `Expr.w.iOfst`).
     - Rename mode skips the AND-false fold and turns multi-row `VALUES` into
  `UNION ALL`.
     - It works with `options.h` and `-DSQLITE_API=static`, and ran clean under
  ASan and UBSan over 167 statements.
     - The wrappers refuse with an error, never silently: parameters; another
  schema in a view; and in trigger bodies `WITH`, `RETURNING`, `DEFAULT VALUES`,
  `INDEXED BY` and schema-qualified targets. `CREATE TABLE ... AS SELECT` also
  fails.
     - The fixer reduces `main.t` to a flag.
  3. **Lemon's parser trace (`PRAGMA parser_trace`, debug build only).** It
  covers every statement kind, but as a derivation of rule texts, with token
  kinds instead of text. 14 of 412 unit rules are optimized out by Lemon (e.g.

  - `LIKE` becomes `like(p, x)` with the operands swapped; `LIMIT a, b` is
  stored as `LIMIT b OFFSET a`.
  - `count(*)` equals `count()`, and `ALL` in a function is dropped.
  - Named windows are chained and their list is reversed.
  - `,`, `JOIN` and `INNER JOIN` are the same; `LEFT` and `LEFT OUTER` are the
  same.
  - `CHECK`, generated-column and index expressions are already resolved;
  defaults are wrapped in `SPAN`.

  - **It catches:** wrong grouping and associativity, clauses on the wrong term
  of a compound, dropped or swapped clauses that don't change results

  name quoting and aliases, and name positions.
  - **It cannot catch:** anything lowered away, keyword spellings, operator
  positions, statements without a tree or refused by the wrappers, or the
  acceptance question itself.

  Fourth approach: the tree has the right shape

  This one checks that the parser understood the statement the way SQLite does,
  not only that it kept all the words.

  How it works: we write the statement out again from our tree, with brackets
  around every operation so that nothing is left to precedence rules. For a + b 
  * c our tree gives (a + (b * c)). Then we ask SQLite about both texts:

  - For expressions: SQLite computes both with the same values, and the results
    must be equal. If our parser had grouped it as ((a + b) * c), the results
    differ.

    program it would run, must be the same. A clause that we attached in the
    wrong place or left out changes that program.

  wrong reading of NOT x NOT NULL in 276,022 random expressions. The second
  found rqlite/sql swapping limit and offset, in 18,286 statements.

  - It needs a printer, code that writes a tree out as SQL. A bug in the printer
    that exactly undoes a bug in the parser would hide both. For anything the
