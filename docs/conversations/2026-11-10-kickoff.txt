  **Most important finding: Tigris's default bucket type is not safe for
  compare-and-swap (CAS).**
  - **Conditional PUTs work.** The current docs say "Use `If-None-Match: "*"` to
  write only if the object does not already exist", and `If-Match` returns `412
  Precondition Failed` when the ETag doesn't match. [V]
  - **Consistency depends on the bucket's location type.** Global (the default)
  and Dual-region are strong within a region but "eventual consistency
  globally". Single-region and Multi-region are strong everywhere. [V]
  - **Tigris's own guidance:** "For conditional operations that may span
  regions, use a Multi-region or Single-region bucket to ensure conditions are
  always evaluated against the latest state." [V]
  - **What "strong" covers there:** read-after-write, read-after-delete, LIST
  right after a PUT, and conditionals that "always evaluate against the latest
  state". Replication lag for eventual reads is "typically sub-second". [V]
  - **Inference:** on a Global bucket, two writers in different regions could
  both win a put-if-absent on the same key. [I]
  - **The `X-Tigris-Consistent` header is now ambiguous.** The 2025 docs said to
  attach `X-Tigris-Consistent:true` to every conditional request and every read
  that must see the latest write, which routed them to a leader. The current
  docs don't mention the header at all. Tigris's Go SDK still has
  `WithConsistentRead()`, and Litestream started sending the header for Tigris
  in Dec 2025. Whether it still does anything is unconfirmed.
  - **Other ways Tigris differs from AWS S3:**
    - The Go SDK's `WithCreateObjectIfNotExists()` sends a non-standard
  `If-Match: ""`.
    - Bucket versioning and bucket policies aren't supported, so you can't
  enforce conditional writes by policy.
    - Its compatibility table doesn't list conditional PutObject as a tested
  case.
    - Conditional CompleteMultipartUpload, conditional DELETE, and what happens
  on a 409 aren't documented. Test all of these against the real endpoint.

  **turbopuffer** [V unless noted]
  - Each namespace is a prefix on object storage. Writes are buffered in memory
  and group-committed to the write-ahead log (WAL) at most once per second per
  namespace. A write is acknowledged only once it is durable; p50 is 165ms for
  500kB.
  - Their own descriptions changed over time:
    - **2024 podcast:** WAL files are numbered sequentially, written with
  put-if-absent, and strong reads first LIST the WAL directory.
    - **2026 CMU talk:** "we commit a file and then commit it into a manifest
  with compare and swap". Strong reads use a conditional GET (`If-None-Match`),
  and LIST is "not one that I recommend ever using in production on a critical
  data path".
  - Strong reads cost about 10ms extra and replay unindexed WAL entries on top
  of the index. Eventual mode skips that round trip; staleness is up to 60s by
  default (3600s max), or about an hour under heavy write backlog.
  - Indexing and tiered compaction run asynchronously from a work queue that is
  itself a single JSON file updated by CAS behind a broker.
  - Latency: cold p50 874ms vs warm 14ms (1M docs), about 100ms per
  object-storage round trip. The design caps cold queries at about three round
  trips.
  - There are no general transactions. Conditional writes behave as
  Serializable; filter-based writes are Read Committed.

  **SlateDB** [V from source code at v0.18.1]
  - Manifests and WAL objects are written with put-if-absent at the next
  sequential ID. If a WAL write finds the ID taken, the writer treats itself as
  fenced. Startup bumps `writer_epoch` through a manifest CAS.
  - The 2024 manifest RFC proposed a DynamoDB/two-phase workaround because S3
  lacked CAS then. That part is out of date.
  - Defaults: `flush_interval` is 100ms ("$130/month in PUT costs on S3
  standard"). Writes return before they are durable unless you call
  `await_durable()`.
  - Their stated write latency is 50–100ms on S3 Standard and 5–10ms on S3
  Express.
  - Transactions support Snapshot and Serializable Snapshot isolation, checked
  in memory, with a single writer.
  - **A pitfall worth copying their fix for:** after garbage collection deletes
  old IDs, a stalled process can put-if-absent a reused ID and "report a stale
  update as successful". SlateDB prevents this with boundary files updated via
  `If-Match`.
  - **Go:** there is an official binding (`slatedb.io/slatedb-go`, added Mar
  2026). It needs cgo plus a Rust shared library and runs a Tokio runtime inside
  your process. The API isn't guaranteed stable. The pure-Go port repo now
  returns 404.

  **Other systems** [V unless noted]
  - **Delta:** commits by exclusively creating the next log file; its Spark docs
  still warn that concurrent S3 writers without DynamoDB can lose data. [S]
  delta-rs now uses S3 conditional writes instead.
  - **Iceberg:** commits by atomically swapping a metadata pointer and retrying
  with validation.
  - **WarpStream and Neon:** both keep the commit point off object storage — a
  strongly consistent metadata log for WarpStream, a Paxos quorum of WAL servers
  for Neon.
  - **Graft:** Rust SQLite VFS that commits by conditionally writing
  `/logs/{id}/commits/{LSN}`. Any concurrent commit to the same database aborts,
  giving strict serializability at low concurrency. Alpha.
  - **Litestream:** uses time-based leases built on conditional writes. [S] Its
  writable VFS syncs about once a second, so up to about 1s of acknowledged
  writes can be lost.
  - **Turbolite:** single writer and experimental. It measured roughly 25ms per
  GET on Tigris vs 4ms on S3 Express.

  **AWS S3 primitives** [V]
  - `If-None-Match: *` and `If-Match` work on PutObject, CopyObject and
  CompleteMultipartUpload. When several race, "the first write operation to
  finish succeeds" and the rest get 412.
  - A concurrent delete can produce 409, which forces a brand-new multipart
  upload. In-progress multipart uploads are ignored until Complete.
  - Conditional deletes (`If-Match`) arrived Sep 2025.
  - Reads and LISTs are strongly consistent after a write. There is no atomicity
  across keys.
  - Limits and cost: at least 3,500 PUTs/s and 5,500 GETs/s per prefix; AWS
  cites 100–200ms latency; $0.005 per 1,000 PUTs.
  - One mid-2025 benchmark of CAS on a single key: S3 managed about 15 ops/s at
  58–68ms, S3 Express about 70 ops/s at 14–26ms, GCS about 1 op/s.
  - Known pitfalls: SDK retries can turn your own success into a 412, timeouts
  leave you unsure whether a write landed, and a lease alone doesn't stop a
  paused holder — the storage itself has to reject stale writes.

  **Trade-offs for your design** [I, based on the facts above]
  - **Single writer with fencing:**
    - **Concurrency:** a newer writer simply blocks the old one.
    - **Isolation:** full Serializable, checked cheaply in memory.
    - **Throughput limit:** how often you group-commit.
  - **Multiple writers with optimistic concurrency:**
    - **Concurrency:** writers race for the next log entry and the loser
  revalidates.
    - **Isolation:** Snapshot by checking write sets against commits made since
  the snapshot. Serializable also needs read and range sets recorded per commit,
  or Graft-style abort on any intervening commit.
    - **Throughput limit:** roughly one commit per round trip across all writers
  combined.
  - **Commit latency floor:** one round trip if the log write is itself the
  commit, two if you write a data object and then CAS a manifest, plus the
  group-commit wait.
  - **Storage layout:**
    - **WAL + LSM** (SlateDB, turbopuffer) fits immutable objects and batched
  writes.
    - **Page segments + page index** (Graft, Turbolite) fits SQLite pages but
  needs its own garbage collection.
    - **One object per page** costs too many requests and has no atomicity.
  - **How readers find a snapshot:** a conditional GET on the manifest (304 if
  unchanged), periodic manifest polling, or pinned checkpoints so GC can't
  delete files a reader still needs.

  **Where sources disagreed or were dated**
  - turbopuffer's commit and freshness mechanism differs between the 2024
  podcast and the 2026 talk.
  - The CMU talk says S3 got CAS in "December 2024". From my own knowledge, not

  - SlateDB's manifest RFC predates S3 CAS.
  - Tigris's 2025 header-based consistency model was replaced by bucket location
  types in Mar 2026.
  - Not confirmed: whether `X-Tigris-Consistent` still matters, how Tigris
  handles multipart and 409 cases under conditions, and Tigris's exact error

⏺ The architecture research is back. The pattern is well established, and the
  main risk is Tigris's bucket type.

  What the existing systems do
  - turbopuffer: writes are buffered and group-committed to a write-ahead log on
    object storage, and acknowledged only once durable (p50 165ms). The commit
    is a compare-and-swap on a manifest. Indexing and compaction run
    asynchronously. Strong reads cost one extra conditional GET of about 10ms.
    Cold queries take about 874ms against 14ms warm, which is why the caches
    exist. It has no general transactions.
  - SlateDB: an LSM tree on object storage, with one writer fenced by an epoch
    in the manifest. Log objects are written put-if-absent at the next
    sequential ID. It offers snapshot and serializable isolation, checked in
    memory. Its Go binding needs cgo and a Rust library, so it is a reference
    for us and not a dependency.
  - Graft: a SQLite layer that commits by conditionally writing the next log
    entry, aborting on any concurrent commit. This is the closest to what we are
    building, and it is alpha.
  - WarpStream and Neon keep the commit point off object storage entirely, which
    we cannot do.

  Constraints this puts on us
  - Tigris's default bucket type is unsafe for us. Global and dual-region
    buckets are eventually consistent across regions, so two writers could both
    win the same conditional write. We need a single-region or multi-region
    bucket.
  - Tigris's conditional-write behaviour is under-documented. Conditional
    multipart completes, conditional deletes and the 409 case are not
    documented, and it is unclear whether the X-Tigris-Consistent header still
    does anything. I want a small probe against the real endpoint before we
    commit to a protocol.
  - Commit latency floor is one S3 round trip, roughly 50–100ms on S3 Standard,
    plus any group-commit wait. A single contended key manages about 15 commits
    per second on S3, so throughput comes from batching transactions into each
    commit.
  - Garbage collection has a known trap. A stalled process can write to a log ID
    that was deleted and reused, and believe it succeeded. SlateDB guards
    against this explicitly, and we must too.
  - Ambiguous outcomes are normal. Timeouts leave a write's fate unknown, and
    SDK retries can turn our own success into a 412.

  Where I lean
  - Commit: a put-if-absent of the next sequential log object, so a commit is
    one round trip, with group commit.
  - Storage: write-ahead log plus immutable sorted files with background
    compaction, and a manifest updated by compare-and-swap.
  - Writers: one writer at a time, fenced by the storage itself, with
    serializable isolation checked in memory. Multi-writer is possible later but
    caps at roughly one commit per round trip across all writers.

  Design
  - One bug class keeps recurring. A "create only if absent" write protects a
    name only while the object exists. Once garbage collection deletes it, a
    stalled process can create the same name again and believe it committed.
    SlateDB has hit this repeatedly, most recently fixed three days ago, and one
    acknowledged-write-lost issue has been open for 18 months.
  - Their fix: a marker object per namespace that garbage collection advances
    before deleting, and that writers check after each create. They apply it to
    the manifest but not the log; we should apply it everywhere.
  - Ambiguous writes are resolved with a token. Every conditional write carries
    a unique ID in the object's metadata. On "already exists", the client reads
    the object back and checks whether the ID is its own. If it can't tell, it
    stops and reopens.
  - SlateDB is not ACID by default. Commit returns before the write is durable,
    and a writer that has been replaced keeps serving stale reads until it
    notices. A SQL layer has to close both gaps.
  - Tigris numbers from their benchmark: durable writes took 231ms at the median
    and 932ms at the 99th percentile, against 105ms and 196ms on S3. There is
    also an open report of a 20-minute livelock when opening a database on
    Tigris.

  Testing
  - Formal models found the subtlest bugs. The latest one needed four writers
    and a 62-step sequence, which its finder says simulation would never hit.
    Their models are not run in CI, which is a gap we can close.
  - Simulation found nothing until they rewrote it in April 2026, then about
    nine bugs since. The rewrite added faults on the response side and
    randomised configuration per seed.
  - Property-based tests found essentially nothing, and narrow input bounds hid
    a production corruption bug. That is a warning about how we write
    generators, not about the technique.
  - They have no Jepsen run, no fuzzing and no history checker.

  - A formal model of the commit and garbage-collection protocol moves from

  Single writer does simplify things: with no concurrent writes there is no
  conflict detection between transactions, and serializable isolation comes for
  free.

  One caution on locks in S3. A lock that relies on time alone is not safe. A
  writer can pause, for example in a long garbage-collection stop or a network
  stall, wake after its lock expired, and still write. So the lock has to be
  enforced by the storage: every commit is a conditional write that fails if
  another writer has taken over. A lock object can still exist on top to tell
  others who the writer is.

  One question to pin the constraint down. "Single writer" can mean two things:

  1. One writer process at a time. A process becomes the writer when it opens
     the database for writing and stays the writer until it closes or another
     takes over. Other processes are read-only. This is what SlateDB does.
  2. Many processes take turns, as in SQLite. Any process can start a write
     transaction and takes the lock for just that transaction. Each turn costs
     extra S3 round trips to take the lock and catch up.

  I recommend option 1: it is simpler, faster per commit, and a takeover is one
  well-defined event to test. Which did you mean?

⏺ Your goals do point to option 2, and I'm changing my recommendation to it.
  Option 1 fails your split-brain case in an annoying way: when you bring up a
  new instance, the old one starts getting errors, and if both are alive they
  keep taking over from each other.

  Option 2 doesn't need a lock. If a commit is a create-if-absent write of the
  next numbered log object, the storage itself allows exactly one writer per
  number:

  - Any process can start a write transaction against the latest state it knows.
  - It commits by creating log object N+1. If another process committed first,
    the create fails, so nothing stale can ever be written.
  - The loser catches up and retries.

  That gives you what you asked for:

  - No split brain, by construction. Two writers can't both win the same number,
    however confused they are about each other.
  - No stuck locks. A crashed process holds nothing, so there are no timeouts to
    tune.
  - No special instance. Every process opens the database the same way, with no
    "who is the writer" configuration.
  - No disaster recovery setup. S3 holds the only copy, and a new instance just
    opens the bucket.

  The speed cost is smaller than I first said. A write transaction that commits
  successfully must have seen the latest state, so with one process running
  there is no extra round trip compared with option 1. The cost only appears
  when two processes write at the same moment: one of them redoes its
  transaction.

  The one visible consequence is that redo. The engine can retry single
  statements itself. A multi-statement transaction with application logic in
  between gets a "retry this transaction" error, the same one Postgres returns
  for serialization failures. A lock could be added later so writers wait their
  turn instead, but only as a courtesy; correctness would never depend on it.

  Is an occasional retry error on simultaneous writes from two processes
  acceptable? If so, I'd propose rewording the spec's constraint to "one commit
  at a time, enforced by the storage; any process may write".

⏺ The spec now says "one commit at a time, enforced by the storage; any process

  The JSON file idea is a good fit, and I'd adopt it. Here is how it works:

  - One small file in the bucket, the manifest, says what the database currently
    consists of: which data files make up the current state.
  - To commit, a process uploads its new data as a fresh file, then replaces the
    manifest with a version that includes it. The replace is conditional: "only
    if the manifest is still the version I read".
  - If someone else committed in between, the replace fails. Nothing has
    changed, and the uploaded file is just unreferenced garbage. The process
    re-reads the manifest and retries.

  So the manifest swap is the commit, as you said. Turbopuffer does this for
  commits, and also uses a single JSON file as its indexing work queue.

  Why I prefer it to numbered log objects, which was my earlier lean:

  - It removes SlateDB's recurring bug class. The manifest is never deleted, so
    a stale writer's swap always fails. With numbered objects, a deleted number
    can be recreated by a stalled process.
  - Readers need one cheap request to know they have the latest state: "give me
    the manifest if it changed".
  - Lost responses are easy to settle. Re-read the manifest and see whether your
    commit is in it.
  - You can open it and read it. The entire state of the database is one
    human-readable file, which helps both operations and trust.

  The cost is speed: a commit is two S3 round trips (upload, then swap) instead
  of one. That matches your trade of speed for correctness. Batching several
  transactions into one commit softens it.

  Two details I'd handle in the design: the manifest must stay small as the
  database grows, and each version needs a unique ID inside it so two versions
  never look identical to the conditional write.

  How it would work

    runs out. This covers your disaster scenario: the new instance starts within
    seconds, with no manual step.

  What stays unconditionally safe: writes. Every commit is still a manifest swap
  that S3 enforces. An instance that wrongly believes it holds the lease can
  never commit anything.

  What depends on the clock: pure reads. The holder decides "my lease is still
  valid" from its own clock. If a machine freezes and its clock freezes with it,
  as can happen when a virtual machine is suspended, it may wake up and serve
  reads from its cache after another instance took over. The damage is bounded:

  - It affects only read-only transactions. Any transaction that writes is
    checked by the commit itself.
  - It lasts at most one lease period, until the next renewal fails.
  - It cannot happen with a single instance, your common case, because nobody
    else ever commits.

  The alternative with no clock dependence is the previous design: every
  transaction pays 10 to 30ms.

  I recommend the lease, with a per-transaction option to verify against S3 for
  reads that must never be stale. The worst case is rare, short and read-only,
  and the common case gets SQLite-speed reads. Is that trade acceptable to you?

  How the Litestream VFS works

  - Storage: each sync turns newly committed pages into an immutable file.
    Background compaction merges those files level by level, with a daily full
    snapshot on top.
  - Cheap cold open: every file ends with an index of its pages. To open a
    database, the VFS fetches only those indexes, about 1% of the data, and
    builds an in-memory map from page number to file and offset.
  - One range read per missing page, then a small local cache. No page data is
    downloaded until SQLite asks for it.
  - Following changes: it lists new files every second and merges their indexes
    into the map. A read transaction keeps seeing the database as it was when it
    started.
  - Time travel: a query can be pointed at an earlier moment by rebuilding the
    map from the files that existed then.
  - Background hydration: it can build a full local database file while serving
    reads remotely, then switch to it.

  Where it falls short of what we want. These are in the research notes, not the
  inspiration doc:

  - Its S3 lease exists but nothing calls it, so it does not actually prevent
    two writers.
  - Write mode uploads about once a second with unconditional writes, so
    acknowledged writes can be lost.

⏺ The spec now says the lease is recorded in the database's manifest, the object

  Next item: is the manifest swap the commit?

  There are two ways to make a transaction durable.

  Option A: the swap is the commit.
  - Upload the transaction's changes as a file, then swap in a manifest that
    lists it.
  - Costs two S3 round trips, about 125ms measured.
  - The lease check and the commit are one atomic step, because both live in the
    manifest. An instance that lost the lease cannot commit.

  Option B: creating a numbered file is the commit.
  - Write the changes as file number N+1 with create-if-absent. The manifest is
    not touched per commit.
  - Costs one round trip, about 62ms.
  - The lease is no longer checked by the commit. An instance that lost the
    lease could still create the next file while the new holder serves reads
    from its cache, which would make those reads stale. Preventing that needs
    extra fencing objects, which is the machinery that keeps producing bugs in
    SlateDB.

  I recommend A. It costs one extra round trip per commit and makes the safety
  argument short: one object, one conditional write, and nothing else to
  coordinate.

  A can also be sped up later without changing the argument, for example by
  batching several transactions into one commit.

  Do you want A?

❯ How does Turbopuffer do it?                                                   

⏺ Turbopuffer does option A today, and it started with option B.

  - In 2024, by their own account, a write was a numbered file in the log
    directory, created only if absent. Readers listed the directory to find the
    latest state. That is option B.
  - By 2026, in their CMU talk, they describe it as: "we commit a file and then
    commit it into a manifest with compare and swap". Readers check freshness
    with one conditional request on the manifest, and they now advise against
    listing on a critical path. That is option A.

  Two other details from their design:

  - They batch. Writes to a namespace are collected and committed together, at
    most once per second, so many writes share the two round trips. Their median
    for a 500 kB write is 165ms.
  - Their indexing work queue uses the same trick: one JSON file, updated by
    compare-and-swap.

  One difference from us: Turbopuffer has no lease. Any of its nodes may write,
  and the swap alone settles who wins. We add the lease so that the holder can
  read from its cache without asking S3.

  Both findings come from Turbopuffer's own talks and posts, as recorded in
  docs/research/object-storage-architectures.md.

❯ What if the lease is not in-memory but based on some sort of key? Does that

⏺ Yes, it has precedent, and it's a good idea. If the lease belongs to a stable
  key instead of to a running process, a restarted app with the same key carries
  on as the holder at once. It needs no release and no wait, even after a
  crash.

  Precedent

  - Kafka static membership is the closest. A consumer with a fixed instance ID
    can restart and rejoin without the group reacting, as long as it returns
    within the timeout. It was added to make rolling restarts cheap.
  - Kubernetes leader election records a holder identity chosen by the client,
    and a process that comes back with the same identity keeps the lease.
  - ZooKeeper and etcd let a client reattach to its session or lease by ID after
    a reconnect.

  SlateDB does the opposite: every new process is a new writer and fences the
  previous one.

  What it risks. Reading from the cache is safe only if one live process holds
  the lease. A key makes that a promise: "whoever has this key is the same
  instance, and the previous one is gone." If two live processes ever share a
  key, both believe they hold the lease, and one can serve stale reads. They
  still cannot both commit, because the manifest swap prevents that.

  How I'd make the promise hold

  - The key lives with the local cache directory, generated on first use. Same
    disk means same instance.
  - An operating-system file lock on that directory allows one live process per
    key on a host. A new process can only start once the old one is really gone.
  - Each new process bumps a counter in the lease when it resumes. If a cache
    directory is ever cloned to another machine, the older copy finds out at its
    next renewal and stops.

  What it doesn't cover: a deploy onto a fresh disk, such as a new container
  without a persistent volume. That is a new key, so it waits for the timeout,
  unless the old app released the lease.

  So the key replaces the release whenever the cache disk survives the restart,
  and the release only still matters for fresh-disk deploys. Do you want the
  key-based lease, and should the release stay alongside it for that case?

⏺ What the manifest holds, and how it stays small.

  My proposal is that the database in S3 is a snapshot plus a log of changes
  since that snapshot. The manifest then holds four things:

  1. A version number, raised by one on every swap. It also makes every manifest
     unique, which the probe showed we need.
  2. The lease: the holder's ID and the renewal.
  3. A reference to the current snapshot: the full contents of the database as
     of some version.
  4. The list of change files since that snapshot, in commit order, each with
     its name and a checksum.

  Two rules go with it

  - Every file except the manifest is immutable and has a unique name. A file is
    never overwritten, so a confused old process cannot damage committed data.
    It can only leave garbage behind.
  - A file belongs to the database only if the manifest references it.
    Everything else is garbage to be cleaned up later.

  How it stays small. Each commit adds one entry to the list, so the list would
  grow without bound. The lease holder therefore folds the log into a new
  snapshot from time to time and swaps in a manifest that points to that
  snapshot with an empty list. The manifest's size then depends on the number of
  commits since the last snapshot, never on the size of the database. That
  matters because every commit rewrites the whole manifest.

  What a new instance does: it downloads the snapshot, replays the listed change
  files into its SQLite cache, and is ready.

  I'm leaving one thing for the next item on purpose: how to make a new snapshot
  without rewriting a whole multi-gigabyte database each time.

❯ Let's take what a change file contains next                                   

⏺ What a change file contains, part 1: results or statements?

  A change file has to carry everything needed to move a cache from the state
  before a commit to the state after it. There are two ways to do that.

  Option 1: record the results. The file lists what the transaction did to the
  data:
  - the rows it inserted or changed, each as a full row with its key
  - the keys of the rows it deleted
  - any schema changes, such as a new table

  Option 2: record the SQL statements and run them again on replay.

  I recommend option 1.

  - Replay doesn't involve the SQL engine. Applying a change file is just "put
    these rows, remove those keys". A bug in our parser or planner then can't
    make a rebuilt cache differ from the original.
  - Statements are not repeatable. random(), the current time, or a later engine
    version with a fixed bug would all give different results on replay. The
    log has to mean the same thing forever.
  - It is easy to test. Replay a log into an empty cache, and the result must
    equal the original cache row for row.

  Within option 1 I'd keep two things simple:

  - Net effect only. If a transaction changes the same row three times, the file
    records the final row once.
  - No old values. The file says what a row is now, not what it was. Replay
    doesn't need the old values, since there is only one history.

  Each file would also carry a small header: the format version, the name of the
  previous change file, and its own position in the chain.

  Do you agree with recording results, as net row changes?

  What engines default to

  - Physical for same-engine standbys: PostgreSQL's streaming replication,
    Oracle Data Guard, SQL Server availability groups, Aurora, Neon. In the
    SQLite world, Litestream, LiteFS and Graft.
  - Logical: MySQL, whose replication log is row-based by default. MongoDB's
    oplog. Distributed databases such as CockroachDB and FoundationDB replicate
    key-value changes, not pages. PostgreSQL added logical replication in
    version 10 for upgrades and selective replication.

  The pattern is that physical wins when the replica is an identical copy of the
  same engine, and logical wins when the log must be independent of the storage
  format.

  Why row-based fits us

  - The log is the truth, forever. It shouldn't depend on any page format.
  - Physical would mean shipping the SQLite cache's pages, which makes SQLite's
    file format our storage format. You rejected that.
  - The usual weakness of logical, missed changes, is smaller for us. We write
    the engine, so the change file is the engine's own output at commit, not
    something captured from outside.

  The real cost is the row above about loading on demand: a new instance can't
  fetch single pages, so it replays the log. That is the optimisation you've
  deferred.

⏺ I'll take how the cache stays in step with the log, since it completes the
  commit protocol.

  The rule: the cache is never ahead of S3.

  - The cache records its own position. A small table in the cache database
    holds the name of the last change file applied. It is updated in the same
    SQLite transaction as the rows, so the cache's contents and its recorded
    position always agree.
  - A transaction works inside an open SQLite transaction on the cache. Its
    writes go there uncommitted, so it can read its own changes, and nothing is
    final yet.
  - Commit order: build the change file from the transaction's net changes,
    upload it, swap the manifest, and only then commit the local SQLite
    transaction. If the upload or swap fails, roll the local transaction back.

  What a crash does

  - Before the swap: nothing was committed in S3. SQLite discards the unfinished
    local transaction on the next open. The uploaded change file, if any, is
    harmless leftover.
  - After the swap, before the local commit: S3 is one commit ahead of the
    cache. On restart, the instance sees that the manifest points past the
    cache's position, walks the chain back to that position, and applies what it
    missed.
  - Swap outcome unknown, for example after a timeout: re-read the manifest. If
    it points to our change file, the commit happened. Since files are named by
    their content, that check is exact.

  Catching up after a crash and rebuilding an empty cache are the same code
  path, just with different starting points.

  One case I'd fail loudly on: the cache's recorded position isn't anywhere in
  the log. That means the cache belongs to a different database or history, so
  the instance should refuse to start and not quietly rebuild.

  Does this order, S3 first and the cache second, with the cache tracking its
  own position, look right to you?

❯ Yes, looks good. How do we avoid stale reads after the swap but before local  
  commit? I guess we can't read while there's an open local write transaction?  
  Or does it not matter because we have the lease? Help me think it through.    

⏺ It doesn't matter, and the lease is exactly why. Here is the reasoning.

  The timeline of one commit

  1. The swap succeeds. S3 is now at commit N+1.
  2. The local SQLite transaction commits. The cache is now at N+1.
  3. Commit() returns to the application.

  A reader that runs between steps 1 and 2 sees N from the cache. That is fine,
  for two reasons.

  - Nobody has been told the commit happened. The writer's own caller is still
    waiting, so no one can know about N+1 and then be shown N. For everyone in
    this process, the commit takes effect at step 2.
  - Nobody else can look. Only the lease holder reads, and it reads only through
    the cache. No second observer exists who could see N+1 in S3 while this
    process still serves N.

  Strong consistency requires that a read reflects every commit that finished
  before the read began. A commit finishes when it is acknowledged, which is
  step 3. So the rule that makes this work is: acknowledge only after the local 
  commit.

  On reading during an open write transaction: reads don't need to stop. SQLite
  can serve readers while one write transaction is open, and they see the last
  committed state. The writer sees its own uncommitted changes. What does queue
  is other writers, since one write transaction at a time holds the cache's
  write lock, including during its S3 round trips.

  After a crash between steps 1 and 2, the writer's caller never got an answer.
  On restart the instance catches the cache up to N+1 before it serves anything,
  so every later read sees it.

  One failure needs a hard rule. If the swap succeeded but the local commit then
  fails, say because the disk is full, the commit is real in S3 and the cache
  can't show it. The instance must stop serving and recover by catching up,
  never carry on at N.

  Does that settle it? If so, I'd add two spec entries: the cache is never ahead
  of S3 and records its own position, and a commit is acknowledged only after
  the local commit.

  Concurrency, part 1: writes one at a time, reads in parallel.

  My proposal:

  - One write transaction at a time per database. A second writer waits until
    the first has committed or rolled back. This is SQLite's own model, and it
    matches "one commit at a time".
  - Reads run in parallel on as many cores as the application uses. Each read
    transaction sees one consistent state of the cache, even while a write is in
    progress.
  - Everything that changes state runs on a single path: write transactions, the
    commit steps, lease renewal and cache catch-up. That path is written as a
    state machine that does no I/O of its own. It receives events, such as "the
    upload finished", and answers with the next action, such as "now swap the
    manifest".

  Why that shape

  - It is what makes exact replay possible. In simulation, a seeded scheduler
    feeds the state machine its events in a chosen order, so the same seed gives
    the same run. In production the same state machine runs with real S3 and
    real timers.

    read-heavy workload.

  other writer on that database, including while it waits for S3. An
  application that begins a transaction, does something slow, and then commits
  holds everyone else up. SQLite behaves the same way.

  **Strongest consensus:**

  `synchronous=NORMAL` and foreign keys on. That includes Kerkour, the Rails 8
  defaults, PocketBase, Litestream and the owner's glue helper. [V]
  - Write transactions should start with `BEGIN IMMEDIATE`, because a deferred
  transaction that upgrades to a write gets `SQLITE_BUSY` and the busy timeout
  does not help. [V]
  - Use one writer connection and a pool of readers, and STRICT tables. [V]
  - Prefer upsert over `INSERT OR REPLACE`, keyset pagination over large
  `OFFSET`s, and accept that many small queries are fine in SQLite. [V]

  **STRICT plus WITHOUT ROWID, the arguments against first:**
  - The SQLite docs recommend WITHOUT ROWID only for non-integer or composite
  keys with rows under about 200 bytes, and say to benchmark first. I found no
  practitioner who uses it by default. [V]
  - Rows of about 2 KB all spilled to overflow pages, and primary-key lookups
  were about 4.7 times slower. [V measured]
  - With text keys, secondary indexes were bigger and lookups through them were
  about 25% slower. Primary-key lookups on small rows were about 1.7 times
  faster. [V measured]
  - There are no generated integer keys or `AUTOINCREMENT`, so the Rails,
  Django, sqlc and wtf schemas cannot be used unchanged. [V]
  - Random UUIDv4 keys made inserts roughly 15 to 18 times slower in one 2026
  benchmark. Time-ordered keys avoid most of that. [V author's post, not
  reproduced]
  - STRICT forbids `DATETIME`, `BOOLEAN` and `JSON`, which is what mattn and
  sqlc use to map columns to Go types. [V source code]
  - `update_hook` and `sqlite3_blob` do not work, and FTS5 needs an extra
  `INTEGER UNIQUE` column to index such a table. [V]
  - **Most serious:** with foreign keys always on and no PRAGMAs, a table that
  others reference cannot be rebuilt by migration. `DROP TABLE` either fails,
  silently deletes the children under `ON DELETE CASCADE`, or makes `COMMIT`
  fail if the keys are deferred. [V measured] Any migration that rebuilds such a
  table would have to be done by the engine, outside SQL. [I]
  - In favour: the SQLite author calls rowid-free tables the "perfect world",
  and they remove all the rowid quirks. [V]

  **Legacy behaviour we can avoid by rejecting syntax:** double-quoted strings,
  bracket and backtick identifiers, bare columns in aggregates, `LIMIT a,b`, odd
  join forms, `OR REPLACE` and the other conflict clauses, the foreign-key
  `MATCH` clause, all PRAGMAs, and the `localtime` modifier. `INSERT OR REPLACE`

⏺ The best-practices research is back, and its notes are on main in
  docs/research/sqlite-best-practices.md. It confirms most of our choices and

  Confirmed

  - Strict tables, foreign keys on, one writer with a pool of readers, and WAL 
    mode with relaxed flushing are what every server-side source recommends.
  - Legacy behaviour we can avoid just by rejecting syntax: double-quoted
    strings, bracket and backtick names, bare columns in aggregates, INSERT OR 
    REPLACE and the other conflict clauses, and all PRAGMAs.

  Arguments against without-rowid everywhere

  - SQLite's own docs recommend it only for non-integer or composite keys with 
    small rows, and say to benchmark first. The agent found no practitioner who
    uses it by default.
  - Large rows get slow. In a single test run, rows of about 2 KB made
    primary-key lookups about 4.7 times slower. Small rows were about 1.7 times
    faster.
  - No generated integer keys, so schemas from most existing tools and
    frameworks can't be used unchanged. Random keys also insert much more slowly
    than time-ordered ones.
  - The most serious: migrations. SQLite's documented way to restructure a table
    is to rebuild it with foreign keys switched off. With foreign keys always
    on and no settings, a table that others reference can't be rebuilt through
    SQL. The engine would have to offer its own migration path.

  In favour: SQLite's author calls rowid-free tables the "perfect world", and
  they remove every rowid quirk.

  Behaviour we must match exactly, since rejection can't avoid it

  - On strict columns, n = '1' is true, and inserting ' 7 ' into an integer
    column stores the integer 7.
  - Integer overflow becomes a float, and division by zero gives NULL.
