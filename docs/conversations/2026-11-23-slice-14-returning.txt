  ## What the pass accepts and refuses
  The tokenizer and parser already read RETURNING, so all the work is in
  `internal/sql/stmt` and `stmttest`.
  - **The form:** a new field `Returning stmt.Returning` on `Insert`, `Update`
  and `Delete`. It holds `Span`, from the keyword RETURNING to the end of the
  last column or the `*`, and `Columns`, the names in text order or nil for `*`.
  `Present()` says whether the clause is there.
  - **Same code as the select list:** `recognizer.returning` reads each column
  with `resultColumn`, the code that reads a select list. The two accept the
  same forms and refuse the rest under the same names.
  - **The select list takes no `t.v`, so RETURNING does not either.** You asked
  to be told which way this went.
  - **Accepted:** `*` alone, or one or more bare or double-quoted names, a
  column more than once, and the 84 keywords SQLite reads as column names.
  RETURNING adds no parameters.
  - **Refused as `result column other than a column or *`:** an expression, a
  function, a literal, `?`, parentheses, COLLATE, `t.v`, `t.*`, `main.t.v` and
  `excluded.v`.
  - **Other refusals:** an alias is `alias`; `*` together with another column is
  `* and another result column`; TRUE and FALSE are `TRUE or FALSE`; names in
  brackets, backticks, or empty get their usual names.
  - **Syntax errors, as SQLite gives them:** an empty list, RETURNING twice,
  `returning distinct`, RETURNING before WHERE, and RETURNING on a select,
  create table, drop table, create index, drop index or inside a trigger.

  **Branch:** `worktree-agent-a9579e82a7d8bcd14`. It has 9 commits on `main`
  (0f32a53). Nothing is pushed.

  ### What runs now
  An insert, an update, or a delete with `returning` and named columns or `*`
  now runs end to end through `database/sql`. This covers Exec, Query, QueryRow,
  prepared statements, arguments, write and read-only transactions, and a
  restart with an empty cache.

  Everything passes:

  - `make test-sql`
  - `make lint`
  - the new tests at `-count=50`, and under `-race` about 130 times

  The four guards of the statement pass are gone, and the driver's `check` calls
  `stmt.Check` alone again, so `Prepare` parses the text once. `engine.Check`
  added nothing there except an argument count that `Prepare` does not know.

  The commit format and replay are unchanged.

  ### Decisions
  All of these are recorded in `docs/todo/slice-14.md` under "The engine and the
  driver".

  - **Where the rows are held: in Go memory.** Each sink adds a row after
  writing it. A delete reads the row with a `get` just before deleting it. The
  rows can't come from the cache: outside a transaction they have to outlive the
  commit, and a delete's rows are gone from the table.
    - There is no bound on this memory. I recorded it as an open item in
  `docs/todo/storage-core.md`; a spool in the cache, like `KeySet`, would bound
  it.
  - **Commit before rows.** `Conn.write` returns the rows only after the commit
  returns nil; `writeIn` returns them after the savepoint is released.
    - A commit that fails, including one whose outcome is unknown, gives its
  error and no rows.
    - `TestConn_returning` pins this with a store that refuses the commit as too
  large (`simstore.Options.MaxSize`). `TestReturning` in `conn_test.go` pins
  the unknown outcome.
  - **A statement while the rows are open.**
    - In a transaction, the rows of a `returning` count as the connection's
  rows, like a select's. So `ErrRowsOpen` applies, and a commit while a loop
  reads them rolls back. I chose this so that one rule covers all open rows in a
  transaction, and so that lifting it later breaks nothing.
    - Outside a transaction the rows hold nothing and are not set as
  `Conn.rows`, so a statement or a begin can run beside them. This is needed
  because a select's open rows may still hold the reader there.
  - **Row order.** The rows come in the order of the primary key of the rows
  changed, or the reverse. The engine draws one direction per statement with
  `returning`, the same way it draws for a query (`Engine.order`). The pair
  checks the order against a select of SQLite run before the change
  (`pair.returnedInOrder`, `pair.checkReturned`), and counts both directions
  under `reached:`.
  - **Context cancellation.** It behaves as for the statement without
  `returning`. A context that ends while the caller reads the rows ends them
  with the context's error, and the change stays committed.
  - **Telemetry.** A statement with `returning` logs one event, as the write it
  is, when the write ends and before its rows are read.
    - `statement.rows` is the count changed, which equals the count returned.
    - An update or a delete also gets `statement.direction`.
    - `statement.rows_read` includes the extra `get` of a delete.
    - `report.end` now logs only once. No new metric or attribute.
  - **Smaller details:**
    - The plan types have a field `Returning *Returning`, and `Format` prints
  it.
    - `-0.0` comes back as `0.0`.
    - The columns are named as the table stores them, with their declared types.
  SQLite reports declared types for `returning` columns too, so they match
  mattn.
    - The `returning` columns are resolved after every other name in the
  statement, with the same `no such column` error as a select list.

  ### Where s4ql differs
  - **From SQLite:** no new difference was found. SQLite gave key order in every
  case I measured; s4ql varies the order, by the spec's rule.
  - **From mattn/go-sqlite3:** its Exec of a statement with `returning` reports
  the change count of the statement before it. mattn steps the statement once,
  and SQLite only updates the count when the statement finishes; the pinned
  shell shows the correct count. The driver check now runs SQLite's side of such
  an Exec through Query and counts the rows (`execByQuery`).

❯ Could we briefly discuss the "Outside a transaction the statement commits     
  before Query returns"? Why did you decide as you did, pros/cons?              

⏺ I chose it because in s4ql a commit is a write to S3 that can fail or end with
  an unknown outcome, and the caller must hear that from a place they always
  check.

  The alternative is SQLite's way: the change is made on the first step, and the
  commit happens when the rows are read to the end or closed.

  For committing before Query returns:
  - Errors reach the caller. A failed commit comes back as the error of Query.
    In SQLite's way it would come from Rows.Close, which most Go code runs in a
    defer and ignores.
  - A row read is a row committed. goqite reads the id of a sent message and
    hands it on. With the commit first, that id always belongs to a message that
    is durably there.
  - One rule with Exec. Both acknowledge at the same point, so the package doc's
    promise on errors holds for both.
  - The writer is not held open. In SQLite's way, a caller that reads slowly or
    forgets to close its rows keeps the write transaction open, and s4ql has one
    writer.

  Against it:
  - Rows are held in memory. They must outlive the commit, so they cannot be
    read from the cache. SQLite also collects them in memory on the first step,
    so this is no worse than SQLite, but it is unbounded for now.
  - Query waits for S3 before the first row, as Exec does.
  - One ambiguity remains. database/sql closes rows when their context ends, so
    a caller can still see a context error for a committed change. It is
    documented, and SQLite's way has the same problem in a worse form.
  - Timing differs from SQLite. I found no case where a caller can observe that,
    other than when the commit error arrives.

  Inside a transaction none of this applies: the rows come at once, and the
  transaction's own commit is the acknowledgement.

❯ What does _scalar_ subquery mean?                                             

⏺ A scalar subquery is a select in parentheses that stands where a single value
  would stand, such as a literal or ?. "Scalar" means it gives one value: one
  column of one row.

  goqite's receive uses one to pick the next message:

  update goqite set timeout = ?
  where id = (select id from goqite where queue = ? order by priority desc,
  created limit 1)
  returning id, body

  The inner select runs first and gives one id, and the outer statement then
  runs as if that id had been written there.

  Two edge cases follow SQLite's rules:

  - No row: the value is null, so id = null matches nothing. That is what goqite
    relies on when the queue is empty.
  - Several rows: SQLite takes the first row and gives no error.

  It is different from the other kinds of subquery, which give more than one
  value: in (select ...) gives a list, exists (select ...) gives a yes or no,
  and a subquery in from gives a table. Slice 15 would cover only the scalar
  kind, on the right of = in a where.
