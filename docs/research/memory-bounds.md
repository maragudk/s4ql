# Memory bounds of operators that hold rows

Date: 2026-11-24. Tags: **[V]** = read in a primary source in this run (official documentation, source code, release notes, or the project's own blog), or measured. **[U]** = not confirmed from a primary source.

Question: what bounds the memory of an operator that holds rows (sort, grouping, hash join, distinct, a materialised subquery or CTE, the rows of `RETURNING`, a result held for the client) in other engines? What happens at the bound, what are the defaults, and what is the scope? How did the design change over time? For s4ql, the options are in [feature-map.md](feature-map.md), core gap 6: (a) spool rows to the cache, (b) a limit with a clear error, (c) no bound for now.

What was read: the documentation, source, and release notes linked below. SQLite was read in the vendored amalgamation `internal/sqlite/c/sqlite3.c` (3.54.1), and measured with the Homebrew `sqlite3` shell 3.54.1, which has `TEMP_STORE=1`, `cache_size = -2000`, and a page size of 4096, as s4ql's binding has. s4ql was read at `main` of this date.

## Summary

- Pattern: each operator gets a memory budget, and spills to temporary files above it. PostgreSQL (4 MB), MySQL, CockroachDB (64 MiB), DuckDB, TiDB, and SQLite itself (its page cache) do this.
- Most add a second bound per query, session, or process, where the query fails or is cancelled: CockroachDB 25% of RAM, TiDB 1 GiB, DuckDB 80% of RAM. PostgreSQL has none and leaves it to the OS.
- Exceptions: each engine has operators that cannot spill (DuckDB's `string_agg`, TiDB's `DISTINCT` aggregates, CockroachDB's rows of `RETURNING`). Only the second bound stops them, with an error.
- Small and embedded engines mostly have an error or nothing. go-mysql-server: an error, off by default, no spilling. libSQL and D1: a cap on the response, 10 MB and 50 MB. ramsql: nothing. chai spills.
- History: engines that changed started with an error or no bound and added spilling one operator at a time. CockroachDB: error only in 2016, spilling from v2.0, again from v20.1 in its new engine. TiDB: spilling from v4.0, more operators up to v8.3. PostgreSQL's hash aggregate spills from 13, and had no bound before. DuckDB's from 0.9.0. None went from spilling back to an error.
- SQLite's docs say `RETURNING` rows are "accumulated in memory". Its code puts them in a transient table that spills: a million-row update with `RETURNING` peaked at 9 MB with s4ql's `temp_store`, and 150 MB with `temp_store = memory`.

## Per engine

### SQLite 3.54.1

- **Sort and grouping.** [V `sqlite3.c`, vdbesort.c] ORDER BY that no index gives, and GROUP BY, use the `VdbeSorter`, "a multi-threaded external merge sort algorithm that is efficient even if the number of elements being sorted exceeds the available memory". "If the amount of space used to store records in main memory exceeds the threshold, then the set of records currently in memory are sorted and written to a temporary file in 'Packed Memory Array' (PMA) format."
- **The sorter's threshold.** [V `vdbeSorterInit`] `mxPmaSize = MAX(szPma * pgsz, MIN(cache size in bytes, SQLITE_MAX_PMASZ))`, where `SQLITE_SORTER_PMASZ` is 250 pages and `SQLITE_MAX_PMASZ` is 512 MiB. With the defaults that is 2000 KiB. The threshold is set only `if( !sqlite3TempInMemory(db) )`. With temporary storage in memory it stays 0, which means "no limit", and the sorter never flushes.
- **Transient tables and indexes.** [V https://sqlite.org/tempfiles.html] DISTINCT, materialised views and subqueries, and the right side of IN use transient tables or indexes, "each stored in their own separate temporary file". "The temporary file is not opened and the information is not truly written to disk until the page cache is full." [V `sqlite3.c`] `OP_OpenEphemeral` opens a b-tree with no file name, and `sqlite3BtreeOpen` sets its page cache to `SQLITE_DEFAULT_CACHE_SIZE`, -2000. The tempfiles page says 500 pages, from a `SQLITE_DEFAULT_TEMP_CACHE_SIZE` that the 3.54.1 source does not have.
- **`temp_store`.** [V tempfiles.html, `sqlite3TempInMemory`] The default `SQLITE_TEMP_STORE` is 1 and the default pragma is 0, so temporary storage is a file. `temp_store = memory` (2) keeps all of it in memory without a bound.
- **RETURNING.** [V https://sqlite.org/lang_returning.html] "all of the database changes occur during the first invocation of sqlite3_step()", and "The RETURNING clause output is accumulated in memory." [V `sqlite3.c`, `codeReturningTrigger` and the end of `sqlite3FinishCoding`] The code writes each row with `OP_Insert` into a transient table opened with `OP_OpenEphemeral`, and reads it back with `OP_Rewind`/`OP_Next` after the changes. So the rows follow `temp_store` like any transient table. RETURNING exists since 3.35.0 (2021-03-12).
- **Measured** [V], Homebrew shell 3.54.1, a table of 1,000,000 rows of about 100 bytes of text, peak of "Memory Used" from `.stats`:

  | Statement | `temp_store = file` | `temp_store = memory` |
  | --- | --- | --- |
  | `update t set v = v \|\| 'x' returning v` | 9.4 MB | 150 MB |
  | `select v from t order by v desc` | 4.9 MB | 131 MB |
  | `select v, count(*) from t group by v` | 4.9 MB | 131 MB |
  | `select distinct v from t` | 5.1 MB | 154 MB |

- **Bound for the process.** [V `sqlite3.h`] `sqlite3_hard_heap_limit64(N)`: "memory allocations will fail when the hard heap limit is reached", which gives `SQLITE_NOMEM`. The soft limit "is advisory only". Both are off by default. `SQLITE_LIMIT_*` bound sizes of values and statements, not rows.
- **History.** [V https://sqlite.org/releaselog/3_7_8.html] vdbesort.c is dated 2011-07-09, and 3.7.8 (2011) lists "Orders of magnitude performance improvement for CREATE INDEX on very large tables". That this release brought the external sorter is [U].

### PostgreSQL

- **`work_mem`.** [V https://www.postgresql.org/docs/current/runtime-config-resource.html] "Sets the base maximum amount of memory to be used by a query operation (such as a sort or hash table) before writing to temporary disk files ... The default value is four megabytes (4MB)." "a complex query might perform several sort and hash operations at the same time ... the total memory used could be many times the value of work_mem". "Resource limits such as work_mem are applied individually to each worker".
- **Which operators.** [V same page] "Sort operations are used for ORDER BY, DISTINCT, and merge joins. Hash tables are used in hash joins, hash-based aggregation, memoize nodes and hash-based processing of IN subqueries." For hash tables, "The final limit is determined by multiplying work_mem by hash_mem_multiplier. The default value is 2.0".
- **Sort.** [V [tuplesort.c](https://github.com/postgres/postgres/blob/master/src/backend/utils/sort/tuplesort.c)] "If we do exceed workMem, we begin to emit tuples into sorted runs in temporary tapes."
- **Hash join.** [V [nodeHash.c](https://github.com/postgres/postgres/blob/master/src/backend/executor/nodeHash.c)] Rows of later batches go to temp files. When many rows share a hash value and the batches cannot be split further: "We have to just gut it out and hope the server has enough RAM."
- **Materialise, CTE, RETURNING, cursors.** [V [tuplestore.c](https://github.com/postgres/postgres/blob/master/src/backend/utils/sort/tuplestore.c)] "If we do exceed maxKBytes, we dump all the tuples into a temp file". A CTE scan calls `tuplestore_begin_heap(true, false, work_mem)` ([nodeCtescan.c](https://github.com/postgres/postgres/blob/master/src/backend/executor/nodeCtescan.c)). A statement with RETURNING runs to completion first: "On first execution, we run the portal to completion and dump the primary query's results into the portal tuplestore; the results are then returned to the client as demanded" ([portal.h](https://github.com/postgres/postgres/blob/master/src/include/utils/portal.h)). That tuplestore is bounded by `work_mem` ([portalmem.c](https://github.com/postgres/postgres/blob/master/src/backend/utils/mmgr/portalmem.c)). So the rows of a large RETURNING spill to a temp file.
- **Temporary files.** [V resource docs] `temp_file_limit`: "A transaction attempting to exceed this limit will be canceled. ... -1 (the default) means no limit." It is per process.
- **No memory limit per query.** [V https://www.postgresql.org/docs/current/kernel-resources.html] No setting raises an error at a memory total. The kernel "might terminate a PostgreSQL server process", after which PostgreSQL "will typically terminate all remaining connections". That a failed allocation gives an "out of memory" error for the query is [U] from documentation.
- **History.** [V https://www.postgresql.org/docs/13/release-13.html] "Allow hash aggregation to use disk storage for large aggregation result sets". Before 13, "once hash aggregation had been chosen, the hash table would be kept in memory no matter how large it got". 13 added `hash_mem_multiplier` with default 1.0 ([docs 13](https://www.postgresql.org/docs/13/runtime-config-resource.html)), and 15 raised it: "Increase hash_mem_multiplier default to 2.0" ([release 15](https://www.postgresql.org/docs/15/release-15.html)).

### MySQL and InnoDB

- **Filesort.** [V https://dev.mysql.com/doc/refman/8.4/en/order-by-optimization.html] Buffers grow "up to the size indicated by the sort_buffer_size system variable", and "A filesort operation uses temporary disk files as necessary if the result set is too large to fit in memory." Default 262144 bytes, global and session ([server variables](https://dev.mysql.com/doc/refman/8.0/en/server-system-variables.html)).
- **Internal temporary tables.** [V https://dev.mysql.com/doc/refman/8.4/en/internal-temporary-tables.html] "When the limit determined by tmp_table_size is reached, MySQL automatically converts the in-memory internal temporary table to an InnoDB on-disk internal temporary table. The default value is 16777216 bytes (16 MiB)." TempTable also has a global pool, `temptable_max_ram`: 1 GiB in 8.0, "3% of total memory, with a default value within a range of 1-4 GiB" in 8.4 ([8.4 changes](https://dev.mysql.com/doc/refman/8.4/en/mysql-nutshell.html)).
- **Hash join.** [V https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-18.html] "A join whose memory requirement exceeds this amount is executed on disk; an on-disk hash join uses a number of disk files and may not be executable if this number exceeds open_files_limit." [V [hash_join_iterator.h](https://github.com/mysql/mysql-server/blob/trunk/sql/iterators/hash_join_iterator.h)] At most 128 chunk files per input; a chunk that does not fit is read in parts.
- **Errors.** [V https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-28.html] 8.0.28 added `connection_memory_limit` and `global_connection_memory_limit`. Above them, "all queries from this connection are rejected with ER_CONN_LIMIT, including any queries currently running". Both default to unlimited. ERROR 1114 "The table ... is full" comes when "the disk is full or that the table has reached its maximum size" ([full-table](https://dev.mysql.com/doc/refman/8.4/en/full-table.html)).
- **History.** [V [8.0.2 notes](https://dev.mysql.com/doc/relnotes/mysql/8.0/en/news-8-0-2.html)] Spilling came first: temp tables were MEMORY tables converted to disk tables at a size. TempTable replaced MEMORY in 8.0.2; InnoDB became the only on-disk engine in 8.0.16; `tmp_table_size` limits each TempTable table from 8.0.28. Hash join in 8.0.18 spilled from the start. The memory limits that give an error came last, in 8.0.28, and are off by default.

### DuckDB

- **Limit.** [V https://duckdb.org/docs/2.0/configuration/overview.html] `memory_limit`, default "80% of RAM", for the database instance. `temp_directory` is `database_name.tmp`; `max_temp_directory_size` is "90% of available disk space".
- **At the limit.** [V https://duckdb.org/2024/07/09/memory-management.html] "The buffer manager abides by the same memory limit as any intermediate data structures." "If the memory limit is exceeded and disk spilling cannot be used ... an out-of-memory error is reported and the query is canceled."
- **What spills.** [V https://duckdb.org/docs/2.0/guides/performance/how_to_tune_workloads.html] GROUP BY, JOIN, ORDER BY, and window functions: "DuckDB supports larger-than-memory processing for all of these operators." What does not: "Some aggregate functions, such as `string_agg()`, do not support offloading to disk", and aggregates with ORDER BY ([oom errors](https://duckdb.org/docs/2.0/guides/troubleshooting/oom_errors.html)). "If multiple blocking operators appear in the same query, DuckDB may still throw an out-of-memory exception". Indexes are "currently not buffer-managed" ([oom](https://duckdb.org/docs/2.0/guides/performance/oom.html)).
- **History.** [V] An external sort by 2021 ([blog](https://duckdb.org/2021/08/27/external-sorting.html)). By 0.6.0 (2022), "an efficient out-of-core sort, out-of-core window functions, and an out-of-core hash join" ([0.6.0](https://duckdb.org/2022/11/14/announcing-duckdb-060.html)). In 0.9.0 (2023), hash tables of GROUP BY and DISTINCT "will spill data to disk instead of throwing an out-of-memory exception" ([0.9.0](https://duckdb.org/2023/09/26/announcing-duckdb-090.html)). The hash join was reworked in 1.2.0. The first version of each out-of-core operator before 0.6.0 is [U].

### CockroachDB

- **Per operator.** [V https://docs.cockroachlabs.com/docs/stable/vectorized-execution] "By default, the memory limit allocated per disk-spilling operation is `64MiB`." "This limit applies to a single operation within a single query". Sorts, unordered aggregations, hash joins, merge joins on non-unique columns, and window functions spill. "Operations that do not support disk spilling ignore the `sql.distsql.temp_storage.workmem` limit."
- **Per node.** [V https://docs.cockroachlabs.com/docs/stable/cockroach-start] `--max-sql-memory`, default 25%; `--max-disk-temp-storage`, default 32 GiB. "If the maximum on-disk storage capacity is reached, the query will return an error during execution." The error is "memory budget exceeded: %d bytes requested, %d currently allocated, %d bytes in budget" with `pgcode.OutOfMemory` ([resource.go](https://github.com/cockroachdb/cockroach/blob/master/pkg/util/mon/resource.go)).
- **RETURNING.** [V [insert.go](https://github.com/cockroachdb/cockroach/blob/master/pkg/sql/insert.go)] With `rowsNeeded`, the insert creates `rowcontainer.NewRowContainer(params.p.ExecMon().MakeBoundAccount(), ...)`, runs "the mutation to completion", and "Result rows must be accumulated." That container is in memory and counts against the node's budget. Whether every execution path does this is [U]. Buffered rows of a subquery or CTE use "a disk-backed row container" ([buffer_util.go](https://github.com/cockroachdb/cockroach/blob/master/pkg/sql/buffer_util.go)).
- **Results for the client.** [V cluster settings] `sql.defaults.results_buffer.size`, 512 KiB: "the buffer that accumulates results for a statement or a batch of statements before they are sent". After it overflows, results stream and automatic retries end ([transactions](https://docs.cockroachlabs.com/docs/stable/transactions)).
- **History.** [V https://www.cockroachlabs.com/blog/memory-usage-cockroachdb/, 2016] Memory was "limited by a global setting `--max-sql-memory`", a query at the limit "fails with a client-side error", and "the server sorts in-memory". [V [RFC 2017](https://github.com/cockroachdb/cockroach/blob/master/docs/RFCS/20170522_external_storage.md)] planned on-disk sorter, aggregator, distinct, and hash joiner. [V cockroachdb/docs, v2.0 settings] v2.0 had `sql.distsql.temp_storage.joins` and `.sorts`. [V https://cockroachlabs.com/blog/disk-spilling-vectorized/, 2020] "v1 of the engine didn't support disk spilling"; from v20.1 such queries "fall back to disk". The v20.2 docs say "Unordered aggregation operations do not support disk spilling". That this arrived in v21.1 is inferred from the docs, [U].

### TiDB

- **Quota.** [V https://docs.pingcap.com/tidb/stable/system-variables/] `tidb_mem_quota_query`, default 1 GiB. Before v6.5.0 it is "for a query"; from v6.5.0 "for a session", including "the memory consumed by the transactions in the session".
- **At the quota.** [V same page and https://docs.pingcap.com/tidb/stable/configure-memory-usage/] `tidb_mem_oom_action` applies when a statement "cannot be spilled over to disk". "The default value is `CANCEL`, but in TiDB v4.0.2 and earlier versions, the default value is `LOG`." CANCEL "stops executing the SQL query immediately" and returns error 8175, "Your query has been cancelled due to exceeding the allowed memory limit for a single SQL query" ([errname.go](https://github.com/pingcap/tidb/blob/master/pkg/errno/errname.go)). Spilling is on by default (`tidb_enable_tmp_storage_on_oom`). `tmp-storage-quota` is off by default; above it, "the current SQL operation is canceled".
- **Instance.** [V system variables] `tidb_server_memory_limit`, new in v6.4.0, default 80%: "TiDB cancels the currently running SQL statement with the highest memory usage", one at a time.
- **History.** [V configure-memory-usage] "Disk spill for the Sort, MergeJoin, and HashJoin operators is introduced in v4.0.0." HashAgg (non-parallel) in v5.2.0; parallel HashAgg experimental in v8.0.0 and GA in v8.2.0; TopN in v8.3.0. "The disk spill for HashAgg does not support SQL executions containing the `DISTINCT` aggregate function." CTEs spill ([cte.go](https://github.com/pingcap/tidb/blob/master/pkg/executor/cte.go)); the version is [U]. RETURNING was not researched.

### Go and embedded engines

- **go-mysql-server (Dolt).** [V [sql/memory.go](https://github.com/dolthub/go-mysql-server/blob/9237da5/sql/memory.go#L78-L135)] `ErrNoMemoryAvailable = errors.NewKind("no memory available")`, read from the environment variable `MAX_MEMORY` in MiB. With it unset, `HasAvailableMemory` returns true. The check measures the heap of the whole process. Sort collects every row into a `RowsCache` and calls `sort.Stable` ([rel_iters.go](https://github.com/dolthub/go-mysql-server/blob/9237da5/sql/iters/rel_iters.go#L571-L592)); GROUP BY and DISTINCT use the same caches. The build side of a hash join and cached subquery results do not go through the check ([hash_lookup.go](https://github.com/dolthub/go-mysql-server/blob/9237da5/sql/plan/hash_lookup.go#L61)). No spilling was found. No Dolt documentation of `MAX_MEMORY` was found.
- **chai (formerly genji).** [V [temp_tree_sort.go](https://github.com/chaisql/chai/blob/e53516f/internal/stream/rows/temp_tree_sort.go#L23-L24)] "It creates a temporary index and uses it to sort the stream." A transient session commits its batch to Pebble when it passes `1 << 19 // 512KB` ([engine.go](https://github.com/chaisql/chai/blob/e53516f/internal/kv/engine.go#L21)). GROUP BY sorts through such a tree, and DISTINCT uses one. No limit or error is documented.
- **ramsql.** [V [predicate.go](https://github.com/proullon/ramsql/blob/6fc02e7/engine/agnostic/predicate.go#L380)] Sorts, groups, distinct, and joins work on Go slices. The README: "RamSQL has been written to be used in your project's test suite."
- **rqlite.** [V https://rqlite.io/docs/api/api/] "By default, SQL queries do not time out." `db_timeout` "is applied per SQL statement". No limit on result size or memory is documented. Since v8.19.0 ([blog](https://www.philipotoole.com/?p=6584)).

### Hosted SQLite and object storage

- **libSQL server.** [V [main.rs](https://github.com/tursodatabase/libsql/blob/a1d031c/libsql-server/src/main.rs#L160-L175)] `SQLD_MAX_RESPONSE_SIZE`, default 10MB, and `SQLD_MAX_TOTAL_RESPONSE_SIZE`, default 32MB. The error: "query response exceeds the maximum size of {}. Try reducing the number of queried rows." ([query_result_builder.rs](https://github.com/tursodatabase/libsql/blob/a1d031c/libsql-server/src/query_result_builder.rs#L27-L28)). Optional heap limits map to SQLite's: "libSQL will bail out with SQLITE_NOMEM error if it goes over this limit". Turso Cloud: "Transaction have a 5 seconds window to complete" ([HTTP reference](https://docs.turso.tech/sdk/http/reference)); whether it uses the sqld response defaults is [U]. Turso's Rust rewrite added "external sorting" in 0.1.3 (2025) and spilling hash joins by 0.5.0 (2026) ([CHANGELOG](https://github.com/tursodatabase/turso/blob/main/CHANGELOG.md)).
- **Cloudflare D1.** [V https://developers.cloudflare.com/d1/platform/limits/] "Maximum SQL query duration: 30 seconds". "Maximum query result size: 50 MB", effective 2026-11-04: "Queries that return a result larger than 50 MB will fail and return an error." Queries "run within the Workers platform CPU and memory limits", with no number. The errors include "D1 DB's isolate exceeded its memory limit and was reset." ([debug D1](https://developers.cloudflare.com/d1/observability/debug-d1/)).
- **ClickHouse.** [V [Settings.cpp](https://github.com/ClickHouse/ClickHouse/blob/196d42c/src/Core/Settings.cpp)] `max_memory_usage` default 0, "unlimited", in open source. `max_bytes_ratio_before_external_group_by` and `..._sort` default 0.5, with the history entry "Enable automatic spilling to disk by default." in 25.1. Before that, spilling was off unless `max_bytes_before_external_*` was set. A server limit of 0.9 of RAM applies ([ServerSettings.cpp](https://github.com/ClickHouse/ClickHouse/blob/196d42c/src/Core/ServerSettings.cpp#L478)). The error is `MEMORY_LIMIT_EXCEEDED` (241).
- **Snowflake.** [V https://docs.snowflake.com/en/user-guide/ui-query-profile] "the query processing engine will start spilling the data to local disk. If the local disk space is not sufficient, the spilled data is then saved to remote disks."
- **Neon.** [V https://neon.com/docs/reference/compatibility] Computes have "20 GiB of local disk space or 15 GiB x the maximum compute size (whichever is highest)" for "temporary files used by Postgres". The page says nothing of `work_mem` or `temp_file_limit`.

## What s4ql has today

- **`KeySet`.** `internal/core/tx.go:729-884`. A set of primary keys of one table in a temporary table of the cache, `temp.s4ql_keys_N`, made by `createKeyTable` (`tx.go:574-590`) as `strict, without rowid` with the key columns. `Add` runs `insert or ignore`. `All` reads one key at a time with `order by ... limit 1` after the last key, each with a statement that has ended before the row of the key changes. The set is dropped when `Tx.Keys` returns. Update and delete use it, so that no cursor is open on a table that changes.
- **Other spools.** The keys that a transaction touched are recorded in temporary tables too (`touch`, `tx.go:539-590`). The commit object and the annotations are written to an unnamed file next to the cache through a 64 KiB buffer, "so that what it holds is never in memory at once" (`internal/core/spool.go`).
- **The cache's SQLite.** The cgo binding sets neither `temp_store` nor `cache_size`, so SQLite's defaults hold: temporary storage in files, and 2000 KiB of page cache (`internal/sqlite/sqlite_browser.go:15-26` states this, and the browser build sets the same with `pragma temp_store = file; pragma cache_size = -2000`). `internal/sqlite/options.h` sets no heap limit, and `DenyProcessPragmas` refuses `soft_heap_limit` and `hard_heap_limit` (`internal/sqlite/sqlite.go:393-399`). A sort that no index gives is done by the cache's SQLite, which "reads every row before it gives the first" (`internal/engine/operator.go:61-66`), so it spills as measured above.
- **Rows of a `returning`.** `returning.rows [][]*s4qlpb.Value` (`internal/engine/returning.go:17-25`), appended by `add` for each changed row (`returning.go:75-88`), and handed over to `returned` (`returning.go:133-151`) once the commit has succeeded (`internal/engine/engine.go:456-461, 549-550`). Through `Exec` they are dropped (`dropReturns`, `returning.go:115-127`). The rows must outlive the write transaction ([storage-core.md](../todo/storage-core.md)).
- **A statement that fails changes nothing.** Outside a transaction, a write runs in a write transaction of its own, rolled back on any error and on a panic (`engine.go:480-491`), and gives no rows if the statement or its commit fails (`engine.go:513-548`). Inside a transaction, each statement runs under the savepoint `s4ql_statement` (`internal/core/tx.go:296-308`), and a failed statement is rolled back to it, so the transaction goes on (`internal/engine/tx.go:331-348`). An error that the engine raises in Go during `check` or `run` takes these paths.
- **Two limits on this.** An error of the cache during a write fails the transaction, which "can then only be rolled back", and "A local I/O failure also stops the instance" (`tx.fail`, `internal/core/tx.go:383-393`). `classify` counts `SQLITE_FULL` and `SQLITE_NOMEM` as local I/O failures (`internal/core/errors.go:150-175`). So a spool in the cache that fills the disk stops the instance, and does not fail only the statement. The exception is SQLite's refusal of a value as too big, which leaves the transaction going on (`tooBig`, `internal/core/tx.go:607-615`, and `KeySet.Add`, `tx.go:824-829`): a precedent of a limit with an error that changes nothing.
