# The object store as the lease clock

Date: 2026-11-12. Tags: **V** = verified in this run, from a source (URL and quote) or a test against the project's Tigris bucket. **I** = my inference. "Silent" = the documentation says nothing.

Question: can a taker decide that the lease in `manifest.json` has expired by comparing the store's `Date` response header with the manifest's `Last-Modified`, so that no machine's wall clock is used? The holder checks only its monotonic clock: less than the lease duration `L` (30 s) since it sent its last successful renewal.

## Short answer

The idea holds up in principle, and it is better than today's design: it replaces "every machine's wall clock is right" with "the store's own clocks agree with each other". But it is not clock-free. Its safety rests on the store's internal clock sync, which no store documents a bound for, and on `Last-Modified` being set by the server, which fails on Tigris and MinIO for any client that sends the right header. No prior art does this; the established clock-free rule (Kubernetes, the DynamoDB Lock Client) costs only a longer wait for a freshly started taker.

The idea is safe under three conditions.

1. **The taker CASes against the version it measured.** It reads the manifest, computes `D = Date − Last-Modified`, and takes the lease only with `If-Match` on the ETag from that same response. Then a slow response, a stale cache, a renewal that lands after the read, and a taker that acts late all err in the safe direction: the CAS fails if anything changed, and time that passes after `Date` only makes the lease older (I, section 6).
2. **The margin covers header resolution and the skew between the store's clocks.** Both headers have whole seconds, which costs under 1.5 s (V for the format, I for the bound). `Last-Modified` and `Date` come from different machines in most stores: an nginx front end and a storage node on Tigris, the receiving and the serving node in distributed MinIO (V). Distributed MinIO allows its nodes 15 minutes of skew (V); the others say nothing (silent). With `L` = 30 s, `m` = 10 s covers resolution and about 8 s of store skew. Store skew in the direction "`Date` clock ahead" is the unsafe one, and nothing in one response reveals it.
3. **The holder follows rules that every lease design needs.** It anchors its window at the start of the first attempt of a renewal (not at a retry, and not at the response), it checks the window after reading its cache rather than before, and it measures with a clock that counts suspended time. Go's monotonic clock on Linux is `CLOCK_MONOTONIC`, which "does not count time that the system is suspended" (V). No margin covers a violation of these (section 6).

What a store must provide:

- **`Last-Modified` from the store's clock, at or after the moment the write request arrived.** Start of request, completion, and forward bumps are all fine. A client-supplied value is not. **Tigris** stores a `Last-Modified` request header and returns it as-is, even `garbage` or a date in 2049, and `CopyObject` copies it (V, test); the listing keeps the real server time. **MinIO** lets any client with `s3:PutObject` set the time with `x-minio-source-mtime` (V, source). AWS documents that only S3 can modify the value (V), but does not say where it comes from; whether it is ever taken from `x-amz-date` should be tested before relying on AWS.
- **`Date` on every response from a clock close to the one behind `Last-Modified`.** RFC 9110 requires `Date` on 2xx, 3xx and 4xx (V). A reverse proxy such as nginx replaces it with its own clock by default (V).
- **`If-Match` on PUT,** which s4ql already requires.

Recommendation, as input for the design decision (I):

- **If trust in correctness comes first, use the clock-free rule:** the taker waits `L + m` on its own monotonic clock after it read version `V`, then CASes against `V`. It needs no shared clock, only clock rates, and it is what Kubernetes and the DynamoDB Lock Client do (section 4). Add **graceful release** on clean shutdown, so that only a crash costs a wait of about 40 s.
- **The S3 clock is then an optional fast path** for an instance that starts and finds a long-abandoned lease. Combined as "CAS at `t + max(0, L + m − D)`", it never waits longer than the clock-free rule, so a `Last-Modified` clock that runs ahead (Garage can produce this, V) cannot block a taker. But it is exactly as unsafe as the pure S3-clock rule when `D` is too large. It buys liveness, not safety, and it should be enabled only on stores where the conditions above have been checked.

## Test against Tigris

Setup: the project's Tigris bucket (endpoint `t3.storage.dev`, `AWS_REGION=auto`), client a Mac Mini in Denmark, every response `X-Tigris-Served-From: fra`. Requests signed with curl's `--aws-sigv4` and with a small SigV4 signer in Python. Keys under `research/s3-clock/`, all deleted afterwards (a final listing of the prefix returned `KeyCount` 0). About 400 requests. The scripts were not published.

Tigris's `X-Amz-Request-Id` is a Unix time in nanoseconds (for example `1794486907725774168` at `Date: Thu, 12 Nov 2026 12:35:08 GMT`), which gives a sub-second server time for each request (I: the format is undocumented; the values matched `Date` and the local clock in every request).

- **`Date` is present on every response.** PUT 200, conditional PUT 200, conditional PUT 412, HEAD 404 and GET 404 all carried `Date` (V, test). The header `Server: nginx` was on every response.
- **Resolution is one second.** `Last-Modified` and `Date` are RFC 1123 dates in whole seconds. The listing showed `<LastModified>2026-11-12T12:36:22Z</LastModified>`, with no fraction (V, test).
- **`Last-Modified` is the time the upload completed.** A 3 MiB PUT throttled to 300 KiB/s: the server's request id said 12:36:12.09 (request start), the local clock saw the response at 12:36:22.27, and `Last-Modified` was 12:36:22 (V, test). In 150 small PUTs, `Last-Modified` was 0 s after the request-id second 146 times, 1 s after 3 times, and 2 s after once (V, test).
- **`Date − Last-Modified` was never negative.** For 150 PUTs followed at once by a HEAD: the PUT's own `Date − Last-Modified` was 0 s (141) or 1 s (9), and the HEAD's was 0 s (119) or 1 s (31). Polling HEAD for 6 s after a PUT, `D` rose 0, 0, 1, 1, 1, 1, 2, 3, ... 6 in step with the local clock (V, test).
- **`Date` is stamped when the response is produced, not when the request arrives.** One HEAD whose request id said 12:37:08.46 took 2.6 s and came back with `Date` 12:37:10 (V, test). This is the safe direction for a taker (section 6).
- **A client can set `Last-Modified` on Tigris.** A PUT with the request header `Last-Modified: Mon, 01 Jan 2001 00:00:00 GMT` returned 200, and later HEAD and GET returned exactly that `Last-Modified`. `Fri, 01 Jan 2049 00:00:00 GMT` and `garbage` were stored the same way. A conditional PUT (`If-Match`) with the header also stored it. `CopyObject` of such an object copied the fake value to the copy. The listing's `LastModified` stayed the real server time in every case (V, test). The 2049 value broke RFC 9110's rule that a server "MUST NOT generate a Last-Modified date that is later than the server's time of message origination" (V, RFC 9110 §8.8.2.1).
- **Other headers did not change `Last-Modified`.** `x-amz-meta-mtime`, `x-amz-meta-last-modified` and `X-Minio-Source-Mtime` had no effect. A request `Date` header got 400. A request signed with an `x-amz-date` 300, 840 or 1,000 s in the past, or 300 s in the future, got 200 and the server's own time as `Last-Modified` (V, test). Tigris accepted a signature 1,000 s old, where AWS's limit is 15 minutes (section 1).
- **Server and client clocks.** The request-id time was 0.07 to 0.11 s after the local send time for every request in one run of 20, which is about the TLS setup time. Tigris's clock and this Mac's NTP clock agreed within tens of milliseconds (I).

## 1. AWS S3

- **`Last-Modified` is system metadata that only S3 can change.** The metadata table: "Last-Modified | The object creation date or the last modified date, whichever is the latest. For multipart uploads, the object creation date is the date of initiation of the multipart upload. | No" (the last column is "Can user modify the value?"). And: "System controlled – Metadata such as the object-creation date is system controlled, which means that only Amazon S3 can modify the date value." (V, https://docs.aws.amazon.com/AmazonS3/latest/userguide/UsingMetadata.html)
- **The moment for a single PutObject is not documented.** The documentation says nothing about whether a single PUT is stamped when the request starts or when it completes (silent). A Stack Overflow question reports the start: "I start upload of a large file at 10:00 AM and say upload takes 4 minutes. I am seeing that instead of showing LastModified time as 10:04 AM its showing the same as 10:00 AM, i.e. when I initiated the upload." It does not say whether the upload was multipart, and SDKs switch to multipart for large files (V for the quote, https://stackoverflow.com/questions/70303934; I for the caveat). A NiFi user wrote in 2021 that "S3 and GCS are setting an object's last modified timestamp to the time when the object started uploading" as his reading of why listings missed files (V, https://www.mail-archive.com/users@nifi.apache.org/msg14192.html). For multipart uploads, the start is documented (quote above). Tigris stamps the completion (V, test). For the lease, either is safe, because both are after the holder sent the request (section 6).
- **Nothing says where the value comes from.** I found no statement that S3 does or does not use the request's `x-amz-date` (silent). If it did, a holder whose wall clock is behind would write an old `Last-Modified`, and the design would again depend on the holder's wall clock. Tigris ignores `x-amz-date` for this (V, test). This needs a test against AWS before s4ql relies on it there: sign a PUT with an `x-amz-date` a few minutes in the past, and read `Last-Modified` back.
- **Resolution: seconds in the header, and in practice seconds in listings.** The header is an HTTP-date, which has whole seconds (V, RFC 9110 §5.6.7). The AWS reference does not state the precision of `LastModified` in listings (silent). Arvados: "AWS and Google implementations of S3 always return zero nanoseconds in the "list objects" response, but Ceph/nautilus returns timestamps with milliseconds" (V, https://dev.arvados.org/issues/16842). An rclone commit: "Normally AWS returns the milliseconds as .000 in listings, but if versions are in use it may not." (V, https://git.frostfs.info/KurlesHS/rclone/commit/cf0bf159abbf8505fab84327c29fe2a24e361ae2)
- **`Date` is listed as a common response header.** "Date | The date and time that Amazon S3 responded; for example, Wed, 01 Mar 2006 12:00:00 GMT." The table "describes response headers that are common to most Amazon S3 responses" (V, https://docs.aws.amazon.com/AmazonS3/latest/developerguide/RESTCommonResponseHeaders.html). "Most" is not "all", and the page does not say which machine produces it (silent). The system metadata table lists "Date | The current date and time. | No" (V, UsingMetadata above). RFC 9110 makes `Date` mandatory on 2xx, 3xx and 4xx (section 3).
- **No statement on clock accuracy inside S3, or on agreement between the clocks behind the two headers** (silent). The nearest thing is in the legacy Glacier vault API: "Note that `Date` returned may drift slightly from other dates, so for example, the date returned from an Upload Archive (POST archive) request may not match the date shown for the archive in an inventory list for the vault." (V, https://docs.aws.amazon.com/amazonglacier/latest/dev/api-common-response-headers.html). That is another service, but it shows that AWS does not promise that its two kinds of timestamp agree.
- **S3 does compare clocks against client requests, coarsely.** `RequestTimeTooSkewed` means "The difference between the request time and the server's time is too large." (V, https://docs.aws.amazon.com/AmazonS3/latest/API/ErrorResponses.html). The window is 15 minutes in the Signature Version 2 documentation (V for SigV2, https://docs.aws.amazon.com/AmazonS3/latest/API/RESTAuthentication.html). This bounds the client's clock, not S3's.
- **Can a newer version have an earlier `Last-Modified`?** For multipart uploads, yes by the documented rule: an upload started at 10:00 and completed at 10:05 is stamped 10:00, so it can replace a version written at 10:02 and still look older (I, from the quote). For unconditional concurrent PUTs, "If two PUT requests are simultaneously made to the same key, the request with the latest timestamp wins" (V, https://docs.aws.amazon.com/AmazonS3/latest/userguide/Welcome.html), which suggests the winner carries the latest timestamp (I). For a chain of `If-Match` PUTs, each write can only be sent after the previous one returned its ETag, so with one correct clock the order holds. With skewed nodes it need not (I). The lease rule only ever reads the current version, so this does not matter for it (section 6).
- **`Last-Modified` later than `Date`?** I found no report for AWS (silent). RFC 9110 requires a server to replace a future `Last-Modified` with its `Date` (section 3), so if S3 follows it, a skew that puts `Last-Modified` ahead is hidden as `D = 0`. That is the safe direction.

## 2. S3-compatible stores

A research agent read the documentation and, where it is open, the source. I checked the MinIO and Garage code claims against the source myself (V). "V via the agent" marks quotes I did not re-fetch. In every store the `Last-Modified` header has whole-second resolution, because it is an HTTP-date.

- **Cloudflare R2.** Set by the server. The S3 compatibility page does not mention `Last-Modified` (silent, https://developers.cloudflare.com/r2/api/s3/api/). The Workers API's `uploaded` is "A Date object representing the time the object was uploaded." (V via the agent, https://developers.cloudflare.com/r2/api/workers/workers-api-reference/). On ordering: "In the event two clients are writing (`PUT` or `DELETE`) to the same key, the last writer to complete 'wins'." (V via the agent, https://developers.cloudflare.com/r2/reference/consistency/). No documented way for a client to set it; the migration tools keep only user metadata (V via the agent). `Date` came from `Server: cloudflare` on an r2.dev URL, so the edge stamps it (V via the agent, probe; the S3 endpoint was not probed). Clock sync: silent.
- **Tigris.** Set by the server at completion (V, test), except that a client's `Last-Modified` request header overrides the header value (V, test, see above). Tigris uses its timestamps for replication and conflict resolution: "Like many other things in Tigris, we use time to determine who wins a conflict" and "We run NTP clients on all our infrastructure and that usually keeps us within about 10 microseconds (10,000 nanoseconds) off of NTP time." The same post describes a skew bug: two servers with skewed clocks let "A DELETE could be sequenced before a PUT", and the fix covers DELETE only (V via the agent, https://www.tigrisdata.com/blog/conflict-resolution-is-fun). `Date` comes from `Server: nginx` on `t3.storage.dev` and `Server: Tigris OS` on `fly.storage.tigris.dev` (V via the agent, probe; nginx on `t3` also V, test). Shadow-bucket migration: silent on whether the source's `Last-Modified` is kept.
- **MinIO.** Set by the node that received the PUT, after the body is received and encoded, before the commit lock: `modTime := opts.MTime` / `if opts.MTime.IsZero() { modTime = UTCNow() }` (V, `cmd/erasure-object.go:1461`, https://github.com/minio/minio). Internally nanoseconds; listings in milliseconds (V via the agent). **Any client with `s3:PutObject` can set it**: `putOptsFromHeaders` parses the `x-minio-source-mtime` header into `MTime` (V, `cmd/object-api-options.go:369`), and the replication permission is checked only `if r.Header.Get(xhttp.AmzBucketReplicationStatus) == replication.Replica.String()` (V, `cmd/object-handlers.go:1931`). On Tigris the same header had no effect (V, test). `Date` is added by Go's `net/http` on the node that serves the read (V via the agent, https://github.com/golang/go/blob/master/src/net/http/server.go). Allowed skew: "All servers in a distributed deployment must have clocks synchronized to within 15 minutes of each other." (V via the agent, https://docs.min.io/community/minio-object-store/operations/checklists/software.html), enforced as `const DefaultSkewTime = 15 * time.Minute` (V, `cmd/storage-rest-server.go:110`). So in distributed MinIO, `Last-Modified` and `Date` come from different nodes whose clocks are only required to agree within 15 minutes. A PUT through a node with a slow clock can make `Last-Modified` go backwards (V via the agent, source reading; I for the consequence). Single-node MinIO has one clock for both. The GitHub repository is archived (V via the agent).
- **Google Cloud Storage (XML API).** Tracks `updated`, which changes on any metadata change: the listing's `LastModified` is "The date and time that the object metadata was last modified." (V via the agent, https://docs.cloud.google.com/storage/docs/xml-api/get-bucket-list), and `updated` is set "whenever any metadata of the object changes", including "changes made by Cloud Storage on behalf of a requester, such as changing the storage class based on an Object Lifecycle Configuration" (V via the agent, https://docs.cloud.google.com/storage/docs/json_api/v1/objects). Changes only move it forward, which is the safe direction for the lease. Listing in milliseconds; the header truncates (V via the agent, observed on a public object). `Date` present. Metadata lives in Spanner; nothing public on which clock stamps `updated` or `Date` (silent).
- **Backblaze B2 (S3 API).** `Last-Modified` appears to be `uploadTimestamp` (I via the agent: the example header matches the version id), and the native API documents `X-Bz-Upload-Timestamp` as "Timestamp from when the upload began." (V via the agent, https://www.backblaze.com/apidocs/b2-download-file-by-id). So B2 stamps the start. `src_last_modified_millis` is ordinary file info and is not documented to change it. A native-API header `X-Bz-Custom-Upload-Timestamp` sets the upload timestamp, "must not use a date that is set to a time in the future", and is enabled only by support for migrations; it is not documented for the S3 API (V via the agent, https://www.backblaze.com/apidocs/b2-upload-file). `Date` present. Clock sync: silent.
- **Garage.** Set by the API node at the start of the request, in milliseconds, and bumped past the previous version: `.map(|t| std::cmp::max(t + 1, now_msec()))` (V, `src/api/s3/put.rs:720-726`, branch `main-v2`, https://git.deuxfleurs.fr/Deuxfleurs/garage). If the previous version came from a node whose clock is ahead, the new `Last-Modified` can be in the future relative to `Date`. Issue #543: "if the clocks on two nodes are diverging, a node B might do a write strictly after a node A but in it's local time it thinks that that write is happening before" (V via the agent, https://git.deuxfleurs.fr/Deuxfleurs/garage/issues/543). Clients cannot set it. `Date` is added by hyper on the API node. The documentation says nothing about clock sync (V via the agent, grep of `doc/book`).
- **Ceph RGW.** Set by the RGW daemon at commit, `meta.set_mtime = real_clock::now()` when not given (V via the agent, `src/rgw/driver/rados/rgw_rados.cc`). Only system users (multisite sync) can preserve an mtime. Listings show seconds as `.000Z`. `Date` from the Beast frontend on the RGW daemon. Ceph monitors allow "clocks to drift up to a maximum of 0.05 seconds (50 milliseconds)", and "it is advisable to synchronize *all* nodes in your cluster" (V via the agent, https://github.com/ceph/ceph/blob/main/doc/rados/troubleshooting/troubleshooting-mon.rst); nothing enforces this for RGW daemons.

| Store | `Last-Modified` set by | Moment | Client can set it | `Date` from | Skew documented |
|---|---|---|---|---|---|
| AWS S3 | S3 ("only Amazon S3 can modify") | undocumented for one PUT; multipart: initiation | no (documented) | S3 front end | silent |
| R2 | server | undocumented | no known way | Cloudflare edge | silent |
| Tigris | server, but a request `Last-Modified` header overrides the header value | completion (test) | **yes** (test) | nginx front end | NTP "about 10 microseconds" (blog) |
| MinIO | receiving node | after body, before commit | **yes**, `x-minio-source-mtime` | serving node | up to 15 minutes allowed |
| GCS | server (`updated`) | finalize (I); bumped by metadata changes | forward only | server | silent |
| B2 | server | start of upload | native API only, with support | server | silent |
| Garage | API node, bumped past previous version | start of request | no | API node | silent; issue #543 |
| Ceph RGW | RGW daemon | commit | system users only | RGW daemon | monitors 50 ms; RGW advised |

What this means for the rule (I): stamping at the start (B2, Garage) or bumping forward (GCS, Garage) is safe, because the value is still after the holder sent the request. A client-settable value (Tigris, MinIO) is unsafe unless every writer to the bucket is s4ql and s4ql never sends the header. Distributed MinIO's 15-minute allowance means the margin cannot be justified from MinIO's own rules. Garage can produce `Last-Modified` after `Date`, which blocks a pure S3-clock taker until the clocks catch up.

## 3. Intermediaries

What HTTP says (V, all from https://www.rfc-editor.org/rfc/rfc9110 and https://www.rfc-editor.org/rfc/rfc9111):

- **The origin generates `Date`, as the time of the message.** §6.6.1: "A sender that generates a Date header field SHOULD generate its field value as the best available approximation of the date and time of message generation. In theory, the date ought to represent the moment just before generating the message content. In practice, a sender can generate the date value at any time during message origination." And: "An origin server with a clock (as defined in Section 5.6.7) MUST generate a Date header field in all 2xx (Successful), 3xx (Redirection), and 4xx (Client Error) responses, and MAY generate a Date header field in 1xx (Informational) and 5xx (Server Error) responses."
- **What a clock is.** §5.6.7: "A "clock" is an implementation capable of providing a reasonable approximation of the current instant in UTC. A clock implementation ought to use NTP ([RFC5905]), or some similar protocol, to synchronize with UTC."
- **Intermediaries add `Date` only when it is missing or invalid.** §6.6.1: "A recipient with a clock that receives a response message without a Date header field MUST record the time it was received and append a corresponding Date header field to the message's header section if it is cached or forwarded downstream." And: "A recipient with a clock that receives a response with an invalid Date header field value MAY replace that value with the time that response was received."
- **`Last-Modified` must not be later than `Date`.** §8.8.2.1: "An origin server with a clock (as defined in Section 5.6.7) MUST NOT generate a Last-Modified date that is later than the server's time of message origination (Date, Section 6.6.1). If the last modification time is derived from implementation-specific metadata that evaluates to some time in the future, according to the origin server's clock, then the origin server MUST replace that value with the message origination date." It also says the server "SHOULD obtain the Last-Modified value of the representation as close as possible to the time that it generates the Date field value for its response."
- **HTTP itself warns about comparing the two.** §8.8.2.2 lets a cache treat `Last-Modified` as a strong validator only if `Date` is "at least one second after the Last-Modified value and the client has reason to believe that they were generated by the same clock or that there is enough difference between the Last-Modified and Date values to make clock synchronization issues unlikely".
- **Caches may serve stored responses without asking the origin.** RFC 9111 §4.2.2: "If the response has a Last-Modified header field (Section 8.8.2 of [HTTP]), caches are encouraged to use a heuristic expiration value that is no more than some fraction of the interval since that time. A typical setting of this fraction might be 10%." A cached response keeps its original `Date` and gets an `Age`, "the cache's estimate of the number of seconds since the origin server generated or validated the response" (§4.2.3).

What real proxies do:

- **nginx replaces `Date` by default.** "By default, nginx does not pass the header fields "Date", "Server", "X-Pad", and "X-Accel-..." from the response of a proxied server to a client." (V, https://nginx.org/en/docs/http/ngx_http_proxy_module.html#proxy_hide_header). So behind an nginx reverse proxy, `Date` comes from the proxy's clock and `Last-Modified` from the storage server's. Every Tigris response carried `Server: nginx` (V, test), so I expect this for Tigris (I). The same holds for a self-hosted MinIO or Garage behind nginx unless `proxy_pass_header Date` is set (I).

What this means for the rule (I):

- **A stale cached response is harmless.** It carries an old ETag. If the holder renewed since, the taker's `If-Match` PUT fails with 412, because a PUT is not answered from a cache. If the holder did not renew, the old `Date` makes `D` smaller than the truth, which only delays the takeover. This holds even for a cache that rewrites `Date` to its own time on a hit: `D` is then too large, but the ETag is stale, so the CAS fails.
- **A proxy's clock is a second clock.** A proxy that generates `Date` makes `D` a comparison between the proxy's clock and the store's, and a proxy clock that runs ahead is the unsafe direction. This is the same failure as skew between store nodes (section 6) and needs the same margin.
- **Cheap defences.** Send `Cache-Control: no-cache` on the taker's GET or HEAD, write the manifest with `Cache-Control: no-store`, and ignore a response that carries `Age`. None of these is needed for safety given the CAS, but they keep takeover times honest.

## 4. Prior art

A research agent collected these; I checked the Kubernetes, Hudi and DynamoDB Lock Client quotes against the source myself (V). Some quotes passed through a summarizing fetch tool and are fragments. The short version: **I found no system that compares the store's `Date` with its `Last-Modified`.** The store-as-clock idea would be new. The clock-free "observe and wait" rule is well established. The most common design in between, a holder-written expiry checked against the taker's wall clock, is today's s4ql design.

### No clock at all

- **SlateDB: fencing by epoch.** "The `writer_epoch` is a monotonically increasing `u64` that is transactionally incremented by a writer on startup", used "to prevent split-brain and fence zombie writers"; "Writers will only detect that they've been fenced when they go to write." (V, https://raw.githubusercontent.com/slatedb/slatedb/main/rfcs/0001-manifest.md). Takeover is immediate. There is no read lease. SlateDB does compare its local wall clock with the store's `last_modified`, but only to delay garbage collection of manifests (`utc_now.signed_duration_since(manifest_metadata.metadata.last_modified) > min_age`, default 300 s; V, https://docs.rs/crate/slatedb/latest/source/src/garbage_collector/manifest_gc.rs).
- **Terraform S3 backend (`use_lockfile`): no expiry.** The lock is written with `IfNoneMatch: aws.String("*")`; a held lock returns an error naming the holder, with no age check and no takeover (V, https://raw.githubusercontent.com/hashicorp/terraform/main/internal/backend/remote-state/s3/client.go). A stale lock needs a manual unlock (I).
- **Delta Lake.** `S3SingleDriverLogStore` has no lock: "Concurrent writes to the same Delta table on S3 storage from multiple Spark drivers can lead to data loss." `S3DynamoDBLogStore` "uses DynamoDB to provide the mutual exclusion that S3 is lacking", as a put-if-absent per commit; its `expireTime` only drives DynamoDB TTL cleanup (V, https://docs.delta.io/latest/delta-storage.html).
- **WarpStream** puts coordination in its control plane: "the hard problems of consensus and coordination onto our fully-managed control plane" (V, https://docs.warpstream.com/warpstream/overview/architecture). Nothing on object-store leases.
- **turbopuffer.** Commits are CAS on the object store ("CAS commit point", V, https://turbopuffer.com/docs/architecture). Its queue fails over by starting a new broker, and "The previous broker eventually discovers it's no longer the broker when it gets a CAS failure on `queue.json`." Job heartbeats send "a timestamp", and the post does not say whose clock (V, https://turbopuffer.com/blog/object-storage-queue).

### Observe and wait, on the taker's own clock

- **Kubernetes client-go.** "A client only acts on timestamps captured locally to infer the state of the leader election. The client does not consider timestamps in the leader election record to be accurate because these timestamps may not have been produced by a local clock. The implemention does not depend on their accuracy and only uses their change to indicate that another client has renewed the leader lease. Thus the implementation is tolerant to arbitrary clock skew, but is not tolerant to arbitrary clock skew rate." And on `LeaseDuration`: "A client needs to wait a full LeaseDuration without observing a change to the record before it can attempt to take over." The package also says it "does not guarantee that only one client is acting as a leader (a.k.a. fencing)." (V, https://raw.githubusercontent.com/kubernetes/client-go/master/tools/leaderelection/leaderelection.go, lines 20-28 and 141). How: each time the raw record differs from the last one seen, it stores it and sets `le.observedTime = le.clock.Now()` (line 889); the lease is held while `observedTime + LeaseDurationSeconds` is after now. Only the observer's own clock is read, and only the record's change matters, never its timestamps.
- **Amazon DynamoDB Lock Client.** "The lock client never stores absolute times in DynamoDB -- only the relative "lease duration" time is stored in DynamoDB." A taker "checks the RecordVersionNumber of the lock (which is a GUID) and starts a timer. If the lock still has the same GUID after the lease duration time has passed, the client will determine that the lock is stale and expire it." "What this means is that, even if two different machines disagree about what time it is, they will still avoid clobbering each other's locks." (V, https://raw.githubusercontent.com/awslabs/amazon-dynamodb-lock-client/master/README.md). The source states the two anchors that section 6 derives: the reader should "err on the side of not expiring the lock, so they don't start counting until after the call to DynamoDB succeeds", and the holder should "start counting towards its expiration before the Put succeeds" (V via the agent, https://raw.githubusercontent.com/awslabs/amazon-dynamodb-lock-client/master/src/main/java/com/amazonaws/services/dynamodbv2/AmazonDynamoDBLockClient.java).
- **Followers of that client.** Iceberg's `DynamoDbLockManager` sleeps for the stored lease duration and then writes on `version` (a random UUID) (V via the agent, https://raw.githubusercontent.com/apache/iceberg/main/aws/src/main/java/org/apache/iceberg/aws/dynamodb/DynamoDbLockManager.java). Hudi's DynamoDB lock provider wraps the client. arrow-rs `object_store`'s DynamoDB commit takes over "If `timeout * max_skew_rate` passed", measured with `Instant::now()`, and the stored `ttl` "is purely an optimisation… and does not impact how long clients may wait to acquire a lock" (V via the agent, https://docs.rs/crate/object_store/0.12.5/source/src/aws/dynamo.rs). delta-rs's older `dynamodb_lock` crate uses the same local-observation rule for old-style records (V via the agent, https://docs.rs/crate/dynamodb_lock/latest/source/src/lib.rs).
- **Consul sessions** (used by LiteFS) expire on the server: "Consul will not expire the session before the TTL is reached… it is allowed to delay the expiration past the TTL", because "time may not progress at the same rate on the client as on the Consul servers". A lock-delay (default 15 s) exists "to allow the potentially still live leader to detect the invalidation and stop processing requests" (V via the agent, https://developer.hashicorp.com/consul/docs/automate/session).

### A holder-written expiry, checked against the taker's wall clock

This is s4ql's current design, and the most common one.

- **Litestream** writes `lock.json` with `ExpiresAt: time.Now().Add(l.TTL)` and checks `time.Now().After(l.ExpiresAt)`, default TTL 30 s, using `If-Match`/`If-None-Match` (V via the agent, https://raw.githubusercontent.com/benbjohnson/litestream/main/leaser.go, https://litestream.io/guides/s3-advanced/). No comment on skew.
- **Hudi `StorageBasedLockProvider`** (S3/GCS/Azure conditional writes) checks `return getCurrentEpochMs() > epochMs + CLOCK_DRIFT_BUFFER_MS;` with `CLOCK_DRIFT_BUFFER_MS = 500`, justified by "In reality, within a single cloud provider all nodes share the same ntp" (V, https://raw.githubusercontent.com/apache/hudi/master/hudi-client/hudi-client-common/src/main/java/org/apache/hudi/client/transaction/lock/StorageBasedLockProvider.java, lines 76-80 and 709). Its RFC requires that "all writers competing for the same lock must be writing from the same cloud provider". Its author's write-up lists the failures: "A process can acquire a lock, pause for longer than the lease (stop-the-world)", retried PUTs that return 412 after succeeding, and "The lock provider alone could not make stale writes impossible." (V via the agent, https://alexr17.github.io/notes/the-sharp-edges-of-object-storage-conditional-writes.html)
- **Vault's GCS HA backend** stores `Timestamp: time.Now().UTC()` and refuses takeover while `time.Now().UTC().Sub(r.Timestamp) < l.ttl` (TTL 15 s), with CAS on generation and metageneration. The object's own `Updated` time is not used (V via the agent, https://raw.githubusercontent.com/hashicorp/vault/main/physical/gcs/gcs_ha.go).
- **Small libraries:** sethvargo/go-gcslock ("Because of clock skew and network latency, granularity below 1s is not a supported use case"), podplane/s3lect, hoplock (`ExpiresAt` is "Compared against the local clock, so all participants must have reasonably synchronised time"), and Hongli Lai's GCS lock gem, which writes `expires_at: (Time.now + @ttl)` (V via the agent; URLs in the agent's sources: https://github.com/sethvargo/go-gcslock, https://github.com/podplane/s3lect, https://pkg.go.dev/github.com/xinix00/hoplock, https://github.com/FooBarWidget/distributed-lock-google-cloud-storage-ruby).

### The store's time, partly

- **Gunnar Morling, "Leader Election With S3 Conditional Writes" (2024)** measures lock validity from S3's timestamp: "For each file, S3 provides the last modification timestamp, specifying when it has been created or updated." It appears to compare that with the node's local time, and suggests calibrating: "nodes could create a temporary file on S3 and compare its creation time on S3 with their local time." He concludes that "leader election will only ever be eventually correct" and that "you'll always need to be prepared to detect and fence off work done by a previous leader" (V via the agent, https://www.morling.dev/blog/leader-election-with-s3-conditional-writes/).
- **Hongli Lai, "A robust distributed locking algorithm based on Google Cloud Storage" (2021)** proposes: "We can use the timestamps that Cloud Storage manages, which change every time an object is modified", and to delete the lock "If the update timestamp is older than the TTL". It does not say which clock "now" is read from, and his own gem uses the holder's wall clock instead (V via the agent, https://www.joyfulbikeshedding.com/blog/2021-05-19-robust-distributed-locking-algorithm-based-on-google-cloud-storage.html).
- **Azure Blob leases** are the one store that enforces lease time itself: "The lock duration can be 15 to 60 seconds, or can be infinite", and a write without the lease ID fails with 412 (V via the agent, https://learn.microsoft.com/en-us/rest/api/storageservices/lease-blob). S3 has nothing like it.
- **AWS SDKs** read S3's `Date` as the server's clock, but only to correct the client's signing time (V via the agent, https://docs.aws.amazon.com/AWSJavaSDK/latest/javadoc/com/amazonaws/retry/ClockSkewAdjuster.html).

What the prior art documents as failures: clock skew between machines (Morling, go-gcslock, hoplock, Hudi's buffer), a skew *rate* (Kubernetes, arrow-rs), stop-the-world pauses (Hudi's author, Morling), and retries that turn a success into a 412 (Hudi's author; also our Tigris probe). Nearly every careful source ends at the same point: a lease cannot stop a paused holder, so writes must be fenced. In s4ql the manifest CAS fences writes. Stale *reads* from a paused holder are the remaining risk, and the holder-side rules in section 6 address them.

## 5. Alternatives that need no shared clock

All inference (I), built on the argument in section 6.

- **Observe and wait (Kubernetes, DynamoDB Lock Client).** The taker reads the manifest and notes its own monotonic time `t` when the response arrived. It then sends `If-Match` on that ETag at `t + L + m`. If the CAS succeeds, nothing replaced the version since the read, so the holder's last successful renewal was sent before `t`, and its window closed before `t + L`. The only clock assumptions are that the holder's and the taker's clocks run at about the right rate, which costs microseconds. A taker that is itself suspended while it waits waits longer in true time, which is safe. The holder-side rules of section 6 (anchor at the first attempt, check after reading, count suspended time) apply unchanged.
- **Graceful release.** A holder that shuts down cleanly writes the manifest with the lease released. A taker that reads a released lease takes it at once. This needs no clock and covers deploys and restarts, which are the common case for "one process at a time". Only a crash leaves a taker waiting.
- **Check per read instead of a read lease.** Before a read that must be current, the holder sends a conditional GET or HEAD of the manifest (`If-None-Match` on its ETag; 304 means nothing changed). No clock and no lease are involved, and stale reads become impossible. It costs one round trip per read or per batch of reads: on Tigris, GET p50 was about 27 ms from Denmark (V, `docs/research/tigris-probe-results.md`, Q6). Writes are already fenced by the CAS on the manifest.
- **Hybrid: the store's clock to shorten the wait.** The taker reads `V` at local time `t` and sends its CAS at `t + max(0, L + m − D)`, with `D` clamped to `[0, L + m]`. If the store's clocks agree, a fresh instance takes an abandoned lease at once. If `D` is negative or zero because the `Last-Modified` clock runs ahead, the taker still takes over after `L + m`, so a broken clock in that direction cannot block it forever. The hybrid is exactly as unsafe as the pure S3-clock rule when `D` is too large (a `Date` clock ahead, a client-set `Last-Modified` in the past). It improves liveness, not safety.

Trade-offs:

| | Fresh instance, abandoned lease | Standby that has been watching | Requests to take over | Shared clock needed | What can go wrong |
|---|---|---|---|---|---|
| Today (holder's wall clock in the manifest) | at once | at expiry | 1 read + 1 CAS | all machines' wall clocks | any wrong wall clock: stale reads (the simulation) |
| S3 clock (`Date − Last-Modified`) | at once | at expiry | 1 read + 1 CAS | the store's internal clocks, and server-set `Last-Modified` | store skew above the margin; a client-set `Last-Modified` (Tigris); a store that takes it from `x-amz-date` (AWS untested) |
| Observe and wait | after `L + m` (about 40 s) | at expiry | 1 read, wait, 1 CAS | none | only the holder-side rules, which every design needs |
| Hybrid | at once if the store's clocks are sane, else up to `L + m` | at expiry | 1 read, maybe a wait, 1 CAS | the store's clocks, for safety | same as the S3 clock |
| Check per read | no lease to wait for; writes need only the CAS | n/a | 1 extra request per read | none | latency on every read |

A standby that has been polling the manifest has already seen the version for a long time, so under every scheme it takes over about `L + m` after the holder's last renewal. The schemes differ only for an instance that has just started and finds the lease already abandoned. With graceful release, that is an instance starting after a crash. The price of the clock-free design is then about 40 s of extra unavailability after a crash, against which the S3-clock rule asks us to trust clock sync inside the store, which no store I found documents.

## 6. Failure analysis of the S3-clock rule

All of this section is inference (I) unless a line says otherwise.

### The argument for safety

Name the events in true time:

- `s`: the holder starts the first attempt of the renewal that wrote version `V`. The holder treats the lease as valid while its clock says less than `L` has passed since `s`.
- `w`: the store stamps `Last-Modified` of `V`, on its clock `C_w`. The store cannot handle a request before it is sent, so `w ≥ s`, whether it stamps the start or the end of the upload.
- `r`: the store stamps `Date` on the taker's read that returned `V`, on its clock `C_r`. The read saw `V`, so `r ≥ w`.
- `c`: the taker's `If-Match` PUT against `V` lands. `c > r`.

A wrong answer means the taker's write lands while the holder still believes its window is open: `c < s + L`.

Write `C_w(w) = w + e_w` and `C_r(r) = r + e_r`, and let `δ = e_r − e_w` (how far the `Date` clock is ahead of the `Last-Modified` clock). Both headers are truncated or rounded to whole seconds, which costs less than 1 s if both truncate, and at most 1.5 s if they round differently. The taker requires `D = Date − Last-Modified > L + m`. Then `r − w > L + m − 1.5 − δ`, and `c > r > w + L + m − 1.5 − δ ≥ s + L + (m − 1.5 − δ)`. The rule is safe when `m ≥ 1.5 + δ_max`, plus the holder's own errors below. With integer headers, `D > L + m` with `m = 2` already covers resolution.

The CAS is what makes the read's staleness harmless: if anything replaced `V` after the read, the CAS fails. The analysis never needs `V` to still be current at time `r`.

### Each failure mode

- **One-second resolution of both headers.** Error under 1.5 s, either direction. A margin of 2 s covers it. Measured on Tigris: `D` was 0 or 1 s right after a write, never negative (V, test).
- **The store stamps the start of the request, the holder counts from when it sent it.** `w ≥ s` either way, so the taker sees the lease as younger than the holder does. Safe, at no margin. Stamping the completion (Tigris, V) makes the takeover later by the upload time, which is a liveness cost only. The holder must take `s` before it calls the SDK, not after the response.
- **The store takes `Last-Modified` from the client.** If the value came from `x-amz-date` or a client header, `w` could be before `s`, or anywhere. No margin covers this. Tigris stores a client-sent `Last-Modified` header verbatim; it ignores `x-amz-date` (V, test). AWS is silent on both (section 1). Requirement: s4ql's client never sends `Last-Modified`, never copies a manifest with `CopyObject`, and the store must be checked for this.
- **Slow responses.** `Date` is stamped when the response is produced (§6.6.1, and V on Tigris: a HEAD that took 2.6 s carried a `Date` 2 s after its request id). The taker acts after `r`. Both delays push `c` later relative to `D`, which is the safe direction. A read that is slow between taking its snapshot and stamping `Date` makes `D` too large for the true current version, but if a renewal landed in between, the ETag is stale and the CAS fails. No margin needed.
- **Skew between the store's clocks, or between a proxy and the store.** `δ > 0` (the `Date` clock ahead) is the unsafe direction, and it subtracts from the margin one for one. `δ < 0` delays takeover. If the store follows RFC 9110, a `Last-Modified` ahead of `Date` is clamped to `D = 0`, so a large negative `δ` shows up as a taker that never sees the lease expire; it needs a fallback (section 5). The only store that documents a bound is MinIO, and its bound is 15 minutes (section 2). Garage's forward bump can also put `Last-Modified` after `Date` (section 2). With NTP inside one operator's fleet, skew of milliseconds is typical (I, not measured in this run except that Tigris agreed with this Mac's NTP clock within about 0.1 s). A margin of 10 s covers anything short of a broken clock. It cannot cover a node whose clock is wrong by minutes.
- **Multi-region stores.** On a globally replicated store, `Last-Modified` may be stamped in the region that took the write and `Date` in the region that served the read. `δ` is then the skew between regions. Not tested: every response in the test came from `fra`.
- **The holder's monotonic clock runs slow.** A rate error `ρ` costs `ρ × L`. At 100 ppm, 3 ms over 30 s. Covered by any margin.
- **The holder is suspended or paused.** Two cases.
  - The holder checks its window, pauses (GC, `SIGSTOP`, VM pause), and then serves a read. No margin covers an unbounded pause. The fix is to check after reading: take the cached state, then check the window. If the window is still open at the check, no other writer can have committed before it, so the read was current at a moment inside the request. A pause after the check only delays the reply.
  - The pause is not counted by the clock. Go's runtime reads `CLOCK_MONOTONIC` on Linux (V, `src/runtime/sys_linux_amd64.s:270`, `MOVL $1, DI // CLOCK_MONOTONIC`, Go 1.27.3), and that clock "does not count time that the system is suspended", unlike `CLOCK_BOOTTIME`, which "also includes any time that the system is suspended" (V, https://man7.org/linux/man-pages/man2/clock_gettime.2.html). The Go documentation warns: "On some systems the monotonic clock will stop if the computer goes to sleep." (V, `go doc time`). On macOS the runtime uses `mach_absolute_time` (V, `src/runtime/sys_darwin_arm64.s:147`). A holder suspended for a minute wakes up believing seconds have passed. No margin covers it. Defence: measure elapsed time with `CLOCK_BOOTTIME` on Linux, or take the larger of the monotonic and the wall-clock elapsed time, which catches a suspend unless the wall clock is also stepped back. Whether a hypervisor pause of a whole VM is counted by the guest's `CLOCK_MONOTONIC` depends on the hypervisor (silent; not researched here). This failure is the same for every lease design, including the Kubernetes one and today's.
- **A retry of a renewal whose first attempt landed.** The first attempt writes `V` at `w1`. The response is lost. The SDK or s4ql retries at `s2`; on Tigris the retry gets 412 because the ETag moved (V, earlier probe: `docs/research/tigris-probe-results.md`, finding 4). If the holder anchors its window at `s2`, it believes it holds the lease until `s2 + L`, while the store's clock dates the lease from `w1`. The error is `s2 − s1`, which is as long as the retries take, so no fixed margin covers it. Rule: anchor at `s1`, the start of the first attempt, whatever the outcome of the retries.
- **A renewal that the holder gave up on lands later.** The store's lease is then newer than the holder thinks. The holder stops serving early, and a taker waits longer. Safe; liveness cost up to `L`.
- **A taker's own CAS is retried.** A retry after a lost success gets 412, as for the holder. The taker must read the manifest to see whether its token is there. This is the same as for any CAS in s4ql, and not specific to the clock.
- **A clock step on the store.** A `Date` clock stepped forward, or a `Last-Modified` clock stepped back, is a temporary `δ > 0`. Same as skew.
- **Someone else writes the manifest.** Any writer with credentials can write a manifest whose `Last-Modified` is server-stamped and fresh, which only delays takers. On Tigris such a writer can also set `Last-Modified` to the distant past, which makes every taker take over at once (V for the behaviour, test). Bucket permissions are the only defence.

### How large the margin must be

- Resolution: 2 s with integer headers.
- Holder clock rate: negligible.
- Store or proxy skew: whatever bound one is willing to assume. Nobody documents one.
- Client-set `Last-Modified`, holder suspension, anchoring at a retry: not coverable by any margin. They need the rules above.

So `m` = 10 s with `L` = 30 s (take over when `D > 40`) covers resolution and up to about 8 s of store skew. The holder renews every 20 s, so a live holder's `D` stays near 20 s, and this margin leaves 20 s of slack for slow renewals.
