# Disk failures from Antithesis's "Nightmare mode", against s4ql's simulation

Date: 2026-11-26. Tags: **[V]** = read in a primary source in this run (the post, a paper, a page on sqlite.org, the vendored amalgamation `internal/sqlite/c/sqlite3.c` 3.54.1, or s4ql's code), or measured on this machine. **[I]** = inferred, not shown. s4ql was read at `main`, commit `474d81fb`.

Question (Markus, 2026-11-24): which error modes of disks does [Nightmare mode: simulating disk failures](https://antithesis.com/blog/2026/nightmare-mode/) (Anjana Ratnayake and Teymour Aldridge, Antithesis, 2026-11-24) describe, and which should s4ql's simulator add as disk failures?

## Summary

- **The post describes seven failure modes:** power loss (unsynced writes lost), torn writes and torn sequences of writes, a full disk and no free inodes, I/O errors on syscalls, EIO on fsync with the page cache's side effects (fsyncgate), and two latency faults: out-of-order completion of syscalls and partly applied operations that a read can see. Memory pressure (eviction of cached pages) appears as the trigger of its one public bug, in bbolt, which needed an fsync error followed by a power loss or an eviction **[V]**.
- **s4ql's simulation injects none of them on the local disk today.** The only failure of the cache that `TestSimulation` reaches is the buggify point in `Tx.commitCache` (`internal/core/tx.go`): the commit after the manifest swap fails, rolled back or committed. Its crash copies the cache's files as the kernel holds them, which is a process kill (SIGKILL), not a power loss, and its workloads run with `pragma synchronous = off` (`Options.SyncOff` in `workloads_test.go`), so no sync is ever issued **[V]**. The scenario tests inject I/O errors (open, read, write, truncate, sync, size, lock, any result code such as `SQLITE_FULL`) through `internal/sqlite/faultvfs`, one fault at a time, and errors of the spool files through `Options.WrapSpools` **[V]**.
- **One gap was found while reading, and measured:** with `synchronous = normal`, which s4ql uses, SQLite syncs only at a checkpoint, and an automatic checkpoint's error is dropped: `sqlite3WalDefaultHook` calls `sqlite3_wal_checkpoint` and returns `SQLITE_OK` **[V]**. Through `faultvfs` with every sync failing, 200 commits all succeeded while 199 syncs failed; with `synchronous = full`, all 200 failed **[V]**. So the spec's rule "if reading or writing the local cache fails, the instance stops" does not hold for a failed sync of the cache: the instance never learns of it. Whether that is harmful depends on what a failed sync leaves behind, which is mode 5 below.
- **The design makes most of the post's modes harmless on paper,** because the cache is never ahead of S3 and records its position in the same SQLite transaction as its rows: any loss that leaves the cache at an earlier commit of the log is caught up. That holds only for losses that leave a prefix of the log or a cache that SQLite refuses. A silently wrong page under a newer position (a page that reverted after a failed writeback was evicted) is neither, and nothing in s4ql checks the cache against the log while it serves. No test shows the claim under a power loss: mutation testing left "the sync of the cache, which only a power loss shows" uncaught ([internal/core/README.md](../../internal/core/README.md), "Mutation testing").
- **Ranked proposals,** by how likely each is to find a real fault in s4ql:
  1. **A failed sync with fsyncgate semantics, then an eviction or a power loss.** Most likely to find something, because the gap above is already real.
  2. **Random I/O errors and a full disk in `TestSimulation`,** through `faultvfs`, which exists; today only scenario tests use it.
  3. **Power loss: unsynced writes lost, at a point tied to a disk operation,** with syncs on, through a VFS that keeps the durable and the volatile state apart.
  4. **Torn writes inside one write,** within the bounds of SQLite's powersafe-overwrite assumption. Mostly retests SQLite.
  5. **A slow disk, as time,** with a sleep of the host around calls into the cache. A different question from the post's latency faults.
- **Do not apply:** out-of-order completion and partly applied operations under concurrent access (the scheduler never has two goroutines in SQLite, and SQLite's locks keep readers off pages that a writer changes), power loss of the spool files (unlinked on open, so nothing survives a crash anyway), and memory pressure on its own (an eviction of a page that reached the disk reads back the same bytes).

## The post, mode by mode

Quotes are from the post **[V]**. "Caught" is what the post says the mode found.

| 1 | Power loss: written but not synced data is lost | "A power failure is less polite. It loses everything the kernel accepted but hadn't synced yet." Emulated with LazyFS, then their own FUSE file system Amnesia, which drops its cache when it kills the container. Fired "before any of the operation has been applied to the internal cache, after part of it has been applied, and after all of it has been applied (but before the syscall returns)" ("correlated faults"). | LazyFS "found some subtle data loss bugs" on customer tenants, not named. |
| 2 | Torn writes and torn sequences of writes | "torn writes and torn sequences of writes, both caused by the fact that the kernel and the disk do not persist data in the order or the units a program might expect" | Nothing named. |

| 4 | I/O errors returned by syscalls | "The obvious approach is to simply return the error, and that model alone was enough to find some bugs." | "some bugs", not named. |

The bbolt bug, from the issue **[V]**: etcd 3.7.3 on bbolt 1.5.0. The data pages of a transaction were synced, the `fdatasync` after the meta page returned EIO, and etcd exited. On restart bbolt read the meta page through the page cache, where the unpersisted page still was with a valid checksum, and treated the transaction as committed; its rebuilt free list let later commits overwrite pages that the durable meta still referenced. After the cached page was evicted, "every later start panics the same way (376 restarts before we stopped it)". The post: "This bug could only be found by an I/O error followed by a power failure." A maintainer's reply proposes what PostgreSQL did: refuse further writes after an fsync error.

## Background that states the modes exactly

- **Lost and torn writes.** The LazyFS paper, Ramos et al., "When Amnesia Strikes: Understanding and Reproducing Data Loss Bugs with Fault Injection", PVLDB 17(11), 2024 ([pdf](https://www.vldb.org/pvldb/vol17/p3017-ramos.pdf)), defines three faults **[V]**: a *lost write*, where all unsynced data is lost; a *linear torn write*, where a prefix of a group of writes, or of the pages of one large write, is persisted and the rest lost; and a *non-linear torn write*, where a later part is persisted and an earlier one lost, which breaks ordering. It reproduced 12 known bugs and found 8 new ones in PostgreSQL, etcd, ZooKeeper, Redis, LevelDB, PebblesDB, and Lightning Network; nine of the twelve known bugs were in log or metadata files.
- **What a failed fsync leaves.** Rebello et al., "Can Applications Recover from fsync Failures?", USENIX ATC 2020 ([page](https://www.usenix.org/conference/atc20/presentation/rebello)) **[V]**: on ext4, XFS, and Btrfs, a data block whose write fails makes fsync fail and the page is marked clean; ext4 and XFS keep the new content in memory, so "applications that read this data block while the page remains in the page cache ... will see the new contents of the data; however, when the page is no longer in memory and must be read from disk, applications will see the old contents"; Btrfs reverts the page. ext4 in data=journal mode reports the failure only at the next fsync. For SQLite in WAL mode it found false failures (a commit reported failed that a restart reads back from the page cache) on ext4 ordered and XFS, and value corruption and lost keys from faults in the database file during a checkpoint on ext4 data=journal.
- **fsyncgate.** The thread on pgsql-hackers from 2018-03-28, archived at [danluu.com/fsyncgate](https://danluu.com/fsyncgate/) **[V]**: Craig Ringer, "When fsync() returns success it means 'all writes since the last fsync have hit disk' but we assume it means 'all writes since the last SUCCESSFUL fsync have hit disk'"; the error is reported once, and only to descriptors open at the time of the error (kernel 4.13 and later). PostgreSQL's answer was to PANIC and redo from its log.
- **What SQLite assumes and tests.** With powersafe overwrite, on by default in the unix VFS since 3.7.10, SQLite assumes that a write changes no bytes outside its range in a power loss, and it never assumes that writing a page is atomic ([psow.html](https://sqlite.org/psow.html)) **[V]**. `SQLITE_POWERSAFE_OVERWRITE` is 1 in the vendored build (`sqlite3.c`, line 15279) **[V]**. SQLite's crash tests use a VFS that "randomly reorders and corrupts the unsynchronized write operations", and its I/O error tests fail the nth operation in a loop and check `integrity_check` afterwards ([testing.html](https://sqlite.org/testing.html), sections 3.2 and 3.3) **[V]**.
- **SQLite's checkpoint and a failed sync.** In `walCheckpoint` **[V]**: the log is synced before any page is copied, and a failed sync stops the checkpoint before the database file is written; the database file is synced after the copy, and `nBackfill` advances only if that sync succeeded, so a failed checkpoint copies the same frames again next time. A later sync that succeeds while frames of the log never reached the disk (fsyncgate) still leaves them in the database file, because the checkpoint reads the frames through the page cache and syncs the database file **[I]**: a reading of the source, not run.

## What s4ql holds on its local disk

- **The cache:** one SQLite database in WAL mode, with `synchronous = normal`, its write-ahead log, and the shared-memory index (`conn.setUp`, `conn.wal` in `internal/core/cache.go`) **[V]**. Its table `s4ql_cache` records the position, the name of the last applied commit object, in the same transaction as the rows. The cache is never ahead of S3: the manifest swap comes first and the commit to the cache second ([spec](../spec.md), "Constraints") **[V]**.
- **The spool files:** the commit object and the annotations of a transaction, next to the cache, unlinked as soon as they are open (`DB.newSpool` in `internal/core/spool.go`) **[V]**. The upload sends the commit object's SHA-256, and the store refuses content that does not match it; the core uploads once more after one refusal and stops at the second (`Tx.upload` in `tx.go`, tested by "should upload again when the store says once that the content does not have its checksum, and stop when it says so twice" in `tx_test.go`) **[V]**. Bytes that a spool reads back wrong therefore stop the instance and never reach the log.
- **The design's claims about the disk:** a power loss leaves the cache behind, never corrupt (doc comment of `conn.setUp`, which cites [pragma.html](https://sqlite.org/pragma.html#pragma_synchronous)); any local I/O failure stops the instance, nothing is tried again in place, and recovery is a normal start that catches up from the recorded position ([spec](../spec.md); [internal/core/README.md](../../internal/core/README.md), "Stopping") **[V]**.
- **What shows the claims today:** the crash of the workload with everything restarts on a copy of the cache and its log, and requires that the cache holds exactly what it held at the crash and what the log says at its position; 761 of 1000 restarts on 2026-11-13 recovered commits that only the log held. Every run ends with a replay of the whole log into an empty cache. `cacheDump` runs `integrity_check`. Scenario tests fail opens, reads, writes, syncs, and locks through `faultvfs` and check the stop and the next open **[V]**. None loses a write that the kernel accepted, and none has a sync on in the simulation.

The store's side, for completeness. The post is about local disks, and S3's own durability is outside it. `simstore.Faults` (`internal/store/simstore/simstore.go`) already injects the analogues at the level of requests **[V]**: a lost request or response (`LostRequest`, `LostResponse`, `Hang`), a download that breaks off (`BrokenRead`), damaged downloads of commit objects (in the workload with everything), slowness (`Slow`), a write held in the network and applied out of order up to 15 minutes later (`Late`, `AfterCrash`, `Long`), conflicts, cut-offs, and outages. A damaged manifest is not injected, and the core's README says it has no guard for one. Nothing in the post adds to this side.

## Proposals, ranked

### 1. A failed sync with fsyncgate semantics, then an eviction or a power loss

- **Why first.** It is the one mode where s4ql's behaviour already differs from its rule: the error never reaches the core. What follows depends on what the page cache does, which no test of s4ql models.
- **Seam.** A VFS under SQLite that keeps two states of each file: what reads see (the volatile state) and what is durable. A write changes the volatile state and records the range as dirty. A sync that succeeds makes the dirty ranges durable. A sync that the fault fails returns `SQLITE_IOERR_FSYNC` and clears the dirty ranges without making them durable, as ext4 and XFS do **[V]**. An eviction event, which the harness fires, replaces the volatile state of those ranges with the durable one; a power loss (rank 3) replaces all of it. It is the model of Amnesia, and of CuttleFS in Rebello et al. It can grow from `internal/sqlite/faultvfs`, which already wraps every file operation in C, or be an in-memory VFS of its own; the shared-memory methods stay passed through, since the index is rebuilt after a crash. The choices (which sync fails, when an eviction fires) come from the harness in Go through the seed, as `faultvfs.Fail` is armed today, so runs stay deterministic. The workloads that use it need syncs on, so they cannot use `SyncOff`; with an in-memory durable state a sync is bookkeeping.
- **Property.** Every read that an instance serves is the model's state at some commit that the read may see (the check that exists), and after a restart the cache is a prefix of the log or refused by SQLite with a local failure, never a cache whose rows differ from the log at its own position. An instance that cannot vouch for its cache stops.
- **Expected result.** Without a change to the core, an eviction after a failed checkpoint should let SQLite read reverted log frames, and the read model or `integrity_check` should report it **[I]**. If it does, it is a design question for Markus, not a detail: one answer is to switch off automatic checkpoints and run them from the core, so that their errors go through `classify` and stop the instance, as the rule says; another is a page checksum, such as SQLite's [checksum VFS](https://sqlite.org/cksumvfs.html), which reports `SQLITE_IOERR_DATA` for a page whose checksum fails **[V]**, though a page that reverted to an older valid version keeps a valid checksum, so it catches torn and garbage pages only **[I]**.
- **Planted bug.** With checkpoints run by the core: `ignoreCheckpointError`, a checkpoint whose error is dropped, which is exactly what SQLite's automatic checkpoint does today. The check judges if it finds that bug and nothing in its control (the same workload with no failed sync) or in the clean runs.

### 2. Random I/O errors and a full disk in `TestSimulation`

- **Why.** The rule "any local I/O failure stops the instance" is shown one path at a time by scenario tests. The simulation would show it on every path at once, under the lease, catch-up, readers that open and close, and restarts, which is where the earlier faults of the core were found. The seam exists and costs little.
- **Seam.** Open the caches of a workload through a `faultvfs.VFS` (`Options.VFS`, as the scenario tests do) and let a task of the harness arm faults at random times: read, write, truncate, sync, size, lock, and open, on the database file, the log, and temporary files, with the usual codes and with `SQLITE_FULL`; and spool faults through `Options.WrapSpools`. `faultvfs` holds one fault per VFS, which is enough with one VFS per instance.
- **Property.** The checks that exist: every read matches the model, the caches match the log, the final replay matches. And `run.stopped` already requires every stop to be explained; it would accept a local failure while a fault was armed on that instance, and nothing else.
- **Planted bug.** `localAsBroken`: replay reports a local failure while it applies a change as `ErrLogBroken`. It is the mutant `replay-cache-error-as-broken`, which a scenario test catches today; in the simulation, `run.stopped` should find it as an unexplained stop. A second candidate: a scan that ends quietly when SQLite's step fails, which the read model should find as missing rows.

### 3. Power loss, tied to a disk operation

- **Why.** The design's central claim about the disk, "behind, never corrupt", has no test, and the mutation of the cache's sync survives. It is less likely than 1 or 2 to find a fault in s4ql's own code, because SQLite does the work and its crash tests are thorough, but it is the test of the claim and of what catch-up does with a cache that went back.
- **Seam.** The VFS of rank 1. At a power loss the harness kills the instance (`sim.Instance.Crash`) and drops every write that is not durable, and the restarted instance opens the durable state, in place of `copyCache`. As in the post, the harness ties the moment to a disk operation: before it, after part of it, or after all of it and before it returns. Since a call into SQLite is one step of the scheduler, the VFS records the operation and the harness decides, from the seed, which of the three states to keep.
- **Property.** The check after a restart changes from "at the position of the crash" to "at a commit of the log at or before the position of the crash, with exactly the model's rows there, and `integrity_check` clean", and the instance then catches up and serves. The count of restarts that came back behind is logged and given a minimum, as the recoveries are today.
- **Planted bug.** `syncOff`: the cache's `synchronous = off`, the surviving mutant. With no sync before a checkpoint copies frames and none before the log is reset, a power loss can keep a newer position with older pages **[I]**, which the check should find.

### 4. Torn writes inside one write

- **Seam and property.** A variant of rank 3: at a power loss, a write that is not durable survives in part, by sectors of 512 bytes, as a prefix or as any subset (LazyFS's linear and non-linear torn writes). The property is that of rank 3.
- **Why low.** Within powersafe overwrite this retests SQLite's own crash tests. A tear that crosses the bounds of a write breaks SQLite's assumption, and nothing in s4ql could recover from that, so a finding would be about SQLite's settings (turning powersafe overwrite off), not about the core.
- **Planted bug.** None in the core. The check could be judged by a VFS that claims atomic writes of a page (`SQLITE_IOCAP_ATOMIC`) while it tears them.

### 5. A slow disk, as time

- **Why.** Not the post's latency faults, which are about concurrency. A local call that takes seconds, such as a sync or a large commit to the cache, moves the lease's clocks, and the simulation never has one: fake time does not move during a call into SQLite (`internal/sim/README.md`).
- **Seam.** A buggify point of the host that sleeps around the calls into the cache in Go: around `Tx.commitCache`, the open of a reader, and the steps of replay.
- **Property.** The checks of the lease and of reads that exist.
- **Planted bug.** None found yet. One is needed before it is built.

## What could not be determined

- **Which bugs LazyFS and Amnesia found besides bbolt's.** The post says "some subtle data loss bugs" and "some bugs", and names none.
- **Whether the post's modes include silent corruption of data at rest.** It does not mention bit rot or misdirected writes; this note does not cover them.
- **Whether an eviction after a failed checkpoint makes s4ql serve a wrong row.** The reasoning in rank 1 is from SQLite's source and Rebello et al.'s results for SQLite in WAL mode, which ran each application "in the form that offers most durability", not with s4ql's `synchronous = normal`. It was not run, because no VFS of s4ql models the page cache yet.
- **What SQLite does with a failed checkpoint when the last connection closes.** Only the automatic checkpoint after a commit was measured.
- **How often a real disk fails a sync.** No source in this run gives a rate; the ranking is by what a fault would cost s4ql and by how directly the gap is shown, not by frequency.
