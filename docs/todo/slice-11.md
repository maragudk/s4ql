# Slice 11: `default` with a literal

The decisions and notes of the builders of [slice 11 of the roadmap](../roadmap.md#slice-11-default-with-a-literal).

## The statement pass

- **Decisions of the statement pass of slice 11, `default` with a literal, by its builder on 2026-11-20, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell or the binding, and the tests of the pass check it against SQLite: `checkCreateTable` and `checkDefaults` on every supported text, and the subtest "should answer for DEFAULT what SQLite does when an insert, an update, or a select meets it" of `TestCheck`. The README of the pass has the forms token for token.
  - The field is `Column.Default`, of the new type `stmt.Default`, with `Value stmt.Value` and `Span stmt.Span`, as a `Term` has them without its `Parameter`. `Value` is nil when the column says no DEFAULT, and `stmt.Null{}` for DEFAULT NULL, so the two cannot be taken for each other. `Span` is that of the literal with its sign, which is exactly the text that SQLite keeps as `dflt_value`. The offset of the keyword DEFAULT is not kept; `defaultRefusal` of the engine finds it as the last token before the span.
  - The literal is one that `insert` takes, read by the same code (`recognizer.sign` and `recognizer.value`, split out of `recognizer.literal`): a decimal integer of 64 bits or a real, with at most one `-` and any spaces and comments after it, a string, a blob, or NULL. SQLite's grammar reads a sign and the literal as two tokens there (`DEFAULT MINUS scantok term`), and the pass gives the value that SQLite gives the text: `default - /* c */ 1` is `-1`, `-0.0` is negative zero, `00012` is 12, `1e-400` is 0.0.
  - Every form that `insert` refuses as a value is refused after DEFAULT with the same name and at the same token: `+ sign` (`default +1`), `NULL after a sign` (`+null`, `-null`), `hex literal` (`0x10`, `-0x10`), `number with a digit separator` (`1_000`), `integer outside 64 bits`, `infinite real number` (`1e999`), `string after a sign` (`-'a'`, which SQLite stores as the text `'0'` in a TEXT column), `blob after a sign`, `TRUE or FALSE` (`default true`, which SQLite stores as 1), and `current date or time` (`current_timestamp`, `current_date`, `current_time`, also `-current_time`, which SQLite stores as `'-21'`).
  - New names of "not supported": `name after DEFAULT`, for a bare word, a keyword that is a name, or a name in double quotes, brackets, or backticks after DEFAULT, which SQLite reads as a string (`default "abc"` and `default abc` store `'abc'`; the build has double-quoted strings off, but `options.h` says that this one place reads any name as a string); `DEFAULT of an expression`, for `default (1)`, `default (1+1)`, `default (null)`, and `default (?)`, at the parenthesis, where SQLite strips the outer parentheses from `dflt_value` and refuses `(?)` with `default value of column [v] is not constant`; `second DEFAULT`, at the second DEFAULT of a column, where SQLite keeps the last (`default 1 default 2` has the `dflt_value` `2`); and `DEFAULT of another type than its column`, at the literal with its sign.
  - A literal of another type than its column is not supported, by the rule of exact types: SQLite takes the declaration in a STRICT table whatever the pair of types, and decides at the insert that stores it, so s4ql could never store such a default. Measured for every pair: an INT or INTEGER column converts `1.0`, `-0.0`, and `'1'` to the integer and refuses `1.5`, `1e300`, `'1.5'`, `'a'`, `''`, and every blob (`cannot store REAL value in INT column t.v`); a REAL column converts `1`, `-1`, `'1'`, and `'1.5'` and refuses other text and every blob; a TEXT column converts every number to its text (`1.0` gives `'1.0'`, `-0.0` gives `'0.0'`) and refuses every blob; a BLOB column refuses every value but a blob. Nothing in the measurement speaks against the refusal at create.
  - DEFAULT NULL is supported on every column, also one that is NOT NULL and the primary key, as SQLite takes it at create: `v int not null default null`, `default null not null`, `k int primary key default null`, and `default null primary key`. An insert that leaves such a column out gives `NOT NULL constraint failed`, as for the column without the DEFAULT.
  - A DEFAULT on the primary key is supported, before, between, or after PRIMARY KEY and NOT NULL. An insert that leaves the key out stores the default as the key, and a second one gives `UNIQUE constraint failed: t.k`.
  - DEFAULT may come anywhere among the constraints of the column, at most once: SQLite records the same table for every order, which `checkCreateTable` checks against the canonical text, where DEFAULT comes last.
  - `CreateTable.SQL` does not change: SQLite keeps the text from the name on with the DEFAULT as written, and `checkCreateTable` compares `SQL` with `sqlite_schema` on every supported text, defaults among them.
  - `insert ... default values` stays not supported as `DEFAULT VALUES`, at the DEFAULT, with or without a list of columns, as before.
  - `stmttest.Generator.Defaults`, 0 by default: one column in Defaults of a create table says DEFAULT, of the type of its column, or NULL one time in `Generator.Nulls`, and one time in eight without Nulls, anywhere among the constraints; a column that `Generator.Create` gives says the DEFAULT of its `Default.Value` whatever Defaults is. With Defaults 0 and no such column, the generator's output is byte for byte what it was. The pass's own tests set Defaults to 3; the engine's and the driver's leave it at 0.
- **Facts of SQLite for the builders of the engine and the core of slice 11, measured by the builder of its statement pass on 2026-11-20.** Pinned by the subtest "should answer for DEFAULT what SQLite does when an insert, an update, or a select meets it" of `TestCheck` and by `checkDefaults`, unless it says otherwise.
  - An insert with a list of columns that leaves out a column with a DEFAULT stores the value of the DEFAULT, for each kind: an integer, a real, a text, a blob, and NULL. A real 0 comes back as 0.0, also for `default -0.0`, as for an insert of `-0.0`: SQLite stores a whole real of a REAL column as an integer. An explicit NULL in the list is not replaced by the default: `insert into t (k, a, c) values (1, null, 2.5)` gives `NOT NULL constraint failed: t.a` where `a` is `not null default 0`, and a NULL for a column with `default 'x'` stores NULL.
  - DEFAULT NULL on a NOT NULL column or on the key changes nothing: leaving the column out gives `NOT NULL constraint failed: t.c` with the first such column in the order of the table, also when a later column is left out too (`(k, a int not null default null, b int not null)` gives `t.a`; measured with the shell only), and for the key `NOT NULL constraint failed: y.k`, also with `insert into y default values`.
  - The order among the errors of an insert, measured (the place of the text, the arguments, and `no such table` with the shell only, the rest pinned): the errors of the text and the arguments, `no such table`, `table t has no column named x`, and the number of values come before the defaults and are the same with them; `attempt to write a readonly database` comes before every error of a row (NOT NULL, the type, UNIQUE, too big); NOT NULL, also of a left-out column with DEFAULT NULL, comes before `string or blob too big` of the record; the type of a given value, `cannot store TEXT value in REAL column t.c`, comes as before. A left-out key with a DEFAULT gives `UNIQUE constraint failed: u.k` when a row has that key. The record of a row holds the defaults of the left-out columns, so it can be too big because of them: at the length limit of 1,000, a default of 500 bytes and a given value of 600 give `string or blob too big`. A default by itself is never too big for a value, since the text of the create table that holds it is under the same limit, which SQLite and the engine check for the text of the table.
  - An insert without a list of columns gives every column a value, so the defaults change nothing: `table t has 5 columns but 1 values were supplied` stays. An update does not meet the defaults: `set b = null` stores NULL, and `set a = null` of `a int not null default 0` gives `NOT NULL constraint failed: t.a`. A select does not meet them.
  - What `pragma table_info` gives as `dflt_value`, and `sqlite_schema` keeps in the text of the table: the text of the literal as written, from its sign to its last token, with the spaces and comments between them, and NULL for a column without DEFAULT. Measured: `-1` gives `-1`, `+1` `+1`, `- 1` `- 1`, `- /* c */ 1` `- /* c */ 1`, `1.0` `1.0`, `.5` `.5`, `1E+3` `1E+3`, `-0.0` `-0.0`, `00012` `00012`, `'it''s'` `'it''s'` (the quotes included), `''` `''`, `x'00'` `x'00'`, `X'aBcD'` `X'aBcD'`, `true` `true`, `TRUE` `TRUE`, `null` `null`, `NULL` `NULL`, `Null` `Null`, `"abc"` `"abc"`, `abc` `abc`. A comment between DEFAULT and the literal is not part of it. `notnull` is 1 for `not null default null` and for the key. How the cache of the core records the default and tells a column that takes NULL is in the decisions of the core step of slice 11, under "The storage core".

## The core

- **Decisions of the core step of slice 11, `default` with a literal, by its builder on 2026-11-21, built, for the lead to confirm.** The agreement with Markus of 2026-11-20: a column may carry `default <literal>`, an integer, a real, a text, a blob, or NULL; the commit format changes so that a column carries its default; the layout of the cache rises by one, with no upgrade. What it left open was decided by SQLite's behaviour and the agreed rules. The reasons are in [internal/format/README.md](../../internal/format/README.md) and [internal/core/README.md](../../internal/core/README.md).
  - The commit format. `Column` has a fourth field, `Value default = 4`, the message that rows hold. A message field has presence, so a column without a default lacks the field and one with DEFAULT NULL holds a NULL. The version of the format stays 0: a reader from before refuses the field as one of a newer version.
  - What the reader and the writer refuse as malformed: a default of another storage class than its column's type, NULL apart (an integer for INT and INTEGER, a real for REAL, text for TEXT, a blob for BLOB), which the rule of exact types could never store and the statement pass refuses; and, as in a row, a real that is NaN, infinite, or -0.0, and text that holds NUL. Text that is not valid UTF-8 is refused everywhere already. A default with a field or a kind that they do not know is from a newer version.
  - DEFAULT NULL is allowed on every column, also one that does not take NULL and a primary-key column, because SQLite takes both and the statement pass supports them. Such a default stores nothing: an insert that leaves the column out gives `NOT NULL constraint failed` in SQLite, and the core refuses a row with NULL there with `ErrInvalid`.
  - -0.0. The format refuses it in a default, as in a row, because a default is a value that a column stores and SQLite stores 0.0 for it: after `default -0.0`, an insert that leaves the column out stores 0.0. `Tx.CreateTable` takes a default of -0.0 and keeps 0.0, in the cache, in `Table` and `Tables`, and in the commit object, as `Tx.Upsert` takes -0.0 in a row; the table that the caller hands in is left as it is. So the engine need not turn the sign of `stmt.Default.Value` around itself.
  - The length. The format has no limit on a default, as it has none on a value in a row. The core refuses with `ErrInvalid`, before anything changes, a table whose statement in the cache is longer than the length limit, as before, and that statement holds the default in its canonical form. A default is therefore never longer than the limit as a value. The canonical form can be longer than the user's spelling, by up to a few bytes for a real (`.5` is `5e-01`, `1.5` is `1.5e+00`), and shorter for an integer (`00012` is `12`), as the cache's statement already differed from the user's by its quoted names, so a create table within a few bytes of the limit that SQLite takes can get `ErrInvalid` from the core.
  - How the cache records a column. Nullability comes from the flag `notnull` of `pragma_table_info`: every column outside the key that does not take NULL is declared `not null`, and one that takes NULL is not. The default is declared in SQLite, `default <literal>`, in one canonical form that the cache writes (`defaultSQL`) and reads back strictly (`parseDefault`), and a column without one declares none. The two are then independent, so `not null default null`, a column that takes NULL with DEFAULT NULL, and one that takes NULL without a default all read back as they were made. The core always writes whole rows, naming every column, so SQLite never applies the default itself; it is declared in SQLite anyway, and not in a table of the core's own, because SQLite's schema is the one catalogue of the cache: a drop table removes it with the table, no second table can disagree with the schema, a person with the `sqlite3` shell sees it, and SQLite would store the same value if a row ever came without the column. The cost is the canonical form and its strict parse.
  - The canonical form: an integer in decimal, with a minus only when negative; a real as the shortest decimal that reads back to its bits, in exponent form, as Go's `strconv.FormatFloat(r, 'e', -1, 64)` writes it (`1e+00`, `-1.5e-300`, `5e-324`), so that SQLite reads it as a real and never as an integer; text in single quotes with each single quote doubled; a blob as `x'...'` in lowercase hexadecimal; and `null`. SQLite reads each back as the same value: measured with the binding on 2026-11-21, `select <literal>` gave the same bits for 240,010 reals (random bits, subnormals, and the edges), and `-9223372036854775808` after DEFAULT is the integer, since SQLite reads the minus after DEFAULT as part of the literal; `cacheDump` reads every default of the tests through SQLite that way.
  - What `conn.load` refuses with `ErrCacheVersion`: a default whose text is not the canonical form of a valid default of the column's type, which covers every other spelling (`+1`, `00012`, `1.0` for INT, `1.5` for REAL, `X'AB'`, `NULL`, `"abc"`, `abc`), a value of another type, an expression, `current_time`, a real that is NaN, infinite, or -0.0, and text with NUL or not valid UTF-8; and a primary-key column that SQLite reports as taking NULL, which is the key of a table with a rowid. `not null default null` and a default on the key, which version 3 refused, are now read. The parse sees only the text that `pragma_table_info` reports, which is the expression inside a pair of parentheses, so `default (1)` reached it as `1` and was read as the literal. Since 2026-11-21 `conn.load` also compares the table's whole statement with the one that the core writes, which refuses it and everything else that the pragma hides.
  - The layout of the cache is version 4. A cache of version 3 is refused with `ErrCacheVersion` and left as it is, with no upgrade. The version has to rise: a version that reads version 3 would read a column of version 4 that takes NULL and has no default as one that does not take NULL, without an error, and with version 4 it refuses the cache instead.
  - The core stores nothing by a default. `Tx.Upsert` and `Tx.Insert` still refuse a row without a value for every column, and an explicit NULL is stored as NULL. The engine fills in a left-out column with its default, or with NULL where it has none, and hands the core whole rows.
  - A default is copied into the table at `Tx.CreateTable` and out of it at `Table` and `Tables`, so that neither the caller's message nor one that the core gave can change the table.

## The engine and the driver

- **Decisions of the engine step of slice 11, `default` with a literal, by its builder on 2026-11-21, built, for the lead to confirm.** The agreement with Markus of 2026-11-20: a column may carry `default <literal>`, and an `insert` with a list of columns that leaves the column out stores the default. Each fact of SQLite here is pinned against SQLite by `TestEngine_defaults` in `internal/engine/defaults_test.go`, unless it says otherwise; the README of the engine has the details under "The stages", "The operators", "Errors", and "How it is tested".
  - Where the default is filled in. The plan's `ColumnDef` has `Default`, the literal of the DEFAULT as an expression (`*Null` for DEFAULT NULL, nil for none), which `Format` prints as ` DEFAULT <literal>` after the NULL of a column. The sink of a create table hands it to the core as `Column.default`. The sink of an insert fills each column that the list leaves out from the table that the transaction gives (`buildValues`), the core's schema as the cache or the log holds it, or with NULL where the column has none, and hands the core whole rows: so an insert after a replay, a restart, or a roll back uses the default of the log, and the core never fills anything in. An explicit NULL, as a literal or a nil argument, is NULL whatever the default.
  - The order of the errors of an insert with defaults, each pair of neighbours measured against SQLite: the text and the arguments; `no such table`; `table t has no column named x`; the number of values; `string or blob too big` for a value that the statement gives, which SQLite gives when it binds it, so a default never meets it; `attempt to write a readonly database`, before every error of a row; `NOT NULL constraint failed` for the first column in the order of the table, the key among them, that gets NULL, from a DEFAULT NULL, a column without a default, or an explicit NULL; the refusal of a value of another type, where SQLite gives `cannot store` or converts; `string or blob too big` for a record that a default makes too long; and `UNIQUE constraint failed`, also for a key from its default. The brief listed UNIQUE before the record; SQLite builds the record before it looks for the key, as the engine of slice 6 already had it.
  - The length check of an insert (`checkLength`) runs on the values that the statement gives, and no longer on the NULL or the default of a column that it leaves out: SQLite meets the length of a value when it binds it, and a default only in the record, which the core measures.
  - -0.0: the engine hands the core the default as the literal gives it, and the core keeps 0.0, as its builder decided; the plan prints -0.0. The test memory of the engine keeps 0.0 as the core does.
  - A table that SQLite takes under a lowered length limit and whose statement in the cache is longer than the limit, which the canonical form of a default makes more likely (`.5` is `5e-01`), gets `s4ql: not supported: the table t, whose statement in the cache is longer than the length limit`, where the engine gave an internal error before. The core wraps `core.ErrTooLongForCache` beside `core.ErrInvalid` for it, in `conn.create` and `conn.createIndex`, and `coreTx.createTable` and `coreTx.createIndex` turn that into the refusal, so every other `ErrInvalid` stays an internal error. An index gets the same with "index". It is "not supported" because SQLite takes the text, and the agreed rule is that s4ql does what SQLite does or says "not supported"; any error of SQLite would be a difference, and an internal error says that s4ql has a fault. It comes where the core creates the table, after every error that SQLite gives, the read-only one among them, and the transaction goes on. The generated checks excuse exactly that shape (`pair.tooLongForCache`, counted as `excusedCacheLimit`): the message for the table of the statement, SQLite takes the text in a savepoint that is rolled back, and `cacheStatementLength`, a second writing of the core's statement in the tests, is longer than the limit. `TestPair_tooLongForCache` pins that measure at the limit against the core, byte for byte, for every kind of default; no create table of the sequences comes near it, and the count is 0.
  - The planted bug `zeroLeftOut` gives the zero value only to a column without a default, as before slice 11 every column was; the new planted bug `nullDefault` gives a column with a default that the list leaves out NULL, of its own and in a transaction. `zeroLeftOut` runs in the hammer workload now, where it meets more columns without a default. The engine has eighteen planted bugs.
  - The driver's `check` calls `stmt.Check` alone again, and the `checkText` wrappers of the tests are gone: nothing refuses a text that the pass supports any more. Telemetry: nothing new.
  - The generated checks. The shapes of `stmttest.Sequence` have, of all their columns, none with a default, all, or each one time in two, a third of the shapes each; a default is NULL one time in six, also on the key and on a column that does not take NULL, a long text of about a third of `stmttest.LengthLimit` or a long blob of a fifth one time in three for text and a blob, and otherwise a value as an insert gives the column one, cut to half the limit; one create table in ten gives one column another default or none, and a retyped column gets a default of its new type. An insert with a list leaves out a column with a default one time in two and the key with a default one time in four, and a list that leaves out a long default gives its first column of text or a blob a value of 85 hundredths of the limit one time in two, so that the default makes the record too big. `Generator.Defaults` stays 0 in the sequence: its hook `Generator.Create` gives the defaults, as it gives NOT NULL. `stmttest.TableColumn` has `Default`, the `dflt_value` text; `TypeRule`, `Faults`, and `NullCases` take a column that the list leaves out as NULL only where its default is NULL or none; the new `stmttest.DefaultCases` names what an insert reaches of defaults, which `TestDifferential`, `TestConn_differential` (again by the kind of the transaction), and `TestGenerated` of the driver check count by outcome and require, a third of what the run gave, or 1. The simulation counts the create tables of the log with a default and the values of its rows that are the default of their column. `FuzzTypes` and `FuzzTypes_core` create a table of each type whose column has the value of the input as its DEFAULT (`typesLiteral`), and insert a row that leaves it out and one that gives NULL. The pinned numbers that moved, with the reason beside each, are in the tests.

## Mutation testing

- **Decided by the builder of the mutation testing of slices 10 to 12 on 2026-11-21, built, for the lead to confirm.** The round mutated the lines that the pull requests of slices 10 to 12 wrote, found with `git blame` of each file at `25c39a7`, in `internal/sql/stmt`, `internal/core`, `internal/format`, `internal/engine`, and the driver; code of the tests, such as `stmttest`, is not mutated. The results of the round are in [the README of the runner](../../internal/sql/mutation/README.md#if-not-exists-default-and-a-value-on-the-left-of-slices-10-to-12), the equivalent mutants in sections of `internal/sql/mutation/equivalent.txt` of their own. #112, the strict load of the cache, rewrote lines of `conn.load` after #111, and those lines are not in this round.
  - The pass (#109): 147 mutants, 16 not compiled, 122 killed, 4 killed by new tests, and 5 in code that nothing needs, removed: the guards of the name after DEFAULT in `recognizer.defaultValue` (a name is the token after the DEFAULT that the caller took, and `recognizer.value` names any token that is no literal). The new tests: `TestCheck` refuses ON CONFLICT before a second DEFAULT at the ON, and `default (0x10)` and `default (current_time)` as `DEFAULT of an expression`. The review of the round found that removing the check of the parenthesis too gave such a DEFAULT the name of the literal inside; the check is back, before the literal is read.
  - The core (#111, #114): 315 mutants, 50 not compiled, 244 killed, 4 killed by new tests, 9 in code that nothing needs, removed, and 8 equivalent. The new tests: `TestOpen_cache_defaults` pins the cache's statement of a table whose key is two columns; `TestTx_tooBig` pins the whole message of a table and of an index too long for the cache; `TestDefaultSQL` refuses every literal for a column of no known type. Removed: the `if`s around the clone of a default in `newTable` and `table.createTable`, `pk == 0` in the nullability of `conn.load`, after which a key column that takes NULL is refused already, and the checks of the quotes and of the `x'` of a text and a blob in `parseDefault`, which its round trip makes. The equivalent ones are the version of the cache, the precision of `strconv.FormatFloat` and the bit size of `strconv.ParseFloat`, the errors of `strconv.ParseInt` and `hex.DecodeString` and the default case of `parseDefault`, which its round trip refuses anyway, and the kind test of `withoutNegativeZero`.
  - The format (#111): 67 mutants, 13 not compiled, 53 killed, and 1 equivalent that the list held. The driver (#114): 10 mutants, 4 not compiled, 6 killed.
  - The engine (#114): 106 mutants, 17 not compiled, 79 killed, 6 killed by new tests, and 4 equivalent. The new tests: `TestBuild` refuses a default of a nil blob literal in a plan with the internal error; `TestFromCore` maps `core.ErrTooLongForCache` of a table and of an index, on a real core, to "not supported" by its name, and any other refusal to an internal error. The equivalent ones are the variants of the planted bugs `nullDefault` and `zeroLeftOut`, and the length check of a left-out default, which is never longer than the limit, since the core holds no table whose statement in the cache, which holds the literal of the default, is.
  - No mutant showed a fault.
