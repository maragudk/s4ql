# Slice 5: several columns

The decisions and notes of the builders of [slice 5 of the roadmap](../roadmap.md#slice-5-several-columns).

## The statement pass

- **Decided by the builder of the pass for slice 5 on 2026-11-20, built, for the lead to confirm:**
  - The typed form. `CreateTable` has `Table` and `Columns`, each a `stmt.Column` with `Name`, `Type`, `PrimaryKey`, and `NotNull`, and the methods `Key()`, the index of the primary key, and `ColumnsError()`. `Insert` has `Table`, `Columns`, which is nil when the statement has no list of columns, and `Values`, each a `stmt.Term` with `Value`, `Parameter`, and `Span`; `Value` is nil for a parameter. `Select` has `Table` and `Columns`, which is nil for `*` and otherwise holds the names in order, each as often as the list names it. `DropTable` is as it was.
  - The names of columns compare as the names of tables do, by `Name.Fold`, which folds only the ASCII letters, as SQLite does.
  - A `create table` with a column named twice, or with more than 2,000 columns, is supported by the pass. `CreateTable.ColumnsError()` gives SQLite's error for it, with the code 1 and the extended code 1, for the engine to give after its check of the table: `too many columns on t1` for the 2,001st column, and before that `duplicate column name: v1`, with the name of the later column. The reason: SQLite raises both in `sqlite3AddColumn`, while it parses, after `sqlite3StartTable` has looked for the table. On a database with a table of the name it gives `table t1 already exists` instead. So the answer depends on the database, and the spec accepts a difference from SQLite only for a syntax error, which the pass decides alone. The tests check `ColumnsError()` against SQLite on a database with the table and on one without it.
  - Two primary keys and no primary key are not supported, as `second PRIMARY KEY` and `table without PRIMARY KEY`. SQLite gives `table "t" has more than one primary key` while it parses, and `PRIMARY KEY missing on table t` after it has parsed the statement.
  - `not null` on the primary key is kept in `Column.NotNull` as the statement says it. SQLite records the same table with it and without it.
  - `select true from t` is not supported, as `TRUE or FALSE`: SQLite reads the bare word as 1 where the table has no column of that name. `select "true" from t` names a column.
  - An insert of more than 32,766 parameters, SQLite's `SQLITE_MAX_VARIABLE_NUMBER`, is not supported, as `parameter beyond SQLite's limit` at the 32,767th `?`. SQLite gives `too many SQL variables` while it parses, whatever the database holds, and such errors of SQLite's grammar actions stay "not supported", as before.
  - `*` beside another result column is `* and another result column`. `insert into t default values` has a name of its own, `DEFAULT VALUES`.
  - Built in the engine since 2026-11-20: SQLite names a result column by the name as the table stores it, so `select B from t` with a column `b` gives `b`. For a name that the table does not have it gives `no such column: v`, and for such a name in double quotes `no such column: "v" - should this be a string literal in single-quotes?`, because the pinned build has `DQS=0`.

## The engine and the driver

- **Decided by the builder of the engine and the driver for slice 5 on 2026-11-20, built, for the lead to confirm.** The README of the engine has the details under "The stages", "Errors", "Changes and the last insert rowid", and "Types". The order of the errors was read from SQLite's source and measured with the sqlite3 shell of 3.54.1, and the tests pin it against SQLite.
  - The order of the errors of an insert: the errors of the text and of the arguments, as before; `no such table: t`; `table t has no column named x`, for the columns of the list in their order; the number of values, which is `table t has N columns but M values were supplied` without a list of columns and `M values for N columns` with one, each with the code 1 and the extended code 1, and with the value of the name of the table that the statement writes; `string or blob too big` for a text or a blob longer than the limit, which SQLite gives when it binds; in a read-only transaction, `attempt to write a readonly database`; `NOT NULL constraint failed: t.c`, with the code 19 and the extended code 1299, which is the new constant `sqlerr.CodeConstraintNotNull`, and with the names as the table stores them, since slice 6 also for a NULL that the insert gives; "not supported" for a value of another type than its column, which is slice 4's rule, where SQLite has `OP_TypeCheck`; `string or blob too big` for a record that is too long, also when its key exists, as SQLite builds the record of a row of a WITHOUT ROWID table before it looks for its key (fixed by the builder of the generated checks of slice 5 on 2026-11-20, after a review of the lead found that the engine gave `UNIQUE constraint failed` there; the engine asked the core's new `Tx.Insert` for a key that exists, so that SQLite measures the record; since slice 6 every row goes through `Tx.Insert`, which is SQLite's `insert ... on conflict do nothing`, with no `get` before the write); and last `UNIQUE constraint failed: t.k`, with the key column at its position.
  - `NOT NULL constraint failed` names the first column without a value in the order of the table, also the key column. The refusal of the type names the first column of another type in the order of the table. An insert that leaves one column out and gives a value of another type to another column gets NOT NULL, as in SQLite, which tests every NOT NULL before it looks at a type. Since slice 6 a column that takes NULL and is left out gets NULL, and a NULL that the insert gives is the same case as a column left out; see the decisions of slice 6 in [slice-06.md](slice-06.md).
  - The order of the errors of a create table: `table t already exists`, with the name as written, and then what `CreateTable.ColumnsError()` of the pass gives, `too many columns on t` or `duplicate column name: v`. In a read-only transaction these come before `attempt to write a readonly database`, as every error that SQLite gives when it prepares a statement does.
  - The order of the errors of a select: `no such table`, and then `no such column: x` for the first name of the list that the table does not have. For such a name in double quotes the message is `no such column: "x" - should this be a string literal in single-quotes?`.
  - `NOT NULL constraint failed` sets the count of changes to 0, as `UNIQUE constraint failed` does, because SQLite gives it when it steps the statement. The refusal of the type leaves the count. The errors of the number of values and `no such column` leave it too, as every error that SQLite gives when it prepares a statement does.
  - The plan held no NOT NULL, because every column was NOT NULL. Since slice 6 a column of the plan has `Nullable`, which is true for a column that is not the key and has no `not null`. The key is always NOT NULL. A table with `not null` on its key and one without are the same table: they have the same plan and the same commit object, and the cache declares both in the same way. SQLite records another text of the schema for each, which s4ql does not expose.
  - The names of the columns of a result are as the table stores them, in `Rows.Columns` of the engine and of the driver: `select B from t` with a column `b` gives `b`, and a column that is named twice has its name twice.
  - The events have nothing new. They carried nothing for a column or a value, and they carry the same fields now; `statement.rows` is still the number of rows.
  - An annotation holds all the arguments of its statement, by position, as before.
  - The driver's `check` in `conn.go` calls `stmt.Check` alone again, without a second parse, and `engine.Check` refuses none of the forms of slice 5. `checkColumns` and the `checkText` wrappers of the tests are gone.
  - The pinned numbers of the generated tests moved, only because the engine now runs the two texts of `stmttest.Others` that it refused: `insert into %[1]v values (%[3]v)` and `select %[2]v from %[1]v`. The generator drew as before then, with `Generator.Columns` 0; the numbers moved again when the sequence wrote several columns, as the builder of the generated checks says below. In `TestDifferential` of the engine, the inserts of a value of another type went from 363 to 371. In `TestGenerated` of `drivercheck`, the errors that SQLite gives at prepare went from 1010 to 1012, the values of another type from 173 to 180, the statements while the rows of a transaction are open from 37 to 38, and the statements prepared outside their transaction from 48 to 49.
  - `drivercheck` excuses an error that SQLite gives when it prepares a text and s4ql when the statement runs. Its list of these errors, `prepareKinds`, now has the new ones too: `no such column`, the two errors of the number of values, `duplicate column name`, and `too many columns on`.

## The generated checks

- **Decided by the builder of the generated checks for slice 5 on 2026-11-20, built, for the lead to confirm.** The README of the engine has the details under "How it is tested" and "Results".
  - Each name of a table of a `stmttest.Sequence` has a shape of its own: one to three columns with names that differ, of mixed types, with the key at any position. A column after the first takes the type of an earlier one half of the time, so that two columns of one type are common. Nine create tables in ten declare the shape, one in ten of these with one column of any type, and the tenth has columns at random, whose names can repeat.
  - The forms and the rates of the faults. Two inserts in three have a list of columns, and two lists in three are shuffled. One list in eight leaves a column out. One list in twelve has another name of the sequence in the place of one of its own. One insert in sixteen has a value more, and one in sixteen a value less. One insert in ten has a value of any type, and a third of these a second. A select is `*` half of the time, and otherwise has one to four names, of which one in four after the first repeats an earlier one and one in twelve is any name of a column of the sequence. The names of columns are those that SQLite reads as a name in every position of a column, the select list too, where SQLite reads a word such as `current_date` as a value.
  - The generator has three hooks for the shapes, `Generator.Create`, `Generator.Insert`, and `Generator.Select`, which `stmttest.Sequence` sets. With them nil the generator draws as before, so the pinned numbers of the tests of the pass did not move.
  - The rule of the type is shared, in `internal/sql/stmt/stmttest/rule.go`: `TableColumn`, `Positions`, `ColumnOf`, `TypeRule`, `ValueKind`, and `Faults`. The tests of the engine and `drivercheck` both use it, because `drivercheck` is a module of its own and cannot use the test helpers of the engine. `TypeRule` reads every value. It gives nothing where a column that does not take NULL has no value, or since slice 6 gets NULL, because SQLite gives `NOT NULL constraint failed` first, and otherwise the refusal for the first column of another type in the order of the table. NULL is of no other type than any column.
  - `drivercheck` has a new counted excuse, `excusedQuoted`. mattn's SQLite reads a name in double quotes that is no column as a string, where the pinned build gives `no such column: "x" - should this be a string literal in single-quotes?`, because it takes double quotes for names only (`DQS=0`). `pair.checkQuoted` keeps such a select out of the comparison with mattn, and checks s4ql's error against the message of the pinned build. The engine's `TestDifferential` compares such selects with the pinned build, 71 times in its default run.
  - `drivercheck` scans the row of a `QueryRow` with one value, and again with as many values as the error of `database/sql` says that the row has, because `database/sql` gives no columns for a row.
  - Two steps of the hand-written sequences of `drivercheck` that the builder of the engine had left out are back: a select of `"x"`, and refusals of a value of another type in a list of several columns.
  - The simulation checks every row that a commit of the log upserts against its table, in `run.verifyRows`: the log has the table there, the rows are for every column in the order of the table, each row has one value for each column, and each value has the type of its column. The replay of the log compares every value of a row; it compared only the first.
  - The planted bug `listOrder` makes an insert with a list give its values to the columns in the order of the list. It is planted in statements of their own only: `writeIn` in `tx.go` gives `buildSink` only `skipUnique` and `convertReal`. Its own violation is "the replay of the log holds", and it is found by three others too. `convertReal` can now be found by "and the rule for the type of a value" too: in a table of several columns, the real that the bug converts can be the first value of another type, and the engine then refuses a later one.
  - The pinned numbers of the engine's `TestDifferential` moved: the texts of a table that exists from 21 to 17, the calls with the wrong number of arguments from 644 to 718, those with an argument that no column holds from 140 to 197, the values of another type from 371 to 336, and the literals that are too long from 5 to 3. An insert has up to four values, and so more parameters and more arguments around them. One insert in ten has a value of any type, where one value in ten had. The sequence draws other random numbers, which moved the first and the last.
  - The pinned numbers of `TestGenerated` of `drivercheck` moved: `excusedPrepare` from 1012 to 1072, `excusedStartedTable` from 12 to 9, `excusedArguments` from 395 to 396, `excusedArgument` from 126 to 189, `excusedType` from 180 to 161, `excusedLevel` from 78 to 70, `excusedRowsOpen` from 38 to 29, `excusedTxOpen` from 22 to 30, and `excusedOutside` from 49 to 68; `excusedQuoted` is new, at 32. The sequence draws other random numbers, which moves every count. Beyond that, the errors of slice 5 that SQLite gives at prepare took `excusedPrepare` up, the arguments of inserts of up to four values took `excusedArgument` up, and the value of any type in one insert in ten, where one value in ten had it, took `excusedType` down. 1,500 other seeds, from 100,000, found no difference.
