# The storage core

Status: built in `internal/core` on 2026-11-12 and 2026-11-13, and merged in pull request #12. The reasoning behind its design, with Markus's words, is in [internal/core/README.md](../../internal/core/README.md). This item holds what is still open or not built. What its tests do not show yet is in [Tests of the storage core](storage-core-tests.md).

- **Not decided: a connection reads each table from the schema again in every transaction.** It forgets its tables at the end of every transaction, so the first call on a table in a transaction runs two statements on the schema, and the first call that needs its indexes runs one more and one for each index (`conn.lookUp`, `TestSchemaReads`). `Get`, `Table`, and `Tables` read no index since 2026-11-20. The cost is not measured in time. The tables could stay while SQLite's schema cookie does.
- **Open: a manifest that is damaged on its way.** A commit object is checked against its name, and the manifest has no such check. A damaged manifest that still parses would be believed, and the swap that takes the lease would write it back. The store's contract promises content that is not changed. Whether the manifest needs a checksum of its own is not decided.
- **Not built: a refusal of a write as too large that is not `400 EntityTooLarge`.** `internal/store/s3store` maps only that answer to `store.ErrTooLarge`. A store or a proxy in front of it that refuses a large write in another way, such as with HTTP 413, gives an unknown outcome, and the commit uploads the same bytes again until the caller gives up. Nothing is committed wrongly, but the caller gets the wrong error, and each attempt may upload gigabytes. Found on 2026-11-18 with the limits of the stores: Amazon S3 takes 5 GiB in one write, Cloudflare R2 5 MiB less, Ceph what it is configured for, MinIO 5 TiB; Tigris documents none.
- **Not decided: catch-up downloads every missing commit object twice.** It reads each one on the walk back through the log, and again when it applies it. A spool of the walk could remove the second download.
- **Known: `Reader.Close` closes its SQLite connection while it holds `DB.mu`,** so a close that stalls on a slow disk holds up every call of the instance and the lease task meanwhile. `DB.Reader` opens without the mutex since pull request #48, and the review of that pull request asked for the close to follow. A builder tried it on 2026-11-19: the close marked the connection closed and counted itself under the mutex, closed it without the mutex, and `DB.Close` waited for the count, as it waits for the readers that are opening. It kept every life-cycle test and the simulation passing, and a new test showed the wait. But it let the close of a reader run at the same time as the closes of `DB.Close`, and SQLite then sometimes left the write-ahead log behind: the close of the last connection deletes it only if that close can lock the cache alone, and two closes at once can keep each other from that. `TestClose` "should refuse a query that comes while the close closes the rows that are open, before the instance has stopped" in the root package, whose `database/sql` closes idle connections while the connector closes the instance, found a log left in 21 of 300 runs, 3 of 100 under `-race`, and once in a run under the address sanitizer, against 0 of 300 before. A log that is left is no loss, because the next start recovers from it, but the tests take a log that is left for a connection that is left. A fix would close the connections one at a time under a lock of their own, which `DB.closeIdleLocked` would then wait for while it holds `DB.mu`. That is no longer simple, so the code was left as it was. The diary is `docs/diary/2026-11-19-reader-follow-ups.md`.
- **To consider: a spare that keeps its cache up to date.** Today an instance without the lease catches up its cache only when it gets the lease, so a spare that waited long has the whole log since its start to download and apply before it serves. Markus asked on 2026-11-19: "Should the cache keep up to date on a spare instance even when it doesn't have the lease (but still reject reads and writes)?" It would shorten the time until a spare serves after it takes over, at the cost of reads from S3 while it waits. Not decided.
- **Not decided: a connection whose close fails.** `DB.Close` marks the instance as closed before it knows that the connections closed, so a connection whose close fails is never closed. Since the fix of the scan, only an `iter.Pull` of a scan without its `stop` can cause that.
- **A possible later addition: S3's timestamps could shorten the wait after a crash.** They would be switched on only for a store that has been checked. They help how fast an instance serves, not safety. Why S3's clock is not safe enough to rest the lease on is in [research/s3-clock.md](../research/s3-clock.md).
- **Open: OpenTelemetry, traces, and metrics.** The core, the engine, and the driver log structured events through `log/slog`, to the logger of `s4ql.Options`, and nothing else. The lead decided on 2026-11-19 to leave traces and metrics out of the first round of the driver.
- **Idea of Markus on 2026-11-20, not agreed and not for now: reads at a named commit, also on an instance without the lease.** His words: "allow reads from instance without lease if commit id given?" A caller that names a commit, for example the one that its own last write produced, could be served by any instance, also one that does not hold the lease, once that instance's cache has caught up to at least that commit. The read then sees the caller's own writes, and reads can spread over instances. Open points:
  - **Exact or later:** whether the read is at exactly that commit, or at that commit or later.
  - **The commit's id in `database/sql`:** how the caller gets the id of a commit from a write, and hands it to a read.
  - **What the spec says today:** in the section "Concurrency", the bullet "Always a lease" says that an instance must hold the lease to read or write and that there is no mode without it, and "An instance without a valid lease refuses and keeps trying" says that its reads fail at once with a temporary error.
- **Known, from the mutation testing of slice 13: `KeySet.All` sorts the whole set for each key of a primary key of more than 63 columns.** Each key is read by a statement of its own that orders by every column of the key with LIMIT 1, which SQLite reads from the primary key of the set for up to 63 columns, and sorts for more. So `All` over n keys of such a table costs n sorts of the set. It gives the right keys, under the largest length limit; only its cost grows. A read that seeks by the columns of the key, or one statement over the set, would avoid it.
- **Open, from slice 14: the rows of a RETURNING are held in memory without a bound.** An insert, an update, or a delete with RETURNING holds each row that it changes, as the values of its columns of RETURNING, in Go memory from the change until the caller has read or closed the rows (`returning` in `internal/engine/returning.go`), when it runs through `Query`; through `Exec`, which drops the rows, it holds none (`dropReturns`). So `update t set v = 1 returning *` on a table of a million rows holds a million rows. The rows must outlive the write transaction, which the commit ends before the first row is given, so they cannot be read from that transaction. A spool in the cache, as `KeySet` is a set of any size, would bound the memory: a temporary table of the rows on a connection of their own, or a file. Not decided. goqite's statements change one row each.
- **Not built: the stop of an instance does not stop a sort that runs.** SQLite stops the sort of a scan, and the count of its unread rows, when the context of the call ends (`sqlite.Stmt.StepContext`, `conn.step`), since 2026-11-21. A stop or a `DB.Close` does not end that context, so a call that is inside a sort when the instance stops finishes the sort first, and `Close` waits for it, as the review of slice 13 measured: about 211 ms for 300,000 rows of about 200 bytes. A scan looks at the stop only between rows (`DB.stoppedError` in `ReadTx.scan`). The progress handler could look at the stop too, through a context that the stop cancels, at the cost of one such context for each scan. Not decided. A review measured the cost of `StepContext` at about 47 ns on the first step of a scan, with no allocation per step.
- **Not built: the browser build does not interrupt a running step.** In the build for a web browser (tag `s4ql_browser`, `internal/sqlite/sqlite_browser.go`), `sqlite.Stmt.StepContext` is `Step`, so a context that ends during a sort or during the count of its unread rows does not stop it, and the call ends with the error of the context only between rows. The official SQLite WebAssembly build exports `sqlite3_progress_handler`, and a handler could call Go through `syscall/js`, but Go's runtime runs every goroutine that is ready during each such call, so goroutines of the simulation would run in the middle of a step and could call SQLite there. The browser build is the site's simulator, where a context that ends during a sort does not matter. The tests of an interrupted step are in files with the constraint `cgo` (`internal/core/index_cgo_test.go`, `internal/core/index_cgo_internal_test.go`) or not built for the browser (`internal/sqlite/sqlite_test.go`, the engine, the driver). Decided by the builder on 2026-11-21, after CI's browser job failed on pull request #124.
