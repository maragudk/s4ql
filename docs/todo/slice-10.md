# Slice 10: `if not exists` and `if exists`

The decisions and notes of the builders of [slice 10 of the roadmap](../roadmap.md#slice-10-if-not-exists-and-if-exists).

## The statement pass

- **Decisions of the statement pass of slice 10, `if not exists` and `if exists`, by its builder on 2026-11-20, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell or the vendored source (`sqlite3StartTable`, `sqlite3CreateIndex`, `sqlite3DropTable`, `sqlite3DropIndex`, and `sqlite3ForceNotReadOnly` in `internal/sqlite/c/sqlite3.c`), and a subtest of `TestCheck` pins each against SQLite, on a database with the object and without it, and under `pragma query_only`. The README of the pass has the forms token for token.
  - The fields are `CreateTable.IfNotExists`, `CreateIndex.IfNotExists`, `DropTable.IfExists`, and `DropIndex.IfExists`, each a `bool`. They have no span, as no other clause of the typed form has one; the IF is the third token of each statement.
  - `CreateTable.SQL` and `CreateIndex.SQL` do not change: SQLite keeps the text from the name on, so the text that it keeps never has the clause. `create table If Not Exists t (v int primary key) strict, without rowid` is kept as `CREATE TABLE t (v int primary key) strict, without rowid`. `checkCreateTable` and `checkCreateIndex` compare `SQL` with `sqlite_schema` for every supported text, the clause among them.
  - A table or an index named by the bare word IF after IF NOT EXISTS, in any case, is not supported, with the new name `bare name IF after IF NOT EXISTS`, at the name. SQLite's parser accepts `create table if not exists if (v int primary key) strict, without rowid`, keeps `CREATE TABLE if (v int ...`, cannot parse that again, and gives `malformed database schema (if) - near "(": syntax error` (`near "on"` for an index) and creates nothing; in a read-only transaction it gives `attempt to write a readonly database`. Without the clause the word IF there starts the clause, so the plain statement is a syntax error. `"if"` in double quotes is a name like any other. `drop table if exists if` and `drop index if exists if` are supported: SQLite reads `if` as a name there, and keeps no text.
  - Every other name follows the rules of the plain statement: the pass checks every keyword after each clause against SQLite and the pools of the generator. 88 keywords are names after `create table if not exists` and after `create index if not exists`, the same as without the clause; 89 after `drop table if exists` and `drop index if exists`, the 88 of the plain statement and `if`.
  - The names `IF NOT EXISTS` and `IF EXISTS` of "not supported" are gone, since the pass supports the clauses wherever SQLite's grammar has them on a supported statement. DROP VIEW, DROP TRIGGER, CREATE VIEW, CREATE TRIGGER, and CREATE VIRTUAL TABLE with a clause keep the names of their statements. TEMP, a schema, `as select`, UNIQUE, and every other form that slices 1 to 9 refuse keep their names and offsets after the clause: `create temp table if not exists` is `TEMP` at the TEMP, `drop table if exists main.t` is `schema name` at the `main`.
  - Syntax errors, which the pass gives as SQLite gives them: the clause in the wrong place (`create if not exists table`, `drop table t if exists`), half a clause (`if exists` on a create, `if not exists` on a drop, `if not`, `if`), the clause twice, a name `not` or `exists` after the clause, and no name after it.
- **Known differences from SQLite of slice 10, decided by the builder of its statement pass on 2026-11-20, for the lead to confirm.** The pass sees only the text, so a text that it does not support stays "not supported" also when the object exists and SQLite would do nothing: `create table if not exists t (a foo primary key) strict, without rowid`, `... (a int primary key, b int primary key) ...`, `... (a int) strict, without rowid`, a table that is not STRICT or has no WITHOUT ROWID, AUTOINCREMENT, COLLATE, `create table if not exists t as select 1`, and `create index if not exists i on t (v, v)`, `(v collate nocase)`, a partial index, and `create unique index if not exists`. SQLite does nothing for each of these when `t`, or `i`, exists, and refuses or creates something s4ql does not support when it does not. The same holds for `drop table if exists json_each`, which SQLite runs as nothing, and the other names the pass refuses. The rule of the pass holds for each: SQLite accepts the text, and s4ql answers "not supported".

## The engine and the driver

- **Decisions of the engine step of slice 10, `if not exists` and `if exists`, by its builder on 2026-11-20, built, for the lead to confirm.** Each case is pinned against SQLite by `TestEngine_exists` in `internal/engine/exists_test.go`, and the generated checks compare every statement of the clauses with SQLite.
  - Where the object is there for a create, or not there for a drop, `buildSink` gives the sink `nothing`, at the place where the plain statement gives `already exists` or `no such`: a create table after the lookup of its table, before the index of its name, `ColumnsError`, and `schemaTooBig`; a create index after `no such table` and `there is already a table named`, before `no such column`, `indexTooBig`, and the refusal of more than 250 columns; a drop table and a drop index at their lookup. That is SQLite's order, in which an index of the name of a create table still gives its error.
  - A statement of its own of the clauses looks its object up in a read transaction of its connection first, and where it does nothing there it succeeds without the place of the writer, and without the lease beyond what a read needs: SQLite only reads the schema for such a statement, under a read lock, so it does not wait for a write transaction of another connection either. While the rows of an earlier query of the connection hold its reader, it looks on a reader of its own. Otherwise, and where the read transaction cannot begin, it begins a write transaction as every statement that may change the database does, and looks again there, which decides: one that does nothing then rolls the transaction back without an annotation. Either way the log does not change, and no commit object is written. The independent review of the branch found that the first version, which always began the write transaction, waited for the writer where SQLite does not (`TestEngine_exists` now pins that it returns while another connection holds a write transaction), and the second review that it still waited while rows of the connection were open (`TestEngine_write` pins with a count that it begins no write transaction then).
  - In a write transaction, a statement that does nothing releases its savepoint and is not annotated, so the commit object of the transaction does not hold it, and a transaction of only such statements writes no commit object, as an empty one does. In a read-only transaction it succeeds, as in SQLite under `pragma query_only`; one that would write gives `attempt to write a readonly database` after the errors of its names and columns, as the plain statement does.
  - While rows of a query of its transaction are open, a statement that would do nothing fails with `ErrRowsOpen`, as every statement in a transaction does: the rule is checked before the statement reads anything, and whether it does nothing is known only after it has read the schema of the transaction, so the refusal cannot depend on it.
  - What only the engine can refuse follows SQLite where the object exists: SQLite gives no `string or blob too big` for a statement that does nothing, also with a declaration or a comment longer than the length limit, and a create index of more than 250 columns does nothing where its index exists, where it is not supported otherwise. A create table with IF NOT EXISTS and a DEFAULT of slice 11, of a table that exists, does nothing before any check of its DEFAULT that the engine makes, since SQLite stops at the table.
  - The four statements leave SQLite's count of changes as it was, whether they do something or nothing, as the plain statements do, so the driver gives the `RowsAffected` of the statement before and `LastInsertId` 0.
  - The event of a statement of the clauses has the attribute `statement.nothing`: true where it did nothing, false where it went on to do what the plain statement does, also if it then failed, and none for one that failed before its sink was built, or without the clause. The simulation reads it, and checks each such statement against SQLite on the state that it saw, where SQLite's database must stay the same.
  - `stmttest.ExistsRule` says why SQLite does nothing for a statement of the clauses from the tables and indexes that it is given, and the tests give it those that SQLite has before each statement, so it follows a roll back and a drop table that took the indexes of its table along without a tracker of its own. `stmttest.Sequence` sets `Generator.Exists` to 3.
  - The planted bug of the simulation is `replaceExisting`, a create table with IF NOT EXISTS of a table that exists that replaces it, found by 123 of 200 seeds of the default workload, 87 of them by its own violation. The other bug that the brief offered, a statement that does nothing and writes to the log, would show only in a transaction with other writes, since the core writes no commit object for a transaction without changes, also with annotations; the check that finds it, a commit object that holds a statement that did nothing, found such a bug planted by hand at the first seed of the hammer workload, and was not kept as a planted bug.
  - `FuzzIndexes` and `FuzzIndexes_core` write the four forms through the bits 4, 8, and 16 of the byte of a drop and a create, and drop and create the table, where a new target would repeat their machinery; the old seeds read as before, since none sets those bits on a drop or a create.
