# The S3 client and S3's checksums

Status: built in `internal/store/s3store` on 2026-11-13. It passes the conformance suite against the project's Tigris bucket. What was found about Tigris, and what rests on AWS's documentation alone, is in [internal/store/s3store/README.md](../../internal/store/s3store/README.md). This item holds what is still open.

Markus asked: "Maybe S3 already knows the hash of its objects?" It does. On upload, the client signs the request with the commit object's SHA-256 as the hash of its payload and sends it as the object's checksum, and the store refuses content that does not match it.

- **Open: the check on download is not the one that was agreed.** The agreed bullet was: "On download, the client compares the checksum that S3 returns with the name, before it reads the body." The builder of the client did not add a checksum to `store.Store.Get`. The client asks the store for the checksum that it holds, and the SDK compares it with the content as it is read, so a read of content that does not match it fails at its end. A comparison with the name before the body would need the name in the interface, and it would only catch an object stored with another checksum, which the check on upload rules out for every object that s4ql writes. The reader of a commit object reads to the end and checks the name anyway. Markus decides whether that is enough.
- **Not checked: AWS, and other stores than Tigris.** There are no AWS credentials. The spec asks three things of a store, and checksums are not among them, so a store that does not check the payload's hash still works, without the second guard.

## A CA bundle of the SDK's configuration

Built on 2026-11-26. `s3store.New` failed whenever `AWS_CA_BUNDLE` was set, with "unable to add custom RootCAs HTTPClient, has no WithTransportOptions, *http.Client", because the SDK adds a bundle only to an HTTP client of its own type, `awshttp.BuildableClient` (`resolveCustomCABundle` in `config/resolve.go` of `aws-sdk-go-v2/config` v1.33.18).

- **Decided by the lead: the client honours the bundle as the SDK does.** It does not ignore it, as it ignores `AWS_MAX_ATTEMPTS`, because a bundle changes only who is trusted.
- **How:** `New` gives the SDK a `BuildableClient` whose roots are a copy of `Options.RootCAs`, lets the SDK read and apply the bundle, and takes the roots of that client into its own transport after the configuration is loaded. The client of the store's requests is still the client's own, on the one transport in `Client.transport`, with every setting it had. s4ql reads no AWS setting itself.
- **What the SDK does without `RootCAs`: the bundle replaces the system's roots.** The SDK's transport has no roots of its own, so it makes an empty pool and adds the bundle to it. With `RootCAs`, the bundle is added to the copy, so both are trusted.
- **`ca_bundle` of the shared configuration goes the same way.** It is read by the same resolver, after `AWS_CA_BUNDLE`, which wins when both are set. An `AWS_CA_BUNDLE` that names a missing file is an error, and does not fall back to `ca_bundle`. The SDK also reads `ca_bundle` from the shared credentials file; only the config file is tested.
- **A bundle that is missing or holds no certificate fails `New`** with the SDK's error, wrapped as "s3store: configuration: ...".
- **Changed on the way: the requests for credentials.** The SDK's default chain sends its requests for credentials, such as to a container's endpoint, to IMDS, or to STS, through the HTTP client of its configuration, and that client must now be the `BuildableClient`. Before, they went through the client's own transport. The `BuildableClient` is set to go through no proxy and to speak HTTP/1.1 only, as before, and it has the same roots. It keeps the SDK's other defaults: timeouts of dial and handshake, and redirects of 307 and 308 followed. `Client.Close` does not close its connections, which close after 90 seconds idle. No test shows the settings of that client, because a credential endpoint in a test is on a loopback address, which no proxy of the environment is used for anyway.
- **Open, from before: the requests for credentials trust only `RootCAs`, when it is set.** With a store behind a private CA in `RootCAs` and credentials from STS or SSO, the call to AWS fails its certificate check. This was so before this change too. If it matters, the `BuildableClient` gets the system's roots and the bundle, and only the store's transport gets `RootCAs`.
