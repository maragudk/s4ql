# Checkpoints and syncs of the cache

Status: built on 2026-11-26 in `internal/core`, on the branch `core-checkpoints`. The finding behind it is in [research/nightmare-mode.md](../research/nightmare-mode.md): with `synchronous = normal`, SQLite synced the cache only at a checkpoint, and its automatic checkpoint dropped its error, so with every sync failing, 200 commits succeeded while 199 syncs failed. This file holds the decisions of the piece of work and what is left open.

## The decisions

- **The cache runs with `synchronous = full`.** Markus decided on 2026-11-26: "I'm leaning full. Correctness wins over speed in our design." SQLite then syncs the write-ahead log at every commit, before the commit is in the index of the log, so a failed sync of the log fails the commit that needed it, and the rule "a local I/O failure stops the instance" holds within one commit, not only at the next checkpoint. The file of the cache is synced only by a checkpoint that copies the whole log, so a failed sync of the file fails no commit: it surfaces at the checkpoint after a later commit, which stops the instance then. The commit to the cache comes after the manifest swap, so a commit whose sync fails is in the log: `Tx.Commit` returns nil and the instance stops, as for any failure of the cache after the swap, and the next start serves the commit, from the cache if SQLite kept it, and else by catching up from the recorded position (`TestDB_sync` in `cache_test.go`). Tests that test neither syncing nor the production setting run with syncs off, which the section "Fixes after the review" describes.
- **SQLite's automatic checkpoint is off on every connection** (`pragma wal_autocheckpoint = 0` in `openConn`). Only a connection that commits a write can run it, and the setting is per connection, so the readers have it off too; `TestDB_checkpoint` reads it back from the writer and two readers.
- **The writer checkpoints, after a commit to the cache, from 1000 frames in the log on.** `DB.checkpoint` runs under the writer lock, after `Tx.commitCache` succeeded and after each commit object that a catch-up applied. It reads the size of the log with `pragma wal_checkpoint(noop)`, which takes no lock, and runs `pragma wal_checkpoint(passive)` when the log holds `Options.checkpointAfter` frames or more, 1000 by default, SQLite's `SQLITE_DEFAULT_WAL_AUTOCHECKPOINT`. That is exactly when and how SQLite's automatic checkpoint ran before (`sqlite3WalDefaultHook`), so the log grows and starts again as it did. A task of its own on another connection was the alternative: it would add a goroutine, a connection, and a lock, and the only gain, keeping the sync off the path of a commit, is small where the commit already waits for S3. The pragma needs nothing new in the binding: `OP_Checkpoint` turns `SQLITE_BUSY` into the first column of its row and fails the statement for any other error.
- **A checkpoint that is busy or held back is no failure.** A passive checkpoint never calls the busy handler. Where a read transaction still needs frames, SQLite copies the frames before them and returns `SQLITE_OK` with fewer frames checkpointed than the log holds (`walCheckpoint` resets the `SQLITE_BUSY` of a read lock); the event says `held_back`. Where another connection holds the lock of the checkpoint, the row says busy; the event says `busy`. "Busy" as an error, which `classify` calls `kindBusy`, counts as busy too, as it does for every call of the cache. So does `SQLITE_LOCKED`, which SQLite gives for any checkpoint, `noop` too, while a statement is still open on the connection (`sqlite3BtreeCheckpoint`): a commit from the loop of a scan, which SQLite allows, would otherwise stop the instance as a local failure where nothing failed; the event says `locked`. The review of the build found that case. The next commit checkpoints.
- **Every other error of a checkpoint stops the instance with `ErrLocal`,** "a checkpoint of the cache: ...", not only those that `classify` calls local. The commit before it is committed and cannot report an error, and a cache that cannot checkpoint cannot keep its log bounded. The commit returns nil with the outcome `committed_and_stopped`; a catch-up ends with the stop.
- **The log is bounded as it was under SQLite's own checkpoint, and no restart or truncate checkpoint is run.** The passive checkpoint never waits, so a read transaction that stays open holds the log back by what is committed meanwhile, and nothing else. Once the read has ended, the next checkpoint copies every frame, and the next write transaction starts the log from its beginning by itself (`walRestartLog`), which `TestDB_checkpoint` shows. A `full` or `restart` checkpoint would wait for the readers for up to the busy timeout in every commit while a read is open, and then still be held back, so it would slow commits and bound nothing that the passive one does not. A `truncate` checkpoint would only give disk space back; the file of the log keeps the size of its longest run, as before. The core has no bound on how long a read transaction stays open, and such a bound would be a decision of its own.
- **The close of the instance runs no checkpoint of the core.** A checkpoint of the core before the close would show its error, but after a failure SQLite's close would then try once more in place. SQLite's own checkpoint at the close of the last connection stays for an instance that has not stopped for a local failure: on success it deletes the log, and on a failure it keeps the log, which the next open recovers, checking the checksum of each frame, while nothing serves in between. After a stop for a local failure, the connections close without it, as the section "Fixes after the review" says.
- **An instance that does not write does not checkpoint.** A spare, which does not hold the lease, writes nothing to the cache, and its readers have the automatic checkpoint off; the holder's writer checkpoints. Another process with the same cache open checkpoints after its own commits, and the lock of the checkpoint keeps the two apart.
- **A restart after the stop is a normal start.** It opens the cache, recovers the log if the close kept it, and catches up from the recorded position. `TestDB_checkpoint` and `TestDB_sync` serve every acknowledged commit after the restart, and from an empty cache that replays the log.
- **A checkpoint is the event `checkpoint`,** with `outcome` (`checkpointed`, `held_back`, `busy`, `locked`, or `failed`), `checkpoint.log_frames`, `checkpoint.frames_moved`, and `duration.total`: Debug when it did not fail, also when held back or busy, and Warn when it failed, beside the Error of the stop. The core has no metrics, so it adds none.
- **The simulation fails syncs in a cell of its own, with the planted bug `ignoreCheckpointError`.** The workloads keep syncs off, for speed. The field `workload.syncs` opens the cache of each node through a `faultvfs.VFS` of its own, with syncs on and a checkpoint after 4 frames, and `workload.syncFaults` arms, at random times, a fault that fails the next sync of the file of the cache, which only a checkpoint that copies the whole log syncs, or of the log, which mostly a commit syncs, and only while the callers run. `run.close` also requires that one open fails one sync at the most, and that its stop is for it (`SQLITE_IOERR_FSYNC`), which the review of the build asked for: a coarser check let an ignored failure hide behind a later stop. `run.stopped` explains a failed sync, `SQLITE_IOERR_FSYNC`, on a node whose VFS has failed since the open, and `run.close` records "the cache of ... failed ... syncs, and the instance did not stop for it" for a database whose VFS failed while it was open and that did not stop for that failure. That check judges the rule itself, because `faultvfs` fails the sync and changes nothing else: the bug leaves no wrong page, and the one thing that it changes is that the instance goes on, so the symptom is that text alone. A buggify point in the core was the smaller change, but it would make up the error where the real path is SQLite's. The bug's workload is `singleWorkload` with two faults per node, and its control has syncs and no faults. Over 1000 seeds on 2026-11-26, under `full` and with the checks as they are, 681 seeds found the bug, none of the control, and none without the bug; the seeds with the bug had 7730 checkpoints, 31 of them held back, and 902 stops for a local failure, 882 of them at a commit after the swap. Before the review tightened the checks and kept the faults within the callers' time, 406 of 1000 found it, and under `normal`, before the coin between the file and the log, 330.

## Measured

On 2026-11-26 on the Mac Mini (Apple M4) of the build, with test binaries of the code before and after run in turns, six times each, at a load of 17 to 25 from other work. `BenchmarkDB_checkpoint` in `checkpoint_test.go` runs 3000 commits of 10 or of 200 rows on one instance, with an in-memory store without latency, so that the cache is most of the cost; 3000 commits of 10 rows pass the threshold of 1000 frames several times. `BenchmarkDB_catchUp` in `catchup_test.go` has an instance with an empty cache catch up on a log of 3000 commits of 10 rows each, from its open until it serves. Medians, in commits per second:

| | `normal` | `full` |
|---|---|---|
| Commits of 10 rows, on the disk `/Volumes/990` | 1916 | 2091 |
| Commits of 10 rows, on the main disk | 2075 | 1880 |
| Commits of 200 rows, on `/Volumes/990` | 561 | 577 |
| Commits of 200 rows, on the main disk | 599 | 618 |
| Catch-up on 3000 commits, on `/Volumes/990` | 6191 (0.49 s) | 4542 (0.66 s) |
| Catch-up on 3000 commits, on the main disk | 6063 (0.50 s) | 5282 (0.57 s) |

No difference is significant (benchstat, p from 0.09 to 1.0, with a spread of 15% to 50% from the load), so the commits showed none, and catch-up was 15% to 35% slower under `full` in the medians. Two things bound what these numbers say. On macOS, SQLite's unix VFS syncs with `fsync`, and with `fcntl(F_FULLFSYNC)` only under `pragma fullfsync`, which the cache does not set (`full_fsync` in `sqlite3.c`), and `fsync` on macOS does not flush the drive's own cache, so a sync here is cheaper than a sync that reaches the medium. On Linux, `fdatasync` waits for the device, so the cost of `full` there can be larger; it is not measured. And the core's checkpoints against SQLite's automatic ones, both under `normal`, measured the same way at a load of 13 to 19: 570 µs and 561 µs for a commit of 10 rows (p = 0.96), 2.00 ms and 2.02 ms for one of 200 rows (p = 0.88), so the extra `pragma wal_checkpoint(noop)` after each commit costs nothing that shows.

Catch-up applies each commit object in a transaction of the cache of its own (`replay`, called once for each by `DB.catchUp`), so under `full` it syncs the log once for each commit object, and the cost of `full` in catch-up grows with the number of commit objects, not with their size.

## Open

- **Not decided: batching the commit objects of a catch-up.** Catch-up applies each commit object in one transaction of the cache of its own (`replay`), so under `full` it syncs the log once for each. If the time to catch up on a long log matters, several commit objects in one transaction would be the remedy; nothing is built.
- **Not measured: the cost of `full` on Linux in production.** A sync on Linux waits for the device, so `full` can cost more there than on this machine. The tests that sync, which are the core's tests of syncing and the production setting, are a few seconds of the run; the cost of the change in CI is in the section "Fixes after the review".
- **OPEN, for the product owner: another instance that shares the cache can sync and reset the log after the first one stopped.** The fix after the review keeps the close of a stopped instance from checkpointing. But another instance, or another process, that has the same cache open already has its connections, and its next checkpoint goes on from the same backfill position in the shared index of the log: it does not copy again the pages that an earlier checkpoint held back after copying them into the file, its sync of the file can succeed where the first instance's failed, and the next write then starts the log again, while the file may hold pages older than the log held. Nothing is built for it. The remedy would be a decision of the product owner: mark the cache as suspect at the stop, so that the next start rebuilds it from the log, which goes against the spec's present words that a cache is not rebuilt ("If the cache cannot be opened, the start fails, and the cache is not rebuilt automatically"). To be decided once the sequence is reproduced in a VFS that keeps the volatile and the durable state apart, in [storage-core-tests.md](storage-core-tests.md).

## Fixes after the review

An independent review of the branch on 2026-11-26 found five things, fixed the same day. Two reviewers of those fixes then found two more holes, also fixed: a local failure that was not the first cause of the stop, and a key of the hook for tests that a literal could forge.

- **After a stop, the close no longer checkpoints.** `DB.Close` closed the readers and then the writer, and the close of the last connection ran SQLite's passive checkpoint from where the last one stopped, dropped its error (`sqlite3PagerClose`), and on success deleted the log (`sqlite3WalClose`). After a stop for a failed sync that is the "tried again in place" that the spec rules out, and it could delete the only durable copy of pages: pages that an earlier held-back checkpoint copied into the file are not written again, a second sync can succeed where the first reported the failure, and the log goes while the file holds old pages. Now every connection that closes once a local failure has stopped the instance, or met it after it stopped for another cause, and every connection of an `Open` that failed for one (`DB.keepLogLocked`, which reads the flag `DB.failedLocally` that `stopLocked` sets for every cause that wraps `ErrLocal`, first or not, in `closeIdleLocked`, `Reader.Close`, `DB.Reader`, and `closeCache`), first sets `SQLITE_DBCONFIG_NO_CKPT_ON_CLOSE`, through `sqlite.Conn.NoCheckpointOnClose` in both bindings: the browser's calls the official build's `sqlite3__wasm_db_config_ip`. The log stays, and the next open recovers from it. `TestDB_Close_afterLocalFailure` stops an instance for a failed sync of the log at a commit and for one of the file at a checkpoint, arms a fault on every write, sync, and truncate of both files, closes, and finds no failure and both files byte for byte as before the close, and the next start serves every commit; a clean close still checkpoints and deletes the log. With `keepLogLocked` returning false, both stop cases fail ("Expected 1, but got 2": the close's checkpoint met the fault). The second review found that a commit that goes on after `DB.Close` stopped the instance with `ErrClosed`, and then fails a sync of the log, closed the write connection with the checkpoint, since the stop records only its first cause; a subtest of `TestDB_Close_afterLocalFailure` shows that case now, and fails with "Expected 1, but got 2" when `keepLogLocked` reads the cause of the stop alone. The tests' check for connections that are left (`leftOpen`, and the same check of the root package's tests) now opens a connection of its own to each cache with a log, reads it, and closes it, so that a log that a stopped instance kept is gone after that close unless another connection holds the cache.
- **The comment on what a failed sync fails was wrong for the file.** `conn.setUp` said that a failing sync fails the commit that needed it. That holds for the log, which SQLite syncs at every commit before the commit is in the index of the log, and not for the file of the cache, which only a checkpoint that copies the whole log syncs, so its failure surfaces at a later commit's checkpoint. Corrected there, in the README of the core, and above.
- **A busy checkpoint has a test.** Nothing tested a checkpoint that cannot start because another connection holds the lock of the checkpoint, and the reviewer's planted fault "a busy row treated as a failure" survived. `TestDB_checkpoint_busy` holds a read open on a connection of its own, has a third connection run `pragma wal_checkpoint(full)` through a `faultvfs.VFS` with a long busy timeout while a write transaction of the instance holds the lock of the writer, and waits until that VFS counts a sleep, which shows that the third connection holds the lock of the checkpoint and waits in its busy handler; the commit's checkpoint then reports busy, and the instance does not stop. With the fault planted (`case after.busy:` giving `failed` and an error), the test fails with "Not true" at the check that the instance did not stop. It is in `checkpoint_cgo_test.go`, built only with cgo: in the browser's binding, SQLite's busy handler of the third connection holds the one thread, and the commit's spool file, which Go's file calls create through the JavaScript event loop, then waits for good (found in headless Chromium, where the test hung in `os.CreateTemp`).
- **The event says whether a checkpoint was busy or locked.** The outcome of the event `checkpoint` is `busy` when another connection holds the lock of the checkpoint or SQLite reports "busy", and `locked` when a statement is still open on the write connection; before, both were `busy`.
- **Tests run with syncs off unless they test syncing.** Under `full`, every instance that a test opened with default options synced at every commit, where the test neither fails a sync nor crashes the operating system, so the syncs checked nothing and cost time on every run. Now the core's scenario tests turn syncs off in their helper `world.openWith`, unless their options say `SyncOn`, which `TestDB_sync`, `TestDB_checkpoint`, `TestDB_checkpoint_busy`, and `TestDB_Close_afterLocalFailure` do (through `syncing` and `checkpointFaults`); the workloads of the simulation keep theirs off, except the cell with syncs. The engine's tests and the root package's tests open the core through `coretest.SyncOff`. The hook: the unexported field `Options.syncs` is set by the exported `core.SyncOff(o, testonly.Key{})`, whose key is of the package `internal/core/internal/testonly`, which Go lets only the packages under `internal/core` import, and has an unexported field, so that no literal of another package can stand for it (the first version, `struct{}`, took `struct{}{}`, which the second review found), and the engine, the driver, and the root package cannot call it; `internal/core/coretest`, which can, is what tests of other packages call, and the linter's rule `coretest` in `.golangci.yml` lets only test files import it. So code outside `internal/core` cannot turn syncs off without importing `coretest`, which fails the lint outside a test file; `core` itself and the packages under it are the only others that can. The production path is shown in two places: a subtest of the core's `TestOpen` reads `pragma synchronous` of an instance that `core.Open` opened with default options (2, full), and `TestOpen_sync` of the root package opens an instance with the core options of the tests without `coretest.SyncOff`, which keeps the core's default syncs, as the `core.Options{}` that `s4ql.Open` passes does, and shows that a failed sync of the log stops it at the commit, and that a failed sync of the file stops it at the core's checkpoint after a commit of more than 1000 frames. The engine opens no core in production, so it has no such test.
