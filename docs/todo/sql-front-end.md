# The SQL front end

Status: open. Of the SQL half the tokenizer is built, in `internal/sql/token`, and the parser of all of SQLite's grammar with its syntax tree, in `internal/sql/parser` and `internal/sql/ast`, tested against SQLite through `internal/sql/oracle`, `internal/sql/corpus`, `internal/sql/parsetest`, and `internal/sql/shapetest`. The pass after the parser is built for slices 1 and 2 of the [roadmap](../roadmap.md), for the column types and the literals of slice 4, for the several columns of slice 5, and since 2026-11-20 for the NULL of slice 6 and for the WHERE of slice 7, in `internal/sql/stmt`; [internal/sql/stmt/README.md](../../internal/sql/stmt/README.md) defines what it supports, token for token. The engine and the driver run the WHERE of slice 7 since 2026-11-20, and hand-written tests, the generated tests, and the simulation, which has a planted bug for WHERE, compare them with SQLite; the tests of the engine read the rows both by the key and with every row read, and `FuzzWhere` and `FuzzWhere_core` build a WHERE from their input. Not built yet for it: mutation testing of the code of slice 7. The engine and the driver run the NULL of slice 6 since 2026-11-20, and hand-written tests, the generated tests, and the simulation, which has a planted bug for NULL, compare them with SQLite; `FuzzTypes` and `FuzzTypes_core` draw NULL too. The engine and the driver run the several columns of slice 5 since 2026-11-20, and hand-written tests, the generated tests, and the simulation compare them with SQLite; `FuzzColumns` and `FuzzColumns_core` build a table of several columns and the calls on it from their input. The code of slices 5 and 6 went through the mutation tester on 2026-11-20. The engine and the driver hold the five types of slice 4 since 2026-11-19, and the generated tests and the simulation run them; their code went through the mutation tester on 2026-11-20, and `FuzzTypes` and `FuzzTypes_core` of the engine fuzz arbitrary values of every type against SQLite. The engine runs slices 1 to 7, in `internal/engine`; [internal/engine/README.md](../../internal/engine/README.md) has its stages, its operators, its errors, and how it is tested. The public package with the `database/sql` driver runs them too, at the root of the module; see [The public package and the driver](driver.md). The facts and the options behind every point here are in [research/sql-front-end.md](../research/sql-front-end.md). Markus decides each open point before it is built.

- **Agreed on 2026-11-16, partly built: the pass after the parser.** The half that rejects is built for slice 1, in `internal/sql/stmt`: it rejects what the roadmap does not list, from the tree of `internal/sql/parser`, and gives a typed statement for the rest. Not built: the errors that SQLite's grammar actions raise while they parse, such as `unknown table option`, `duplicate column name`, or `ORDER BY clause should come after UNION not before`. The parser accepts such statements, and the list of those errors, with where SQLite raises each, is in `internal/sql/parser/README.md`. Slice 1 does not need them. None can occur in a statement of slice 1, so every statement that has one is "not supported"; the README of `internal/sql/stmt` gives the reason for each. A later slice needs them as soon as it supports a form in which one can occur. One gap is known until then: where an action's error comes before a syntax error in the same statement, SQLite gives the action's error, and the pass gives the parser's syntax error. The oracle does not say on such texts, so no test compares them. For the builder of the action errors:
  - When a statement has two faults, SQLite reports the one it meets first, and of the messages raised while one token is handled, the last; an action runs when the token after its rule arrives. On 308 of the corpus's statements SQLite does not say whether they parse, because an action stopped it early: those are the test cases for these errors.
  - A keyword read as a name keeps the kind of the keyword in the tree. Where SQLite reads a keyword as a name is decided by Lemon's tables, not by `parse.y` alone: GENERATED after a column's name or type is a word of the type, so `a int generated always as (1)` has the type `int generated always`.
  - Decided by the lead on 2026-11-18 for the pass of slice 1, which a builder is building; each can be changed later, and when the pass is merged its README holds them:
    - The pass gives a supported statement to the engine in a small typed form that it builds only from what it has recognized, and the engine never reads the raw tree to decide what to do. So no second place has to agree on what is supported.
    - A statement is supported only if every token that the parser read for it is one that the supported form expects in that place. When in doubt, a form is not supported.
    - One statement for each text of `stmt.Check`, which `Query` and `Prepare` use. After the first statement only spaces, comments, and semicolons may follow; a second statement makes the text "not supported". `Exec` runs several statements one after another, which `stmt.Split` reads; see [several-statements.md](several-statements.md).
    - A text with no statement at all (empty, or only spaces, comments, and semicolons) is an outcome of its own. The driver answers it with "not supported".
    - The errors that SQLite's grammar actions raise, such as `unknown table option`, are not reproduced in slice 1: such statements are "not supported". They come when a supported shape can reach one.
- **Agreed on 2026-11-16, partly built: how the parser is tested.** Four checks, with SQLite as the judge wherever it can be. The first three are built: agreement with `sqlite3_prepare_v2`, the ownership of every token, and the shape of the tree, in `internal/sql/shapetest`, which writes the tree with every operation in parentheses and requires the same `EXPLAIN` output and the same values from SQLite.
  - For what the engine supports, rows and errors are compared with SQLite's, when the engine exists. `shapetest.Check` and `shapetest.Test` are there for the engine's builders, and `shapetest.Pairs` and `shapetest.Triples` give expressions that combine every pair of operator forms.
  - Open, a possible later check: the mutation tester, `internal/sql/mutation`, changes the tokenizer, the tree, the parser, and the pass after it, but not the judges, `internal/sql/oracle` and `internal/sql/parsetest`. A fault in a judge that makes it say less, such as a `NotSaid` too many, shows only in the pinned counts of the tests, not in a list of surviving mutants.
  - The shape check cannot see a few things, which its README lists: groupings that SQLite treats the same, such as `x NOT BETWEEN a AND b` against `NOT (x BETWEEN a AND b)`, and what SQLite does not record of a table, such as the names of constraints other than CHECK. Where a wrong tree prints the same tokens, as at the boundary between a column's type and its constraints, the check compares what the tree declares with what SQLite records of the table. REGEXP, MATCH, and GLOB with ESCAPE are compared through stub functions that the binding gives a test's connection.
- **In reserve, not planned: reading SQLite's own tree out of its memory.** It works for the statements that build a tree, through the parse-only mode that `ALTER TABLE ... RENAME` uses and a walker in C over SQLite's private structs. It is not built, because it compares against SQLite's internal form through a function of ours that would mirror about 30 of its rewrites, and the checks above cover what it would catch, except a fault in the parser and one in the printer that cancel each other, and the gaps of the shape check named above. If those gaps come to matter, this closes them. The routes and their costs are in [research/sqlite-parse-tree.md](../research/sqlite-parse-tree.md).
- **Decided on 2026-11-18, built: a syntax error never depends on the database.** The spec: "Text with a syntax error gets the error that SQLite gives for it on an empty database." So `stmt.Check` alone decides a syntax error, and the engine gives it without a transaction: never an error of the lease, the stop of the instance, or the context. SQLite differs where a grammar action looks the schema up while it parses. For `CREATE TABLE` and `CREATE VIRTUAL TABLE` with the name of a table that exists, SQLite gives `table %s already exists` before a later syntax error: with `t1`, `create table t1 (v1 int primary key) strict without rowid` gives `table t1 already exists`, and on an empty database `near "without": syntax error`, which is what s4ql gives. This is the one difference from SQLite that the tests accept, through `stmttest.StartedTable`. The README of `internal/sql/stmt` has the details, under "Known gaps". The reviewer verified sibling cases, where SQLite gives another error than the syntax error because of what is in the database or because of an earlier grammar action. All have the result code 1 and the extended code 1 on both sides; only the message differs:
  - `alter table nosuch add v1 int primary key x y` gives `no such table: nosuch`, and `duplicate column name: v1` when the table and the column exist.
  - `create table t2 (v1 int, v1 int) x y` gives `duplicate column name: v1`.
  - Others seen: `unknown database x`, `object name reserved for internal use`, `temporary table name must be unqualified`, `table "t2" has more than one primary key`, and for `CREATE TRIGGER` `no such table: main.X` and `cannot create INSTEAD OF trigger on table: X`.
  - **Still a gap against the spec's rule:** every one of these. On an empty database SQLite gives `no such table: nosuch` for the ALTER TABLE, `duplicate column name`, `unknown database`, `object name reserved for internal use`, `temporary table name must be unqualified`, and `has more than one primary key` as above, and `no such table: main.X` for both triggers, where s4ql gives the syntax error. Measured with the sqlite3 shell of 3.54.1. The ALTER TABLE's `duplicate column name` and the INSTEAD OF trigger's `cannot create` depend on the database, so the rule does not ask for them, but the empty database's answer for those texts is not the syntax error either. They close with the errors of the grammar actions, under the first item of this section.
- **Decided by the lead on 2026-11-18, built: a text with no statement gives the sentinel `ErrNoStatement`** of `internal/engine`. The driver answers it with "not supported", as the lead decided on 2026-11-19.
- **Decided by the lead on 2026-11-18, built: the annotation of a write is the statement's own text,** from its first token to its end, the end of its semicolon if it has one, and not the whole text given to the call. Comments and semicolons before it, and the text after it, are left out.
- **Open, found by the builder of the engine for slice 4: s4ql gives no `statement too long`.** SQLite refuses a text longer than `SQLITE_LIMIT_SQL_LENGTH`, 1,000,000,000 bytes, with code 18 and `statement too long` when it prepares it. s4ql parses such a text, and a literal in it that is longer than the limit gets `string or blob too big` instead. No slice says what s4ql does with such a text.
- **Known difference, found by the independent review of pull request #91 on 2026-11-20: a record that is too long in an update of many rows.** At the length limit of 1000, with `t (k int primary key, a text, b text not null)` and the rows `(1, '', '')` and `(2, <301 bytes>, '')`, `update t set b = <700 bytes>` succeeds in SQLite 3.54.1 on macOS and stores a row of 1002 bytes, and s4ql gives `string or blob too big`; where the new key also exists, SQLite gives `UNIQUE constraint failed` and s4ql `string or blob too big`. The cause is SQLite's `OP_MakeRecord`: it checks the limit only when the buffer of its output register, which holds the record of an earlier row of the statement, is too small for the next record, and the buffer has the size that the allocator gives, which can be some bytes more than was asked for. So whether SQLite refuses a record a little over the limit depends on the earlier rows and on the platform's allocator: on macOS the slack is larger, on Linux it is at most about 7 bytes. The first row of a statement always gets a new buffer, and SQLite measures its record. s4ql's answer is the deterministic one, and it stays: the core measures each record, because it writes each row on its own. The engine's generated checks excuse exactly this shape, as `excusedRecordSlip` in `differential_test.go`: an update that s4ql refuses with `string or blob too big` for a record, that SQLite runs, in a savepoint that is rolled back, without that error, which finds two rows or more, and whose rows, changed one at a time in the order of the key, as the engine changes them, each by an update of that row alone in SQLite in a savepoint that is rolled back, fail first with `string or blob too big` (`pair.recordSlips`). An update of one row alone gets a new buffer, and SQLite measures its record. `TestPair_recordSlips` pins the shape. The count of the excuse is in the tally, and not pinned, since it depends on the platform.
- **Known difference, found by the builder of the engine for slice 7 on 2026-11-20: a literal in WHERE that is longer than the length limit.** Measured in SQLite under a lowered length limit. A string literal in WHERE that is longer than the limit mostly gets `string or blob too big`, because SQLite evaluates it as a constant, also on an empty table. As the upper bound of a search of the primary key, `k < 'long'`, SQLite evaluates it only when the search reaches a row: on an empty table, or with `k > 'zz' and k < 'long'` where no key is above `'zz'`, the select gives no rows. A blob literal that long becomes NULL, and the select gives no rows. s4ql gives `string or blob too big` for all of them, as it does for an insert, whatever the table holds. `TestEngine_where` pins the string literal on a column outside the key against SQLite, and the blob literal against s4ql's rule. Since the generated checks of slice 7, the generated tests of the engine make such literals, in the sequences that run at the lowered length limit. `pair.checkType` leaves a select with one to the comparison with SQLite (`pair.longCondition`), and `pair.step` excuses a difference, as `excusedLongCondition`, only where SQLite gives no error and s4ql gives `string or blob too big`. The default run of `TestDifferential` reaches 2 such selects, and SQLite refuses both too, so the run does not reach the difference, and the count of the excuse is pinned at 0. A full run with the default flags that reaches the difference fails until the pin is changed on purpose. A run with other flags, and a fuzz target, excuse it.
- **Not built: the core's own model and simulation tests drive `Tx.Upsert` and not `Tx.Insert`,** whose record of the keys that it touches only a subtest of `TestTx_tooBig` checks. The engine's tests on the core, `FuzzColumns_core` among them, reach `Tx.Insert` through the engine.
- **Decided by the builder of the pass, for the lead and Markus to confirm: the names of SQLite's eponymous virtual tables are "not supported".** They are `json_each`, `json_tree`, `jsonb_each`, `jsonb_tree`, and `pragma_<name>` for 59 PRAGMAs. SQLite reads these tables without a CREATE, and an engine with a catalog of its own would answer `no such table`. This goes beyond the roadmap's restrictions.
- **Decided on 2026-11-18: the statements of a transaction that changes nothing are stored nowhere.** Such a transaction writes no commit object, so its annotations are dropped. Examples are an `insert` that fails on a key that exists and a `drop table` of a table that does not exist. Markus agreed to keep it so: annotations explain the results in the log, and without results there is nothing to explain or to replay. The spec's wording fits, because it speaks of the statements that produced the results. If every statement is to be kept one day, for an audit for example, that needs a place of its own, since a commit object without changes would only make the log grow.
- **Open, found by the builder of the statement pass of slice 14 on 2026-11-23: the pass reads RETURNING, and the engine refuses it.** The pass gives an insert, an update, or a delete with RETURNING in `stmt.Returning`, and `engine.returningRefusal` refuses it with `RETURNING clause`, as the pass did before, until the engine and the driver run it. [slice-14.md](slice-14.md) has the decisions of the pass and the facts of SQLite for the engine.
- **Open, found by the builder of the statement pass of slice 14 on 2026-11-23: s4ql runs a select of more than 2,000 result columns.** SQLite refuses it with `too many columns in result set`, code 1, when it prepares the statement, after it has found the table and its columns, as `SQLITE_MAX_COLUMN` is 2,000. Measured with the pinned shell and the engine on 2026-11-23: `select k, k, ..., k from t` with 2,001 columns gives the rows in s4ql. The pass supports such a select, and the engine gives no error for it. RETURNING has the same limit, and the engine must give the error for it too.
- **To consider: how a developer learns what is not supported in a query.** Today a statement that s4ql does not support fails when it runs, with an error that names one thing. Markus asked on 2026-11-19: "how does a developer know what's not supported based on the incoming query?" Questions to answer: whether the error names the exact construct and where it is in the text, whether it reports all unsupported things in a statement or only the first, whether the error can be told apart in code (a sentinel or a type), and whether there is a way to check queries before they run, such as a tool over an application's SQL or a list of what is supported in the documentation. Not decided.
