# CI

- **Seen once: CI's job `browser` hung in four packages at once.** On 2026-11-19, on pull request #63, the tests of `internal/sqlite`, `internal/sqlite/faultvfs`, `internal/core`, and `internal/sim` ran until the timeout of 30 minutes ("the program did not exit within a minute after its -test.timeout"), while the three packages after them passed. A rerun passed. The pull request did not change those packages. It was not looked into. If it comes again, the hang should give a stack, and the timeout of the job should be far shorter than 30 minutes.
- **The check of the simulator's page hangs at times, and the hang is not fixed.** CI's job `site` hung in 7 of 132 runs from 2026-11-18 to 2026-11-20, first on pull request #70: `make site-check` printed "sitecheck: the check did not end within 10m0s" and nothing else, where a check that ends takes 34 s at the median and 63 s at the most, and a rerun passed. Since pull request "Make CI faster and more reliable", the check stops after 3 minutes, and then prints the stacks of its goroutines, the requests of the page so far, and the output of Chromium. It does not print the page's console or its state: Chromium writes the console to its output only with `--enable-logging=stderr`, and the state needs `check.html` to report it, both in `internal/simulator`, which another piece of work owns. The cause is not known.
- **Fixed on 2026-11-26: the race of the counter in the store's conformance test failed on a transient error of the real bucket.** Twice in 40 failed runs of CI, `should lose no increment of a counter that racing clients swap` of `TestClient_conformance` failed against Tigris: on 2026-11-24 a swap had its connection reset ("the counter is \"29 racer-7-3\""), and on 2026-11-26, on pull request #160, Tigris answered five gets with `408 RequestCanceled` ("the counter is \"21 racer-0-3\""). Neither the SDK nor the client nor a context made the 408: the client retries nothing, its transport has no timeout, and an ended context would show as `context canceled`. A racer stopped at its first such error, and the test still wanted all 32 increments, without counting those that had succeeded. Now a racer tries a get or a swap again and gives up after 5 failures in a row, with the error, and the test checks that the counter is at least the swaps that succeeded and at most those plus the swaps whose outcome is unknown. A swap that ignores If-Match in the fake (a lost increment), one that is applied and answered as changed (a counter too large), and a get that always fails each still fail the test; a get that fails one time in ten passes.
- **The planted-bug tests stop a bug's subtest at its first seed with an unknown symptom, which can hide a later seed of the same bug in the nightly.** `TestSimulation_plantedBugs` of `internal/core` (`is.True(t, known, …)`) and of `internal/engine` (`t.Fatalf("seed %v finds the bug by another violation …")`) end the subtest of a bug at the first seed whose violations hold none of its symptoms. CI stops at the first few seeds that find the bug anyway, so this matters only for the nightly's 1000 seeds, where a second unknown symptom of the same bug shows only the night after the first is accepted. `TestDifferential` had the same effect, which hid sequence 25196 behind 16832 from 2026-11-21 to 2026-11-25 (issue #117); it now reports up to ten failing sequences. The planted-bug tests could report each such seed with `t.Errorf` and go on, in a few lines each; it was left for now, since the engine's tests were being changed on another branch at the time.
- **`TestDifferential` does not check which rows a subquery reads before its first match, so its excuse for a subquery's evaluation error by one direction lets a fault through where the write changes nothing.** A subquery without an ORDER BY that decides its first row reads in the direction that each engine draws, so an update or a delete with arithmetic in a subquery may give an evaluation error by one direction and not by the other (the nightly of 2026-11-26, sequence 47712). `pair.bothWays` excuses that difference where neither instance changed a row and the error is justified. `pair.due` does not model the rows that a subquery reads in the direction it drew, so a fault that drops such an error by one direction, where the write changes nothing either way, is not seen. A planted fault of that kind is still found where a row changes (2 of the sequences of `-sequences 400`). The fix is a check of the due errors of a subquery by the direction and the rows that it read, which the engine records in its event of the statement.
- **The nightly's log does not show the seed of the directions of the pair's other instance, so a failure that depends on it cannot be replayed exactly.** Locally, a failing `TestDifferential` prints "an instance of the engine drew the directions of its scans from the seed …" for each instance, but the log of run 45742532324 has no such line, for a reason not found. Printing the seed would not be enough anyway: `-directions` sets the seed of every instance, also of the instance whose directions follow the sequence. A flag for the other instance's seed alone would make it replayable.
- **The nightly runs the generated checks of the engine at night sizes, but not those of several statements in a transaction (`TestConn_differential`) or of the driver (`TestGenerated` of `internal/sqlite/crosscheck/drivercheck`).** Both have fixed sizes, the same in CI and at night, so a fault that only longer runs reach shows in neither. On 2026-11-26 the failures of the walk of several statements showed only in `TestDifferential -sequences 400`. A flag or an environment variable for their number of sequences, set by `.github/workflows/nightly.yml`, would make the night reach further.
- **Open: a round of mutation testing in CI builds every mutant on its own.** Each mutant of `.github/workflows/mutation.yml` builds the test binary of every stage that it reaches with its file in an overlay, which is most of the cost of a mutant that the first stage kills, and the build of a mutant that does not compile is spent to learn that: 462 of the 2,488 mutants of the engine's round of arithmetic. Two ideas are not built. One compiles all the mutants of a package into one binary, each behind a check of a variable that names the mutant to switch on (mutant schemata), so that a shard builds once and a mutant only runs; a mutant that does not type-check would be dropped by `go/types` before the build, without a build of its own. The other runs first only the tests that cover the mutated line, from a profile of coverage per test that the planning records, and the other tests only when those pass; a mutant that no test covers survives without a run. Both change what the runner measures, so each would need the merged results of a round compared with those of the runner as it is on the same tree.
- **Open: `internal/sql/mutation/round.txt` records one commit for every package.** A round that a builder runs on one package does not move it, so the next round mutates that package's changes again. The first weekly round covers what changed since 8c53a53f (#156); `core.DB.CloseCache`, which b94fbe2a added before that and no round mutated, is not in it (one mutant, the removal of its one call).
- **Open: each shard of a round in CI plans every package of its share.** The mutants are dealt out so that every shard has some of every package, so every shard builds and times the stages of every package of the selection; for the binding, `internal/sqlite`, that is the tests of nearly every package under `internal`. A round of everything, or one where the binding changed, pays that once per shard.
- **Open: a round by `-since` does not see tests that got weaker.** It mutates the declarations whose code changed since the last round, and a mutant's result also depends on the tests: a test that is removed or loosened after a round can leave a mutant of code that did not change alive, and no later round runs it. A round of everything (`since` all, by hand) finds those. A rule that also mutates the packages whose tests changed would catch most of them, at the cost of many more mutants per round.
