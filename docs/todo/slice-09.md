# Slice 9: indexes

The decisions and notes of the builders of [slice 9 of the roadmap](../roadmap.md#slice-9-indexes).

## The statement pass

- **Decisions of the statement pass of indexes, slice 9, by its builder on 2026-11-20, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell, the binding, or the vendored source (`sqlite3CreateIndex`, `sqlite3DropIndex`, `sqlite3HasExplicitNulls`, and `sqlite3StringToId` in `internal/sqlite/c/sqlite3.c`), and the tests of the pass check it against SQLite. The README of the pass has the forms token for token.
  - `stmt.CreateIndex` has `Index` and `Table`, each a `Name`, and `Columns []stmt.IndexColumn`, in the order of the text, from 1 to 2,000. A `stmt.IndexColumn` has `Name` and `Descending`, true for DESC and false for ASC and for neither. `stmt.DropIndex` has `Index`. Both have `Span`, and `Parameters()` is 0.
  - A column named twice in an index, as `Name.Fold` compares names, is not supported, as `column named twice`, at the later name, as in INSERT and SET. SQLite makes an index of the column twice, `(a, a)` with two key columns `a`, and `(a, a desc)` with both orders. The roadmap leaves this to the slice.
  - The name of an index that is the name of its table, or of another table, is supported. SQLite never creates such an index: it gives `there is already a table named t`, with the value of the name of the index, once it has found the table. Which error comes depends on the database, so it is the engine's, as `table t1 already exists` is for CREATE TABLE. The roadmap leaves this to the slice.
  - A string in single quotes in the columns, `('a')`, is not supported, as `single-quoted name`, as in every other place. SQLite reads it as the name of the column (`sqlite3StringToId`), never as an expression: `('zz')` gives `no such column: zz`. A name in double quotes is a name, since the build has `SQLITE_DQS=0`.
  - `((a))` is not supported, as `parentheses`, though SQLite reads it as the column `a`. `t.a` and `main.t.a` are `column with the name of a table`; SQLite gives `the "." operator prohibited in index expressions`. TRUE and FALSE are `TRUE or FALSE`, as in WHERE: SQLite reads them as 1 and 0 where the table has no column of the name, an index on an expression. COLLATE is `COLLATE`, at the column before it. Everything else that is not a name is `index on an expression`, at its first token: NULL, CURRENT_TIME, a number, a string after a sign, a parameter, `a + 1`, `-a`, and `lower(a)`.
  - NULLS FIRST and NULLS LAST are not supported, as `NULLS FIRST or NULLS LAST`, at the NULLS. SQLite refuses them with `unsupported use of NULLS FIRST` (or LAST) on any database, as the first check of `sqlite3CreateIndex`, after the parse; the oracle says the text parses.
  - More than 2,000 columns, `SQLITE_MAX_COLUMN`, are not supported, as `index beyond SQLite's limit`, at the 2,001st. SQLite gives `too many columns in index` once it has found the table, before it looks for the columns, also for 2,001 names that the table does not have. 2,000 columns on a table of 2,000 columns work.
  - The name of an index that starts with `sqlite_` or `s4ql_`, in any case of the ASCII letters, is not supported in both statements, as `reserved index name`. SQLite gives `object name reserved for internal use: sqlite_x` in CREATE INDEX, once it has found the table, and `index associated with UNIQUE or PRIMARY KEY constraint cannot be dropped` for `drop index sqlite_autoindex_t_1`, the index of the primary key of every table of s4ql. `s4ql_` is reserved as it is for tables. The name of an eponymous virtual table, such as `json_each` or `pragma_table_list`, is an index name like any other: SQLite creates and drops such an index, and the virtual table works beside it. The table after ON has the rules of every table name, so `json_each` is `name of a virtual table of SQLite` there.
  - A schema on the name of the index, `main.i` or `temp.i`, and in DROP INDEX, is `schema name`. SQLite creates `main.i`, gives `cannot create a TEMP index on non-TEMP table "t"` for `temp.i`, drops `main.i`, and gives `no such index: temp.i`. A schema on the table after ON is `near ".": syntax error` in SQLite's grammar, and the pass gives it.
  - The new names of what is not supported: `UNIQUE INDEX`, at the UNIQUE; `partial index`, at the WHERE; `index on an expression`; `NULLS FIRST or NULLS LAST`; `index beyond SQLite's limit`; and `reserved index name`. IF NOT EXISTS and IF EXISTS keep the names of CREATE TABLE and DROP TABLE, `IF NOT EXISTS` and `IF EXISTS`; REINDEX and ANALYZE keep `REINDEX` and `ANALYZE`, at their first token.
  - Three names that were shared are apart now, in every statement: `EXPLAIN QUERY PLAN` at the EXPLAIN, where it was `EXPLAIN` (EXPLAIN alone stays `EXPLAIN`); and `INDEXED BY` and `NOT INDEXED`, each at its first token, where both were `INDEXED BY or NOT INDEXED`. The brief asked for a name of its own for each, and with indexes in the slices the two tell different things: INDEXED BY names an index.
  - Syntax errors, which the pass gives as SQLite gives them: an empty list, `near ")": syntax error`; `create temp index`, `near "index": syntax error`; a schema on the table; WITH before CREATE INDEX, `near "create": syntax error`; and `drop index i, j` and `drop index i on t`.
  - Facts of SQLite for the builder of the engine, each checked by `checkCreateIndex` and `checkDropIndex` in the tests of the pass, on a table whose names are those of the statement with the case swapped. CREATE INDEX gives its errors in this order: `no such table: main.t`, with `main.` before the value of the name of the table, also for a name in double quotes (`no such table: main.No Such`); then `there is already a table named i`, with the value of the name of the index as the statement writes it, for a table of the name in any case, the table of the statement among them; then `index i already exists`, with that value too, for an index of the name in any case on any table; then each column in the order of the text, where the first that the table does not have gives `no such column: z` for a bare name, and `no such column: "z" - should this be a string literal in single-quotes?` for a name in double quotes, as in WHERE. Each has the code 1. Measured with the binding, and not checked by the tests of the pass: `no such column` has the offset of the name, the others -1. DROP INDEX gives `no such index: i`, with the value, code 1, offset -1, also when a table has the name. Measured with the shell only: `drop table` drops the indexes of the table with it, and a table of the same name and an index of the same name can be created after; a CREATE INDEX or a DROP INDEX in a transaction that rolls back is undone with it; SQLite's index of a WITHOUT ROWID table has the columns of the index and then those of the primary key that the index does not have already (`isDupColumn`), so an index `(b desc, a)` on a table of the primary key `a` has the key `b desc, a` and nothing after it; an index on a table with rows is built from them, and it is not unique, so no row can make it fail.
  - `stmttest`: the positions `IndexName`, `IndexTable`, `IndexColumn`, and `DropIndex`. The pool of `IndexColumn` is checked as that of `SelectColumn`, with `no such column`: 84 keywords, those of the select list. That of `IndexName` has 88 keywords, `IndexTable` 89 (`if` too), and `DropIndex` 88; `TestCheck` checks every keyword in the five places against SQLite and the pools. The kinds `KindCreateIndex` and `KindDropIndex`. `Generator.Indexes` makes one statement of a kind at random in Indexes a create index or a drop index, each one time in two, drawn after `Changes`; a create index has from 1 to `Columns` other columns, or 1 without `Columns`, each descending one time in three and otherwise with ASC one time in two. The hook `Generator.CreateIndex` gives the columns of a create index of a name on a table. With `Indexes` at 0 and the hook nil, the generator draws as before: a dump of 54,900 lines of statements, calls, and arguments of `Generator`, in five settings, and of `Sequence`, from 30 seeds, is the same on the code of `main` and the new code, byte for byte. The pass's tests set `Indexes` to 4; `stmttest.Sequence` and `stmttest.Others` are unchanged, so the tests of the engine and the driver draw the same calls.
  - The pinned numbers of the pass's generated tests moved, only because the generator draws other random numbers with `Indexes` on: `TestGenerate_mutants` from 64 to 39 syntax errors and from 196 to 153 not supported where SQLite does not say, and `TestGenerate_nearMisses` from 2,054 to 1,531. A throwaway test grouped the excused texts by SQLite's message: every one is of a CREATE TABLE, none of an index, and 261 of the 2,000 statements of the near misses are CREATE TABLE where 349 were. The corpus, its mutants, and the grammar have supported CREATE INDEX texts now, and their pinned numbers did not move.
  - The engine runs both statements since its step of slice 9, so `indexRefusal`, its test, the call of `engine.Check` in the driver's `check`, and the `checkText` wrappers of the tests are gone. A create index or a drop index that the pass does not support keeps the name and the offset of what it does not support.

## The core

- **Decisions of the core step of indexes, slice 9, by its builder on 2026-11-20, built, for the lead to confirm.** The agreement with Markus of that day: the log holds only the definition of an index, the cache holds a real index of SQLite, the engine picks the index and the core scans exactly that one, and the layout of the cache is version 3 with no upgrade. What it left open was decided by SQLite's behaviour and the agreed rules. Each fact of SQLite here was found with the pinned shell or is checked by a test of the core.
  - The commit format. `Change` has two more kinds, `create_index = 5` and `drop_index = 6`. `CreateIndex` holds `index`, the name, `table`, and `columns`, each an `IndexColumn` with `column`, a position in the table's columns as in `UpsertRows`, and `descending`, which a column in ascending order is without, as `nullable`. `DropIndex` holds `index` alone. The version of the format stays 0: a new kind is a new member of the `oneof`, which a reader of before refuses as one of a newer version.
  - A drop table drops the indexes of its table, and the commit object does not list them: the reader derives it. SQLite drops them itself, a list could only disagree with the cache, and a drop table does not list its rows either.
  - The order within a commit object. Replay applies the changes in their order, as before, and checks each against the cache as it is then, so a create index after the create of its table, a create and a drop of one index, and a drop and a new create of a table with another index all apply. The net effect that `Tx.Commit` writes is: the drops of the indexes that were there at the start and that the transaction dropped by name, in that order; then the tables as before; then the indexes that the transaction created and that are there, in the order of their creation. The doc comment of `Tx.spoolCommit` says why every change then finds what it needs. An index that went with its table is in no drop of an index. An index that is dropped and created again, also exactly as it was, is a drop and a create, because it is then the last of its table's indexes.
  - What stops replay. The reader refuses as malformed a create index with no name, no table name, the name of its own table, no columns, a column without a position, or a column twice, and a drop index with no name. Replay refuses as a broken log (`ErrLogBroken`) a create index on a table that is not there, on a column outside the table, under the name of a table or of an index, under a reserved name, or of more than 250 columns, a drop of an index that is not there, and a create table under the name of an index.
  - The order of creation is not stored. It is the order of the rowids of the indexes in `sqlite_schema`: SQLite gives a new row the rowid after the largest one, so a later index has a larger rowid than every index that still exists, also after drops. `TestIndexes_order` checks it through drops, a rowid that is taken again, a close, and a replay, and `cacheDump` reads the order another way, from `pragma_index_list`, in every test that reads a cache and in the simulation.
  - The indexes of a table are read and checked when the table is first looked up, as its columns are, and not all at `Open`. An index that the layout does not make (unique, partial, on an expression, with a collation, with a column twice, of a constraint, or with a reserved name) then stops the instance with `ErrCacheVersion`.
  - An index has at most 250 columns (`ErrInvalid`), where SQLite takes 2,000. It is a restriction of the build, as the 250 columns of a primary key are: a scan pins each column of the key of an index with one term, the key is the index's columns and then the primary key's, and SQLite refuses a condition nested deeper than a thousand levels. The engine has to answer for it.
  - The errors. `Tx.CreateIndex` fails in SQLite's order: `ErrNoTable`, `ErrReservedName`, `ErrTableExists` (a table has the name), the new `ErrIndexExists`, and then `ErrInvalid`. `Tx.CreateTable` under the name of an index fails with `ErrIndexExists`, for SQLite's `there is already an index named`. `Tx.DropIndex` fails with the new `ErrNoIndex` for anything that is no index of the database, a table and SQLite's index of a primary key among them. After each the transaction goes on. The core takes the columns of an index as positions, so `no such column` is the engine's, which comes after `index ... already exists` in SQLite: the engine can ask `Tx.Table` and `Tx.Index` for the name first.
  - The schema for the engine: `Indexes(table)` on `Tx` and `ReadTx` gives the indexes of a table as `s4qlpb.CreateIndex`, in the order of creation, and `Index(name)` gives one. `Table` is unchanged.
  - The scan. `ScanIndex(table, IndexScan{Index, Equal, Lower, Upper, Backward})` on `Tx` and `ReadTx`; no index name means the primary key. The bounds are values: `Lower` is the smallest value and `Upper` the largest, also on a descending column, and SQLite turns them into the ends of the range of the index, because the statement compares values (`scanConditions`). A NULL in `Equal` pins a column to NULL. A bound that is NULL, and a NULL for a column that does not take it, are refused with `ErrInvalid`: the engine reads nothing for those. A row whose bounded column is NULL is within no bound, as in SQL.
  - The statement of a scan names its index with `indexed by`, and SQLite's name of the index of the primary key for the table itself; `Scan`, `ScanRange`, and the scan of a commit use the same statement now, so SQLite never picks. It orders by the columns of the key that are not pinned. SQLite compares at most 63 terms of an `order by` with an index, so a scan with more than 63 such columns reads the same rows by the same index and then sorts them; a test pins that. The sorter holds the columns of the key once, as columns of the row, so it takes the longest row that the table takes, which a test pins too.
  - The count. `RowsRead` on `Tx` and `ReadTx` is the number of rows that the cache gave the transaction's scans, one for each step, and that its gets found. The statement has no condition but the bounds, and the tests check with `explain query plan` that SQLite seeks all of them, so the rows stepped are the rows within the bounds. SQLite's own counters are not compared: the build has no `SQLITE_ENABLE_STMT_SCANSTATUS`, and the binding, which is two bindings, has no call for `sqlite3_stmt_status`.
  - The simulation creates and drops indexes, under names that tables compete for, and scans whole tables by them, in every workload. That moved every draw, so the minimums of what the workloads reach got four more entries, and `deletes of the key -0.0` left those of the full workload, where the 30 default seeds have none now; the single and the hammer workloads keep it.
  - `FuzzScanIndex` is the first fuzz test of `internal/core`, so `internal/core` is in `FUZZDIRS` of the Makefile now.

## The engine and the driver

- **Decisions of the engine step of indexes, slice 9, by its builder on 2026-11-20, built, for the lead to confirm.** The agreement with Markus of that day: the engine picks the access by fixed rules with no statistics, the order of rows without `order by` varies, and the checks compare such rows as a multiset. What it left open was decided by SQLite's behaviour and the agreed rules. Each fact of SQLite here is pinned against SQLite by `TestEngine_indexes` in `internal/engine/index_test.go`. The README of the engine has the rules and the tests in full.
  - The rules are `chooseAccess(t *s4qlpb.CreateTable, indexes []*s4qlpb.CreateIndex, conditions []condition) (access, error)` in `internal/engine/access.go`, one function of the table, its indexes in the order of creation, and the conditions, which the tests reach as `engine.ChooseAccess` and, for a statement's text, as `engine.AccessOf`. It fails only with an internal error, for two bounds of values of two types, which the check of the types refuses before.
  - A column is pinned by the first condition, in the order of the text, that pins it: `a = 1 and a = 2` pins `a` to 1, and `b is null and b = 'x'` pins `b` to NULL. The filter rejects the rows of the other condition. The bounds of the column after the pinned ones are the tightest of the conditions, and of two bounds at one value the open one is the tighter, as in slice 7. Bounds that hold no value are passed on as they are, and the cache reads nothing for them.
  - The "no row" cases are those of slice 7 and no more: a comparison with NULL, and `is null` of the primary key. `is null` of another column that does not take NULL is never true either, but it pins nothing and is left to the filter, so the statement reads the rows that its other conditions leave. The reason: `stmttest.KeyAccess`, the model of slice 7, says "a scan of every row" for it, and its counts are pinned. The storage refuses a scan that pins such a column to NULL, so the rules must never pin one.
  - A `where` that pins the whole primary key with `=` is a get, also when an index pins more columns. The first two rules do not depend on the indexes, so the engine asks the rules first without them, and reads the indexes of the table only for another answer: a point lookup and a "no row" case read no index.
  - The direction of a query is one draw, the low bit of `host.Host.Uint64`, taken when the statement is prepared to run, also for a query that then reads no row or one row. An engine with a seed of its own, `engine.Options.Directions`, draws from a splitmix64 sequence of the seed and nothing from the host. It is an option of the engine, and the public package has none for it. An update and a delete read forward. The simulation of the engine and the simulator of the site give each engine a seed from the seed of the run, the node or process, and the number of its engine, so the draws of the scheduler are those of a run without them: with draws from the host, the idle workload of `TestSimulation` and two tests of the simulator of the site failed. Every instance of the engine's tests has a seed, logs it when its test fails, and takes it from the flag `-directions`. The tests of the driver, in the root package and in the driver check, cannot set a seed: they compare rows as multisets, or accept the order of the key and its reverse, and a failure of theirs that depends on a direction cannot be had again by a seed.
  - The forced path of the tests is `engine.Path{Full, Primary, Index, Limited, Pins, Forward, Backward}`, through `Options.Path` and `Engine.SetPath`. `Full` reads every row and tests no condition for "no row", as `ScanAll` did. `Primary` scans by the primary key with the key pinned where the rules get one row. `Index` names an index, and a statement on a table without it reads as the rules say. `Limited` with `Pins` pins at most that many columns, and then bounds nothing unless the conditions pin no more. A path with a direction draws nothing, and holds for an update and a delete too.
  - A create index gives SQLite's errors in SQLite's order: `no such table: main.<table>`, `there is already a table named <index>`, `index <index> already exists`, each with the offset -1, then `no such column` for the first column in the order of the text that the table does not have, with the offset of the name and SQLite's question about quotes for a name in double quotes, and then `string or blob too big`. A drop index gives `no such index: <index>`, also for the name of a table. A create table under the name of an index gives `there is already an index named <name>`, with the value of the name and the offset -1, where a table of the name gives `table <raw> already exists`.
  - `string or blob too big` for a create index, under a lowered length limit: SQLite writes the index into its schema with `INSERT INTO 'main'.sqlite_master VALUES('index',%Q,%Q,#1,%Q);`, formatted under the limit, with the name of the index, the name of the table as the table stores it, and the text that it keeps, and refuses the statement when that text is as long as the limit or longer. The text that SQLite keeps is `CREATE INDEX ` and the text from the name of the index to the semicolon or the end, as for a table, and the pass gives it as `stmt.CreateIndex.SQL`, which its tests compare with `sqlite_schema`. `indexTooBig` in `internal/engine/errors.go` is the rule, and a test compares it with SQLite at every length of a name from 400 to 480 bytes at a limit of 1,000, in seven forms. SQLite gave the same answers on macOS and on Linux in Docker. `FuzzCreateIndex_core` creates an index of one to four columns under the lowered limit beside SQLite, with a restart and a replay, and its seeds are the lengths at which the cache needs the largest limit, at which SQLite refuses, and at which the text itself is longer than the limit.
  - An index of more than 250 columns is not supported, as `index of more than 250 columns`, at the 251st column, after every error of SQLite, `string or blob too big` among them. SQLite takes 2,000, and the storage core 250, which is `core.MaxIndexColumns`.
  - `drop table` drops the indexes of its table, and their names are free for tables and indexes afterwards. A create index and a drop index in a transaction that rolls back are undone, a statement that fails leaves the transaction open, and both give SQLite's `attempt to write a readonly database` in a read-only transaction, after the errors of the names. Neither sets SQLite's count of changes.
  - The event of a statement has `statement.access`, which is `none`, `primary_key`, `index`, or `full_scan`, for a select, an update, and a delete once the access is chosen; `statement.index`, the name of the index of an access by an index, as it was created, and of the index that a create index or a drop index names; `statement.rows_read`, the rows that the cache gave the statement, with the row that an update reads to check NOT NULL; and `statement.direction`, `forward` or `backward`, which the engine drew for a query. The kinds are `create_index` and `drop_index`, and a drop index has the empty name of a table.
  - The comparison of rows with SQLite is `answer.String` of the engine's tests, which gives the rows sorted, each row in quotes: two answers have one text only if they hold the same rows the same number of times. The driver check compares its outcomes in the same way.
  - The cache creates and drops an index under SQLite's largest length limit (`conn.createIndex` and `conn.dropIndex` through `conn.changeSchema`), as it creates a table since pull request #95, since SQLite formats the statement that writes an index into its schema under the limit. It refuses with `core.ErrInvalid` an index whose own statement, without `main.`, is longer than the limit, before anything changes and before the index reaches the log, after which the transaction goes on; replay goes through the same call. A cache that holds an index near the limit opens again, and another cache replays it: two subtests of `TestTx_tooBig` of the core, with the two indexes that the merge of the index core found. The engine answers "not supported" for an index that SQLite takes and whose statement in the cache is longer than the limit, since the engine step of slice 11: see the item on such a table in [slice-04.md](slice-04.md). No create index of up to four columns reaches it, since SQLite's own statement for the schema is longer than the cache's quotes make the text.
  - The cost of a statement in reads of the cache's schema, each a statement on `sqlite_schema` or a pragma, for the first statement of a transaction on a table with N indexes, as `TestSchemaReads` of the core pins them: 2 for a select that pins the whole primary key, as before slice 9; 3 + N for every other select, with or without a `where`, since a scan names the index of the primary key and the choice of an access reads the indexes; 3 + N for an insert, an update, and a delete, since the check that refuses a foreign index runs before a row is written. A later statement of the same transaction on the same table reads nothing more.
  - The fake of the fuzz tests, `memory`, holds the definition of an index and sorts the rows of the table for a scan by it, so the fuzz tests on it compare a second way to the rows of an index scan with SQLite.
  - The equivalent mutants of `keyAccess` and of `openBounds.scanRange` left `internal/sql/mutation/equivalent.txt` with the functions, and the two of `build.bind` whose reason was that the choice never fails: it can fail now, when the storage cannot give the indexes.

## The mutation testing

- **Decided by the builder of the mutation testing of slice 9 on 2026-11-21, built, for the lead to confirm.** The results and the survivors are in [the README of the runner](../../internal/sql/mutation/README.md#the-indexes-of-slice-9), the equivalent mutants in a section of `internal/sql/mutation/equivalent.txt` of their own.
  - A fault, fixed: the event of a query in a transaction had `statement.access` and no `statement.direction`, which the README of the engine promises for every query; `Conn.queryIn` drew the direction and did not record it.
  - Code that nothing needs, removed: the check of rule 4 in `engine.chooseAccess` (the winner that pins and bounds nothing is the primary key, whose access is the scan of every row), the parameter `byNull` of `engine.pinOf`, the bounds of `core.conn.scan`, and the refusal of an index without columns in `core.conn.loadIndexes`, which SQLite never gives. `core.conn.lookUpIndex` reads the owner of an index with LIMIT 1.
  - The planted bug `convertReal` was found by 8 of 200 seeds of the hammer workload, since the create indexes and drop indexes of the sequence take turns of the inserts that it needs (11,096 inserts in 200 seeds against 14,509). The hammer workload's sequence is `stmttest.Sequence.Mistyped` now: one insert in eight gives an integer of an INT or INTEGER column as the real of its value. Over 600 seeds, `checkOutside` and `openBound`, the other bugs of the hammer workload that need inserts and selects, were found by about as many seeds with it as without: 107 and 107 for `checkOutside`, and 62 with it and 54 without for `openBound`.
  - The two tallies of updates and deletes to an upper bound of the key were lost to the random numbers of the sequences with indexes, not to a new name: their kind is `stmttest.KeyAccess`'s, by the primary key alone. `Sequence.changeConditions` bounds the key on one side, for every third of the values of an insert that it keeps, where it had the key equal to the value, with the operator from the place of the value, so that it draws the random numbers of `main`. Both kinds are required again.
  - `keepFailed` and `keepOldKey` count "is not in the log" among their violations: under either bug a transaction's acknowledged write can have a net effect of nothing on the rows that the bug left, and be in no commit object.
  - Scope: the mutants on lines of slice 9 (#92, #97, #105, #108) and of this round; lines that #107, #111, #112, and the engines of slices 10 and 11 wrote in the same functions are left to their own rounds.

## The faults of the commit and the replay of indexes

- **Decided by the builder of the fault tests of indexes on 2026-11-21, built, for the lead to confirm.** `TestTx_Commit_indexFaults` and `TestReplay_indexFaults` in `internal/core/index_test.go` close the 18 mutants that the mutation testing of slice 9 left open in the core. They fail each read of the cache (through `faultvfs`) and each write of a spool file (through `Options.WrapSpools`), one fault in each run, at the commit and at the replay of five transactions: a create index, a drop index, both, a create table with an index on it, and row changes with both beside them. No fault in the code was found.
  - The cache of the tests has `pragma default_cache_size = 1`, which SQLite keeps in the file and applies to every connection that opens it, so SQLite reads most pages from the file each time it needs them. With the default page cache, the reads of `sqlite_schema` by `conn.indexNames` and `conn.lookUpIndex` find their pages in memory and no fault reaches them, which is why the first try of the round failed elsewhere. The official SQLite build of the browser omits the PRAGMA; the tests pass there too, with fewer positions.
  - A failed read must never pass unseen: a commit that succeeds after one must have stopped the instance, and a replay that succeeds must have had no failed read. That, the check that no failure reads as a cache of another version or as a broken log, and the comparison of the commit object with the one of the same transaction without a fault kill 14 of the 18.
  - The other 4 ignore an error of `CommitWriter.CreateIndex` or `CommitWriter.DropIndex`. The writer keeps its first error and returns it at its next method and at its close, so the commit fails as before; they are in `internal/sql/mutation/equivalent.txt`.
