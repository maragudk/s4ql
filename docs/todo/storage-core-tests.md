# Tests of the storage core

Status: open. What the tests of `internal/core` and the simulation harness do not show yet, and the runs that are not done.

- **No test shows that the margin on the watcher's wait is enough.** The harness cannot make a clock run fast, so the fault that the margin is for stays out of the workloads.
- **The simulation does not reach every failure.** It does not have SQLite's "busy" or the order in which the connections open, because the scheduler runs one goroutine at a time. It also does not have a manifest that is damaged on its way, a cache that fails anywhere but at the commit after a manifest swap and at a sync (the cell with syncs, `workload.syncs`), a power loss, or clock faults on an instance that was restarted after a crash.
- **A real S3 client under simulation is not shown.** The core runs on the real client and a real bucket only in `TestClient_core` of `internal/store/s3store`, which CI runs in the job `test`, and has no faults but a manifest swap that another instance's commit makes fail.
- **A separate stress test on the real clock is not built.** It covers what only true parallelism reaches. The free-running mode runs on the fake clock of a `testing/synctest` test. Ideas to revisit later about the free-running mode are in [internal/sim/README.md](../../internal/sim/README.md#ideas-to-revisit-later).
- **The planted bugs were counted over 1000 seeds each, not 10000.** Over 10000 seeds they need about five and a half hours on the machine of the build.
- **Three decisions of the core have no test that can reach them.** The mutation testing on the final code changed each of them, and no test failed; the list is in [internal/core/README.md](../../internal/core/README.md). One needs a power loss, and one needs real parallelism after a crash. The third is a local failure of the rollback at the end of a read, which no file system can cause: SQLite ends a read transaction through functions that return nothing, so only out of memory could reach it. A test could reach it only with an error that is made up, not with a file that fails.
- **The clean runs of the planted bugs repeat each other.** Several bugs share a workload, so 40 of the clean runs of the first 10 seeds are the same as others. Each distinct clean workload could run once, or each bug could get its own seeds.
- **The minimums of what each workload of `TestSimulation` reaches are a snapshot.** They are a quarter of what the default seeds reached on 2026-11-18. A change to the core or to a workload that moves the faults between seeds can make one fail without a fault in the core; it is then set again from the logged counts, and the change is checked for what it switched off.
- **An adversarial review of the storage core with the `agy` CLI and the codex CLI was tried on 2026-11-26; when such reviews run is not decided.** Markus on 2026-11-24: "You now also have access to the `agy` CLI. We might want to do some adversarial reviews with it later, together with the codex CLI." The review covered `internal/core`, `internal/store`, and `internal/format`, gave each model the spec's rules as the properties to break, and had maragubot check every claim and reproduce what it could. The note is [research/adversarial-core-2026-11-26.md](../research/adversarial-core-2026-11-26.md). Of 16 claims, 4 were confirmed faults, 10 were true only on paper, 1 was already recorded, and 1 was wrong; the two models found nothing in common. Three of the confirmed faults and the cheap hardening from the claims that were true on paper were fixed on 2026-11-26 on the branch `core-hardening`; what was done is in [internal/core/README.md](../../internal/core/README.md) and the diary [2026-11-26-core-hardening.md](../diary/2026-11-26-core-hardening.md).
  - **Open: two transactions whose commit objects have the same bytes are both acknowledged.** The name of a commit object does not identify one transaction, and `Tx.inLog` takes it as if it did. It needs two wall clocks that read the same nanosecond. A random value in the header would make every name unique, which changes the commit format and is Markus's to decide. The failing test is `TestAdversarial_identicalCommits` in `internal/core/adversarial_test.go` on the branch `adversarial-core`; it is not on `main`.
  - **How it ran:** codex refused two runs as a "possible cybersecurity risk" after reading for about 140,000 tokens, also with "adversarial" and "attack" taken out of the prompt, and answered when a resumed session asked only for its final answer. agy ran for about 45 minutes. Open: when such a review runs, and whether codex gets a higher effort or a narrower scope.
- **More kinds of disk failure in the simulation are proposed, and none is decided.** Markus on 2026-11-24 asked to check out [Nightmare mode](https://antithesis.com/blog/2026/nightmare-mode/), a post by Antithesis, for adding error modes as disk failures. The note is [research/nightmare-mode.md](../research/nightmare-mode.md). Today `TestSimulation` fails the cache only at the buggify point in `Tx.commitCache`, crashes as a process kill, and runs with `synchronous = off`; `faultvfs` is used by scenario tests, and by the cell with syncs of the planted bug `ignoreCheckpointError`, which fails one sync at a time and changes nothing else. The gap that the note found, a failed sync that never stopped the instance, is closed: the cache runs with `synchronous = full`, and the core runs its checkpoints itself and stops when one fails ([cache-checkpoints.md](cache-checkpoints.md)). Proposed, most likely to find a fault first:
  1. A failed sync that leaves pages clean and unpersisted, then an eviction or a power loss, through a VFS that keeps the volatile and the durable state apart. It would show whether the second try of SQLite's checkpoint at the close, after a failed one, can copy pages that went back to older bytes: see [cache-checkpoints.md](cache-checkpoints.md).
  2. Random I/O errors and `SQLITE_FULL` in `TestSimulation` through `faultvfs` and `Options.WrapSpools`, judged by the checks that exist and by `run.stopped`. Planted bug: a local failure in replay reported as `ErrLogBroken`.
  3. Power loss tied to a disk operation (before, during, after), with syncs on; the restart must be at a commit of the log at or before the crash, with the model's rows. Planted bug: `synchronous = off`, the surviving mutant.
  4. Torn writes inside one write, as a variant of 3. Mostly retests SQLite.
  5. A slow disk as time, by a sleep of the host around calls into the cache. No planted bug found yet.

  The post's out-of-order completion and partly applied operations do not apply, because the scheduler never has two goroutines in SQLite.
