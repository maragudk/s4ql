# The order in which an update changes its rows

The piece of work that makes an update change its rows in SQLite's order, so that an update of which two rows fail with different errors gives SQLite's error. The adversarial review of 2026-11-26 found the fault (`docs/research/adversarial-codebase-2026-11-26.md` on the branch `adversarial-codebase`, agy 2.2): with an index on `a`, `update t set x = nx, y = ny where a > 0` gave `NOT NULL constraint failed: t.x` in s4ql and `t.y` in SQLite, and with a row that is too long in place of the second NULL, `19/1299` in s4ql and `18: string or blob too big` in SQLite.

## Step 1: what SQLite does, measured

Measured on 2026-11-26 with the shell of SQLite 3.54.1, on `t (k int primary key, a int, b int, x int not null, y int not null, z int not null, nx int, ny int, nz int) strict, without rowid` with the indexes `ia (a)` and `iab (b, a)`, or `iad (a desc)`, and three rows of which each gives NULL to a column of its own that does not take it, so that the error names the row that SQLite changed first. `explain query plan` gave the access. The source of SQLite says the same (`sqlite3Update` in `update.c`, `sqlite3DeleteFrom` in `delete.c`, and the one-pass part of `sqlite3WhereBegin`).

- **An update that SQLite can run in one pass changes each row when its access finds it,** so the rows change in the order of the access: of the primary key for a lookup or a range of the key and for a scan of the table, and of the key of the index for an equality or a range of an index, as the index holds it, so backward for a column of the index that is `desc`. Within the rows that an equality pins, the order is that of the rest of the key of the index, and then of the primary key. SQLite reads an update without ORDER BY forward, always.
- **SQLite runs an update in one pass unless one of these holds,** and then it collects the keys of the rows that it finds first, and changes the rows in the order of the primary key, whatever the access:
  - the update sets a column of the primary key, also to itself, as in `set k = k`;
  - the update sets a column of the index that its access reads by, also to itself (a column of another index does not count);
  - the WHERE has a subquery (a subquery in SET does not count);
  - the statement has RETURNING, which SQLite runs as a trigger;
  - (outside what s4ql supports: a trigger, a foreign key, `or replace`, a nested statement.)
- **A row in one pass is found, checked, and written before the next row is read,** so an error of the WHERE of a later row (SQLite's `string or blob too big` of an expression with a column) comes after the error of an earlier row's SET. With two passes, every WHERE is evaluated before any row changes.
- **The rows of RETURNING come in the order of the primary key,** for an update and a delete, by every access measured: the primary key, its range, an index with an equality, an index with a range, a scan, and a scan through an index. That follows from the rule above: RETURNING is never one pass.
- **A delete can fail on no row in what s4ql supports:** it has no trigger and no foreign key, and RETURNING gives columns alone, so the only error of a row is one of its WHERE, whose message is the same for every row. Its order decides no error. SQLite runs it in one pass under the same rules, without the one on the columns that the statement sets.
- **`changes()` after a statement that fails partway** is 0 for a constraint error and a record that is too long, whatever row failed, as SQLite sets it when it rolls the statement back (the pair checks this already), so the order does not change it.

## Where SQLite's planner decides, and the engine cannot know it

The order of a one-pass update is that of the access that SQLite's planner chooses. The engine's rules (`chooseAccess`) agree with it where one candidate is better by the rules, but SQLite chooses by its estimate of costs, and differs from the rules here, all measured:

- **A scan of every row.** For an update or a delete of a table without a rowid, SQLite reads every row through an index, in the order of the index, where the index holds every column that the WHERE names (none for an update without WHERE) and is narrower than the table by its estimate of the widths of the columns: `update t set x = nx, y = ny` reads by `ia`. The engine reads every row by the primary key. With two such indexes SQLite takes the narrower, and of two that are as wide the one created last.
- **A tie between two indexes.** With `ia (a)` and `ib (b)`, `where a = 1 and b = 1` and `where a > 0 and b > 0` read by the index created last in SQLite; the rules take the one created first.
- **Two bounds against one.** `where k > 0 and a > 0 and a < 9` reads by `ia` in SQLite, which bounds it on both sides; the rules take the primary key.
- **`is null` against `=`.** `where a is null and b = 1` reads by `ib` in SQLite; the rules take `ia`, which they count as pinned by `is null`.
- **`is not null`.** `where a is not null` is a range of `ia` in SQLite; the rules bound nothing by it.

## Step 2: what the engine does, and what the generated checks reach

Decided by the builder on 2026-11-26.

- **The engine follows both rules** (`changeOrder`, `build.changeOrder` in `internal/engine/operator.go`). In one pass, it changes the rows in the order of the key of the access that the rules choose (`chooseAccess`), forward: for an index, the columns of the index in their directions and then the primary key, as `core.IndexKey` gives it. Otherwise, and for a delete, in the order of the primary key. The order is that of the rules' access also where the tests force a path, so that the error of a SET does not depend on the path; under a forced path the engine looks the indexes up once more for it. `TestEngine_updateOrder` checks each rule above against SQLite, with the instance by the rules and the one that reads every row.
- **The keys of an update in one pass by an index go into a set of the core in the order of the index,** `core.Tx.KeysBy`. Its first read numbers the keys with `row_number()` over that order into a second temporary table, under the largest length limit, as a sort of the cache is, and then reads them one at a time by their number, so that no statement on the set is open while a row changes. The set takes no key after that. An update in the order of the primary key keeps `core.Tx.Keys`.
- **In one pass, an error of the WHERE of a row comes after the changes of the rows that the scan found before it:** `changeRows` stops at the first evaluation error or `string or blob too big` of the conditions, changes the rows that it has, and gives the first error of those, or else that of the WHERE. Where a forced path reads the rows in another order than SQLite, the rows before are those of the path, as the rows whose WHERE is evaluated at all already depend on the access.
- **RETURNING.** SQLite gives the rows of RETURNING in the order in which it changed them, which is always the order of the primary key, since RETURNING makes two passes. The engine's forward order is that order, and its backward order the reverse; `pair.checkReturned` already requires both. So SQLite's order is matched where the engine draws forward, and nothing changed there.
- **Events, counts of rows read, and `changes()`** do not change: the scan reads the rows by the same access as before, the set reads no row of the table, and SQLite's count after a failed update is 0, whatever row failed.

## What the generated checks did, and do now

- **Before: the workload never reached the case, and no excuse hid it.** In a default run of `TestDifferential`, 38 updates failed with `NOT NULL constraint failed` and 6 with `string or blob too big` by an index, but in none did the first row to fail in SQLite's order differ from the first in the order of the key. Every row of a generated update that fails gets NULL from one literal, or from one column of the row, so its failing rows fail alike. An update of two such columns from two different columns that take NULL needs a table with two columns that do not take NULL and two of their classes that do, which the shapes of the profiles rarely have. `pair.recordSlips`, the one rule that ran rows one at a time, ran them in the order of the key, and now runs them in the engine's order.
- **Now: `pair.checkUpdateOrder` checks the order of every update that SQLite fails for a row,** and counts "update whose first row to fail is another in SQLite's order than in the order of the key" where the first row that fails in SQLite's order, changed one row at a time in SQLite (`pair.firstError`), is SQLite's error and another than in the order of the key. SQLite's order comes from its plan of the statement (`explain query plan`) and the rules of one pass above (`pair.changeOrderOf`). The engine must then give SQLite's error, except where SQLite's planner reads by another access than the rules' (`excusedPlannerOrder`), or SQLite runs the statement with the values of its subqueries in their place, in one pass, where the engine runs it in two: the engine's error must then be that of the first row that fails in its order, changed one row at a time in SQLite. `TestPair_updateOrder` checks the count and the excuse.
- **Open: the workload does not reach it yet,** so the kind is not required in `testdata/reached/TestDifferential.kinds`. A first attempt, which made one SET of the profile `arithmetic` in four copy a column that takes NULL into each column that does not, still reached it 0 times in a default run, for want of tables with enough such columns, and moved pinned counts of every profile that runs arithmetic, so it was taken back. The next step is a generator of its own for it, for a fresh builder: a table with two or three columns that do not take NULL, each with a column of its class that does, rows with NULL in different ones, an index whose order runs against the key, and an update of those columns by a range or an equality of the index and without WHERE, which then makes the kind required.

## Open: where SQLite's planner decides

The cases of "Where SQLite's planner decides" above are not matched: in each, the engine changes the rows in the order of the rules' access, and SQLite in that of its own. `excusedPlannerOrder` excuses them in the generated checks, checked row by row in each order, and no test requires SQLite's error for them. The smallest statement: `create table t (k int primary key, a int, x int not null, y int not null, nx int, ny int) strict, without rowid`, `create index ia on t (a)`, the rows `(1, 20, 1, 1, null, 1)` and `(2, 10, 1, 1, 1, null)`, and `update t set x = nx, y = ny` gives `NOT NULL constraint failed: t.y` in SQLite, which reads through `ia`, and `t.x` in s4ql. To match them, the rules of the access of an update would have to be SQLite's estimate of costs: for a scan of every row, the width of each index and of the table by the declared types of their columns (`estimateIndexWidth` and `estimateTableWidth` in SQLite), with the index created last first among equals. That is a question of design for the lead: whether the rules of the access may follow SQLite's costs for an update, or whether the order of a one-pass update stays that of the rules.
