# Slice 13: `order by` and `limit` on `select`

The decisions and notes of the builders of [slice 13 of the roadmap](../roadmap.md#slice-13-order-by-and-limit-on-select).

## The statement pass

- **Decisions of the statement pass of slice 13, `order by` and `limit` on `select`, by its builder on 2026-11-21, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell or the binding, and the tests of the pass check it against SQLite: `checkWhere` and `checkOrder` on every supported text, and the subtests of `TestCheck` named below. The README of the pass has the forms token for token.
  - The fields are `stmt.Select.OrderBy`, a list of the new type `stmt.OrderColumn`, with `Name stmt.Name` and `Descending bool`, as `stmt.IndexColumn` has them, in the order of the text, and nil for a select without ORDER BY; and `stmt.Select.Limit`, a `stmt.Term`, a literal `stmt.Integer` from 0 to the largest of 64 bits or a parameter, with its span, as a value of a condition is, and the zero Term, which is neither, for a select without LIMIT, as the value of a test for NULL is. `stmt.Select.Limited` says whether there is a LIMIT. A pointer was not taken: no statement holds one, and the statements are compared and printed by value. The keywords ORDER, BY, and LIMIT have no offset of their own; `engine.orderLimitRefusal` finds them as the last token of their kind before the first column and before the number.
  - Parameters are numbered in the order of the text: those of WHERE, then the `?` of LIMIT. `stmt.Select.Parameters` counts it. `select v1 from t1 where v2 > ? order by v1 limit ?` has the parameters 1 and 2.
  - A column of ORDER BY need not be in the select list. SQLite accepts it, and goqite's receive needs it: it selects `id` and orders by `priority desc, created`. With `select *` the columns are those of the table.
  - A column that ORDER BY names twice, as `stmt.Name.Fold` compares names, is not supported, as `column named twice`, at the later name, as for the list of an insert, the SET of an update, and the columns of an index. SQLite accepts it and orders by the first: `order by a, a desc` gives the rows of `order by a`, so the later one orders nothing.
  - A name in brackets or backticks in a list of columns, of an insert, a SET, an index, or ORDER BY, is `name in brackets` or `name in backticks`, also where a name before it has the same fold: `order by "[v]", [v]` names `[v]` and `v`, which the pass gave `column named twice` before (found in the review of this step).
  - A column that the table does not have is not decided here, since it depends on the database. SQLite gives `no such column: x` after the names of the select list and of WHERE, a missing column of a test for NULL included, and then for the first missing column of ORDER BY in the order of the text; a name in double quotes gets `no such column: "x" - should this be a string literal in single-quotes?`; `no such table` comes before all of them. An alias does not exist yet, so `order by x` where no column is `x` is that error.
  - Each form of an ORDER BY term that SQLite accepts and slice 13 does not is not supported at the start of the term, under a name of its own, as for a column of CREATE INDEX: `ordering term other than a column`, for every literal, parameter, and expression, such as `1`, `0`, `99`, `-1`, `0x1`, `1.5`, `'v'`, `x'00'`, `null`, `?`, `current_time`, `v + 1`, `-v`, `abs(v)`, `cast(v as int)`, and `(select 1)`; `parentheses` for `(v)`; `column with the name of a table` for `t.v` and `main.t.v`; `COLLATE` for `v collate nocase`; `TRUE or FALSE`; `name in brackets`, `name in backticks`, and `empty name`. NULLS FIRST and NULLS LAST are `NULLS FIRST or NULLS LAST`, at the NULLS, also after DESC. SQLite reads an integer literal that fits 32 bits as the position of a result column, also in hex, after a sign, in parentheses, or with COLLATE: `order by 2` orders by the second result column, and `0`, `99`, `-1`, and `2147483647` give `1st ORDER BY term out of range - should be between 1 and N` when it prepares, on a database with the table; `2147483648`, `-2147483648`, `1.0`, `'a'`, `?`, `null`, and `true` are constants that order nothing. A string in single quotes is not a name in ORDER BY, as it is in CREATE INDEX: `order by 'a'` orders nothing.
  - Syntax errors, which the pass gives as SQLite gives them: `order by` without a column and `order by v,` (`incomplete input` at the end of the text), `order by v asc desc`, ORDER BY twice, LIMIT before ORDER BY, LIMIT twice, `limit` without a number (`incomplete input`), and OFFSET without LIMIT, `select * from t offset 2`, which is `near "2": syntax error`, since SQLite reads `offset` there as an alias of the table. ORDER BY and LIMIT on an update and a delete stay `near "order": syntax error` and `near "limit": syntax error`: the pinned build lacks `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`.
  - LIMIT takes a decimal integer literal without a sign that fits in 64 bits, with leading zeros or without (`007` is 7), 0 included, or a plain `?`. Every other number of LIMIT is not supported, at its first token: `negative LIMIT` for a `-` before anything (`-1`, `-0`, `- 5`, `-?`), `+ sign`, `LIMIT other than an integer` for a real, string, blob, or NULL literal (`1.5`, `1.0`, `1e2`, `'5'`, `x'05'`, `null`), `hex literal`, `integer outside 64 bits`, `number with a digit separator`, `current date or time`, `TRUE or FALSE`, `parentheses`, `numbered parameter`, `named parameter`, and `LIMIT of an expression` for anything else, such as `1 + 1`, `~1`, `abs(1)`, and a name, which SQLite refuses with `no such column` whatever the table holds. LIMIT with OFFSET is `OFFSET`, at the OFFSET, and `limit 2, 1`, whose first number is the offset, at the comma. Why: SQLite converts the number when the statement runs, as OP_MustBeInt does: a real or a text that holds an integer is that integer (`1.0`, `1e2`, `'5'`, `'2.0'`, `0x5`, `1_0`, `true` all limit), every other value is `datatype mismatch`, code 20, at the first step, also on an empty table (`1.5`, `'x'`, `null`, `x'05'`, `9223372036854775808`, `current_time`), and a negative integer is no limit (`-1`, `0xffffffffffffffff`, `-9223372036854775808`, `-1.0`, `'-1'`). By the rule of exact types, the number of rows is an integer, so a literal of another type is refused before it runs, and a negative number, which reads as "at most -1 rows" and means "every row", is refused too. `limit 0` gives no row, in SQLite and in s4ql.
  - For the engine: an argument of a `?` of LIMIT, which only the run sees, should follow the same rule, so that a literal and an argument agree: an int64 from 0 runs, and a negative int64 and every argument of another type are refused. SQLite would run a negative int64 as no limit, a float64 that holds an integer (`2.0`, `-0.0`) and a string that does (`"2"`, `" 2 "`, `"2.0"`) as that integer, and refuse every other float64, string, []byte, and nil with `datatype mismatch`. Which error the engine gives for each is the engine builder's to decide; the rule of exact types of the conditions is the model.
  - `stmttest.Generator.OrderBy`, 0 by default, and the hook `stmttest.Generator.Order`: with OrderBy, one select in OrderBy has an ORDER BY of from 1 to Columns+1 columns, 1 or 2 without Columns, each another name from the pool of `SelectColumn` or one time in three a column of the select list or of a condition, with ASC, DESC, or neither, and, drawn apart, one select in OrderBy has a LIMIT, of 0 to 5 one time in two and otherwise of `stmttest.Integer` with its bits turned over if it is negative, with leading zeros now and then, or a `?` with its argument, after those of WHERE. The hook gives the columns and the LIMIT of a select whatever OrderBy is. With OrderBy 0 and no hook, the generator draws nothing more: a dump of 73,800 lines, `%#v` of every statement and call of `Generator.Statement` and of `Generator.CallOf` of every kind in six settings, three of them with hooks, and of `Sequence.Next` with and without `Sequence.Indexed`, over 30 seeds, was the same byte for byte before the change of the generator and after it. The pass's own tests set OrderBy to 3; `Sequence` writes no ORDER BY and no LIMIT, and the engine's and the driver's tests set no OrderBy.
  - The numbers that the pass's tests pin moved only by the generator's draws: `TestGenerate_mutants` from 27 to 41 syntax errors and from 150 to 131 not supported where SQLite does not say, and `TestGenerate_nearMisses` from 1,979 to 2,089. With OrderBy 0 they are 27, 150, and 1,979 again. A tally by SQLite's message found create tables only (`duplicate column name`, `unknown table option`, `generated columns cannot be part of the PRIMARY KEY`, `AUTOINCREMENT is only allowed on an INTEGER PRIMARY KEY`, `table "t" has more than one primary key`, `no such collation sequence`, `non-deterministic functions prohibited in index expressions`), and one select whose WHERE a mutant turned into ON, with `a JOIN clause is required before ON`, an error of a grammar action of SQLite that the oracle does not say, as for the create tables. The corpus and the grammar keep their numbers.
  - Until the engine runs slice 13, `engine.orderLimitRefusal`, called in `engine.check`, gives a select with ORDER BY or LIMIT the error that the pass gave it before: `s4ql: not supported: ORDER BY clause` at its ORDER, or for a select without ORDER BY `LIMIT clause` at its LIMIT. A text with a token in ORDER BY or LIMIT that the pass refuses gets the pass's error for that token, where before it got the one for the clause: `order by 1` gives `ordering term other than a column`, `limit -1` `negative LIMIT`. `TestCheck_orderLimit` in `internal/engine/orderby_test.go` pins it, and `orderedOrLimited` there lets the differential tests of the engine take the refusal for a text that is not supported. The driver's `Prepare` calls `stmt.Check` alone, so it takes such a text, and its first run gives the refusal; `TestPrepare` in `conn_test.go` refuses `group by` after WHERE at its prepare in place of `order by`, and `checkNotSupported` of `internal/sqlite/crosscheck/drivercheck` takes the refusal of the engine for such a select.
- **Facts of SQLite for the builder of the engine of slice 13, measured by the builder of its statement pass on 2026-11-21.** The subtests "should order a column of each type of a strict table as SQLite does", "should limit as SQLite does", and "should give SQLite's errors for ORDER BY after those of the select list and of WHERE, in the order of the text" of `TestCheck` pin the order of NULL, the order within a type, the refusal of a strict column, the LIMIT of each kind of argument, and the order of the errors; the order of rows that tie, the conversions of a strict column, and the plans were measured with the shell only.
  - NULL sorts first in ASC and last in DESC, in a column of every type, INT, REAL, TEXT, and BLOB, of a strict table.
  - Within a type: integers by value, `-9223372036854775808` first; reals by value, and `-0.0` and `0.0` compare equal, so their rows tie (a `-0.0` that an insert of SQL stores in a REAL column reads back as `0.0`); texts by their bytes, the BINARY collation, so `''` < `'A'` < `'B'` < `'a'` < `'a b'` < `'ab'` < `'b'` < `'z'` < `'É'` (C3 89) < `'é'` (C3 A9) < `'ÿ'` < U+FFFD < `'😀'`; blobs by their bytes and then their length, `x''` < `x'00'` < `x'01'` < `x'0100'` < `x'7f'` < `x'80'` < `x'ff'`.
  - A column holds one type and NULL, so values of two types never meet in ORDER BY: a strict INT or REAL column refuses a text, a TEXT column a blob, and a BLOB column an integer, with `cannot store TEXT value in INT column t.v` and code 3091, `SQLITE_CONSTRAINT_DATATYPE`; it converts an integer to the text or the real it stands for, which the rule of exact types of s4ql refuses before. In a column of type ANY, which s4ql has not, NULL < numbers < texts < blobs.
  - SQLite gives rows that tie in the order in which it reads them, key order on a plain scan, in ASC and DESC alike: `order by v desc` with `v` 1, 1, 1, 0 for the keys 1 to 4 gives the keys 1, 2, 3, 4. s4ql varies them, by the spec.
  - LIMIT: 0 gives no row; a negative number, `-1` or `-9223372036854775808`, gives every row; a number above the number of rows and `9223372036854775807` give every row.
  - An argument of `limit ?` through the binding, on four rows: an int64 as above; a float64 `2.0` limits to 2, `-0.0` to none, `-1.0` gives every row, and `1.5`, `1e19`, `+Inf`, and NaN give `datatype mismatch` (code 20); a string `"2"`, `"2.0"`, and `" 2 "` limit to 2, `"-1"` to every row, and `"x"`, `""`, and `"0x2"` give `datatype mismatch`; a []byte, also `"2"` and the empty one, and nil give `datatype mismatch`, and so does a `?` without an argument. SQLite gives `datatype mismatch` at the first step, also on an empty table, after every error of the names. The driver refuses a bool and a time.Time as not supported before the engine (`argument` in `conn.go`), and the binding has no bind of its own for them.
  - `explain query plan` of goqite's receive, `select id from goqite where queue = ? and ? >= timeout and received < ? order by priority desc, created limit 1`, on goqite's table made strict and without rowid, gives the same plan as with `timeout <= ?`, on an empty table and with 100,000 rows in 2 queues and 3 priorities: with no index, `SCAN goqite` and `USE TEMP B-TREE FOR ORDER BY`; with goqite's index `(queue, priority desc, created)` alone, `SEARCH goqite USING INDEX goqite_queue_priority_created_idx (queue=?)` and no sort, also without LIMIT; with a second index `(queue, timeout)`, alone or beside goqite's, created before it or after it, `SEARCH goqite USING INDEX goqite_queue_timeout (queue=? AND timeout<?)` and `USE TEMP B-TREE FOR ORDER BY`. That agrees with [the research note](../research/index-selection.md). Without WHERE, `select k from t order by a limit 1` with an index `(a)` is `SCAN t USING COVERING INDEX ta`, without the index a scan and a sort, and `order by k desc` on the key a scan without a sort.

## The engine and the driver

- **Decisions of the engine and the driver of slice 13, by their builder on 2026-11-21, built, for the lead to confirm.** The tests named here pin each of them: `TestDelivers`, `TestChooseAccess_orderBy`, and `TestForcedAccess_orderBy` in `internal/engine/access_internal_test.go`; `TestEngine_orderBy` and `TestEngine_orderBy_paths` in `internal/engine/orderby_test.go`; `TestAccessOf_golden`, `TestEngine_rowsRead`, and `TestEngine_events_order` in `internal/engine/access_test.go`; and `TestScanIndex_order` in `internal/core/index_test.go`.
  - **When a candidate delivers the order** (`engine.delivers`). Take the columns that the conditions pin, with `=` or with `is null` on a column that takes NULL, out of the key of the candidate and out of the ORDER BY. The candidate delivers the order if what is left of the ORDER BY is the start of what is left of the key, column for column, with every column in the direction that the key holds it in (the scan runs forward) or every column in the other direction (it runs backward). The key is `core.IndexKey`: the columns of the index and then the columns of the primary key that it lacks, or the primary key. An ORDER BY that ends before the key does is delivered; one of pinned columns alone is delivered by every key, forward; one with a column that the key does not have next is not; one with directions mixed against the key is not. NULL needs no rule: a key holds NULL first in an ascending column and last in a descending one, which is where ORDER BY puts it, and a scan backward turns both.
  - **This is wider than the brief in one place, on purpose.** The brief took only the leading pinned columns out of the key. Here a pinned column is taken out wherever it is in the key: with an index on `(a, b)`, `where b = 5 order by a, k` is delivered, because every row that passes has one value of `b`. It is sound for the reason that the brief gives for the ORDER BY ("a pinned column has one value"), it does not depend on whether the scan itself pins the column, since the filter drops the other rows, and it makes the rule one sentence. SQLite's own planner skips only the leading ones.
  - **Not built, and sound: an ORDER BY is not cut after the primary key.** `order by a, k, b` with an index on `(a)` is sorted, though no two rows tie after `k`, so `b` orders nothing. The brief said so ("one that names a column the key does not have next is not"). It can be built later without a change of format.
  - **The choice of the access** (`engine.chooseAccess`, `engine.orderBy.better`). No row and the row of a primary key come first, as before, and deliver every order. Otherwise the candidate that pins the most leading columns of its key wins. Of those that pin as many: for a query with ORDER BY and LIMIT, one that delivers the order wins, and then one with a bound; for a query with ORDER BY and without LIMIT, one with a bound wins, and then one that delivers the order; without ORDER BY, one with a bound wins, as in slice 9, with a LIMIT or without. Then the primary key, then the index created first. So more pins win over the order also with a LIMIT: `where b = 'x' order by a limit 1` reads by an index on `(b)` and sorts, also beside an index on `(a)`. With nothing pinned and nothing bounded, an index that delivers the order wins over the scan of every row with a sort, with a LIMIT or without.
  - **Sorting is SQLite's** (`core.IndexScan.Order`, `core.table.sortTerms`). Where the access does not deliver the order, the statement that the cache runs for the scan gets the ORDER BY: each column after a unary plus, and then the columns of the primary key that the ORDER BY does not name, ascending, or all descending if the query drew backward. SQLite's sorter holds rows in memory up to the size of its page cache, 2 MB, and then in temporary files, so Go holds one row at a time, as for every other statement. The unary plus keeps SQLite from using the order of the index for a part of the ORDER BY: every sort is one sort of every row within the bounds, read before the first row is given, so "sorted" means one thing, the plan of the cache has exactly one `USE TEMP B-TREE FOR ORDER BY`, and the rows read do not depend on where the query stops. SQLite sorts whole rows, and also the rows that the filter then drops: the filter is the engine's.
  - **Rows read.** A delivered order reads the rows up to the last one that the query gives: with `limit 1`, up to the first row that passes the filter. A sort reads every row within the pins and the bound of its access, whatever the LIMIT, unless the LIMIT is 0. `limit 0` reads nothing, with ORDER BY or without, and gives the errors of the names and of the arguments all the same. A LIMIT without ORDER BY reads up to the last row that it gives, in the direction that the query drew. When a query stops before the end of a sort, the core counts the rows of the scan with a second statement, `select count(*)` by the same conditions on the same index (`core.conn.unread`), since SQLite does not say how many rows its sorter holds, and stepping through the rest would cost a call for each.
  - **Rows that tie.** Where the storage sorts, they come in the order of the primary key, or in its reverse, by the draw of the query, the same draw that turns the scan of a query without ORDER BY. Where the access delivers the order, they come as its key holds them, and the draw decides nothing; an ORDER BY of pinned columns alone is read forward. The engine still makes one draw for each query, used or not, so the n-th query of two engines with one seed has the same draw.
  - **An argument of `limit ?`** (`engine.limitCount`). An int64 from 0 runs. Every other argument is not supported, with `s4ql: not supported: argument N, which is K, for LIMIT, which takes an integer from 0`, where K is `a negative integer`, `a real`, `text`, `a blob`, or `NULL`, in the manner of the message for a value of another type than its column, and without the value. So a real that holds an integer and a text that holds one, which SQLite converts, are refused, and so are those for which SQLite gives `datatype mismatch`. The order of the errors: SQLite's for the names (the table, the select list, WHERE, then the first column of ORDER BY that the table does not have, with SQLite's message for a name in double quotes); `string or blob too big` for a value of a condition, and then for the argument of LIMIT, as SQLite gives it when it binds; "not supported" for the first value of a condition of another type than its column; and last the argument of LIMIT.
  - **The plan** has two new nodes, `engine.Order` and `engine.Limit`, under the `engine.Project`: `project`, `limit`, `order by`, `filter`, `scan`. `Order` says what the order is, and the access says how the rows get into it.
  - **The event** of a statement has `statement.order`, `delivered` or `sorted`, for a query with ORDER BY that got as far as its access. `statement.direction` is left out where the order is delivered.
  - **For the tests:** `engine.Path.Sort` makes every query with ORDER BY sort, also where its access delivers the order; without it, a forced access (`Full`, `Primary`, `Index`, with `Limited` pins) delivers the order where its key does and is sorted otherwise. `engine.Access` has `Delivered`, `Sorted`, and `By`, and its text ends in `, in order` or `, sorted`. `engine.AccessOf` answers for a select with ORDER BY and no WHERE too. `engine.Delivers` and `engine.ChooseOrderedAccess` give the rule and the choice to a model. `ordered.differs` in `internal/engine/orderby_test.go` compares rows with SQLite in order.
  - **Left as it was:** a scan whose key has more than 63 columns that it does not pin is sorted by SQLite also where the engine says that the order is delivered, as slice 9 found for a scan without ORDER BY. The rows are in the right order, and the rows read and the plan of the cache are those of a sort.
