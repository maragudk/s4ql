# Storage formats

Status: the manifest and the commit object are built in `internal/format`, with the schema in `proto/s4ql/v1/commit.proto`, and replay into the cache is built in `internal/core`. One check in CI is not built, and two questions are open. The reasons behind the formats are in [internal/format/README.md](../../internal/format/README.md).

- **`buf breaking` under its `WIRE` rules is set up when version 1 is settled.** While the formats are drafts, a change to the schema may break old commit objects.
- **Nothing produces an `UpsertRows` with only some columns yet.** The format writes and reads it, the samples cover it, and replay applies it. It is first produced when a slice of the roadmap brings `update`.
- **Replay in later slices applies results only.** When a slice brings triggers, cascades, or foreign keys, replay must not run triggers or cascades. Foreign keys cannot be checked row by row at replay, because a commit object holds the net effect and not the order of the statements.
- **Decided by the builder of the format and the core on 2026-11-19, built: a commit object never holds -0.0 in a row or a primary key,** and a reader and the writer refuse it there as malformed, because a column of the cache holds 0.0 for it. A parameter of an annotation keeps -0.0 as the caller gave it. The writer also refuses a NaN, an infinity, and text with NUL in a parameter, which s4ql never stores; the reader does not check annotations. The reasons are in [internal/format/README.md](../../internal/format/README.md).
- **Decided by the lead and confirmed by Markus on 2026-11-20, built: `Column` has `bool nullable = 3`,** which says that the column takes NULL. It is `nullable` and not `not_null`, so that the commit objects written before it, in which no column takes NULL, read right without it. The writer and the reader refuse a create table whose primary key holds a column with `nullable`, and a NULL in a primary key of a `DeleteRows`. They cannot refuse a NULL in a row of an `UpsertRows` for a column that does not take NULL, because the batch does not hold its table, so the core does that. The format's version stays 0. The reasons are in [internal/format/README.md](../../internal/format/README.md).
- **Open: whether a new lease holder keeps the unknown fields of the old lease.** `Manifest` keeps the unknown fields of a `Lease` only while the same value is changed in place, and a new `Lease` has none. The core does not keep them: a new holder writes a new lease entry.

- **Agreed with Markus on 2026-11-26, not built: the annotation of a statement is its text only.** `Statement` in `proto/s4ql/v1/commit.proto` loses its field `parameters`, and its comment on non-deterministic inputs goes: the annotation holds no parameters, no time, and no random bytes. Why: an insert passes its values as parameters, so every value was in the commit twice, in the row and in the annotation; and what a statement saw is in the rows that it wrote. A literal written into the text stays in the log; a parameter does not. Nothing is in use yet, so the format changes without a migration. The tests that run annotated statements again take the arguments from the calls that they made themselves, and a statement's time, random bytes, and subquery values from test hooks.

- **Agreed with Markus on 2026-11-26, not built: every commit object holds a random value in its header.** Markus: "a), let's add the random value to the commit object (not a UUID though)". It is 16 random bytes from the host's source of randomness, drawn once for a transaction's commit object and not a UUID: plain bytes, with no version or variant bits and no text form. Why: a commit object is named by the checksum of its content, and a writer that lost its lease while a swap of its own had no answer looks for its object's name in the log to learn whether its commit landed. Two instances that made the same change from the same parent at the same reading of the wall clock made the same bytes, so one took the other's commit for its own and both were told success: a lost update ([the review](../research/adversarial-core-2026-11-26.md), fault 1; [what others do](../research/commit-identity.md)). With the value, a name belongs to one attempt by construction. A retried upload or swap of the same commit sends the same bytes, so it still finds its own object. In the simulation the value comes from the seeded host, so runs stay deterministic. The spec's rule that a commit object is named by the checksum of its content, with no metadata in the name, is unchanged. The failing test of the fault waits on the branch `adversarial-core` (`TestAdversarial_identicalCommits`). It is built after the change of the annotation, which changes the same format.
