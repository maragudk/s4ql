# Storage formats

Status: the manifest and the commit object are built in `internal/format`, with the schema in `proto/s4ql/v1/commit.proto`, and replay into the cache is built in `internal/core`. One check in CI is not built, and two questions are open. The reasons behind the formats are in [internal/format/README.md](../../internal/format/README.md).

- **`buf breaking` under its `WIRE` rules is set up when version 1 is settled.** While the formats are drafts, a change to the schema may break old commit objects.
- **Nothing produces an `UpsertRows` with only some columns yet.** The format writes and reads it, the samples cover it, and replay applies it. It is first produced when a slice of the roadmap brings `update`.
- **Replay in later slices applies results only.** When a slice brings triggers, cascades, or foreign keys, replay must not run triggers or cascades. Foreign keys cannot be checked row by row at replay, because a commit object holds the net effect and not the order of the statements.
- **Decided by the builder of the format and the core on 2026-11-19, built: a commit object never holds -0.0 in a row or a primary key,** and a reader and the writer refuse it there as malformed, because a column of the cache holds 0.0 for it. Since 2026-11-26 an annotation holds no parameters. The reasons are in [internal/format/README.md](../../internal/format/README.md).
- **Decided by the lead and confirmed by Markus on 2026-11-20, built: `Column` has `bool nullable = 3`,** which says that the column takes NULL. It is `nullable` and not `not_null`, so that the commit objects written before it, in which no column takes NULL, read right without it. The writer and the reader refuse a create table whose primary key holds a column with `nullable`, and a NULL in a primary key of a `DeleteRows`. They cannot refuse a NULL in a row of an `UpsertRows` for a column that does not take NULL, because the batch does not hold its table, so the core does that. The format's version stays 0. The reasons are in [internal/format/README.md](../../internal/format/README.md).
- **Open: whether a new lease holder keeps the unknown fields of the old lease.** `Manifest` keeps the unknown fields of a `Lease` only while the same value is changed in place, and a new `Lease` has none. The core does not keep them: a new holder writes a new lease entry.
- **Agreed with Markus on 2026-11-26, built the same day: the annotation of a statement is its text only.** The reasons are in [internal/format/README.md](../../internal/format/README.md#annotations). The wording of the sentence in `docs/spec.md` ("Statements are kept as annotations") waits for Markus's agreement. What the builder decided:
  - **The format.** `Statement` keeps `sql = 1` and reserves the number 2 and the name `parameters`. The version stays 0, as the draft allows. A commit object written before still reads: inside an annotation the reader skips a field it does not know, so the old parameters are unknown bytes that nothing uses, and the writer refuses them as it refuses any unknown field. `Tx.Annotate` takes the text alone.
  - **The link of the tests from an annotation to its call.** The engine's simulation already writes a comment with an ID of its own into each statement that it runs, also into each statement of a text of several, and the text of the annotation carries it. `run.noteOf` takes the arguments from the attempt of that ID, and `run.verify` now requires the annotation to be the attempt's own text, from its first token to its end, which it did not check before. No hook and no field were needed. The check that replaced the comparison of the annotation's arguments with the caller's is `commitRows`: after the statements of a commit ran in SQLite with the callers' arguments, SQLite must hold each row that the commit upserts and none of a key that it deletes, so a statement that ran with other arguments is found at its commit, also where a later commit overwrites its rows. The differential tests compare two instances that ran the same calls, so they compare the annotations' texts commit by commit, and the commits' rows show the arguments that each statement ran with.
  - **The planted bugs.** `annotateNext` (the annotation held each argument plus one) and `argsFromStart` (each statement of a text annotated with the arguments of the text from its start) only got the arguments of an annotation wrong, which no longer exist, so both are removed, with their rows in the README of `internal/engine` and the four equivalent mutants of `annotateNext` in `internal/sql/mutation/equivalent.txt`, which `TestEquivalent` would otherwise refuse. `annotateText` stays, and is found first by the new check of the text. A new planted bug, `argsNext`, runs a statement of its own that changes the database with each integer argument plus one, so that `commitRows` has a bug of its own: 97 of the first 200 seeds of the profile `arguments` find it, 95 of them by `commitRows`.
