# Expressions and functions

What is agreed and not built about expressions and functions, and what is open. The short statement is in [the roadmap](../roadmap.md#expressions-and-functions). The engine evaluates arithmetic with the evaluator of `internal/expr`; [arithmetic.md](arithmetic.md) has the piece of work. The options behind the decisions are in [the feature map](../research/feature-map.md), core gap 1.

- **Agreed with Markus on 2026-11-24, built for arithmetic: an evaluator of s4ql's own.** The engine evaluates expressions itself, in Go. The cache's SQLite does not evaluate them, so the spec's rule that "SQLite does not run the application's SQL" holds for expressions too. The evaluator is checked against SQLite with generated expressions. It may support only a subset of what SQLite supports. Markus: "a, but we might want only a subset of what SQLite supports. In particular, we don't want to copy all quirks that may still be there in the name of backwards compatibility." The option that he did not take was to evaluate expressions in the cache's SQLite, in statements that s4ql writes.
- **Agreed with Markus on 2026-11-24, built for arithmetic: SQLite's answer or an error.** For every expression, s4ql gives the answer that SQLite gives, or an error, and never a different answer. Where SQLite's answer is a quirk, s4ql refuses the expression. So an application written for s4ql also runs unchanged on SQLite. Refused:
  - arithmetic on text, such as `'1' + 1` and `'abc' + 1`;
  - an integer overflow, where SQLite silently gives a float;
  - a division by zero, where SQLite gives null;
  - a comparison of values of different types by SQLite's order of types.

  An integer with a real, such as `1 + 0.5`, works as in SQLite.
- **Agreed with Markus on 2026-11-24, not built: time and randomness come from the host.** `'now'` is the host's clock, read once for each statement, so every `'now'` in one statement has the same value. This also holds inside a transaction, where each statement reads the clock again. Random bytes come from the host's source of randomness. The simulation drives both, as the spec has it for time and randomness. A commit records rows, so replay never calls such a function again. The check against SQLite gives both sides the same instant. For random bytes it compares their type and their length, and the simulation checks that the same seed gives the same bytes.
- **Decided by the lead on 2026-11-24: which operators and functions come first is decided by what is needed next,** and the others follow by need. The arithmetic `received = received + 1` in the `set` of goqite's receive is left out of [slice 15](../roadmap.md#slice-15-a-scalar-subquery-in-where), and comes after it.
- **Agreed with Markus on 2026-11-26, not built: the annotation of a statement records the time that it read and all the random bytes that it drew.** The time is one value for each statement that read the clock, and absent otherwise. The random bytes are every run that the statement drew, in the order of the calls, with no cap: all or nothing, so a statement that draws many bytes about doubles its commit. They are fields of `Statement` in `proto/s4ql/v1/commit.proto`, which has none for them yet. Replay never depends on them. The tests that run annotated statements again must not decide the format: they may take a statement's time and random bytes from the annotation, since it records them.
- **Decided by the builders of the evaluator and of the engine step of arithmetic on 2026-11-25, built: which error a refused expression gets, and when.** Arithmetic on text or a blob is "not supported", and an overflow, a division by zero, and a real result that is not finite are an evaluation error of their own. An expression without a column is computed once for each run, before any row, so its error comes also where no row is read; one with a column is computed on each row that the rule evaluates. Through the driver, an evaluation error matches `s4ql.ErrEvaluation` and its kind. [arithmetic.md](arithmetic.md#the-engine-and-the-driver) has the details.
- **Decided by the lead on 2026-11-25, built: a NULL that a column or an argument gives in arithmetic gives NULL,** as in SQLite and standard SQL, which is no quirk. The literal NULL stays refused by the pass, as `NULL in arithmetic`, since such an expression is always NULL. The evaluator computes the other operand of a NULL all the same, so its error comes where SQLite gives NULL; [arithmetic.md](arithmetic.md) has the facts.
- **Decided by the builder of the engine step of arithmetic on 2026-11-25, built: the types of an expression in SET and in a comparison.** The rule of exact types holds by four classes, integer, real, text, and blob, and the two sides of a comparison, and a value and its column in SET, must be of one class. Arithmetic never meets text or a blob, so a TEXT or BLOB column beside an expression is refused from the schema, where SQLite converts the number by the column's affinity. [arithmetic.md](arithmetic.md#the-engine-and-the-driver) has the details.
