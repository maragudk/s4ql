# Slice 8: `update` and `delete`

The decisions and notes of the builders of [slice 8 of the roadmap](../roadmap.md#slice-8-update-and-delete).

## The statement pass

- **Decisions of the statement pass of slice 8, by its builder on 2026-11-20, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell or the vendored source, and the tests of the pass check it against SQLite. The README of the pass has the forms token for token.
  - `stmt.Update` has `Table`, `Set []stmt.Assignment`, and `Where []stmt.Condition`, nil without WHERE; a `stmt.Assignment` has `Column`, a `Name`, and `Value`, a `stmt.Term` as for a value of an insert. `stmt.Delete` has `Table` and `Where`. Both have `Span`. `Parameters()` counts the `?` of SET and then those of WHERE, and the k-th `?` of the text has the number k, as SQLite numbers them.
  - The same column twice in SET, as `Name.Fold` compares names, is not supported, as `column named twice`, at the later name. SQLite takes the last value for the column, where it takes the first for INSERT; the roadmap names neither.
  - `==` in an assignment, `set v == 1`, is supported and means `=`: SQLite's tokenizer gives both `TK_EQ`, the one token that the grammar takes there. `<>` there is a syntax error.
  - A column named `rowid`, `oid`, or `_rowid_` in SET is a name like any other. In a WITHOUT ROWID table SQLite gives `no such column: rowid`, with the name as written, since it asks `sqlite3IsRowid` only of a table with a rowid. In SET a bare TRUE or FALSE is a name too, `no such column: true`, unlike in WHERE and as a value, where it stays `TRUE or FALSE`.
  - A table with a schema, `main.t` or `temp.t`, is `schema name`, as in INSERT and SELECT. SQLite takes `main.t` and gives `no such table: temp.t` for `temp.t`.
  - The new names of what is not supported: `UPDATE OR`, at the OR, for each conflict clause; `SET of a list of columns`, at the parenthesis, for `set (a, b) = (...)` and `set (a) = 1`; and `SET beyond SQLite's limit`, at the 2,001st assignment: SQLite gives `too many columns in set list` for more than 2,000 (`SQLITE_MAX_COLUMN`) while it parses, whatever the database holds, as for the other limits of slices 2 and 7. Every other form has the name of its node, as before: `RETURNING clause`, `FROM clause` for `update ... from`, `alias`, `INDEXED BY or NOT INDEXED` (since slice 9 `INDEXED BY` and `NOT INDEXED`), `WITH clause`, `EXPLAIN` (since slice 9 `EXPLAIN QUERY PLAN` for that), and for an expression in SET the name that the value of an insert gives it, such as `binary operator`, `column reference`, `function call`, or `+ sign`. A WHERE has every name of slice 7.
  - ORDER BY and LIMIT on either statement are syntax errors in the pinned build, which lacks `SQLITE_ENABLE_UPDATE_DELETE_LIMIT`: `near "limit": syntax error` and `near "order": syntax error`. The pass gives SQLite's error, as for every syntax error. The roadmap's slice 8 lists them under "Rejected as not supported, where SQLite would accept it", which this build of SQLite does not do; its text is left for the lead.
  - Facts of SQLite for the builder of the engine, each checked by `checkChange` in the tests of the pass. The errors of names come in this order: `no such table`; then the columns of SET, in the order of the text, where the first that the table does not have gives `no such column: v` with the value of the name, also for a name in double quotes, without the question about single quotes; then the columns of WHERE by the rule of slice 7, with that question for a name in double quotes. `update t set z = 1 where y is null` gives `z`. `changes()` counts every row that WHERE matches, also one whose values do not change; an update or a delete without WHERE counts every row. Measured with the shell only: an update that gives a key that another row has, `update t set a = 2 where a = 1`, gives `UNIQUE constraint failed: t.a`, as an insert of the key does, and changes nothing, also `update t set a = 3` of two rows; `set c = null` of a NOT NULL column gives `NOT NULL constraint failed: t.c`; and `set b = 1` of a TEXT column of a STRICT table stores the text `'1'`, so the exact types of slice 4 must refuse it.
  - `stmttest`: the positions `UpdateTable`, `UpdateColumn`, and `DeleteTable`, whose pools are those of `InsertTable` and `InsertColumn` exactly, and the column of a condition is from the pool of `SelectColumn`, as in a select: `TestCheck` checks every keyword in the five places against SQLite. The kinds `KindUpdate` and `KindDelete`. `Generator.Changes` makes one statement of a kind at random in Changes an update or a delete, each one time in two; an update has from 1 to `Columns` assignments to other columns, with `=` or, one time in four, `==`, and a value as a condition has one; both have a WHERE as a select without the hook has one. The hooks `Generator.Update`, which gives the assignments and the conditions of an update of a table, and `Generator.Delete`, which gives the conditions of a delete. With `Changes` at 0 and both hooks nil, the generator draws as before: a dump of 51,000 texts, statements, and arguments of `Generator` and `Sequence` from 30 seeds is the same on the old code and the new, byte for byte. `Sequence` takes its names from the new positions too, which changes no name. The pass's tests set `Changes` to 3; `stmttest.Sequence` sets neither the option nor the hooks, so the tests of the engine and the driver draw the same calls.
  - The pinned numbers of the pass's generated tests moved, only because the generator draws other random numbers with `Changes` on: `TestGenerate_mutants` from 54 to 64 syntax errors and from 284 to 196 not supported where SQLite does not say, and `TestGenerate_nearMisses` from 3,003 to 2,054. A throwaway test grouped the excused texts by SQLite's message: every one is of a CREATE TABLE, none of an update or a delete, and 349 of the 2,000 statements of the near misses are CREATE TABLE where 515 were. The corpus has 1,124 supported texts more, 590 updates and 534 deletes, and its pinned numbers did not move.
  - An update or a delete that the pass does not support gets the name and the offset of what it does not support, as every other statement does: `update t set v = 1 returning *` gives `RETURNING clause (at offset 19)`. (Before the engine ran slice 8, its `check` refused every update and delete with `UPDATE (at offset 0)`; it runs them now.) The driver's `check` in `conn.go` calls `engine.Check` after `stmt.Check`, as it did for slice 7, so `Prepare` refuses at once. `checkText` wrappers take the place of `stmt.Check` in the engine's `differential_test.go` and `simulation_test.go` and in `drivercheck_test.go`, as in slice 7. No pinned number of the engine or of `drivercheck` moved.

## The engine and the driver

- **Decisions of the engine step of slice 8, by its builder on 2026-11-20, built, for the lead to confirm.** Each fact of SQLite here was measured with the pinned shell or is pinned against SQLite in `TestEngine_update`, `TestEngine_delete`, `TestConn_Begin`, or `TestConn_netEffect`.
  - How the rows change. The engine finds the rows of an update and a delete as a select finds them, with the same scan, `keyAccess`, and filter, and the test option that makes every query read every row covers them too. It adds the key of each row that it finds to a set in the cache, `core.Tx.Keys`, while the scan runs, and then reads the keys back one at a time, each by a statement of its own that has ended, and changes the row of each (`changeRows` in `internal/engine/operator.go`). So SQLite never has a cursor open on a table that changes, which its documentation leaves undefined; a row that the statement writes, also under a new key, is never in the set, so no row is changed twice and none is missed, also when SET writes the key or the columns that WHERE reads; and no row is held in memory.
  - The rows change in the order of the key. SQLite changes the rows of a multi-row update that changes the key in the order of the key too (its second pass reads an ephemeral table in key order). The order decides only which error a failing update gives, such as `string or blob too big` of one row before the key that exists of another.
  - The order of the errors of an update: `no such table`; the columns of SET that the table does not have, the first in the order of the text, as `no such column: v` with the value of the name and without the question about quotes, also for a name in double quotes; the columns of WHERE by the rule of slice 7, with the question for a name in double quotes; `string or blob too big` for a value of SET, and then of WHERE, that is longer than the limit, the first in the order of the text, which is also the order of the parameters; "not supported" for a value of WHERE of another type than its column, as for a select; in a read-only transaction, `attempt to write a readonly database` here, as for an insert; `NOT NULL constraint failed` for the first column of SET, in the order of the table, the key among them, that gets NULL and does not take it, but only if the update finds a row, as SQLite checks it on each row that it changes; "not supported" for the first value of SET, in the order of the table, of another type than its column, whether the update finds a row or not; and, for each row in the order of the key, `string or blob too big` for a row whose record is too long and then `UNIQUE constraint failed` for a new key that another row has. SQLite gives the same, but for a record that is too long of a row after the first, which SQLite does not always measure: see the known difference of a record that is too long in an update of many rows, in [sql-front-end.md](sql-front-end.md). A delete has the errors of its table and its WHERE, in the same places.
  - The exact types of SET are s4ql's rule of the text, as for an insert, and hold also when the update finds no row, where SQLite would change nothing: `update t set v = 1 where k = 9` on a TEXT column `v` is refused. They come after NOT NULL, as for an insert, and after the read-only error. The refusal of a value of WHERE comes before NOT NULL and before the read-only error, as for a select, where it is a check of the build.
  - A literal of SET that is longer than the limit gets `string or blob too big` also when the update finds no row, where SQLite steps no value and gives no error. This is the known difference of a literal of a condition, in [sql-front-end.md](sql-front-end.md), for SET.
  - A change of the key is the delete of the old row and the insert of the new one, which the statement's savepoint takes back if a later row fails. A new key that is the old one by SQLite's comparison, such as -0.0 for 0.0, is no change of the key, and the row is written in place, as SQLite does.
  - The count of changes: an update and a delete set it to every row that they find, also one whose values an update does not change, and a delete without WHERE to every row. One that fails when it steps, with NOT NULL, UNIQUE, a record that is too long, or the read-only error, sets it to 0, as SQLite does; one that fails before, with an error of the names, of a value that is too long, or "not supported", leaves it. `RowsAffected` of the driver is this count, and `LastInsertId` stays 0.
  - The commit object: an update is the row as it is afterwards, a change of the key is that row and the delete of the old key, and a delete is the delete of the key, with no change to the format: the core's touched keys already give the net effect for each key (`TestConn_netEffect`). A statement of its own that changes no row leaves no commit object, as the core commits no transaction that changed nothing, so its annotation is not in the log.
  - The event of a statement has the kinds `update` and `delete` in `statement.kind`. No other telemetry is new.
  - The generated tests run the update of `stmttest.Others` now, which the engine refused before, and the `checkText` wrappers stayed only for the create index and the drop index of slice 9, which the engine runs since its step of slice 9, so they are gone. `stmttest.UpdateRule`, `stmttest.DeleteRule`, `stmttest.WhereRule`, and `stmttest.FoundQuery` in `rule.go` give s4ql's rule of the types for them, and `typeRule`, `typeRefusal`, and `readOnlyRule` of the engine's tests and `pair.typeRefusal` of `drivercheck` use them. The pinned count of values of another type moved from 478 to 483 in `TestDifferential`, and from 231 to 234 in `drivercheck`'s `TestGenerated`: 5 and 3 of those updates give an integer to a column of another type. No other pinned number moved.

## The generated checks

- **Decided by the builder of the generated checks for slice 8 on 2026-11-20, built, for the lead to confirm.** The checks found no difference from SQLite or from mattn, no difference between the two ways of reading rows, and no lost or wrong write.
  - The forms and the rates. `stmttest.Sequence` sets the hooks `Generator.Update` and `Generator.Delete`, which are `Sequence.update` and `Sequence.delete`, and the pools of `UpdateTable`, `UpdateColumn`, and `DeleteTable`, and leaves `Generator.Changes` at 0. Of the statements that the sequence writes itself, which are eleven calls in twelve, 4 in 24 are a create table, 10 an insert, 4 a select, 3 an update, 2 a delete, and 1 a drop table, where 4, 10, 5, and 1 in 20 were the first four and the last. An update sets from one to all of the columns of the shape, each once, in any order, and leaves the key out of two or more one time in two; one update in twelve has a name that the shape does not have in place of one. Each value is NULL one time in ten, also for the key and for a column that does not take NULL, for text or a blob of about `stmttest.LengthLimit` bytes one time in twelve of the others, so that the record of a row is too long now and then, and otherwise a value as `Sequence.conditionValue` draws one for a condition on the column: mostly a value that an insert gave the column, a neighbour, or an edge, now and then of another type, so that a change of the key meets a key that exists and one that does not. The values of an update are kept for the conditions, as those of an insert. Three updates in four and four deletes in five have a WHERE, of which one in three is the one condition that the key is a value that an insert gave it (`Sequence.changeConditions`), since most WHERE of `Sequence.conditions`, which is the WHERE of a select, find no row in a table of a few rows; the others are those of a select.
  - Both ways of reading rows, with a second engine. `pair` of the engine's tests has `other`, a second instance of the kind of its instance, in memory or on the core with the same length limit, which runs every call, through `pair.bothWays`, with every row read where the instance reads by the key and the other way round, and must give the same answer, message, and count of changes; after an update or a delete with WHERE, a select of * of its table on each must give the same rows. A second run on the same engine, which is what `bothWays` did for a select, cannot check an update or a delete, which changes what a second run would find; a second engine that runs every call holds what the first holds, also in transactions, which `txDifferential` and `FuzzChanges` begin and end on both. The select is checked by the second engine too now. The tables of both are compared with SQLite at the end of each sequence and of each transaction.
  - The cross-check of the access. `engine.AccessOf` of `export_test.go` knows an update and a delete: it builds the sink with `buildSink` on `tableOf`, now a `writer` whose writes panic, and gives the access of the scan of the sink. `reachChange` compares it with `stmttest.KeyAccess` of the select of the same conditions, which `stmttest.SelectOf` gives with its parameters numbered from 1, for each update and delete of `TestDifferential` and `TestConn_differential`.
  - The length of a literal. `pair.checkLength` holds the rule of a literal longer than the length limit for an update and a delete too, in SET and in WHERE: `string or blob too big` after the names whenever SQLite prepares the statement, and the call is not run in SQLite, as `excusedLongChange`. SQLite gives that error only when it changes a row, and turns a blob literal into NULL, which is the known difference of a literal of SET in [sql-front-end.md](sql-front-end.md). A select with such a literal stays compared with SQLite, as `pair.longCondition` says.
  - What the workload reaches. `stmttest.SetCases` names the cases of SET: a column that the table does not have, also in double quotes, the key, every column, NULL for a column that does not take it, each kind of value, and a value of another type. `reachChange` in the engine's tests and `pair.reachChange` in `drivercheck` count each update and delete by its kind, with or without WHERE, and its outcome, where "ok" is "ok, rows changed" or "ok, no row found" by the count; with arguments that s4ql refuses; the cases of SET; the cases of the WHERE as a whole of `stmttest.WhereCases`; and in the engine whether it changes every row, some, or none of a table with rows, a record that is too long, and a literal over the limit in SET or in WHERE. `TestDifferential` and `TestGenerated` require a least number of each, a third of what the run gave, and `TestConn_differential` requires the updates and deletes changed both ways, also in a read-only transaction, the commits and roll backs of a transaction whose update or delete changed rows, and the read-only error of an update and a delete.
  - `drivercheck`. Through the pool, the rows affected are compared for an update and a delete as for an insert. After each update and delete that succeeds, `pair.compareChanged` reads its table back on both sides, in the transaction where it ran. `pair.checkQuoted` checks an update and a delete with a name of WHERE in double quotes that is no column against the pinned build too, since mattn's SQLite reads it as a string; its excuse counts them. `TestGenerated` runs 250 sequences where it ran 200, so that it still reaches each outcome that it requires.
  - The simulation. An update or a delete of its own that the engine says changed no row is in no commit object, so the engine's word decided that it was not in the log. Now `run.verify` runs each such statement in SQLite, in a savepoint that is rolled back, on the state of the log that it saw, and requires no error and a count of 0 there, and that the state holds every write acknowledged before it started, as for a select. The count of changes of each update and delete that succeeded is compared with SQLite's: of its own by the run of its commit's statement, in a transaction by the run of the transaction's statements. A write transaction whose rows SQLite has at its end as at its beginning may leave no commit object, as one that inserted a row and deleted it, where the core commits nothing for a key whose row was not there before and is not there after. `TestSimulation` requires least numbers of the updates and deletes, a quarter of what the first 1,000 seeds gave.
  - The planted bugs `changeNothing`, which makes an update and a delete find no row and report 0, at the top of `changeRows`, as the review of pull request #91 planted it, and `keepOldKey`, which makes an update that changes the key leave the row of the old key, in `update.run`. Both are planted in a statement of its own and in a transaction. The engine has fifteen planted bugs now. See the README of the engine for the counts.
  - `FuzzChanges` and `FuzzChanges_core`. The first byte chooses a table `c_<type>` of one of the five types, with a key `k`, `v`, which takes NULL, and `w`, which does not, and rows at the edges of the type; the second whether the statements run in a write transaction and whether it commits; the rest builds up to four updates and deletes (`changesOf`): the columns of SET by a mask, also `x`, which the table does not have, in either order and in double quotes, with values and conditions as `FuzzWhere` builds them, through the reader `fuzzBytes` that `whereOf` uses now. The tables are compared with SQLite at the end, on both engines, and after a replay of the log for the core. A run of one minute of each found nothing, in 223,248 and 9,089 executions.
  - The pinned numbers moved, because the sequence draws other random numbers and writes updates and deletes, each with its reason beside it in the code. In the engine's `TestDifferential`: `acceptedStartedTable` from 19 to 14, `excusedArguments` from 718 to 707, `excusedArgument` from 248 to 300, `excusedType` from 483 to 576, `excusedLong` from 4 to 2, and the new `excusedLongChange` 4; the least numbers of "-0.0 literal into REAL UNIQUE constraint failed" from 6 to 2 and of "select of names with NULL ok" from 25 to 7, a third of what the run gives now, as the sequence writes fewer inserts and selects, and the select with a column that the table does not have under IS NULL, alone, is required of a delete now, since the selects no longer reach it. In `drivercheck`'s `TestGenerated`, of 250 sequences: `excusedPrepare` from 1178 to 1410, `excusedStartedTable` from 11 to 12, `excusedArguments` from 411 to 556, `excusedArgument` from 260 to 343, `excusedType` from 234 to 328, `excusedLevel` from 69 to 90, `excusedRowsOpen` from 24 to 16, `excusedTxOpen` from 24 to 39, `excusedOutside` from 58 to 72, and `excusedQuoted` from 69 to 89; the least number of "select of names with NULL ok" from 15 to 4, and "read-only transaction: insert while rows are open" is required in place of the same with a parameter, which the run no longer reaches.
