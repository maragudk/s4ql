# Several statements in one `Exec`

The decisions and notes of the builders of the piece of work "several statements in one `Exec`", which Markus agreed on 2026-11-24 ([driver.md](driver.md) had the item): several statements in one `Exec` mean the same as running them one after another, nothing is wrapped around them, and `Query` with several statements stays refused, as the lead decided. glue's migration files and fixtures and goqite's schema file are the milestone. The rule for every detail is "SQLite's answer or an error", where SQLite's answer is what `mattn/go-sqlite3` v1.14.53 does for the same `Exec`; each fact of mattn here was measured, and `TestSeveral` in `internal/sqlite/crosscheck/drivercheck` pins it beside s4ql's answer.

## The code and the hand-written tests

- **Decisions of the builder on 2026-11-25, built, for the lead to confirm.**
  - **How the text is split.** `stmt.Split` in `internal/sql/stmt/split.go` reads the statements as mattn does: the first statement of the text as `sqlite3_prepare_v2` prepares it, then the first statement of the tail, from the end of the semicolon on, until the tail holds no statement. It parses each statement once, with `parser.ParseAt`, which reads from an offset with the offsets in the whole text, and recognizes it as `stmt.Check` does. Each `stmt.Part` has its statement, with spans in the whole text, and its span of the text: from the end of the part before to the end of its semicolon, and for the last part to the end of the text. So every offset of an error is in the text that the application gave.
  - **Where the loop lives.** In the engine, `engine.Conn.ExecAll` in `internal/engine/several.go`, which the driver's `Exec` calls. `engine.Conn.Exec` is left as it was, one statement for each text, so the engine's tests, its differential test, its fuzz targets, and the simulation, which give it texts of the corpus with second statements, are not changed. Each part runs through the code of `Exec` after the check of its text (`execPlan`), so each statement is its own transaction, or a statement of the transaction of the connection, with its own event and its own annotation, as if it ran alone.
  - **Arguments.** Each statement takes as many arguments as it has parameters, in order, as mattn binds `sqlite3_bind_parameter_count` of each. Too few for a statement: the statements before it run, and it fails with an error of `ErrArguments`, `s4ql: wrong number of arguments: 1 for a text whose statements up to the one at offset 32 have 2 parameters`, where mattn gives `not enough args to execute query: want 1 got 0` after the same statements. More than the statements have: mattn drops them without an error, which s4ql does not copy; it refuses them before any statement runs, `s4ql: wrong number of arguments: 3 for a text whose 2 statements have 2 parameters`. That is known only when every statement of the text checks; a text with a statement that s4ql refuses runs the statements before it and then gives its error. A text of one statement counts its arguments as `Exec` does, with the same messages. An argument that no column holds, such as a NaN, or whose value its statement refuses, such as text for an INT column, fails its statement after the statements before it, and its error names it by its number among the arguments of its statement, as if the statement ran alone: the errors that a statement gives while it runs number its parameters so, and the review of 2026-11-25 found that a check of the values that numbered them in the call disagreed with them within one call. An argument of a Go type that s4ql does not support, such as a bool, is judged by the driver before any statement runs, and named by its number in the call, after the errors that `engine.CheckAll` gives, which are those that `ExecAll` gives before any statement runs: an error of the whole text or of its first statement, no statement, the count of a text of one statement, and too many arguments. So such an argument runs nothing also in a text whose later statement s4ql refuses, or that has too few arguments, where the statements before would run with arguments of supported types. **Open:** an error that names an argument by its number in the call would read better; the engine numbers the parameters of a plan from 1 for each statement.
  - **The result.** `RowsAffected` is SQLite's count of changes on the connection after the last statement that ran, `sqlite3_changes`: the count of the last insert, update, or delete, also of one that failed, which sets it to 0, and a create table or a select after it leaves it. mattn gives the same, as `select changes()` after its `Exec` shows, but in two cases, where s4ql gives SQLite's count and not mattn's: a text that ends in an empty statement after the last one, `insert ...; -- c` or `insert ...;;`, gives 0 rows affected in mattn, its fix of its issue 963, where the result had been nil; and a last statement with RETURNING gives in mattn the count of the statement before it, because mattn steps it once. This follows the driver's decision of slice 1 that its result is SQLite's count after the statement, and that of slice 14 for RETURNING through `Exec`, and is no refusal: **the lead may prefer an error from `RowsAffected` for these texts**, which would never differ from mattn. `LastInsertId` stays 0.
  - **Empty statements, spaces, and comments.** Before a statement and between statements they are skipped, as SQLite and mattn skip them, and they belong to the part of the statement after them; after the last statement, to the last part. A text without a statement is `ErrNoStatement`, "not supported" in the driver, as before; mattn gives 0 rows affected for it.
  - **A refusal: the spaces that Go's `strings.TrimSpace` removes and SQLite does not read as spaces.** mattn trims every tail with `TrimSpace`, which removes the no-break space U+00A0, U+0085, U+2028 and the other Unicode spaces, and a vertical tab where a token starts, all of which SQLite reads as part of a token: a character of a name from 0x80 on, and an illegal token for the tab. So `insert ...; insert ...` runs both inserts in mattn and is a syntax error in SQLite. At the end of the text the trim also changes what SQLite would read: `insert ...; /* ` ends in a comment for SQLite and in `near "/": syntax error` in mattn, and `select 'abc   ` gives `unrecognized token: "'abc"` without the spaces. s4ql refuses such a text as a whole, before any statement runs, with "not supported": `space after a statement that SQLite reads as part of a token` at the start of a tail, and, if a tail follows the first statement, `space at the end of the text that SQLite reads as part of a token`. A comment that stays the same kind of comment without the trimmed spaces, a line comment or a block comment without its end, is no such space. Where the two readings agree, the statements after the first are read from the text without the spaces at its end, as mattn hands them to SQLite, which shows only in the text that SQLite keeps of a CREATE TABLE or a CREATE INDEX without a semicolon at the end of the text.
  - **Errors.** A statement that fails ends the run with its error, and keeps the statements before it, as mattn does: SQLite's errors when it runs (`UNIQUE constraint failed`) and of the names (`no such table`), SQLite's syntax error of a later statement, and "not supported" of a later statement that s4ql does not support, which mattn may run. The errors of the whole text come before any statement runs: those of `stmt.Check` before it parses (NUL byte, invalid UTF-8, a text longer than SQLite's limit), the refusal of spaces above, too many arguments, and no statement. mattn reads a text up to a NUL byte; s4ql refuses it.
  - **In a transaction.** The statements are statements of the transaction, each counted in its event's `transaction.statements`. One that fails has no effect, the statements before it stay in the transaction, which stays open, and a commit commits them, as in mattn.
  - **Query and Prepare.** `Query` and `QueryRow` of a text of several statements stay "not supported", `second statement`, as before. So does `Prepare`: mattn's prepared statement of such a text runs only its first statement, which s4ql does not copy. A prepared statement runs its one statement through `engine.Conn.Exec`, as before, so a comment after it that the trim would change, such as `insert ...; /* `, is no refusal there: mattn's prepared statement ignores its tail too.
  - **Telemetry.** Each statement has the event `statement` that it has when it runs alone, with the text of its part as `statement.sql`, at Debug. An error that comes before any statement runs is the event of a statement whose text is the whole text, with no kind, as the event of a text that fails its check is. The error of a later statement that does not check is an event whose text is the rest of the text from that statement on. The driver and the engine have no span or event of a call of their own, so there is none to give the number of statements, and there is no new metric.

- **Not built: the rest of the generated checks.** The generated workload, the driver's generated test, the engine's differential tests, and the differential test and the fuzz target of `Split` are built, below. What stays open: the simulation's planted bugs for the loop (such as a statement run twice, the arguments of a statement shifted, the result of the first statement in place of the last, a failure that keeps going); and mutation testing of `stmt.Split`, `engine.Conn.ExecAll`, and the driver's `exec`. The open item of the cost of `parser.ParseAt` is in [driver.md](driver.md).

## Generated workload and the driver's generated test

- **Decisions of the builder on 2026-11-26, built, for the lead to confirm.** The diary `2026-11-25-several-statements-workload.md` has the steps.
  - **The workload.** The area `several` and the profile `several` at slot 14 of `stmttest.Profiles`; `Mixed` has `Several: 32`, one call in 32. `Sequence.several` (`internal/sql/stmt/stmttest/several.go`) writes two to five statements, each one that the sequence writes with a number of a statement of its own, so that each draws as a statement alone does; one time in twelve after the first, an earlier statement of the text again, which makes an insert fail on its key or a create table on its name; as faults, a text of `Others` or of `ArithmeticRefused` in the middle; the last statement one time in three with RETURNING. Before, between, and after the statements stand spaces, comments, and empty statements, and as faults the spaces that Go's `TrimSpace` removes and SQLite reads as part of a token (`severalTrimmed`, `severalTrimmedEnds`), at the start of a tail and at the end, too few arguments, and one too many. `Sequence.Next` gives the arguments of such a text the cases around them too. A `Call` of such a text has `Statements` and `Each`, whether each statement is one that s4ql supports, and `Supported` false. One text in eight is a query; the driver check runs two in three of those that it would run through a prepared statement through `Exec` instead. The profile `several` turns on the areas `selects`, `changes`, `indexes`, `exists`, `arguments`, `returning`, and `arithmetic`, for evaluation errors in the middle, and begins transactions one turn in seven.
  - **The oracle** (`pair.several` in `internal/sqlite/crosscheck/drivercheck/drivercheck_test.go`) replaces the stopgap that ran a text as its statements, each a step of its own. s4ql's side runs the whole text in one `Exec`. Then: an error that comes before any statement runs is checked against its rule, and nothing runs in SQLite: the refusal of spaces (as `stmt.Split` gives it), more arguments than parameters (the message as the rule writes it), and an argument of a Go type that the driver refuses for the whole call (`driverRefusal`, by its number in the call). A text that s4ql runs to its end runs in mattn in one `Exec` on the same connection, which must run it to its end; s4ql's rows affected must be `select changes()` after it in mattn, and mattn's must be too, but for the two decided differences, each a named excuse: `excusedSeveralEnd`, a last statement that ends in a semicolon after which a comment or an empty statement follows, and `excusedSeveralReturning`, a last statement with RETURNING. Through the pool the count is compared only for a text with an insert, an update, or a delete. A text at which s4ql stops runs in mattn as mattn runs it, one statement after another, each with its arguments, up to the statement at which s4ql stopped (`pair.severalFailed`, `pair.severalWalk` since the fixes below): too few arguments for a statement is checked against the rule's message; an error of s4ql's own with an offset belongs to the statement whose span holds it, and one without, of an argument or a type, to the first statement whose rules give it, and either is judged by `pair.compare` as an `Exec` of that statement alone, with the offset in it, against the rules that judge a statement alone, and not run in SQLite; the pinned build's error of a name in double quotes is judged by `pair.checkQuoted`; and every other error is SQLite's, which mattn must give for the same statement, or one that `knownGap` or `pair.startedTable` accepts. After every call of such a text, also one that failed, every table is read back on both sides where the call ran, in the transaction if one is open (`pair.compareIn`). Open rows of the transaction are read to their end and closed before such a text.
  - **Reach kinds.** `pair.reachSeveral` counts, under "reached: several statements: ", the outcome, the number of statements, the arguments, each kind of statement that ran, a last statement with RETURNING that ran, too few and too many arguments, a statement that failed after one ran and one before the last, by its error, and the empty statements and comments before, between, and after the statements; in a transaction too. `pair.reach` counts a text of several statements through Query, QueryRow, and Prepare by its call and its outcome. 52 kinds are in `TestGenerated.kinds` at a third of their totals of 2026-11-26: among them, of all profiles, 152 texts that ran to their end and 970 that failed, 74 with more arguments than parameters and 24 with fewer, 78 that failed on `UNIQUE constraint failed` after a statement ran, 39 on `no such table`, 78 on "not supported", 6 on an evaluation error, 13 on a syntax error, 43 last statements with RETURNING that ran, and 57, 33, 93, 50, and 22 refused through Query, QueryRow, Prepare and Exec, Prepare and Exec several times, and Prepare and Query. `TestGenerated` runs 80 sequences of `several` for its rarest kinds.
  - **The excuses**, pinned exactly in `TestGenerated.tsv`: the result after an empty statement at the end 62 times in `several` and 2 in `mixed`, the result of a last statement with RETURNING 4 times in `several`, the refusal of spaces 48 and 4 times, the wrong number of arguments of a text of several statements 89 and 9 times. The refusals of a statement in the middle count under the excuses of a statement alone.
  - **One statement.** A subtest of `TestConn_ExecAll` in `internal/engine/several_test.go` runs the texts of one statement of six sequences of each profile through `engine.Conn.Exec` on one engine in memory and `engine.Conn.ExecAll` on another, whose scans draw their directions from the same seed, in and out of write and read-only transactions, and requires the same result, the same error with its type, message, offset of SQLite's error, and sentinels, and the same state. The count of arguments of a text of one statement turned off in `ExecAll`, and an offset of SQLite's error moved by one, each fail it.
  - **Planted faults**, each in `internal/engine/several.go`, one at a time, each reverted, each failing `TestGenerated`: every statement takes its arguments from the start of the list; the loop goes on after a failure and gives the last error; a failed statement undoes the statements before it outside a transaction; the result of the first statement that sets the count is given; a trailing empty statement runs the statement before it again; and in a transaction a failure after the first statement rolls the transaction back. The first and the second fail it where SQLite fails at another statement than s4ql, the third and the last on a table read back after the text, the fifth where s4ql fails on a key that only it meets, and the fourth on the count of changes of the call after the text, which the connection keeps.
  - **The engine's counts.** The texts of several statements of `mixed` take the place of statements in the engine's generated tests too, so `TestDifferential`, `TestConn_differential`, and `TestSimulation` were recounted. - **No fault of s4ql was found** by the generated texts: every difference from mattn that they showed was one of the decided differences or a recorded refusal.
- **Fixes after the self-review of 2026-11-26**, by the builder: the excuse of an empty statement at the end requires mattn's 0; a create table at which s4ql stopped is no longer taken for created; a failure before any statement or of the statement that `Split` refused is noted in the tally of the transaction; a trimmed space after a line comment at the end of the text is written on a line of its own, so that it is no longer part of the comment; `Sequence.other` lost its unused branch; and the check of one statement closes its engines after each sequence.
- **Open, from the self-review:** an error without an offset that two statements of a text give alike, as a statement written again does, is taken for the first. An s4ql that ran the first and failed at the second changed what the tables read back show, but for a first that changes nothing, such as a select, which only the checks of a statement alone judge. The same holds for SQLite's error, such as `UNIQUE constraint failed`, that two statements give alike. Telling them apart needs the number of statements that ran, which neither driver gives; an event of each statement would.

## Fixes after the self-review

- **By the builder on 2026-11-25, built,** after two independent reviews of the branch:
  - `FuzzSequence` failed on correct behaviour, as above; fixed with `pair.several`, and three seeds.
  - `Split` refused `drop table t; drop table u -- c\v`, a last statement without a semicolon whose comment ends in a space that SQLite reads as part of a token: it looked at the trimmed end of the comment as the start of a tail. The tail of a statement that ends the trimmed text is no tail now; `TestSplit` has three such texts.
  - `Split` took time in the square of the number of statements, because `parser.ParseAt` looked for a NUL byte in the rest of the text for each statement: 80,000 statements, 2.5 MB, took 8.9 s in a review. `ParseAt` takes the end of the text now, and does not look; `Split` has refused a NUL byte already. That also removed a panic of `ParseAt` for an offset after a NUL byte.
  - An argument was named by its number in the call by the check of the values and by its number in its statement by the errors that a statement gives while it runs. Both number it in its statement now, as said above.
  - `engine.CheckAll` refused another number of arguments in both directions and the error of a later statement up front, which `ExecAll` does not; it gives exactly what `ExecAll` gives before any statement runs now, so a call with an argument of an unsupported Go type gives the same errors of the text as one without.
  - A panic in `stmt.Split` logs the event of a statement of the whole text, as a panic of the check of `Exec` does.
  - The literal no-break spaces in the tests are ` ` escapes, and comments that named their callers say what the code does.
- **Left, from the reviews:** the result of a text that ends in an empty statement, or with RETURNING, differs from mattn's without an error, as said above, for the lead to decide. Both reviews measured mattn's two paths of `Exec`, the one without arguments (`execNoArgs`) and the loop, and they agree; `TestSeveral` reaches only the loop, because `t.Context()` can end.

## Fixes after the review of the workload

- **By the builder on 2026-11-26, built,** after an independent review of the generated workload and the driver's generated test:
  - **The statements that s4ql ran are judged by the rules of a statement alone.** `pair.severalWalk` (in place of `pair.severalFailed`) walks every text that is not refused before its first statement, also one that s4ql ran to its end, and before each statement that runs in SQLite asks `pair.refusedAlone` for the refusal that s4ql's rules give it alone, on the tables as SQLite has them there: the check of its text, an argument that s4ql does not support, the refusals of its arithmetic, and those of the type of a value. A statement that SQLite runs and those rules refuse fails the test. The planted fault "the refusal of a select after the first statement is turned into success", in `internal/engine/several.go`, fails `TestGenerated` there.
  - **The oracle has its own rule of spaces.** `spaceRule` reads the statements of the text as SQLite's `sqlite3_complete` reads where one ends (`sqliteStatements`, its table of states, on the tokens of `internal/sql/token`), and refuses a text where Go's `TrimSpace` and SQLite read the start of the text after a statement, or the end of the text, differently, up to the first statement that `stmt.Check` refuses, as the agreed refusal says. s4ql must give that refusal exactly where the rule does, and no refusal of spaces anywhere else. Two planted faults in `internal/sql/stmt/split.go`, `trimmedStart` turned off and its refusal widened to a tab or a line break before a later statement, each fail it. The rule reads the spaces by SQLite's tokens, not by its characters: a vertical tab after a tab is no refusal, as SQLite reads it as part of the token of spaces that the tab starts, which a first version of the rule, by characters, got wrong.
  - **mattn's own `Exec` is the reference after the walk.** The walk runs in a savepoint that is rolled back. Then mattn's `Exec` runs on the connection: the whole text, if s4ql ran it to its end, with the checks of its result as before, or if SQLite gave the error at which the walk stopped, which mattn's `Exec` must give too; or the text up to the statement at which s4ql stopped with an error of its own, which mattn's `Exec` must run. Too few arguments is such an error, because mattn prepares a statement before it counts its arguments, and gives SQLite's error of its names where s4ql counts first.
  - **`stmt.Split` refuses the end of a text at its first token** that the trim changes, not its last, so that the offset of `space at the end of the text that SQLite reads as part of a token` is the first such space; `TestSplit` has a text with two.
  - **No count varies with the direction of a scan.** The profile `several` has no LIMIT and no subquery, so its arithmetic fails or not by the rows alone. `mixed` has both, and a text of several statements of `mixed` stops or goes on at such a select, which would decide the state and the counts of the rest of its sequence; `Sequence.several` writes its statements without LIMIT and subqueries where the profile has arithmetic. The excuses stay pinned exactly.
  - **Two kinds of the engine are required once.** `TestDifferential` requires "arithmetic with a column in WHERE of a delete, no such column" and "arithmetic without a column in WHERE of a delete, wrong number of arguments" once at least, as `TestGenerated` requires its kind of NULL beside a value of another type.
  - **New forms.** The workload writes a CREATE TRIGGER whose body holds two statements (s4ql refuses it, and the split must take it as one statement); a create table, an insert, and an update that depend on each other, on a table whose name in double quotes holds a semicolon, with a key in a string that holds one, a third of them from the insert on; and comments that hold a semicolon before, between, and after the statements. `pair.reachForms` counts each form by the position of its statement, first, in the middle, or last, as 15 kinds of `TestGenerated.kinds` at a third of their totals of 2026-11-26.
  - **No fault of s4ql was found** by the tightened checks. The excuse of mattn's result after a last statement with RETURNING is reached no more by the generated texts; `TestSeveral` keeps it. (The engine's differential tests below made the generator reach it again.)

## The engine's differential tests

- **Decisions of the builder on 2026-11-26, built, for the lead to confirm.** The diary `2026-11-26-several-statements-engine.md` has the steps.
  - **What runs where.** `TestDifferential` and `TestConn_differential` run the profile `several`, twice and four times as many sequences as a plain profile, and the texts of several statements of `mixed`, through `engine.Conn.ExecAll` (`pair.several` in `internal/engine/several_test.go`, which `pair.step` calls for a text with `Statements` through Exec; a query of such a text stays on the path of a statement alone, which refuses it for its second statement). The instance of the pair runs the statements one after another, each alone through `pair.step` with as many of the arguments as it has parameters, so each is judged against SQLite by every rule of a statement alone, up to the first that fails; the other instance runs the whole text in one `ExecAll` after it. So the rules of a statement alone are reused and not copied, and the other instance's commits are compared with commits of the same statements run alone.
  - **The oracle's statements** are SQLite's: `sqliteParts` reads them on the tokens of SQLite's own tokenizer (`sqlite.Tokenize`), and a semicolon ends a statement where `sqlite3_complete` takes the text from the statement's first token on for complete, so a CREATE TRIGGER's body ends none. Each part runs from the end of the statement before to the end of its semicolon, and the last part to the end of the text, as `stmt.Split`'s parts do; that is a decision of the doc of `Split`, which the oracle follows, but it does not call `Split`.
  - **The rules before any statement runs**: the refusal of spaces by `spaceRule`, which reads the agreed refusal on SQLite's tokens (the driver check's `spaceRule` reads it on s4ql's tokens; `TestSpaceRule` requires the engine's rule to agree with `Split` on 14 texts); more arguments than parameters, where the rules of a statement alone accept every statement, with the message written from the rule. A text that is not valid UTF-8 or holds NUL fails the test, since the oracle has no rule for it and the generator writes none.
  - **What is judged of each call.** The error, by its kind, message, and offset in the whole text: the error of the statement at which the walk stopped, with the offset of SQLite's error and the offset in the message of s4ql's own error moved by the start of its part, or, for too few arguments, the message of the rule. The result: that of the last statement of the walk that set the count of changes, or none. The tables after the call, also after a failed one: every table of the other instance, read from the core outside a transaction and by a select of each table in it. The commits: the other instance's new commits, their changes and their annotations, must be those that the instance wrote for the statements alone, and none in a transaction; `TestConn_differential` compares the whole logs of both instances after the end of each transaction (`pair.sameLog`).
  - **Evaluation errors of another row.** The two instances draw the directions of their scans each from a seed of their own, so a statement with arithmetic can fail on another row in `ExecAll` than alone. Where both give an evaluation error with other messages, the other instance's error must belong to the statement at which the walk stopped and be justified by `pair.justify` on SQLite's rows before it; this was reached once in `TestConn_differential` on 2026-11-26, and its count is not required, since the other instance's seed is drawn for each run.
  - **Not read both ways.** `pair.bothWays` does nothing for the statements of the walk: the other instance has run the whole text, or will, so it cannot run each statement too. The statements alone are read both ways in every other call.
  - **Reach kinds**, under "reached: several statements: ", in `TestDifferential.kinds` (28 kinds) and `TestConn_differential.kinds` (35), at a third of their totals of 2026-11-26 (totals of `TestDifferential`, then of `TestConn_differential`): a text of 2, 3, 4, and 5 statements that ran to its end, 129/92, 133/121, 93/62, 55/40; a stop at the first, a middle, and the last statement, for a constraint 137/84, 89/56, 37/25, an evaluation error 13/27, 10/14, 3/1 (the last only in `TestDifferential`), not supported 238/226, 86/96, 46/31, SQLite's error 339/713, 123/153, 63/72, and too few arguments 16/19, 8/7, 7/8; fewer arguments than parameters 31/34 and more 129/134; the refusal of spaces 67/78; one commit of a text outside a transaction 317/110, and a commit of each of two statements or more 392/125; a statement on a table that an earlier statement of the text created 475/385, or whose rows one changed 329/227; a last statement with RETURNING that ran 204/162, and one after another count of changes 136/110. In `TestConn_differential` alone: a text in a write transaction 868 and in a read-only one 557; one that stopped after a statement ran, in each, 233 and 63; and the commit and the roll back of a write transaction in which a text failed, 161 and 81, and of a read-only one, 114 and 59.
  - **The generator.** `Sequence.several` ends one text of three statements or more in four, in a profile with RETURNING, in `severalReturning`: a create table of `"c;r"`, an update of every row of it, and an insert with RETURNING of a new key. The update changes as many rows as earlier such texts inserted, so the count of changes before the last statement differs from the count after it, which is where mattn's result differs. ## A differential test and a fuzz target for the split

- **By the builder on 2026-11-26, built.** The diary `2026-11-26-split-fuzz.md` has the steps, and the README of `internal/sql/stmt` the test.
  - **What it compares.** `TestSplit_differential` in `internal/sql/stmt/split_test.go` checks `stmt.Split` on 100,000 generated texts, 10,000 under `-short`, against SQLite read twice through `oracle.Judge` and the binding of `internal/sqlite`, each statement from the tail of the one before: as SQLite alone reads the text, and as mattn's `Exec` does, with `strings.TrimSpace` on each tail. The readings are compared statement by statement by the verdict, SQLite's error and its offset, and the range of the statement's tokens by SQLite's own tokenizer. `FuzzSplit` runs the same check on any text, seeded with the hand cases of `TestSplit`, which moved to package-level variables, and 200 generated texts.
  - **The rule it checks.** A NUL byte or a byte that is not UTF-8 is refused at the first. Where the readings agree, `Split` cuts where SQLite does, with each statement on SQLite's tokens, and gives SQLite's syntax error at its offset or "not supported" inside a statement that SQLite parses; at a statement on which SQLite does not say, the check stops. Where they differ, `Split` refuses the text with a refusal of spaces, or stops with "not supported" before the first statement at which they differ. The refusal of the start of a tail comes only where the readings differ after it. The refusal of the end comes exactly where SQLite's tokenizer reads the end of the text otherwise without the spaces that the trim removes, at the offset that SQLite's tokens give, once a first statement that s4ql supports has text after it. That is broader than "the readings differ": it is decided for the whole text before any later statement is read, so a text whose later statement fails before such an end is refused as a whole, where mattn runs the statements before the failure and gives SQLite's error. This is the agreed refusal, and the oracle of the driver check (`spaceRule`) has it too, so the test checks it as it is; the lead may want to narrow it to the texts that reach the end.
  - **Counts at seed 0, 100,000 texts, 105,693 parts:** 19,099 texts of several statements read to the end, 15,788 of one, 3,795 without a statement, 26,501 that end in SQLite's syntax error, 14,387 in a statement that s4ql does not support and 695 of them before the readings differ, 3,143 refused for a NUL byte, 6,253 for invalid UTF-8, 1,863 for a space after a statement, and 2,617 for a space at the end, and 5,859 that stop at a statement on which SQLite does not say, most of them a CREATE TABLE with a duplicate column, which s4ql supports with the error of its columns. The test requires each of them but the last.
  - **At a statement on which SQLite does not say,** the check stops, because SQLite gives no tail of it. If it is the first statement, a refusal of the end is still checked at its offset by SQLite's tokens; a refusal of the start of a tail after it is accepted. The self-review found both cases failing on correct behaviour, `create table t (v int primary key, v int) strict, without rowid; drop table u` with a no-break space at the end or after the semicolon; both texts are cases of the test and seeds of `FuzzSplit`.
  - **Planted faults,** one at a time, each reverted, each failing `TestSplit_differential` under `-short`: the tail of each statement one byte late, in `split.go`; a `--` comment after a semicolon that swallows the rest of the text, in `split.go`; a semicolon inside a name in brackets that ends the token, in the parser's `read`; and both refusals of spaces turned off, in `split.go`. `trimmedStart` alone turned off fails it too.
  - **Fuzzing:** `FuzzSplit` made 1,414,900 executions in 5 minutes on 2 workers and found nothing, and after the fixes of the self-review 901,511 in 1 minute.
  - **No fault of s4ql was found.** The open item of a guard for the cost of the split stays open in [driver.md](driver.md), with what was tried.

## Fixes after the review of the engine's differential tests

- **By the builder on 2026-11-26, built,** after an independent review of the engine's differential tests:
  - **How many times each statement runs.** `pair.several` compares, for every text, the events of statements that `ExecAll` logs on the other instance with those that the instance logs in the walk, by their number, their order, their kind, their outcome, and the kind of their transaction, and in a transaction the statements that each counts in it (`engine.Conn.TxStatements`, from `tx_export_test.go`). An instance whose options have no logger of their own records the events with `recorder`, which is enabled only while a text of several statements runs; a text refused before any statement runs must log one event without a kind. The planted fault "in a read-only transaction each select of a text runs twice", in `execPart`, survived both differential tests before and fails `TestConn_differential` now on the events (`["select" ok "read_only" "select" ok "read_only" "delete" sqlite_error "read_only"]` against the walk's two events); an extra count in the transaction alone fails it on the count.
  - **mattn's number for a last statement with RETURNING.** mattn steps such a statement once, and SQLite counts its changes when it ends, so mattn's result is SQLite's count of changes before the last statement: that of the last statement before it that sets one, or that of an earlier call if none does, as a probe of mattn showed (`create table u ...; insert ... returning k` gives the count of the call before). The excuse `excusedSeveralReturning` now requires exactly that number, which `severalBeforeLast` measures by running the statements before the last in mattn in a savepoint that it rolls back, which keeps SQLite's count. `TestSeveral` pins the case where no statement before the last sets a count. A planted fault that takes mattn's number as one more fails `TestGenerated` at once, where the excuse had taken any number.
  - **Each statement of the walk is judged by its own support.** `stmttest.Call` has `Supports`, whether each text that `Sequence.several` joined is a statement of the sequence, and `Each` is whether all are. The walk passes each statement its own, so a statement that s4ql supports is no longer judged only as "SQLite prepares it" because another statement of its text is one that s4ql does not support. The walk stops at the first part of the first text that s4ql does not support, so the parts of the walk and the texts of the generator are one to one; a walk that reaches a part beyond them fails the test. The driver check still passes `Each` for the whole text.
  - **No fault of s4ql was found** by the tightened checks; no count of the `.kinds` and `.tsv` files changed.
