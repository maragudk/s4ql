# Several statements in one `Exec`

The decisions and notes of the builders of the piece of work "several statements in one `Exec`", which Markus agreed on 2026-11-24 ([driver.md](driver.md) had the item): several statements in one `Exec` mean the same as running them one after another, nothing is wrapped around them, and `Query` with several statements stays refused, as the lead decided. glue's migration files and fixtures and goqite's schema file are the milestone. The rule for every detail is "SQLite's answer or an error", where SQLite's answer is what `mattn/go-sqlite3` v1.14.53 does for the same `Exec`; each fact of mattn here was measured, and `TestSeveral` in `internal/sqlite/crosscheck/drivercheck` pins it beside s4ql's answer.

## The code and the hand-written tests

- **Decisions of the builder on 2026-11-25, built, for the lead to confirm.**
  - **How the text is split.** `stmt.Split` in `internal/sql/stmt/split.go` reads the statements as mattn does: the first statement of the text as `sqlite3_prepare_v2` prepares it, then the first statement of the tail, from the end of the semicolon on, until the tail holds no statement. It parses each statement once, with `parser.ParseAt`, which reads from an offset with the offsets in the whole text, and recognizes it as `stmt.Check` does. Each `stmt.Part` has its statement, with spans in the whole text, and its span of the text: from the end of the part before to the end of its semicolon, and for the last part to the end of the text. So every offset of an error is in the text that the application gave.
  - **Where the loop lives.** In the engine, `engine.Conn.ExecAll` in `internal/engine/several.go`, which the driver's `Exec` calls. `engine.Conn.Exec` is left as it was, one statement for each text, so the engine's tests, its differential test, its fuzz targets, and the simulation, which give it texts of the corpus with second statements, are not changed. Each part runs through the code of `Exec` after the check of its text (`execPlan`), so each statement is its own transaction, or a statement of the transaction of the connection, with its own event and its own annotation, as if it ran alone.
  - **Arguments.** Each statement takes as many arguments as it has parameters, in order, as mattn binds `sqlite3_bind_parameter_count` of each. Too few for a statement: the statements before it run, and it fails with an error of `ErrArguments`, `s4ql: wrong number of arguments: 1 for a text whose statements up to the one at offset 32 have 2 parameters`, where mattn gives `not enough args to execute query: want 1 got 0` after the same statements. More than the statements have: mattn drops them without an error, which s4ql does not copy; it refuses them before any statement runs, `s4ql: wrong number of arguments: 3 for a text whose 2 statements have 2 parameters`. That is known only when every statement of the text checks; a text with a statement that s4ql refuses runs the statements before it and then gives its error. A text of one statement counts its arguments as `Exec` does, with the same messages. An argument that no column holds, such as a NaN, fails its statement, named by its number in the call, after the statements before it. An argument of a Go type that s4ql does not support, such as a bool, is judged by the driver before any statement runs, after the errors of the text and of the number of arguments, through `engine.CheckAll`.
  - **The result.** `RowsAffected` is SQLite's count of changes on the connection after the last statement that ran, `sqlite3_changes`: the count of the last insert, update, or delete, also of one that failed, which sets it to 0, and a create table or a select after it leaves it. mattn gives the same, as `select changes()` after its `Exec` shows, but in two cases, where s4ql gives SQLite's count and not mattn's: a text that ends in an empty statement after the last one, `insert ...; -- c` or `insert ...;;`, gives 0 rows affected in mattn, its fix of its issue 963, where the result had been nil; and a last statement with RETURNING gives in mattn the count of the statement before it, because mattn steps it once. This follows the driver's decision of slice 1 that its result is SQLite's count after the statement, and that of slice 14 for RETURNING through `Exec`, and is no refusal: **the lead may prefer an error from `RowsAffected` for these texts**, which would never differ from mattn. `LastInsertId` stays 0.
  - **Empty statements, spaces, and comments.** Before a statement and between statements they are skipped, as SQLite and mattn skip them, and they belong to the part of the statement after them; after the last statement, to the last part. A text without a statement is `ErrNoStatement`, "not supported" in the driver, as before; mattn gives 0 rows affected for it.
  - **A refusal: the spaces that Go's `strings.TrimSpace` removes and SQLite does not read as spaces.** mattn trims every tail with `TrimSpace`, which removes the no-break space U+00A0, U+0085, U+2028 and the other Unicode spaces, and a vertical tab where a token starts, all of which SQLite reads as part of a token: a character of a name from 0x80 on, and an illegal token for the tab. So `insert ...; insert ...` runs both inserts in mattn and is a syntax error in SQLite. At the end of the text the trim also changes what SQLite would read: `insert ...; /* ` ends in a comment for SQLite and in `near "/": syntax error` in mattn, and `select 'abc   ` gives `unrecognized token: "'abc"` without the spaces. s4ql refuses such a text as a whole, before any statement runs, with "not supported": `space after a statement that SQLite reads as part of a token` at the start of a tail, and, if a tail follows the first statement, `space at the end of the text that SQLite reads as part of a token`. A comment that stays the same kind of comment without the trimmed spaces, a line comment or a block comment without its end, is no such space. Where the two readings agree, the statements after the first are read from the text without the spaces at its end, as mattn hands them to SQLite, which shows only in the text that SQLite keeps of a CREATE TABLE or a CREATE INDEX without a semicolon at the end of the text.
  - **Errors.** A statement that fails ends the run with its error, and keeps the statements before it, as mattn does: SQLite's errors when it runs (`UNIQUE constraint failed`) and of the names (`no such table`), SQLite's syntax error of a later statement, and "not supported" of a later statement that s4ql does not support, which mattn may run. The errors of the whole text come before any statement runs: those of `stmt.Check` before it parses (NUL byte, invalid UTF-8, a text longer than SQLite's limit), the refusal of spaces above, too many arguments, and no statement. mattn reads a text up to a NUL byte; s4ql refuses it.
  - **In a transaction.** The statements are statements of the transaction, each counted in its event's `transaction.statements`. One that fails has no effect, the statements before it stay in the transaction, which stays open, and a commit commits them, as in mattn.
  - **Query and Prepare.** `Query` and `QueryRow` of a text of several statements stay "not supported", `second statement`, as before. So does `Prepare`: mattn's prepared statement of such a text runs only its first statement, which s4ql does not copy. A prepared statement runs its one statement through `engine.Conn.Exec`, as before, so a comment after it that the trim would change, such as `insert ...; /* `, is no refusal there: mattn's prepared statement ignores its tail too.
  - **Telemetry.** Each statement has the event `statement` that it has when it runs alone, with the text of its part as `statement.sql`, at Debug. An error that comes before any statement runs is the event of a statement whose text is the whole text, with no kind, as the event of a text that fails its check is. The error of a later statement that does not check is an event whose text is the rest of the text from that statement on. The driver and the engine have no span or event of a call of their own, so there is none to give the number of statements, and there is no new metric.

- **Not built: the generated checks.** `stmttest.Others` has one text of two statements, `select * from %[1]v; select * from %[1]v`, which the generated workload runs half the time through `Exec`. The engine's generated tests run it through `engine.Conn.Exec`, which still refuses it. The driver's `TestGenerated` and `FuzzSequence` now get the two selects run, and compare them with mattn's run of the first statement only (`firstStatement`), which gives the same answer for two selects. They still pass, with the same pinned counts. What the generated checks need: a workload that writes texts of several statements of the slices, also with arguments, empty statements, comments, a failing statement in the middle, and the spaces of the refusal, in and out of transactions; an oracle that runs the whole text in mattn and reads `select changes()` after it, with the two differences of the result above and the refusals excused by exact count; the simulation's planted bugs for the loop (such as a statement run twice, the arguments of a statement shifted, the result of the first statement in place of the last, a failure that keeps going); and mutation testing of `stmt.Split`, `engine.Conn.ExecAll`, and the driver's `exec`.
