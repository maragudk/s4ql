# Upserts

The decisions and notes of the builders of the piece of work "upserts": `insert ... on conflict (key) do nothing` and `insert ... on conflict (key) do update set ...`, as Markus agreed on 2026-11-24 ([writing.md](writing.md), [the roadmap](../roadmap.md#writing)). `replace into` and `insert or ...` stay refused. The engine and the driver, the generated checks, and mutation testing are later steps.

## The statement pass

- **Decisions of the statement pass of upserts, by its builder on 2026-11-26, built, for the lead to confirm.** Each fact of SQLite here was measured with the pinned shell (3.54.1). The tests of the pass check the typed form against SQLite: `checkUpsert` in `internal/sql/stmt/stmt_test.go` on every supported text, and the cases of `TestCheck` under "Upserts" and "Upserts that are not supported". [The section Upserts of the README of the pass](../../internal/sql/stmt/README.md#upserts) has the forms token for token.
  - **The forms.** One ON CONFLICT clause after VALUES and before RETURNING: a target of one or more columns in parentheses, and DO NOTHING, or DO UPDATE SET with assignments as an update has them and an optional WHERE as an update has it, without subqueries. In DO UPDATE, `excluded.c` is the column `c` of the row that the insert proposes, wherever a column stands: alone, in arithmetic, in `||` and the calls, on either side of a comparison, and before IS NULL and IS NOT NULL.
  - **The typed form, the contract for the engine.** `stmt.Insert.Conflict`, a `stmt.Conflict`: `Span` (from ON to the end of the clause; `Present()`), `Target []stmt.Name` with offsets, `Action` (`stmt.DoNothing` or `stmt.DoUpdate`), `Set []stmt.Assignment`, and `Where []stmt.Condition`. A column of excluded is a new kind of node, `stmt.ExprExcluded`, with `Column` and a new field `Table`, the name `excluded` as the text writes it, which SQLite prints in `no such column: EXCLUDED.x`. A new kind, and not a flag on `ExprColumn`, so that code that knows only the old kinds cannot read it as a column of the table. `HasColumn` is true for it, so a condition on it is a filter and its side is the tested one. A test for NULL of `excluded.c` has the node as its `Expression` and the zero `Column`, the one test for NULL with an `Expression`. The parameters are numbered in the order of the text, VALUES first, then SET, then WHERE.
  - **The depth.** `excluded.c` is 2 deep, as SQLite counts the dot an operator over two names; each value of SET has its own limit of 1,000 and the WHERE one, as for an update. The edges are checked against SQLite.
  - **No limit of 2,000 assignments in DO UPDATE.** SQLite counts those of an update while it parses (`too many columns in set list`), but not those of an upsert, whose columns, more than any table has, it refuses once it has found the table with `no such column`. So the pass takes them, and the engine gives SQLite's error.
  - **Refused from the text, each at the token named, with what SQLite does:**
    - `ON CONFLICT without a target`, at the DO: `on conflict do nothing` and `on conflict do update ...`. SQLite takes both, for every constraint of uniqueness of the table, `do update` only as the last clause. In a table of s4ql, whose one constraint of uniqueness is the key, it means the same as a target of the key, but the agreed form names the key, a unique index would make the two differ, and with a target the engine can give SQLite's error for one that is not the key. The lead's brief leaned to refusing too.
    - `WHERE of a conflict target`. SQLite matches it to a partial index, or to an index that is not partial: `on conflict (k) where k > 0 do update` updates the row. s4ql has no partial index.
    - `ASC or DESC` after a column of the target, which SQLite ignores; `NULLS FIRST or NULLS LAST`, which SQLite refuses with `unsupported use of NULLS FIRST`; `COLLATE`, for which SQLite matches the collation of the index (`collate binary` matches the key, `collate nocase` nothing); `parentheses`, which SQLite reads as the column; `conflict target other than a column` for a literal, a string, a parameter, or an expression, which match no index of s4ql; `TRUE or FALSE`; `column with the name of a table` for `t.k`, which SQLite takes as `k`, and `excluded.k` (SQLite: `no such column: excluded.k`); `column named twice` for `(k, K)`, which matches no index.
    - `second ON CONFLICT clause`, at its ON. SQLite takes the first clause whose target the row meets. One clause is what was agreed, and the order of several is a rule that s4ql need not copy.
    - `assignment to a column of the conflict target`, at the column. SQLite moves the row to the new key, and gives `UNIQUE constraint failed: t.k` when another row has it. Since the target of s4ql is always the key, this refuses every change of the key in DO UPDATE. Refused in the pass rather than left to the engine because the pass knows the target from the text, and the case is rare and easy to get wrong; it can be lifted later, since the storage core's upsert can move a row.
    - `subquery` in DO UPDATE, in SET (as for an update) and in WHERE (where an update takes one). SQLite takes both; a subquery there can name the columns of both rows, which is correlation of a new kind. Refused rather than let fall out, since the subqueries of a statement are a list of the statement and `Insert` has none.
    - `column with the name of a table` for `t.v` in DO UPDATE, which SQLite reads as the row of the table, for `main.excluded.v`, and for `excluded.v` in an upsert into a table named `excluded` (by `Name.Fold`): SQLite then reads `excluded.v` as the column of the table and not of the row of the insert, `set v = excluded.v + 100` gives 101 for a row `(1, 1)` and an insert of `(1, 5)`. A compatibility quirk that s4ql does not copy.
    - `single-quoted name`, `name in brackets`, and `name in backticks` for `'excluded'.v`, `[excluded].v`, and `` `excluded`.v ``, which SQLite takes as excluded, as for every name.
    - A column of excluded outside DO UPDATE keeps the names it had: `column reference` in VALUES and `result column other than a column or *` in RETURNING (SQLite: `no such column: excluded.k`), and `column with the name of a table` in an update.
    - Everything an update refuses in SET and WHERE, by the same names, and everything an insert refuses before the clause (REPLACE, INSERT OR, WITH, an alias, a second row, SELECT), by its old name.
    - Syntax errors are SQLite's: `excluded.*`, `set excluded.v = 1`, ON CONFLICT on an update, after DEFAULT VALUES, or after a clause without a target, and DO UPDATE without SET.
  - **Names that changed.** `ON CONFLICT clause` was the name of every upsert. Now `on conflict do nothing` is `ON CONFLICT without a target`, at the DO, and `on conflict (v) do update set v = ?` is `assignment to a column of the conflict target`. `ON CONFLICT clause` stays the name of the clause of a column of CREATE TABLE.
- **Where s4ql is stricter than SQLite or differs from it, in the statement pass,** for the lead to tell Markus: a clause without a target, a second clause, a target with WHERE, ASC, DESC, COLLATE, or parentheses, a target `t.k`, an assignment to the key in DO UPDATE, a subquery in DO UPDATE, `t.v` there, `excluded` in single quotes, brackets, or backticks, and `excluded.v` in an upsert into a table named `excluded` are refused, where SQLite takes each.
- **Left to the engine step, because it needs the table.** These were measured with the shell; the README of the pass lists them under [Upserts](../../internal/sql/stmt/README.md#upserts).
  - Whether the target is the primary key: otherwise `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`, also for a column of a plain index and for a target of two columns, and `no such column: z` for a column of the target that the table lacks. In another case or in double quotes, the name of the key matches.
  - Whether the columns of SET, of the values, of excluded, and of WHERE exist, in SQLite's order: `no such table`, the list and the number of the values, the columns of the target, the assignments of SET in the order of the text, each its value before its column (`set zz = yy` gives `no such column: yy`, `set zz = 1, v = yy` gives `zz`), then WHERE and RETURNING. `no such column: EXCLUDED.zz` prints `excluded` as written without quotes, and `excluded.rowid` is missing in a WITHOUT ROWID table. These errors come at prepare, with a conflict or without one. The engine step should pin the whole order against SQLite or refuse such a statement, as for text.
  - The rows and counts: without a conflict the insert, `changes()` 1; DO NOTHING on a conflict changes nothing, no row of RETURNING, `changes()` 0; DO UPDATE changes the row if WHERE holds (RETURNING gives it after the change, `changes()` 1), else nothing and 0. `excluded.c` of a column that the list leaves out is its DEFAULT or NULL.
  - The types: `set v = excluded.w` of a TEXT into an INT column gives `cannot store TEXT value in INT column t.v`; the exact types of slice 4, and the types of arithmetic and of text, hold for `excluded.c` as for a column of the type of its column. NOT NULL holds for the insert also with DO NOTHING, and for the assignments of DO UPDATE.
  - Under `pragma query_only`, `attempt to write a readonly database`, also for an upsert that would change nothing.
  - The storage core's `Tx.Upsert` (`conn.upsert` in `internal/core/cache.go`) inserts a row or replaces the row of its key, which DO UPDATE can use as `update` does.
- **The allow-list.** `TestAllowList` allows `ColumnRef.Table` and `ColumnRef.Dot2` for every statement now, since its keys have no context, so it no longer notices on its own a form like `select t.v from t` becoming supported; the cases of `TestCheck` that refuse `column with the name of a table` still do.
- **The engine refused an upsert until the engine step, which removed the refusal.** `upsertRefusal` in `internal/engine/upsert.go` gives `ON CONFLICT clause`, at the ON, from `textRefusal`, so after the checks of the text and the arguments, in `engine.Check`, in each run and for each statement of `ExecAll`, and before the database is read. `engine.NewPlan` panics for an insert with a clause, so that no path can run an insert without its clause. `TestEngine_upsert` pins both. `stmttest.UpsertRefusal` gives the same refusal, and the differential pairs of the engine and of the driver (`internal/sqlite/crosscheck/drivercheck`) accept it for any text that the pass takes (`excusedUpsert` in each), which `FuzzSQL` seeds and a subtest of the driver's `TestPair` pins through Exec, Query, and Prepare. The engine's pair takes the refusal before its rule of the length limit, since the engine refuses an upsert before it measures its values. The engine step removed the refusal, `stmttest.UpsertRefusal`, the panic of `NewPlan`, and both excuses.
- **Open after the statement pass:** the generators of `stmttest` do not write upserts yet, which is the step of the generated checks. Mutation testing of the new code of the pass is open too. With one row per insert, the order in which a write visits rows of one key ([non-determinism](../research/non-determinism.md), row 8) does not arise yet; several rows per insert must decide it.

## The engine and the driver

- **Decisions of the engine step of upserts, by its builder on 2026-11-26, built, for the lead to confirm.** Each fact of SQLite here was measured with the pinned shell (3.54.1), and the tests check it against the pinned build: `TestEngine_upsert` and `TestPair_upsert` in `internal/engine/upsert_test.go`, the subtest of upserts of the driver's `TestPair` in `internal/sqlite/crosscheck/drivercheck`, and `TestUpsertRefusals` in `stmttest`.
  - **What runs.** An insert with ON CONFLICT of the key inserts its row where the table has none of its key, with `changes()` 1 and the row in RETURNING. On a conflict, DO NOTHING changes nothing, gives no row, and counts 0; DO UPDATE changes the row of the key where its WHERE holds, gives the row after the change, and counts 1, and otherwise nothing and 0. `excluded.c` of a column that the list leaves out is its DEFAULT, or NULL.
  - **How.** DO UPDATE reads one row of a combined table, `combinedTable` in `internal/engine/upsert.go`: the columns of the table, then a column for each under a name that starts with a NUL byte, which no text holds. Once SQLite would have given every error of the names, each `excluded.c` becomes a column of that table, and the `update` and the filter of an update check, bind, and compute SET and WHERE. So `excluded.c` is a column of the type of its column everywhere: copied alone, compared alone with a column of its class (`v = excluded.v`, also of TEXT and BLOB), and in arithmetic as a column. The evaluator is unchanged. The write is the storage's `insertNew` for the row and `upsert` for the row that DO UPDATE changes, as an update writes a row whose key stays; `internal/core` is unchanged.
  - **The errors of the names, in SQLite's order and at SQLite's offsets,** pinned with and without a conflict: `no such table`; the list of columns and the number of values, as for an insert; every column of the target, `no such column: z` at the name (with the question about quotes for `"z"`), and only then `ON CONFLICT clause does not match any PRIMARY KEY or UNIQUE constraint`, without an offset, so `(v, z)` gives `no such column: z`; the assignments of SET in the order of the text, each its value before its column, the column as an update gives it (`no such column: zz`, no offset, no question about quotes); the conditions of WHERE as for a select: a test for NULL of a missing column, or of `excluded.c` of one, waits for the next comparison or the end, and a later one replaces it; then RETURNING. A missing `excluded.c` is `no such column: excluded.c` with the two names as the text writes their values (`EXCLUDED.zz`, `excluded.ZZ` for `excluded."ZZ"`), at the offset of `excluded`; `excluded.rowid` and `rowid` are missing in a WITHOUT ROWID table. Then the lengths of the arguments and literals, of the row, then of SET, then of WHERE, which SQLite gives when it binds them, also without a conflict.
  - **The refusals, s4ql's own, after SQLite's errors of the names and the lengths, whatever the database holds.** When the statement is built, those of DO UPDATE, as for an update: the operands of arithmetic of SET in the order of the text, the classes of SET in the order of the table, then WHERE in the order of the text; then the expressions without a column of SET and then of WHERE are computed once, with their evaluation errors. When it is checked, the proposed row as an insert: `NOT NULL constraint failed` first, then a value of another type than its column. A refusal names a column of excluded as `the column excluded.c of type T`.
  - **The run.** `insertNew` measures the record of the proposed row before it looks for the key, so `string or blob too big` comes also with DO NOTHING on a conflict, as in SQLite. On a conflict with DO UPDATE, the conditions of WHERE are computed on the row in the order of the text, up to the first that is not true, then SET in the order of the text, then NOT NULL of each column that SET gives, in the order of the table, also for a value of one run (`set n = null` fails only where it changes a row), and the write measures the new record.
  - **A read-only transaction** gives the errors of the names and of the lengths, and then `attempt to write a readonly database`, also for an upsert that would change nothing; it checks no type and computes nothing, since SQLite refuses the write before it looks at a value.
  - **Text** (`||`, `lower`, `hex`) in SET or WHERE of DO UPDATE is refused by `textRefusal`, before the database is read, as for an update on `main` today.
- **Where s4ql is stricter than SQLite or differs from it, in the engine,** for the lead to tell Markus: a refusal of the types of DO UPDATE, and an evaluation error of an expression without a column of DO UPDATE, come also where the table has no row of the key, where SQLite inserts the row and never looks at DO UPDATE; this is the rule of an update, whose refusals and constants come whether it finds a row or not. In a read-only transaction an upsert gives no refusal of its types, where an update gives those of its WHERE.
- **The pairs.** The engine's differential pair judges an upsert by `pair.checkUpsert`: a refusal must be one of `stmttest.UpsertRefusals`, which reads DO UPDATE over the same combined columns, independently of the engine; an evaluation error must be justified by SQLite, and no error is due where the engine gives none. SQLite's quirk of an operator on the row of the conflict is found by a probe, `stmttest.UpsertQuirkQuery`: the upsert's own row with `do update set k = k where <the conditions before the site> and <the quirk> returning 1`, after `stmttest.UpsertConflictQuery` (the row with DO NOTHING) has said whether there is a conflict, each in a savepoint that is rolled back. The probes set SQLite's `changes()`, so the pair sets it back by an insert of as many rows into a temporary table WITHOUT ROWID, which keeps the last insert rowid. The driver's pair takes the same rules in `pair.checkRefused`, `pair.justifyUpsert`, and `pair.compare`, its probes in a transaction of their own or a savepoint of the open one. `FuzzSQL` seeds five upserts.
- **The rules of the pairs are tested against wrong answers** (the fixes after the independent review, 2026-11-26): a subtest of `TestPair_upsert` gives `pair.checkUpsert` answers that are wrong, and one of the driver's `TestPair` gives them to `pair.compare`: a refusal that is none of the rules', a success where a refusal was due, also of the proposed row and where the table has no row of the key, and an evaluation error that SQLite does not justify, for another value, without a conflict, of a constant, and in a read-only transaction. Each must fail. Before, the driver's pair had no rule that a success of an upsert was due no refusal, and left it to SQLite's outcome, which cannot show it where SQLite converts a value that s4ql refuses (`set v4 = excluded.v3` of 2.0 into an INT column); `pair.compare` now has it, as the engine's pair has.
- **`value compared with a value` in the WHERE of DO UPDATE is the update's rule.** `where 1 = 1`, `where ? = 1` with NULL, and `where 1 + 0 = 1` are refused where SQLite runs them, in DO UPDATE as in the WHERE of an update, a delete, and a select: the statement pass gives the one refusal `value compared with a value` for each (`recognize.go`; the README of the pass says DO UPDATE refuses what an update refuses), and `TestCheck` pins it for DO UPDATE. So the upsert follows the update, and nothing differs to fix.
- **Open:** the generators of `stmttest` write no upsert yet, so no generated check reaches one: the workload with the engine's differential test, planted bugs of upserts in the simulation (no planted bug touches `upsert.go`; `checkOutside` and `skipUnique` leave an upsert alone), and the driver's generated test are each a later builder's. Mutation testing of `upsert.go` and of the rules in `stmttest/upsert.go` is open, for the workflow in CI. Several rows per insert, and the forms that the pass refuses, stay out. The event of an upsert has no `statement.access` and no `statement.rows_read`, as that of an insert has none, although DO UPDATE reads the row of the key with `get`; whether a write that reads by its key should report it is open.
