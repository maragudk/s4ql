# Slice 6: `null`

The decisions and notes of the builders of [slice 6 of the roadmap](../roadmap.md#slice-6-null).

## The statement pass

- **Decided by the builder of the pass for slice 6 on 2026-11-20, built, for the lead to confirm:**
  - The literal NULL is `stmt.Null{}`, an empty struct and a fifth type of `stmt.Value`. Its `stmt.Term` has `Value: stmt.Null{}` and `Parameter: 0`. It is not a nil `Value`, which still means a parameter, so the two cannot be taken for each other. It is not a bool on `Term` beside a nil `Value` either, since code that reads a nil `Value` as a parameter would then take a NULL for one.
  - `-null` and `+null`, which SQLite reads as NULL, are not supported, as `NULL after a sign`: the roadmap lists only the plain word. The offset for `-null` is that of the NULL, as for `string after a sign`, and for `+null` that of the `+`. `- -null` stays `second sign`, and `+-null` stays `+ sign`.
  - The column constraint NULL without NOT, as in `v2 text null`, is not supported, as `NULL constraint`, at the NULL, also before or after NOT NULL and on the key. SQLite reads it as no constraint, and the roadmap lists only a column without `not null`. NOT NULL twice stays `NULL or NOT NULL constraint`, and `default null` stays `DEFAULT`.
  - A table without a primary key is `table without PRIMARY KEY`, at the `)`, whatever its columns say. The names `column without PRIMARY KEY or NOT NULL`, `column without NOT NULL`, and `NULL` are gone.
  - `Generator.Nulls` of `stmttest` turns on the forms of slice 6. With n, one column in n that is not the key has no NOT NULL, and one value in n of an insert is NULL, as a literal or as a `?` with a nil argument. With 0 the generator draws as before: a dump of 27,000 texts and arguments from 30 seeds is the same on the old code and the new, byte for byte. The pass's tests set it to 5. `stmttest.Sequence` leaves it 0. Since the generated checks of slice 6 the sequence writes NULL through its hooks, and `Nulls` does not apply to what a hook gives; see the decisions of the builder of those checks below.
  - Until the engine ran slice 6, it refused the forms of the slice as not supported, with `checkNulls` in `internal/engine/errors.go`, as `checkColumns` did for slice 5. `checkNulls` and the `checkText` wrappers of the tests are gone since the engine and the driver run the slice; see the next item. The driver's `check` in `conn.go` calls `stmt.Check` alone again, and `engine.Check` refuses none of the forms of slice 6. `Prepare` still refuses at once what the text alone shows is not supported, such as `-null`.
  - The pinned numbers of the pass's generated tests moved, only because the generator draws other random numbers with `Nulls` on. The README of the pass has them, with the reasons, under "Results".

## The engine and the driver

- **Decided by the builder of the engine and the driver for slice 6 on 2026-11-20, built, for the lead to confirm.** The README of the engine has the details under "The stages", "The operators", "Errors", "Parameters", "Types", and "How it is tested".
  - The plan's `ColumnDef` has `Nullable`, which is true for a column that is not the key and has no `not null`. `Format` prints ` NULL` after the type of such a column, so the plans of slices 1 to 5 print as before. The key is never nullable, and `buildSink` gives an internal error for a plan whose key is. The literal NULL is the expression `*Null`, which `Format` prints as `null`. `nullable` of a column of the commit object is set only when it is true, as the core gives the table back.
  - Every nil is NULL, and every nil `[]byte` stays refused, because it does not say whether it means NULL or the empty blob. `database/sql` hands the driver nil for a Go `nil`, for a nil pointer of any type, also `(*[]byte)(nil)`, for a `driver.Valuer` that gives nil, such as a `sql.NullString`, a `sql.NullInt64`, a `sql.NullFloat64`, or a `sql.Null[T]` that is not valid, also `sql.Null[[]byte]{}`, and for a nil pointer to a `Valuer` with a value receiver. It hands a nil `[]byte` for `[]byte(nil)`, for `new([]byte)`, for a `sql.Null[[]byte]{Valid: true}` whose `V` is nil, and for `sql.RawBytes(nil)`. Each of these four gets `s4ql: not supported: argument 1 of type []byte, which is nil`. `TestNulls` and `TestParameters` in `conn_test.go` check each kind.
  - A NULL that an insert gives, as a literal or as a nil argument, and a column that its list leaves out are one case: `buildValues` puts NULL at a column left out. `NOT NULL constraint failed: t.c`, with the codes 19 and 1299, names the first column in the order of the table that does not take NULL and gets it, the key too, also when one statement gives a NULL and leaves a column out. It comes where slice 5 gave it for a column left out: after the names, the number of values, a text or a blob that is too long, and the refusal of a read-only transaction, and before the refusal of a value of another type, `string or blob too big` for a record, and `UNIQUE constraint failed`. NULL has no type: a NULL in a column that takes it is never refused for its type, and the check of the type goes on to the other columns.
  - A NULL takes no bytes of its own in SQLite's record, so the length at which a record is too long moves with it. The core measures the record exactly. A new subtest of `TestEngine_tooBig` finds a length at which a row with NULL fits and the same row with a real does not, and compares both with SQLite, also in a transaction and after a replay.
  - Every row of an insert goes through `insertNew`, which is the core's `Tx.Insert`, SQLite's `insert ... on conflict do nothing`. The lead decided this on 2026-11-20, after an independent review. It returns false for a key that exists, which the engine turns into `UNIQUE constraint failed`, and its `core.ErrTooBig` is `string or blob too big`. So SQLite's order of the two, too big first, is kept without a `get` before the write. `upsert` stays only for the planted bug `skipUnique`. The planted bug `checkOutside` checks the key itself, with a `get` in its own read transaction, after the checks of the sink, and the pinned order of its calls did not change. The fake of `operator_internal_test.go` records an insert as `insert t1 1`, so the pinned orders of the calls read `table t1 insert t1 1 annotate …` where they read `table t1 get t1 1 upsert t1 1 annotate …`. Every planted bug is still found in the default run of `TestSimulation_plantedBugs`, and no seed finds anything without them.
  - The states that the engine's tests compare print ` NULL` after the type of a column that takes NULL: `oracle.state`, `instance.state`, `coreState`, and the state of the database in memory. SQLite's side reads it from `pragma_table_info`: the column's `notnull` is 0, and it is not the key. So every comparison of tables, also after a replay, checks which columns take NULL. In the simulation, `run.verifyRows` takes NULL only in a column that takes NULL.
  - The rule of `internal/sql/stmt/stmttest/rule.go` knows NULL. `TableColumn` has `Nullable`. `ValueKind` gives `"null"` for the literal NULL and for a nil argument; a nil `[]byte` is a blob there. `TypeRule` gives nothing where the key, or a column that does not take NULL, gets NULL or is left out, because SQLite's NOT NULL comes first, and NULL is of no other type than any column. `Faults` has the new fault `NULL in a column that does not take it`, and a column that takes NULL and is left out is no fault. `TestTypeRule` in `rule_test.go` pins the rule.
  - Three pinned numbers of the generated tests moved, with the generator drawing as before. In the engine's `TestDifferential`, the calls with an argument that no column holds went from 197 to 184: the 13 calls with a nil argument are no longer refused, and run in SQLite. In `TestGenerated` of `drivercheck`, `excusedArgument` went from 189 to 184, for 5 calls with a nil argument, and `excusedPrepare` from 1072 to 1075: one of those 5 calls, and two inserts of the literal NULL of `stmttest.Others` that s4ql refused as not supported before, meet SQLite's error of a name at prepare. The helper `converted` of `drivercheck` applies a `driver.Valuer` and a nil pointer as `database/sql` does.

## The core

- **Decided by the builder of the core on 2026-11-20, built: the decisions of detail of slice 6 in the core,** with their reasons in [internal/core/README.md](../../internal/core/README.md). A column takes NULL only if its `Column` says `nullable`; the core refuses a NULL in any other column and in the key with `core.ErrInvalid`, in `Tx.Upsert` and `Tx.Insert` before SQLite sees the row, and at replay as a broken log. The cache declares a column that takes NULL `default null`, and every other column outside the key `not null`, and the version of its layout went from 1 to 2: a cache of version 1 is refused with `core.ErrCacheVersion`, as any other version, and left as it is, and a version that reads only version 1 refuses a cache of version 2 instead of reading a column that takes NULL as one that does not. The builder had written an upgrade of a cache of version 1 in place; Markus had it removed on 2026-11-20, since nothing outside the tests uses s4ql yet. Before slice 6 the core took a NULL in any column outside the key, and some of its own tests and of the format's samples wrote one; a log with such a NULL, in a column whose `Column` lacks `nullable`, is now refused at replay. No engine before slice 6 wrote one.

## The generated checks

- **Decided by the builder of the generated checks for slice 6 on 2026-11-20, built, for the lead to confirm.** The README of the engine has the details under "How it is tested" and "Results".
  - The shapes and the rates of NULL. Each shape of a `stmttest.Sequence` of more than one column has, among its columns outside the key, none that takes NULL, only columns that take NULL, or columns that each take NULL one time in two; a third of the shapes are of each kind. Of the create tables that declare the shape, one in ten turns whether one column takes NULL, which changes nothing for the key. In the create table in ten with columns at random, each column outside the key takes NULL one time in two. An insert gives NULL one time in four to a column that takes NULL, and a list leaves such a column out one time in three. One insert in twelve has NULL for any column, also the key. A `?` for NULL has nil as its argument.
  - A call around a NULL argument has a nil `[]byte` in its place, which s4ql refuses. Nil is no longer in `stmttest.Unsupported`, because it is NULL.
  - `Generator.Nulls` stays 0 in the sequence. The hook `Generator.Create` gives, for each column outside the key, whether it is NOT NULL, in `stmt.Column.NotNull`, and the generator writes NOT NULL after such a column only if the hook says so. `Nulls` does not apply to the columns of the hook. The pinned numbers of the tests of the pass did not move.
  - `stmttest.Faults` names "NULL in the key" apart from "NULL in a column that does not take it". The new `stmttest.NullCases` gives the cases of NULL that an insert reaches: each NULL, as a literal or as an argument, into the key, into a column that takes NULL, or into one that does not; an insert that leaves out a column that takes NULL; and NULL beside a value of another type. The engine's `TestDifferential` and `drivercheck` share it.
  - The engine's `TestDifferential` counts these cases by outcome, the create tables by whether none, all, or some of the columns outside the key take NULL, and the selects of `*` and of names with NULL in their rows. `reachedDifferential` requires a least number of each, a third of what the run gave. The run found no difference from SQLite, and 4,000 more sequences from seed 1,000,000 found none. Its pinned numbers moved: the texts of a table that exists from 17 to 18, the calls with the wrong number of arguments from 718 to 703, those with an argument that no column holds from 184 to 220, the values of another type from 336 to 339, and the literals that are too long from 3 to 8. The sequence draws other random numbers, which moves each. The third also went up because a call around a NULL argument has a nil `[]byte`: the arguments that are a nil `[]byte` went from 26 to 54.
  - `TestGenerated` of `drivercheck` makes each nil argument one of `nils`: nil, a nil pointer to an `int64`, a `float64`, a `string`, or a `[]byte`, a nil `*sql.NullString`, and a `sql.NullInt64`, a `sql.NullFloat64`, a `sql.NullString`, or a `sql.Null[[]byte]` that is not valid. It makes each nil `[]byte` one of `nilBytes`: `[]byte(nil)`, `new([]byte)`, and `sql.Null[[]byte]{Valid: true}`. It reads each row of a query into an `any`, and again into a `sql.Null*` value and into a pointer for each column, and compares the scans of both sides (`outcome.scans`, `outcome.full`). It requires a least number of each case of slice 6 and of each kind of nil, and found no difference from mattn. Its pinned numbers moved, for the same reasons: `excusedPrepare` from 1075 to 1060, `excusedStartedTable` from 9 to 10, `excusedArguments` from 396 to 426, `excusedArgument` from 184 to 200, `excusedLevel` from 70 to 74, `excusedRowsOpen` from 29 to 46, `excusedTxOpen` from 30 to 29, `excusedOutside` from 68 to 53, and `excusedQuoted` from 32 to 45; `excusedType` stayed at 161.
  - The simulation counts the NULL values in the rows of the log, in `run.verifyRows`, as "NULL values in the log". `TestSimulation` requires 0.4, 0.08, and 0.67 of them for each seed in the default, the idle, and the hammer workload, a quarter of the 1,581, 316, and 2,694 that the first 1,000 seeds gave.
  - The planted bug `zeroLeftOut` makes an insert with a list give a column that takes NULL, and that the list leaves out, the zero value of its type in place of NULL. It is in `buildSink`, and only a statement of its own plants it, as with `listOrder`. Its own violation is ", and in SQLite": a query gives the zero value where SQLite has NULL. "The replay of the log holds" finds it too. The engine has twelve planted bugs now.
  - `FuzzTypes` and `FuzzTypes_core` have five more tables, `t_<type>_n`, whose first column takes NULL beside an INT key, and the form `formNull`. The form gives NULL by the length of the input: as a nil argument for a length of 1 modulo 3, by leaving the first column out of the list of a table of two for 2, and otherwise as the literal.
