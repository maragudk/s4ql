# Slice 14: `returning` on `insert`, `update`, and `delete`

The decisions and notes of the builders of [slice 14 of the roadmap](../roadmap.md#slice-14-returning-on-insert-update-and-delete).

## Agreed with Markus on 2026-11-23

- **The slice.** `returning` at the end of an `insert`, an `update`, or a `delete`, with a list of column names of the statement's table, or `*` for all columns in table order. One row per inserted, updated, or deleted row: the values after the change for `insert` and `update`, and the row's last values for `delete`. The rows come in the order of the spec's rule on row order, as for an unordered `select`. Outside a transaction the statement commits before it gives its first row; inside one the rows come at once. `Exec` drops the rows, and `Query` gives them. The commit format does not change. An expression in the list, an alias, and a column with the name of its table are not supported.

## The statement pass

- **Decisions of the statement pass of slice 14, by its builder on 2026-11-23, built, for the lead to confirm.** Each fact of SQLite here was found with the pinned shell, and the tests of the pass check it against SQLite: `checkInsertReturning`, `checkChangeReturning`, and the checks of `no such column` in `stmt_test.go` on every supported text, and the two subtests of `TestCheck` named below. The README of the pass has the forms token for token.
  - The field is `Returning`, of the new type `stmt.Returning`, on `stmt.Insert`, `stmt.Update`, and `stmt.Delete`. It has `Span`, from the keyword RETURNING to the end of its last column or of its `*`, and `Columns`, the names in the order of the text, each as often as the clause names it, or nil for `*`, as `stmt.Select.Columns` holds the select list. A statement without RETURNING has the zero `Returning`, and `Returning.Present` says whether there is one. A pointer was not taken, as for `stmt.Select.Limit`: no statement holds one, and the statements are compared and printed by value. RETURNING holds no parameter, so `Parameters` of each statement is as before.
  - A column of RETURNING is read as a column of a select list, by the same code, `recognizer.resultColumn`, so the two support the same forms and refuse the rest under the same names. The brief asked to treat RETURNING as the select list where that list takes a column with the name of its table: it does not, so neither does RETURNING.
  - A column that RETURNING names twice is supported, as in a select list, and the statement gives it twice. SQLite agrees: `returning v, v` gives two columns `v`, and `returning v, V` gives two columns with the name as the table stores it. Unlike a column named twice in the list of an insert, in SET, in an index, or in ORDER BY, where the later one does nothing, the later column of RETURNING is a column of the result, as in a select list.
  - `*` with another column is not supported, as `* and another result column`, at the `*`: `returning *, v`, `returning v, *`, and `returning *, *`. SQLite takes all three and gives the columns of `*` and the others in the order of the text. It is the rule of the select list, which slice 5 decided.
  - Not supported, each at the first token of its column, as in a select list: an expression, a function, a literal, NULL, a parameter, parentheses around a column, and COLLATE, as `result column other than a column or *`; a column with the name of its table, `t.v`, `main.t.v`, and `excluded.v`, and `t.*`, as `result column other than a column or *` too; an alias, with AS or without, as `alias`, at the AS or the alias; the bare word TRUE or FALSE, as `TRUE or FALSE`; and a name in brackets, in backticks, or empty, as for every name. SQLite takes `t.v` and refuses `t.*` with `RETURNING may not use "TABLE.*" wildcards` and `main.t.v` with `no such column: main.t.v` when it prepares the statement; it reads `true` as 1 and a string in single quotes as a string.
  - A column that the table does not have is not decided here, since it depends on the database. SQLite gives `no such column: x`, or `no such column: "x" - should this be a string literal in single-quotes?` for a name in double quotes, for the first column of RETURNING that the table lacks, in the order of the text, after every other error of the names: `no such table` first; for an insert, `table t has no column named x` for its list, `1 values for 2 columns`, and `table t has 2 columns but 1 values were supplied`; for an update, the columns of SET; and for an update and a delete, the columns of WHERE, by the rule of WHERE, so that a missing column under IS NULL gives its error before RETURNING. `rowid` is a name like any other, and SQLite gives `no such column: rowid` for it on a table without rowid.
  - The keywords that SQLite reads as a column in RETURNING are the 84 of the select list, in each place: after an insert, an update, and a delete, first in the list and after another column. The generator draws the columns of RETURNING from the pool of `SelectColumn`, which holds those keywords.
  - Syntax errors, which the pass gives as SQLite gives them: RETURNING without a column (`incomplete input` at the end of the text, `near ";": syntax error` before a semicolon), a comma without a column after it, RETURNING twice, `returning distinct`, RETURNING before WHERE in an update and in a delete, ORDER BY after RETURNING, and RETURNING after a select, a create table, a drop table, a create index, a drop index, and in the body of a trigger, which are `near "returning": syntax error`.
  - What the pass refuses before RETURNING stays as it was, at the same token: an upsert is `ON CONFLICT clause` at its ON, DEFAULT VALUES is `DEFAULT VALUES`, a second row is `second row`, an insert with SELECT is `INSERT with SELECT`, UPDATE OR is `UPDATE OR`, an update with FROM is `FROM clause`, and WITH and EXPLAIN are `WITH clause` and `EXPLAIN`.
  - More than 2,000 columns in RETURNING give `too many columns in result set` in SQLite when it prepares the statement, as for a select list. `*` alone gives at most 2,000, the most columns of a table, and the pass supports no `*` with another column. The pass does not check it, as it does not for a select list; see the open item in [the SQL front end](sql-front-end.md).
  - `stmttest.Generator.Returning`, 0 by default: with it, one insert, update, or delete in `Returning` ends with RETURNING, `*` one time in three, and otherwise from 1 to Columns+1 columns, or 1 without `Columns`. A column after the first is one time in four an earlier column of the clause; otherwise it is one time in two a column that the statement names before, in the list of an insert, in SET, or in WHERE, where SQLite reads it as a column of a select list, and otherwise a name of the pool of `SelectColumn`. With `Returning` 0 the generator draws nothing more: a dump of 32,400 lines, `%#v` of every statement and call of `Generator.Statement` and of `Generator.CallOf` of every kind in three settings, one of them with hooks, and of `Sequence.Next`, over 30 seeds, was the same byte for byte before the change of the generator and after it. The pass's own tests set it to 3. There is no hook yet, as `Generator.Order` is for ORDER BY: `Sequence` writes no RETURNING, and the engine's and the driver's tests set no `Returning`. The builder of the generated checks adds the hook with the area and its profile.
  - The numbers that the pass's tests pin moved only by the generator's draws: `TestGenerate_mutants` from 41 to 45 syntax errors and from 131 to 167 not supported where SQLite does not say, and `TestGenerate_nearMisses` from 2,089 to 1,983. With `Returning` 0 they are 41, 131, and 2,089 again, with the new near misses of RETURNING in place of the six old ones that are supported now. A tally by SQLite's message found create tables only (`generated columns cannot be part of the PRIMARY KEY`, `default value of column [x] is not constant`, `AUTOINCREMENT is only allowed on an INTEGER PRIMARY KEY`, `duplicate column name`, `table "t" has more than one primary key`, `unknown table option`, `non-deterministic functions prohibited in index expressions`, `no such collation sequence`), and two selects whose WHERE a mutant turned into ON, with `a JOIN clause is required before ON`, as for slice 13. No excused text has RETURNING. The corpus and the grammar keep their excused numbers; the supported texts of the corpus rose by 22, and its supported mutants by 1.
  - Until the engine runs slice 14, `engine.returningRefusal`, called in `engine.check`, gives an insert, an update, or a delete with RETURNING the error that the pass gave it before: `s4ql: not supported: RETURNING clause`, at the keyword RETURNING. A text with a column of RETURNING that the pass refuses gets the pass's error for that column, where before it got the one for the clause: `returning v + 1` gives `result column other than a column or *`. `TestCheck_returning` and `TestConn_returning` in `internal/engine/returning_test.go` pin it, and `returned` there lets the differential tests of the engine take the refusal for a text that is not supported. The driver's `Prepare` checks the text with `engine.Check` after `stmt.Check`, so it refuses such a text when it is prepared, as it did before; `TestPrepare` in `conn_test.go` pins both errors.
- **Facts of SQLite for the builder of the engine of slice 14, measured by the builder of its statement pass on 2026-11-23.** The subtest "should give SQLite's errors for RETURNING after those of the rest of the statement, in the order of the text" of `TestCheck` pins the order of the errors and the failures of constraints; `checkInsertReturning` and `checkChangeReturning` check the rows of every supported text; the rest was measured with the shell only.
  - A result column of RETURNING has the name of the column as the table stores it, as in a select: on `create table T (K int primary key, V text, W int)`, `returning k, v, "w", *` gives the columns `K`, `V`, `W`, `K`, `V`, `W`. `*` gives every column in the order of the table.
  - An insert gives one row, with the values that a select of the same columns reads after it: the DEFAULT of a column that the list leaves out, or NULL without one, and `0.0` for a `-0.0` in a REAL column. An update gives one row for each row that its WHERE chooses, as many as `changes()` counts, also a row whose values do not change, with the values after the update, also of the key: `update t set k = 100 where k = 1 returning k` gives 100. A delete gives one row for each row that it deletes, with the values that it had.
  - SQLite gives the rows of an update and a delete in the order in which it changes them, which is key order on a plain scan. s4ql promises no order, by the spec's rule for an unordered select.
  - A failure of a constraint comes when the statement runs, after every error of the names, and SQLite then gives no row and changes nothing: `UNIQUE constraint failed: t.k`, code 1555, for an insert of a key that exists and for an update that gives a row the key of another; `NOT NULL constraint failed: t.k`, code 1299, for an insert of NULL in the key. With a missing column of RETURNING, `insert into t (k) values (null) returning nope` gives `no such column: nope`.
  - Under `pragma query_only`, as a read-only transaction of s4ql runs it, an insert, an update, and a delete with RETURNING give `attempt to write a readonly database`.
  - `changes()` after an insert with RETURNING is 1, as without it.

## The engine and the driver

- **Decisions of the engine step of slice 14, by its builder on 2026-11-23, built, for the lead to confirm.** Each fact of SQLite here was measured with the pinned shell, and `TestEngine_returning` and `TestConn_returning` in `internal/engine/returning_test.go` and the sequences of slice 14 and `TestPair` in `internal/sqlite/crosscheck/drivercheck` check them against SQLite and mattn/go-sqlite3.
  - **The guards of the statement pass are gone.** `engine.returningRefusal`, the panic in `NewPlan`, `returned`, and the exceptions in `pair.step` are removed. The driver's `check` calls `stmt.Check` alone again, as before the statement pass, so `Prepare` parses the text once: with the refusal gone, `engine.Check` adds nothing to it but the count of the arguments, which `Prepare` does not know.
  - **The plan.** `Insert`, `Update`, and `Delete` have a field `Returning *Returning`, with `Star` and `Columns` as a `Project` has them, nil without RETURNING. `Format` prints it on the line of the statement: `update t set v = 1 returning *`.
  - **The rows are held in Go memory.** Each sink adds a row once it has written it: an insert the row that it inserted, an update the row after the change, and a delete the row that it read with a `get` just before it deleted it. `Conn.write` gives them, as a `returned` source of the rows, only after the commit has returned nil, and `Conn.writeIn` after the release of the savepoint. The rows cannot be read from the cache instead: outside a transaction they must outlive the write transaction, which the commit ends, and the rows of a delete are gone from the table. So the memory of a statement with RETURNING grows with the rows that it changes, without a bound; see the open item in [the storage core](storage-core.md).
  - **A row that a caller has read belongs to a committed change.** Outside a transaction, `Conn.Query` returns the rows after the commit is acknowledged, as `Conn.Exec` returns its result. A commit that fails gives its error and no rows, also one whose outcome is unknown. `TestConn_returning` pins it for an insert, an update, and a delete with a store that refuses the commit as too large (`simstore.Options.MaxSize`), and `TestReturning` in the root package for an unknown outcome. In a transaction, the rows come at once, and a roll back takes the change back although its rows were read.
  - **The values are those that a later select reads.** A real that is -0.0 is given as 0.0, which the table stores (`returning.add`); the core normalizes the stored value, and the sink normalizes the value that it gives. Every other value is given as the sink wrote it: the default of a column that an insert leaves out, NULL, and the values of SET. An update gives every row that it finds, also one whose values do not change, and a delete gives every row that it deletes, so the rows are as many as the count of changes.
  - **The columns** are those of a select of the same columns: the name as the table stores it and the declared type, each as often as the clause names it, `*` in the order of the table. A statement that changes no row gives no rows with its columns. SQLite gives the declared types through `sqlite3_column_decltype` for RETURNING too, so `ColumnTypeDatabaseTypeName` of the driver matches mattn's.
  - **The errors.** RETURNING is resolved after every other name of the statement, with SQLite's `no such column` of a select list (`noSuchResultColumn`, with the message about quotes for a name in double quotes): for an insert after the value counts, and for an update and a delete after the names of WHERE, before the lengths and the types of the values. A failed constraint gives its error and no row, and changes nothing. In a read-only transaction the statement gives `attempt to write a readonly database` after the errors of its names, RETURNING among them.
  - **The order of the rows.** The sink changes the rows in the order of the primary key of the rows that it found, as `changeRows` reads its `KeySet`. For each insert, update, and delete with RETURNING, and for no statement without it, the engine draws a direction, one draw for each statement, as it draws one for each query (`Engine.order`, `Engine.reading`), and gives the rows in that order or in its reverse. The draw is made before the sink is built, also when the statement then fails, and only in a write transaction; a statement in a read-only transaction draws nothing. An insert gives one row, for which the draw decides nothing. A path that the tests force with `Path.Forward` or `Path.Backward` fixes the direction. SQLite gave the rows of an update and a delete in the order of the key in every case measured, also through an index; s4ql promises no order, by the spec's rule.
  - **A statement while the rows of a RETURNING are open is treated as for a select.** In a transaction, the rows are the rows of the connection, and every statement of the connection fails with `ErrRowsOpen` until they are closed, and a commit while a loop reads them rolls back, as for a query. Outside a transaction they are not the connection's rows and hold nothing: a statement beside them runs, also a begin. The rows are fully held, so allowing a statement beside them in a transaction would have been simple too. It was not done, so that one rule covers every open rows of a transaction, and so that rows read lazily from the cache later, which the open item on memory may bring, need no new refusal; lifting the refusal later breaks nothing. Outside a transaction, the rows of a select may hold the reader when a write with RETURNING runs beside them, so the rows of the write must not take the place of the select's rows on the connection.
  - **Context.** A statement with RETURNING ends with the error of its context as the statement without RETURNING does, in each stage, and its commit as any commit. Once the rows are given, the change is committed, and a context that ends while the caller reads them ends the rows with its error, as `values` does for the rows of a query, before the next row.
  - **Telemetry.** A statement with RETURNING logs the event of the write that it is, once, when the write ends, before its rows are read: the kind, the access, `statement.rows_read`, `commit.parent`, and `statement.rows`, the count of the rows that it changed, which are the rows that it returned. An update and a delete with RETURNING also have `statement.direction`, the direction of their rows. `report.end` logs once, so the end of the rows logs nothing again. A delete with RETURNING reads each row once more, with the `get` before the delete, which `statement.rows_read` counts. No new metric and no new attribute.
  - **The commit format does not change,** and neither does replay: the commit object of a statement with RETURNING holds its text, with RETURNING, and its arguments, as for any statement.
- **Known difference of mattn/go-sqlite3, not of SQLite: its Exec of a statement with RETURNING gives the count of changes of the statement before.** mattn steps the statement once and reads `sqlite3_changes` then, and SQLite counts the changes of a statement with RETURNING once it has run to its end, although it makes them all in its first step. So `RowsAffected` of mattn's Exec of `update t5 set v2 = 'y' where v1 = 3 returning *` was 2, the count of the update before, where SQLite's `changes()` after the statement is 1 and s4ql gives 1. The driver check runs SQLite's side of such an Exec through Query and counts its rows (`execByQuery`).
- **For the builder of the generated checks.** `stmttest.Generator.Returning` stays 0 in `Sequence`, so the generated sequences, their least numbers in `testdata/reached/`, and the pinned counts are as before. The engine's `pair.step` checks the order of the rows of an update and a delete with RETURNING through Query (`pair.returnedInOrder`, `pair.checkReturned`): the rows of a select with the WHERE of the statement before it runs, in the order of the key, with the values of SET in the select list, or their reverse where `Rows.Backward` says so, and it counts `RETURNING whose rows came in the order of the key` and `... in the reverse of the order of the key` under `reached:`. `PathAccessOf` builds an update or a delete without its RETURNING, so that `reachChange` sees the access also for a column of RETURNING that the table does not have. In the driver check, `pair.openRows` of a `callQueryOpen` runs its text a second time, which for a write with RETURNING changes the database twice on both sides; an insert with RETURNING fails there with `UNIQUE constraint failed` on the second run, where the test requires no error. The QueryRow of a text with more than one column runs it twice too. The simulator's SQL box (`internal/simulator/box.go`) runs a statement with RETURNING down its write path with `Conn.Exec`, and drops the rows, where it was refused before.
