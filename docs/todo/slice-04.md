# Slice 4: the other types

The decisions and notes of the builders of [slice 4 of the roadmap](../roadmap.md#slice-4-the-other-types).

## The statement pass

- **Decided by the builder of the pass for slice 4 on 2026-11-19, built:**
  - `stmt.Type` names the five types, with SQLite's names as its `String`, and its zero value is no type. `stmt.Value` is a sealed interface of `Integer`, `Real`, `Text`, and `Blob`. It is nil for a parameter, and the value of a blob literal is never nil.
  - A real literal is read by a port of SQLite's routine, not by `strconv.ParseFloat`, so that the value is SQLite's bit for bit for every literal, also for those of more than 19 digits, where the two differ: 6,998 of the 100,000 texts of `TestCheck_reals`. So the roadmap's rule, that s4ql rejects a literal for which the same float is not sure, rejects none: with the port it is sure for every literal, as `TestCheck_reals` and `FuzzLiteral` check against SQLite. With `strconv.ParseFloat`, the rule would have rejected literals that SQLite reads fine, by a bound on the digits.
  - A column type that SQLite does not know stays "not supported", as `int(10)` was: SQLite's `unknown datatype` comes after parsing and is not a syntax error.
  - `-'a'` and `-x'01'`, which SQLite reads as the integer 0, are `string after a sign` and `blob after a sign`. A bare TRUE or FALSE is `TRUE or FALSE`. A literal that SQLite reads as an infinity is `infinite real number`, also after a `-`. `1e-400` is 0.0 and supported, as SQLite gives it.
  - A double-quoted string stays `column reference`, as before.
  - `stmttest` writes every type and every kind of literal and argument of slice 4, and the pass's tests run it without a wrapper.

## The engine and the driver

- **Decided by the builder of the engine and the driver for slice 4 on 2026-11-19, built, for the lead to confirm.** The README of the engine has the details under "Types" and "Parameters".
  - The check of the type comes where SQLite's `OP_TypeCheck` is: after SQLite's errors of the names, after `string or blob too big` for a text or a blob argument longer than the limit, which SQLite gives when it binds, and after `attempt to write a readonly database` in a read-only transaction, which SQLite gives at `OP_Transaction` before it looks at a value; before `UNIQUE constraint failed`, and before `string or blob too big` for a row whose record alone is too long. So every error of SQLite that s4ql reproduces comes where SQLite gives it.
  - The messages: `s4ql: not supported: argument 1, which is text, for the column t1.v1 of type INT` (or `an integer`, `a real`, `a blob`), and `s4ql: not supported: a string literal for the column t1.v1 of type INT` (or `an integer literal`, `a real literal`, `a blob literal`), with the names as the table stores them, as SQLite prints them in `UNIQUE constraint failed`. No value is in a message. Such a refusal leaves the count of changes, as every "not supported" does.
  - An argument that no column holds is refused before the instance, in the engine: `argument 1, which has no value`, `which is a real that is not a number`, `which is an infinite real`, `which is text that is not valid UTF-8`, and `which is text that holds the character NUL`. The driver refuses a `bool`, a `time.Time`, and every other type that is no value by their type, as before, and a nil `[]byte` as `argument 1 of type []byte, which is nil`. An empty `[]byte` that is not nil is the empty blob. Since slice 6 NULL is a value: the engine's `argument 1, which is NULL` is gone, and the driver turns nil into NULL.
  - The length limit is `core.Options.LengthLimit`, exported for the tests of the engine and the driver, which lower it to 1000; it must be from 1000 to 1,000,000,000. SQLite takes any limit from 30, but the builder of the mutation testing found on 2026-11-20 that a cache cannot even be made below about 300 bytes, since SQLite refuses the text of the cache's own `create table` in `sqlite_schema` and the row of its identity, so the core's lower bound is now 1000, the limit that the tests use. The engine reads it with `core.DB.LengthLimit` and checks the length of every value after the names, and `core.ErrTooBig` for a record becomes SQLite's error in `fromCore`.
  - **Known difference, found by the builder of `fix-create-too-long` on 2026-11-20: a table that SQLite holds under a lowered length limit and whose statement in the cache is longer than the limit.** SQLite keeps the statement in sqlite_schema, and a connection under the limit refuses a schema with a longer text when it loads it, so `Tx.CreateTable` refuses such a table with `core.ErrInvalid` and `core.ErrTooLongForCache`, and the transaction goes on. Since the engine step of slice 11 the engine answers "not supported" for it, `the table t, whose statement in the cache is longer than the length limit`, where it gave an internal error, and SQLite takes the table: see the decisions of that step. The cache's statement quotes every name, declares every column outside the key that does not take NULL `not null`, and writes each default in its canonical form, so it is longer than a short text of many columns. The generated tests do not reach it (at most three columns, names of at most 200 bytes, so at most about 850 bytes); a text of `FuzzSQL` could. Only a lowered limit reaches it. The same holds for an index since slice 9: `Tx.CreateIndex` refuses such an index the same way, and the engine answers "not supported", `the index i, whose statement in the cache is longer than the length limit`.
  - A literal longer than the limit gets `string or blob too big` too, after the names. SQLite cannot meet one with its default limits, since the text that holds it would be longer than `SQLITE_LIMIT_SQL_LENGTH`; the tests do not compare it with SQLite.
  - The driver gives every blob as a copy of its own, and the empty blob as `[]byte{}`, not nil. `Prepare` checks the text with `stmt.Check` alone again.

## The core

- **Decided by the builder of the core on 2026-11-19, built: the decisions of detail of slice 4 in the core,** with their reasons in [internal/core/README.md](../../internal/core/README.md). The core stores -0.0 as 0.0, as SQLite does, and does not refuse it. A text or blob above SQLite's length limit, and a row whose record is above it, is refused with the new `core.ErrTooBig` exactly where SQLite's own table refuses it, and the transaction goes on; the engine is to turn it into SQLite's "string or blob too big". The version of the cache's layout stays 1, because a table of `int` columns is declared as before. `int` and `integer` are two values of `Type`, so that a column is declared again as it was declared.

## The generated checks

- **Decided by the builder of the generated checks for slice 4 on 2026-11-19, built, for the lead to confirm.** The README of the engine has the details under "How it is tested".
  - Each name of a table of a `stmttest.Sequence` has a type of its own, which nine create tables in ten declare and nine values in ten have; the tenth takes any of the five types, so that some values are of another type than their column, which s4ql refuses. Half of the sequences of the engine's `TestDifferential` run with the length limit of the cache and of SQLite lowered to 1000 bytes, `stmttest.LengthLimit`, and the generator writes texts and blobs around that length.
  - A literal longer than the limit is not run in SQLite, as the engine's README says, and is checked against s4ql's rule instead: `string or blob too big`, after the names.
  - The simulation checks that every insert of the log has a value of the type of its column, and every refusal for the type against SQLite on the state that the statement saw. The planted bug `convertReal` shows that the first check finds what no comparison with SQLite finds, since SQLite converts the real of the log as the bug did.
  - The driver's generated test does not reach `string or blob too big`, because `s4ql.Options` has no length limit and a value of 1,000,000,000 bytes is too large for a test. The driver hands the engine's error through, and its `TestTypes` checks the error with a lowered limit through `OpenStore`. A length limit in the public options would be a change of the public API.
