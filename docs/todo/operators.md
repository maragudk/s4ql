# Operators that sort, group, join, or hold rows

What is agreed and not built about the operators of the engine that sort, group, or join, and about the memory of an operator that holds rows, and what is open. The short statements are in the roadmap, under [Reading](../roadmap.md#reading) and [Limits of the core](../roadmap.md#limits-of-the-core). The options are in [the feature map](../research/feature-map.md), core gaps 2 and 6, and what other engines do is in [research/memory-bounds.md](../research/memory-bounds.md).

- **Agreed with Markus on 2026-11-24, not built: grouping and joining get operators of s4ql's own, in Go.** They work on top of the ordered scans and the lookups by key that the cache gives. Sorting stays an ordered scan of the cache, as today: the cache's SQLite sorts the rows of a scan that no index orders, and spills to a temporary file as it does so ([the engine's README](../../internal/engine/README.md#the-operators), and the measurements in the research note). The option that Markus did not take was to group and join in the cache's SQLite.
- **Agreed with Markus on 2026-11-24, not built: a limit on the memory of an operator that holds rows, with a clear error, first.** A statement that would hold more than a set amount fails and changes nothing. The engine already has the paths for that: a write outside a transaction is rolled back on any error, and one inside a transaction is rolled back to its savepoint, so the transaction goes on. SQLite's refusal of a value as too big (`tooBig` in `internal/core/tx.go`) is a limit of this kind already: it fails the statement, and the transaction goes on.
- **Agreed with Markus on 2026-11-24, not built: spooling to the cache later, one operator at a time, starting with the rows of a `returning`.** The caveat from the research note: an error of the cache during a write fails the transaction, a local I/O failure also stops the instance (`tx.fail` in `internal/core/tx.go`), and `classify` counts `SQLITE_FULL` and `SQLITE_NOMEM` as local I/O failures. So a spool in the cache that fills the disk stops the whole instance, and does not fail only its statement.
- **Open: the size and the form of the limit.**
- **Known, from slice 14: the rows of a `returning` are held in memory without a bound.** An insert, an update, or a delete with `returning` holds each row that it changes, as the values of its columns of `returning`, in Go memory from the change until the caller has read or closed the rows (`returning` in `internal/engine/returning.go`), when it runs through `Query`; through `Exec`, which drops the rows, it holds none (`dropReturns`). So `update t set v = 1 returning *` on a table of a million rows holds a million rows. The rows must outlive the write transaction, which the commit ends before the first row is given, so they cannot be read from that transaction. A spool in the cache, as `KeySet` is a set of any size, would bound the memory: a temporary table of the rows on a connection of their own, or a file. goqite's statements change one row each.
