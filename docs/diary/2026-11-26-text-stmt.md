# Diary: Text in expressions, the statement pass

The piece of work "text in expressions" brings the operator `||` and the functions `lower` and `hex`, which goqite's table needs for `id text primary key default ('m_' || lower(hex(randomblob(16))))`; `randomblob`, `strftime`, and `default (<expression>)` are later pieces. This task is its first step, the statement pass in `/internal/sql/stmt`: read the new forms into the typed form, refuse from the text what SQLite would answer with a quirk, check every answer against SQLite, and make the evaluator and the engine refuse the new kinds cleanly until the evaluator step computes them. The work is on the branch `text-stmt`, from `1b66c9db` on `main`.

## Step 1: SQLite's behaviour and the shape of the typed form

**Author:** text-stmt builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Your ONE task is the first step of a new piece of work, **text in expressions**: the STATEMENT PASS for the operator `||` and the functions `lower` and `hex`. [...] The statement pass reads, in the places where it reads arithmetic today (the right sides of `set` in `update`, and either side of a `where` comparison): `a || b`, with operands that are text literals, parameters, columns, parenthesised expressions, and calls; `lower(x)` and `hex(x)`, with one argument that is an expression. It gives them as new kinds of `stmt.Expression` (a kind for the concatenation, and a kind for a call that carries the function), following the existing contract [...] Refused from the text, each with a clear `ErrNotSupported` naming the form and its offset, and each checked against what SQLite does for the same text [...]"
**Interpretation:** Extend the recognizer's expressions with `ExprConcat` and `ExprCall`, keep arithmetic and text apart where the text shows the type, give SQLite's own syntax errors, and refuse every other form by name.
**Inferred intent:** The front half of goqite's id: a typed form that the builder of the evaluator can compute without a redesign, and the facts of SQLite it needs.

### What I did

Read `/AGENTS.md`, `/docs/todo/arithmetic.md`, `/docs/todo/expressions.md`, `/docs/diary/2026-11-25-arithmetic-stmt.md`, `/internal/sql/stmt/recognize.go`, `/internal/sql/stmt/stmt.go`, `/internal/sql/stmt/vocabulary.go`, and the README of the pass. Built the pinned shell into the scratchpad as the arithmetic builder did (`cc -O1 -include internal/sqlite/options.h -Iinternal/sqlite/c internal/sqlite/c/shell.c internal/sqlite/c/sqlite3.c -o sqlite3 -lm`, 3.54.1) and ran each question as its own statement on a table with TEXT, INT, and BLOB columns. Read `sqlite3ExprFunction` and `exprSetHeight` in `/internal/sqlite/c/sqlite3.c` for the depth of a call.

### Why

What SQLite does with each text decides what the pass can refuse from the text alone, and which errors are SQLite's to give.

### What worked

The shell answered every question:

- `1 || 2` is `12`, `'a' || 1.5` is `a1.5`, `'a' || x'4243'` is `aBC`, `null || 'a'` is NULL. `lower(1)` is `1`, `hex(1)` is `31`, `hex(1.5)` is `312E35`, `lower(x'41')` is `a`, `lower(null)` is NULL, and `hex(null)` is the empty text, not NULL.
- `lower('É')` is `É`, `lower('ÀBC')` is `Àbc`: only ASCII letters change. `hex('é')` is `C3A9`.
- `lower()`, `lower(1,2)`, and `hex(*)` give `wrong number of arguments to function lower()`; `nosuch(v)` gives `no such function`; `lower(v order by v)`, `lower(v) filter (where 1)`, and `lower(v) over ()` give errors of their own. Each comes only once SQLite has found the table: `update nosuch set v = lower()` gives `no such table: nosuch`. So none is SQLite's answer on an empty database, and the pass refuses them as not supported, as it does for `row value misused`.
- `lower(distinct v)` and `lower(all v)` run and change nothing. `"lower"(v)`, `[lower](v)`, and `` `lower`(v) `` run. `'lower'(v)` is a syntax error.
- A function node is one level higher than its arguments and is checked when it is made, as a binary operator is.

### What didn't work

Nothing failed in this step.

### What I learned

The parser's `FuncCall` holds DISTINCT and ALL in one field, `*` in another, and ORDER BY, FILTER, and OVER as child nodes, so the recognizer's describe walk names each of them for free once the call is accepted and they are not.

### What was tricky

The brief asks for SQLite's error for "a wrong number of arguments" and also for a clear `ErrNotSupported` for "every other argument count". SQLite raises that error only after it has found the tables, so on an empty database it gives `no such table` first; the pass cannot give it from the text alone. I refused it as `wrong number of arguments`, as the pass refuses other errors that SQLite gives when it resolves names.

### What warrants review

That decision, and the decision that the result of `||`, `lower`, and `hex` is text that arithmetic never takes, and that their operands are never numbers, NULL, or (but for hex) blobs.

### Future work

The recognizer and its tests, the next step.

## Step 2: The recognizer, the checks against SQLite, and the refusals above the pass

**Author:** text-stmt builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "What SQLite itself rejects (a syntax error, a wrong number of arguments) must come out as SQLite's error with SQLite's offset [...] Statements with the new kinds must be refused cleanly by the layers that cannot run them yet (the engine must give `ErrNotSupported`, not a panic or a wrong answer): find where the engine and the evaluator `internal/expr` meet an unknown kind and make that a clear refusal with a test, touching as little as possible."
**Interpretation:** Build it, check each case against SQLite, and find the first place above the pass that meets the new kinds.
**Inferred intent:** A branch on which the pass takes goqite's id, and nothing above it breaks.

### What I did

`/internal/sql/stmt/stmt.go`: `ExprConcat`, `ExprCall`, `Expression.Function`, `stmt.Function` with `FuncLower` and `FuncHex`, and the documents of `Expression`, `Term`, and `Condition`. `/internal/sql/stmt/recognize.go`: a `place` passed down `recognizer.expression` (anywhere, in arithmetic, in a concatenation, the argument of lower or hex), `place.refusal`, `recognizer.operandLiteral`, `recognizer.call`, and the place in `unary` and `parenthesized`; a `FuncCall` after a `-` is an expression in `plainValue`, and parentheses around a call are `parentheses`. `/internal/sql/stmt/vocabulary.go`: `FuncCall.Distinct` and `FuncCall.Star` named.

Tests: 12 supported cases and 60 refused or syntax-error cases in `checkCases` of `/internal/sql/stmt/check_test.go`, six renamed or rewritten older cases, depth cases of chains of `||` and of calls in the subtest of the depth, and calls and concatenations in the subtest of 100 parentheses; `canonicalExpression`, `precedence`, `parenthesized`, `checkExpression`, `checkPlace`, and `oneToken` in `/internal/sql/stmt/stmt_test.go`, and `TestFunction_String`; the allow list in `/internal/sql/stmt/vocabulary_test.go`; two near misses of `/internal/sql/stmt/generate_test.go` that became supported.

Above the pass, the first place that meets the new kinds is `expr.Check`, through `engine.bindArithmetic`, which gave an internal error for an unknown kind. `/internal/expr/expr.go` refuses `ExprConcat` and `ExprCall` there as `concatenation`, `call of lower`, or `call of hex`, at the root, once the names are resolved. `/internal/engine/plan.go`: `formatArithmetic` writes the new kinds instead of panicking. `/internal/sql/stmt/stmttest/arithmetic.go`: `expressionClass` gives that refusal and `ArithmeticRefusal` knows it; `/internal/sql/stmt/stmttest/rule.go`: `ExpressionText` writes a call. Tests: `TestEngine_text` in `/internal/engine/expression_test.go`, a subtest of `TestCheck` in `/internal/expr/expr_test.go`, a text branch and two seeds in `FuzzExpr` of `/internal/expr/differential_test.go`, four seeds of `fuzzSQL` in `/internal/engine/differential_test.go`, cases of `TestArithmeticRefusals`, `TestHasExpression`, and a new `TestExpressionText` in `stmttest`, and a subtest of `TestArithmetic` in `/conn_test.go`.

### Why

Refusing at `expr.Check` and not at `engine.check` keeps SQLite's own errors of the names first (`no such table`, `no such column`), and covers every path that binds an expression, `ExecAll` included, which does not go through `engine.check`.

### What worked

The supported cases passed `checkMeaning` against SQLite on the first run, the tree check included, and every depth edge matched SQLite's `Expression tree is too large` on the first run. `make lint`: 0 issues.

### What didn't work

- `TestCheck` first failed on six older cases: `lower(v) = 'a'` is supported now, and `abs(1)` is `function other than lower or hex`; I changed `lower` to `upper` in three that test the order of refusals before OR, and renamed the others.
- `TestGenerate_nearMisses`: `"select * from A where lower(A) = 'a'", a near miss of slice 1, is supported`, and then `"update CAST set over = '-0' || '-0'"`. The forms became `upper(...)` and `%[3]v || null`. The pinned count of 2,275 did not move.
- The subtest of 100 parentheses with nested `hex(` failed in the tree check: `sqlite: string or blob too big (code 18)`, since hex doubles the length of its argument at each level. The nested calls are of `lower` now, with a comment.
- With texts of `||` and `lower` as seeds of `FuzzSQL` (written as temporary files in `testdata/fuzz` by a script in the scratchpad, and removed after), `go test -run 'FuzzSQL$' ./internal/engine/` panicked in `stmttest.ExpressionText` at `rule.go:342`, which read the second operand of every node that is not a leaf, from `subqueryCandidates` in `/internal/engine/subquery_test.go`. `ExpressionText` writes a call now, and the seeds pass, in memory and on the core.
- A first shell loop that wrote the seed files was refused by the harness as "too complex to verify that it stays inside the worktree"; a Python script with the directory as its argument did it.

### What I learned

The engine's walks over an expression (`missingName`, `argumentLengths`, `HasColumn`) go by `Operands` and need nothing for a new kind; only the evaluator, `formatArithmetic`, and the test rules switch on the kind.

### What was tricky

The offset of a refusal inside parentheses: `(w || 'a') * 2` is refused at `w`, since the parentheses are taken before the operand is read, and that is the first token of what is not supported.

### What warrants review

`place.refusal` and `recognizer.call` in `/internal/sql/stmt/recognize.go`; the names of the refusals, in `/docs/todo/text-functions.md`; and the changes outside `/internal/sql/stmt`, listed above.
