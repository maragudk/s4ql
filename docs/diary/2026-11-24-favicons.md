# Diary: Favicons from the barcode logo

The public site in `/site/` had a `favicon.svg` and an `apple-touch-icon.png`, both made by hand on 2026-11-16. Markus asked for the full set of favicons that his app template gets from `html.FavIcons` of `maragu.dev/glue/html`, the set that RealFaviconGenerator produces, but drawn from the site's barcode logo: the 32 bits of "s4ql" as bars.

## Step 1: Requirements and plan

**Author:** builder (favicons)

### Prompt Context

**Verbatim prompt:** (the brief from the lead, abridged) "You are giving the public site of s4ql (`site/`, served at www.s4ql.com) a full set of favicons drawn from its barcode logo. [...] In his words: "generate favicons like in ../app but with the barcode logo". [...] 1. The site gets the whole set, in `site/`: `favicon.svg`, `favicon-96x96.png`, `favicon.ico` (with 16, 32, and 48 pixel images), `apple-touch-icon.png` (180 by 180), `web-app-manifest-192x192.png`, `web-app-manifest-512x512.png`, and the web app manifest. 2. Every icon shows the barcode logo, the same mark as in the header, white on black as the site is. The bars sit on the pixel grid at every size: draw each size for its grid instead of scaling one bitmap down, so that no bar is blurred, and at 16 pixels use as many bars as stay legible, not all of them squeezed. The touch icon and the manifest icons have an opaque black background and enough margin for the masks that iOS and Android apply [...] `favicon.svg` stays a real vector and stays legible on a light browser tab as well as a dark one [...] 3. Name the manifest file `site.webmanifest`, not `manifest.json` [...] 4. Both pages [...] link the set in their heads in the order above, with relative paths [...] 5. The icons are reproducible: a small committed program or script draws them all from one description of the logo [...] 6. If anything checks the site's files [...] make it know the new files where needed."

**Interpretation:** a small Go program that draws seven files into `site/` from the word "s4ql", each raster size laid out for its own pixel grid; a Makefile target that runs it; six `link` and `meta` tags in the heads of the two pages in place of the two that are there.

**Inferred intent:** browsers, iOS, and Android all show the site's own mark, crisp, and a later change of the mark costs one edit and one command.

### What I did

Read the history of the existing icons. `site/favicon.svg` came with the site in `02394fe` and `site/apple-touch-icon.png` with the link previews in `1b50a63`; neither has a generator. `site/simulator/og.png` was made by a card page captured in Playwright, recorded in `/docs/diary/2026-11-18-simulator-page.md`, step 9. The mark in the headers is drawn by script from the bytes `0x73 0x34 0x71 0x6c`, one column per bit, 32 columns by 22 high.

The plan:

- The bits of "s4ql" are `01110011 00110100 01110001 01101100`. The ink runs from bit 1 to bit 29, 29 columns wide.
- Each size gets its own layout: which bytes of the word it shows, how many pixels a bit is, and how high the bars are, centred on the ink. At 16 pixels the full mark does not fit, so it shows "s4", the first two bytes: 13 columns of one pixel, four bars of 3, 2, 2, and 1 pixels.
- The program goes in `/internal/siteicons/` as a `main` package, as the tools in `/internal/simulator/serve/` and `/internal/simulator/sitecheck/` are, with a Makefile target `site-icons`.
- No check in CI that the committed files match the program's output: `/.github/scripts/changes.sh` lists `site/**` as a path that no test reads, and the repository checks generated Go code only, in its job for the schema.

### Why

The brief asks for pixel-exact bars at every size, which only a layout per size gives, and for reproducibility from one description, which the word "s4ql" is.

### What worked

Nothing to report yet; this step is the plan.

### What didn't work

Nothing yet.

### What I learned

`/site/` is an allowlisted path in `/.github/scripts/changes.sh`: a change to it alone runs only the job site. A test that read the files in `/site/` would therefore not run when only they change, which is a reason not to write one.

### What was tricky

The maskable safe zone: a circle of 40% of the size in radius. The ink's half diagonal must fit in it. At 512 with 10 pixels a bit, the ink is 290 by 220, half diagonal 182, inside 204.8. At 192 with 4 pixels a bit, 116 by 88, half diagonal 72.8, inside 76.8.

### What warrants review

The layouts per size, once they are in the code.

## Step 2: The generator, the icons, and the pages

**Author:** builder (favicons)

### Prompt Context

**Verbatim prompt:** the brief of step 1.

**Interpretation:** write the program test first, generate the set, link it from both pages, and check it by eye and in a browser.

**Inferred intent:** as in step 1.

### What I did

`/internal/siteicons/main.go` is a `main` package with no dependencies outside the standard library. `bars` turns the word into runs of set bits; `rects` centres the runs of a `layout` on its square; `draw` paints them white on opaque black; `ico` wraps PNG images in an ICONDIR of 6 bytes and an entry of 16 bytes each; `svg` writes the vector; `manifest` writes the manifest with `encoding/json/v2`; `write` puts all seven files into a directory. `make site-icons` runs it into `site/`. The tests in `/internal/siteicons/main_test.go` came first and failed against a stub: the runs of "s4ql"; for each layout, that every pixel is black or white, every column is all white over the bar height or not at all, the middle row reads as the bars at the layout's width a bit, and the ink is centred within a pixel with a margin; that the ink of the maskable icon is inside the circle of 40%; the ICO's directory and that each image decodes at its size; the SVG's structure; the manifest's members, decoded with unknown members rejected; and that two runs of `write` give the same bytes.

The layouts: 16 shows "s4", 13 columns of 1 pixel (four bars, 3, 2, 2, and 1 wide), 10 high; 32 and 48 show the whole word at 1 pixel a bit, 22 high; 96 at 2; 180 and 192 at 4; 512 at 10. The 32 icon puts each bit at the column it has in the header's mark.

The first `favicon.svg` was the 32 icon as a vector. On the contact sheet, Chromium drew it at 16 CSS pixels at a device pixel ratio of 1 with grey, smeared bars, since its 1-unit bars fall on half pixels. The SVG now holds both the 32 icon and the 16 icon at twice its size, and a `<style>` with `@media (max-width:24px)` shows the 16 one at small sizes. Screenshots of `<img>` elements at 16 and 32 CSS pixels, at device pixel ratios 1 and 2, show crisp bars in both, on white, `#dee1e6`, `#202124`, and `#35363a`.

The manifest lists the 192 icon with `purpose` `any` and the 512 icon with `maskable`. Both would fit the safe zone, but `any maskable` on one entry makes Chrome's manifest panel warn, and an icon of at least 144 pixels with `any` is what Chrome's installability needs.

In both pages the two old lines became the six of the set, in the brief's order, with relative paths, in the style of the pages' other tags (no closing slash).

### Why

Each size drawn on its own grid is what keeps the bars from blurring. The media query in the SVG is the one way that a single vector file is crisp at 16 pixels as well as above.

### What worked

- The contact sheet at `/private/tmp/claude-502/-Users-maragubot-Developer-s4ql/3a1f6409-2444-4c23-8123-ed5164204cd4/scratchpad/favicons/sheet.png` (outside the repository): every raster enlarged without smoothing, the ICO's three images parsed by a script in the page, the 180 icon under a rounded mask of 22.5%, the 512 icon with the safe zone drawn and cropped to it, and the SVG as drawn by Chromium.
- `make site-serve` on port 8097, and both pages loaded in Playwright: every icon and the manifest answer 200, no request fails, the console has no warning or error, and `Page.getAppManifest` gives no errors and two icons on both pages.
- `make site-check` passed. `golangci-lint run ./internal/siteicons/` gave 0 issues, and `go test -race -count 20 -shuffle on ./internal/siteicons` passed.
- GitHub Pages serves `.webmanifest` as `application/manifest+json; charset=utf-8`: checked on four Pages sites that have one, among them `https://bearsunday.github.io/site.webmanifest` (server `GitHub.com`). That is the type of mime-db for the extension.

### What didn't work

- The harness refused Bash commands that held a URL or path with "github" in it, or a `for` loop with `git diff` after it: "this command names git in a form too complex to verify that it stays inside the worktree". The probe of Pages went into a script in the scratchpad that builds the host name from a variable, and the edits of the pages went through the Edit tool.
- Drawing the SVG on a canvas with `drawImage` at 16 pixels does not evaluate its media query at 16 (the image is laid out at its own size), so the sheet shows the SVG through screenshots of `<img>` elements instead.
- `Page.getInstallabilityErrors` lists `in-incognito` and `start-url-not-valid` for both pages. The first is Playwright's context. The second I did not chase: the manifest has no `start_url`, as the brief's list of members has none, and the site is not meant to be installed.

### What I learned

- In Chromium, a media query on `max-width` inside an SVG used as an image is evaluated against the size the image is drawn at in CSS pixels. A query on `resolution` did not tell a device pixel ratio of 2 from 1 there, so the SVG shows the 16 icon at 16 CSS pixels on a high-density screen too, at 2 device pixels a bit.
- Go's `mime` table on macOS does not know `.webmanifest`, so the local server of `internal/simulator/serve` sends it as `text/plain; charset=utf-8`. Chromium does not check a manifest's type and parsed it.
- Go's PNG encoder writes an opaque image as 8-bit RGB, which is the colour type of every PNG of the set and of the old touch icon.

### What was tricky

The browser's favicon path cannot be watched in headless Chromium: it requested neither `favicon.svg` nor `favicon.ico`. That the media query picks the right drawing in a tab is inferred from how `<img>` draws it.

### What warrants review

- `/site/favicon.svg`: the media query and its threshold of 24 CSS pixels.
- The manifest's `purpose` values.
- At 180 CSS pixels the SVG has grey edges, since 180 is not a multiple of 32; nothing uses the SVG at that size (the touch icon is a PNG).

### Future work

None.
