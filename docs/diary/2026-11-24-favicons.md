# Diary: Favicons from the barcode logo

The public site in `/site/` had a `favicon.svg` and an `apple-touch-icon.png`, both made by hand on 2026-11-16. Markus asked for the full set of favicons that his app template gets from `html.FavIcons` of `maragu.dev/glue/html`, the set that RealFaviconGenerator produces, but drawn from the site's barcode logo: the 32 bits of "s4ql" as bars.

## Step 1: Requirements and plan

**Author:** builder (favicons)

### Prompt Context

**Verbatim prompt:** (the brief from the lead, abridged) "You are giving the public site of s4ql (`site/`, served at www.s4ql.com) a full set of favicons drawn from its barcode logo. [...] In his words: "generate favicons like in ../app but with the barcode logo". [...] 1. The site gets the whole set, in `site/`: `favicon.svg`, `favicon-96x96.png`, `favicon.ico` (with 16, 32, and 48 pixel images), `apple-touch-icon.png` (180 by 180), `web-app-manifest-192x192.png`, `web-app-manifest-512x512.png`, and the web app manifest. 2. Every icon shows the barcode logo, the same mark as in the header, white on black as the site is. The bars sit on the pixel grid at every size: draw each size for its grid instead of scaling one bitmap down, so that no bar is blurred, and at 16 pixels use as many bars as stay legible, not all of them squeezed. The touch icon and the manifest icons have an opaque black background and enough margin for the masks that iOS and Android apply [...] `favicon.svg` stays a real vector and stays legible on a light browser tab as well as a dark one [...] 3. Name the manifest file `site.webmanifest`, not `manifest.json` [...] 4. Both pages [...] link the set in their heads in the order above, with relative paths [...] 5. The icons are reproducible: a small committed program or script draws them all from one description of the logo [...] 6. If anything checks the site's files [...] make it know the new files where needed."

**Interpretation:** a small Go program that draws seven files into `site/` from the word "s4ql", each raster size laid out for its own pixel grid; a Makefile target that runs it; six `link` and `meta` tags in the heads of the two pages in place of the two that are there.

**Inferred intent:** browsers, iOS, and Android all show the site's own mark, crisp, and a later change of the mark costs one edit and one command.

### What I did

Read the history of the existing icons. `site/favicon.svg` came with the site in `02394fe` and `site/apple-touch-icon.png` with the link previews in `1b50a63`; neither has a generator. `site/simulator/og.png` was made by a card page captured in Playwright, recorded in `/docs/diary/2026-11-18-simulator-page.md`, step 9. The mark in the headers is drawn by script from the bytes `0x73 0x34 0x71 0x6c`, one column per bit, 32 columns by 22 high.

The plan:

- The bits of "s4ql" are `01110011 00110100 01110001 01101100`. The ink runs from bit 1 to bit 29, 29 columns wide.
- Each size gets its own layout: which bytes of the word it shows, how many pixels a bit is, and how high the bars are, centred on the ink. At 16 pixels the full mark does not fit, so it shows "s4", the first two bytes: 13 columns of one pixel, four bars of 3, 2, 2, and 1 pixels.
- The program goes in `/internal/siteicons/` as a `main` package, as the tools in `/internal/simulator/serve/` and `/internal/simulator/sitecheck/` are, with a Makefile target `site-icons`.
- No check in CI that the committed files match the program's output: `/.github/scripts/changes.sh` lists `site/**` as a path that no test reads, and the repository checks generated Go code only, in its job for the schema.

### Why

The brief asks for pixel-exact bars at every size, which only a layout per size gives, and for reproducibility from one description, which the word "s4ql" is.

### What I learned

`/site/` is an allowlisted path in `/.github/scripts/changes.sh`: a change to it alone runs only the job site. A test that read the files in `/site/` would therefore not run when only they change, which is a reason not to write one.

### What was tricky

The maskable safe zone: a circle of 40% of the size in radius. The ink's half diagonal must fit in it. At 512 with 10 pixels a bit, the ink is 290 by 220, half diagonal 182, inside 204.8. At 192 with 4 pixels a bit, 116 by 88, half diagonal 72.8, inside 76.8.
