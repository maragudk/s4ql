# Diary: the S3 client

Build the implementation of `store.Store` that talks to a real S3-compatible store, on the AWS SDK for Go, version 2. The interface, the simulated store, and the conformance suite are in `/internal/store` (`/docs/diary/2026-11-12-object-store.md`), and the storage core that uses them is in `/internal/core`. Markus chose the SDK over a client of our own on 2026-11-13, mostly for its credential chain. The spec's line for this work: "Real S3 checks that the simulated store behaves like the real one, and runs the integration tests."

## Step 1: Requirements

**Author:** s3-builder

### Prompt Context

**Verbatim prompt:** You are building the client for real S3 of s4ql, a Go SQL database whose truth is a log in an S3-compatible object store [...] You build the implementation that does. The product owner, Markus, decided on 2026-11-13 that it uses the AWS SDK for Go, version 2 ("SDK"), over a small client of our own, mostly for the SDK's credential chain. [...] A difference between the real store and the simulated one is the most valuable thing you can find. [...]
**Interpretation:** A package under `/internal/store/` with an implementation of `store.Store` on the SDK, which passes `storetest` against the project's Tigris bucket and a set of tests without a network against a local HTTP server, and which never reports "not applied" for a write that may have been applied.
**Inferred intent:** Give the core a real store that keeps the contract of `store.Store` exactly, and find out where the simulated store, which judges the core, differs from a real one.

### What I did

I read `/AGENTS.md`, the spec's "Terms" and "Testing", the todo's item "The S3 client and S3's checksums", `/internal/store/store.go`, the suite, the object store's diary, the three research notes, and the core's README on the commit and on unknown outcomes. The requirements of the brief:

1. The client passes `storetest.Test` against a real bucket. Each case runs under a new key prefix, and the test deletes what it wrote with the SDK directly. The bucket's settings come from the environment, and the access key and secret are never printed, logged, or written down.
2. The integration tests are skipped, with a message that says how to run them, when the settings are not in the environment. `make test` passes without them.
3. Tests without a network, against an `httptest` server that plays the store: every answer that the client maps to an error, every answer that it must report as an unknown outcome, a connection cut before and after the store applied a write, a body that ends early on a read, and a slow answer with a context that ends.
4. Never a false "not applied". The SDK sends no conditional write a second time by itself, or the refusal of a second attempt is an unknown outcome, shown with a test that cuts the connection after the store applied the first attempt. Every retry that the SDK or `net/http` can make by itself is checked, including the retry of `net/http` on a reused connection.
5. The checksum on upload is checked by the store, on the real bucket: a write with a wrong checksum stores nothing and fails with `ErrChecksum`. Find out how to make the SDK send our own SHA-256 so that Tigris checks it, and what AWS documents for the same request. If the store cannot be made to check it, stop and report.
6. The check on download: decide whether `Get` returns the stored checksum, takes one to compare, or neither, and say why.
7. The content is never held in memory, shown with a test of the heap for a large upload and download. One `PutObject` goes up to 5 GB; a larger object is refused before anything is sent.
8. Options of the constructor: bucket, endpoint, region, path-style addressing, and what else a compatible store needs. Credentials from the SDK's default chain. No option switches off a safety property.
9. No timeout of the client's own that ends a call earlier with another meaning, and no read of the caller's content after the call has returned.
10. One structured event per request through a `*slog.Logger` that discards by default, with the caller's context: Debug for success and for a refusal that is normal work, Warn for an unknown outcome and an unexpected answer. Operation, key, bytes, duration, status, request ID, and outcome, with the names of `/internal/core/telemetry.go` where the concept is the same.
11. The client's own code passes `simlint`, or is exempt with a reason.

Also: a short `README.md` next to the code; `/docs/todo.md` brought up to date; commits as I go, with no credential in a diff; and at the end `make test` and `make lint` without the settings, the integration tests three times in a row with them, and `go test -race` on the package.

The settings in the repository's `.env` are `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, `AWS_ENDPOINT_URL_IAM`, `AWS_REGION`, and `BUCKET`. The endpoint is `https://t3.storage.dev` and the region `auto`.

### Why

The core's design rests on the four errors of `store.Store` meaning "not applied". A real client that reports one of them for a write that was applied would make the core believe that a commit did not happen when it did.

## Step 2: The client, and how Tigris checks our checksum

**Author:** s3-builder

### Prompt Context

**Verbatim prompt:** The checksum on upload is checked by the store. A `Create` or `Swap` with a checksum that does not match the content stores nothing and fails with `ErrChecksum`, on the real bucket. The research note says that Tigris does not check a checksum that is sent as a header, and checks one in a trailer; find out, by testing, how to make the SDK send our own checksum so that the store checks it, on Tigris, and what AWS documents for the same request. If the store cannot be made to check our checksum, stop and report.
**Interpretation:** Before writing the client, find a request that carries our own SHA-256 and that Tigris refuses when it does not match, and then build the client around it.
**Inferred intent:** The second guard on a commit object's bytes must be real on the store that the project uses, not only on AWS's documentation.

### What I did

I added `github.com/aws/aws-sdk-go-v2` v1.48.0, its `config` v1.33.18, and `service/s3` v1.114.10. A throwaway test printed the middleware stack of `PutObject`, and the source of `service/internal/checksum` showed why a precomputed SHA-256 cannot go in a trailer through the SDK: `AddInputChecksumTrailer.HandleFinalize` returns early "If any checksum header is already set", and otherwise computes the checksum from the bytes it reads, so a trailer only ever carries the SDK's own checksum of the content, which always matches.

A second throwaway test sent eight PUTs with `If-None-Match: *` to the project's bucket, each with a middleware of its own, and read each key back with `ChecksumMode: ENABLED`:

| request | answer | stored |
|---|---|---|
| our SHA-256 in an aws-chunked trailer, right | 200 | the object and its SHA-256 |
| the same, wrong | `400 BadDigest`: "Aws-chunked trailer checksum does not match: x-amz-checksum-sha256 expected ..., computed ..." | nothing |
| trailer, empty content, right | 200 | the object |
| trailer, empty content, wrong | `400 BadDigest` | nothing |
| our SHA-256 as the signed payload hash (`x-amz-content-sha256`), right | 200 | the object, no checksum |
| the same, wrong | `400 XAmzContentSHA256Mismatch`: "The provided 'x-amz-content-sha256' header does not match what was computed." | nothing |
| payload hash, empty content, wrong | `400 XAmzContentSHA256Mismatch` | nothing |
| `x-amz-checksum-sha256` header, wrong | 200 | the object, with the wrong checksum |

So Tigris checks our checksum in two ways. The client uses the payload hash, `signPayload` in `/internal/store/s3store/s3store.go`, which sets `v4.SetPayloadHash` in a finalize middleware before `ComputePayloadHash`, and also sends the checksum as `x-amz-checksum-sha256`, so that the object carries it. I chose it over a trailer of our own because it needs no aws-chunked encoding written by us, it works over plain HTTP, where the SDK refuses trailers ("HTTPS required"), and a store must compute the payload's hash anyway to check a SigV4 signature. AWS documents both: the header ("If the checksum value calculated by S3 matches your provided value, the request is accepted. If the values don't match, the request is rejected.", https://docs.aws.amazon.com/AmazonS3/latest/userguide/checking-object-integrity-upload.html) and the payload hash ("If the upload request is signed with Signature Version 4, then Amazon Web Services S3 uses the `x-amz-content-sha256` header as a checksum instead of `Content-MD5`.", https://docs.aws.amazon.com/cli/latest/reference/s3api/upload-part.html).

Then the package `/internal/store/s3store`: `s3store.New(ctx, s3store.Options)` with `Bucket`, `Endpoint`, `Region`, `PathStyle`, `RootCAs`, and `Logger`; `Client.Get`, `Client.Create`, and `Client.Swap`; `s3store.MaxSize` and `s3store.ErrTooLarge`. In `/internal/store/s3store/s3store.go`, the transport is an `http.Transport` of our own with HTTP/1.1 only, no proxy, no timeout, and a `CheckRedirect` that follows nothing; the SDK's retryer is `aws.NopRetryer` with `RetryMaxAttempts` 0, set in the option function of `s3.NewFromConfig` so that it comes after the environment; `request.refusal` maps 412 `PreconditionFailed`, 409 `ConditionalRequestConflict` on a swap, 404 `NoSuchKey` on a swap, and 400 `BadDigest` or `XAmzContentSHA256Mismatch`, each with the code and not the status alone, and returns no refusal if `httptrace` counted more than one write of the headers. `/internal/store/s3store/content.go` has the `guard` of a write's content and the `body` of a read, which logs the read's event when it is closed. `/internal/store/s3store/telemetry.go` has the event `store_request` and its attributes. `/internal/simlint/simlint.go` exempts the package.

The tests without a network run against `fake` in `/internal/store/s3store/fake_test.go`, an `httptest.NewTLSServer` that applies conditional PUTs, checks `x-amz-content-sha256` and `x-amz-checksum-sha256` as S3 does, and lets a test take over any request. The integration tests in `/internal/store/s3store/s3store_test.go` run `storetest.Test` with a new prefix for each case, and five checks of their own. A mutation script in the scratchpad, which replaces one file at a time with `go test -overlay`, checked that the tests catch 26 of 28 changes to the client; the two that they miss are in "What didn't work".

### Why

A wrong "not applied" from the client would make the core believe that a commit did not happen when it did. Every way for a write to go out twice is closed, and the one that cannot be closed from outside net/http, its own retry on a reused connection, is caught by the count of attempts.

### What worked

- The conformance suite passed against Tigris at the first run: `S4QL_S3_BUCKET=$BUCKET go test ./internal/store/s3store/ -count=1 -run 'conformance|realBucket' -v`, after `set -a; . ./.env; set +a`, passed 17 of 17 cases in 14 s, and the checks of `TestClient_realBucket` in 7 s. A listing of `s4ql-test/` afterwards was empty.
- Keys with `?`, `#`, `%20`, `+`, `//`, a leading and a trailing slash, a tab, a newline, `...`, NFC and NFD forms of é, and keys of 1024 bytes are kept apart and read back on Tigris.
- A large object of 256 MiB up and down raised the heap's live objects by 256 KiB at their peak, sampled every millisecond with `runtime/metrics`.
- `AWS_MAX_ATTEMPTS=5` and `AWS_RETRY_MODE=adaptive` in the environment still give one request for a write and for a read.

### What didn't work

- `go test ./internal/store/s3store/ -count=1 -run Scratch` was refused at first by the sandbox, with `This agent is isolated in the worktree ..., but this command is too complex to verify that it stays inside the worktree`, because I wrote the test file with a here-document in the same command. Test files are now written with the editor, and scripts run from the scratchpad.
- The first mutation run missed six changes: the guard on the content, both of them; a refusal after two attempts; both length checks of a read; and the length of the content measured from its start. Three mutants did not build at all, because the change left an import unused. The offset of the content now has a test against the fake, the count of attempts and the length checks have internal tests, and the mutants keep their imports.
- The guard could not be shown end to end. I tried three ways to make net/http read a write's body after `RoundTrip` returned: an answer of 412 before the body was read, with the connection closed and with it held open without reading; and a context that ends while a slow body is read. With Go 1.27.3, `RoundTrip` returned only after the read in progress had ended, every time, and no read started after it. `http.RoundTripper` still allows it ("depending on the implementation may do so in a separate goroutine even after RoundTrip returns"), so the guard stays, and is tested directly in `/internal/store/s3store/content_internal_test.go`. Removing the call of `guard.close` in `Client.put` is a mutant that no test catches.
- The heap test measured `runtime.MemStats.TotalAlloc` first, which failed under `go test -race` with `74 MiB allocated`: the race detector allocates as data goes through. It now samples the bytes of live objects, which is what "the content is never held in memory" means.
- `ChecksumMode: ENABLED` on a read is a mutant that no test catches, because `ResponseChecksumValidation: WhenSupported` makes the SDK ask for the checksum by itself. Both stay.
- `golangci-lint` reported `ST1008: error should be returned as the last argument` on the first form of the refusal mapping, and two unchecked `Flush` calls in the tests.

### What I learned

- A write without a checksum is sent with `UNSIGNED-PAYLOAD` over HTTPS, so the SDK does not read the content before it sends it.
- 409 on a create cannot be `ErrExists`: AWS documents it for `If-None-Match` only when a delete races the write, and then no object may be there. It is an unknown outcome.
- Go follows a 307 of a PUT whose body is empty, because it needs no `GetBody` to send an empty body again. That is a second request for a conditional write, and the reason for `CheckRedirect`.
- The SDK's default chain reads `AWS_ENDPOINT_URL_S3` by itself, so `Options.Endpoint` matters only when the environment does not have it.

### What was tricky

- Finding where in the middleware stack to set the payload hash: `ComputePayloadHash` computes one only if none is in the context, and `SigV4ContentSHA256Header` copies the context's value into `x-amz-content-sha256`, so the middleware goes before the first.
- Deciding what to count as an attempt. The SDK's own retry loop is off, and net/http's retry is inside `Transport.RoundTrip`, where no wrapper of the transport sees it. `httptrace.ClientTrace.WroteHeaders` is called inside it, once for each write of a request.

### What warrants review

- `/internal/store/s3store/s3store.go`, `request.refusal`: that each of the four errors is returned only for an answer that shows that the write was not applied.
- `/internal/store/s3store/s3store.go`, `New`: that no setting of the environment can turn on a retry. The test sets `AWS_MAX_ATTEMPTS` and `AWS_RETRY_MODE`, but the SDK reads more.
- `/internal/store/s3store/s3store_test.go`, `TestClient_connections`: the cut after the store applied a write, on a reused connection.

### Future work

- The README of the package, `/docs/todo.md`, and the self-review.

## Step 3: Self-review, the README, the todo, and verification

**Author:** s3-builder

### Prompt Context

**Verbatim prompt:** Self-review as your standing instructions say, and fix what is real. [...] When the client is built, bring `docs/todo.md` up to date yourself: delete from "The S3 client and S3's checksums" what is built, and keep what is open. [...] Verify at the end: `make test` and `make lint` pass without the settings in the environment; the integration tests pass with them, run three times in a row; `go test -race` passes on your package.
**Interpretation:** Run the `fabrik:code-review` skill with two competing reviewers over the branch, fix what they found that is real, write the README and the todo, and run the verification on the code as it is after the fixes.
**Inferred intent:** The client is the seam that real S3 is held to, so it has to survive someone who tries to make it report "not applied" for a write that was applied.

### What I did

A writer sub-agent drafted `/internal/store/s3store/README.md` from a brief with the facts of Step 2. I corrected one sentence in it: a PUT is replayable to net/http only with an `Idempotency-Key` header and a body that is nil or that `GetBody` gives again, and the client's PUT has neither. I rewrote the item "The S3 client and S3's checksums" in `/docs/todo.md` to what is open: the check on download, which is not the one that was agreed, a commit object above 5 GiB, the tests in CI, and AWS.

Two reviewers on the `fable` model reviewed the branch independently, with `go test -overlay` from the scratchpad. Neither found a path that returns one of the four errors for a write that was applied with the code as it was used, but each found one that came close. What I fixed:

- **An error of the content could make an unknown outcome look like a refusal** (reviewer B, serious). The unknown path wrapped the SDK's error with `%w`, and that error wraps whatever the caller's content returned. net/http reads once more after the length of the content, when the store may have it all, so content that failed there with an error wrapping `store.ErrExists` gave `errors.Is(err, store.ErrExists)` for a write that was stored. The error of an unknown outcome now has the text of its cause and wraps only `context.Canceled` or `context.DeadlineExceeded` (`unknown` in `/internal/store/s3store/s3store.go`), and the errors of the content's seeks wrap nothing. A test fails content with each of the four errors.
- **The count of attempts counted a request for credentials** (both reviewers). The `httptrace` was on the context of the call, which the SDK passes on to its credential providers. With credentials from `AWS_CONTAINER_CREDENTIALS_FULL_URI`, the first create of an existing key was an unknown outcome with `attempts` 2. The trace is now put on the request in a finalize middleware after signing (`request.trace`), and a refusal counts only with exactly one attempt, so a count that never reached the transport is unknown too. A test serves credentials over HTTP and expects `ErrExists` with one attempt.
- **No test without a network checked that a swap is conditional** (reviewer A, serious as a gap). Replacing `If-Match` with nothing passed every test. `TestClient_conformanceOnFake` runs the conformance suite against the fake, and the test of the request checks the headers `If-None-Match` and `If-Match`.
- **Step 2 was wrong about why the guard cannot be shown** (both). net/http in Go 1.27.3 does read a body after `RoundTrip` returns, with a plain `http.Client`. What stopped it in my tests was smithy-go, which wraps the body in a reader that it closes after `http.Client.Do`. The guard stays as a second layer, because that is not part of the SDK's API, and the README says so.
- **The rest:** content whose offset is past its end is refused before anything is sent (both); an endpoint that is not an http or https URL makes `New` fail (reviewer A); a call that the client refuses before it sends anything logs an event at Warn with the outcome `not_sent` (reviewer B), so that a write that is too large is not silent; the tests without a network no longer read the machine's AWS configuration (both), through `isolate` in `/internal/store/s3store/fake_test.go`; the test of a slow read no longer needs a TLS handshake within 50 ms (both; it failed 16 of 480 and 23 of 600 times under load); the large object is 64 MiB, not 256; the payload-hash middleware is placed by `(&v4.ComputePayloadSHA256{}).ID()`, not a literal; a sentence of `telemetry.go` that named the storage core, and single-use constants for the names of the event and its attributes, are gone (both); and new tests cover HTTP/1.1 against a server that offers HTTP/2, no proxy, a certificate outside `RootCAs`, a 1024-byte key, a read without a content length, a 412 without a body, a 500 with the code `BadDigest`, and the level and outcome of every kind of event.

What I did not change:

- A misused call, an invalid key or a swap from an empty version, returns an error, which `store.Store` reads as an unknown outcome, where `simstore` panics (reviewer A). Changing it is a question of the interface's contract for the lead.
- A 412 without a body is a refusal: the SDK takes the code `PreconditionFailed` from the status text. Step 2 said that each mapping needs the code; for 412 the status alone gives it. A test now pins it.
- `New` may make requests outside the store with `AWS_DEFAULTS_MODE=auto`, for the SDK's defaults (reviewer B). Its doc comment now says that it sends no request to the store.

### Why

The four errors are the one promise of the client that the core cannot check. Both findings that came close to breaking it were about something outside the client's own code, the caller's content and the SDK's credential providers, reaching into how the client reads an answer.

### What worked

The verification after the fixes, without `S4QL_S3_BUCKET` in the environment: `make test` and `make lint` pass, and `go test -race -count=1 -shuffle on ./internal/store/s3store/` passes in 4 s. With the settings of the project's bucket: three runs in a row of `S4QL_S3_BUCKET=$BUCKET go test ./internal/store/s3store/ -count=1 -shuffle on -v` passed in 19.4 s, 15.2 s, and 15.4 s, and the same with `-race` in 19.0 s. A listing of `s4ql-test/` afterwards was empty. The mutation script now has 40 mutants, and the tests catch 38. The two that survive are equivalent while the SDK behaves as it does: removing `guard.close` from `Client.put`, and `ChecksumMode: ENABLED`.

### What didn't work

- A test that sets `HTTPS_PROXY` and counts requests to a proxy server did not catch a transport with `Proxy: http.ProxyFromEnvironment`, because net/http reads the proxy variables once per process, and another test had read them first. The check is now an internal test that the transport's `Proxy` is nil.
- The first run of the updated mutation script skipped five mutants with `pattern found 0 times`, because the refusal now returns its outcome first. The patterns are updated.

### What I learned

- `aws.CredentialsCache.Retrieve` passes the values of the call's context on to the credential provider, so anything put on that context, such as an `httptrace.ClientTrace`, sees the SDK's own requests too.
- `http.ProxyFromEnvironment` caches the environment for the life of the process.

### What was tricky

Keeping the error of an unknown outcome useful without letting it wrap anything that could look like a refusal. The contract allows it to wrap a context error, and the core's callers may test for one, so those two are the only ones it keeps.

### What warrants review

- `/internal/store/s3store/s3store.go`, `unknown` and `request.trace`.
- `/docs/todo.md`, the item "The S3 client and S3's checksums": the check on download is a deviation from what was agreed, for Markus.

### Future work

- The lead decides whether a misused call should panic, as in `simstore`, or wrap an error of its own.
- `simstore`'s `AllFaults` delays a stuck write by up to 60 s, while a signed request is accepted for 15 minutes on AWS and for at least 1000 s on Tigris (`/docs/research/s3-clock.md`), and nothing documents how long a store may hold a request it has received. The core does not rely on a bound, so this is described, not changed.
