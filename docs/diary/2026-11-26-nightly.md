### What I did

The engine package is the same at `fc854d36` and at `main` of that morning: only `/internal/sql/stmt/split_test.go` and docs differ. So I replayed from a test binary built once at `main` (`go test -c -o …/engine.test ./internal/engine/`).

- C1, five planted bugs at seed 19821 of the hammer workload: `copySelf` and `copyAcross` ("finds something without the bug"), and `setFromNew`, `evalStops`, and `errorSkipsRow` ("finds the bug by another violation"). The violation is the same in all five: statement 133, an UPDATE with arithmetic and two subqueries of `*` of a table of three columns, "gives \"s4ql: not supported: second subquery of * of more than one column (at offset 312)\", and SQLite gives 1/1: sub-select returns 3 columns - expected 1". `-replay 19821 -workload hammer` fails without any bug. The refusal is s4ql's own rule (`subqueries.widths` in `/internal/engine/subquery.go`), which `subqueryRule` reproduces. But a statement with arithmetic that was refused goes to `run.arithmetic` in `/internal/engine/simulation_test.go`, and that function counted every error of SQLite's prepare as a violation. The pair's `checkArithmetic` already leaves such a statement to the rule of types. The sqlite3 CLI gives the same `sub-select returns 3 columns - expected 1` on the reduced `update v set t1 = null where t1 = 441 and t1 + 1 <= (select * from v) and (select * from v order by t1 limit 1) > "ÉTÉ" + .0`.
- C2, `nullCompares` at seed 12973: "the statement 178 … gives the subquery 2 the value x'c0ca5e631709db', and SQLite one of [null]". The seed passes without the bug. The condition of subquery 2 is `exclude + ? = -0E0` with the argument NULL. In SQLite that condition is NULL for every row, so the subquery has no row. The bug makes a comparison with a NULL side true (`/internal/engine/operator.go`, which the conditions of a subquery use too), so the subquery finds a row. `arithmeticFinds` did not list "gives the subquery".
- C3, `TestDifferential` sequence 47712 (profile mixed): a delete with two subqueries, with the arguments `[-9223372036854775808, 0, 3]`. The engine gives "integer overflow in * (at offset 342)" as the rules choose. The other instance gives no error, and neither changes a row. `-seed 47712 -sequences 1` failed in 152 of 300 runs. Offset 342 is `ConFLiCT*?` (× 3) in subquery 2, which has no ORDER BY. Its first row is the first of the direction that each engine draws. One direction reaches −9223372036854775806 before a row that matches and overflows (s4ql's rule; SQLite goes to REAL). The other direction finds a positive row first and stops. The instance draws its directions from a seed of the sequence. The other instance draws from a seed it draws itself, so the result changes from run to run.

### Why

A seed that a planted bug finds by a symptom outside its list fails the subtest, and so does one that fails without the bug. A difference between the two instances of the pair fails `TestDifferential`. Each of the three is legal by s4ql's rules.

### What worked

Running `-seed 47712 -sequences 1` in a loop of 300 runs showed at once that the failure depends on a draw, and the failing runs logged the seeds of their instances.

### What didn't work

The first run of the replay printed nothing about the other instance's seed. The nightly's log has no "drew the directions" line either, so the exact case of the night cannot be replayed (see step 3).

### What I learned

A subquery draws its direction like a query, even inside an update or a delete, whose own scan draws none (`Engine.reading` in `/internal/engine/engine.go`). So a write with arithmetic in a subquery can give different answers on two engines with the same path.

### What was tricky

C1 came from the meeting of two areas: the refusal of slice 15 for two wide subqueries, and the check of arithmetic of #156. Neither check was wrong alone.

### What warrants review

That the widened symptom of C2 is for `nullCompares` alone. No other bug of arithmetic was seen to give it.

## Step 2: the fixes, and a first fix of C3 that lost a check

**Author:** nightly-2026-11-26

### Prompt Context

**Verbatim prompt:** "Now apply the fixes and land them. … Also show that C3 loses no check: plant one fault of your own in the engine's arithmetic of a write with a subquery (for example a wrong answer for one scan direction only) and show `TestDifferential` still fails on it; revert."
**Interpretation:** apply C1, C2, and C3. Prove that each passes the replays and the nightly's commands, and that C3 hides no fault that the test found before.
**Inferred intent:** green nightlies, with no check lost.

### What I did

- C1: `run.arithmetic` now gives no violation where SQLite does not prepare the statement and s4ql's answer is the refusal that `subqueryRule` gives.
- C2: `nullCompares` also accepts "gives the subquery", with a sentence on how the bug gives it.
- C3, first version: an `Engine.Draws` in `/internal/engine/export_test.go`, with which `pair.bothWays` set the other instance's directions to the instance's (`SetSeed`) for a write with arithmetic. It passed every replay, and seed 47712 failed in 0 of 100 runs.

I planted a fault to check the first C3: in `build.value` of `/internal/engine/subquery.go`, a subquery of a write that read backward dropped its evaluation error (`errors.Is(err, expr.ErrEvaluation) && inside.how.backward && !b.how.drawn`, then `break`). `TestDifferential -sequences 400` passed with the fault and the first C3. Without C3 it failed in sequences 5997 and 20909 ("with 0 changes as the rules choose and 1 by the path"). With both instances drawing alike, `bothWays` could not see the difference any more, and no other check models a subquery's direction. So the first C3 lost a check.

C3, as it is now: the other instance keeps its own draws. `bothWays` excuses a difference only when one side is an evaluation error whose offset is inside a subquery of an update or a delete with arithmetic, the other side succeeds, neither side changed a row, and `pair.justify` justifies the error (without the values that the instance computed, which belong to another read). With the planted fault, `-sequences 400` still failed, in two sequences, both "with 0 changes as the rules choose and 1 by the path". Then I reverted the fault.

### Why

When neither side changes a row, the two instances keep the same state. The error side is then checked against SQLite's result of its operator, and the other side's success is what a read in the other direction legally gives.

### What worked

Planting the fault before landing. It showed the cost of the first C3, which every replay had missed.

### What didn't work

The first C3 (mirroring the draws): `go test -count=1 -p 3 -run '^TestDifferential$' ./internal/engine/ -sequences 400` passed with the planted fault, while the same run without C3 failed in two sequences.

### What I learned

The comparison of the two instances is the only check of the direction of a subquery: `pair.due` does not model which rows a subquery reads before its first match.

### What was tricky

Making the two instances deterministic looked strictly better, and it was not. The randomness between the instances is a check of its own.

### What warrants review

The guard of the excuse in `subqueryErrorOfOne` and `pair.bothWays` of `/internal/engine/differential_test.go`. A fault that drops a subquery's error by one direction where the write changes nothing either way is still excused. That is the open item in `/docs/todo/ci.md`.

### Future work

A check of due errors in a subquery by the direction it read, recorded in `/docs/todo/ci.md`.

## Step 4: the failures of `TestDifferential -sequences 400` on main

**Author:** nightly-2026-11-26

### Prompt Context

**Verbatim prompt:** "Now take the new failures you found, in the same way (reproduce, decide with evidence, fix, land), on a fresh branch … (4) Then run every generated test at the sizes the nightly uses, not only this one … so that tonight's nightly has been run here before it runs there."
**Interpretation:** list the ten failing sequences, find the cause of each class, fix it in the test where the test is wrong, prove each fix with a planted fault, and run every night-sized generated check before landing.
**Inferred intent:** tonight's nightly runs green, and a builder can run it here first.

### What I did

After #163 and #164 landed, `go test -count=1 -p 3 -run '^TestDifferential$' ./internal/engine/ -sequences 400` failed ten sequences on main, with main's own tests. There were three classes, and none is a fault in s4ql:

- 22752, 4558, 7214, 7438, 10030, 10510, 11790, and 13294: "the walk reaches its statement N of N, and the generator wrote N-1 texts, so the oracle cannot tell whether s4ql supports it". Every one of these texts holds `select * from X; select * from X`, a form of `Others` in `/internal/sql/stmt/stmttest/sequence.go` that `Sequence.several` joins through `Sequence.other`. SQLite reads it as two statements, and so do `sqliteParts` and `stmt.Split`. The generator gave it one entry of `Supports`, so the walk in `/internal/engine/several_test.go`, which indexes `Supports` by SQLite's statements, ran out of entries, or gave the statement after it the entry of another text. The two readings of s4ql and SQLite agree; the generator miscounted.
- 14222: "its statement 3 of 4 alone: … values (1e999): the engine does not support a statement that the pass supports". This is the same misalignment: the text after the two selects is an `Others` text, `insert … values (1e999)`, which got the entry `true` of the next text.
- 8782: an `update … returning "pragma", "pragma"` of two rows under the lowered length limit, which sets the REAL key of both rows to `-0E+00`. The engine gives "UNIQUE constraint failed: DO.TempoRARy" and SQLite gives "string or blob too big". Reduced in sqlite3 with `.limit length 1000`: on `create table d (p blob not null, k real primary key not null) strict, without rowid` with two rows, `update d set k = -0.0, p = x'<995 bytes>' returning p, p` gives "string or blob too big", the same update without RETURNING gives "UNIQUE constraint failed: d.k", and a one-row update with RETURNING gives "string or blob too big". So SQLite builds the RETURNING row of the first row before it checks the key of the second. This is the recorded difference of slice 14 (s4ql does not refuse a row of RETURNING longer than its row in the table) in a new shape. `pair.returningTooBig` excused it only where the statement succeeds without RETURNING.

Fixes:

- `Sequence.several` gives each statement of an `Others` text its own entry of `Supports`, counted with `statementsIn` (runs of tokens between semicolons), and a text that runs again keeps its count. `Call.Supports` now documents one entry per statement as SQLite reads them. `TestSequence_several` checks `len(Supports) >= Statements` and that the two-statement form is reached. The generator draws nothing new, so every sequence stays as it was.
- `pair.returningTooBig` also takes a statement that fails without RETURNING under the limit, provided its error is not one of length and is the error that SQLite gives with RETURNING without the limit. The caller then compares the engine's answer with that error. `TestPair_returning` pins the reduced case, twice. It failed on main's `differential_test.go` ("UNIQUE constraint failed: d.k" against "string or blob too big") and passes with the fix.

Proof by planted faults, each reverted:

- In `Conn.ExecAll` (`/internal/engine/several.go`), a write that follows two selects of the text is skipped. Of the ten sequences, 7438, 10030, and 10510 then fail ("ExecAll logs the events of statements …"). The others have no write after the two selects.
- In `uniqueFailed` (`/internal/engine/errors.go`), the column of the message gets a `!` for the table `d`. The new subtest of `TestPair_returning` then fails ("UNIQUE constraint failed: d.k!" against "d.k"), so the excuse compares the error and does not just pass it.

The nightly's generated checks, run here in this order, one at a time, after the fixes, all passed:

- `go test -count=1 -p 3 -run '^TestDifferential$' -timeout 40m ./internal/engine/ -sequences 400`: ok in 317 s.
- `S4QL_ENGINE_SIM_SEEDS=100 go test -count=1 -p 3 -run '^TestSimulation$' -timeout 40m ./internal/engine/`: ok in 141 s.
- `S4QL_ENGINE_SIM_SEEDS=1000 go test -count=1 -p 3 -run '^TestSimulation_plantedBugs$' -timeout 300m -v ./internal/engine/`: all 40 bugs passed, unsharded, in 3,336 s.
- `cd internal/sqlite/crosscheck && go test -count=1 -p 3 -timeout 40m ./drivercheck/`: ok in 24 s. Its `TestGenerated` has no size of the night, and neither has `TestConn_differential`.

### Why

A text's statements and the generator's entries for them must line up for the walk to judge each statement by its own support. The length difference is the one the lead decided to keep, so its excuse has to take every shape in which it shows, but no other error.

### What worked

Counting the failures by their texts: all eight of the first class held the same form of `Others`.

### What didn't work

`go test ./internal/sqlite/crosscheck/drivercheck/` from the root fails with "main module (maragu.dev/s4ql) does not contain package maragu.dev/s4ql/internal/sqlite/crosscheck/drivercheck", because the driver check is a module of its own. It runs from `internal/sqlite/crosscheck`, as the Makefile's `test` does.

### What I learned

#163 documented `Supports` as one entry per joined text, while its oracle read it as one per statement. A comment beside a field can record a mismatch like that without the code noticing.

### What was tricky

Sequence 14222 looked like a third class (a refusal of `1e999`), but it was the misalignment of the first class in another symptom.

### What warrants review

`statementsIn` in `/internal/sql/stmt/stmttest/several.go`, and the guard in `pair.returningTooBig` of `/internal/engine/differential_test.go`.

### Future work

None beyond `/docs/todo/ci.md`.
