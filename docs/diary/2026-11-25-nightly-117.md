# Diary: the nightly run passes again (issue #117)

The workflow `/.github/workflows/nightly.yml` failed every night from 2026-11-21 to 2026-11-25, five runs, and opened issue #117. An investigation by the lead found six causes, none a fault in s4ql: each is the oracle of a test that is too narrow, on seeds or sequences that CI's shorter runs do not reach. This task fixes the six in the tests, runs what the nightly runs, and records how the nightly is watched from now on.

## Step 1: the four planted bugs whose symptoms were not in their lists

**Author:** builder

### Prompt Context

**Verbatim prompt:** "The nightly run has failed every night since 2026-11-21 (issue #117, five runs). An investigation reproduced every failure and found that none is a fault in s4ql: each is a test's oracle that is too narrow. CI does not reach these seeds; the nightly runs many more. Your task: fix the six causes in the tests, show that the nightly's commands pass, and add a note on how the nightly is watched." (the opening of the lead's brief, which then lists the causes C1 to C6 with their replays and fixes)
**Interpretation:** for each cause, replay the seed, see that the planted bug (or a known, recorded difference) causes exactly that symptom, and only then widen the oracle by the smallest hunk; then run the nightly's simulation and generated jobs in full.
**Inferred intent:** the nightly should be green, so that a red one means something again, without hiding a real fault behind a wider list of symptoms.

### What I did

I replayed each seed with the command that the nightly printed, with the bug and without it.

- C1, core, `renewOutsideLock`, seed 411: `go test -count=1 -run '^TestSimulation$' -v ./internal/core/ -replay 411 -bug renewOutsideLock`. The first violation is "the commit of transaction 17867670975346570105 was acknowledged, and the log does not have it". The trace shows the mechanism: the renewal's request 49 is stuck in the network, sent without the manifest lock (the bug, in `send` of `/internal/core/lease.go`); meanwhile caller-0's commit retries its swap from `a735deaa` until request 63 lands at `1c0b7a11`; the renewal then reports "outcome=unknown", takes the lock, and resends its old 312-byte manifest from `1c0b7a11` as request 64, which is applied and drops the commit. A commit and a renewal can be in flight from one version only under the bug. With `-clean` the seed passes with no violation. I added the symptom to the bug's `symptoms` in `/internal/core/workloads_test.go`, with a comment on how the bug gives it.
- C2, engine, `replaceExisting`, seeds 7557 and 769: replayed with the test binary built once into the scratch directory, `-replay 7557 -workload default -bug replaceExisting`. The violation is "commit 11, … stores a value of another type than its column: s4ql: not supported: argument 1, which is an integer, for the column /* x */.TEMPORARY of type TEXT". The type rule (`typeRule`) runs on SQLite's state, where the CREATE TABLE IF NOT EXISTS did nothing, and the engine stores into the replaced table, whose column has another type. Seed 769 failed only on 2026-11-21 (run 44855847000, commit `9ae52f6`) with the same symptom; it no longer reproduces at `main`, since the profile has changed since. Both seeds pass without the bug.
- C3, engine, `keepFailed`, seed 20456: the violation is "the statement 30, …, of the transaction 8 (write), which began at commit 5, gives … rows [3] and in SQLite … [4]". The trace has updates in write transactions that fail with "UNIQUE constraint failed: NO.fUll"; under the bug what they changed stays, and a later select of the transaction sees it. Passes without the bug.
- C4, engine, `swapSubqueries`, seed 10252: the violation is "s4ql: internal error: a comparison of a value of kind blob with one of kind text", on a select with two subqueries, one compared with a TEXT column and one with a BLOB column. The swap puts each value into the other's comparison after the check of the types, as the comment of the bug already says for the storage. Passes without the bug.

For C2 to C4 I added the symptom to the bug's finds in `/internal/engine/simulation_test.go`, each with a sentence in the comment above it.

### Why

A seed that finds a planted bug by a symptom outside its list fails the subtest, so every seed of the nightly's 1000 that finds the bug some other legal way turns the night red. The lists were written from the 200 seeds that CI runs.

### What worked

Building the engine's test binary once (`go test -c -o /Volumes/990/s4ql/nightly-117/engine.test ./internal/engine/`) made the replays quick. The core's replay has `-clean`; the engine's has no such flag, but a replay without `-bug` runs the same seed and profile without the bug, which is what the planted-bug test itself runs.

### What didn't work

A loop over the seeds in zsh, `for a in "7557 default replaceExisting" …; do set -- $a; …`, did not split `$a` into words (zsh does not split unquoted parameters), so each run got one argument and wrote its log to a file named `eng-7557 default replaceExisting.log`. A script run with `sh` from the scratch directory did it.

### What I learned

The engine's planted-bug test stops at the first unknown symptom of a bug (`t.Fatalf`), so a bug's later seeds are not checked in a night where an early seed fails: the full run after the fixes can still show new ones.

### What was tricky

The engine's trace does not hold the text of a CREATE TABLE, so for C2 the different column type is read from the rule's message and the bug's description, not seen directly; the run without the bug passing is the control.

### What warrants review

That each added symptom string is specific enough: "internal error: a comparison of a value of kind" would also hide an engine fault of that kind, but only under `swapSubqueries`, and the bug's run without it on every finding seed still checks that nothing is found without the bug.

### Future work

None from this step.

## Step 2: the two known differences of `TestDifferential`, and a run that goes past a failure

**Author:** builder

### Prompt Context

**Verbatim prompt:** the same brief as step 1; for this step its items C5 ("`returning` under the lowered length limit, `TestDifferential` sequence 16832") and C6 ("a subquery under a sort that is too big, `TestDifferential` sequence 25196 (hidden behind C5, because the test stops at the first failing sequence)"), the entry for `AGENTS.md`, and "A short record in `docs/todo/ci.md` only if something stays open (for example that `TestDifferential` stops at its first failing sequence, which hid C6 behind C5: say whether reporting all failing sequences of a run would be cheap, and do it if it is a few lines)."
**Interpretation:** widen the excuse of slice 14's known difference to every statement with RETURNING, keeping its other guards; give `subqueryCandidates` SQLite's answer without the limit where slice 13's known difference refuses the subquery alone; pin both by hand; and make `TestDifferential` report more than one failing sequence.
**Inferred intent:** the nightly's generated job passes for the known reasons only, and a later failure does not hide behind an earlier one.

### What I did

C5: `go test -count=1 -run '^TestDifferential$' ./internal/engine/ -seed 16832 -sequences 1` failed with "the engine gives columns \"oId REAL, RIGht TEXT\", rows [\"real 0,…\"] and SQLite 18/18: string or blob too big" on an insert of `-0E+00` and a long text with `RETURNING *`. Red first: I added to the subtest of `TestPair_returning` in `/internal/engine/returning_test.go` the lead's smallest case, `create table c (a real not null, b text not null primary key) strict, without rowid` and `insert into c … (0.0, 995 × x) returning *`, once with the text as an argument and once as a literal; it failed with the same refusal. Then I removed the loop over `r.Columns` that required a column named twice from `pair.returningTooBig` in `/internal/engine/differential_test.go`, and rewrote the comments of the function and of `excusedReturningTooBig`, whose text changes too. The subtest is renamed to say a row of RETURNING longer than its row in the table. In `/docs/todo/slice-14.md` the note of the difference no longer says "waits for the lead's decision" nor that it needs a column named twice, and a new entry records the lead's decision; the paragraph of `/internal/engine/README.md` says the same.

C6: `-seed 25196 -sequences 1` failed with "the engine gives the subquery 1 the value x'…', and SQLite one of []" on goqite's shape, `update current set "T1" = ? where ÉTÉ == (select ÉTÉ from current where … order by "T1", "été" desc limit 1) returning …`. Red first: `TestSubqueryCandidates` in `/internal/engine/subquery_test.go`, on the table and row of `TestPair_sortTooBig`, asserts that SQLite refuses `select b from l order by c limit 1` under the limit, that `subqueryCandidates` gives the 990-byte text as its one candidate and first, and that the pair passes an update with that subquery; it failed with "Expected slice of length 1, but got 0". The fix: when the run of the subquery alone gives `tooBig`, the subquery has ORDER BY, and `o.unlimited` succeeds, `subqueryCandidates` takes that answer and runs its second query (the one with the ORDER BY columns) without the limit too.

`TestDifferential` now calls `differentialFind` itself, reports a failing sequence with `t.Error`, goes on to the next, and stops with `t.Fatal` after ten. I checked it by disabling the excuse for a moment (a `sed` that put `true ||` in front of its condition, restored from a copy afterwards): `-seed 16831 -sequences 3` reported 16832 and still logged "113 calls ran in SQLite", so it ran to the end.

The entry "The nightly run is looked at every day" went into `/AGENTS.md` after the one on merging pull requests.

### Why

Both failures are known differences that the lead decided to keep, reached in shapes their excuses did not take. The guards that stay (the statement without RETURNING succeeds under the limit; s4ql's answer equals SQLite's without the limit; the subquery has ORDER BY and runs without the limit) keep the excuses from covering a wrong answer.

### What worked

The lead's smallest case for C5 reproduced at once. For C6 the setup of `TestPair_sortTooBig` gave a too-big sort with no new measurement.

### What didn't work

Nothing failed beyond the red tests that were meant to.

### What I learned

The pair checks the subqueries' values against SQLite's candidates before it runs the statement, and then runs the statement in SQLite with the engine's values in place of the subqueries, so a statement whose subquery alone is too big to sort runs in SQLite without a sort: only the candidates needed the run without the limit.

### What was tricky

`subqueryCandidates` runs SQLite twice, the subquery alone for the first row and a second select with the columns of the ORDER BY for the ties; both sort, so both need the run without the limit, or the second one's `tooBig` branch returns no candidates again.

### What warrants review

That `TestDifferential` going on after a failure only adds noise after the first real one: the checks of the counts of `testdata/reached` at the end may then fail too, since the failed sequence counted only part of its statements.

### Future work

The planted-bug tests of the core and of the engine still stop a bug's subtest at its first seed with an unknown symptom, which can hide a later seed of the same bug in the nightly; recorded in `/docs/todo/ci.md`.

## Step 3: self-review, and a fallback that was too wide

**Author:** builder

### Prompt Context

**Verbatim prompt:** "Once the implementation is done, self-review before handing back to the lead." (the builder's standing instructions; the review used the `fabrik:code-review` skill, two competing reviewers over `git diff main...HEAD`)
**Interpretation:** have two independent reviewers read the diff, keep what both found and what is serious, and fix it.
**Inferred intent:** no widened oracle may hide a real fault of s4ql.

### What I did

Both reviewers found the same serious issue in step 2's fix of C6: the fallback in `subqueryCandidates` took SQLite's answer without the limit whenever the subquery alone gave `string or blob too big` and had ORDER BY. SQLite also gives that error for a literal or an argument of the subquery longer than the limit, which s4ql must refuse, and before the fix such a subquery had no candidates, so an engine that computed it anyway failed. One reviewer planted that fault through `go test -overlay` (`subqueries.lengths` in `/internal/engine/subquery.go` not measuring a subquery's condition values) and showed that 4 of 8 statements now passed silently. The other showed a second hole: with LIMIT 1, SQLite's sort skips the record of a row that sorts after the first, so the subquery alone can succeed while the second select (every row, for the ties) is too big, and the candidates were empty again.

The fix replaces the fallback: a subquery with ORDER BY whose literals (of its conditions and its LIMIT) and bound arguments all fit the limit runs both selects without the limit; any other runs them under the limit as before. `TestSubqueryCandidates` now has three subtests: the first case, the one where only the ties' sort is too big, and a long literal and a long argument that must give no candidates. With the reviewer's overlay, all 8 of its planted statements are reported again.

Also from the review, both reviewers agreeing: `TestDifferential` now returns before the checks of the counts when a sequence failed, so that `S4QL_RECOUNT=1` cannot write `testdata/reached` from a partial tally; the symptom of `keepFailed` is narrowed to `"(write), which began at commit"`, as `skipUnique` has it; seed 769 is no longer cited, since it does not reproduce at `main`; "of 1000" is dropped after the seeds; the sentence that an integral REAL "takes no byte" in the table's record is corrected, since only 0 and 1 take none (4.0 takes one byte); `/docs/todo/slice-14.md` no longer says the choice is open; the README rows of `swapSubqueries` and the sort excuse say what changed; the open item went into `/docs/todo/ci.md`.

### Why

The rule this branch adds to `AGENTS.md` is that an oracle is widened only by exactly the symptom that the bug or the recorded difference causes. The first fallback was wider than slice 13's difference.

### What worked

The reviewers' reproductions came with their inputs and an overlay, so the fix could be checked against the same planted fault without changing the code of s4ql.

### What didn't work

A Python here-doc that rewrote `TestSubqueryCandidates` was refused by the harness: "This agent is isolated in the worktree …, but this command is too complex to verify that it stays inside the worktree." The Edit tool did it.

### What I learned

`pair.step` flattens a statement's subqueries into `?` with the engine's values before SQLite runs it, so a check on the candidates is the only place where a subquery's own long literal or argument is seen for a select.

### What was tricky

Left as they were, by judgement: an `Exec` of a statement with RETURNING that the excuse covers is compared correctly but not counted as excused (older than this branch; counting it would change the exact pins of `testdata/reached`), and the theoretical case of a multi-row update with RETURNING whose too-long record SQLite lets slip without RETURNING.

### What warrants review

The condition in `subqueryCandidates` that decides between `o.run` and `o.unlimited`, and its third subtest.

### Future work

The stop of the planted-bug tests at their first unknown symptom, in `/docs/todo/ci.md`.

## Step 4: the nightly's commands, run locally, and a limit of open files

**Author:** builder

### Prompt Context

**Verbatim prompt:** "Run the nightly's simulation and generated jobs locally in full once (they take a while; run them in the background and wait), and report the result per job. If a further seed fails, treat it the same way: reproduce, find the cause, and widen an oracle only if the planted bug or a known, recorded difference is shown to cause exactly that symptom."
**Interpretation:** run the commands of the jobs `simulation-core`, `simulation-engine`, and `generated-engine` of `/.github/workflows/nightly.yml` with its settings, unsharded, and require each to pass.
**Inferred intent:** show that the next nightly passes, or say why it may not.

### What I did

- `simulation-core`: `S4QL_SIM_SEEDS=1000 go test -count=1 -run '^TestSimulation_plantedBugs$' -timeout 600m -v ./internal/core/` passed in 4,217 s, every bug on 1000 seeds. `renewOutsideLock` found its bug in 856 of 1000 seeds, once by the new symptom.
- `generated-engine`: `go test -count=1 -run '^TestDifferential$' ./internal/engine/ -sequences 400` passed in 1,104 s at the last commit (and in 937 s before the review's fix), and `S4QL_ENGINE_SIM_SEEDS=100 go test -count=1 -run '^TestSimulation$' ./internal/engine/` passed in 377 s.
- `simulation-engine`: `S4QL_ENGINE_SIM_SEEDS=1000 go test -count=1 -run '^TestSimulation_plantedBugs$' -v ./internal/engine/` in one process failed, as described below. Each of the 34 bugs then ran in a process of its own, four at a time, from a test binary of the last commit (`-test.run '^TestSimulation_plantedBugs$/^<bug>$'`, a script in the scratch directory that sampled `lsof -p` every 5 s): all 34 passed on 1000 seeds, `keepFailed` with 990 of 1000 and `replaceExisting` with 912.
- `make test` and `make lint` pass.

### Why

The nightly runs each job in shards on Linux; the local runs are unsharded, which is more than any shard does, except for the limit of open files below.

### What worked

Running each planted bug in a process of its own separated the question of the oracles from that of the files.

### What didn't work

The single process of the engine's planted bugs stopped in its ninth bug, `rollbackKeeps`, with "seed 7496 finds the bug by another violation: [a2 stopped: the instance has stopped: local I/O failure: spool file: open …/a2.db-spool-101155897: too many open files …]", and every later bug failed at its first seed the same way. macOS allows 61,440 open files a process (`sysctl kern.maxfilesperproc`). `lsof` of a later run of `keepFailed` alone showed about 1,400 sets of `a.db`, `a.db-wal`, `a.db-shm`, `b.db`, … open, each in the temporary directory of a seed that had already been removed: `run.crash` keeps every crashed `core.DB` open until the binary ends, by design. Each bug of the default workload peaked at 8,000 to 13,300 open files, each of the hammer workload, which has no crashes, at 22. By the nightly's two shards that is about 84,000 for shard 1 and 51,000 for shard 2. Before this branch, `keepFailed` and `replaceExisting`, both of shard 1, stopped at their first unknown symptom, so shard 1 held about 58,000 and passed in CI; now they run all 1000 seeds. Recorded in `/docs/todo/ci.md`, with the numbers for three and four shards.

My first per-bug script read the names of the bugs with `sed -E 's/^\s+\{"…'`, which BSD sed does not take, so the names kept `{` and `"`, no subtest matched, and each "passed" with 7 open files; the script now runs only names checked by hand, and I counted the 34 PASS lines in the logs.

### What I learned

A test that matches no subtest passes, so a run by name is proven only by its PASS line.

### What was tricky

Telling the limit of files apart from a fault: every failure after the first named "too many open files" or "unable to open database file (code 14)", none a wrong answer, and each bug passed in a process of its own.

### What warrants review

Whether the runner of `simulation-engine` allows more than about 84,000 open files; if not, the next nightly fails in shard 1 for this reason alone.

### Future work

More shards for `simulation-engine`, or closing a crashed instance's files at the end of its seed, as `/docs/todo/ci.md` says.
