# Diary: the nightly run passes again (issue #117)

The workflow `/.github/workflows/nightly.yml` failed every night from 2026-11-21 to 2026-11-25, five runs, and opened issue #117. An investigation by the lead found six causes, none a fault in s4ql: each is the oracle of a test that is too narrow, on seeds or sequences that CI's shorter runs do not reach. This task fixes the six in the tests, runs what the nightly runs, and records how the nightly is watched from now on.

## Step 1: the four planted bugs whose symptoms were not in their lists

**Author:** builder

### Prompt Context

**Verbatim prompt:** "The nightly run has failed every night since 2026-11-21 (issue #117, five runs). An investigation reproduced every failure and found that none is a fault in s4ql: each is a test's oracle that is too narrow. CI does not reach these seeds; the nightly runs many more. Your task: fix the six causes in the tests, show that the nightly's commands pass, and add a note on how the nightly is watched." (the opening of the lead's brief, which then lists the causes C1 to C6 with their replays and fixes)
**Interpretation:** for each cause, replay the seed, see that the planted bug (or a known, recorded difference) causes exactly that symptom, and only then widen the oracle by the smallest hunk; then run the nightly's simulation and generated jobs in full.
**Inferred intent:** the nightly should be green, so that a red one means something again, without hiding a real fault behind a wider list of symptoms.

### What I did

I replayed each seed with the command that the nightly printed, with the bug and without it.

- C1, core, `renewOutsideLock`, seed 411: `go test -count=1 -run '^TestSimulation$' -v ./internal/core/ -replay 411 -bug renewOutsideLock`. The first violation is "the commit of transaction 17867670975346570105 was acknowledged, and the log does not have it". The trace shows the mechanism: the renewal's request 49 is stuck in the network, sent without the manifest lock (the bug, in `send` of `/internal/core/lease.go`); meanwhile caller-0's commit retries its swap from `a735deaa` until request 63 lands at `1c0b7a11`; the renewal then reports "outcome=unknown", takes the lock, and resends its old 312-byte manifest from `1c0b7a11` as request 64, which is applied and drops the commit. A commit and a renewal can be in flight from one version only under the bug. With `-clean` the seed passes with no violation. I added the symptom to the bug's `symptoms` in `/internal/core/workloads_test.go`, with a comment on how the bug gives it.
- C2, engine, `replaceExisting`, seeds 7557 and 769: replayed with the test binary built once into the scratch directory, `-replay 7557 -workload default -bug replaceExisting`. The violation is "commit 11, … stores a value of another type than its column: s4ql: not supported: argument 1, which is an integer, for the column /* x */.TEMPORARY of type TEXT". The type rule (`typeRule`) runs on SQLite's state, where the CREATE TABLE IF NOT EXISTS did nothing, and the engine stores into the replaced table, whose column has another type. Seed 769 failed only on 2026-11-21 (run 44855847000, commit `9ae52f6`) with the same symptom; it no longer reproduces at `main`, since the profile has changed since. Both seeds pass without the bug.
- C3, engine, `keepFailed`, seed 20456: the violation is "the statement 30, …, of the transaction 8 (write), which began at commit 5, gives … rows [3] and in SQLite … [4]". The trace has updates in write transactions that fail with "UNIQUE constraint failed: NO.fUll"; under the bug what they changed stays, and a later select of the transaction sees it. Passes without the bug.
- C4, engine, `swapSubqueries`, seed 10252: the violation is "s4ql: internal error: a comparison of a value of kind blob with one of kind text", on a select with two subqueries, one compared with a TEXT column and one with a BLOB column. The swap puts each value into the other's comparison after the check of the types, as the comment of the bug already says for the storage. Passes without the bug.

For C2 to C4 I added the symptom to the bug's finds in `/internal/engine/simulation_test.go`, each with a sentence in the comment above it.

### Why

A seed that finds a planted bug by a symptom outside its list fails the subtest, so every seed of the nightly's 1000 that finds the bug some other legal way turns the night red. The lists were written from the 200 seeds that CI runs.

### What worked

Building the engine's test binary once (`go test -c -o /Volumes/990/s4ql/nightly-117/engine.test ./internal/engine/`) made the replays quick. The core's replay has `-clean`; the engine's has no such flag, but a replay without `-bug` runs the same seed and profile without the bug, which is what the planted-bug test itself runs.

### What didn't work

A loop over the seeds in zsh, `for a in "7557 default replaceExisting" …; do set -- $a; …`, did not split `$a` into words (zsh does not split unquoted parameters), so each run got one argument and wrote its log to a file named `eng-7557 default replaceExisting.log`. A script run with `sh` from the scratch directory did it.

### What I learned

The engine's planted-bug test stops at the first unknown symptom of a bug (`t.Fatalf`), so a bug's later seeds are not checked in a night where an early seed fails: the full run after the fixes can still show new ones.

### What was tricky

The engine's trace does not hold the text of a CREATE TABLE, so for C2 the different column type is read from the rule's message and the bug's description, not seen directly; the run without the bug passing is the control.

### What warrants review

That each added symptom string is specific enough: "internal error: a comparison of a value of kind" would also hide an engine fault of that kind, but only under `swapSubqueries`, and the bug's run without it on every finding seed still checks that nothing is found without the bug.
