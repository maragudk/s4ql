# Diary: Make CI faster and more reliable

A measurement of 194 CI runs from 2026-11-18 to 2026-11-20 found a median wall time of 11.4 minutes, decided by `browser` and `asan`; a build cache that did not work; `site` hanging in 7 of 132 runs; and no job with `timeout-minutes`. This task shards the sanitizer's tests of `internal/core` and `internal/engine` into jobs of their own, gives each job a build cache of its own, sets timeouts, makes the check of the site stop sooner and say more, shards the fuzz tests by target, and adds a nightly workflow for the long runs. The branch is `ci-faster`, from `origin/main` at `093b646`.

## Step 1: Shards, caches, timeouts, and the nightly workflow

**Author:** ci-faster builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Make CI faster and more reliable without removing or weakening any check: no test removed, no seed count or fuzz time lowered in the pull-request run without an equal or stronger check elsewhere, and `make test`, `make test-asan`, and the other Makefile targets still run everything locally as they do today. 1. Take `internal/core`, and `internal/engine` as well, out of the shared `asan` job's critical path [...] split `TestSimulation_plantedBugs` [...] across shards by its subtests, in a way that cannot silently drop a planted bug [...] 2. Make the caches work [...] a cached test result must never stand in for a run [...] 3. Set `timeout-minutes` on every job [...] except [...] the `browser` job [...] 4. `site`: lower `sitecheck`'s timeout from 10 minutes to about 3, and on a timeout make it print what helps diagnose the hang [...] 5. asan-fuzz: assign shards by fuzz target, not by package [...] 6. Add a scheduled workflow (nightly) [...] 7. Measure [...] 8. Update `docs/todo.md` [...]"
**Interpretation:** Change how CI runs the checks, not what they check: every test and fuzz test still runs on every pull request, in more jobs, each with a cache and a timeout, and the shards are given out by an index modulo the number of shards, with a check that they hold everything once.
**Inferred intent:** A wait for CI that is decided by the slowest job only, jobs that fail with a stack instead of hanging for hours, and long runs of fuzzing and simulation that happen every night without slowing a pull request.

### What I did

- `internal/testshard`: `Get(t)` reads `S4QL_TEST_SHARD=i/n`, `Holds(index)` is `index % n == i-1`. Without the variable a run is the shard 1/1, so every local run runs every subtest; a malformed value fails the test. Its tests show for every n up to 16 and up to 100 subtests that each subtest is in exactly one shard, and that the shards differ by one subtest at most. `TestSimulation_plantedBugs` of the core and of the engine skip, by `continue` before `t.Run`, the bugs that are not in their shard; four lines each.
- `make asan-test` takes `ASANPKGS`, `ASANSKIPPKGS`, `ASANSHARD`, `ASANSHARDED` (default `TestSimulation_plantedBugs`), and `ASANTIMEOUT` (default 10m, go test's own). A name in `ASANPKGS` or `ASANSKIPPKGS` that is not a package that links C fails. With `ASANSHARD=i/n`, the tests in `ASANSHARDED` run with `S4QL_TEST_SHARD=i/n`, and the first shard also runs every other test with `-skip`, without the variable, so whole. A sharded run that prints "no tests to run" fails. Without the settings it runs what it ran before.
- `make fuzz` gives the fuzz tests to the shards one by one, the k-th to the shard k modulo n plus one, in place of whole directories. `make fuzz-shards FUZZGROUP=... FUZZSHARDS=n` checks that every directory with a `func Fuzz` in a test file outside testdata is in `FUZZDIRS` (by `git grep`), and that the union of the n selections, with the same awk program that `make fuzz` uses, is the unsharded selection exactly; it prints each shard.
- `.github/actions/go` sets up Go without setup-go's cache and restores `GOCACHE` and `GOMODCACHE` under `go-<name>-<os>-<arch>-go<version>-<sha>`, from the newest key of the prefix; `.github/actions/go-save` saves on a push to `main` only. Every job but `changes` and `browser` uses them, with a name per job and kind of build, and a shard of its own for `asan-fuzz`.
- `ci.yml`: `lint` and `test` inline, in place of the reusable workflows of `maragudk/workflows`, since a job that calls a reusable workflow can have neither `timeout-minutes` nor a cache of its own here. `test` runs `go test -race -shuffle on -timeout 20m ./...`, with the two secrets in the environment of that step only; the build tags `sqlite_fts5,sqlite_math_functions,sqlite_foreign_keys` of the reusable workflow are dropped, since no file of the root module uses them. `asan` runs every package that links C but `ASAN_CORE` and `ASAN_ENGINE`, workflow-level variables that the jobs `asan-core` (3 shards) and `asan-engine` (2 shards) take, so that the names are in one place. A sharded job takes n from `strategy.job-total`, so a shard cannot go missing from the matrix. `timeout-minutes` on every job but `browser`, about three times the measured maximum and at least 5, and above the go test timeout. The heap check `go test -run '^TestTx_Commit_large$'` got `-count=1`.
- `sitecheck`: default `-timeout` 3m, and on a timeout the error holds the stacks of its goroutines (`runtime/pprof`, taken before Chromium is stopped), the requests of the page so far, and the tail of Chromium's output.
- `.github/workflows/nightly.yml`: each fuzz test for 5 minutes (6 shards under the sanitizer, one job without), the planted bugs of the core with `S4QL_SIM_SEEDS=1000` in 4 shards and of the engine with `S4QL_ENGINE_SIM_SEEDS=1000` in 2, without the race detector; a failed job opens an issue with the label `nightly`, or comments on the open one, and a failed fuzz test prints its new files under testdata/fuzz with `.github/scripts/fuzz-failures.sh`, which `ci.yml` uses too.

### Why

- An index modulo n, inside the test, needs no list of names that could go stale: a planted bug that is added gets an index, and with it a shard.
- The first shard runs the rest of the package without `S4QL_TEST_SHARD`, so a test that someone gives to `testshard` but does not add to `ASANSHARDED` runs whole there, and is not cut to a share.
- Saving only from `main` keeps the caches of pull requests from crowding out those of `main` in the 10 GB of the repository.
- The nightly workflow does not close its issue on a pass, as `Security` does, because a fuzz test may not find the same input on the next night.

### What worked

- `make fuzz-shards FUZZGROUP=c FUZZSHARDS=4` gives 8, 8, 8, and 7 of the 31 fuzz tests that link C, and refuses a shard count above the number of tests, a `FUZZDIRS` without a directory that has fuzz tests, and a malformed count.
- `make asan-test` in the Docker container of `make test-asan`, with `ASANPKGS=maragu.dev/s4ql/internal/sqlite/faultvfs` and `ASANSHARDED` set to its tests, ran both shards, and failed on a name in `ASANSHARDED` that the package does not have.
- `S4QL_TEST_SHARD=3/7 go test -run '^TestSimulation_plantedBugs$' -v ./internal/engine/` ran `checkOutside` and `convertReal`, the bugs at index 2 and 9.

### What didn't work

- A local run of the core's tests under `-race`, to weigh the shards, was useless at a load of 50 on 10 cores, and I stopped it; the shards are weighed from CI's runs instead.
- `go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.7` was refused by the permission system, so the workflows are checked by GitHub's run only.

### What I learned

- `go test -fuzz` stops the alarm of `-timeout` before it fuzzes (`testing.M.Run` calls `stopAlarm` before `runFuzzing`), so a long `-fuzztime` needs no `-timeout`.
- A test run through `-exec`, as `make test-browser` does, is not cached: go test writes no test log then, and a result without one is not saved.

### What was tricky

- The shell of the Makefile is `sh` (dash in CI), so the sharded run takes the status of go test through a file beside `tee`, not `PIPESTATUS`.

### What warrants review

- `make asan-test` with `ASANSHARD` and `make fuzz-shards`: the proof that nothing is dropped.
- That `ci.yml`'s `test` matches the reusable workflow it replaces, without the build tags.
- The timeouts, and the shard counts of `asan-core` and `asan-engine`, which the measured runs will set.
