# Diary: No test skips itself, except under `-short`

`AGENTS.md` got a new rule on 2026-11-19: "A test never skips itself, except under `-short`". A skipped test looks like a passing one, so a missing variable turns a check off without anyone seeing it. This task removes every `Skip` in the repository that `testing.Short()` does not cause, except those of the tests against a real bucket, which another builder is changing, and adds a lint rule that keeps it so. The work is on the branch `no-skips`, which starts from `main` at `8294863`.

## Step 1: The brief, and a plan

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Remove every `t.Skip` (and `Skipf`, `SkipNow`, and the same on `b` and `f`) in the repository that is not caused by `testing.Short()`. [...] **Leave alone:** the skips in `internal/store/s3store/s3store_test.go` and anything under `internal/store/s3test` and the root package's tests against a real bucket. Another builder is changing those right now. For each skip, first find out what it is for [...] Then choose, case by case, what serves the rule best: **A tool that only a person runs with a variable** [...] is not written as a test that skips when the variable is missing. [...] The replay of a seed must stay as easy as it is today (one command that a failing simulation prints and a person pastes); keep the command that the failure message prints correct. **A fuzz target that calls `t.Skip()` for an uninteresting input** returns instead [...] **A test that needs a build mode** (the race detector) either always runs and asserts what is true in each mode, or lives in a file with a build constraint [...] **A test that needs an environment that the caller provides** (a page that drives the engine in a browser): the same idea, a build constraint or an entry point that is not a skipping test. Whatever you choose, nothing that runs today may stop running [...] If a workflow file would have to change, do not change it: stop on that case [...] Then add a guard so that the rule keeps itself: a check that fails when a `Skip` call appears outside a `testing.Short()` condition. [...] It must allow `if testing.Short() { t.Skip(...) }` and reject every other form, and for now allow the real-bucket test files named above through an explicit list with a comment that says they are being changed [...] Test the rule with planted violations as the other rules are."
**Interpretation:** Ten skips in seven files, each with its own reason, get a form in which nothing skips: a fuzz target returns, a test that needs the race detector is built only with it, a tool for a person is a mode of a test that always runs or a test file behind a build tag, and the program of the simulator does real work when no page drives it. Then a second analyzer next to `simlint` reports every `Skip` outside `if testing.Short() { ... }`.
**Inferred intent:** A test that does not run is seen, because it fails or is not there, and never passes as a skip.

### What I did

Reset the worktree to `origin/main` at `8294863`, created the branch `no-skips`, and read `/AGENTS.md`, the `Makefile`, `/.github/workflows/ci.yml`, each test with a skip, `/internal/core/README.md`, `/internal/engine/README.md`, `/internal/sim/README.md`, `/internal/simulator/README.md`, `/internal/simulator/serve/main.go`, `/internal/simulator/engine/worker.js`, the pattern of a test with two roles in `/internal/sql/shapetest/check_test.go`, and `/internal/simlint`.

What each skip is for, and who runs it today:

- `TestPlantedDataRace` in `/internal/core/free_test.go` skips without `S4QL_CORE_PLANT_RACE`. `TestFreeRunning_plantedDataRace` starts it as a child process with the variable set, and skips itself without the race detector. CI's job `simulation` runs both under `-race` with `-run '^TestFree'`, and the reusable job `test` runs the package under the race detector too.
- `TestSimulationSeed` in `/internal/core/workloads_test.go` and in `/internal/engine/simulation_test.go` replays one seed, by `S4QL_SIM_SEED` and `S4QL_ENGINE_SIM_SEED`. Only a person runs them. No failure message prints a command to replay a seed today: the failures say `seed 7: ...` and the READMEs give the command.
- `TestSimulationSpeed` and `TestScheduler_mutexHeldAcrossWait` in `/internal/sim/sim_test.go`, by `S4QL_SIM_SPEED` and `S4QL_SIM_HANG`. Only a person runs them. Both need a `testing.T`, for the bubble of `testing/synctest`, so neither can be a benchmark or a command.
- `TestEngine` in `/internal/simulator/engine/engine_test.go` is the program of the simulator in a browser: `make simulator`, `make site`, and `make site-check` (CI's job `site`) build its test binary with `go test -c`, and `worker.js` drives it. `make test-browser` (CI's job `browser`) runs it with no page, where it skips; `make check-browser` and the lint of the browser's build compile and lint it.
- The fuzz targets `FuzzJudge`, `FuzzMutants`, and `FuzzConn_Prepare` skip an input that is too long or that holds a PRAGMA that changes the whole process.

The plan, one commit for each:

1. The fuzz targets return.
2. The planted race: one test, in a file built only with the race detector, that is the parent without the variable and the child with it, as in `/internal/sql/shapetest/check_test.go`.
3. The replay of a seed: a mode of `TestSimulation`, which runs only that seed when the variable is set, as `S4QL_SIM_SEEDS` already changes what it runs. The failure of a seed then prints the command that replays it.
4. The speed and the hang: test files behind build tags of their own, with a `make` target each, and `make lint` vets them so that they cannot drift unseen.
5. `TestEngine`: without a page it drives itself, with messages through its own `submit`, `ready`, and `done`, and checks the answers against those of an engine called directly.
6. The guard: an analyzer next to `simlint`, which `cmd/simlint` runs together with it, so that CI's job `simulation` runs it with no change to a workflow.

### Why

Each form is chosen so that whatever ran before still runs in the same job, and whatever did not run before is either a real test or is not in the test binary at all.

### What worked

The project already has a test with two roles, the shards of `/internal/sql/shapetest/check_test.go`, so the planted race follows a pattern that is there.

### What didn't work

Nothing yet.

### What I learned

The skips under `-short` that the rule allows do not exist yet: the tests that do less under `-short` (`slow()` in several packages) do less, and do not skip.

### What was tricky

The replay and the speed and hang tools need a `testing.T`, so the way of the brief through `TestMain` or a command of their own does not work for them.

### What warrants review

The choice for each case, in the steps below.

### Future work

## Step 2: The fuzz targets return

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "**A fuzz target that calls `t.Skip()` for an uninteresting input** returns instead (a `return` is what the fuzzing documentation asks for; `t.Skip` in a fuzz target only marks the input). Check that returning does not change what the fuzzer keeps or reports in a way that matters."
**Interpretation:** `FuzzJudge`, `FuzzMutants`, and `FuzzConn_Prepare` return for an input that they leave out.
**Inferred intent:** No `Skip` is left in a fuzz target for the guard to allow.

### What I did

Replaced the `t.Skip()` in `/internal/sql/oracle/oracle_test.go` (an input of more than 10,000 bytes), `/internal/sql/parsetest/parsetest_test.go` (more than 1,000 bytes), and `/internal/sqlite/sqlite_test.go` (a PRAGMA `heap_limit` or `directory`, which change the whole process) with `return`, and changed "are skipped" in the comment of the last to "are left out".

Ran each for five seconds, as `make fuzz` runs them: `go test -run '^$' -fuzz '^FuzzJudge$' -fuzztime 5s .` in `/internal/sql/oracle`, the same for `FuzzMutants` in `/internal/sql/parsetest` and `FuzzConn_Prepare` in `/internal/sqlite`. All three passed, with 412418, 308894, and 365642 inputs.

### Why

The fuzzer keeps an input by the coverage that it reaches and reports it only when the target fails, and a skip is neither. In `src/testing/fuzz.go` of Go the run of an input returns `!t.Failed()`, and `cmd/go` does not instrument the package `testing` for coverage (its list `skipInstrumentation`), so the code of `SkipNow` adds no coverage either. A `return` at the same place reaches the same coverage and the same outcome. Outside fuzzing, every seed of the corpus is shorter than the limits, so a plain `go test` sees no difference either; with `-v`, an input that is left out would now show `PASS` where it showed `SKIP`.

### What worked

The check in the Go source settled what the fuzzer keeps.

### What didn't work

Nothing.

### What I learned

The documentation of `F.Fuzz` forbids the methods of `*F` inside the target, but says nothing against `t.Skip`; the difference from a `return` is only in the report of the one input.

### What was tricky

Nothing.

### What warrants review

That no seed of the corpora hits the early return in a plain `go test`, so that nothing that was checked before is left out now. The limits are the same as before.

### Future work

None.

## Step 3: The planted data race is built only with the race detector

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "**A test that needs a build mode** (the race detector) either always runs and asserts what is true in each mode, or lives in a file with a build constraint, so that it is not in the binary where it cannot run."
**Interpretation:** `TestFreeRunning_plantedDataRace` goes into a file with `//go:build race`, and `TestPlantedDataRace`, its child, stops being a test of its own.
**Inferred intent:** Neither of the two tests shows a skip in any run.

### What I did

Moved `TestFreeRunning_plantedDataRace` from `/internal/core/free_test.go` to `/internal/core/race_test.go`, which already holds `raceEnabled = true` behind `//go:build race`. The test has two roles now, as the shards of `/internal/sql/shapetest/check_test.go` do: without `S4QL_CORE_PLANT_RACE` it starts the test binary twice with `-test.run ^TestFreeRunning_plantedDataRace$` and the variable set to `free` and to `scheduler`, and with the variable it runs the planted workload in that mode and returns. Another value fails the test. `TestPlantedDataRace` and the constant `plantRace` are gone. Updated the paragraph in `/internal/core/README.md`.

Ran what CI's job `simulation` runs, `go test -race -count 1 -shuffle on -run '^TestFree' -v ./internal/core/`: `TestFreeRunning_plantedDataRace` passed in 3.00 s, so the child in free mode reported `WARNING: DATA RACE` and failed, and the child under the scheduler passed. Without `-race`, `go test -count 1 -run '^TestFree' -v ./internal/core/` runs `TestFreeRunning` alone, with no skip.

### Why

Always running it and asserting what is true without the race detector would assert only that a binary without the detector reports no race, which checks nothing about the free-running mode. Without the detector, the test has nothing to show, so it is not in that binary. Before, CI's job `simulation` and the reusable job `test`, both under `-race`, ran it; they still do, by the same `-run` pattern, as the name did not change. The runs without the detector, `make test`, `make test-browser`, and CI's jobs `asan`, `fuzz`, and `browser`, skipped it, and now do not have it.

### What worked

The pattern of a test with two roles needs no `TestMain` and keeps the child's `testing.T`, which `simulate` and `free` need.

### What didn't work

My first edits ran as one shell command with a heredoc and `python3`, and the harness refused them: "this command is too complex to verify that it stays inside the worktree". I made the edits with the file tools and a small script in the scratchpad instead.

### What I learned

A build constraint on a test file needs no other change in CI as long as the name of the test still matches the `-run` pattern of the job that ran it.

### What was tricky

Nothing.

### What warrants review

That the child starts with `-test.run ^TestFreeRunning_plantedDataRace$`, built from `t.Name()`, so a rename cannot leave the child running nothing: with no test matched, the child would pass and the free subtest would fail.

### Future work

None.

## Step 4: The replay of a seed is a mode of `TestSimulation`

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "The replay of a seed must stay as easy as it is today (one command that a failing simulation prints and a person pastes); keep the command that the failure message prints correct."
**Interpretation:** `TestSimulationSeed` of `core` and of `engine` goes, and the replay stays one command.
**Inferred intent:** A person who sees a seed fail can paste one line and see its trace, and no test shows a skip on the way.

### What I did

In `/internal/core/workloads_test.go` and `/internal/engine/simulation_test.go`, `TestSimulation` starts with a check of `S4QL_SIM_SEED` and `S4QL_ENGINE_SIM_SEED`: when the variable is set, it calls `replaySeed`, which is the body of the old `TestSimulationSeed`, and returns. `replayCommand` builds the command, and every failure of a seed in `TestSimulation` and `TestSimulation_plantedBugs` now prints it after "replay it with:", with the workload and the bug that the failing run had:

```sh
S4QL_SIM_SEED=7 S4QL_SIM_WORKLOAD=full go test -run '^TestSimulation$' -v ./internal/core/
S4QL_ENGINE_SIM_SEED=7 S4QL_ENGINE_SIM_WORKLOAD=hammer S4QL_ENGINE_SIM_BUG=checkOutside go test -run '^TestSimulation$' -v ./internal/engine/
```

The engine's replay could only run the default workload, so a failure of the hammer workload, or of the bug `checkOutside`, which runs on it, could not be replayed. `S4QL_ENGINE_SIM_WORKLOAD` (`default` or `hammer`) fixes that, and the table of the engine's planted bugs got the name of each bug's workload for the command. Updated `/internal/core/README.md` and `/internal/engine/README.md`.

Ran the replays as a person would: `S4QL_SIM_SEED=3 S4QL_SIM_WORKLOAD=full go test -run '^TestSimulation$' -v ./internal/core/` passed and logged the trace of 3298 steps; `S4QL_SIM_SEED=0 S4QL_SIM_BUG=renewOutsideLock` failed with the bug's 13 violations, and the same with `S4QL_SIM_CLEAN=1` passed. `S4QL_ENGINE_SIM_SEED=7 S4QL_ENGINE_SIM_BUG=skipUnique go test -run '^TestSimulation$' -v ./internal/engine/`, the example of the engine's README, failed with the UNIQUE constraint violations of the bug, and `S4QL_ENGINE_SIM_SEED=3 S4QL_ENGINE_SIM_WORKLOAD=hammer` passed.

### Why

The brief's ways through `TestMain` or a command of its own do not work here: the replay needs a `testing.T`, for the bubble of `testing/synctest` that `simulate` runs in. A build tag would rebuild the packages that link SQLite for every replay and leave the code unbuilt in CI. `TestSimulation` already changes what it runs by `S4QL_SIM_SEEDS`, so a second variable that narrows it to one seed is the same kind of thing, and the test that runs without the variable is the full simulation. The failure messages did not print a command before, and the brief takes it as given that they do; they print one now, because a command that is built next to the run that failed cannot name the wrong workload.

### What worked

Moving the body into a helper with `t.Helper()` kept the replay's output as it was; the lines of the trace now point at the call in `TestSimulation`.

### What didn't work

Nothing failed.

### What I learned

The replay of the engine could not reach the hammer workload before. Nobody had needed it, because no seed of the hammer workload had failed.

### What was tricky

With `S4QL_SIM_SEED` set and no `-run`, `TestSimulation` replays the seed while every other test runs as usual. That is what a person who sets the variable asks for; the command that is printed has `-run '^TestSimulation$'`.

### What warrants review

That every printed command names the workload and the bug of the run that failed: in `core`, the control prints `S4QL_SIM_CONTROL=1` and the run without the bug `S4QL_SIM_CLEAN=1`; in `engine`, the run without the bug prints no `S4QL_ENGINE_SIM_BUG`.

### Future work

None.

## Step 5: The speed and the hang of the scheduler are `make` targets

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "**A tool that only a person runs with a variable** (the replay of one seed, a speed measurement, a planted race or hang that another test or a `make` target starts as a child process) is not written as a test that skips when the variable is missing. Options: [...] or the tool becomes a flag of the test binary or a `make` target with a program of its own."
**Interpretation:** `TestSimulationSpeed` and `TestScheduler_mutexHeldAcrossWait` of `/internal/sim` stop being tests that a plain run of the package sees.
**Inferred intent:** The two tools stay one command away, and the suite has no test that only reports a skip.

### What I did

Moved `TestSimulationSpeed` into `/internal/sim/speed_test.go` behind `//go:build s4ql_speed`, and `TestScheduler_mutexHeldAcrossWait` into `/internal/sim/hang_test.go` behind `//go:build s4ql_hang`, both without their checks of `S4QL_SIM_SPEED` and `S4QL_SIM_HANG`. The `Makefile` got two targets: `make sim-speed` runs the first with `-v`, and `make sim-hang` runs the second with `-timeout 5s` and succeeds only if the output has `panic: test timed out` and a line `sync.(*Mutex).Lock` in the dump of the goroutines, so that the target checks what it shows. `make lint` runs `golangci-lint run --build-tags s4ql_speed,s4ql_hang ./internal/sim/`, so that the two files cannot drift from the helpers that they use. Updated `/internal/sim/README.md`.

Ran both as a person would: `make sim-speed` passed and logged "320180 steps in 3.15 s", and `make sim-hang` exited 0 after the run timed out with goroutine 25 in `sync.Mutex.Lock` in the bubble. `golangci-lint run --build-tags s4ql_speed,s4ql_hang ./internal/sim/` gave "0 issues." A plain `go test -run 'Speed|mutexHeld' ./internal/sim/` finds no test.

### Why

Both need a `testing.T`, for the bubble of `testing/synctest`, so neither can be a benchmark or a command with a `main` of its own, and neither can run in every run of the suite: the hang cannot pass, and the speed asserts nothing and takes three seconds. A tag keeps them out of every binary of the suite, and a `make` target is the one command a person types. Before, no `make` target and no CI job ran them, and with the variables unset every run of the package skipped them; now no run of the package has them.

### What worked

The dump that the timeout of `go test` prints names the state of each goroutine of the bubble, `sync.Mutex.Lock` among them, so the target can check that the hang is the one it means to show.

### What didn't work

Nothing failed.

### What I learned

The timeout of `go test` prints every goroutine, with its bubble of `testing/synctest`, also without `GOTRACEBACK=all`.

### What was tricky

The rule of one test file for each source file: the two tests need files of their own for their build constraints, as `/internal/sim/cgo_test.go` and `/internal/core/race_test.go` have.

### What warrants review

That `make sim-hang` bounds real time from the side that a slow machine can break: on a machine so slow that the run does not reach the mutex in five seconds, the target fails. It is a tool that a person runs, not a check of CI, and the timeout is the one that the diary of the spike used.

### Future work

None.

## Step 6: `TestEngine` plays the page when no page drives it

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "**A test that needs an environment that the caller provides** (a page that drives the engine in a browser): the same idea, a build constraint or an entry point that is not a skipping test."
**Interpretation:** `TestEngine` in `/internal/simulator/engine`, the program of the simulator, does not skip in `make test-browser`, where no page drives it.
**Inferred intent:** The run of the package in the browser checks something, and the program stays what `worker.js` runs.

### What I did

Split `TestEngine` of `/internal/simulator/engine/engine_test.go` into `serve`, which is the old body, and the test. With the object `s4qlEngine` of `worker.js`, the test calls `serve` with it, as before. Without it, the test makes an object of its own with `ready` and `done` and serves it: in `ready` it submits a message, a second one while the first waits, and one without its three arguments, and in the first `done` it submits the second again. It checks that `submit` answered true, false, false, and true, that `done` got the ids 1 and 2, and that the answers are those of a `simulator.Engine` called directly with the same messages, a `state` before any run and a `now` without a session. `serve` returns when `done` returns true, which only the test's own object does: `worker.js` returns nothing from `done`. Updated `/internal/simulator/engine/doc.go` and `/internal/simulator/README.md`.

Ran `make test-browser BROWSERPKGS=./internal/simulator/engine BROWSERFLAGS='-count=1 -v' BROWSERTIMEOUT=5m`: the subtest passed in Chromium in 0.01 s. `make site-check`, which builds the program with `make site` and drives it through `worker.js` in headless Chromium, ended with `sitecheck: ok`. `make check-browser` and `GOOS=js GOARCH=wasm golangci-lint run --build-tags s4ql_browser ./internal/simulator/engine` passed.

### Why

A build constraint would have taken the file out of `make check-browser` and out of the lint of the browser's build in CI's job `browser`, which compile and lint it today; only `make site-check` would still have built it. Playing the page keeps the file in every build that has it now, and turns the skip in CI's job `browser` into a check of the protocol between `submit`, `ready`, and `done`, which only `make site-check` covered before, and only through the whole page. Messages that need no run keep the test fast in the browser.

### What worked

A call from Go into JavaScript that calls a function of `js.FuncOf` runs that function on the same goroutine, so the test's `ready` and `done` can call `submit` while `serve` waits in `hook.Call`, and the order of the messages is fixed: the second `submit` in `ready` is refused because `serve` has not yet read the first.

### What didn't work

Nothing failed.

### What I learned

The runner of `/internal/sqlite/browser` finds a Chromium on this machine without `S4QL_CHROMIUM_FLAGS`.

### What was tricky

The object that the test makes stands in for `worker.js`, which the brief's rule against test doubles touches. It plays the caller, not a dependency of the code under test, and the real `worker.js` is what `make site-check` drives.

### What warrants review

The one change to the protocol: `done` may now end `serve` by returning true. `worker.js` returns `undefined`, so the program serves for as long as it runs, as before.

### Future work

None.

## Step 7: The lint `skiplint` keeps the rule

**Author:** no-skips builder

### Prompt Context

**Verbatim prompt:** (from the brief) "Then add a guard so that the rule keeps itself: a check that fails when a `Skip` call appears outside a `testing.Short()` condition. The project has a linter of its own, `internal/simlint` [...] a small rule there or next to it is the natural place. It must allow `if testing.Short() { t.Skip(...) }` and reject every other form, and for now allow the real-bucket test files named above through an explicit list with a comment that says they are being changed (the lead removes the entries when that work has merged). Test the rule with planted violations as the other rules are."
**Interpretation:** A second analyzer next to `simlint`, run by the same command, so that `make lint` and CI's job `simulation` run it.
**Inferred intent:** A new skip outside `-short` fails a check, and nobody has to remember the rule.

### What I did

Wrote `/internal/simlint/skiplint/skiplint.go`, a package of the module `internal/simlint` with an `analysis.Analyzer`. It reports, in every Go file, a test or not, each use of the methods `Skip`, `Skipf`, and `SkipNow` of the package `testing`, found by the type of the selector and not by its name, so that `testing.T`, `testing.B`, `testing.F`, `testing.TB`, a type that embeds one, a method value, and a method expression are all caught, and a method `Skip` of another type is not. It allows a call that is a statement of its own directly in the body of an `if` whose condition is `testing.Short()` alone, with no init statement. The list `allowed` holds `/internal/store/s3store/s3store_test.go` and the directory `/internal/store/s3test/`, matched by the end of the path, with a comment that they are being changed and that the entries go once that is merged. I did not add the root package's tests against a real bucket: none exist on `main`, and the brief names no file for them.

`/internal/simlint/cmd/simlint/main.go` runs both analyzers with `multichecker` in place of `singlechecker`, so the step "Lint for the simulation" of CI's job `simulation`, which runs `simlint ./...`, now runs the rule without a change to the workflow. `make lint` also runs it alone (`-skiplint`) over the tests behind `s4ql_speed` and `s4ql_hang`, over the module of the cross-checks, and over the module of the lints, which `./...` from the root does not reach.

The tests in `/internal/simlint/skiplint/skiplint_test.go` run `analysistest` over planted skips in `/internal/simlint/skiplint/testdata/src/skips`: a bare `t.Skip`, a `Skipf` under a variable, `SkipNow`, `b.Skip`, `f.Skip` and `t.Skip` in a fuzz target, `!testing.Short()`, `testing.Short() && ...`, the `else` branch, an init statement, a loop inside the `if`, a `defer`, a method value, a method expression, `testing.TB`, an embedding type, and a function `Short` of the package itself, all reported; and `if testing.Short()` with a skip, in parentheses, after another statement, in a subtest, on `b`, and on `testing.TB`, and a method `Skip` of another type, not reported. A helper in a file that is not a test is reported too. A second subtest shows that the allowed file and directory are not reported, and that another test file of the same package is.

Ran `go test -count 1 ./...` in `/internal/simlint`, the built command over the repository (exit 0, nothing reported), the command over a planted `t.Skip("planted")` in `/internal/sim` (reported, exit 3; the file is deleted), and `make lint` (exit 0).

### Why

A rule in `cmd/simlint` reaches CI through the one step that already runs it, where a command of its own would need a change to the workflow, which the brief rules out. A package of its own keeps the documentation of `simlint`, which is about code under the simulation, about that. Matching by the type of the method means that a wrapper or a method value cannot slip past it.

### What worked

The first run of the tests failed: "skips/skips_test.go:82: no diagnostic was reported matching `SkipNow skips the test`". I had put the method expression `(*testing.T).SkipNow(t)` inside `if testing.Short()`, where it is the allowed form. The planted case moved out of the `if`, and the failure showed that the test checks what it says.

### What didn't work

The failure above, which was the test and not the rule.

### What I learned

`multichecker` runs every analyzer by default and takes a flag for each, so `-skiplint` runs one alone where the rules of the simulation do not apply, such as in the module of the cross-checks.

### What was tricky

The allowed form had to be exact, or a test that keeps the old check under a new shape (`if testing.Short() || os.Getenv("X") == ""`) would pass. Only a condition that is the call `testing.Short()` itself counts.

### What warrants review

The list `allowed`, which the lead removes when the work on the tests against a real bucket has merged. The run over the crosscheck module and over the lints' own module happens only in `make lint`, not in CI, because the job `simulation` runs the command only from the root.

### Future work

The entries of `allowed` go once the tests against a real bucket fail without their bucket.
