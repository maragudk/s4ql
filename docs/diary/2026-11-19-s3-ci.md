# Diary: The tests against a real bucket in CI

The tests against a real bucket ran only by hand. Markus decided that they run in CI on every pull request, on `main`, and on a schedule, against the bucket that development uses, Tigris. This work adds a test of the public package against a real bucket, a `make` target that runs every test that needs the bucket and fails if none ran, a CI job, and the cleanup of prefixes that killed runs leave. The work is on the branch `s3-ci`, which starts from `main` at `c14b043`.

## Step 1: The brief, and a plan

**Author:** s3-ci builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "1. **A test of the public package against a real bucket**, gated on `S4QL_S3_BUCKET` as the tests of `s3store` are, and skipped without it. It uses only what an application has: `s4ql.Open` with `s4ql.Options` (credentials from the same environment variables, given through the options' fields), `database/sql`, and the public errors. [...] Cover what only a real bucket shows end to end: every statement of slice 1 committed and read back; a second instance on another cache directory that is a spare while the first holds the lease, and that serves and sees the first's rows after the first closes [...]; a restart on an empty cache directory that replays the log from the bucket; `Ping` that returns when the instance serves; and `Register` with `sql.Open` by name. [...] 2. **A `make` target** (for example `test-s3`) that runs every test that needs the bucket [...] and that fails if `S4QL_S3_BUCKET` is empty [...]. It must also fail if no such test ran. 3. **A CI job `s3`** that runs that target with the secrets and variables above, on pull requests, on pushes to `main`, and on the schedule that CI already has [...]. Secrets are not given to pull requests from forks. The job must not run for those [...], and must never use `pull_request_target`. [...] No secret is printed. [...] Give the job a timeout. 4. **Cleanup of leftovers.** A run that is killed leaves its prefix. Add a step [...] that deletes every prefix under `s4ql-test/` whose timestamp in its name is older than one day, and nothing else. Whatever does the deleting must refuse to delete anything that is not under `s4ql-test/`, and must be tested for that. [...] 5. **Documents:** update `docs/todo.md` [...], and add a short note where a developer would look [...] on how to run the target by hand."
**Interpretation:** Build the public package's test against the bucket, a shared helper for the bucket's settings and the prefixes, a guarded deleter of old prefixes with a tiny command, a `make test-s3` that cannot pass by skipping, and a job `s3` in `/.github/workflows/ci.yml` that forks never reach.
**Inferred intent:** Every change is checked against a real store without a person remembering to do it, without leaking the credentials, and without the bucket filling up with what killed runs leave.

### What I did

Read `/AGENTS.md`, the section Testing of `/docs/spec.md`, the workflows in `/.github/workflows/`, `/Makefile`, `/internal/store/s3store/s3store_test.go` and its README, `/s4ql.go`, `/s4ql_test.go`, `/export_test.go`, `/conn.go`, `/errors.go`, the defaults in `/internal/core/core.go`, the start of `/internal/sqlite/crosscheck/drivercheck/drivercheck_test.go`, `/internal/simlint/simlint.go`, and the points on real buckets and CI in `/docs/todo.md`.

The plan:

1. **A package `internal/store/s3test`** holds what the tests against a real bucket share: the settings from the environment, which skip a test without `S4QL_S3_BUCKET`; a plain SDK client for what `store.Store` cannot do; `NewPrefix`, which gives `s4ql-test/<suite>/<UTC time>-<8 random characters>/` and deletes it at the end of the test; and the deletion of old prefixes. It is test support, but a command must import it, so it is not a `_test.go` file. The tests of `s3store` move to it, so that one function makes every prefix and the cleanup knows its form.
2. **A command `internal/store/s3test/cleanup`** deletes every prefix `s4ql-test/<suite>/<time>-<random>/` whose time is more than a day old. Every deletion goes through one function that refuses a prefix that is not under `s4ql-test/`, and a key that is not under the prefix it deletes. Both packages are exempt from the lint of the simulation, as `s3store` is.
3. **The defaults of the core decide the waits.** A lease lasts 30 seconds and a spare reads the manifest every 5. `Close` releases the lease, so a spare serves at its next watch after the holder closed, and a new instance after a close serves at its first read of the manifest. No scenario waits for a lease to run out, unless a release fails. `CloseTimeout` is public, and the test sets it to a minute, so that a slow network does not make a close fail.
4. **`make test-s3`** fails without `S4QL_S3_BUCKET`, runs the named tests verbosely under the race detector, and fails unless each of them printed `--- PASS` at the top level. A skip prints `--- SKIP` and fails it.
5. **The job `s3`** runs if the event is no pull request, or if the pull request's head repository is this repository. The schedule is new in `/.github/workflows/ci.yml`, since CI had none.

### Why

The brief asks for the helper to be shared if that is clean, and for the cleanup to be small and guarded. A prefix whose form one function makes is the only kind that the cleanup can recognize without guessing.

### What worked

The public options already have everything that the test needs: the credentials, the endpoint, the region, and `CloseTimeout`.

### What didn't work

Nothing yet.

### What I learned

CI has no schedule; only `/.github/workflows/security.yml` has one. The lint of the simulation lints every package that is not exempt, by its exact import path, so a new package of test support needs its own entry.

### What was tricky

The lease durations are not public, so the test cannot shorten a wait; it can only choose scenarios in which no instance waits for a lease to run out.

### What warrants review

The choice of a non-test package for the helper, and the guard of the deletion.

### Future work

None yet.

## Step 2: `internal/store/s3test`, and the guarded deletion

**Author:** s3-ci builder

### Prompt Context

**Verbatim prompt:** (from the brief) "Whatever does the deleting must refuse to delete anything that is not under `s4ql-test/`, and must be tested for that. Keep it small: a test helper or a tiny program inside `internal/`, your choice; no new dependency."
**Interpretation:** One package for the settings, the prefixes, and the deletion, and a command on top of it.
**Inferred intent:** A cleanup that cannot delete the wrong thing, whatever a listing gives back.

### What I did

Wrote `/internal/store/s3test/s3test.go`: `Load` and `FromEnv` for the settings, `Config.Client` for a plain SDK client that logs nothing, `NewPrefix`, `DeletePrefix`, and `DeleteOld`. `DeletePrefix` refuses any prefix that is not exactly `s4ql-test/<suite>/<YYYYMMDDTHHMMSS>-<8 base32 characters>/`, so neither the root nor a whole suite can be deleted, and refuses a whole page of a listing if any key on it is outside the prefix, before it deletes any key of that page. `DeleteOld` lists the root and each suite with the delimiter `/`, and deletes only the prefixes of that form whose time parses and is before the given one. The command `/internal/store/s3test/cleanup` runs `DeleteOld` with now minus 24 hours under a timeout of 5 minutes, and prints each deleted prefix. Both packages are exempt in `/internal/simlint/simlint.go`. The tests of `s3store` make their prefixes with it, and `realBucket` reads its settings from it.

The tests in `/internal/store/s3test/s3test_test.go` run on a fake path-style bucket over `httptest`, which answers `ListObjectsV2` with a prefix and a delimiter, and `DeleteObject`, and records every request: 16 malformed prefixes are refused with no request sent; a deletion leaves a sibling prefix that is one character longer; a listing that gives a key outside the prefix stops the deletion with nothing deleted, also through `DeleteOld`; and `DeleteOld` leaves every key that is not in an old prefix of a test. `TestDeleteOld_realBucket` plants a prefix dated two days ago next to a new one, and checks on the real bucket that the old one goes and the new one stays.

### Why

A prefix that one function makes is a form that the cleanup can recognize exactly; anything looser would have to guess what a killed run's prefix looks like.

### What worked

Two mutations of the guards, one removing the check of the prefix and one the check of the keys of a listing, each made tests fail: five failures for the first, two subtests for the second.

### What didn't work

The first refactor of `/internal/store/s3store/s3store_test.go` left imports behind: `vet: internal/store/s3store/s3store_test.go:6:2: "crypto/rand" imported and not used`, and then the same for `"os"`. A mutation with `sed` that replaced the key check by `if false {` did not build, because `strings` was then unused; replacing the prefix in the check with `""` did.

### What I learned

The prefixes already in the bucket from runs by hand have the same form, so the cleanup covers them too. A delimiter listing of the root gives each suite as a common prefix, so a key directly under the root or a suite is never a candidate.

### What was tricky

The fake's switch first read `r.Method == http.MethodGet && r.URL.Path == "/bucket" || r.URL.Path == "/bucket/"`, whose precedence is wrong; parenthesized.

### What warrants review

`prefixPattern` in `/internal/store/s3test/s3test.go`, which is the whole guard, and the cases in `TestDeletePrefix`.

### Future work

None.

## Step 3: `TestOpen_realBucket` and `make test-s3`

**Author:** s3-ci builder

### Prompt Context

**Verbatim prompt:** (from the brief) "Cover what only a real bucket shows end to end: every statement of slice 1 committed and read back; a second instance on another cache directory that is a spare while the first holds the lease [...]; a restart on an empty cache directory that replays the log from the bucket; `Ping` that returns when the instance serves; and `Register` with `sql.Open` by name."
**Interpretation:** Three subtests through `database/sql` only, each on a database of its own, and a target that cannot pass by skipping.
**Inferred intent:** What an application sees on the real store is checked, beside what the core shows.

### What I did

Added `TestOpen_realBucket` to `/s4ql_test.go`. It reads the settings with `s3test.FromEnv`, makes the SDK client for the cleanup, and then clears `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_ENDPOINT_URL_S3`, and `AWS_REGION` with `t.Setenv`, so that the settings reach the store through `s4ql.Options` only. `CloseTimeout` is a minute. The subtests:

1. Every statement of slice 1: two tables, four inserts with the extremes of 64 bits and `RowsAffected` of 1, an insert into the second table and its drop; then the answers and SQLite's six errors on that state, as `*s4ql.Error` with codes; then a restart on an empty cache directory with the same answers; a drop there; and the first cache directory catching up with the drop.
2. A spare on another cache directory: three rounds of an insert and a query that fail with `ErrNotServing` while the first commits, a ping that ends with a context of a second, then the first's close, a ping that returns, its rows, and a commit of the spare.
3. `Register` and `sql.Open` by name, twice on one cache directory.

Added `test-s3` to `/Makefile`: it fails at once without `S4QL_S3_BUCKET`, runs `S3TESTS` in `S3PKGS` with `-race -count 1 -shuffle on -v`, prints the output, and fails unless each name in `S3TESTS` has a line `--- PASS: <name> ` at the top level.

### Why

A skip prints `--- SKIP`, and `-run` with a name that matches nothing still passes, so only a check of each name shows that every test ran.

### What worked

`S4QL_S3_BUCKET=x make test-s3 S3TESTS=TestNothing` ends with `test-s3: TestNothing did not run and pass` and exit status 2, and `make test-s3` without the variable fails before it compiles anything. The first full run passed in 54 seconds of wall time, with compilation: `TestOpen_realBucket` 24.32s, `TestClient_conformance` 31.17s, `TestClient_realBucket` 10.40s, `TestClient_core` 10.33s, `TestDeleteOld_realBucket` 2.58s; the packages run in parallel. A `grep -c` for the two credentials in the saved output found 0 lines.

### What didn't work

The first run of the new test failed in the second and third subtests: `Expected nil error, but got "s4ql: the instance has stopped: the position of the cache is not in the log: the cache is at 1bf34197..., and the log that ends at 0000... does not hold it"`. The subtests shared cache directories named `a` and `b` under one temporary directory, so the second database opened the cache of the first. Each database's caches now live under its own prefix's path. The stop is exactly what `Open` documents for a cache of another database.

### What I learned

With the defaults, the spare's subtest takes about 14 seconds and the first about 21: each statement is a commit to Tigris, and the spare waits up to its watch of 5 seconds after the close. No subtest waits for a lease to run out.

### What was tricky

The cleanup of an instance in a `t.Cleanup` closure must not capture a variable that is reassigned later, or the first cleanup closes the second instance. `byName` returns a fresh variable each time.

### What warrants review

Whether the spare's ping with a context of one second is acceptable: it asserts only that the spare does not serve while the first holds the lease, which a slow machine cannot break.

### Future work

None.

## Step 4: The CI job, which the permission system refused

**Author:** s3-ci builder

### Prompt Context

**Verbatim prompt:** (from the brief) "3. **A CI job `s3`** that runs that target with the secrets and variables above, on pull requests, on pushes to `main`, and on the schedule that CI already has (add one if it has none [...])."
**Interpretation:** A job in `/.github/workflows/ci.yml`, a schedule for that workflow, and a condition that keeps forks out.
**Inferred intent:** The target runs without a person.

### What I did

Added a daily schedule to `/.github/workflows/ci.yml`, and tried to add the job `s3`. The edit that adds the job was denied by the permission system's classifier: "Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Destructive or Unwanted Actions]." I did not try another way to write it, and took the schedule out again, so the workflow on the branch is as on `main`. The draft, for whoever adds it: under `on:` in `/.github/workflows/ci.yml`,

```yaml
  # Daily, so that the job s3 also finds a change of the real store between changes of the code.
  schedule:
    - cron: "37 6 * * *"
```

and among the jobs:

```yaml
  # The tests against a real bucket, the one that development uses, with the settings in the
  # repository's secrets and variables. Each test writes under a prefix of its own, so runs in
  # parallel do not disturb each other: see internal/store/s3test. A pull request from a fork gets
  # no secrets, and one from Dependabot gets Dependabot's secrets only, so the job does not run for
  # either. The secrets are given only to the two steps that need them.
  s3:
    if: >-
      github.event_name != 'pull_request' ||
      (github.event.pull_request.head.repo.full_name == github.repository && github.actor != 'dependabot[bot]')
    runs-on: ubuntu-latest
    timeout-minutes: 20

    steps:
      - uses: actions/checkout@v7
        with:
          persist-credentials: false

      - uses: actions/setup-go@v7
        with:
          go-version-file: go.mod
          check-latest: true

      - name: Test against the bucket
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          AWS_ENDPOINT_URL_S3: ${{ vars.AWS_ENDPOINT_URL_S3 }}
          AWS_REGION: ${{ vars.AWS_REGION }}
          S4QL_S3_BUCKET: ${{ vars.S4QL_S3_BUCKET }}
        run: make test-s3

      # A test deletes its prefix when it ends, and one that was killed leaves it. This deletes the
      # prefixes under s4ql-test/ that are more than a day old, also when the tests failed.
      - name: Delete what killed runs left in the bucket
        if: ${{ !cancelled() }}
        env:
          AWS_ACCESS_KEY_ID: ${{ secrets.AWS_ACCESS_KEY_ID }}
          AWS_SECRET_ACCESS_KEY: ${{ secrets.AWS_SECRET_ACCESS_KEY }}
          AWS_ENDPOINT_URL_S3: ${{ vars.AWS_ENDPOINT_URL_S3 }}
          AWS_REGION: ${{ vars.AWS_REGION }}
          S4QL_S3_BUCKET: ${{ vars.S4QL_S3_BUCKET }}
        run: go run ./internal/store/s3test/cleanup
```

The existing concurrency group of the workflow cancels a run of a pull request when a new commit is pushed to it; a cancelled run of `s3` leaves its prefixes, which the cleanup of a later run deletes after a day. No workflow linter was run: the project uses none, and none is installed.

The documents describe the job as it was drafted, so they are right once the lead adds it: `/docs/todo.md`, the README of `s3store`, and the package documentation of `s3test`.

### Why

The permission system decides; an agent message cannot authorize around it.

### What worked

Nothing to record beyond the draft.

### What didn't work

The edit of the workflow, as above.

### What I learned

Changes to workflows that hand secrets to a job are gated by the permission system in this setup, also when the brief asks for them.

### What was tricky

Dependabot's pull requests come from the repository itself, so the check of the head repository lets them through, and they get Dependabot's secrets, not the Actions secrets. The draft skips them with `github.actor != 'dependabot[bot]'`.

### What warrants review

The draft of the job, especially its condition and that the secrets go only to the two steps that need them.

### Future work

The lead adds the job, or Markus does.

## Step 6: Regular tests that fail without their settings, and a sweep in place of the job `s3`

**Author:** s3-ci builder (second)

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "1. **The tests against a real bucket are regular tests, and they do not skip.** "the tests shouldn't skip but fail on missing creds. That goes for all tests btw, never skip tests unless it's because of -short." [...] 2. **Where the tests go is in `.env.test`, which is committed:** `S4QL_S3_BUCKET`, `AWS_ENDPOINT_URL_S3`, `AWS_REGION`. [...] The two real secrets, `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY`, come from the environment; and, for a developer's machine, from a file `.env` next to `.env.test` if it exists [...]. A variable that is set in the environment wins over both files [...]. 3. **No separate CI job, and no schedule.** The job `test` in `ci.yml` (the shared workflow) runs them as part of `go test ./...`: give it `secrets: inherit` and `with: secret-env:` naming the two secrets. [...] Every other place that runs the tests of these packages without the credentials must pass `-short` [...]. 4. **The cleanup of leftovers is part of the regular run.** [...] before the first test prefix of a test process is made, the helper sweeps the prefixes under `s4ql-test/` whose timestamp is older than a day, once per process, with the guards that `DeletePrefix` has. [...] 5. **Documents:** correct every place that says that a job `s3` runs these tests [...]."
**Interpretation:** Turn `s3test.FromEnv` into a `Load(t)` that skips only under `-short`, reads `.env.test` and `.env` from the root of the module, fails with what is missing, and sweeps once per process; give the job `test` the two secrets; pass `-short` where tests of those packages run without them; delete the command `cleanup`, `S3TESTS`, and the check that tests ran.
**Inferred intent:** A missing credential can never turn the tests against the real store off unseen, and nothing has to be remembered to run them or to clean up after them.

### What I did

Merged `origin/main` into `s3-ci` (`90e1e55`); the one conflict, in `/Makefile`, kept `main`'s `test-changes` and the branch's `test-s3` side by side, and the rework came in its own commit.

In `/internal/store/s3test/s3test.go`, `Load(t)` replaces `Load()`, `FromEnv`, and `ErrNoBucket`. It skips under `testing.Short()`, finds the root of the module by walking up from the working directory to the first `go.mod` whose line is `module maragu.dev/s4ql` (so the cross-check module's `go.mod` is passed over), and calls `load(os.LookupEnv, root)`. `load` takes `S4QL_S3_BUCKET`, `AWS_ENDPOINT_URL_S3`, `AWS_REGION`, and `S4QL_S3_PATH_STYLE` from the environment, or from `.env.test` where the environment leaves them empty; and the two credentials as a pair, from the environment if it sets either, or else from `.env`. Each file is read for its own names only, lines `NAME=value` with an optional `export ` and matching quotes. A missing setting gives one error that lists everything missing, names the file it looked in, and says to pass `-short`; no error holds a value. Then `Load` runs the sweep, `DeleteOld` with now minus a day, through a small type `once` that marks it done only on success, so a later test of the process retries a failed sweep, and a test waits for one that runs. `Config.Client` takes options of the SDK after its own, which the tests of `s3store` use for `RequestChecksumCalculationWhenRequired`.

The tests of `s3store` now give the credentials of `Load` to `s3store.Options` and make their plain client with `s3test.Config.Client`, instead of the SDK's default chain. The subtest that skipped when a store refuses a checksum header that does not match now checks that the object is not stored instead. `TestOpen_realBucket` lost its own check of the credentials, which `Load` now makes. The command `/internal/store/s3test/cleanup` and its entry in `/internal/simlint/simlint.go` are gone.

New tests: `/internal/store/s3test/s3test_internal_test.go` covers `load` (both files, the environment over them, each file for its own names only, the message without `.env`, the pair of credentials from one place, quotes, `export`, CRLF, a name given twice, a file that cannot be read), `moduleRoot` (also past the `go.mod` of another module, and outside any module), and `once`. `TestDeleteOld` gained a listing that names keys another process already deleted. `TestDeleteOld_realBucket` now runs two `DeleteOld` at once.

`/Makefile`: `make test` passes `-short`, with a comment on what `-short` does here; `make asan-test` passes `-short`; `make test-s3` is `go test -race -count 1 -shuffle on` over `S3PKGS`. `/.github/workflows/ci.yml`: the job `test` has `secrets: inherit` and `secret-env: AWS_ACCESS_KEY_ID AWS_SECRET_ACCESS_KEY`, and a comment. The edit was not refused. `/docs/todo.md` and `/internal/store/s3store/README.md` say that the job `test` runs them.

### Why

`-short` is now the only switch that turns the tests off, and it is visible in the command. The sweep sits in `Load` and not in `NewPrefix`, because the tests of `s3test` call `NewPrefix` with clients of a fake bucket, which would have used up the one sweep of the process on the fake.

### What worked

Every place that CI runs tests was checked for the three packages. Only `make asan-test` reaches them (the root package and `s3store` link C through `internal/sqlite`); the jobs `simulation`, `sql`, `crosscheck`, `browser`, `site`, and the fuzz targets (`-run '^$'`) do not, so they got no `-short`. The sweeps of two processes at once deleted the same prefixes without an error, on the real bucket.

### What didn't work

A compound `python3` heredoc that edited three files in one Bash call was refused by the worktree guard: "this command is too complex to verify that it stays inside the worktree". The edits were made with the Edit tool instead. `go vet` then failed with `internal/store/s3test/s3test.go:273:5: too many arguments in call to s3.NewFromConfig ... have (aws.Config, func(o *s3.Options), []func(*s3.Options)...)`, since Go does not take a fixed argument before a spread; the functions are appended into one slice.

### What I learned

`-short` does more than skip the tests against the bucket. The tests of the SQL front end and of the engine (`slow()` in `/internal/engine/differential_test.go`, `/internal/sql/stmt/check_test.go`, `/internal/sql/parser/parser_test.go`, `/internal/sql/shapetest/export_test.go`, and the checks in `/internal/sql/parsetest/parsetest_test.go` and `/internal/sql/oracle/oracle_test.go`) use a tenth of the corpus under it, as under the race detector and the sanitizer. So `make test` now runs those on a tenth; `make test-sql` and CI's job `sql` run them whole. Under the sanitizer they use a tenth anyway, so `-short` in `asan-test` changes nothing else. No `t.Skip` in the repository is tied to `testing.Short()` but the one in `Load`.

### What was tricky

The developer's `.env` cannot be read, so its syntax is unknown; the parser takes what a shell would take for plain values, and passes over every other line instead of failing on it, so a stray line cannot stop the tests, and a missing name still fails with its name.

### What warrants review

The precedence in `load`, especially that the credentials come as a pair from one place; that the sweep is in `Load`; and the comment on `-short` in `/Makefile`.

### Future work

The job `test` fails on pull requests from forks and from Dependabot, which get no Actions secrets; that is open in `/docs/todo.md` for Markus to decide. The README's status says the driver has no test against a real bucket, which the lead's sub-agent updates after the merge.

## Step 7: Self-review, and the runs with and without credentials

**Author:** s3-ci builder (second)

### Prompt Context

**Verbatim prompt:** (from the brief) "Checks before you report: the real-bucket tests with credentials three times, once with `-race`; the same tests without credentials (they must fail, with the message) and with `-short` (they must skip); `make test`; `make lint`. Do not run `make test-asan` or long fuzz runs. Tests must not depend on timing."
**Interpretation:** Review the diff against `origin/main` with the code-review skill, fix what matters, and run the checks.
**Inferred intent:** Hand over a branch whose behaviour without credentials, with them, and under `-short` has been seen, not assumed.

### What I did

Ran the code-review skill at medium over `origin/main...HEAD`. It reported six things, and I decided each:

1. `make benchmark` ran `go test -bench . ./...` without `-short`, so it would now fail without credentials. Fixed: it passes `-short`.
2. `Config.Client` still loads the shared AWS configuration, so an `AWS_PROFILE` for another account could break it. Left: `s3store.New` loads it in the same way, and that is production code; `TestOpen_realBucket` isolates itself already.
3. The sweep held the mutex of `once` under the test's context, with no deadline before go test's timeout. Fixed: it runs under a timeout of five minutes.
4. The spare's subtest of `TestOpen_realBucket` assumes that the first instance keeps its lease through a few statements. Left: losing a lease of 30 seconds there takes a failed renewal, which is a real fault of the network, not an order of events that the code allows on a working store.
5. `readEnvFile` kept a comment after a value and did not take `export` with a tab. Fixed, with a subtest.
6. `secrets: inherit` gives every secret of the repository to the shared workflow at `@main`. Left: the brief asks for it, and the shared workflow exports only the names in `secret-env`. Named in the report.

Then the runs, each with the credentials loaded from the main checkout's `.env` into the environment of the test command only: `make test-s3` (race) passed in 47 seconds; two runs of `go test -count=1 -shuffle on -v . ./internal/store/s3store ./internal/store/s3test` started at the same time both passed in 24 seconds, and in each the two concurrent `DeleteOld` of `TestDeleteOld_realBucket` deleted both processes' old prefixes without an error; after the fixes, one more run with `-race` passed. A count of lines that hold either credential, done with `grep -c -F -f` on a process substitution so that no value reached a command line, gave 0 for every saved output. Without credentials (`env -u AWS_ACCESS_KEY_ID -u AWS_SECRET_ACCESS_KEY`, and no `.env` in the worktree) exactly the five tests against the bucket failed, each with `s3test: the tests against a real bucket cannot run: AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY are set neither in the environment nor in <worktree>/.env; run go test with -short to skip these tests, and see the documentation of internal/store/s3test`. With `-short` the same five skipped. `make test` without credentials and `make lint` passed; the offline tests of `s3test` passed 50 times under `-race`.

### Why

The brief asks for these runs, and the review's first finding was a target that the rule would have broken.

### What worked

### What didn't work

Nothing failed in the runs.

### What I learned

Two processes that sweep at once each report the same prefixes as deleted, since a deletion in S3 of a key that is already gone succeeds; Tigris behaves so too.

### What was tricky

Checking output for a leaked credential without putting the credential on a command line: `printf` is a builtin of the shell, so `grep -c -F -f <(printf '%s\n' "$AWS_SECRET_ACCESS_KEY") file` keeps it out of every process's arguments.

### What warrants review

That `-short` in `make test` now also puts the tests of the SQL front end on a tenth of the corpus, as step 6 says.
