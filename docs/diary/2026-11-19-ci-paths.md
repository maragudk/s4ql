# Diary: Skip the Go jobs of CI when a change touches no code

Every change runs every job of CI, also a change that touches only the site or the documents, and many direct commits to `main` are documents. The work is to decide at the start of `/.github/workflows/ci.yml` what a change touches, and to run the Go jobs only for code and the check of the site only for the site or code. The work is on the branch `ci-paths`, which starts from `main` at `9003ad8`.

## Step 1: The brief, and what the jobs read

**Author:** ci-paths builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Every change runs every CI job, also a change that touches only the site or the documents. [...] Markus, the product owner: \"Maybe we should also skip CI jobs when certain code hasn't changed? For example, we probably don't need to run asan when site/ only has changed\", and on the lead's plan: \"Sounds good, you decide the split on what runs when. We can adjust down the road if needed.\" [...] 1. **A job `changes` at the start of `ci.yml`** that decides what the change touches and gives outputs that the other jobs depend on [...] No third-party action for the decision: a small script that takes the list of changed files, so that the rule can be tested without GitHub. 2. **Conservative by an allowlist.** The change is \"not code\" only if every changed file is in a list of paths that no test, lint, or build of the Go code reads. Start from: `docs/**`, `site/**`, `.impeccable/**`, `PRODUCT.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `LICENSE`. Before you trust that list, find out what the jobs read [...] 3. **The split.** With \"code\": everything runs, as today. Without it: the jobs that test, lint, fuzz, simulate, cross-check, and generate Go code do not run [...] The check of the site runs when the change touches what it reads [...] move it into a job of its own [...] 4. **When the decision cannot be made, everything runs:** a schedule or a manual run, a push whose previous commit is unknown or all zeros (a new branch, a forced push), a diff that fails, a shallow checkout that lacks the base. [...] 5. **Other workflows** [...] apply the same idea only where it is clearly right and small [...] 6. **Tests of the rule.** The script has a table of cases that runs in CI and locally [...] A wrong rule turns checks off without anyone seeing it, so prefer running too much. [...] simulate the decision locally for real commits of this repository: run your script over the changed files of the last 40 commits on `main` [...]"
**Interpretation:** Write a POSIX shell script that turns a list of changed paths into two answers, code and site, and a part that gets the list from git for the event of the run, falling back to "everything" whenever it cannot. Add a job `changes` that runs the script's own tests and then the decision, make every Go job depend on its answer, and move `make site-check` out of `browser` into a job of its own.
**Inferred intent:** Documents and site work stop waiting for, and paying for, half an hour of Go jobs, without any check of code being turned off by mistake.

### What I did

Reset the worktree to `origin/main` at `9003ad8` and created the branch `ci-paths`. Read `/AGENTS.md`, the four workflows in `/.github/workflows/`, and the `/Makefile`, and searched the code for anything that reads a file under `/docs/`, `/site/`, or a Markdown file.

What the workflows do:

- `/.github/workflows/ci.yml` runs on a push to `main` and on a pull request to `main`. The jobs `lint` and `test` call the reusable workflows `lint.yml` and `test.yml` of `maragudk/workflows`; the others (`simulation`, `sql`, `proto`, `crosscheck`, `asan`, `asan-fuzz` with four shards, `fuzz`, `browser`) run their steps here. `browser` builds, vets, and lints the browser's build, tests and lints the simulator, runs the tests in headless Chrome, and as its last step runs `make site-check`, which runs `make site` (builds the engine with Go into `/site/simulator/engine/`) and then `internal/simulator/sitecheck`, which serves `/site/` and drives `/site/simulator/` in Chrome.
- `/.github/workflows/pages.yml` already runs only on pushes that touch `site/**`, `internal/**`, `go.mod`, `go.sum`, `Makefile`, or the workflow itself, and on a manual run.
- `/.github/workflows/sqlite-verify.yml` already runs only on changes to the vendored SQLite, the corpus, and the code that makes them.
- `/.github/workflows/security.yml` runs `govulncheck` through a reusable workflow on push, pull request, a daily schedule, and a manual run.

What reads documents, the site, or Markdown:

- `/internal/sql/stmt/check_test.go` reads `/internal/sql/stmt/README.md`, the vocabulary of what is not supported. So the README of a Go package is read by a test.
- `make mutation` (`/internal/sql/mutation/main.go`) hashes every file under `/internal/`, Markdown too, into the fingerprint of its results. It does not run in CI, but it is one more reason to keep every file under `/internal/` as code.
- `make site-check` and the Pages workflow read all of `/site/`, and they build the engine from the Go code.
- Nothing reads `/docs/`: the hits for `docs/` in Go files are comments, and `/site/index.html` only links to the documents on GitHub. No workflow, no `Makefile` target, no `go:embed`, and no test reads `/README.md`, `/AGENTS.md`, `/CLAUDE.md` (a link to `/AGENTS.md`), `/PRODUCT.md`, `/LICENSE`, or `/.impeccable/`. The files under `/docs/` are all `.md` and `.txt`, and those under `/site/` are HTML, JavaScript, fonts, and images, so `go build ./...` sees none of them.

### Why

The allowlist is only as safe as the search behind it: a file on the list that a test reads would let a change to it pass without the test.

### What worked

A grep over Go files, the `Makefile`, and the workflows for `os.ReadFile`, `go:embed`, `docs`, `site/`, `README`, and `.md` found every reader in a few calls.

### What didn't work

Nothing failed in this step.

### What I learned

The README of `/internal/sql/stmt/` is test input: a change to its vocabulary can break `TestCheck`. Markdown inside `/internal/` therefore stays code.

### What was tricky

`git diff --name-only` shows only the new name of a renamed file. A Go file moved from `/internal/` into `/docs/` would then look like a change to documents only, and the deletion of the Go file would go unseen. The diff must run with `--no-renames`, so that both names are listed.

### What warrants review

Whether a skipped job counts for the rule in `/AGENTS.md` on merging, which counts the checks of a pull request against "as many as CI has jobs" in the bucket `pass`: a skipped job is in the bucket `skipping`.

### Future work

None yet.

## Step 2: The rule, as a script with a table of cases

**Author:** ci-paths builder

### Prompt Context

**Verbatim prompt:** (from the brief) "a small script that takes the list of changed files, so that the rule can be tested without GitHub. [...] The script has a table of cases that runs in CI and locally (a `make` target, called from a job that always runs, for example `changes` itself) [...] Plain POSIX shell is fine; a tiny Go program with a Go test is fine too if it does not make the job `changes` slow. Say which you chose and why."
**Interpretation:** Write the rule and its tests first, red then green, before touching the workflow.
**Inferred intent:** A rule that can be read, run, and broken on purpose on a laptop.

### What I did

Wrote `/.github/scripts/changes_test.sh` first and ran it against a missing script: `changes_test: 48 of 50 cases failed` (the two that passed were the case of an unknown mode, which expects no output and a failure). Then wrote `/.github/scripts/changes.sh`, with two modes:

- `sh changes.sh paths < list` prints `code=...` and `site=...` for a list of paths, one a line.
- `sh changes.sh event` reads `EVENT`, `BASE`, `BEFORE`, `FORCED`, and `HEAD`, checks that the base and the head are commits in the checkout, lists the changed paths with `git -c core.quotePath=false diff --no-renames --name-only "$base" "$HEAD" --`, and decides for them. Whenever it cannot decide it prints `code=true` and `site=true` with the reason on standard error.

The rule: a path is not code if it is under `docs/`, `site/`, or `.impeccable/`, or is `PRODUCT.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, or `LICENSE` at the top, unless it is a Go file, a `go.mod`, a `go.sum`, or a `go.work`, which are code wherever they are. `site` is true with code or when a path under `site/` changes. An empty list of changes is code. Added `make test-changes` to the `/Makefile`, and made `make test` run it first.

The table has 52 cases: 27 lists of paths (only documents, only the site, the site and documents, one Go file, a document and a Go file, a Go file under `docs/`, a workflow, the script itself, the `Makefile`, `.env.test`, `go.mod`, two Markdown files inside Go packages, names like listed ones at other places, paths with a space, a path that git quotes, a list without a final line feed, an empty list, a list of empty lines), 22 runs of the mode `event` against a temporary repository (pushes of one and of several commits, a Go file and a text file renamed into `docs/`, a document renamed into a Go package, a deleted Go file, a document with a space and one with `ü` in its name, an empty commit, a forced push, a new branch with a previous commit of zeros, no previous commit, a previous commit or a head that the checkout lacks, a previous commit that is not a commit name, pull requests, a schedule, a manual run, no event), a shallow clone that lacks the previous commit, and an unknown mode.

### Why

Plain POSIX shell, because the job `changes` then needs no setup of Go and starts its decision within seconds of the checkout, the rule is a `case` statement that reads like the list it implements, and the runners' `sh` is `dash`, which is also on this machine to test with. The tests run the script as the job does, through its mode `event` against real commits, so that the options of `git diff` are under test too, not only the list.

### What worked

The tests pass under `sh` (bash in POSIX mode on macOS), `dash`, and `bash`: `make test-changes`, `SH=dash make test-changes`, and `SH=bash make test-changes` each print `changes_test: all 52 cases passed`.

To check that the table catches a wrong rule, a scratch script made 14 mutants of `changes.sh`, one at a time, and ran the tests on each. 11 failed the tests, among them dropping `--no-renames`, dropping the exception for Go files, putting `internal/*` on the list, turning `core.quotePath` back on, treating a schedule as a pull request, and comparing a pull request with `BEFORE`. Three survived, and each is a guard behind another guard: without the check for a commit of zeros, the check that the commit is in the checkout still fails; without the check for hex digits, `git cat-file` still refuses `--output=x`; and without `git cat-file`, `git diff` still fails on a missing commit. I kept them, because each says in the script what it guards against, and the hex check keeps a value from reaching `git diff` as an option.

### What didn't work

Dropping `--no-renames` passed the first version of the tests. Its only rename case moved a Go file into `docs/`, which the exception for Go files catches by its name alone. A second case that moves a text file from `internal/a/` into `docs/` fails without `--no-renames`, since `git diff --name-only` then lists only `docs/notes.txt`. Turning `core.quotePath` back on passed too, until a case with `docs/über.md` was added: git quotes that name by default, and a quoted name is never listed, so the mutant ran everything for a document.

The first try at the mutants was a one-line loop in Bash, which the sandbox refused: "this command names git in a form too complex to verify that it stays inside the worktree". The same loop from a file in the scratchpad ran.

### What I learned

`git diff --name-only` follows renames by default since git 2.9, and then prints only the new name. `--no-renames` lists a rename as a deletion and an addition.

### What was tricky

An empty list of changes could mean an empty commit, or a comparison of the wrong commits. The script treats it as code, so that a mistake in the comparison runs everything.

### What warrants review

The list in `listed` in `/.github/scripts/changes.sh`, against the search in step 1, and the rule that a Go file is code wherever it is.

### Future work

Markdown inside `internal/` that no test reads, such as `internal/simulator/README.md`, could go on the list package by package, after a check that no test reads it. It would have saved two of the 40 runs.

## Step 3: The job `changes`, the conditions, and the job `site`

**Author:** ci-paths builder

### Prompt Context

**Verbatim prompt:** (from the brief) "With \"code\": everything runs, as today. Without it: the jobs that test, lint, fuzz, simulate, cross-check, and generate Go code do not run (`lint`, `test`, `simulation`, `sql`, `proto`, `crosscheck`, `asan`, `asan-fuzz`, `fuzz`, and the Go parts of `browser`). The check of the site runs when the change touches what it reads [...] or is \"code\". Today that check is a step inside `browser`; move it into a job of its own so that it can run alone, with only the setup it needs. [...] For a pull request compare with its base; for a push compare with the commit before the push (all commits of the push, not only the last). Get the checkout depth right for both. [...] **Other workflows** (`Security`, `Pages`, and any other): look at them and apply the same idea only where it is clearly right and small"
**Interpretation:** Put the job `changes` first in `/.github/workflows/ci.yml`, make every other job depend on it, and split the site check out of `browser`.
**Inferred intent:** The rule of step 2, wired so that a failure of the wiring runs more, not less.

### What I did

In `/.github/workflows/ci.yml`:

- The job `changes` checks out with `fetch-depth: 0`, runs `sh .github/scripts/changes_test.sh`, and then `sh .github/scripts/changes.sh event` with `EVENT=github.event_name`, `BASE=github.event.pull_request.base.sha`, `BEFORE=github.event.before`, `FORCED=github.event.forced`, and `HEAD=github.sha`. It writes the two lines to `$GITHUB_OUTPUT` and to the log, and gives them as the outputs `code` and `site`.
- Every other job has `needs: changes` and `if: ${{ !cancelled() && needs.changes.outputs.code != 'false' }}`, and the new job `site` the same on `site`. The comparison is with exactly `'false'`, and `!cancelled()` makes a job run even when `changes` failed, when its outputs are empty: a broken `changes` job turns red and runs everything.
- The job `site` checks out, sets up Go, and runs `make site-check` with `S4QL_CHROMIUM_FLAGS=--no-sandbox`. The step left `browser`, whose comment now points to `site`.

For a pull request, `github.sha` is the commit that merges the pull request into its base, so its diff with the base is what the pull request changes. If the base moved on between the event and the merge commit, the diff also has the base's new changes, which only adds paths. For a push, `git diff before after` compares the two trees, so it takes in every commit of the push. The whole history is about 11 MiB packed (`git count-objects -vH`: `size-pack: 11.42 MiB`), so `fetch-depth: 0` is cheap, and it is the only depth that has the base of any pull request and the commit before any push.

The other workflows stay as they are. `/.github/workflows/pages.yml` and `/.github/workflows/sqlite-verify.yml` already run only for the paths they read. `/.github/workflows/security.yml` runs `govulncheck` on every push and pull request and daily: a filter there would need a second copy of the allowlist, as a workflow's `paths-ignore`, which could drift from the script, for one short job whose result also depends on the database of vulnerabilities, not only on the change.

### Why

The job `changes` runs the test script directly and not through `make test-changes`: it has no Go set up, and `make` reads the whole `/Makefile` first, whose `ifeq ($(shell go env GOOS),linux)` runs `go env` in the module, which may download the Go 1.27.3 that `/go.mod` names onto a runner that has an older one.

### What worked

`make site-check` passed alone from a clean checkout (`sitecheck: ok`), as the job `site` runs it. A scratch Python script parsed `/.github/workflows/ci.yml` with PyYAML and checked that every job but `changes` has `needs: changes` and the right condition, and listed the steps of each job: the Go steps of `browser` are all still there, and `site` has only the checkout, the setup of Go, and the check. The decision for this branch as a pull request from `9003ad8` is `code=true`, from `.github/scripts/changes.sh`, `.github/scripts/changes_test.sh`, and the `Makefile`.

### What didn't work

`go run github.com/rhysd/actionlint/cmd/actionlint@v1.7.7 -shellcheck= .github/workflows/ci.yml` was refused by the permission system ("Permission for this action was denied by the Claude Code auto mode classifier. Reason: [Undermining Oversight]"), so the workflow is not checked by actionlint. Only a run on GitHub will show that the expressions and the outputs behave as intended.

### What I learned

A job whose `needs` failed is skipped unless its `if` has a status function; `!cancelled()` is the one that runs it after a failure but not after a cancellation of the run.

### What was tricky

Skipped jobs count as passed checks on GitHub, so a decision that skipped wrongly would look green. That is why the rule is an allowlist and every doubt is code.

### What warrants review

The first run on GitHub: that a pull request of this branch runs every job (it changes `.github/`), that the log of `changes` shows the comparison and the decision, and later that a push of a document runs only `changes`. The rule in `/AGENTS.md` on merging counts the checks against "as many as CI has jobs" in the bucket `pass`; a skipped job is in the bucket `skipping`, and CI now has two more jobs, `changes` and `site`.

### Future work

The rule in `/AGENTS.md` on merging needs to allow skipped jobs and to count the two new ones; that is the lead's to change.

## Step 4: Self-review, and three fixes

**Author:** ci-paths builder

### Prompt Context

**Verbatim prompt:** (from the brief) "Review your own diff once more before you report."
**Interpretation:** Run the code-review skill over `9003ad8...HEAD`, judge each finding, and fix what matters.
**Inferred intent:** No hole in the rule that a reviewer could find in an afternoon.

### What I did

Ran the code-review skill (`/code-review medium 9003ad8...HEAD`). It reported three findings, and I fixed all three:

1. **Important: a cancelled run on `main` would leave code untested.** The concurrency group of CI was `CI-main` for every push to `main`, without `cancel-in-progress`, and GitHub keeps only one pending run in a group: a new pending run cancels the older pending one. With the job `changes`, a push of Go code whose run was still pending when a push of a document came would never be tested, since the later run compares only with its own previous commit and sees a document. Before this branch the later run tested the whole tree. The group of a push is now `CI-<sha>`, so no run of a push waits for, or is cancelled by, another; a pull request keeps its group by ref, since it is compared with its base and a new run covers all of it.
2. **Nit: a Go package under `docs/` or `site/`.** Only its Go files, `go.mod`, `go.sum`, and `go.work` were code; a file that it embeds or its test data would have counted as a document. The mode `event` now lists the tree of `HEAD` under `docs`, `site`, and `.impeccable` with `git ls-tree -r -z --name-only`, and runs everything while any `.go`, `go.mod`, or `go.work` is there. None is today, so the decisions for the 40 commits are the same (checked by running the scratch script again and diffing its output: the same).
3. **Nit: the tests used the git configuration of the machine.** A global hook or template could reject the commits of the temporary repository, and the cases would then fail with empty commit names. The tests now set `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_CONFIG_NOSYSTEM=1`, `core.hooksPath=/dev/null`, and `git init --template=`, and stop with "cannot make the temporary repository" if a commit fails.

Four new cases: a push of a Go package under `site/`, a push of a file that it embeds, and pushes of a document while `site/` or `docs/` holds a Go package. Before the fix of the script, three of them failed (`changes_test: 3 of 56 cases failed`); after it, all 56 pass under `sh`, `dash`, and `bash`.

### Why

The first finding is the kind of fault that the brief warns about: checks that turn off without anyone seeing it. Direct pushes of documents right after a merge are common in this repository, so it would have happened.

### What worked

The mutants of step 2, run again: the same three guards behind guards survive, and every other mutant fails the tests.

### What didn't work

After the second fix, the mutant that drops `--no-renames` survived again: the case of a text file renamed into `docs/` came after the case that moved a Go file into `docs/`, so the new check of the tree made it code by itself. The two commits now come in the other order, and the mutant fails the tests again.

### What I learned

A concurrency group without `cancel-in-progress` still cancels: it keeps one running and one pending run, and drops the older pending one. Any CI that compares a push with only its previous commit has to keep every run of a push.

### What was tricky

With the group by commit, runs of pushes to `main` that come close together now run at the same time instead of one after another. Nothing in CI shares state between runs, and the Pages workflow has its own group, so this costs only runners.

### What warrants review

The new `concurrency` of `/.github/workflows/ci.yml`. One gap stays: if someone cancels a run of a push to `main` by hand, the next push of documents will not test its commits, as before it would have. Neither the skipped jobs of a later run nor its green mark show that.
