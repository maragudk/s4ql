# Diary: Skip the Go jobs of CI when a change touches no code

Every change runs every job of CI, also a change that touches only the site or the documents, and many direct commits to `main` are documents. The work is to decide at the start of `/.github/workflows/ci.yml` what a change touches, and to run the Go jobs only for code and the check of the site only for the site or code. The work is on the branch `ci-paths`, which starts from `main` at `9003ad8`.

## Step 1: The brief, and what the jobs read

**Author:** ci-paths builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Every change runs every CI job, also a change that touches only the site or the documents. [...] Markus, the product owner: \"Maybe we should also skip CI jobs when certain code hasn't changed? For example, we probably don't need to run asan when site/ only has changed\", and on the lead's plan: \"Sounds good, you decide the split on what runs when. We can adjust down the road if needed.\" [...] 1. **A job `changes` at the start of `ci.yml`** that decides what the change touches and gives outputs that the other jobs depend on [...] No third-party action for the decision: a small script that takes the list of changed files, so that the rule can be tested without GitHub. 2. **Conservative by an allowlist.** The change is \"not code\" only if every changed file is in a list of paths that no test, lint, or build of the Go code reads. Start from: `docs/**`, `site/**`, `.impeccable/**`, `PRODUCT.md`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `LICENSE`. Before you trust that list, find out what the jobs read [...] 3. **The split.** With \"code\": everything runs, as today. Without it: the jobs that test, lint, fuzz, simulate, cross-check, and generate Go code do not run [...] The check of the site runs when the change touches what it reads [...] move it into a job of its own [...] 4. **When the decision cannot be made, everything runs:** a schedule or a manual run, a push whose previous commit is unknown or all zeros (a new branch, a forced push), a diff that fails, a shallow checkout that lacks the base. [...] 5. **Other workflows** [...] apply the same idea only where it is clearly right and small [...] 6. **Tests of the rule.** The script has a table of cases that runs in CI and locally [...] A wrong rule turns checks off without anyone seeing it, so prefer running too much. [...] simulate the decision locally for real commits of this repository: run your script over the changed files of the last 40 commits on `main` [...]"
**Interpretation:** Write a POSIX shell script that turns a list of changed paths into two answers, code and site, and a part that gets the list from git for the event of the run, falling back to "everything" whenever it cannot. Add a job `changes` that runs the script's own tests and then the decision, make every Go job depend on its answer, and move `make site-check` out of `browser` into a job of its own.
**Inferred intent:** Documents and site work stop waiting for, and paying for, half an hour of Go jobs, without any check of code being turned off by mistake.

### What I did

Reset the worktree to `origin/main` at `9003ad8` and created the branch `ci-paths`. Read `/AGENTS.md`, the four workflows in `/.github/workflows/`, and the `/Makefile`, and searched the code for anything that reads a file under `/docs/`, `/site/`, or a Markdown file.

What the workflows do:

- `/.github/workflows/ci.yml` runs on a push to `main` and on a pull request to `main`. The jobs `lint` and `test` call the reusable workflows `lint.yml` and `test.yml` of `maragudk/workflows`; the others (`simulation`, `sql`, `proto`, `crosscheck`, `asan`, `asan-fuzz` with four shards, `fuzz`, `browser`) run their steps here. `browser` builds, vets, and lints the browser's build, tests and lints the simulator, runs the tests in headless Chrome, and as its last step runs `make site-check`, which runs `make site` (builds the engine with Go into `/site/simulator/engine/`) and then `internal/simulator/sitecheck`, which serves `/site/` and drives `/site/simulator/` in Chrome.
- `/.github/workflows/pages.yml` already runs only on pushes that touch `site/**`, `internal/**`, `go.mod`, `go.sum`, `Makefile`, or the workflow itself, and on a manual run.
- `/.github/workflows/sqlite-verify.yml` already runs only on changes to the vendored SQLite, the corpus, and the code that makes them.
- `/.github/workflows/security.yml` runs `govulncheck` through a reusable workflow on push, pull request, a daily schedule, and a manual run.

What reads documents, the site, or Markdown:

- `/internal/sql/stmt/check_test.go` reads `/internal/sql/stmt/README.md`, the vocabulary of what is not supported. So the README of a Go package is read by a test.
- `make mutation` (`/internal/sql/mutation/main.go`) hashes every file under `/internal/`, Markdown too, into the fingerprint of its results. It does not run in CI, but it is one more reason to keep every file under `/internal/` as code.
- `make site-check` and the Pages workflow read all of `/site/`, and they build the engine from the Go code.
- Nothing reads `/docs/`: the hits for `docs/` in Go files are comments, and `/site/index.html` only links to the documents on GitHub. No workflow, no `Makefile` target, no `go:embed`, and no test reads `/README.md`, `/AGENTS.md`, `/CLAUDE.md` (a link to `/AGENTS.md`), `/PRODUCT.md`, `/LICENSE`, or `/.impeccable/`. The files under `/docs/` are all `.md` and `.txt`, and those under `/site/` are HTML, JavaScript, fonts, and images, so `go build ./...` sees none of them.

### Why

The allowlist is only as safe as the search behind it: a file on the list that a test reads would let a change to it pass without the test.

### What worked

A grep over Go files, the `Makefile`, and the workflows for `os.ReadFile`, `go:embed`, `docs`, `site/`, `README`, and `.md` found every reader in a few calls.

### What didn't work

Nothing failed in this step.

### What I learned

The README of `/internal/sql/stmt/` is test input: a change to its vocabulary can break `TestCheck`. Markdown inside `/internal/` therefore stays code.

### What was tricky

`git diff --name-only` shows only the new name of a renamed file. A Go file moved from `/internal/` into `/docs/` would then look like a change to documents only, and the deletion of the Go file would go unseen. The diff must run with `--no-renames`, so that both names are listed.

### What warrants review

Whether a skipped job counts for the rule in `/AGENTS.md` on merging, which counts the checks of a pull request against "as many as CI has jobs" in the bucket `pass`: a skipped job is in the bucket `skipping`.
