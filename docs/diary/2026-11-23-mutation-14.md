# Diary: Mutation testing of slice 14

Slice 14 (`returning` on `insert`, `update`, and `delete`: the statement pass of #129, the engine and the driver of #130, and the generated checks of #131) is built and merged, and no round of the mutation tester `internal/sql/mutation` has run over its code. This task runs it over every function that the slice added or changed, kills every survivor with a test of what the code promises, lists it in `equivalent.txt` with a reason, or removes code that nothing needs, and fixes any fault it shows. The branch is `worktree-agent-aa464ec2f3c64d4c6`, from `main` at `8f5156e`.

## Step 2: The survivors of the first runs

**Author:** mutation-14 builder

### Prompt Context

**Verbatim prompt:** (from the brief) "**For every mutant that survives**, decide which it is: a gap in the tests (write the test that kills it; a table test where the generated checks cannot reach it, a required kind or an aimed profile where they should have), dead or needless code (remove it, if the removal is clearly right and small), a real fault in s4ql (the best outcome: write the smallest test that shows it, fix it if the fix is small and clear, and report it prominently), or truly equivalent (add it to `equivalent.txt` with a reason a reader can check; the last slice's first run had two wrong entries there, so be strict: an entry needs an argument, never \"no test fails\")."
**Interpretation:** Classify each survivor as it comes, check each new test against its mutant at once through the overlay, and give every entry of the list an argument that a reader can follow in the code.
**Inferred intent:** No survivor of slice 14 left without a reason, and no entry in the list that hides one.

### What I did

- The three first runs ended on `tree1`: `stmt` 204 mutants, 19 not compiled, 184 killed, 1 survived (the accept of a node that the list held already); the root 45, 6 not compiled, 31 killed, 5 timed out, 3 survived; the engine 1,510, 361 not compiled, 1,076 killed (1,046 by the hand-written tests, 30 by the simulation), 2 timed out, 71 survived, of which 29 the list held already.
- The engine's run was stopped twice and continued in the same results directory: once to go from 3 workers to 5 when the other two runs had ended, and once to add `-first` with the tests of RETURNING, the plans, the sinks, and the events, which cut the hand-written stage of a killed mutant from up to 40 s to about 4 s.
- Gaps in the tests, each with a test that kills its mutants, checked through `scripts/mut.sh`:
  - `Rows.Holds` had no test in the engine; only the root's tests read it, and they do not run for a mutant of the engine. "should hold nothing with the rows of a RETURNING outside a transaction, which a begin and a statement beside them do not wait for, and hold the connection with them in one" of `TestConn_returning` reads it for each kind of rows, and begins a transaction while the rows of a RETURNING outside one are open, which the mutant that made them the connection's rows (`c.tx != nil => true`) refused with `ErrRowsOpen`.
  - The driver's `QueryContext` that does not close the engine's rows when the connector refuses to hold them: "should refuse a query that comes while the close closes the rows that are open" of `TestClose` now requires a second refused query on the same connection to be refused as closed, where the mutant gave `s4ql: not supported: a statement that reads on a connection whose rows of an earlier query are open`.
  - The draw of a direction for an insert with RETURNING: a subtest of `TestEngine_reading` counts one draw for each insert, update, and delete with RETURNING, of its own and in a transaction, through Exec and Query, and none without it, and reads `Engine.order` directly on each kind of plan.
  - The read of the row before a delete with RETURNING: `TestChangeRows` has the calls of a delete and an update with RETURNING, the error of that read, and a row that is gone at that read.
  - `buildReturning` of a RETURNING of no columns, and `dropReturns` of each sink: `TestBuildReturning` and `TestDropReturns` in the new `/internal/engine/returning_internal_test.go`.
  - In a transaction, `Exec` of a delete with RETURNING read each row again, and `Query` of an update or a delete with RETURNING had no direction in its event, with the mutants of `Conn.writeIn` that hold the rows for `Exec` and that do not record the draw: the Exec and the event subtests of `TestConn_returning` now run in a transaction too.
- Code that nothing needs: the `slices.Clone` before the reverse in `newReturned`. Each statement calls `returnedOf` once, and nothing reads the sink's rows after it, so the rows are reversed in place, and the doc says so.
- Equivalent, in two new sections of `/internal/sql/mutation/equivalent.txt`: the `err != nil` of `Conn.queryText` beside a nil `ret`; the `noRows` shortcut of the driver for a statement that is no query, whose rows over engine rows that have ended give the same; `v.HasReal() => true` in `returning.add`, since `GetReal` of anything else is +0.0; and 16 variants of the planted bugs `rowsOfFailed`, `skipUnique`, `starKeyFirst`, `dropLast`, and of `oldValues`, `deleteNone`, and `starKeyFirst` left out of a write in a transaction.
- Two old entries were wrong after slice 14, and the report of the first run showed both as matching no survivor: `report.end condition: r.access != "" => true #2`, which said that a direction is never set without an access (an insert with RETURNING draws one and has no access, and the event test of RETURNING kills it), is gone; and `report.end remove statement: return =>` named the new guard `if r.ended { return }` once slice 14 put it first in the function, so the entry of the check of the level is `#2` now.

### Why

The planted bugs follow the rule of the earlier rounds: a variant that the test of the planted bugs still finds is another planted bug, and the test passing is that finding. Each reason says how it is found.

### What worked

- `-first` with the tests of the slice: the last 1,290 mutants of the engine ran in about 1 h 10 min with 5 workers at a load of 18 to 26, where the first 220 had taken 23 min with 3.
- The overlay checker: each new test failed on its mutant in a second, with the message that the reason above quotes.

### What didn't work

- A first reason for the mutant of `SetsChanges` in the planted bug `rowsOfFailed` said "the simulation reads no count of changes"; `run.statement` in `/internal/engine/simulation_test.go` does read it where `SetsChanges` is set. The reason now says that the mutant makes it read none for that statement.
- The first version of the Exec test in a transaction inserted two rows with one statement and got `not supported`, since slice 14 supports one row per insert; it inserts them one at a time.
- Commands that chained `git add` and `git commit` with `go test` were refused: "this command names git in a form too complex to verify that it stays inside the worktree". Each git command runs alone.

### What I learned

- An engine mutant runs only the tests under `internal`, so a promise that only the driver reads, such as `Rows.Holds`, needs a test in the engine too.
- A new statement at the top of a function renumbers the keys of the same text after it, so an old entry can silently name a new mutant. The report's list of entries that match no survivor is what shows it.

### What was tricky

- Telling a planted bug's variant from a gap: `returns => true` in the hook of `rowsOfFailed` changes nothing at all, since `dropReturns` has already emptied the sink where `returns` is false, while `returnsOf(s) != nil => true` plants a wider bug that the simulation finds by its own violation.

### What warrants review

- The reasons of the new entries, above all the driver's `noRows` shortcut, whose only difference is a nil or an empty slice of names.

### Future work

- The rerun on the final code, the checks, the self-review, and the notes.
