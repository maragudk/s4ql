# Diary: Slice 6 of the roadmap in the statement pass, `null`

Slice 6 adds a column that takes NULL, the literal NULL as a value of an insert, and a nil argument. This task is the statement pass, `internal/sql/stmt`, and its generator `stmttest`; the engine and the driver do not store NULL yet, and refuse the new forms as not supported until their builder comes. The work is on the branch `null-stmt`, from `origin/columns-checks` at `bcbee40` (pull request #74, the generated checks of slice 5, in review).

## Step 1: The typed form, the recognizer, the generator, and the refusal in the engine

**Author:** null-stmt builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "The statement pass (`internal/sql/stmt`) reads the statements of slice 6. [...] **A nullable column:** in `create table`, a column that is not the primary key may be declared without `not null`. [...] **The literal `null`** as a value of an `insert`, in any case of the letters. `stmt.Term` must say that the value is null in a way that cannot be mistaken for a parameter (today a nil `Value` means a parameter): choose the shape and document it. A sign before `null` (`-null`, `+null`), which SQLite reads as null, is rejected as not supported, with a name of its own. **Stays not supported, each with a name that says what it is:** the column constraint `null` (`v2 text null`), `default`, `is null` and `is not null` and every other expression, `null` anywhere but as a value of an `insert`. [...] the engine refuses what it cannot run yet (a `create table` with a nullable column, an `insert` with a `null` literal) with an error that matches `stmt.ErrNotSupported`, in `engine.Check` too, so that `Prepare` in the driver refuses at once."
**Interpretation:** Extend the recognizer and the typed form to the two forms of slice 6, check each against SQLite as the pass's tests do, extend `stmttest` behind an option so that the engine's and the driver's generated tests draw the same calls, and make the engine and the driver refuse the new forms at the check of the text, as `checkColumns` did for slice 5.
**Inferred intent:** The front half of slice 6 with the same trust as slices 1 to 5, so that the engine's builder only has to make the engine store NULL.

### What I did

`/internal/sql/stmt/stmt.go`: a fifth value, `stmt.Null`, an empty struct. A `Term` of the literal NULL has `Value: stmt.Null{}` and `Parameter: 0`; a nil `Value` still means a parameter, so the two cannot be taken for each other. `/internal/sql/stmt/recognize.go`: `column` no longer requires PRIMARY KEY or NOT NULL; a NULL constraint without NOT is `NULL constraint`; `literal` gives `Null{}` for a NULL token, and `NULL after a sign` for `-null` (at the NULL, after the `-` is taken, as `string after a sign` does) and for `+null` (at the `+`). Gone: the names `column without PRIMARY KEY or NOT NULL`, `column without NOT NULL`, and `NULL`. `table without PRIMARY KEY` now covers a table of nullable columns without a key.

`/internal/sql/stmt/stmttest`: `Generator.Nulls`; with 0 the generator draws as before, with n one column in n that is not the key lacks NOT NULL, and one value in n is NULL, as a literal or a `?` with a nil argument. `Literal`, `Argument`, and `LiteralKind` know `stmt.Null`. The pass's tests set `Nulls = 5`.

Tests: `checkInsert` in `/internal/sql/stmt/stmt_test.go` puts the key on the first value that is not NULL, gives a column of a NULL a type from the five and no NOT NULL, and a new `checkNotNull` checks that on a table whose columns all say NOT NULL SQLite gives `NOT NULL constraint failed: T.c` (1299) for the first column in table order that gets NULL; an insert of only NULLs is checked only that way. `checkCreateTable` expects `notnull` 0 for a nullable column. About 40 hand-written cases in `/internal/sql/stmt/check_test.go`; near misses in `/internal/sql/stmt/generate_test.go` replace the four that became supported and add eleven more.

The engine: `checkNulls` in `/internal/engine/errors.go`, called by `engine.Check` and `prepare`, and `NewPlan` panics for those forms. The driver's `check` in `/conn.go` calls `engine.Check` for a supported statement again. `checkText` wrappers came back in `/internal/engine/differential_test.go` (also used by `/internal/engine/simulation_test.go`) and in `/internal/sqlite/crosscheck/drivercheck/drivercheck_test.go`, at the same places as in `eb25197`. `TestEngine_nulls` in `/internal/engine/engine_test.go` and `TestPrepare` in `/conn_test.go` pin the refusals.

### Why

`-null` and `+null` give NULL in SQLite, but the roadmap's principle is to reject a form that is not listed; a name of its own says why. `v2 text null` means the same as `v2 text` in SQLite, and stays not supported as the brief asks, with the name `NULL constraint`.

### What worked

- A dump of 27,000 texts and arguments of `Generator` (with `Columns` 0 and 3) and `Sequence` from 30 seeds, written once on the new code and once with `internal/sql/stmt` checked out from `bcbee40` through a temporary WIP commit, was byte for byte the same (`cmp old.txt new.txt && echo SAME`).
- `go test -count=1 ./internal/engine/ .` and `cd internal/sqlite/crosscheck && go test -count=1 ./...` passed with their pinned numbers unchanged.
- Every guessed name of the new hand-written cases (`IS`, `NULL test`, and so on) was right at the first run.

### What didn't work

- `TestPrepare` in the root package failed with `Expected "column without NOT NULL (at offset 44)", but got "a column that takes NULL, which the engine does not run yet"`; it now pins `v2 text null` as `NULL constraint (at offset 45)` and the two refusals of the engine.
- `TestOpen_realBucket` fails without credentials (`AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY are set neither in the environment nor in .../.env`), as it should; `make test` runs with `-short`.
- A Bash command with a heredoc that appended to a test file was refused: "this command is too complex to verify that it stays inside the worktree". The Edit tool worked.

### What I learned

The pinned numbers moved only because the generator draws other numbers with `Nulls` on; a throwaway test that grouped the excused texts by SQLite's message, on the old and the new code, found no new message. Mutants: syntax errors where SQLite does not say 85 to 77 (76 `duplicate column name`, 1 collation; before 83 and 2), not supported where SQLite does not say 310 to 305 (251 `unknown table option`, 47 `duplicate column name`, 6 collation, 1 AUTOINCREMENT; before 254, 51, 3, 2). Near misses 3,022 to 2,942: 502 CREATE TABLE among the 2,000 statements where there were 520, so 4 × 502 `more than one primary key`, 502 generated columns, 406 AUTOINCREMENT, and 26 of the two table-constraint forms. The corpus's excused numbers did not move; its supported texts went from 12,736 to 13,454: 717 more INSERT with NULL and 1 more CREATE TABLE.

### What was tricky

- An insert of only NULLs cannot be stored in any table, since the key is never NULL; `checkInsert` checks only the errors then.
- `Others` of `stmttest.Sequence` has `insert into %[1]v (%[2]v) values (null)`, which the pass now supports, so the engine's and the driver's tests need the `checkText` wrappers to keep counting it as not supported.
