# Diary: mutation testing of slice 15

The last step of slice 15, the scalar subquery in the `where` of a `select`, `update`, and `delete`: mutate the code that the slice added or changed in `internal/sql/stmt` and `internal/engine`, and end every mutant as killed, equivalent with its reason in `/internal/sql/mutation/equivalent.txt`, or killed by a new test. Slice 14's round is the model.

## Step 1: The selection and the first runs

**Author:** mutation-15 builder

### Prompt Context

**Verbatim prompt:** (excerpt from the lead's brief) "Run the mutation runner over the code that slice 15 added or changed in the three packages (use the same way of choosing the scope as slice 14 did; `git diff 2273d72..main -- internal/sql/stmt internal/engine '*.go'` shows what slice 15 touched; test files are not mutated). Every mutant ends as one of: killed; equivalent, with its reason recorded in `equivalent.txt` in the form the file uses; or killed by a new test that you add. None may stay unexplained. Where a surviving mutant shows code that is not needed, remove the code instead of recording it [...] Check the entries of `equivalent.txt` that slice 15 made stale [...] The runner does not run the root package's tests for engine mutants, so an engine promise needs an engine test." The brief also asks for economy: the week's usage budget is nearly spent.
**Interpretation:** Select every mutant of every declaration that `git diff 2273d72..main` touches in the non-test files of `stmt` and the engine, as slice 14 did; run each package on a copy of the tree under `/Volumes/990/s4ql/slice-15-mutation/`; classify every survivor.
**Inferred intent:** The same trust in the subquery as in the slices before it, at the lowest cost that gives it.

### What I did

- The scripts are in `/Volumes/990/s4ql/slice-15-mutation/scripts/`. `pick/main.go` (built as `pick.bin`) reads the saved output of `git diff -U0 2273d72..main` of the code files, marks every declaration that holds an added or changed line or the place of a removal, and prints the mutants of the tool's `-list` whose line is in a marked declaration. `run.sh` runs the tool on the copy `tree/` with `-run` set to an exact list of `file:line` per package, which the tool matches as well as keys, and `TMPDIR` on that disk.
- The root package is not in the selection: slice 15 changed only `conn_test.go` there.
- The files of the selection: `recognize.go` and `stmt.go` of `stmt`; `access.go`, `bugs.go`, `engine.go`, `operator.go`, `plan.go`, `subquery.go`, `telemetry.go`, and `tx.go` of the engine. 3,087 mutants: 687 in `stmt` and 2,400 in the engine, the counts that the runs report too, 355 of them in `buildSink`, 168 in `report.end`, and 123 in `Conn.writeIn`, which the slice changed in a few lines and which are mutated whole. `bugs.go` adds the planted bug `changedOneByOne`, with 29 mutants.
- Started two runs at a load of 11 on 10 cores: `stmt` with 2 workers, and the engine with 4, `-factor 5`, and `-first 'TestEngine_subquery|TestNewPlan'`.

### Why

The brief asks for the scope of slice 14, which was by whole declaration.

### What worked

- Matching `-run` by `file:line` instead of by key: the selection is by line anyway, so no key needs to be escaped.

### What didn't work

- A shell command that ran a program which itself ran `git -C ...`, and an `rsync` with `--exclude .git`, were refused: "this command is too complex to verify that it stays inside the worktree". The diff is saved by a plain `git diff` into a file now, and the copy is made by a plain `rsync` with `--exclude=/.git`.

### What I learned

- In a worktree `.git` is a file; the copy leaves it out, and the tool does not need it.

### What was tricky

- The copy of the tree also took `.env.test`, which I deleted from the copy; the tool reads only `internal`, `go.mod`, and `go.sum`.

### What warrants review

- The selection: `pick/main.go` and its output `sel.txt` in the scratch directory.

### Future work

- The survivors of the two runs.

## Step 2: The survivors of the pass, and the first of the engine

**Author:** mutation-15 builder

### Prompt Context

**Verbatim prompt:** (the brief of step 1) "Every mutant ends as one of: killed; equivalent, with its reason recorded in `equivalent.txt` in the form the file uses; or killed by a new test that you add."
**Interpretation:** Classify the 19 survivors of `stmt` and the engine's survivors so far, while the engine's run goes on, on its copy of the tree.
**Inferred intent:** No survivor left unexplained.

### What I did

- `stmt`: 687 mutants, 95 not compiled, 571 killed, 2 timed out, 19 survived, 4 of them in the list. Of the other 15: 9 are killed by new cases of `TestCheck` ("should take a subquery as deep as SQLite allows"), which pin the height of the select of a subquery without a WHERE (1), with a LIMIT (2), and with an ORDER BY against SQLite at 998 and 999 conditions of the statement's WHERE, the refusal of a subquery of 997 conditions at the subquery once SQLite has found the tables, and a compound select in a subquery of 999 conditions, which is refused at its UNION; 2 are equivalent (`max` is symmetric; the height of a value that is no subquery is not read); and 4 were in code that nothing needs, which is gone: `r.at() == rc.Bounds().Start` in `selectOf`, `r.isNext(sq.LParen)` in `subquery`, and `r.isNext(x.Op)` and `r.accept(x)` before the refusal of a subquery after a sign in `conditionValue`.
- The engine, from the first 965 results: `TestFilter` builds a subquery with a reading without an engine (`reading.inner`) and pins the internal error of a subquery that the statement does not have (`build.walk`); `TestChangeRows` pins the error of the read of a subquery of an update and a delete, which the sink computes when it is built (`build.bind`). The flag `subqueries.prepared` is gone: its only reader, the check of the width in `build.walk`, sees a width only in a select, since an update and a delete find the table of a subquery after the walk reaches it, and `subqueries.names` refuses a second look-up. `buildQuery` no longer guards `newSubqueries`, which gives nil for nil.
- The entry `build.ordered condition: f != nil => true #4` named a mutant that is killed now: slice 15 added two tests of `f != nil` before the filter of no conditions, whose entry is `#5` now.
- `scripts/emit/` (a copy of the tool's `generate.go` with a `main`) and `scripts/mut.sh` and `many.sh` run `go test -overlay` of the worktree against one mutant by its key, so each new test was checked against its mutants in seconds.

### Why

Each survivor needs a test, a reason, or the removal of its code.

### What worked

- Probing the pass with a throwaway test file to see what it gives for a deep compound subquery before writing the case.

### What didn't work

- The first version of the test of `build.bind` failed the read of the indexes: `f.indexesFails`. It did not kill `build.bind condition: err != nil => false #3`, because the statement's own access, with the subquery's value unset, read the indexes too and failed with the same error. A failing scan (`f.scanFails = 0`), which the statement does only when it runs, kills it.
- The first expectation of the test of `reading.inner` was wrong: `Expected "[40,4]", but got "[10,1]"`; the fake scans in the order of the key, not of insertion.
- A shell command with a here-doc of Python that edited a test file was refused as "too complex to verify that it stays inside the worktree"; the Edit tool did it.

### What I learned

- In a mutant that ignores an error of a subquery, the statement can fail with the same error later by itself, so a test of the error must fail the subquery in a way that the statement does not repeat.

### What was tricky

- Deciding that `prepared` is not needed: it holds because `subqueries.names` refuses to look a subquery up twice, so the width of a subquery of an update or a delete is 0 when the walk checks it.

### What warrants review

- The removal of `subqueries.prepared` in `/internal/engine/subquery.go` and the new comment at the check in `/internal/engine/operator.go`.

### Future work

- The rest of the engine's run.
