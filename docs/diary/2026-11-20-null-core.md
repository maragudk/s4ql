# Diary: `null` in the commit format and the storage core

Slice 6 of `/docs/roadmap.md` lets a column that is not the primary key take null. This task brings that to the commit format (`/proto/s4ql/v1/commit.proto`, `/internal/format`, `/internal/s4qlpb`) and the storage core (`/internal/core`), with the tests of the core, the model, the simulation, and a planted bug for null. The engine and the driver are other builders' tasks; the engine still creates only columns that do not take null. The branch is `null-core`, from `origin/main` at `4e42473`.

## Step 1: the field `nullable` and the refusals of NULL in the format

**Author:** builder (null-core)

### Prompt Context

**Verbatim prompt:** You build the commit format and storage core part of "Slice 6: `null`" in s4ql (`maragu.dev/s4ql`) [...] `message Column` gets `bool nullable = 3`: the column takes null. It is never true for a column of the primary key; the writer and the reader refuse that. It is named `nullable`, not `not_null`, so that the logs that exist, in which every column is `not null`, read correctly with the field absent. A null value in a row uses the format's existing null value. The writer and the reader refuse a null for a column of the primary key. Decide by reading the code whether the format's checks can also refuse a null in a row for a column that is not nullable (they can only if they know the table at that point); if they cannot, the core does it. The format version stays 0 (draft). Regenerate with `make generate`. [...]
**Interpretation:** add the field, refuse it on a primary-key column, refuse NULL where the format knows a value is of a key column, write the samples again with a nullable column, and say in the README which refusals the core keeps.
**Inferred intent:** a table's definition in the log says which columns take NULL, so that a replay and a later version know it, and no commit object can say that a key takes NULL.

### What I did

`/proto/s4ql/v1/commit.proto`: `bool nullable = 3` on `Column`, with a comment; `make generate` rewrote `/internal/s4qlpb/commit.pb.go`, and `make lint-proto` passes.

`/internal/format/check.go`: `checkCreateTable` refuses a primary key that holds a column with `nullable`, and `checkPrimaryKey` refuses a NULL in a key of a `DeleteRows`, both as malformed. The doc comment of `CommitReader` in `/internal/format/reader.go` lists both.

The checks cannot refuse a NULL in a row of an `UpsertRows`, neither for a column that does not take NULL nor for a key column: the batch names its table and its column positions, and the table may come from an earlier commit object, which the reader does not see. Each commit object stands alone. The core refuses both, in a write and at replay, in `table.checkValue`.

Tests: the reader and the writer refuse a key column with `nullable` and a NULL in a primary key (also one after a key without NULL in the same batch). The samples `commit-v0-first.bin` and `commit-v0-all.bin` now mark `users.age` and `kv.c` as nullable, the two columns whose rows already held NULL, and were written again with `go test ./internal/format -run TestCommitSamples -update`; the test that every field is held by some sample now sees `Column.nullable`. `FuzzCommitWriter` makes the columns outside the key nullable by the bits of a byte, and makes a NULL in a key the integer 0 (`fuzzInput.keyValue`). The README of the format has a point on `nullable` under "Keys and values", and the paragraph on the checks at replay counts three checks now. In `/docs/roadmap.md` the sentence of slice 6 on the commit format now says that it gets the field.

### Why

A NULL in a `PrimaryKey` is malformed in itself, since all its values are of key columns of a `without rowid` table, so the format refuses it where it can. The rest needs the table, which only the core has.

### What worked

The existing tables of refusals took the new cases with a line or a few each. A fuzz run of 20 seconds of `FuzzCommitWriter` passed.

### What didn't work

The test that refuses an unknown field in a column used field number 3, which is now `nullable`:

```

    reader_test.go:297: error is not newer version: nil
```

It uses 4 now.

### What I learned

The samples already held NULL in rows for columns that, by the new field, did not take it; the format never checked that, and cannot.

### What was tricky

Nothing beyond the choice of which refusals belong to the format: only those that one change shows by itself.

### What warrants review

- The README's new point, which records the decision of the lead and the split between the format and the core.

## Step 2: NULL in the core, the cache's layout, the model, the simulation, and `nullZero`

**Author:** builder (null-core)

### Prompt Context

**Verbatim prompt:** see step 1. [...] **Core** (`internal/core`): a table's definition carries which columns take null, from `CreateTable` through the cache to the commit object and the replay. `Tx.Upsert` and `Tx.Insert` take a null for a nullable column, and refuse it with `core.ErrInvalid` for any other column and for the key, before SQLite sees the row. [...] Decide how the cache's own table records that a column takes null (it must survive a restart and a replay, and a cache that an older version of the code made must still open and read right: every column of its tables is `not null`); record what you chose and why the cache's version stays or changes. [...] **A planted bug for null** in the core's simulation, found by the default run and by none of the runs without it [...]
**Interpretation:** carry `nullable` through `table`/`column`, the cache's declaration, `conn.load`, and `table.checkValue`; give every test that wrote NULL into a column a table that takes it; add NULL to the model, the shapes of the simulation, the random savepoints, the types and the too-big tests; plant a bug in the commit object.
**Inferred intent:** NULL goes exactly where a table allows it, everywhere a row goes, and every check of the core sees it.

### What I did

`/internal/core/cache.go`: `column` has `nullable`, `newTable` and `table.createTable` carry it (the latter sets the field only when it is true, so the message is the same as one written without it). `table.createSQL` declares a column that takes NULL `default null` and every other column outside the key `not null`. `conn.load` asks `pragma_table_info` for `notnull` and `dflt_value` too: a column takes NULL if its default is the text `null`; any other default, a default on a key column, or `not null` beside `default null` is `ErrCacheVersion`. `table.checkValue` refuses NULL in a column without `nullable` with "NULL in the column ... which does not take NULL". `cacheVersion` is 2, and `conn.upgrade`, called from `conn.setUp` before the version is checked, raises a cache of version 1 to 2 in a `begin immediate` transaction.

`/internal/core/tx.go`: `Tx.committed` takes the table, for the new planted bug `nullZero` (`/internal/core/bugs.go`), which writes each NULL of a row in the commit object as the zero value of its column's type (`zeroValue`); the doc comment of `Tx.Upsert` says what a row may hold.

Tests: `describe` marks a column that takes NULL with `?`, and `nullableTable` and the step `createWith` make such tables. Every test that wrote NULL into a column now makes that column nullable (`TestOpen`, `TestTx_Commit`, `TestTx_Commit_large`, the hand-written log of `TestReplay`), and the old cache of `TestOpen_cache` holds no NULL, since no engine before slice 6 wrote one. `TestOpen_cache` checks that a cache of version 1 is raised to 2, reads its columns as not taking NULL, refuses NULL in them, and takes a new table with a column that takes NULL across a restart and a replay. `TestDB_stop_cache` (the case of a table that another process adds) refuses three more tables: a default of 0, `not null default null`, and a key with `default null`. `TestReplay` refuses NULL in a column that does not take it, in a full and in a partial batch, NULL in the key of a table that the commit object creates, and, as malformed by the format, NULL in a deleted key and a key column with `nullable`. The new `TestTx_null` takes NULL in a column of every type that takes it and refuses it elsewhere, with `Upsert`, `Insert`, `Delete`, and `Get`. `TestTx_types` has a second column of every type that takes NULL, NULL in every other row of those, and a row of NULL only. `TestTx_tooBig` has two shapes with NULL. `TestTx_Savepoint_random` makes one shape in four nullable, upserts NULL there one time in three, and puts NULL into one refused upsert in four, with minimums of 50 and 14 (a quarter of 203 and 56). The model's strict replay refuses a value that does not fit its column (`fits`), and `cacheDump` reads `default null` with SQL of its own. The simulation's shapes have columns of every type that take NULL in five of eight shapes, `randomRow` gives NULL only there, and one upsert in ten puts NULL where a column takes none and must get `ErrInvalid`. The trace marks "upserts with NULL" and "refused upserts of NULL", with minimums of a quarter in every workload.

### Why

`default null` is the only part of a column's declaration that `pragma_table_info` shows and that a strict table leaves free; the flag `notnull` could not tell an old cache's columns, which all lack `not null` and do not take NULL, from columns that take NULL. The version changes because a version that reads 1 would silently misread a column declared `default null`; with 2 it refuses the cache.

### What worked

The planted bug `nullZero` was found in 179 of 200 seeds (`S4QL_SIM_SEEDS=200 go test -run 'TestSimulation_plantedBugs/should_find_a_commit_object_that_writes_a_NULL' -v ./internal/core`), by "with the changes" in all 179, "a read saw at commit" in 177, and "the cache of" in 124, and in none of 200 without it. The default run finds it four times in the first seeds. Every earlier minimum of `TestSimulation` and `TestTx_Savepoint_random` still held after the draws of the random numbers changed.

### What didn't work

The first full run of the package after the change to `table.checkValue` failed wherever a test or the simulation had put NULL into a column, since the core took NULL in any column outside the key before:

```
--- FAIL: TestOpen/should_serve_a_new_database,_keep_what_is_committed,_and_replay_it_into_an_empty_cache (0.00s)
    core_test.go:339: Expected nil error, but got "invalid: NULL in the column "v" of the table "t1", which does not take NULL" (type *fmt.wrapError)
free_test.go:32: run 0: upsert: invalid: NULL in the column "v \"w\"" of the table "Q\"T'1", which does not take NULL; ...
```

And before that, with the format alone, `TestReplay` "deletes with a key that is NULL" failed because the format now refuses that key before the core sees it; the case moved to the list of malformed commit objects:

```
replay_test.go:259: Expected "the log is broken" (type *errors.errorString), but got "the instance has stopped: commit object 927ae79c...: malformed: record 2.delete_rows.primary_keys[0].values[0] is NULL, which no primary-key column takes"
```

My first version of the old-cache test opened the cache again and then served a second instance while the first still held the lease, so the second waited for the lease to time out and the run looked hung; it now closes the first.

### What I learned

- `pragma_table_info` reports `notnull` as 1 for the key column of a `without rowid` table, declared or not, and the default as the text as written (`null` or `NULL`), with SQL NULL for no default.
- The trace line of a refused upsert of NULL first started with "upsert", so the markers of keys counted it as an upsert of a text key; it now starts with "NULL where a column takes none".

### What was tricky

Pinning new minimums after a change that moves the random draws of every seed: the earlier minimums are a quarter, so they held, but each had to be checked again rather than assumed.

### What warrants review

- `/internal/core/cache.go`: `conn.upgrade`, `conn.load`, `table.createSQL`, and `table.checkValue`.
- That a cache of version 1 holds no NULL in practice: the engine of slices 1 to 5 refused NULL, but the core did not, so a log written through the core alone (the tests, and the format's samples before this change) can hold one, and its replay now refuses it as a broken log.
- `Tx.Insert` runs `insert or ignore`, which skips a row that breaks a `not null` of the cache instead of failing; the core's own check comes first, so this matters only if that check is wrong.

### Future work

None from this step; the engine's part of slice 6 is another builder's.

## Step 3: what the review found, and the checks

**Interpretation:** run the code-review skill over the branch, judge each finding, and fix those that matter.
**Inferred intent:** hand in a branch that a reviewer finds nothing more in.

### What I did

`code-review high null-core` gave six findings. I fixed four:

- `conn.setUp` raised a cache of version 1 to 2 before it checked the position and the identity, so a cache refused as one of another database had been changed already. Now `conn.positionAt` checks a cache of version 1 as one of its version, the identity is checked, and only then does `conn.upgrade` run. `TestOpen_cache` opens the old cache with another identity first and checks that it stays at version 1.
- A cache of version 1 could hold NULL in a column outside the key, since the core took one then, and version 2 would read that column as not taking NULL. `conn.upgrade` now looks for NULL in every column that does not take it (`conn.checkNoNull`, one query per column, once per cache) and refuses such a cache with `ErrCacheVersion`, at version 1. A new subtest of `TestOpen_cache` shows it.
- `Tx.Insert` ran `insert or ignore`, which also skips a row that breaks `not null`, so the `not null` of the cache was no backstop there. `conn.insert` runs `insert ... on conflict do nothing returning 1` now, which skips only for the key. `TestTx_tooBig`'s insert case still finds the boundary exactly.
- `Tx.CreateTable` committed the caller's message, which can hold `nullable: false`, while the cache gives the field back only when it is true. It commits `table.createTable()` of the new table now, and a subtest of `TestTx_null` checks that the commit object and `Tx.Table` agree.

I left two: that `conn.load` does not require `not null` on the columns of a table of version 2 (a table carried over from version 1 lacks it, so the check could not be made, and the README says so), and that the roadmap's sentence on the commit format was changed before Markus confirmed the field (the lead asked for that sentence, and `docs/todo.md` marks the field for Markus to confirm).

Checks: `make test`, `make lint`, and `make check-browser` pass. The new and changed tests passed `-count=20`, also under `-race`. `go test -count=1 -v ./internal/core` took 60.9 s, against 57.0 s before the change; `TestTx_Savepoint_random` took 2.28 s against 2.32 s, `TestTx_types` 0.02 s as before, and `TestTx_tooBig` 0.05 s against 0.04 s.

### Why

The rule of the cache is that a cache that is refused is left as it is, and that the core never misreads a cache; the first two fixes keep both for a cache of version 1.

### What worked

Each fix was small, and its test failed on the code before it in the way the finding said.

### What didn't work

Nothing failed in this step.

### What I learned

SQLite's `on conflict do nothing` without a target applies only to uniqueness constraints, where `or ignore` applies to `not null` and `check` too.

### What was tricky

The order of the checks in `conn.setUp`: the identity query needs the column `database`, which a cache of version 0 lacks, so the check of the version and the position must still come first, for version 1 as for version 2.

## Step 4: the merge of `main`, and the race of two instances that upgrade one cache

**Author:** builder (null-core-fixed)

### Prompt Context

**Verbatim prompt:** "Merge `origin/main` into the branch ... With a merge commit. Known conflict: `internal/core/core_test.go` ... Keep the tests of both sides." and "Fix a bug that an independent review found: `conn.setUp` in `internal/core/cache.go` reads whether the cache is of version 1 (`count(... where version = 1)`) and then `positionAt(1)` reads the version again, each in its own autocommit read. If another instance upgrades the cache between the two reads, `positionAt(1)` finds version 2 and the open fails with `ErrCacheVersion` ... Fix it so that an instance that finds the cache already upgraded by another carries on as with any version 2 cache, and so that the decision \"upgrade or not\" is made on a version read inside the upgrade's own `begin immediate` transaction, not on an earlier read. Keep every refusal that exists."
**Interpretation:** bring the mutation tests of slice 4 into the branch, then make the upgrade from version 1 to 2 decide inside its own transaction, with a test that forces the order, a concurrent test, and a version 1 cache with a table of every type.
**Inferred intent:** a branch for pull request #77 that holds what `main` holds and opens a version 1 cache from many instances at once without a false refusal.

### What I did

The merge (commit `2aab1df`). The one conflict was the table of `TestDB_stop_cache` of tables that s4ql did not make: `main` had made it a map from the create to a part of the error message, and this branch had added three tables with defaults. I kept the map and gave the three their messages (`has the default "0"`, `has the default "null"` twice). `main`'s new step of `TestTx_types`, which upserts a row that existed and then deletes it, built a row of 6 values for tables that have 11 columns on this branch, and failed with `invalid: a row of 6 values for the table "t_int", which has 11 columns`; it now appends NULL for the five columns that take NULL. In `/internal/sql/mutation/equivalent.txt` the key `Tx.spoolTouched remove statement: row = tx.committed(row) =>` named no mutant any more (`TestEquivalent` said `no such mutant`); the line is `row = tx.committed(t, row)` now. I removed the line by hand and ran `TestSimulation_plantedBugs`: both `blobCut` and `nullZero` were still found, through the tables that a transaction creates, so the entry stays with the new key and a reason that names both bugs. The entry `Tx.committed condition: v.WhichKind() == s4qlpb.Value_Blob_case => true` still names a mutant, and stays equivalent because no test plants `blobCut` beside `nullZero`; its reason says so now. I added `table.checkValue remove statement: return nil => #4`, the `return nil` of a NULL that is taken, which is equivalent for the reason of `#2` and `#3`. I checked every other key of `internal/core` and `internal/format` against `-list -pkgs internal/core,internal/format`, and each names the same code as before.

The fix. `conn.setUp` reads the record of the cache, which is now a type `record` (version, position, identity), and checks it with `record.check`: version 1 or 2, a position that is a name, and the instance's identity. For version 1 it calls `conn.upgrade(identity)`, which takes `begin immediate`, reads the record again inside the transaction, checks it again, and then decides: version 2 by then means another instance upgraded it, and the transaction ends without a change; version 1 means `conn.checkNoNull` and the update. `positionAt` is gone; `conn.position` reads with `conn.head` (version and position, one statement) and refuses any version but 2. The review (below) found one more case, and `conn.upgrade` now also handles it: when `begin immediate` fails, it reads the version again, and opens a cache that is at version 2 by then without the lock.

The tests, all in `TestOpen_cache`, with the helpers `versionOne`, `newVersionOne`, and `versionOne.write` in `/internal/core/core_test.go`: the test of a real version 1 cache has a table of each of the five types now, with a row for each of the `edges` of its key's type, written with the statements of the version before (`insert or replace`, bound with `core.Bind`); after the upgrade and a restart it reads the same, and `cacheDump` of it equals `cacheDump` of a replay. A test-only hook, `Options.versionRead` (set with `Options.OnVersionRead` in `/internal/core/export_test.go`), runs after `conn.setUp` has read the version. Two tests use it to force the order: in one, another instance upgrades the cache in the hook, and in the other, it also holds the write lock afterwards, with a busy timeout of 1 ms. In the first, the hook also puts a NULL into the table `t1` after the other instance's upgrade, and the open must take it, since a cache of version 2 is not looked through again. A third makes the cache another version or another database, gives it a NULL, or deletes its record in the hook, and the open must refuse it with the message of that refusal and leave the version as the hook left it. One more test opens a version 2 cache while another connection holds its write lock, with a busy timeout of an hour, so that an open that waited for the lock would not end, and a version 1 cache in the same state, which must fail and keep version 1. One makes every write to the write-ahead log fail (`faultvfs`), so that the commit of the upgrade fails, and the cache must stay at version 1. The tests of a tampered cache in `TestOpen_cache` and `TestDB_stop_cache` now check the message of each refusal too. Last, 8 instances open one version 1 cache at once, for 20 rounds. Every open must succeed, and each instance in turn must read what the log holds.

### Why

The decision whether to upgrade has to be made on what the cache holds under the write lock, or a concurrent upgrade by another instance turns a good cache into a refused one whose message tells the operator to delete it.

### What worked

The hook made the race deterministic: the forced test failed on the code before the fix with exactly the reviewer's message, `it has version 2, and this version of s4ql reads version 2`, and passes after it. The test of the busy path failed with `open the cache: local I/O failure: sqlite: database is locked (code 5)` when I disabled the branch for "busy", and passes with it.

### What didn't work

- My first rewrite read `select version, head, database` in one statement. `TestOpen_identity`'s test of a cache of version 0 failed with it, because version 0 has no column `database`: the mutation tool reported `killed TestOpen_identity/should_refuse_a_cache_of_version_0,_which_records_no_identity,_and_leave_it_as_it_is: ... got "open the cache: local I/O failure: sq...` on its baseline. `conn.record` now reads the identity in a statement of its own, and only for version 1 or 2. Step 3 had noted this ordering, and I missed it.
- The first version of the five-type test hung until the timeout of 60 s: it served the replay "b" while "old" still held the lease. It closes "old" first now.
- A mutation run aborted with `internal/core/cache.go changed since its mutants were made`, because I edited the file while it ran.

### What I learned

The write lock is the only thing that orders two instances that open one cache, so every decision that leads to a write of `s4ql_cache` has to be read again after `begin immediate`. A read before it can only choose whether to try.

### What was tricky

The upgrade path takes the write lock, and an instance that wins the race can start writing at once. So an instance that loses the race can hit "busy" on a cache that no longer needs an upgrade. Reading the version again only inside the transaction does not help when the transaction cannot start.

Self-review. `code-review medium` gave three findings, and I fixed all three. The first was the busy case above. The second was the doc comment of `conn.record`, which claimed one snapshot outside a transaction too; it now says that the identity can come from a later state there, which no check cares about because no instance changes the identity. The third was that the concurrent test left instances open when it failed; a cleanup closes them now. Then I ran the mutation tool on the new and changed functions (`go run ./internal/sql/mutation -out <dir> -pkgs internal/core -run 'cache.go (conn.upgrade|conn.record|conn.head|conn.position |conn.setUp condition: r.version)'`). The first full run over them had 20 survivors of 151. Seven were my code's and are killed now. Two of them went away because the code became simpler: the busy branch no longer asks `classify`, and `conn.record` returns at once on an error. The tests above kill the other five. Of the rest, six are equivalent and are in `equivalent.txt` with their reasons: the rollbacks and forgets of `conn.upgrade` on an error, which the close of the connection by `Open` does anyway; the forget before the commit; the rollback after a commit that succeeded; and the `return err` after a failed begin, whose fall-through fails with the same busy. The last run had 8 survivors of 105, and one mutant still ran: `conn.setUp condition: r.version != cacheVersion => true`, which hangs on the busy timeout of an hour. I stopped the run there and checked it by hand: `panic: test timed out after 30s`. My loops that waited for the tool with `pgrep -f 'internal/sql/mutation -out'` matched their own command lines and never ended; I stopped them.

Checks: `make test`, `make lint`, and `make check-browser` pass. The tests of the open and of a tampered cache ran 50 times, and 50 times under `-race`, both at once.

### What warrants review

- `/internal/core/cache.go`: `conn.setUp`, `conn.upgrade`, `conn.record`, `conn.head`, `record.check`, and `conn.position`.
- `/internal/core/core_test.go`: the new subtests of `TestOpen_cache` and the helpers `versionOne`.
- `/internal/sql/mutation/equivalent.txt`: the three changed or added entries.

### Future work

- Opening a version 1 cache still needs the write lock for its upgrade, so an open can fail with busy if another instance holds the lock for longer than the busy timeout before the cache is upgraded. This was so before the fix as well.
- Two mutants of `conn.head` survive and are not equivalent: `condition: err != nil => false` and `remove statement: return record{}, err =>`. A failed read of `s4ql_cache` would then be refused as `it records 0 positions` (`ErrCacheVersion`, which tells the operator to delete the cache) instead of a local failure. Only a read fault in the right statement reaches it. `positionAt` had the same shape. It is left for the mutation testing of slice 6.
