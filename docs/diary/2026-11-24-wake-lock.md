# Diary: screen wake lock on the simulator page

The simulator page (`/site/simulator/`) asks the browser to keep the screen on while the simulation plays, with the Screen Wake Lock API, so that a phone does not dim during a run.

## Step 1: hold a screen wake lock while the page plays

**Author:** wake-lock builder (sub-agent)

### Prompt Context

**Verbatim prompt:** Can we ask the screen to stay on on mobile while the sim runs? (Markus, relayed by the lead; also: "It's better to use the design to make usage self-evident where possible. Minimize words.")
**Interpretation:** Request `navigator.wakeLock.request("screen")` while the page plays, release it when it does not, on every device that has the API, with no visible interface.
**Inferred intent:** A visitor who watches a run on a phone should not have the screen go dark in the middle of it.

### What I did
Added `keepAwake` in `/site/simulator/page.js`, called at the end of `setPlaying`, which is the one place where `playing` changes (Play, Pause, halt, end, and Reset all go through it). When the page plays and is visible and holds no lock and has no request on its way, it requests the lock. When it does not play, it releases the lock. The sentinel's `release` event clears the page's idea of the lock, so a lock that the browser took back is requested again. Listeners: `visibilitychange` (ask again when visible and playing), `pagehide` (release), and capture-phase `click` and `keydown` on the document (retry after a refused request, in the manner of `wake` in `/site/simulator/sound.js`). A missing `navigator.wakeLock`, a rejected request, or a synchronous throw is ignored. No words, button, or indicator.

### Why
One hook in `setPlaying` keeps the lock tied to the state that the page already has. A request that is on its way when the page pauses is released when it resolves.

### What worked
Checked in Chromium with playwright-cli against `make site-serve`'s server, with `navigator.wakeLock.request` wrapped by counters: one request per Play, released by Pause, taken again by the next Play, no errors. With a stub that plays the browser's part: a lock released by the browser while the page is hidden is not requested again until `visibilitychange` to visible; a refused request at Play is retried by the next click and not requested again by later clicks; Reset releases. With `navigator.wakeLock` undefined: the page plays and logs no error. `make site-check` prints `sitecheck: ok`; `go test -tags s4ql_browser -short ./internal/simulator/...` passes.

### What didn't work
My first counters showed two requests per Play. The cause was my script: it ran twice in one browser context, so `addInitScript` wrapped the request twice. With a fresh browser, one request. Headless Chromium does not hide a tab on `tab-select`, so the real hiding of a tab could not be driven; the stub stands in for it.

### What I learned
Chromium's real release on hidden is the browser's own behaviour; the page only has to listen to `release` and `visibilitychange`.

### What was tricky
A request can resolve after the page paused; the `then` handler checks `playing` and releases at once.

### What warrants review
`keepAwake` in `/site/simulator/page.js` and the listeners added in the setup next to the Play button's listener.

### Future work
