# To do

A working list of things that are agreed but not built, and of design questions that are still open. The agreed rules are in [spec.md](spec.md), and the SQL slices are in [roadmap.md](roadmap.md).

Each item is marked agreed or open. An agreed item carries the details that a builder needs who was not in the conversation. When an item is built, it is deleted from this list, and its reasoning moves next to the code as tests and doc comments. The code is then the source of truth for how it was done.

- **Agreed on 2026-11-16, partly built: the pass after the parser.** The half that rejects is built for slice 1, in `internal/sql/stmt`: it rejects what the roadmap does not list, from the tree of `internal/sql/parser`, and gives a typed statement for the rest. Not built: the errors that SQLite's grammar actions raise while they parse, such as `unknown table option`, `duplicate column name`, or `ORDER BY clause should come after UNION not before`. The parser accepts such statements, and the list of those errors, with where SQLite raises each, is in `internal/sql/parser/README.md`. Slice 1 does not need them. None can occur in a statement of slice 1, so every statement that has one is "not supported"; the README of `internal/sql/stmt` gives the reason for each. A later slice needs them as soon as it supports a form in which one can occur. One gap is known until then: where an action's error comes before a syntax error in the same statement, SQLite gives the action's error, and the pass gives the parser's syntax error. The oracle does not say on such texts, so no test compares them. For the builder of the action errors:
  - When a statement has two faults, SQLite reports the one it meets first, and of the messages raised while one token is handled, the last; an action runs when the token after its rule arrives. On 308 of the corpus's statements SQLite does not say whether they parse, because an action stopped it early: those are the test cases for these errors.
  - A keyword read as a name keeps the kind of the keyword in the tree. Where SQLite reads a keyword as a name is decided by Lemon's tables, not by `parse.y` alone: GENERATED after a column's name or type is a word of the type, so `a int generated always as (1)` has the type `int generated always`.
  - Decided by the lead on 2026-11-18 for the pass of slice 1, which a builder is building; each can be changed later, and when the pass is merged its README holds them:
    - The pass gives a supported statement to the engine in a small typed form that it builds only from what it has recognized, and the engine never reads the raw tree to decide what to do. So no second place has to agree on what is supported.
    - A statement is supported only if every token that the parser read for it is one that the supported form expects in that place. When in doubt, a form is not supported.
    - One statement for each text. After the first statement only spaces, comments, and semicolons may follow; a second statement makes the text "not supported" for now.
    - A text with no statement at all (empty, or only spaces, comments, and semicolons) is an outcome of its own. The driver answers it with "not supported".
    - The errors that SQLite's grammar actions raise, such as `unknown table option`, are not reproduced in slice 1: such statements are "not supported". They come when a supported shape can reach one.
- **Agreed on 2026-11-16, partly built: how the parser is tested.** Four checks, with SQLite as the judge wherever it can be. The first three are built: agreement with `sqlite3_prepare_v2`, the ownership of every token, and the shape of the tree, in `internal/sql/shapetest`, which writes the tree with every operation in parentheses and requires the same `EXPLAIN` output and the same values from SQLite.
  - For what the engine supports, rows and errors are compared with SQLite's, when the engine exists. `shapetest.Check` and `shapetest.Test` are there for the engine's builders, and `shapetest.Pairs` and `shapetest.Triples` give expressions that combine every pair of operator forms.
  - Open, a possible later check: the mutation tester, `internal/sql/mutation`, changes the tokenizer, the tree, the parser, and the pass after it, but not the judges, `internal/sql/oracle` and `internal/sql/parsetest`. A fault in a judge that makes it say less, such as a `NotSaid` too many, shows only in the pinned counts of the tests, not in a list of surviving mutants.
  - The shape check cannot see a few things, which its README lists: groupings that SQLite treats the same, such as `x NOT BETWEEN a AND b` against `NOT (x BETWEEN a AND b)`, and what SQLite does not record of a table, such as the names of constraints other than CHECK. Where a wrong tree prints the same tokens, as at the boundary between a column's type and its constraints, the check compares what the tree declares with what SQLite records of the table. REGEXP, MATCH, and GLOB with ESCAPE are compared through stub functions that the binding gives a test's connection.
- **In reserve, not planned: reading SQLite's own tree out of its memory.** It works for the statements that build a tree, through the parse-only mode that `ALTER TABLE ... RENAME` uses and a walker in C over SQLite's private structs. It is not built, because it compares against SQLite's internal form through a function of ours that would mirror about 30 of its rewrites, and the checks above cover what it would catch, except a fault in the parser and one in the printer that cancel each other, and the gaps of the shape check named above. If those gaps come to matter, this closes them. The routes and their costs are in [research/sqlite-parse-tree.md](research/sqlite-parse-tree.md).
- **Decided on 2026-11-18, built: a syntax error never depends on the database.** The spec: "Text with a syntax error gets the error that SQLite gives for it on an empty database." So `stmt.Check` alone decides a syntax error, and the engine gives it without a transaction: never an error of the lease, the stop of the instance, or the context. SQLite differs where a grammar action looks the schema up while it parses. For `CREATE TABLE` and `CREATE VIRTUAL TABLE` with the name of a table that exists, SQLite gives `table %s already exists` before a later syntax error: with `t1`, `create table t1 (v1 int primary key) strict without rowid` gives `table t1 already exists`, and on an empty database `near "without": syntax error`, which is what s4ql gives. This is the one difference from SQLite that the tests accept, through `stmttest.StartedTable`. The README of `internal/sql/stmt` has the details, under "Known gaps". The reviewer verified sibling cases, where SQLite gives another error than the syntax error because of what is in the database or because of an earlier grammar action. All have the result code 1 and the extended code 1 on both sides; only the message differs:
  - `alter table nosuch add v1 int primary key x y` gives `no such table: nosuch`, and `duplicate column name: v1` when the table and the column exist.
  - `create table t2 (v1 int, v1 int) x y` gives `duplicate column name: v1`.
  - Others seen: `unknown database x`, `object name reserved for internal use`, `temporary table name must be unqualified`, `table "t2" has more than one primary key`, and for `CREATE TRIGGER` `no such table: main.X` and `cannot create INSTEAD OF trigger on table: X`.
  - **Still a gap against the spec's rule:** every one of these. On an empty database SQLite gives `no such table: nosuch` for the ALTER TABLE, `duplicate column name`, `unknown database`, `object name reserved for internal use`, `temporary table name must be unqualified`, and `has more than one primary key` as above, and `no such table: main.X` for both triggers, where s4ql gives the syntax error. Measured with the sqlite3 shell of 3.54.1. The ALTER TABLE's `duplicate column name` and the INSTEAD OF trigger's `cannot create` depend on the database, so the rule does not ask for them, but the empty database's answer for those texts is not the syntax error either. They close with the errors of the grammar actions, under the first item of this section.

## The public package and the driver

Status: built for slice 1 on 2026-11-19, in package `s4ql` at the root of the module: the options, the errors, `Open`, and `Register`, with the `database/sql` driver behind them in types that are not exported. The driver runs slices 2 to 7 too: see [Parameters](#parameters), [Transactions](#transactions), and, for the types of slice 4, the several columns of slice 5, the NULL of slice 6, and the WHERE of slice 7, [The SQL front end](#the-sql-front-end). What an application gets is in the package's documentation, and how it behaves in its tests. This item holds what Markus agreed, the decisions below his level, which he and the lead can change, and what is open or not built.

- **Agreed with Markus on 2026-11-18, built.** `s4ql.Open(ctx, options)` returns a plain `*sql.DB` at once and fails only on local problems; `db.PingContext(ctx)` waits until the instance serves. `s4ql.Register` is for code that needs `sql.Open` by name, and nothing registers a driver by itself. A stopped instance answers every statement and `Ping` with an error that matches `s4ql.ErrStopped` and carries the cause. `db.Close()` releases the lease within a timeout from the options. A statement is bounded by its context, and so is its commit. No error is or wraps `driver.ErrBadConn`, because `database/sql` runs a statement again after it. "Not supported" matches `s4ql.ErrNotSupported`, starts with `s4ql: not supported: `, and carries no result code.
- **Decided by the lead on 2026-11-19, built:**
  - `Register(name string, options Options)`. The driver is a `driver.DriverContext`, so each `sql.Open(name, "")` opens one instance, as `Open` does, and fails on the same local problems. A data source name that is not empty is an error. A name that is registered twice panics, as `sql.Register` does.
  - The driver never runs under the simulation's scheduler, because `database/sql` starts goroutines of its own. `internal/simlint` has a list of exceptions for one package and one identifier each, and the root package has two: `host.New`, and `context.Background`, which it needs because `database/sql/driver` gives no context to `OpenConnector`, to the `Close` of a connector, and to the `Exec` and `Query` of a statement. Every other rule holds for the driver.
  - The lead also decided that the driver bridges the engine's `Rows.All` to `driver.Rows.Next` with `iter.Pull`. **The builder did not keep that, for the lead to confirm:** the Go runtime ends the process with `fatal error: coro: OS thread locking must match locking at coroutine creation` when a coroutine is resumed from a goroutine whose lock to an operating system thread differs from its creator's, and `database/sql` closes rows from a goroutine of its own when the context of a query ends. A goroutine under `runtime.LockOSThread` that read one row and whose context then ended killed the process. The loop over the rows runs in a task of the host, which hands over one row at a time through two semaphores of the host; `TestRows` has the case. It costs two switches of goroutines for each row. A pull-style cursor in the engine would need neither.
  - A text with no statement is "not supported": `s4ql: not supported: a text that holds no statement`.
  - Parameters are those of slice 2 of the [roadmap](roadmap.md): a plain `?` as a value of an insert. Since slice 4 its argument has the type of its column, since slice 5 an insert can have several, and since slice 7 a select has them as the values of its conditions. See [Parameters](#parameters) for the decisions of detail. Transactions are those of slice 3; see [Transactions](#transactions) for the decisions of detail.
  - `ColumnTypeDatabaseTypeName` is the declared type as SQLite reports it: `INT`, `INTEGER`, `REAL`, `TEXT`, or `BLOB`.
  - SQLite's errors are a `*s4ql.Error` with `Code`, `ExtendedCode`, and `Message`, whose `Error()` is SQLite's message. The offset of the error is not exposed.
  - The options are typed values, and there is no connection string. The lease durations and the timeouts of the core are not exposed.
  - The driver logs through the `slog` logger of the options, which the core and the engine get too. It logs what it decides itself: `open`, `close`, and `stop_seen`, the first statement that it answers with a stop. The engine logs each statement.
- **Decided by the builder on 2026-11-19, for the lead to confirm:**
  - The whole driver is in the root package. The public error type must be defined where it is documented, and an internal package that returned it would have to import the root package, which imports it. The tests are in package `s4ql_test` and open a database on a store and a host of their own through `export_test.go`, so they use the errors by their public names only.
  - Five sentinels: `ErrNotSupported`, `ErrNotServing` for "no valid lease", `ErrOutcomeUnknown`, `ErrStopped`, and `ErrTooLarge`. An error matches at most one. Slice 1 had the first four, and a commit object that is too large had no public name then, with the note that a slice that makes "too large" reachable should give it one, since the spec promises an error that says so. Slice 3 made it reachable with transactions, and `ErrTooLarge` is public since then; see [Transactions](#transactions). Nothing else has a public name: a cache that is busy, an internal error, and an error of a context that ended are errors whose message starts with `s4ql: `, and the cause of a stop is in the message of the error that matches `ErrStopped`.
  - `db.Prepare` checks the text with `stmt.Check`, so SQLite's syntax error and "not supported" come when the statement is prepared, also on an instance that does not serve. The tables are looked up when the statement runs. The engine is not changed.
  - What the text alone decides does not depend on the instance: a syntax error and "not supported" give the same error on a stopped instance, and not `ErrStopped`. This narrows the agreed "every operation" to every statement that reaches the instance, and every ping. Since slice 3 `BeginTx` reaches the instance, and gives `ErrStopped` on a stopped one. What its options alone decide does not depend on the instance either: an isolation level that is not supported gives "not supported" on a stopped instance too.
  - A statement that is no query and is run with `Query` gives rows that hold nothing and never fail, so a committed insert is never answered with an error by its rows.
  - `s3store.Options` has `AccessKeyID` and `SecretAccessKey`, which the builder added for the public options to mirror; both empty means the SDK's default chain. A session token and `RootCAs` are not in the public options.
  - The cache is the file `cache.db` in `Options.CacheDir`, which is created with the mode 0700 if it is missing.
  - `Options.CloseTimeout` is 10 seconds by default. The core gives half of it to the release of the lease, so closing an instance whose store cannot be reached takes 5 seconds and fails.
  - `db.Close()` closes the rows that the application left open, before it closes the instance. `database/sql` does not close them, and a loop over the rows of the core that waits between two rows is a call that uses the cache, which the close of the instance waits for until its timeout, and then fails. Their next row is the error of an instance that was closed.
  - A ping whose context ends gives the error of the context only, also on a spare.
  - `core.Options.VFS` is part of the core, and not only of its tests, so that the tests of the driver can make the cache fail through `internal/sqlite/faultvfs`. Nothing but tests uses it.

A NULL scans into a `sql.Null*` value, a pointer, and an `any`. A scan of NULL into a plain `int64` or `string` gives the error of `database/sql`, such as `converting NULL to string is unsupported`, and the driver reports nothing itself.
  - A panic in the loop over the rows of a query, which runs in a task of the host, is recovered there. A panic in a turn that `Next` gave the task is raised again on the goroutine that calls `Next`, after the rows are closed; the engine has ended the read transaction by then, and a later `Next` gives `s4ql: internal error: the query panicked`. A panic in a turn that a close gave the task, at the end of the loop, is not raised, because `database/sql` closes rows also from a goroutine of its own when the context of their query ends, where a panic would end the process: `Rows.Close` gives `s4ql: internal error: the query panicked: ` and the value, and the close of the database drops it and goes on. The driver logs each such panic as the event `panic` at Error, with the stack where it came, because a panic that is raised again has the stack of `Next`.

The close goes on with the other open rows and the close of the instance, so the lease is released and the cache is closed, and `db.Close()` gives `s4ql: internal error: the query panicked: ` and the value. If the close of the instance fails too, `db.Close()` gives that error, and the panic is only in the log. The lead decided this on 2026-11-19. A panic in the close of rows that `db.Close()` left to a call of their connection, because the call held the connection, is raised on the goroutine of that call, after the connection is freed.
- **Agreed with Markus on 2026-11-19, built: each connection of the pool has a reader of its own, so the pool sets how many reads run at once.** The spec says: "The number of connections in the database pool sets how many reads run at once." Before, the core had a fixed pool of read connections, `core.Options.Readers`, 4 by default, and a fifth concurrent query waited, so `db.SetMaxOpenConns` could lower the number of reads at once and could not raise it above 4. Markus agreed that the code follows the spec's sentence. The details, decided by the lead and the builder on 2026-11-19:
  - A connection of the driver owns one connection of the engine, an `*engine.Conn`, which owns one reader of the core, a `*core.Reader`: one read connection to the cache. The reader is opened for the first statement of the connection that reads, so a connection that only writes has none, and it is closed when `database/sql` closes the connection. So `SetMaxOpenConns`, `SetMaxIdleConns`, `SetConnMaxIdleTime`, and `SetConnMaxLifetime` govern the readers. A reader is two open files, the cache and its write-ahead log. The close of a reader gives back the descriptor of the write-ahead log, and not that of the cache: SQLite's unix VFS keeps the descriptor of a database file while another connection of the process holds a lock on that file, which the write connection always does, and reuses it for the next connection that opens the file. So the descriptors of the cache stay at the most readers that were open at once, plus the write connection, until the instance closes. Measured with `lsof` on 2026-11-19, in the diary of the follow-ups of the reader of each connection: 50 queries open gave 51 descriptors of the cache and 51 of the write-ahead log; after the pool had closed every connection, 51 and 1; 20 queries open after that, 51 and 21; after `db.Close()`, 0 and 0. Found by the review of pull request #48.
  - `core.Options.Readers` is gone, with `core.DB.Read` and the core's pool of read connections. The production wiring passes `core.Options{}`, and nothing sets a number of readers.
  - **A change of behaviour: a statement that reads on a `sql.Conn` whose rows of an earlier query are open is refused at once.** Its error matches `s4ql.ErrNotSupported`: `s4ql: not supported: a statement that reads on a connection whose rows of an earlier query are open`. A write on such a connection runs. Before, two queries at once on one `sql.Conn` worked, each on a reader of the core's pool. The test "should run several queries at once on one connection" in `rows_test.go` is replaced by one for the refusal.
  - The statement is refused and does not wait, because `database/sql` holds the mutex of a connection during every call of the driver on it, also during `Rows.Close` and `Rows.Next`. A second query that waited inside the driver for the rows of the first would hold that mutex, so nothing could close or read those rows, and the wait could end only with its context.
  - A failure to open a reader is treated as every error of the cache is while the instance runs: a local I/O failure stops the instance, as the spec says. That includes SQLite's `CANTOPEN`, which a process without a free file descriptor gets. The first read of a new connection opens the write-ahead log too, and a failure there already stopped the instance before this change, so an open that failed without a stop would make the outcome depend on which of the two files met the limit.
  - `TestReaders` in `conn_test.go` shows 20 queries at once on 20 connections, the reader opened at the first read and closed when the pool closes the connection, and no file left open after `db.Close()` with rows open on 12 connections. `TestStop` shows the stop when the cache cannot be opened for a reader, and `TestRows` the bound of `SetMaxOpenConns`. The tests count the open files through `faultvfs.VFS.OpenFiles()`, because a test file of the root package cannot see the core's fields. It counts the files that SQLite opens and closes through the VFS, not the descriptors of the process, which the unix VFS under it keeps as said above. `SetConnMaxIdleTime` and `SetConnMaxLifetime` have no test of their own, because one would depend on time; they close a connection through the same `Close` of the driver's connection.
- **Agreed with Markus on 2026-11-19, built: `s4ql.Open` bounds the pool from the process's limit of file descriptors, so that the readers use at most half of it.** With a reader on each connection and no bound on the pool, a burst of queries could use up the file descriptors of the process, and the reader that could not be opened stopped the instance for good: an independent review saw the 29th open query fail with `s4ql: the instance has stopped: local I/O failure: open a reader: sqlite: unable to open database file (code 14)` under a limit of 64 descriptors. It also measured that SQLite's unix VFS keeps the descriptor of the cache of a closed reader until the instance closes, and gives it to the next reader that opens, so the descriptors stay at the most readers that were open at once. The details, decided by the lead and the builder on 2026-11-19:
  - The bound is the soft limit of open files, `RLIMIT_NOFILE`, as `Open` reads it, divided by four, because a reader holds up to two descriptors and the readers get half; at least 1, at most the largest `int`. `Open` sets it with `SetMaxOpenConns`, and the application can change it so. The pure function `maxOpenConns` in `s4ql.go` has the arithmetic, and `fileLimit` reads the limit: through `syscall.Getrlimit` in `filelimit_unix.go`, for `//go:build unix`, and none in `filelimit_other.go`, for `!unix`, such as Windows, js, and wasip1. A limit that is unlimited or cannot be read is none, and then the pool has no bound, as `database/sql` gives none by default.
  - Go raises the soft limit to the hard limit when a process starts, on Darwin to `kern.maxfilesperproc`, so the soft limit that `Open` reads is mostly the hard limit. On the builder's Mac it is 61440, a bound of 15360; in a Linux container of `golang:1.27` with Docker's default it is 1048576, a bound of 262144.
  - `Register` cannot set it, because `database/sql` makes the `*sql.DB` of `sql.Open`, and the driver never sees it; there is no second mechanism in the connector. Its documentation says that the application sets `SetMaxOpenConns` itself, and why.
  - The event `open` of the driver has the bound as `pool.max_open_conns`, 0 for none, as `DBStats.MaxOpenConnections` has it; 0 for each instance of `Register`.
  - A failure to open a reader still stops the instance, and there is no public option.
  - **For the lead to confirm: the bound is for each instance.** Each `Open` reads the limit and sets a quarter of it, without counting the instances that are open already, so two instances in one process can use every descriptor through their readers. The documentation of `Open` says so, and that an application that opens several lowers the bound of each. A budget that the instances of a process share would be a second mechanism, which the brief ruled out for `Register`. The limit is read at `Open`, and a later change of it is not seen.
  - A limit that reads as unlimited gives no bound, also on a system whose kernel has a cap of its own for each process, such as `kern.maxfilesperproc` on FreeBSD, where Go raises the soft limit to an unlimited hard limit. A reader whose read needs a temporary file of SQLite would hold a third descriptor; the builder did not check whether a read of the engine can need one.
  - The tests do not lower the limit of the test process, because other tests in the process would be hit, so the review's scenario is not a test. `TestMaxOpenConns` has the table, `TestFileLimit` compares `fileLimit` with `syscall.Getrlimit`, `TestOpen` and `TestOpen_s3` show the bound of `Open` and that `SetMaxOpenConns` changes it, `TestRegister` and `TestOpen_s3` the pool without a bound of `Register`, and `TestRows` already shows that a further statement waits for a connection until its context ends.
- **Agreed with Markus on 2026-11-19, built: a cache records the database that it belongs to, and an instance refuses a cache of another database.** Before, two instances of two databases that started on one empty cache directory both served, and each read the tables that the other wrote. The details, decided by the lead and the builder:
  - The identity of a database is the endpoint, the bucket, and the prefix as the public options give them, written as `s3://bucket/prefix`, with ` at ` and the endpoint after it if the options give one. The bucket and each segment of the prefix are escaped with `url.PathEscape`, so that two databases never give one identity. Another text for the same store, also an empty endpoint in place of the URL that the environment gives, is another database to the cache; a change of the environment is not seen. The region, the credentials, and `PathStyle` are not part of it.
  - The public package hands the identity to the core as `core.Options.Identity`, which the core only compares. The core's tests, the engine's, and the simulator open with the empty identity.
  - The column `database` of `s4ql_cache` holds it, and the version of the layout of the cache is 1. A cache of version 0 is refused with `core.ErrCacheVersion`, as any other version, and not migrated.
  - `core.Open` refuses a cache that records another identity with `core.ErrCacheDatabase`, not under `ErrLocal`, so the public `Open` fails with `s4ql: open the cache: the cache belongs to another database: it records the database "…", and this instance opens the database "…"; open each database with a cache of its own, or delete the cache, with its files -wal and -shm, if the database has moved`. It has no public sentinel. The event `open` of the driver has the attribute `db.identity`; a refused open logs nothing, as any open that fails, and the error carries it.
  - A cache that has its table `s4ql_cache` is only read at the open, so a spare of the same database does not wait for the write transaction of the instance that serves. A new cache gets the table and its row in a `begin immediate` transaction that looks again whether the table is there, so of two instances that open one new cache at once, exactly one makes it, and the other reads its record. The change of a new cache to the journal mode wal is retried after "busy", because SQLite does not wait for that lock: the doc comment of `conn.wal` says why. On `main` before, two instances of one database that opened one new cache at once could fail `Open` with "busy".
  - `TestOpen_identity` in `internal/core` and `TestOpen_cacheDir` in the root package have the cases, also 50 and 20 rounds of the race.
- **Open: a `*sql.Rows` that is neither read to its end nor closed holds one of the reads** until its context ends or the database is closed. The package's documentation says so.
- **To look at again, now that transactions are built: a statement on a pinned connection whose rows are still open is refused as "not supported".** A connection runs one read at a time, and the second query cannot wait for the first, because `database/sql` holds the connection's mutex during a call of the driver, so nothing could close or read the first rows meanwhile. A `sql.Conn` pins a connection, and since slice 3 a `sql.Tx` pins one too. On a `sql.Conn` without a transaction, a statement that reads is refused, and a write runs. In a transaction, every statement is refused while rows of the transaction are open, also a write, where SQLite runs it. Its message says to close the rows first; see [Transactions](#transactions). A query or a write inside the loop over the rows of another query is common use of SQLite, which this refuses. It also meets an application that cancels a query and goes on without `Rows.Close`, because `database/sql` closes such rows from a goroutine of its own some time after: the review of pull request #48 measured that a query on the same `sql.Conn` right after the cancel of the context of the one before it, without `Rows.Close`, was refused 1928 of 2000 times. The package's documentation says that only `Rows.Close` makes the next statement sure to find them closed.
- **Not built: the first phase of the close of the database is not bounded by `Options.CloseTimeout`.** `db.Close()` first closes the rows that are left open, and the close of rows waits for a `Next` that runs on them. In slice 1 a row comes at once, so that wait is short. It becomes a fault when an operator can run long between two rows, such as a sort or an aggregate over a large table: the close then waits for it without a bound. The fix is a context for the engine, which the connector cancels when it closes.
- **If an application ever has to learn of a stop before its next query,** methods on the connector can carry that, without breaking anything.
- **Decided by the builder of the differential test on 2026-11-19, for the lead to confirm:**

  - The oracle runs only the first statement of a text, up to its semicolon. mattn runs every statement of a text, also one that is only a comment, and gives the result of the last, so `insert into t1 (v1) values (1); -- c` affects 0 rows in mattn, and 1 in SQLite's `sqlite3_changes`. s4ql does not support a second statement, so the first is all that it runs.
  - SQLite gives `no such table`, `already exists`, and `has no column named` when it prepares the text, and s4ql when the statement runs, because `db.Prepare` checks only the text. Since slice 5 that holds also for `no such column`, the two errors of the number of values of an insert, `duplicate column name`, and `too many columns on`. The test compares the error and excuses the step that fails, by exact count.
  - Of `ColumnTypes`, only the name and `DatabaseTypeName` are compared. s4ql reports nothing else, and mattn's `ScanType` and `Nullable` are its own choices: `sql.NullInt64`, and nullable for a key, which SQLite does not say.

## Parameters

Status: built for slice 2 of the [roadmap](roadmap.md) on 2026-11-19: the plain `?` in `internal/sql/stmt`, the arguments in `internal/engine`, and their conversion in the driver. What slice 2 includes and rejects is in the roadmap. The decisions of detail below are the builder's, for the lead to confirm.

- **The error of another number of arguments** than the statement has parameters is `s4ql: wrong number of arguments: 2 for a statement with 1 parameter`, with "parameters" for any number but 1. It matches `engine.ErrArguments`, and in the public package none of s4ql's sentinels: there is no public sentinel for it, because the brief asked for an ordinary error, and a public sentinel is API.
- **The order of the checks:** the text, as `stmt.Check` judges it; then the number of arguments; then each argument in order, its name before its type. So `select * from t1` with the argument `"x"` gives the error of the number, not of the type. All of it comes before the instance, so a stopped instance and a context that has ended give these errors too.
- **`NumInput` of a prepared statement is -1.** With any other number, `database/sql` would refuse the call itself with `sql: expected 1 arguments, got 2`, which does not start with `s4ql: `, before the driver sees it. So the driver counts, with the same error for a direct call and a prepared one.
- **`CheckNamedValue` converts as `database/sql` converts for a driver without it,** with `driver.DefaultParameterConverter`: every integer type and every type whose kind is an integer become an `int64`, a `driver.Valuer` gives its value, and a pointer what it points to. It never fails, because `database/sql` gives its error before the driver has judged the text. A value that the conversion refuses is kept with the conversion's error, and comes after the text as `s4ql: not supported: argument 1 of type T, which database/sql cannot convert`, with that error as its cause and not in its message. So the error of a `driver.Valuer` matches with `errors.Is` what the application's `Value` gave, and its text, which can hold a value, is not in the message. Whether the error of an application's `Valuer` should be "not supported" at all is for the lead to decide.
- **An unsigned integer above the largest `int64` is refused** as `s4ql: not supported: argument 1 of type uint, whose value does not fit a signed 64-bit integer`, for every unsigned type and a pointer to one. `driver.DefaultParameterConverter` refuses such a `uint64`, but turns a `uint` or a named type of kind `uint` into a negative `int64`: `uint(1<<63)` would be inserted as `-9223372036854775808`. That is how `database/sql` converts for every driver without `CheckNamedValue`; s4ql rejects it rather than reinterpret it. Found by the test of the refused types.
- **The message of an argument of a type that no column holds** is `s4ql: not supported: argument 1 of type bool`, with the type after the conversion: a named type of kind `bool` is `bool`. Until slice 6, a `sql.NullInt64` that is not valid, a nil pointer, and nil were `argument 1 of type nil`. They are NULL now, and that message is gone; a nil `[]byte` stays `argument 1 of type []byte, which is nil`. The decisions of slice 6 under [The SQL front end](#the-sql-front-end) list every kind of nil. Since slice 4 a `float64` (and a `float32`), a `string`, and a `[]byte` that is not nil are values; see the decisions of slice 4 in the engine under [The SQL front end](#the-sql-front-end). A named argument is `s4ql: not supported: the named argument "v"`; `database/sql` itself refuses a name that does not start with a letter, before the driver. No message holds a value.
- **The names of "not supported" in the pass:** `numbered parameter` for `?NNN`, `named parameter` for `:name`, `@name`, `$name`, and `#name`, and `parameter after a sign` for `-?`. `?0` and `?32767` are `numbered parameter` too, where SQLite gives `variable number must be between ?1 and ?32766`; that error of a grammar action is not reproduced, as none of slice 1 is. `#1` and `(? ?)` are syntax errors, which the pass gives as SQLite gives them. A parameter in any other place gets the name of what holds it, such as `WHERE clause`.
- **The engine refuses an argument that no column holds,** such as a value of no kind, with `s4ql: not supported: argument 1, which has no value`, which matches `stmt.ErrNotSupported`, and since slice 4 a value of another type than its column after the names. Since slice 6 it takes NULL, which is a value. `engine.Check(src, n)` gives the errors of the text and of the number without the database and without an event, for the driver's path where an argument cannot be converted; on the path where every argument can, the text is parsed once.
- **The event of a statement** has the outcome `wrong_arguments`, at Debug, for the error of the number. No value of an argument is in any event, of the engine or of the core. A statement that the driver refuses for an argument that it cannot convert, a named one or one of another type, logs no event: the driver refuses it through `engine.Check`, which logs nothing, as a text refused by `Prepare` logs nothing. The same statement with the wrong number of arguments and an integer logs one, because it reaches the engine.
- **The plan prints a parameter as `?1`,** by its number.
- **The tests read SQLite's count of parameters** as the largest index that `sqlite3_bind_int64` takes on the prepared statement, because the binding has no call for `sqlite3_bind_parameter_count`, and a change to the binding would need a run under the sanitizer.
- **The differential tests of the engine and of the driver** check s4ql's refusals of arguments against s4ql's rule, and do not compare them with SQLite: SQLite binds NULL to a missing argument and binds every type, `database/sql` refuses an argument too many for mattn with an error of its own, and mattn takes a name. A refusal is the error of the number, with the message that `engine.Check` gives, or the "not supported" of the first argument that s4ql does not support, with its exact message; each run of a prepared statement is checked. Every other outcome is compared with SQLite: the error of a text, which SQLite gives before it binds and which runs there without the arguments, and the outcome of a statement that s4ql ran, which must have had an argument that s4ql supports for each parameter, and which runs there with the same arguments. The tests pin how many calls each kind of refusal lets through.
- **The generator of the tests, `stmttest.Sequence`, gives a call with its arguments.** One value in three of an insert is a `?` with the value as its argument: an `int64`, a `float64`, a `string`, a `[]byte`, or nil for NULL. The arguments of one call in four of a statement with a parameter, and of one in twenty of one without, are changed to a case around them: one fewer, one more, one that no column holds (one of `stmttest.Unsupported`: a bool, a `time.Time`, a `uint64` above the largest `int64`, a real that is not a number or is infinite, text that holds NUL or is not valid UTF-8, or a nil `[]byte`), a named one, or a value of another Go type. That value is another Go integer type or a `float32`, which s4ql supports, or text that no column holds for text and a nil `[]byte` for a blob or for NULL, which it refuses. `stmttest.Others` has the other forms of a parameter. The engine's tests get the arguments as the driver would hand them: a named one as its value, and a type that the engine has no value for as a value of no kind.
- **The simulation of the engine** runs the calls of the sequence with their arguments, checks that each commit's annotation holds exactly the arguments that its caller gave, and runs the log in SQLite with the annotations' parameters. The planted bug `annotateNext` annotates each argument plus one.

## Transactions

Status: built for slice 3 of the [roadmap](roadmap.md) on 2026-11-19: transactions that span statements, in `internal/engine` and `internal/core`, and in the driver, in `tx.go` at the root of the module. What slice 3 includes and rejects is in the roadmap, and what an application gets is in the package's documentation. The product owner decided the design. A write transaction takes the place of the single writer when it begins, as SQLite's `begin immediate` does, and holds it until its commit or its roll back. A read-only transaction is a read transaction: it sees the state of its beginning, never writes, takes no place of a writer, and blocks no one. How the engine behaves and how it is tested is in [its README](../internal/engine/README.md#transactions). This item holds the decisions of detail of the engine and of the driver, what is open, and what is not built.

- **Decided by the builder on 2026-11-19, for the lead to confirm:**
  - **The engine has four calls on a connection:** `Conn.Begin`, `Conn.BeginReadOnly`, `Conn.Commit`, and `Conn.Rollback`. `Conn.Close` rolls back a transaction that is open.
  - **The core has five new calls:** `Tx.Serving`, `Tx.Savepoint`, `Tx.Release`, `Tx.RollbackTo`, and `ReadTx.Serving`. One savepoint is open at a time. A commit while a savepoint is open is refused as not committed, with an error that matches `core.ErrInvalid`.
  - **`Begin` waits for the place of the writer as long as its context allows,** with no deadline of its own, and gives the error of the context if the context ends first. On an instance that does not serve it fails as a write of its own does. `BeginReadOnly` is a read transaction on the reader of the connection: it waits for nothing, and fails as a query does. Both fail with `ErrTxOpen` while a transaction is open on the connection, and with `ErrRowsOpen` while the rows of an earlier query of the connection have not ended. When a begin fails, nothing has begun, and the engine logs no event.
  - **A statement in a transaction is checked in this order:** its text and its arguments, as everywhere; the context, whose error it gets if the context has ended; the instance, which must serve now by the clocks, as for a statement of its own; and the rows of an earlier query of the connection, which give `ErrRowsOpen` while they are open. The check of the instance is `Tx.Serving` or `ReadTx.Serving`, and its error matches `core.ErrNoLease` or `core.ErrStopped`. The other calls of an open transaction of the core do not look at the clocks, because the commit of a write transaction is judged by its manifest swap.
  - **A statement that changes the database in a write transaction runs between `Tx.Savepoint` and `Tx.Release`,** on SQLite's `savepoint s4ql_statement`, and is annotated before the release. If it fails, or an operator panics, the engine calls `Tx.RollbackTo`, which restores the cache and what the transaction had recorded of each table for its commit object. So the statement has no effect, the work of the statements before it is kept, and the transaction stays open, as in SQLite. A query takes no savepoint. The reason for the savepoint: a statement can fail after its write, by a lease that is lost before the annotation, by its context, or by a panic of an operator, and its row would otherwise stay in a transaction that then commits.
  - **The engine annotates last, because an annotation cannot be taken back** from its spool file. A roll back to a savepoint before an annotation makes the core fail the transaction, and the engine never makes one. After an error of the cache, the core lets the transaction only roll back: every later statement and the commit fail, and the roll back works.
  - **`create table` and `drop table` are transactional.** The later statements of the transaction see them, and a roll back undoes them. A transaction that changes nothing in the end writes no commit object, and its commit succeeds, which is the core's rule: a create and a drop of the same table, a transaction whose statements all failed, or one that only read.
  - **Every statement of a read-only transaction sees the state of the beginning.** A statement that would write gets `attempt to write a readonly database`, with the code 8 and the extended code 8, as in SQLite under `pragma query_only = 1`. Before it come SQLite's errors of the names, which SQLite gives when it prepares the statement: `no such table`, `has no column named`, and `already exists`, looked up in the state of the transaction. The transaction stays usable. Its commit and its roll back end it and write nothing, and return nil on an instance that has stopped, because there is nothing to commit. The code is the new constant `sqlerr.CodeReadOnly`.
  - **An insert that a read-only transaction refuses sets SQLite's count of changes to 0,** and a create or a drop that is refused there leaves it. The pinned test measured this against SQLite, and `pair.step` of the differential test accepts it.
  - **While the rows of a query of a transaction are open, every statement of the connection fails with `ErrRowsOpen`,** also a write, where SQLite runs it, because the scan holds a statement of SQLite on the connection of the transaction, and the core refuses a change of a table while it scans it. `Commit` and `Rollback` first end the rows that no loop reads, and a later `Rows.All` on them gives nothing.
  - **Rows that a loop over `Rows.All` reads cannot be ended from outside,** while the body of the loop runs or its iterator is suspended. `Commit` and `Rollback` mark them, so that the loop ends at its next row with `ErrTxDone` and reads nothing more. The end of the transaction runs when the loop ends, after the scan of the core has ended: the roll back of a write transaction, or the end of a read transaction. Until then a write transaction keeps the place of the writer, every statement and every begin of the connection fail with `ErrRowsOpen`, and `Conn.Close` gives `core.ErrReaderInUse`. `Rows.Close` after the loop returns nil, if the end worked.
  - **A `Commit` of a write transaction while a loop reads its rows does not commit.** It rolls the transaction back, and fails with an error that matches `ErrRowsOpen` and ends with `so the transaction is rolled back and not committed`. A `Commit` of a read-only transaction ends it then, and returns nil. The reasons: SQLite cannot commit while a statement of the connection reads, because the commit of the core drops temporary tables, which SQLite refuses then. A roll back at once would leave an aborted statement that the loop finishes later, on the write connection, while the transaction of the next writer runs there. A transaction is over when `Commit` returns, so the commit cannot be left to the loop.
  - **With a lease that is lost or an instance that has stopped, the statements fail as a statement of its own does,** and `Commit` gives the error of the core: one that matches `core.ErrNoLease` or `core.ErrStopped`, which means that nothing is committed, or `core.ErrOutcomeUnknown`, as for a statement of its own. An instance that has lost its lease ends the transaction: see the decision below. `Rollback` frees the place of the writer, and returns nil, except after a stop by a local failure, where the roll back in the cache can give its error. The transaction is over when `Commit` returns, with or without an error. `Commit` and `Rollback` on a connection without a transaction give `ErrNoTx`. The spec: "A write transaction that is already open commits only if its manifest swap still succeeds."
  - **`ErrTooLarge` is matched by the error of a commit whose commit object the store refuses as too large,** for a transaction and for a statement of its own. The error also matches `core.ErrTooLarge`, and its message starts with `s4ql: the transaction is too large to commit: `. The tests set the limit to 4 KiB with `simstore.Options.MaxSize`, which the commit object of 100 inserts exceeds.
  - **The commit object holds, in order, the statements of the transaction that succeeded and that write,** each with its arguments. A statement that failed and a query are not kept.
  - **The texts `begin`, `commit`, `end`, `rollback`, `savepoint`, and `release` stay "not supported",** also inside a transaction, and the transaction stays open.
  - **The engine logs the event `transaction` when a transaction ends,** in the style of the event of a statement. Its level is the one that `outcomeOf` gives the error of its commit or its roll back, and Debug for success. Its attributes are `transaction.kind`, `write` or `read_only`; `transaction.end`, `commit` or `rollback`, where a close of the connection is a roll back; `transaction.statements`, every statement that the connection was given meanwhile, also those that failed; `transaction.writes`, those that changed the database, succeeded, and were annotated; `transaction.position`, the state that it began from; `commit.parent` for a write transaction, which joins the core's event of the commit; `outcome`; `error`; and `duration.total`, from the call of the begin, so with its wait for the place of the writer. When a loop reads rows of the transaction at its end, the event is logged when the loop ends and the transaction with it. It has no SQL text and no value. The event of a statement in a transaction has `transaction.kind`, and in a write transaction `commit.parent`, also for a query.
  - **Two new outcomes of an event, both at Debug:** `tx_state` for `ErrTxOpen`, `ErrNoTx`, and `ErrTxDone`, and `too_large` for `ErrTooLarge`. `ErrRowsOpen` is `not_supported`, as `core.ErrReaderBusy` is.
  - **Of the planted bugs of statements of their own, a write in a transaction plants only `skipUnique`.** `ackUnknown`, `checkOutside`, and `keepOpen` are of a statement of its own. `keepRead` is in `Rows.Close`, so it also leaves open the rows of a query in a transaction. Three bugs are of transactions since 2026-11-19, `keepFailed`, `readNewest`, and `rollbackKeeps`; the [engine's README](../internal/engine/README.md#how-it-is-tested) says why the rollback to the savepoint of a failed statement is not one of them yet.
- **Decided by the builder of the driver on 2026-11-19, for the lead to confirm:**
  - **The commit runs within the context given to `BeginTx`.** `driver.Tx.Commit` has no context. `database/sql` gives the driver's `BeginTx` the application's context, and not the one that it derives from it and cancels before it calls the driver's `Commit`. Its documentation says that the context of `BeginTx` is used until the transaction is committed or rolled back. So a commit whose context ends before the instance knows whether the commit is applied gives an error that matches `ErrOutcomeUnknown`, as a statement of its own does. The roll back runs with `context.WithoutCancel` of that context, because `database/sql` rolls the transaction back when the context ends.
  - **The isolation levels `sql.LevelDefault` and `sql.LevelSerializable` are accepted, for both kinds of transaction.** Every other level gives `s4ql: not supported: the isolation level Read Committed`, with the name that `sql.IsolationLevel.String` gives, which is `IsolationLevel(99)` for a level that it does not know. The level is checked before the instance, so a stopped instance gives this error too, and nothing is begun.
  - **`ErrTooLarge` is a public sentinel,** matched through `core.ErrTooLarge`, for the commit of a transaction and of a statement of its own. Its message starts with `s4ql: the transaction is too large to commit: `, and the error matches no other sentinel. In slices 1 to 3 the commit object of a statement of its own holds one row or one table, so a transaction is what reaches the limit of a store.
  - **The engine's `ErrRowsOpen` is "not supported", with three messages.** A statement in a transaction gets `s4ql: not supported: a statement while the rows of a query of a transaction on its connection are open; close the rows first`. A `BeginTx` on a `sql.Conn` whose rows are open gets `s4ql: not supported: a transaction that begins on a connection whose rows of an earlier query are open; close the rows first`. A commit while a loop reads rows of the transaction gets `s4ql: not supported: a commit while the rows of a query of the transaction are read, so the transaction is rolled back and not committed`. Only a call of the driver's own interface makes that commit: `database/sql` closes the rows of a `sql.Tx` before it calls the driver's `Commit` or `Rollback`.
  - **A second `BeginTx` on a `sql.Conn` whose transaction is open gets the engine's `ErrTxOpen` as an ordinary error,** `s4ql: a transaction is open on the connection`, which matches no sentinel. `database/sql` allows the call. SQLite's `cannot start a transaction within a transaction` is not reproduced, because `BeginTx` is no statement. The statements of a `sql.Conn` whose transaction is open run in that transaction, as `database/sql` allows for every driver.
  - **The driver keeps the transaction that is open on its connection.** A `Commit` or a `Rollback` of a `driver.Tx` that is not the open one gives `s4ql: internal error: the transaction has ended`, and changes nothing. `database/sql` makes no such call, because it keeps the state of a `sql.Tx` itself and gives `sql.ErrTxDone`. So the engine's `ErrNoTx` does not reach the application. The engine's `ErrTxDone`, of rows whose transaction ended under a running loop, is given as `s4ql: the transaction of the rows has ended`, and only the driver's own interfaces reach it.
  - **`Rollback` returns nil when the engine's roll back gives nil or an error that matches `core.ErrStopped` or `core.ErrNoLease`.** The engine ends the transaction whatever it returns, and nothing is committed, so `defer tx.Rollback()` is quiet. Another error, such as a busy cache or an internal error, is returned. The engine's roll back gives nil in every case that the tests reach. A roll back after a stop by a local failure whose own roll back in the cache fails is not reached: in a probe of the builder with 300 inserts, while each kind of file operation of `faultvfs` failed, a roll back touched no file. The probe is not kept as a test; the diary of the driver's transactions has it.
  - **The commit of a read-only transaction returns nil, also on an instance that has stopped or does not serve.** It has nothing to commit, and each of its statements was refused or answered as the instance was then. This was open before the driver was built: whether the application gets that nil, or the error of the stop.
  - **`driver.Validator.IsValid` is false while a transaction is open on the connection.** So `database/sql` closes such a connection and does not put it back in the pool, and the close of the engine's connection rolls the transaction back. `driver.SessionResetter.ResetSession` resets nothing and returns nil, never `driver.ErrBadConn`. With both, `database/sql` keeps the connection of a transaction that it rolls back because its context ended.
  - **`IsValid` is also false while rows of the connection are open, and the close of a connection whose rows a loop reads is left to those rows.** Only the driver's own interfaces reach this: `database/sql` closes the rows of a `sql.Tx` before it calls the driver's `Commit` or `Rollback`, and the rows of a connection before it gives the connection back or closes it. Through `sql.Conn.Raw`, an application can commit or roll back while a loop reads rows of the transaction, which leaves the end of the transaction to the rows, and give the connection back before it closes them; the connection then does not go back to the pool, where the next statement on it would be refused for the open rows. The engine's `Conn.Close` gives `core.ErrReaderInUse` while a loop reads, and closes nothing, so the driver's `Close` then returns nil, and the close of the last of those rows closes the engine's connection: its reader, and its transaction, which the close rolls back if it is still open. `TestTx_raw` pins both, after a commit, after a roll back, and with the transaction still open. Decided by the builder of the driver's checks on 2026-11-19, for the lead to confirm.
  - **The close of the connector closes the rows of a connection only while no call of the connection runs in the engine.** It closes every rows that are open from its own goroutine, and the engine's connection is not safe for concurrent use, so under `-race` the close of the rows raced a statement that the application ran on the same connection (`Rows.end` wrote what `Conn.rowsOpen` read). A call of the connection now holds the engine's connection from `conn.enter` to `conn.leave`, and the close of rows by the connector holds it too. While a call holds it, the connector leaves the rows to the call, which closes them when it ends, so the close never waits for a call, which can itself wait for the stop of the instance that the close makes next. `TestTx_instance` and `TestClose` make the overlap 20 times each, in a transaction and outside one. Decided by the builder of the driver's checks on 2026-11-19, for the lead to confirm.
  - **The deprecated `driver.Conn.Begin` begins a write transaction with `context.Background()`,** so it waits for the place of the writer without an end.
  - **The driver has no new event.** Its event `stop_seen` is logged for a `BeginTx` or a commit that is answered with the stop, through the same path as for a statement. A `Rollback` that returns nil for a stop logs nothing. The engine logs its event `transaction`. No value of an argument is in a log, and a test checks the text of the log for one.
  - **The differential test of the driver, `internal/sqlite/crosscheck/drivercheck`, runs transactions on both sides.** The call `begin` begins a write transaction, `begin read-only` a read-only one, each with the isolation level that its text names, and `commit` and `rollback` end it; the calls between run in it. Calls of their own prepare a statement where the transaction began and run it through `tx.StmtContext`, leave the rows of a query open for the next call, and query beside the transaction: on a pinned `sql.Conn`, in the transaction, and through the pool, outside it. mattn ignores `ReadOnly` and every isolation level, so the oracle is opened with `_txlock=immediate`, so that its transactions take the place of the writer when they begin, as s4ql's do, and runs a read-only transaction under `pragma query_only`. Through the pool, a begin while a transaction is open commits it first, because a second write transaction of s4ql would wait for the first. What s4ql refuses by its own rule is checked against the rule and pinned: an isolation level other than the default and serializable, and a statement while rows of its transaction are open, neither of which runs in SQLite, and a second begin on a pinned connection, which SQLite must refuse too, with its own error. So is a statement prepared outside a transaction through the pool whose names only the transaction has, which mattn's Prepare outside refuses and s4ql's, which checks only the text, does not; it is compared with mattn's statement prepared in the transaction, where `database/sql` prepares it again.
- **Decided with the product owner on 2026-11-19: an instance that has lost its lease ends the write transaction that is open, so that it can take the lease back.** The lease task takes the lease and catches the cache up under the writer lock of the core, which a write transaction holds from its begin to its end, so before, an idle transaction kept such an instance from serving until the application ended it. Markus agreed that the instance fails the transaction at once. The spec's sentence "A write transaction that is already open commits only if its manifest swap still succeeds" is to be reworded by the lead with him. Built on 2026-11-19 (diary `docs/diary/2026-11-19-lease-ends-transaction.md`). Decided by the builder, for the lead to confirm:
  - **When:** in `DB.acquire` and `DB.resume`, before the lease task waits for the writer lock (`DB.endForLease`), so when the instance does not hold the lease or does not serve because a commit of it has an unknown outcome. A lease that has only run out by the clocks, while the instance still holds it, ends nothing: a renewal needs no writer lock. So when the store comes back and no other instance has taken the lease, the transaction goes on and can commit. Meanwhile `Tx.Serving` gives an error that wraps `core.ErrNoLease`, so a statement of the engine in the transaction fails with that error, which is temporary, and has no effect; the transaction is not rolled back, and after the renewal its statements work again and its commit holds exactly the statements that succeeded. The calls of the core's `Tx` other than `Serving` do not look at the clocks, and work meanwhile. Tests of `TestLease_openTx` in the core and of `TestConn_leaseLost` in the engine pin this. A transaction in its commit or its roll back is left alone, and its manifest swap decides.
  - **What the transaction gives:** every later call fails with an error that wraps the new `core.ErrTxLeaseLost`, which wraps `core.ErrNoLease`, with the text "the transaction was ended because the instance lost its lease" and the reason in a word, also once the instance serves again. `Tx.Rollback` returns nil. `Tx.Lost` gives the error. In the driver the error matches `ErrNotServing` and no other sentinel.
  - **A call that runs is not cut.** The lease task never uses the connection while a call of the transaction does: it marks the transaction under `DB.mu`, and the last call to leave the connection rolls it back and frees the writer lock (`Tx.leave`). With no call running, the lease task does it at once. A call that starts after the mark fails, and a scan fails at its next row.
  - **Rows of a scan that nobody reads hold the writer lock** until the application reads their next row, which gives the error, or stops them. The scan holds a statement of SQLite on the write connection, which no other goroutine can end safely. So an instance whose application keeps such rows open and untouched still does not serve again until then; through `database/sql`, the rows also end with the context of their query. This is the one case left of the problem.
  - **`DB.Begin` records its transaction under the same critical section that checks that the instance serves,** so a transaction cannot begin unseen by the lease task.
  - **Events:** the core logs `transaction_ended` at Info, Warn if the roll back in the cache failed, with `outcome`, `reason`, `commit.parent`, `transaction.waited_for_call`, and `duration.total` from the mark to the end. The engine's event `transaction` of such a transaction has the outcome `lease_lost`, at Debug, with the error, and `transaction.end` stays what the application called; a statement refused so has the outcome `lease_lost` too.
  - **Tests:** `TestLease_openTx` in the core, `TestConn_leaseLost` in the engine, `TestTx_leaseLost` in the driver. The simulations have callers that hold a write transaction idle while their instance is cut off, and a check that an instance whose transaction is still open serves again once the others are closed: the workload `idling` of the core, with the planted bug `keepIdleTx`, and the workload `idle` of the engine, which cannot plant a bug of the core.
- **Not built:**
  - **A known gap: rows of a scan that nobody reads keep the place of the writer** of an instance that has lost its lease, until the caller reads the next row or stops the scan, because the scan holds a statement of SQLite on the write connection between rows. Meanwhile the instance holds no lease and refuses everything, other instances can take the lease, and `Close` ends the wait. A scan that holds no statement between rows, which seeks again by the last key for each row or each batch of rows, would close the gap. It is not built.
  - Fuzz targets over transactions. The mutation testing of the code of transactions, on 2026-11-19, is in [the README of the runner](../internal/sql/mutation/README.md#the-transactions-of-slice-3).
  - A commit of unknown outcome in a transaction on the real core, in the tests of the engine. `TestConn_writeIn` tests it only against the fake. `TestTx_instance` of the driver reaches one through `database/sql`, with a store that applies the manifest swap and loses its answer.
  - The state "can only be rolled back" of the core without a stop. The tests of the engine do not reach it on the real core, because every real failure of the cache that is not "busy" stops the instance. They reach only the stop.

## The storage core

Status: built in `internal/core` on 2026-11-12 and 2026-11-13, and merged in pull request #12. The reasoning behind its design, with Markus's words, is in [internal/core/README.md](../internal/core/README.md). This item holds what is still open or not built. What its tests do not show yet is in [Tests of the storage core](#tests-of-the-storage-core).

- **Decided by the builder of the core on 2026-11-19, built: the decisions of detail of slice 4 in the core,** with their reasons in [internal/core/README.md](../internal/core/README.md). The core stores -0.0 as 0.0, as SQLite does, and does not refuse it. A text or blob above SQLite's length limit, and a row whose record is above it, is refused with the new `core.ErrTooBig` exactly where SQLite's own table refuses it, and the transaction goes on; the engine is to turn it into SQLite's "string or blob too big". The version of the cache's layout stays 1, because a table of `int` columns is declared as before. `int` and `integer` are two values of `Type`, so that a column is declared again as it was declared.
- **Decided by the builder of the core on 2026-11-20, built: the decisions of detail of slice 6 in the core,** with their reasons in [internal/core/README.md](../internal/core/README.md). A column takes NULL only if its `Column` says `nullable`; the core refuses a NULL in any other column and in the key with `core.ErrInvalid`, in `Tx.Upsert` and `Tx.Insert` before SQLite sees the row, and at replay as a broken log. The cache declares a column that takes NULL `default null`, and every other column outside the key `not null`, and the version of its layout went from 1 to 2: a cache of version 1 is raised to 2 in place when it opens, since none of its columns takes NULL, and a version that reads only version 1 then refuses the cache instead of reading a column that takes NULL as one that does not. Before slice 6 the core took a NULL in any column outside the key, and some of its own tests and of the format's samples wrote one; a log with such a NULL, in a column whose `Column` lacks `nullable`, is now refused at replay, and a cache of version 1 that holds one is refused when it opens. No engine before slice 6 wrote one.
- **Open: a manifest that is damaged on its way.** A commit object is checked against its name, and the manifest has no such check. A damaged manifest that still parses would be believed, and the swap that takes the lease would write it back. The store's contract promises content that is not changed. Whether the manifest needs a checksum of its own is not decided.
- **Not built: a refusal of a write as too large that is not `400 EntityTooLarge`.** `internal/store/s3store` maps only that answer to `store.ErrTooLarge`. A store or a proxy in front of it that refuses a large write in another way, such as with HTTP 413, gives an unknown outcome, and the commit uploads the same bytes again until the caller gives up. Nothing is committed wrongly, but the caller gets the wrong error, and each attempt may upload gigabytes. Found on 2026-11-18 with the limits of the stores: Amazon S3 takes 5 GiB in one write, Cloudflare R2 5 MiB less, Ceph what it is configured for, MinIO 5 TiB; Tigris documents none.
- **Not decided: catch-up downloads every missing commit object twice.** It reads each one on the walk back through the log, and again when it applies it. A spool of the walk could remove the second download.
- **Known: `Reader.Close` closes its SQLite connection while it holds `DB.mu`,** so a close that stalls on a slow disk holds up every call of the instance and the lease task meanwhile. `DB.Reader` opens without the mutex since pull request #48, and the review of that pull request asked for the close to follow. A builder tried it on 2026-11-19: the close marked the connection closed and counted itself under the mutex, closed it without the mutex, and `DB.Close` waited for the count, as it waits for the readers that are opening. It kept every life-cycle test and the simulation passing, and a new test showed the wait. But it let the close of a reader run at the same time as the closes of `DB.Close`, and SQLite then sometimes left the write-ahead log behind: the close of the last connection deletes it only if that close can lock the cache alone, and two closes at once can keep each other from that. `TestClose` "should refuse a query that comes while the close closes the rows that are open, before the instance has stopped" in the root package, whose `database/sql` closes idle connections while the connector closes the instance, found a log left in 21 of 300 runs, 3 of 100 under `-race`, and once in a run under the address sanitizer, against 0 of 300 before. A log that is left is no loss, because the next start recovers from it, but the tests take a log that is left for a connection that is left. A fix would close the connections one at a time under a lock of their own, which `DB.closeIdleLocked` would then wait for while it holds `DB.mu`. That is no longer simple, so the code was left as it was. The diary is `docs/diary/2026-11-19-reader-follow-ups.md`.
- **To consider: a spare that keeps its cache up to date.** Today an instance without the lease catches up its cache only when it gets the lease, so a spare that waited long has the whole log since its start to download and apply before it serves. Markus asked on 2026-11-19: "Should the cache keep up to date on a spare instance even when it doesn't have the lease (but still reject reads and writes)?" It would shorten the time until a spare serves after it takes over, at the cost of reads from S3 while it waits. Not decided.
- **Not decided: a connection whose close fails.** `DB.Close` marks the instance as closed before it knows that the connections closed, so a connection whose close fails is never closed. Since the fix of the scan, only an `iter.Pull` of a scan without its `stop` can cause that.
- **A possible later addition: S3's timestamps could shorten the wait after a crash.** They would be switched on only for a store that has been checked. They help how fast an instance serves, not safety. Why S3's clock is not safe enough to rest the lease on is in [research/s3-clock.md](research/s3-clock.md).
- **Open: OpenTelemetry, traces, and metrics.** The core, the engine, and the driver log structured events through `log/slog`, to the logger of `s4ql.Options`, and nothing else. The lead decided on 2026-11-19 to leave traces and metrics out of the first round of the driver.

## The memory-mapped wal-index

Status: open. A local I/O failure on the cache stops the instance, as the spec says, and `internal/core` does that. The failure must arrive as an error for that.

- **Open: the wal-index is memory-mapped.** The build sets `SQLITE_MAX_MMAP_SIZE=0`, so SQLite never memory-maps the database file, and an I/O error there arrives as an error code. In WAL mode SQLite still memory-maps its shared index, the `-shm` file: "The wal-index is implemented using an ordinary file that is mmapped" (https://sqlite.org/wal.html). An I/O failure on a memory-mapped file arrives as a signal that kills the process, not as an error that SQLite can handle (https://sqlite.org/mmap.html). How to handle this is not designed.
- **A possible answer, parked: SQLite's `unix-excl` VFS.** Markus on 2026-11-11: "park it in TODO.md for now as a potential thing". It keeps the wal-index in ordinary memory and creates no `-shm` file, which would close the gap above. It also locks every other process out of the cache file while our process has it open, including the `sqlite3` shell, so a live cache cannot be inspected from outside. Several connections in one process still work. It does not change the file format, so it can be switched on or off at any time, and `sqlite.OpenVFS` opens a database through a VFS by its name. To find out before deciding: what happens after a crash (whether the operating system releases the lock, and that the next start recovers from the WAL), and a test that no signal arrives on a disk error. It exists on macOS and Linux only. Details are in [research/sqlite-busy.md](research/sqlite-busy.md).

## Storage formats

Status: the manifest and the commit object are built in `internal/format`, with the schema in `proto/s4ql/v1/commit.proto`, and replay into the cache is built in `internal/core`. One check in CI is not built, and two questions are open. The reasons behind the formats are in [internal/format/README.md](../internal/format/README.md).

- **`buf breaking` under its `WIRE` rules is set up when version 1 is settled.** While the formats are drafts, a change to the schema may break old commit objects.
- **Nothing produces an `UpsertRows` with only some columns yet.** The format writes and reads it, the samples cover it, and replay applies it. It is first produced when a slice of the roadmap brings `update`.
- **Replay in later slices applies results only.** When a slice brings triggers, cascades, or foreign keys, replay must not run triggers or cascades. Foreign keys cannot be checked row by row at replay, because a commit object holds the net effect and not the order of the statements.
- **Decided by the builder of the format and the core on 2026-11-19, built: a commit object never holds -0.0 in a row or a primary key,** and a reader and the writer refuse it there as malformed, because a column of the cache holds 0.0 for it. A parameter of an annotation keeps -0.0 as the caller gave it. The writer also refuses a NaN, an infinity, and text with NUL in a parameter, which s4ql never stores; the reader does not check annotations. The reasons are in [internal/format/README.md](../internal/format/README.md).
- **Decided by the lead on 2026-11-20, for Markus to confirm, built: `Column` has `bool nullable = 3`,** which says that the column takes NULL. It is `nullable` and not `not_null`, so that the commit objects written before it, in which no column takes NULL, read right without it. The writer and the reader refuse a create table whose primary key holds a column with `nullable`, and a NULL in a primary key of a `DeleteRows`. They cannot refuse a NULL in a row of an `UpsertRows` for a column that does not take NULL, because the batch does not hold its table, so the core does that. The format's version stays 0. The reasons are in [internal/format/README.md](../internal/format/README.md).
- **Open: whether a new lease holder keeps the unknown fields of the old lease.** `Manifest` keeps the unknown fields of a `Lease` only while the same value is changed in place, and a new `Lease` has none. The core does not keep them: a new holder writes a new lease entry.

## The S3 client and S3's checksums

Status: built in `internal/store/s3store` on 2026-11-13. It passes the conformance suite against the project's Tigris bucket. What was found about Tigris, and what rests on AWS's documentation alone, is in [internal/store/s3store/README.md](../internal/store/s3store/README.md). This item holds what is still open.

Markus asked: "Maybe S3 already knows the hash of its objects?" It does. On upload, the client signs the request with the commit object's SHA-256 as the hash of its payload and sends it as the object's checksum, and the store refuses content that does not match it.

- **Open: the check on download is not the one that was agreed.** The agreed bullet was: "On download, the client compares the checksum that S3 returns with the name, before it reads the body." The builder of the client did not add a checksum to `store.Store.Get`. The client asks the store for the checksum that it holds, and the SDK compares it with the content as it is read, so a read of content that does not match it fails at its end. A comparison with the name before the body would need the name in the interface, and it would only catch an object stored with another checksum, which the check on upload rules out for every object that s4ql writes. The reader of a commit object reads to the end and checks the name anyway. Markus decides whether that is enough.
- **Not checked: AWS, and other stores than Tigris.** There are no AWS credentials. The spec asks three things of a store, and checksums are not among them, so a store that does not check the payload's hash still works, without the second guard.

## Vendoring s4ql

Status: open, not fixed.

A module that vendors s4ql with `go mod vendor` cannot build, because Go vendors only directories that hold Go packages and so drops `internal/sqlite/c/`, which holds the SQLite C code. It is not fixed, because nothing depends on s4ql yet.
